# 一、评审强制原则（必须遵守）

1. ❗ 不允许抽样评审，必须覆盖整个代码仓库（所有模块、所有文件）
2. ❗ 所有结论必须基于实际代码证据（文件路径 + 代码片段）
3. ❗ 所有架构类问题必须对应清单中的检查项（如 R1.1 / R3.6 等）
4. ❗ 不允许“猜测”或“假设代码存在”，无法确认必须标注“不确定”
5. ❗ 不允许泛泛而谈，每一个问题必须可定位、可修改

---

# 二、评审执行方式（核心）

本次评审必须分三层执行：

---

## 第一层：架构红线审计（强制逐条执行）

严格按照 架构评审可执行清单.md，对 R1～R16 所有检查项逐条执行验证。

输出格式必须如下：

【示例】
R1.1 ❌
证据：

* 文件：xxx/booking-core/src/.../BookingService.java
* 代码：import org.apache.kafka...

问题说明：core 模块直接依赖 Kafka，违反插件隔离红线

---

要求：

* 每一条必须输出 ✅ 或 ❌
* ❌ 必须附带证据
* 不允许跳过任何一条
* 必须标明严重等级（Zero / High / Medium / Low）

---

## 第二层：工程质量与隐性风险审计

基于以下 14 个维度，对代码进行穷举分析（必须给证据）：

1. 是否存在越架构红线的代码（补充 R1~R16 未覆盖的情况）
2. 是否存在隐性依赖或耦合（跨插件、跨层、绕过 Runtime）
3. 是否存在非最佳实践或硬编码（URL、tenantId、magic number 等）
4. 是否存在潜在性能问题（N+1、阻塞调用、无缓存、线程问题等）
5. 是否存在层次错位（契约写在实现层、UI写逻辑等）
6. 开源准备度（brix）：是否全部英文（类名、注释、提示）
7. 目录结构或命名不符合最佳实践
8. 是否存在无用代码/脚本/历史遗留文件
9. 是否做到前后端完全分离（无 fetch 混入 UI 层）
10. 是否做到前后端架构对齐（契约→适配器→Host→基础设施→插件）
11. sdk-api 已声明但未实现或未启用的能力
12. 关键链路是否真正打通（多租户 / i18n / event / auth 等）
13. 代码整体质量评分（分维度评分）
14. 是否符合国际大厂最佳实践（给出具体对标建议）

---

输出要求：

每一个问题必须包含：

* 问题描述
* 文件路径
* 代码片段
* 违反原则（蓝图 or 清单项）
* 风险说明
* 修改建议（必须可落地）

---

## 第三层：链路级验证（必须真实检查）

1. 多租户链路
   （JWT → TenantResolver → TenantContext → DB/业务）

2. 事件链路
   （Plugin A → EventBus → Plugin B → traceId贯通）

3. 前端调用链
   （View → Hook → Repository → Capability → Backend）

4. i18n链路
   （资源 → 注入 → UI）
