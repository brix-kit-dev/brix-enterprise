## 1. 改造原则（红线，先于任何代码动作）

> 沿用前端稳定性 v1.0 §1，本计划新增 R-8 ~ R-10。

| # | 原则 | 反模式 |
|---|---|---|
| R-1 | 所有新能力先定 **Layer 2A 契约**，再在 **Layer 2C** 实现 | 直接在 Host / 插件写实现 |
| R-2 | Host 仍然 **极薄**：只组装、零业务、零工具 | Host 内出现 Service/Controller/if-else |
| R-3 | 插件 **0 行**直 import `@mui/material` / `@brix-sdk/platform-design-tokens` / `localStorage` / `fetch` | "临时方便" |
| R-4 | 视角切换（PlatformAdmin ⇄ TenantActor ⇄ TenantSubject）**必须后端重签 JWT** | 纯前端 setTenantId 后并行调接口 |
| R-5 | 任何新增 Capability 必须配套 **ESLint 规则 + 单测** | "先用着，规则后补" |
| R-6 | **不破坏现有契约签名**，只做加法（向后兼容） | 改 `UIAdapter` 现有 41 组件 props |
| R-7 | **不引入新依赖**（除 testing 必需） | 装新 UI 库 / 状态库 |
| **R-8** | **脚手架产出 = 现网最佳实践插件骨架**，CI 必须跑 scaffold smoke | CLI 产物与现网代码风格不一致 |
| **R-9** | dev/standalone 入口禁止内嵌 mock 实现替代 Capability，需复用真实 Adapter | 在插件源码里手写 mock fetch / mock auth |
| **R-10** | 所有 Zero Tolerance 红线检查项必须自动化（grep + ArchUnit + ESLint），评审清单与 CI 一致 | 仅靠人工评审 |
| **R-11** | IntegrationEvent 的 `tenantId` / `traceId` / `schemaVersion` 必须进入基类 metadata，不能只放 payload 字段 | `super(SOURCE_MODULE)` 后在子类字段里另存 `tenantId` |
| **R-12** | Host 只能启动和装配，不能硬编码业务/基础设施扫描策略；扫描/发现规则必须由 starter、manifest 或 auto-configuration 承担 | Host `@ComponentScan("io.brix.enterprise.app")` / `@EntityScan("io.infra.adapter")` |

### 3.0 Z-0：Host 扫描边界收敛，恢复极薄 Host

#### 问题

#### 设计

| 步骤 | 文件 | 内容 |

| 4 | `host-shell-embedded` | 修正 `io.brix.enterprise.app.app`，并用契约测试证明 embedded / standalone 对插件发现行为一致 |
| 5 | CI | grep 禁止 Host Shell 出现 `io.brix.enterprise.app`、`io.infra.adapter`、`io.runtime.orchestrator` 的硬编码扫描字符串 |

#### 验收标准
- [ ] `host-shell-standalone` 与 `host-shell-embedded` 启动类内不再出现业务/infra 硬编码扫描包名
- [ ] Standalone Host 仍能加载现有插件与 infra capabilities
- [ ] Embedded Host 修正包名后启动 smoke 通过
- [ ] 故意在 Host 启动类新增 `@ComponentScan("io.brix.enterprise.app")` → CI 立即红

#### 影响现有功能
- ⚠️ 影响启动发现路径，必须先以 AutoConfiguration / manifest 双跑验证，再删除旧扫描。

### 3.3 Z-3：IntegrationEvent tenant metadata 与消费者幂等闭环

#### 问题
- 多个 IntegrationEvent 子类有业务字段 `tenantId`，但构造函数仍调用 `super(SOURCE_MODULE)`，没有初始化基类 `IntegrationEvent.tenantId`。代表文件：`CaseCreatedEvent`、`AvatarUploadedEvent`、`MessageSentEvent`、`MessageReadEvent`、`ComplianceCheckCompletedEvent`。
- `CaseEventHandler` 的 `isEventProcessed()` 永远返回 `false`，`markEventProcessed()` 为空，Kafka / Outbox 至少一次投递下会重复执行业务副作用。

#### 设计

| 步骤 | 文件 | 内容 |
|---|---|---|
| 1 | `*-api/**/*Event.java` | 所有带租户语义的 IntegrationEvent 改为 `super(SOURCE_MODULE, tenantId)` 或 `super(SOURCE_MODULE, version, tenantId)` |
| 2 | `runtime-sdk-api/IntegrationEvent.java` | 补单测：payload-only tenantId 不应被视为 metadata 已设置；tenant-aware constructor 必须设置基类字段 |
| 3 | `case-core/.../CaseEventHandler.java` | 使用 StateStoreCapability 或数据库唯一键实现 `eventId + handlerId + tenantId` 幂等记录 |
| 4 | `infra-adapter-kafka-outbox` / `infra-adapter-simple` | 发布前强校验 `eventId`、`tenantId`、`traceId`、`schemaVersion` 非空，并结构化日志输出 |
| 5 | CI | grep / ArchUnit 禁止 tenant event 构造函数出现裸 `super(SOURCE_MODULE);`；消费者 handler 必须引用 StateStore 或 IdempotencyStore |

#### 验收标准
- [ ] `enterprise-solutions/**/*Event.java` 中所有租户事件基类 `getTenantId()` 有值
- [ ] `CaseEventHandler` 重复消费同一 `eventId` 只执行业务一次
- [ ] EventBus 发布缺失 `tenantId` 的 IntegrationEvent 时 fail-fast，并输出结构化错误
- [ ] 故意新增 `super(SOURCE_MODULE);` 的租户事件 → CI 立即红

#### 影响现有功能
- ⚠️ 会改变部分事件序列化 metadata，需回归 Kafka/Outbox 与 simple event bus 双路径。

### 3.4 CI-A：架构 grep + scaffold smoke 接入 CI

#### 设计
在 `brix/.github/workflows/architecture-check.yml` 与 `brix-enterprise/.github/workflows/architecture-check.yml` 各加 3 个 job：

```yaml
# brix-enterprise 仓
red-line-grep:
  steps:
    - name: Plugin core MUST NOT depend on infra
      run: |
        ! grep -rE 'spring-(kafka|data-redis)|rabbit|jms|minio|elasticsearch' \
              packages/@brix/enterprise-solutions/**/*-core/pom.xml
    - name: Plugin core MUST NOT contain REST/Listener annotations
      run: |
        ! grep -rE '@RestController|@KafkaListener|@RabbitListener|@JmsListener' \
              packages/@brix/enterprise-solutions/**/*-core/src/
    - name: No cross-plugin import
      run: |
        ! ./scripts/check-cross-plugin-import.sh   # 详细脚本
    - name: Host MUST NOT hardcode plugin/infra scan packages
      run: |
        ! grep -rE 'io\.brix\.enterprise\.app|io\.infra\.adapter|io\.runtime\.orchestrator' \
              packages/@brix/enterprise-host/**/ShellApplication.java
    - name: IntegrationEvent tenant metadata MUST NOT be payload-only
      run: |
        ! grep -rE 'super\(SOURCE_MODULE\);' \
```

## 4. Phase 1 — 红线裁决 + 残留清理

### 4.1 H-1：R1.1 JPA / Spring stereotype / 事务边界红线条款裁决

#### 问题
11 个 plugin-core 的 `pom.xml` 都引入 `spring-boot-starter-data-jpa`，pom 注释声称"JPA 属于持久化能力的标准接口"，但架构评审清单 R1.1 标记 Zero Tolerance。两边定义不一致。

补充评审差异：问题不只在 Maven 依赖。部分 `*-core` 内存在 `@Repository`、`@Service`、`@Transactional` 等 Spring stereotype / transaction 边界。H-1 必须同时裁决“plugin-core 是纯领域 core，还是 application core”。如果仍定义为纯领域 core，则这些 stereotype 也应迁移到 application/server；如果采用方案 A，则必须在蓝图中明确 `plugin-core` 的语义是“application core + persistence contract”，而不是纯领域层。

#### 推荐方案：方案 A（最小变更，接受现状语义）
1. **更新 v3.0.9 蓝图 §9 红线表**：追加例外
   > **R1.1 例外**：`spring-boot-starter-data-jpa`、`jakarta.persistence-api`、`jakarta.transaction-api` 视为持久化标准契约，允许 plugin-core 直接依赖；但仍禁止 `spring-boot-starter-data-jdbc`、`mybatis-spring-boot-starter`、`spring-data-redis`、`spring-kafka`、`spring-data-mongodb`、`spring-boot-starter-data-elasticsearch` 等基础设施实现绑定。
2. **新增 Core 语义说明**：若采用方案 A，蓝图必须写明 `plugin-core` 允许承载 application service、Spring Data Repository interface、transaction boundary；但禁止 Controller、Listener、外部 SDK client、infra adapter implementation。
3. **更新 [架构评审可执行清单.md](架构评审可执行清单.md) R1.1**：与蓝图同步，并把 `@Service` / `@Transactional` 的允许范围写入清单。
4. **ArchUnit 规则 [`BrixArchitectureRules.pluginProfile()`]**：保留对其他基础设施 import 的禁用，新增白名单 `jakarta.persistence.*`；`@Transactional` 仅允许在 `..core..service..` 或明确的 application service 包下。
5. **Maven Enforcer**：`bannedDependencies` 排除 `spring-boot-starter-data-jpa`，但保留对 `mybatis`、`spring-data-redis`、`spring-kafka` 的封禁
6. plugin-core pom 注释统一为英文 + 引用蓝图章节号

#### 备选方案：方案 B（语义最纯，工程量大）
- 在 plugin-core 定义 `XxxPersistencePort` 纯领域接口，把 `extends JpaRepository` 与 `@Entity` 移到 plugin-server
- 工程量：11 插件 × 5~10 文件，需要 Phase 1 → Phase 2 间停产新业务

> **建议采用方案 A**。理由：JPA Repository 接口本身就是抽象，不绑定任何特定数据库；移到 server 层会反而把"领域聚合根 + 仓储抽象"切碎，破坏 DDD 一致性；国际大厂（Spring 官方 reference、Netflix DGS、Shopify 等）皆把 JPA 接口视为持久化契约。

#### 验收标准
- [ ] v3.0.9 蓝图 §9 与 [架构评审可执行清单.md](架构评审可执行清单.md) R1.1 文字一致
- [ ] 蓝图明确 `plugin-core` 语义：纯领域 core 或 application core 二选一，不再混用口径
- [ ] ArchUnit 测试在所有 11 plugin-core 通过
- [ ] Maven Enforcer 在 plugin-core 加 `spring-data-redis` 仍能 fail-fast
- [ ] 故意在 plugin-core 新增 `@RestController`、`@KafkaListener`、`io.minio.*`、`spring-data-redis` → CI 立即红

#### 影响现有功能
