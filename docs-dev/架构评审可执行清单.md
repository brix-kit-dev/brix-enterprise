## 使用说明

1. **评审时**：将整个清单交给 AI，要求"按照此清单逐条执行验证命令，每条给出 ✅/❌ 结果和具体证据"
2. **维护时**：每次评审发现新问题类型，必须追加一条新检查项（附验证命令）
3. **自动化时**：标记 `[可CI化]` 的检查项应优先转为自动化脚本

### R3. 所有跨插件通信必须可观测

> 蓝图明确要求"所有跨插件通信必须可观测"，此为硬检查（Zero tolerance），不达标即阻塞。

| ID | 检查项 | 验证命令 | 容忍度 |
|:---|--------|----------|:------:|
| R3.1 | IntegrationEvent 均携带 traceId | `[可CI化]` 检查事件基类（`IntegrationEvent`/`BaseEvent`）是否有 `traceId` 字段且标记为 `@NonNull`；检查 EventBusCapability 实现的 `publish()` 方法是否在事件无 traceId 时自动从当前上下文注入 | Zero |
| R3.2 | 事件发布/消费有结构化日志 | `[可CI化]` 检查 EventBus 实现中 `publish()` 和 `subscribe()` 路径是否有 `log.info`/`log.debug` 记录事件名、来源插件、目标插件、traceId；日志格式需包含 `eventName`、`sourcePlugin`、`traceId` 字段 | Zero |
| R3.3 | 事件发布/消费有指标埋点 | 检查 EventBus 实现中是否有 Micrometer Counter/Timer（如 `meterRegistry.counter("brix.event.published")`）或前端等效的性能指标采集 | Zero |
| R3.4 | 关键跨插件链路有端到端追踪 | 检查 Capability 调用链（如 Plugin A → EventBus → Plugin B → HttpCapability → Plugin C）是否通过 traceId 串联；验证 `ObservabilityCapability` 或 OpenTelemetry 集成是否覆盖 EventBus 和 HttpCapability 的出入口 | Zero |
| R3.5 | 前端跨插件事件同样可观测 | 检查前端 `EventBusCapability` 实现中 `publish()`/`subscribe()` 是否有 console.debug 或 ObservabilityCapability 记录，至少包含 eventName、sourcePlugin、traceId | Medium |
| R3.6 | 事件元数据完整 | `[可CI化]` 检查事件基类（`IntegrationEvent`/`BaseEvent`）必须包含以下字段且均为 `@NonNull`：(1) `eventId`（全局唯一，UUID） (2) `traceId`（链路追踪 ID） (3) `tenantId`（租户标识） (4) `schemaVersion`（事件 Schema 版本号，用于消费端兼容性判断）。验证：EventBusCapability `publish()` 在任一字段缺失时抛出 `IllegalArgumentException` 或自动补全 | Zero |
| R3.7 | Retry / DLQ 指标可观测 | 检查 EventBus 实现（含 Kafka/RabbitMQ adapter）中：(1) 消费失败重试次数有 Micrometer Counter（如 `brix.event.retry.count`） (2) 进入 DLQ（Dead Letter Queue）的事件有独立计数指标（如 `brix.event.dlq.count`） (3) 最终失败率可通过 `brix.event.consumed.failure` / `brix.event.consumed.total` 计算 (4) DLQ 积压数量可通过告警阈值触发报警 | Zero |
