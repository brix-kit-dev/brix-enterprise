# Brix v3.0.10 运行壳架构模型升级改造计划

> 日期：2026-07-24  
> 类型：架构改造计划  
> 输入基线：`Brix-底层架构摸底评审报告-2026-07-22.md` 第 3 章、`v3.0.10-运行壳架构设计蓝图.md`  
> 权威状态：本计划服从 v3.0.10 根蓝图 Freeze Candidate；不得自行创造或覆盖架构裁决  
> 当前模型：v3.0.9 兼容实现，`RuntimeContext + Spring AutoConfiguration + AbstractModule`  
> 目标模型：v3.0.10 根模型，`BrixPlugin + PluginContext + ServiceLoader + Ultra-thin Host`  
> 首轮商业样板：仅改造 `app-tenant`，其他商业插件暂不迁移  

---

## 1. 改造目标

本计划只解决“架构模型从 3.0.9 升级到 3.0.10”的根模型迁移，不在同一阶段改造 Bootstrap 到首位超管的业务流程。

目标状态如下：

```text
Ultra-thin Host
        │
        │ calls Runtime Shell Bootstrap API
        ▼
L2B Runtime Orchestrator
        │
        │ ServiceLoader<BrixPlugin>
        ▼
tenant-server 中唯一 BrixPlugin provider
        │
        │ configure() 只登记 Handler Factory
        ▼
Runtime 在 B2 全局屏障后以 PluginContext 创建 Handler
        │
        │ onStart() 成功、B3 完成后
        ▼
L2B Dispatcher 原子发布完整 Host 路由快照
```

首轮验收只要求 `app-tenant` 在该模型下跑通商业插件业务闭环：

1. Host 通过 v3.0.10 Runtime Bootstrap 启动；
2. Runtime 通过 `ServiceLoader` 发现 `tenant-server` 的唯一 `BrixPlugin`；
3. `tenant-server` 的 `plugin-manifest.yaml` 被加载、校验并与 provider 实现一致；
4. required Capability 缺失时启动失败；
5. Runtime 依次完成 P0-P3，并在 B0-B3 Host 全局屏障下创建、启动和发布插件；
6. required Capability 满足且 `tenant` 插件进入 `STARTED`、路由已发布、health/依赖满足时，插件 readiness 为 true；
7. Tenant Endpoint 只能经 Manifest `endpoints.provides` + Handler Factory + L2B Dispatcher 暴露并完成租户列表、详情和创建入口的最小闭环；
8. required Plugin/Platform Operational Module 运行期进入 `FAILED -> STOPPED` 时，Standalone Host 受控非零退出；Embedded Host 通过 fatal callback/future 通知宿主重建；
9. 不迁移 `booking/case/products/partners/messenger/contracts/storage/identity/carousel/intake` 等其他商业插件。

---

## 2. 不做范围

本轮不做以下事项：

1. 不批量迁移所有 `app-*` 插件；
2. 不把 v3.0.10 扩展为多 ClassLoader、OSGi、PF4J 或热升级模型；
3. 不新增运行期下载、安装、卸载插件；
4. 不重写多租户 v3.1.3 数据模型；
5. 不在本阶段修复 Bootstrap 到首位超管的业务语义；
6. 不修改已发布 Flyway 迁移；
7. 不把平台超管 operator 建模为租户成员；
8. 不把旧 `RuntimeContext` 在全仓一次性删除。

Bootstrap 到首位超管流程必须在本计划验收后单独进入下一阶段，因为该流程依赖新的 Host 启动期校验、插件 readiness、Capability 解析和身份/租户边界守护。

## 3. 当前差距

| 领域 | 当前实现 | v3.0.10 要求 | 改造结论 |
|---|---|---|---|
| 插件入口 | Spring `@Component` / `@AutoConfiguration` / `AbstractModule` | `{name}-server` 中唯一 `BrixPlugin` | 新增 SPI 与样板 provider |
| 能力入口 | `RuntimeContext` / `CapabilityRegistry` 可被插件侧感知 | `PluginContext.require/find(...)` 是插件唯一入口 | L2A 新增 `PluginContext`，旧入口仅供未迁移插件兼容 |
| 插件发现 | Maven 依赖 + Spring 自动配置 | Host 组装依赖 + Runtime `ServiceLoader` 发现 | L2B 新增 ServiceLoader discovery |
| Manifest | `plugin-manifest.json` 与旧 `module-manifest.yaml` 并存 | 唯一 `META-INF/brix/plugin-manifest.yaml` + strict schema | `app-tenant` 切换后删除旧声明，禁止双 SSoT |
| Host | `SpringApplication.run` 后由 Spring 条件装配 | Host 只调用唯一 bootstrap API | Host 接入 Runtime bootstrap，业务逻辑仍不进 Host |
| 启动顺序 | Spring bean 初始化顺序隐式决定 | P0-P8/O0-O8 局部管线 + B0-B3 Host 全局屏障 | Runtime 冻结候选集合、DAG 和 Host 路由快照 |
| 平台运维模块 | 无唯一装配入口 | descriptor + L2B internal ServiceLoader provider + Composition required/optional | 本轮落地 SPI/Schema/契约测试，不实现平台超管业务 |
| readiness | Spring actuator 默认健康为主 | Registry READY + required plugins/operational modules 派生 readiness | 新增 Runtime 聚合与 fatal Host 行为 |
| 守护 | CI 与 docs-dev 仍引用 v3.0.9 / RuntimeContext | v3.0.10 红线 R17.9 等 | 先加 tenant-only 门禁，再推广 |

设计要求：

1. `BrixPlugin` 和 `PluginContext` 位于 L2A，不依赖 Spring、L2B、Adapter 或业务类型；

3. Capability 缺失时 required fail-fast，optional 返回空或抛可识别异常，但不得 NPE；
4. `RuntimeContext` 在兼容期可以继续存在，但新守护不得鼓励继续使用。

设计要求：

1. L2B 可以依赖 L2A，但不得依赖任何商业 `app-*` 实现；
2. ServiceLoader 只发现 `BrixPlugin` provider，不通过 Spring 扫描寻找插件；
3. Runtime 内部 MAY 使用 Spring 管理非业务基础对象，但所有 HTTP Endpoint 必须经唯一 L2B Dispatcher；不得保留 Spring Controller 自动发布路径；
4. H3 只能读取 B0 已冻结且通过 P0/O0 的 descriptor；B2 前禁止创建 Handler，B3 前禁止发布路由；
5. 首次发布必须把全部 surviving Plugin/Operational Endpoint 作为一个不可变 Host 路由快照原子替换；
6. required module 启动失败必须阻断 Host readiness；运行期终态失败必须触发 Standalone 非零退出或 Embedded fatal callback/future；
7. `CapabilityRegistry` 对插件和 operational module 均不可见，插件只拿 `PluginContext`，operational module 只拿受限 `OperationalContext`。

`TenantPlugin` 职责边界：

1. `configure(PluginBootstrapContext)` 只按 Manifest `handlerId` 登记 Handler/Task Factory；
2. Manifest 由 Runtime 按 provider artifact 读取，`TenantPlugin` 不提供 `manifest()` 或 descriptor getter；
3. Factory 只通过参数 `PluginContext.require/find` 获取已声明 Capability；
4. `onStart(PluginContext)` 只启动已经绑定的受管资源，不注册 Handler、Endpoint 或订阅；
5. 不直接创建数据库连接、Kafka client、Redis client；
6. 不调用 Spring `ApplicationContext.getBean(...)` 获取平台能力，也不依赖 Spring 自动发布 Endpoint；
7. `health()` 只报告插件自身健康，不替代 Host readiness。

## 5. 分阶段实施计划

### 阶段 0：冻结改造基线

目标：停止旧模型继续扩散，明确只迁移 `app-tenant`。

任务：

1. 确认两个仓库基线 commit 和 working tree；
2. 标记当前 `RuntimeContext/AbstractModule/module-manifest.yaml/plugin-manifest.json` 为 legacy；
3. 建立 tenant-only 构建/Profile 选择并固定使用 v3.0.10 主链；不得在同一 tenant 制品中保留运行期旧模型回退开关；
4. 在 CI 中新增 tenant-only 检查 job，不影响其他插件；
5. 明确后续 Bootstrap→首位超管流程不进入本阶段。

产出：

1. 基线记录；
2. tenant-only 验证 profile；
3. legacy 清单；
4. 回滚策略。

退出条件：

1. `app-tenant` 以外插件没有被修改；
2. CI 可单独执行 tenant-only job；
3. 文档索引不再把 v3.0.9 作为活动基线。

### 阶段 1：落地 L2A SPI

目标：让 v3.0.10 的 `BrixPlugin/PluginContext` 成为真实编译契约。

任务：

1. 新增 `io.runtime.sdk.plugin.BrixPlugin`；
2. 新增 `PluginBootstrapContext`、`HandlerFactory`、`EndpointHandler`；
3. 新增只含 `require/find/pluginIdentity` 的 `PluginContext`；
4. 新增 `BrixHealth`、`PluginLifecycleState`，并验证不存在 READY 生命周期状态；
5. 将 `RuntimeContext`、`AbstractModule`、`LifecycleCapability` 标记为 legacy；
6. 增加 SPI 恰有四个方法、无 `manifest()`、无容器类型的 ABI/契约测试；
7. 更新 `runtime-sdk-api/pom.xml` 描述。

退出条件：

1. `runtime-sdk-api` 单测通过；
2. 新 SPI 不依赖 Spring、L2B、L2C、L0；
3. 旧 API 仍可编译，保证其他插件暂不迁移。

### 阶段 2：冻结 Plugin/Operational Descriptor 体系

目标：先让 P0/O0 有唯一、可校验的输入，再允许 Runtime 构建 H3 依赖图。

任务：

1. 升级 Plugin Manifest Schema 并支持唯一 `META-INF/brix/plugin-manifest.yaml`；
2. 新增唯一 `META-INF/brix/platform-operational.yaml` Schema；
3. 统一 `runtime`、`modules`、`endpoints.provides`、`capabilities.required/optional`、`queries/commands/events`；
4. 冻结 Platform Operational Module id、runtime range、internal dependency、特权 allowlist 和 Endpoint 字段；
5. 旧 JSON 兼容解析只能服务未迁移插件；同一 artifact 出现 JSON/YAML 双份声明必须构建或启动失败；
6. 增加 descriptor/provider artifact 关联、重复 ID、保留命名空间和签名/attestation 校验；
7. 更新 architecture-guard 规则。

退出条件：

1. Plugin/Operational descriptor strict schema 校验通过；
2. descriptor 中 id/version 与 provider artifact 一致；
3. 缺失、重复、一个 artifact 多 provider 或 `/api/platform/**` 越权声明均 fail-fast；
4. H3 的所有输入都能由 P0/O0 校验并在 B0 冻结；
5. 旧 `module-manifest.yaml` 不再被 tenant-only job 当作活动裁决源。

### 阶段 3：落地 L2B ServiceLoader、全局屏障与 Bootstrap

目标：Runtime 基于阶段 2 已验证的 descriptor 发现、解析、启动模块，并对 Host 提供唯一 bootstrap API。

任务：

1. 新增 `ServiceLoaderPluginDiscovery` 和 `DefaultPluginContext`；
2. 新增 Platform Operational Module internal SPI、ServiceLoader discovery、`OperationalContext` 和 O0-O8 manager；
3. 新增 `PluginRuntimeManager`，实现 P0-P8 局部管线；
4. 新增 `HostBootstrapCoordinator`，严格实现 H0-H4 和 B0-B3；
5. 新增 `RuntimeShellBootstrap`/Handle 和 Host 路由快照；
6. 修改 Runtime auto-configuration，但不得自动扫描插件或发布 Controller；
7. 增加 required Capability、required Query DAG、operational internal dependency 和 privilege 校验；
8. 增加屏障越级、全局路由冲突和并行确定性测试；
9. 建立包含 required Plugin/Operational Module 的 Runtime readiness 聚合；
10. 实现 required module 终态失败的 Standalone 非零退出与 Embedded fatal callback/future。

退出条件：

1. H3 只读取 B0 冻结的 descriptor，未验证输入无法进入 DAG；
2. `ServiceLoader` provider 缺失时 required item fail-fast；
3. Capability 缺失时 `app-tenant` 无法进入可发布候选集合；
4. 相同输入在不同线程调度下得到相同 DAG、候选集合和 Host 路由快照；
5. B2 前无 Handler 创建，B3 前无路由可见；
6. `CapabilityRegistry` 未泄露到插件或 operational module；
7. required module 终态失败不会形成永久 live-but-not-ready。

### 阶段 4：改造 `app-tenant` 为 v3.0.10 样板插件

目标：`tenant-server` 中存在唯一 `BrixPlugin` provider，并通过 Runtime 主链启动。

任务：

1. 新增 `TenantPlugin`；
2. 新增 `META-INF/services/io.runtime.sdk.plugin.BrixPlugin`；
3. 新增 `plugin-manifest.yaml`；
4. 由 `TenantPlugin.configure()` 登记 Endpoint Handler Factory，移除 Spring MVC Controller 自动发布路径；
5. 修正 `app-tenant/pom.xml`、`tenant-core/pom.xml` 注释；
6. 补 `TenantPluginServiceLoaderTest`；
7. 补 manifest/provider 一致性测试；
8. 补 required Capability 缺失测试；
9. 检查 `tenant-ui-web` 与后端 manifest 的 route/manifestUrl 一致。

退出条件：

1. `ServiceLoader.load(BrixPlugin.class)` 能发现且只发现一个 `TenantPlugin`；
2. Runtime 按 provider artifact 关联唯一 Manifest，`TenantPlugin` 不含 `manifest()`；
3. `configure()` 只登记 Factory，Factory 只经 `PluginContext.require/find` 获取 Capability；
4. `TenantPlugin.onStart(PluginContext)` 不使用 `RuntimeContext`，也不注册 Endpoint；
5. `tenant-core` 无 `RuntimeContext`、`AbstractModule`、L2B import；
6. Endpoint 只经 L2B Dispatcher 发布，REST API 最小闭环可用。

### 阶段 5：Host 接入 Runtime Bootstrap

目标：Host 从“Spring 自动扫描自然启动”升级为“调用 Runtime Shell bootstrap，完成 B0-B3 和 Host 路由快照发布后再报告 Ready”。

任务：

1. 修改 standalone `ShellApplication`；
2. 修改 embedded `ShellApplication`；
3. 新增或调整 `StandaloneShellAutoConfiguration` / `EmbeddedShellAutoConfiguration`；
4. standalone POM 增加 `tenant-server` 依赖或 tenant-only profile；
5. embedded contract-test profile 增加 `tenant-server`；
6. application.yml 增加 required plugin 配置；
7. Composition 增加显式 `operationalModules.required/optional`，tenant-only 可写空数组但不得省略；
8. actuator readiness 接 Runtime 派生状态，liveness/fatal 接 Host 可恢复性；
9. Standalone bootstrap handle 在 required module 终态失败时有界 Drain 并非零退出；
10. Embedded bootstrap handle 完成 fatal callback/future，禁止 `System.exit`；
11. Host 架构测试禁止源码 import tenant 业务类型。

退出条件：

1. Host 源码只 import Runtime Bootstrap API，不 import `TenantPlugin`；
2. tenant-only Host 启动后 Runtime 插件集合包含 `brix-app-tenant`；
3. 暂时 Provider 故障只使 readiness=false，liveness 保持可恢复；
4. required module `FAILED -> STOPPED` 时 Standalone 非零退出，Embedded 报告 fatal `DOWN` 并通知 owner 重建；
5. `/actuator/health/readiness` 在 Registry、required Plugin/Operational Module 或 Host 路由快照未就绪时为不可接流量；
6. required module 启动失败时 Host fail-fast；
7. Host 源码没有 Controller/Handler fallback 或第二套路由发布机制。

### 阶段 6：业务闭环验证

目标：用 `app-tenant` 验证商业插件在 v3.0.10 壳中的最小闭环。

验证用例：

1. 启动 tenant-only Host；
2. Runtime 发现 `brix-app-tenant`；
3. Runtime 校验 manifest；
4. Runtime 注入 required Capability；
5. `TenantPlugin` 进入 `STARTED`，B3 完成并原子发布 Host 路由快照；
6. 派生 readiness 满足后 `GET /actuator/health/readiness` 返回 UP；
7. `GET /api/v1/tenants` 在有权限 token 下返回列表；
8. `GET /api/v1/tenants/{tenantId}` 返回详情；
9. `POST /api/v1/tenants` 进入现有创建逻辑；
10. 关闭 EventBusCapability 或 AuthCapability 后启动失败；
11. 删除 ServiceLoader provider 后启动失败；
12. manifest pluginId 与 provider 不一致时启动失败。
13. 让 required `TenantPlugin` 在运行期进入 `FAILED -> STOPPED`，验证 Standalone 有界 Drain 后非零退出；
14. 在 Embedded contract test 中验证同类失败只完成 fatal callback/future，不调用 `System.exit`；
15. 以不同并行调度重复启动，验证 DAG、候选集合和路由快照摘要一致。

注意：

1. 该闭环只证明运行壳模型升级成功；
2. 不证明首位超管流程已经正确；
3. 不证明公开租户注册、FIRST_OWNER、安全事件 outbox 等 P0/P1 已修复。

### 阶段 7：门禁收敛

目标：防止 `app-tenant` 样板回退到旧模型，并为后续批量迁移做模板。

任务：

2. CI 增加 `{name}-server` 唯一 `BrixPlugin` provider 规则；
3. CI 增加 manifest/provider/Maven 版本一致规则；
4. CI 增加 Host 源码不 import 商业插件业务类型规则；
5. CI 增加 required Capability 缺失 fail-fast 测试；
6. `docs-dev/README.md` 和 `docs-dev/评审提示.md` 指向 v3.0.10；
7. `architecture-check.yml` 删除 v3.0.9 活动裁决文案。

退出条件：

## 6. Bootstrap 到首位超管流程的顺序约束

该流程必须在 v3.0.10 架构模型升级后再改，原因如下：

1. Bootstrap 是 Host 启动期行为，必须依赖 Runtime readiness，而不是 Spring bean 是否被扫描；
2. 首位超管流程涉及平台身份、租户、邀请、审计和权限能力，必须通过 `PluginContext`/Capability 主链验证能力存在；
3. FIRST_OWNER 邀请接管不能再建立在旧 `RuntimeContext + 自动激活租户` 假设上；
4. P0/P1 修复需要 Host fail-fast 和 readiness 机制作为保护层；
5. 如果先改业务流程，后续再换运行壳，会重复改 Controller、Service、测试和启动脚本。

下一阶段建议命名：

`v3.0.10-后续-Bootstrap到首位超管流程验证架构改造计划.md`

下一阶段入口条件：

1. 本计划阶段 0 至阶段 7 全部完成；
2. `app-tenant` tenant-only Host 闭环通过；
3. v3.0.10 SPI、manifest、readiness、Host bootstrap 门禁已启用；
4. `docs-dev` 和 CI 不再把 v3.0.9 作为活动裁决源；
5. Bootstrap 相关脚本、配置和测试基线已盘点。

下一阶段重点文件预计包括：

| 文件/目录 | 预计动作 |
|---|---|
| `packages/@brix/enterprise-host/host-shell-standalone/src/main/resources/application.yml` | 明确 bootstrap 开关、超管初始化策略、生产 fail-fast |
| `scripts/remote-deploy/_set_bootstrap_env.sh` | 收敛 bootstrap 环境变量 |

## 8. 回滚策略

1. 旧 `RuntimeContext` 和 Spring AutoConfiguration 可继续服务未迁移插件，但 `app-tenant` 不得回退到旧入口；
2. `tenant-server` 切换到 YAML 后不得恢复 JSON/YAML 双份声明；
3. Host 新增 tenant-only profile，生产默认组装不被首轮强行改变；
4. Runtime bootstrap 失败时回滚整个 tenant-only 制品/commit，不通过运行期开关在同一制品中恢复旧路径；
5. 回滚只允许撤销本次新增 SPI/bootstrap/tenant provider 接入，不允许修改已发布 Flyway 迁移。

## 9. 风险与治理

| 风险 | 等级 | 应对 |
|---|---:|---|
| SPI 名称与现有 `RuntimeContext` 体系长期并存 | 高 | 明确 legacy 标注，CI 禁止 `app-tenant` 回退 |
| Manifest 字段从 JSON 旧结构切到 YAML 新结构引发工具不兼容 | 高 | 未迁移 artifact 可走独立兼容器；tenant artifact 只认唯一 YAML，双份声明 fail-fast |
| Host bootstrap 与 Spring AutoConfiguration 生命周期重叠 | 高 | 生命周期裁决归 Runtime；Spring 不扫描插件、不自动发布 Controller/Endpoint |
| required Capability ID 命名不统一 | 中 | 建立 Capability Catalog/Schema 白名单 |
| 其他插件继续使用旧模型 | 中 | 本阶段接受，但不得复制旧模板；后续按样板批量迁移 |
| 先改 Bootstrap 业务流程导致返工 | 高 | 本文明确禁止，下一阶段再处理 |
