## 0. 结论

1. **一个模型，两种记录**。
   - **键记录**：每个幂等键一行，由第一个成功执行的请求占用，记下请求指纹和结果。
     - 命令沿用 `{storageId}_command_idempotency`，追加一列指纹。
     - 端点新建同样形状的 `{storageId}_endpoint_idempotency`，另存响应。
   - **命令结果记录**：每个没有占到键的命令一行（重复、冲突、被拒绝，以及 Kafka 一侧被运维丢弃的），新建 `{storageId}_command_outcome`。占到键的命令，它的键记录就是结果。
   - Inbox 不变，仍只按 `(handlerId, commandId)` 去重。
2. **命令有两种终态**：成功（`SUCCEEDED`）和被拒绝（`REJECTED`，带错误码）。
   - Handler 抛出业务类别的 `BrixException`，就是拒绝：不重试、不停放，也不占键。之后同一个键的新命令会重新执行。
   - 其他失败照旧重试、停放。
3. **同一个键再来一个命令**：
   - 指纹相同是重复（`DUPLICATE`），Handler 不执行，状态指向占着键的那个命令；
   - 指纹不同是冲突（`CONFLICT`），Handler 不执行，不重试、不停放，状态里看得到。
4. **指纹**：Owner 把收到的载荷 JSON 规范化后取 SHA-256。只存指纹，不存载荷。
5. **状态**：发送方按 commandId 查。
   - 运行时依次看 Owner 的键记录与结果记录、Owner 一侧的停放、发送方自己的 Outbox。
   - 只有提交它的发送方、在同一租户里看得到。
   - 记录保留 30 天。
6. **并发**：先占键、再执行。PostgreSQL 上同一个键的第二个插入会等第一个事务结束：第一个提交，它得到"已存在"；第一个回滚，它自己插入成功（§10 实测）。
7. **全部是追加**。
   - 新列可空；新表只给提供命令、或声明了结果重放的 Owner 建。
   - 共享环境现在没有这样的 Owner，第 7～9 点上线不会改那里的表结构。第 10 点给平台端点打开结果重放时才会新建表。
8. **蓝图**：第 7～10 点都不与现行条款冲突（§5.5）。现行条款没写清的四处语义整理成 RFC-009：
   - 幂等范围由运行时派生；
   - 指纹与冲突；
   - 只有成功占键；
   - 状态和它的可见范围。

   建议按本设计施工第 7～10 点；RFC 的审批和根 3.4.0 的发布作为 §11 末尾的新一点。

## 3. 业界做法与取舍

| 做法 | 出处 | Brix 的取舍 |
|---|---|---|
| 同一个键、请求内容不同时拒绝：服务端比较请求指纹 | IETF Idempotency-Key 草案（422）；Stripe（比较参数，不同即报错）；AWS Powertools（载荷哈希，`IdempotencyValidationError`） | 采用。命令记为 `CONFLICT`，端点返回 422 |
| 端点开始执行后才保存结果；校验失败、与并发请求冲突时不保存，可以重试 | Stripe | 采用。键记录与业务写入同一事务，失败回滚，不留记录 |
| Handler 抛异常时删除幂等记录，同一载荷再来会重新执行 | AWS Powertools | 采用。被拒绝的命令不占键 |
| 同一个键的请求还在处理时返回 409；缺少键返回 400 | IETF 草案 | 端点采用。命令改为等前一个结束：同一个键的命令本来就要串行 |
| 键至少保留 24 小时；清理后再用同一个键算新请求 | Stripe | 命令 30 天（与 Inbox 一致）；端点按清单的保留策略，缺省 24 小时 |

## 4. 数据模型

### 4.1 概念

| 概念 | 含义 |
|---|---|
| 入口 | 产生记录的 Handler：一个命令 Handler，或一个端点 Handler |
| 幂等范围 | 由运行时派生，调用方不能指定。命令是"发送方插件｜租户｜命令类型"（L4 已实现）；端点是"租户｜调用方主体"：没有租户的写 `platform`，主体是通过认证的 actor，超过 128 字符改存 SHA-256（与命令相同） |
| 幂等键 | 调用方给的键。命令由发送方传，如订单号；端点取请求头 `Idempotency-Key` |
| 请求指纹 | 规范化请求的 SHA-256（§4.5） |
| 结果 | 命令是终态与错误码；端点是状态码与响应正文 |
| 占键 | 第一个**成功**执行的请求占用这个键。占键记录与业务写入、Outbox 在同一事务里提交 |

### 4.2 表结构

参考 DCP（PostgreSQL）的平台迁移，放在 `META-INF/brix/messaging/postgresql/` 下，只追加，已执行的迁移不改。

命令键表，追加 V2（第 8 点）：

```sql
-- command-idempotency/V2__command_idempotency_fingerprint.sql
ALTER TABLE {{storageId}}_command_idempotency ADD COLUMN request_fingerprint VARCHAR(64);
```

- `request_fingerprint` 是 SHA-256 的十六进制。V2 之前写的行为空：无法比较，按重复处理。
- `status` 仍写 `ACCEPTED`，含义写明为"成功执行并占用这个键"，不增加取值。

命令结果表，新建 V1（第 7 点）。和键表一样，只给提供命令的 Owner 建：

```sql
-- command-outcome/V1__canonical_command_outcome.sql
CREATE TABLE {{storageId}}_command_outcome (
    handler_id          VARCHAR(128) NOT NULL,
    command_id          VARCHAR(64)  NOT NULL,
    idempotency_scope   VARCHAR(128) NOT NULL,
    idempotency_key     VARCHAR(128) NOT NULL,
    outcome             VARCHAR(20)  NOT NULL,
    error_code          VARCHAR(128),
    holder_command_id   VARCHAR(64),
    tenant_id           BIGINT,
    created_at          TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_{{storageId}}_command_outcome PRIMARY KEY (handler_id, command_id),
    CONSTRAINT chk_{{storageId}}_command_outcome_outcome
        CHECK (outcome IN ('DUPLICATE', 'CONFLICT', 'REJECTED', 'DISCARDED'))
);

CREATE INDEX idx_{{storageId}}_command_outcome_created ON {{storageId}}_command_outcome (created_at);
```

- `holder_command_id`：`DUPLICATE`、`CONFLICT` 时，是占着键的那个命令。
- `error_code`：`REJECTED` 时是 Handler 的稳定错误码，`CONFLICT` 时是 `command.idempotency_conflict`。
- `DISCARDED`：Kafka 传输下，运维丢弃了 Owner 一侧停放的命令。进程内传输的丢弃记在发送方 Outbox 上，不写这里。
- `idempotency_scope` 用于状态查询的访问检查（§4.8）。

端点键表，新建 V1（第 10 点）。只给声明了结果重放的 Owner 建：

```sql
-- endpoint-idempotency/V1__canonical_endpoint_idempotency.sql
CREATE TABLE {{storageId}}_endpoint_idempotency (
    entry_id            VARCHAR(256) NOT NULL,
    idempotency_scope   VARCHAR(128) NOT NULL,
    idempotency_key     VARCHAR(128) NOT NULL,
    request_fingerprint VARCHAR(64)  NOT NULL,
    result_status       INTEGER,
    result_body         JSONB,
    tenant_id           BIGINT,
    trace_id            VARCHAR(32),
    created_at          TIMESTAMPTZ  NOT NULL,
    expires_at          TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_{{storageId}}_endpoint_idempotency PRIMARY KEY (entry_id, idempotency_scope, idempotency_key)
);

CREATE INDEX idx_{{storageId}}_endpoint_idempotency_expiry ON {{storageId}}_endpoint_idempotency (expires_at);
```

- `entry_id` 是"模块 ID/handlerId"。运维端点的记录写在 Owner 的表里（§5.4），所以要带上模块。handlerId 只在同一类入口里唯一，端点不与命令共用一张表。
- `result_status`、`result_body`：插件端点存 HTTP 状态码与响应正文（204 没有正文）；运维端点存写契约的结果，没有状态码。
- `trace_id` 是原请求的 trace，重放时写进日志，方便对照；Dispatcher 有审计出口之后也写进审计。
- `expires_at` 按端点的保留策略算，清理依据它。

### 4.3 命令的状态（第 7～9 点）

| 状态 | 含义 | 来源 | 由谁写、什么时候写 |
|---|---|---|---|
| `QUEUED` | 已持久受理，Owner 还没处理完 | 发送方 Outbox 行是 `PENDING`、`IN_FLIGHT` 或 `PUBLISHED`，且 Owner 没有记录 | 发送方运行时（现有） |
| `SUCCEEDED` | Handler 成功，事务已提交；这个命令占着键 | Owner 键表，按 `(handler_id, command_id)` 查 | Owner 运行时，与业务写入同一事务（现有；第 8 点加指纹） |
| `DUPLICATE` | 同一个键、同一指纹，键已被另一个成功的命令占着；Handler 没有执行 | Owner 结果表；`holder_command_id` 指向占键的命令 | 同一事务（第 7 点） |
| `CONFLICT` | 同一个键、指纹不同；Handler 没有执行 | Owner 结果表 | 同一事务（第 8 点） |
| `REJECTED` | Handler 以业务类别的错误拒绝；事务回滚，没有效果 | Owner 结果表，带错误码 | 回滚之后另开短事务（第 9 点） |
| `PARKED` | 重试用尽或永久失败，等运维重放或丢弃 | 进程内传输：发送方 Outbox `PARKED`；Kafka 传输：Owner 的停放视图 | 现有 |
| `DISCARDED` | 运维丢弃了停放的命令 | 进程内传输：发送方 Outbox `DISCARDED`；Kafka 传输：Owner 结果表 | 现有；Kafka 一侧由第 7 点补写 |
| `UNKNOWN` | 查不到：不是这个发送方或这个租户的命令、过了保留期，或者从未存在 | — | — |

- 查询顺序：Owner 键表 → Owner 结果表 → Owner 一侧的停放 → 发送方 Outbox → `UNKNOWN`。前面查到就停。
- `DUPLICATE` 的结果就是占键命令的结果。占键的一定是成功的命令，所以发送方看到的是"重复，原命令已成功"。
- 状态查询不读 Inbox。第 7 点上线之前处理过的重复命令没有结果行，会查成 `QUEUED`，过了发送方 Outbox 的保留期变成 `UNKNOWN`。现在只有样例和测试库有这样的行。

### 4.4 写入顺序与并发（命令）

都在 Owner 的 Unit of Work 里进行，时长受投递截止时间限制（第 3 点）：

1. 写 Inbox `(handlerId, commandId)`。已有记录说明是重投，直接提交（现有）。
2. 计算请求指纹（§4.5）。
3. 占键：`INSERT ... ON CONFLICT DO NOTHING`，写进键表，带上指纹。
   - **插入成功**，执行 Handler：
     - 正常完成：一起提交 Inbox、键记录、业务写入、Outbox，状态是 `SUCCEEDED`；
     - 业务拒绝：回滚；再开一个短事务，写 Inbox 行和 `REJECTED` 结果行，然后提交；
     - 其他失败：回滚，照旧重试、停放。
   - **没有插入**：键已被一个已提交的命令占着。如果占着它的事务还没结束，这一步会等它，最长等到投递截止时间。然后读占键行，比较指纹：
     - 相同，或者占键行没有指纹：`DUPLICATE`；
     - 不同：`CONFLICT`。

     写结果行，提交。Handler 不执行。
4. 等待超过截止时间时，按暂时性失败处理，稍后重投。那时占键的事务已经提交或回滚，结果就确定了。

拒绝之所以另开事务：

- Handler 的事务必须回滚，才能撤销它已经做的写入；拒绝又必须记下来，否则重投会再执行一次，发送方也看不到结果。
- 第二个事务在第一个结束之后才开，不是嵌套（DATA-029）。
- 两个事务之间主机崩溃，命令会被重投，Handler 再执行一次，又被拒绝或者这回成功了。这和暂时性失败一样，不会重复产生副作用。
- 第二个事务发现 Inbox 已有记录（另一次重投先完成了），就什么都不写。

### 4.5 请求指纹

- **命令**：Owner 一侧，对收到的 `payload` 部分规范化后取 SHA-256，存十六进制（64 字符）。不包括 `idempotencyScope`、`idempotencyKey`、`actorId` 和信封字段。
- **端点**：对经过 Schema 校验、交给 Handler 的请求取指纹。POST、PUT、PATCH 是请求体，其他方法是查询参数，都加上路径变量。
- **规范化**：结构按 RFC 8785（JCS）：对象成员按名字的 UTF-16 码元排序，没有空白，数组保持顺序，字符串按 JCS 转义。与 JCS 不同的两处：
  - 去掉值为 null 的对象成员：新的 Minor 版本加了可选字段时，旧发送方不传、新发送方传 null，这两者算同一个请求；
  - 数字写成精确的十进制值并去掉末尾的零（`1`、`1.0`、`1.00` 是同一个数，`1e2` 是 `100`），不像 JCS 那样先转成双精度：否则超过 2^53 的两个不同 id 会算成同一个请求，后一个命令被当成重复而丢掉。第 8 点施工时定下，见收尾方案 §10.19。
- **不计入**：
  - 命令的 schemaVersion：同一个 Major 内升级，不应让同一个业务请求变成冲突；
  - 发起人 `actorId`：同一租户里两个用户对同一个订单点"取消"，是重复，不是冲突。
- **为什么在 Owner 一侧算**：不改信封，旧消息也能算，发送方也伪造不了。PostgreSQL 的 JSONB 会重排键（§10 实测第 4 项），所以必须先规范化，不能直接对文本取哈希。
- **只存指纹，不存请求本身**：三张表都不含载荷或个人信息。

### 4.6 结果与数据分类

- **命令**：只存终态、稳定错误码和相关的 commandId（D67）。
  - 冻结的 `CommandHandler` 返回 `CompletionStage<Void>`（根 §5.3、MANIFEST-027），没有类型化的结果。
  - 需要新建资源 ID 的，由发送方在命令里给出 ID，或者订阅 Owner 发布的事件。
- **错误码**：只存稳定错误码，不存异常消息、细节参数和堆栈。
- **端点**：存状态码与响应正文；运维端点存写契约的结果（§5.4）。
  - 响应 Schema 里有 secret、credential 分类字段的端点，不提供结果重放：声明 `required` 时启动失败。
  - 正文上限 64 KiB（D76）。
- **幂等键原样保存**（不超过 128 字符）。作者文档要写明：键用订单号这类业务标识，不要用个人信息或秘密。

### 4.7 保留与清理

| 记录 | 保留 | 清理依据 |
|---|---|---|
| 命令键表 | 30 天，与 Inbox 相同（Kafka 方案 D34） | `created_at`（现有） |
| 命令结果表 | 30 天 | `created_at` |
| 端点键表 | 清单的保留策略，缺省 24 小时，上限 30 天 | `expires_at` |

- 含义是"至少保留这么久"。清理之前，同一个键仍按重复或冲突处理（与 Stripe 相同）。
- 清理沿用现有的保留任务：分批删除、计数，失败时告警。

### 4.8 隔离与可见性

- 范围由运行时派生（命令："发送方｜租户｜类型"；端点："租户｜主体"）。调用方占不到别的发送方或别的租户的键。
- 命令状态只有两种情况下可见：查询的是提交它的发送方，并且在同一个租户的调用里。
  - 访问检查：用调用方插件、当前租户、命令类型重新算出范围，与记录里的 `idempotency_scope` 比较；查发送方 Outbox 时只看调用方自己的 Outbox，并比较 `tenant_id`。
  - 其他情况一律返回 `UNKNOWN`，不透露命令是否存在。
- 这三张表是平台受托表（根 DATA-004），插件代码不能直接读写。运行时经 Owner 的持久化单元访问，与 Inbox 相同。

### 4.9 迁移、兼容与回滚

- 全部追加：一个可空的新列，两张新表（DATA-019）。启动期表结构检查（`CanonicalMessagingTables`）同步加入这两张表。
- 命令的两张表只给提供命令的 Owner 建；端点键表只给声明了结果重放的 Owner 建。
- 回滚：旧版本 jar 不读新列、新表，回滚不需要迁移数据。新表留在库里无害。
- 第 10 点给平台端点打开结果重放时，共享环境会新建端点键表。那一点部署时按惯例先备份、演练。

## 5. 第 7～10 点怎么用

### 5.1 第 7 点：发送方按 commandId 查命令状态

- SDK（L2A）：给 `CommandClient<C>` 加 `status(String commandId)`，是 default 方法（CAP-019），返回 `CommandStatus`：commandId、状态、错误码、占键的 commandId、时间。
- 运行时：
  - 按 §4.3 的顺序查，按 §4.8 做访问检查；
  - 新建结果表，把今天只记日志的 `duplicate_key` 写成 `DUPLICATE`；
  - Kafka 一侧丢弃停放的命令时，写 `DISCARDED`。
- 样例：拒收接口返回的 commandId 可以查状态。端到端：拒收两次，第二个命令是 `DUPLICATE`，指向第一个。
- 文档：改正 `CommandCapability` 里"exactly once"和"Owner 用事件报告"两处说法。

### 5.2 第 8 点：同一个键、内容不同时拒绝

- 键表 V2 加指纹。
- 占键改为 `INSERT ... ON CONFLICT DO NOTHING`：并发时等前一个结束，不再让事务作废、不再消耗尝试次数。
- 冲突写 `CONFLICT`，稳定错误码 `command.idempotency_conflict`（类别 CONFLICT）。
- 可观测：指标 `brix.command.idempotency.conflicts`（Prometheus 里是 `brix_command_idempotency_conflicts_total`；标签 owner、handler）；WARN 日志，不带载荷。
- 样例：拒收请求加一个原因（例如"破损""拒签"）。同一个订单先后用两个不同的原因拒收，第二个命令是 `CONFLICT`。
- 一致性套件在两种传输上各加场景。

### 5.3 第 9 点：命令 Handler 的结果随幂等记录保存

- 拒绝的判定：Handler 抛出 `BrixException`，错误码类别是 INVALID、DENIED、NOT_FOUND 或 CONFLICT，就是 `REJECTED`（D65）。UNAVAILABLE、DEADLINE_EXCEEDED、INTERNAL 和其他异常照旧重试、停放。
- 写入：回滚后用短事务写 Inbox 行和结果行（§4.4）。
- 说明：写明键表 `status` 的含义；`IdempotencyContext` 的说明改成实际行为。
- 样例：取消一个不存在的订单时，sample-orders 以 `sample-orders.order_not_found` 拒绝，状态是 `REJECTED`。
- 一致性套件：拒绝不重试、不停放；同一个键的新命令会再执行。

### 5.4 第 10 点：创建类写端点的结果重放

- 清单：`idempotency.mode: required` 重新可用，`optional` 继续让插件启动失败（D72）；键取请求头 `Idempotency-Key`；保留策略用一个目录名，缺省 `idempotency-24h`（D73）。只有类型化写端点能声明（D74）。
- Dispatcher 按 MANIFEST-022 的顺序处理（错误码见 D75）：
  - 缺少键或键不合法：400；
  - 同一个键还在处理：立即返回 409，不占着连接等（D77）；
  - 指纹不同：422；
  - 指纹相同：重放保存的状态码与正文，加响应头 `Idempotent-Replayed: true`；
  - 每种情况都记指标和日志。Dispatcher 现在没有审计出口，审计等它有了再接。
- 记录位置（D70）：
  - 插件端点：在插件自己的 Unit of Work 里，与业务写入一起提交。
  - 运维端点：Handler 的事务不传给 Owner（HOST-020），所以记录跟着它唯一的那次写契约调用，在 Owner 的事务里保存契约结果。
    - MANIFEST-022 要求冲突在 Handler 之前拒绝：Dispatcher 先按键读 Owner 的记录，指纹不同就返回 422；指纹相同就让 Handler 照常运行，写契约直接返回保存的结果。
    - 两个同键请求同时通过预检时，由 Owner 事务里的占键分出先后。
    - 具体做法在 10b 定。
  - 一个端点写两个 Owner 时，没有原子的重放边界。这样的端点要拆开，或者继续靠业务键。
- 要处理的平台端点：
  - 超管 4.0.1 §6 表要求 `required`、代码里已有的 6 个运维端点：`bootstrap/session`、`bootstrap/create-first-admin`、`POST /api/platform/tenants`，以及首位 OWNER 邀请的创建、重发、撤销；
  - 多租户 ENTRY-005 的首位 OWNER 接受端点（platform-tenant）；
  - L7a 之前还声明过 `required` 的 `auth/setup/totp/init`、`auth/setup/complete`：超管 4.0 把 setup 划给了身份协议面，§6 表不要求 `required`，不打开（2026-11-04 核对）。
  - §6 表里另外 4 个写端点（新建、撤销超管，重置超管密码，改租户状态）代码里还没有，建的时候直接声明 `required`。
- 前提：
  - platform-admin 的端点要先改成类型化形状、补上 Schema：指纹和响应分类都依赖 Schema。
  - `bootstrap/session` 的响应带会话令牌，按 §4.6 不能保存，而且与 BRX-SA-SEC-004 不符（收尾方案 §11 末尾新的一点）。第 10 点先不给它打开结果重放，等那一点定了再说。
- 规模：施工前再拆成两点：
  - 10a：Runtime 机制，加上样例下单接口；
  - 10b：平台端点逐个打开，每个都跑超管端到端。开工时再拆成 10b-1～10b-7，清单在收尾方案 §11。

### 5.5 与现行条款的关系、顺序

| 点 | 现行依据 | 有没有冲突 |
|---|---|---|
| 7 | MESSAGE-013 之后一句允许"可查询状态"；新方法以 default 方法加入（CAP-019） | 无 |
| 8 | MESSAGE-014 只要求不重复产生副作用；冲突时 Handler 同样不执行，只是变得可见 | 无 |
| 9 | §6.1 命令"可接受/拒绝"；MESSAGE-015 的重试是 MAY；拒绝没有副作用，再执行也不会重复产生副作用 | 无；"拒绝不占键"由 RFC-009 写定 |
| 10 | MANIFEST-018 本来就要求结果重放与冲突边界 | 无 |

- 顺序 7 → 8 → 9 → 10a → 10b。前一点建好的表和写入路径，后一点直接用。
- 7～9 只影响提供命令的 Owner。共享环境上没有这样的 Owner，这几点在那里不改变行为；10b 才动共享环境的表。
- RFC-009 的审批与发布不卡第 7～10 点，作为 §11 末尾的新一点。如果负责人要先发布新根再施工，就把它挪到第 7 点之前（D71 备选）。

## 6. 不在本设计范围

- 类型化的命令结果（D67 备选）。
- 把结果推给发送方（回发事件、回调）。发送方查状态，或者订阅 Owner 的事件。
- 提交后同步等结果（submit-and-wait），需要对 MESSAGE-016 提 RFC。
- 把停放载荷移出主机堆（§11 队列里 Kafka 评审的一项）。状态查询暂时读现有的停放视图。
- 事件 Handler 的永久失败信号（Kafka 评审 P2 的一项）。本设计只给命令定义拒绝。

| 编号 | 推荐 | 备选 |
|---|---|---|

| D66 请求指纹 | Owner 一侧对收到的载荷 JSON 按 RFC 8785 的结构规范化（数字取精确十进制）、去掉 null 成员，取 SHA-256；不计 schemaVersion 和发起人；V2 之前的记录没有指纹，按重复处理 | 发送方算好随信封传：要改信封，旧消息没有；把 schemaVersion 计入：同一 Major 内升级后，同一个请求会变成冲突 |

| D68 状态查询 | `CommandClient.status(commandId)`：依次查 Owner 键表、结果表、Owner 一侧的停放、发送方 Outbox；只对发送方本身、同一租户可见，其余一律 `UNKNOWN`；记录保留 30 天 | Owner 把结果作为事件回发给发送方：要新增一类主题和订阅，发送方还要自己建状态表 |
| D69 并发 | 先占键再执行（`INSERT ... ON CONFLICT DO NOTHING`）。命令等前一个同键事务结束，再判重复或冲突，等待受投递截止时间限制；端点同一个键还在处理时，立即返回 409 | 保持"先查后插"：并发的同键命令整个事务作废、消耗一次尝试；端点也等待：占着连接，直到截止时间 |
| D70 端点记录的位置与内容 | 记录与业务写入同一事务，放在产生效果的 Owner 的表里。插件端点存状态码与正文；运维端点经唯一的写契约存契约结果；写两个 Owner 的端点、响应含 secret 或 credential 的端点，都不提供重放 | 运维模块在自己的表里另开事务存响应：与业务写入不原子，崩溃窗口里会重复执行，不符合 MANIFEST-018 |
| D71 蓝图与顺序 | 第 7～10 点按本设计在现行条款内施工；RFC-009（根 Minor，3.4.0）的审批与发布作为 §11 末尾的新一点 | 先审批 RFC、发布根 3.4.0，再开始第 7 点 |
| D72 `optional` | 继续让插件启动失败。现在没有端点需要它，以后支持是追加，不影响现有声明 | 现在就支持：不带键时照常执行、带键时重放，多一个分支，没有使用方 |
| D73 声明 | `idempotency.mode: required`。键固定取请求头 `Idempotency-Key`，范围由运行时派生，都不在清单里写。`retentionPolicyRef` 可选，目录现在只有 `idempotency-24h`（缺省） | 清单里写键来源和范围：只有一种取值，是空配置 |
| D74 适用范围 | 只有类型化写端点（POST、PUT、PATCH、DELETE）：声明了请求和响应 Schema、调用方已认证（`authentication.mode: required`）、Owner 有持久化。响应 Schema 含 secret、credential 分类字段时启动失败（§4.6） | 也开放给匿名入口：没有主体，不同调用方共用键，能读到别人的响应 |
| D75 键与错误 | 键是 1～128 个可见 ASCII 字符。缺少或不合法：400 `endpoint.idempotency_key_required`；同一个键还在处理：409 `endpoint.idempotency_in_progress`；指纹不同：422 `endpoint.idempotency_conflict` | 409 时等前一个结束再重放：占着连接（D69 已否） |
| D76 保存的正文 | 上限 64 KiB。声明 `required` 的是创建类端点，响应很小，超过是插件缺陷：请求失败、事务回滚、记 ERROR | 超过时只存状态码：重放给不出原来的响应；截断：重放的内容不对 |
| D77 判断"还在处理" | 占键前取事务级 advisory lock（`pg_try_advisory_xact_lock`）。取不到就是同一个键还在处理，立即 409，事务不作废；事务结束自动释放 | §5.4 原写的 `lock_timeout`：0 表示不限时，只能设一个很短的等待；要在插入前后设置和恢复，否则影响 Handler 自己的语句；超时后事务作废 |

## 8. RFC-009（建议稿）

全文见 [RFC-009](rfc/RFC-009-运行壳-命令幂等的请求指纹、结果与状态（Draft）.md)。要点：

1. 改写 MESSAGE-014，写明：
   - 幂等范围由运行时派生；
   - 键由第一个成功的命令占用，记下指纹；
   - 同一个键、同一指纹是重复，指纹不同以 `command.idempotency_conflict` 拒绝，不重试、不停放。
2. 新增 MESSAGE-030（命令结果）：
   - 两种终态；
   - 业务类别的拒绝回滚后另记，不重试、不停放、不占键；
   - 结果记录不含载荷与个人信息。
3. 新增 MESSAGE-031（命令状态）：
   - 发送方按 commandId 查询，列出状态值；
   - 只对发送方本身、同一租户可见；
   - 至少保留到 Inbox 保留期。
4. 根升为 3.4.0（Minor，`compatibilityEpoch` 不变）；四份专项各出一个只改继承版本的 Patch，与 RFC-008 的做法相同。
5. 端点的结果重放沿用 MANIFEST-018，不在这份 RFC 里。

## 9. 风险

| 风险 | 对策 |
|---|---|
| 把暂时性错误错判成拒绝，命令不再重试 | 只认四个业务类别；UNAVAILABLE、DEADLINE_EXCEEDED、INTERNAL 和非 `BrixException` 都按暂时性；一致性测试覆盖每个类别 |
| 指纹把同一个请求判成冲突 | Owner 一侧对同一份文本规范化；去掉 null 成员；不计版本与发起人；冲突可见，发送方可以换键重发；冲突有指标 |
| 占键等待占住连接 | 受投递截止时间限制；同一个键的命令本来就要串行；端点不等，直接 409 |
| 状态泄露别人的命令 | 用调用方算出的范围比对，查不到一律 `UNKNOWN` |
| 端点存响应带进敏感数据 | 含 secret、credential 字段的端点不提供重放；正文有大小上限；保留期短 |
| 第 10 点改动面大 | 拆成 10a、10b；平台端点逐个打开，每个都跑超管端到端 |

## 10. 核验

1. 现状表（§2）每一行都对照了代码，行号以 brix `e04c3d9` 为准。
2. 在一次性 PostgreSQL 15 上实测（127.0.0.1:25433，用完即删）。做法：一个会话插入一个键，持有 3 秒后提交或回滚；另一个会话 1 秒后插入同一个键，记下等了多久、结果是什么。结果：
   1. `INSERT ... ON CONFLICT DO NOTHING` 遇到别的事务未提交的同一个键时会等。对方提交，它不插入（等了 2.2 秒），随后读到对方的指纹；对方回滚，它插入成功（等了 2.3 秒）。
   2. 等待可以限住：`lock_timeout` 200 毫秒报 lock timeout，`statement_timeout` 500 毫秒报 statement timeout。
   3. 现在的"先查后插"：`SELECT COUNT` 看到 0，`INSERT` 等对方提交后报主键冲突，事务作废。
   4. JSONB：`{"b": 1, "a": 1.0, "c": null, "d": {"y": 2, "x": 1}, "e": 1.50}` 存进去再取出，是 `{"a": 1.0, "b": 1, "c": null, "d": {"x": 1, "y": 2}, "e": 1.50}`。键被重排，数值的小数位和 null 都保留。
3. 架构基线校验器 PASS。本设计不改任何冻结蓝图。
