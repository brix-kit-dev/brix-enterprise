### 0.0c v5.1.1 修订结论（RFC-004）

1. 租户成员邀请（`TENANT_MEMBER`）由持有 `tenant:member:invite` 的 `ACTIVE` 成员发起，默认即 OWNER 与 ADMIN（§5.5、§5.7 第 3 条），与 §9.8.2 一致；v5.1 中"只能由 `ACTIVE OWNER` 发起"的写法作废。

3. 权限码目录与默认授予、DDL、T-1～T-30、Token 结构与隔离语义不变；兼容代际保持 `3`，`rebaseRequired=true` 不变。

### 0.0b v5.1 修订结论（RFC-003）

1. 新增 §9.8 租户最小 RBAC：权限码只来自插件 Manifest；角色只用内置的 Actor（OWNER、ADMIN、MEMBER）与 Subject（CUSTOMER、GUEST）；默认授予写在声明权限的模块里，Runtime 启动时汇总成不可变授予表。
2. 权限在请求时由 Dispatcher 按已验证的 `mtype`/`ptype` 展开；Token 不携带可信的权限列表（T-30）。
3. 数据范围只有 `TENANT` 与 `SELF`，随访问判定交给 Handler（§11.2 `BRX-TENANT-CONTRACT-007`）；Subject 只能获得 `SELF`，T-22 增加授予表启动校验。
4. 租户 Endpoint 必须声明只接受 Actor（`tenant-actor`）或只接受 Subject（`tenant-subject`），一个权限只授予一类角色，落实 §8.1 第 3 条与 T-11。
5. 新增租户控制台权限码目录与默认授予（§9.8.2）；OWNER 专属动作用专属权限码表达。
6. 新增红线 T-29、T-30 与实施验收项 I11；成员、主体、Token 结构、DDL 与隔离语义不变，兼容代际保持 `3`。

### 0.0a v5.0 修订结论（RFC-002）

1. 租户员工与终端用户的登录改经身份协议面：`tenant-console` 与品牌应用两类客户端取代 `/api/auth/login/actor`、`/api/auth/login/subject` 两个对外 API；B/C 入口分离的语义不变。

### 0.1 什么是"最小实现"

"最小实现"= **生产可用的多租户底座所必需的最小能力集**，不多不少：

- **必须有**：区分租户、隔离数据（全栈）、双轨认证（B 端 Actor / C 端 Subject）、租户选择与切换、租户基础配置、开源/商业边界、租户内最小授权（v5.1，§9.8）。
- **明确不做**（留待后续版本，见 [§16 范围边界](#16-范围边界minimum--deferred)）：Schema/DB 级隔离、计费、SSO、自定义域名、白标 App、合规报告、复杂配额计量。

### 0.2 对标的国际大厂模式

| 设计点 | 对标对象 | 采纳结论 |
|--------|----------|----------|

### 0.5 唯一所有权、模块形状与仓库边界

[BRX-TENANT-OWNER-001] OSS `platform-tenant` 是平台租户目录的唯一 Data Owner，唯一拥有 `sys_tenant`、`sys_tenant_member`、`sys_tenant_principal`、`biz_user_profile`、`sys_tenant_invitation`、`sys_tenant_config`、`sys_installation_quota`，以及这些聚合的 Schema、migration、Repository contract、本地事务、租户审计和 canonical Outbox/Inbox。

[BRX-TENANT-OWNER-002] `platform-tenant` 是 OSS 官方 L1 Plugin，目标物理形状固定为：

```text
platform-tenant-api     moduleKind=plugin-api
platform-tenant-core    moduleKind=plugin-core
platform-tenant-server  moduleKind=plugin-server
```

`plugin-server` 通过唯一 `ServiceLoader<BrixPlugin>` provider 和唯一 `META-INF/brix/plugin-manifest.yaml` 进入 Runtime。Host 只静态组装 Runtime、Adapter、Plugin 和 Operational Module，不承载租户 Service、Repository、Controller、转换或按 pluginId 分支。

[BRX-TENANT-OWNER-003] Enterprise `app-tenant` 只能拥有企业租户扩展、展示模型或业务配置，不得拥有第二套平台租户目录、成员/邀请权威写模型、平台超管路由或 `sys_*` 表写权限。既有 `app_tenant_*` 资产必须在环境账本确认后采用前滚迁移、只读兼容或显式归档；禁止静默双写、直接删除或以现有代码反向定义 Owner。

[BRX-TENANT-OWNER-004] `platform-admin` 不拥有租户、Member、Principal、Profile、邀请、配额或租户审计数据。它的租户运维写入只可通过 `OperationalContext.requireInternalContract()` 取得 `brix.internal.tenant.administration` / `io.brix.platform.tenant.internal.TenantAdministration` `1.0.0`；Provider 由 `platform-tenant` 在自身 Manifest `internalContracts.provides` 声明并经唯一 `InternalContractProvider` Factory 绑定。普通 Plugin 不得消费、枚举或查找 internal contract。

## 1. 开源版与商业版边界（Open Core）

> **核心原则一：安全是底座，不是商品。** 多租户隔离、JWT 校验、跨租户防泄漏、审计在任何版本中都完整提供，永不进付费墙。
> **核心原则二：采用 Open Core，不依赖"不可绕过的代码限制"做商业保护。** 本仓核心代码以 Apache 2.0 开源，用户**有权修改**——因此 **3 租户上限是开源版的默认配置/许可约定，而非技术上不可绕过的商业护城河**。真正的商业价值来自 License 服务、企业能力与支持，而非锁死代码。

### 1.1 Open Core 分层

| 层 | 内容 | 许可 |
|----|------|------|
| **Open Core（开源）** | 完整多租户底座：三层身份、Actor/Subject 分表、全栈隔离、JWT 双轨、防泄漏、审计、行级隔离 | Apache 2.0，可自由修改 |
| **Commercial（商业）** | 企业 License 配额、SSO/SAML/OIDC 联合登录、Schema/DB 级高级隔离、合规报告、白标、官方支持与 SLA | 商业许可 |

> 开源版默认 `maxTenants = 3`，是**许可与产品策略约定**，并通过 License 模块在官方发行版中生效；不假装它是无法被有源码者绕过的技术屏障。商业护城河 = SSO + 高级隔离 + 合规 + 支持，而非"删不掉的 if 判断"。

### 1.2 租户数量计数与配额规则（红线 [T-16](#12-架构红线)）

**1. 配额主体（统计范围）**：3 租户上限按**整个 Brix 部署实例**统计，**不得按 `owner_identity_id` 统计**——否则每个用户都能各建 3 个租户，上限形同虚设。配额主体**统一固定为单一字段 `installation_id`**（同一部署实例全局唯一），全实例共享同一配额行；**不再并列 `deployment_id` / `license_subject_id` 等多种写法**（避免多主体歧义）。

**2. 哪些状态计入上限**：仅 **`ACTIVE` 与 `TRIAL`** 状态的租户计入配额。`PENDING_ACTIVATION` / `DISABLED` / `ARCHIVED` / `DELETED`（软删）**不计入**。

**3. 删除是否释放名额**：

- **软删（`ARCHIVED`/`DISABLED`）**：仍占数据但**不计入**配额名额（可被新建复用）；保留期内可恢复——恢复时需重新占用名额（若已满则拒绝恢复并提示）。
- **硬删（数据彻底清除）**：立即释放名额。
- 名额计算统一以"当前 `ACTIVE`+`TRIAL` 计数"为准，避免软删占名额导致用户困惑。

**4. 激活租户并占用配额必须并发安全（禁止 `COUNT → INSERT`）**：

> 简单"先 `COUNT` 再 `INSERT`"在并发下会突破上限（TOCTOU）。**冻结方案固定为「首位 OWNER 接受邀请时，配额行 + `SELECT FOR UPDATE`」**（不再提供 advisory lock 备选，见 §16 Rejected Alternatives）。创建租户本身只产生 `PENDING_ACTIVATION` 租户，不正式占用租户数量配额；首位 OWNER 接管成功、租户转为 `TRIAL` 或 `ACTIVE` 时才占用配额。

```sql
-- 冻结方案：首位 OWNER 接管时，部署实例级配额行 + SELECT FOR UPDATE（全实例唯一配额主体）
BEGIN;
SELECT used, quota FROM sys_installation_quota
    WHERE installation_id = :installationId FOR UPDATE;  -- 锁定全实例唯一配额行
-- 应用层校验 used < quota，否则回滚拒绝（fail-closed）
UPDATE sys_installation_quota SET used = used + 1
    WHERE installation_id = :installationId;             -- 首位 OWNER 接管成功后正式占用名额
INSERT INTO sys_tenant_member (... tenant_id, identity_id, member_type, status, ...)
  VALUES (:tenantId, :ownerIdentityId, 'OWNER', 'ACTIVE', ...)
  RETURNING id;                                        -- 首位管理员
INSERT INTO biz_user_profile (... tenant_id, member_id, ...)
  VALUES (:tenantId, :ownerMemberId, ...);             -- 首位管理员档案
UPDATE sys_tenant SET status = 'TRIAL' WHERE id = :tenantId; -- 或 ACTIVE，按 License/试用策略决定
COMMIT;                                                  -- 失败则整体回滚，名额自动归还
```

> `sys_installation_quota` 是**全实例单行**配额表：`installation_id`（PK）、`quota`（开源版=3 / 商业版=License 值）、`used`。`SELECT FOR UPDATE` 串行化所有并发激活/恢复租户事务，杜绝突破上限。新增租户先保持 `PENDING_ACTIVATION`；首位管理员必须通过 `FIRST_OWNER` 邀请接管后创建为 `ACTIVE OWNER`（见 §5.7），不得以普通 `ADMIN` 替代；UI 可展示为“租户管理员 / 所有者”。

**5. 租户状态变化必须与配额联动（同一事务 + 行锁，红线 [T-27](#12-架构红线)）**：

> 配额 `used` 必须与租户状态变迁**在同一事务内原子变更**，且**先 `SELECT ... FOR UPDATE` 锁定 `sys_installation_quota` 配额行**，防止并发突破上限。

| 状态变迁 | 配额动作 | 说明 |
|----------|----------|------|
| 接受 `FIRST_OWNER` 邀请，将租户从 `PENDING_ACTIVATION` 激活为 `ACTIVE` / `TRIAL` | `used = used + 1` | 与创建首位 `ACTIVE OWNER`、对应 Profile、邀请置 `ACCEPTED` 同事务（见 §5.7） |
| `ACTIVE`/`TRIAL` → `DISABLED`/`ARCHIVED`/`DELETED` | `used = used - 1` | 与状态更新同事务，释放名额 |
| 恢复（`DISABLED`/`ARCHIVED` → `ACTIVE`/`TRIAL`） | 先检查再预占 | 必须先 `FOR UPDATE` 锁行、校验 `used < quota` 再 `used+1`；已满则拒绝恢复（fail-closed） |
| 硬删（彻底清除） | `used = used - 1`（若之前未减） | 与删除同事务 |

> 并发铁律：**任何会改变 `ACTIVE`+`TRIAL` 计数的状态变迁，都必须在同一事务内先锁配额行再改 `used`**；状态变更与配额变更不得拆到两个事务（否则中间态会造成计数不一致）。

License 与配额的硬约束：

1. **安全相关能力（隔离、JWT 校验、防泄漏、审计）一律不得作为付费开关**，任何版本默认开启且不可关闭。
2. 开源版默认租户数上限 = 3（许可约定）；超限时**拒绝新增租户**（fail-closed），不影响已有租户。
3. 商业版租户数由 License 配额控制；超限时**仅拒绝新增**。
4. **License 到期只禁止新增租户，绝不删除或停用已有租户数据**。到期后：
   - 已有租户：正常读写、登录、隔离、审计照常。
   - 新增租户 / 新增成员（若 License 含席位限制）：拒绝并提示续期。
5. License 校验失败按 fail-closed 处理（拒绝新增），但**不得**导致已有数据不可访问。

## 2. 核心设计共识（不可推翻）

| # | 设计共识 | 不可推翻原因 |
|---|----------|--------------|
| 1 | **Actor / Subject 物理分离** — `sys_tenant_member`（B 端）与 `sys_tenant_principal`（C 端）独立建表 | 同一人可同时是某租户员工与客户；统一表会语义污染、生命周期纠缠、C 端百万级扩展污染 B 端查询 |
| 2 | **三层身份模型** — Identity（全局）→ Member / Principal（租户接入）→ Profile（租户内档案） | 表结构与外键定型，演进只能加字段 |
| 3 | **JWT 双轨签发** — Actor Token（`mid/mtype`，aud=actor）与 Subject Token（`pid/ptype`，aud=subject）**互斥** | 已签发 Token 不可改，结构必须前向兼容 |
| 4 | **TenantContext 统一抽象** — 契约在 Layer 2A，技术实现（ThreadLocal/Reactor/TaskDecorator）在 Layer 2C | 所有业务代码依赖统一 API，实现可演进 |
| 5 | **全栈租户隔离** — 不仅 SQL，Redis/Kafka/对象存储/异步任务/搜索/审计全部携带并清理 tenant 上下文 | 任一基础设施漏过 tenant 即构成越权面 |
| 6 | **基座层零行业语义** — `member_type` / `principal_type` 仅含通用枚举 | 平台不被任何行业锁死 |
| 7 | **BusinessObject 不入基座，插件不依赖平台表** — 插件仅存不透明 `tenant_id + member_id/principal_id` 引用，禁止跨服务外键 | 保持基座中性、服务可独立演进 |
| 8 | **安全能力不商业化** — 隔离/JWT/防泄漏/审计在任何版本完整提供 | 安全是底座责任，不是付费特性 |

## 3. 三层身份模型

```text
Layer 0: sys_identity                  全局身份（手机/邮箱/凭证），跨租户共享
   │                                    与租户无关，1 人 = 1 条记录
   │
   ├─► Layer 1A: sys_tenant_member     B 端 — 组织成员（Actor）  [tenant 隔离]
   │     • member_type ∈ { OWNER, ADMIN, MEMBER }
   │     • 准入：邀请 → 审批 → 加入（管理流程）
   │
   └─► Layer 1B: sys_tenant_principal  C 端 — 访问主体（Subject）[tenant 隔离]
         • principal_type ∈ { CUSTOMER, GUEST }
         • 准入：邀请 / 预约 / 注册绑定 → 创建（自动化）
                 │
                 ▼
Layer 2: biz_user_profile              租户内用户档案（每租户独立）[tenant 隔离]
   • member_id / principal_id 双可空字段（恰一非空，见 §5.3）
   • 同一人在不同租户可有不同昵称、偏好
```

> **重要**：`sys_tenant_member` / `sys_tenant_principal` / `biz_user_profile` 均带 `tenant_id`，**受租户隔离保护**，**不在** `TenantInterceptor` 白名单内（见 [§6](#6-平台表白名单与隔离边界)）。

**四术语精确区分（防混淆）：**

| 概念 | 表 | 回答的问题 | 举例 |
|------|------|-----------|------|
| **Member** | `sys_tenant_member` | 谁管理/运营这个租户？ | OWNER/ADMIN/MEMBER |
| **Principal** | `sys_tenant_principal` | 谁有资格被这个租户服务？（准入凭证） | CUSTOMER/GUEST |
| **Profile** | `biz_user_profile` | 你在这个租户叫什么、偏好什么？ | 昵称、locale、theme |
| **BusinessObject** | 插件自建表 | 你为什么来、做了什么业务？ | medical_case / order / enrollment |

> 关键优势：同一 `identity` 可在同一租户**同时持有** Member + Principal 记录（医生在自己诊所看病），两条独立记录互不污染；通过稳定 `contextId`（§9.3）区分登录视角。

## 4. B2B2C Actor/Subject 分离模型

### 4.1 角色全景

```text
Platform
  ├── PlatformAdmin       平台运维（sys_platform_admin，全局表）
  └── Tenant
       ├── Actor（B端）   → sys_tenant_member（tenant 隔离）
       │   ├── OWNER      租户创建者 / 所有者（每租户至少 1 个，见 §5.6）
       │   ├── ADMIN      管理员
       │   └── MEMBER     普通职员（行业语义在插件层）
       ├── Subject（C端） → sys_tenant_principal（tenant 隔离）
       │   └── CUSTOMER   终端用户（患者/学员/买家...）
       └── Guest          → sys_tenant_principal
           └── GUEST      受限访客（按需启用）
```

> **v5.1**：上述五个角色是本版本租户授权的全部内置角色，取值即 `member_type` / `principal_type`；权限码、默认授予与数据范围见 §9.8，租户自定义角色留待后续版本。

### 4.2 行业映射（基座层零感知）

| 行业 | Actor(MEMBER) | Subject(CUSTOMER) | BusinessObject（插件自建） |
|------|---------------|-------------------|------|
| 医疗 | 医生/药师 | 患者 | medical_case（病例） |
| 教育 | 教师/教练 | 学员 | enrollment（报名） |
| 电商 | 店铺运营 | 买家 | order（订单） |
| 法律 | 律师/助理 | 当事人 | legal_case（案件） |

### 4.3 Subject 准入硬规则

- **仅在"有效准入动作"后创建 Principal**：邀请准入 / 接受邀请 / 注册并绑定租户 / 业务行为触发（提交预约、完成报名）。
- **单纯浏览品牌页、扫码预览、访问公开链接，不创建 Principal。**
- Principal 生命周期**独立于** BusinessObject：Case/Order 结束**不删除/失效** Principal。仅在「主动退出 / 管理员停用 / 状态置 `DISABLED`|`REVOKED`」时失效。

## 5. 数据模型（最小 DDL）

> 全部时间字段统一 `TIMESTAMPTZ`（带时区，存 UTC）；默认时区由外部配置注入，**禁止硬编码地域时区**。本节 DDL 是目标 Schema 和约束的规范语义，不授权修改任何已经执行的 Flyway 文件。`V007`～`V011` 仅保留为 v3.1.3 历史设计标签；实际施工必须先读取所有正式/共享环境的 `flyway_schema_history` 和已发布文件 raw hash，再选择全环境安全的下一单调版本。不得 repair、重命名、复用版本或原地改写历史 migration。

### 5.2 sys_tenant_member（收窄 + 完整性 — V008）

```sql
-- 数据迁移：检测 CUSTOMER/GUEST 是否存在，存在则阻断并产出报告（禁止静默 DO NOTHING，见 §5.8）
-- 迁移成功后收窄约束，仅保留 B 端角色
ALTER TABLE sys_tenant_member DROP CONSTRAINT IF EXISTS chk_member_type;
ALTER TABLE sys_tenant_member ADD CONSTRAINT chk_member_type

ALTER TABLE sys_tenant_member ADD CONSTRAINT chk_member_status
    CHECK (status IN ('ACTIVE', 'INVITED', 'DISABLED', 'REVOKED'));
-- 授权版本号：状态/角色/权限变更即自增；Token mver 快照（见 §8.2）
ALTER TABLE sys_tenant_member ADD COLUMN IF NOT EXISTS authz_version INTEGER NOT NULL DEFAULT 1;

-- 复合唯一键：供 biz_user_profile 复合外键保证 tenant 一致（见 5.3）
ALTER TABLE sys_tenant_member ADD CONSTRAINT uk_member_tenant_id UNIQUE (tenant_id, id);
```

> **`context_id` 数据来源（红线 T-20 相关）**：每条 `sys_tenant_member` 记录 = **一个 Actor Context**；`sys_tenant_principal` 每条 = **一个 Subject Context**。两表的 `context_id` 即 Token `cid`，由 `select-context` 据 `contextSelectionTicket` 解析得到（见 §9.3）。`context_id` 创建后**不可修改**。

> **`context_id` 数据库层强制不可变（红线 [T-20](#12-架构红线)）**：不仅依赖应用层与 Code Review，**必须**用 `BEFORE UPDATE` 触发器在数据库层阻止任何对 `context_id` 的修改（`sys_tenant_member` 与 `sys_tenant_principal` 两表均加）。

```sql
-- 数据库层强制 context_id 不可变（V008 同批，两表共用同一函数）
CREATE OR REPLACE FUNCTION guard_context_id_immutable() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.context_id IS DISTINCT FROM OLD.context_id THEN
        RAISE EXCEPTION 'CONTEXT_ID_IMMUTABLE: context_id of % cannot be modified', TG_TABLE_NAME;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_member_context_id_immutable
    BEFORE UPDATE ON sys_tenant_member
    FOR EACH ROW EXECUTE FUNCTION guard_context_id_immutable();
CREATE TRIGGER trg_principal_context_id_immutable
    BEFORE UPDATE ON sys_tenant_principal
    FOR EACH ROW EXECUTE FUNCTION guard_context_id_immutable();
```

### 5.3 biz_user_profile（修复多态引用 — V009）

> **不再使用 `ref_type + ref_id` 弱多态**（无法被外键约束、易产生悬挂引用、无法保证 tenant 一致）。
> **冻结方案：单表双可空字段 `member_id` / `principal_id`**，以 CHECK 保证"恰好一个非空"，以**复合外键**保证引用对象与本行 `tenant_id` 一致。（拆两表方案见 §16 Rejected Alternatives，不作为可选实现。）

> **迁移拆分为 4 个独立 Flyway 版本，严禁在一段 SQL 内同时加列/加外键/加 CHECK/删旧列**（脏数据会导致整体失败且难回滚）。

**V009a — 仅增加新列（可空，不加任何约束）**

```sql
ALTER TABLE biz_user_profile ADD COLUMN IF NOT EXISTS member_id    BIGINT;
ALTER TABLE biz_user_profile ADD COLUMN IF NOT EXISTS principal_id BIGINT;
```

**V009b — 分批回填并检查冲突（不加约束）**

```sql
-- 按旧 ref_type 分批回填（避免长事务）：
UPDATE biz_user_profile SET member_id    = ref_id WHERE ref_type = 'MEMBER'    AND member_id    IS NULL;
UPDATE biz_user_profile SET principal_id = ref_id WHERE ref_type = 'PRINCIPAL' AND principal_id IS NULL;
-- 冲突检查（任一非空 → 阻断迁移并产报告，禁 DO NOTHING，见 §5.8）：
--   ① 存在两列都空或都非空的行
--   ② member_id/principal_id 指向的对象不存在或 tenant_id 不一致
-- 检查不通过 → 迁移以非零退出码失败 → 人工裁决后重跑
```

**V009c — 增加外键、唯一约束与 CHECK（数据已干净）**

```sql
-- 复合外键：引用对象必须与本行 tenant_id 一致（依赖 5.1/5.2 的复合唯一键）
ALTER TABLE biz_user_profile ADD CONSTRAINT fk_profile_member
    FOREIGN KEY (tenant_id, member_id)    REFERENCES sys_tenant_member(tenant_id, id);
ALTER TABLE biz_user_profile ADD CONSTRAINT fk_profile_principal
    FOREIGN KEY (tenant_id, principal_id) REFERENCES sys_tenant_principal(tenant_id, id);
-- 每个 member/principal 在租户内恰好一个 profile（快照改为 uk，确保 1:1 不可多不可少）
ALTER TABLE biz_user_profile ADD CONSTRAINT uk_profile_member    UNIQUE (tenant_id, member_id);
ALTER TABLE biz_user_profile ADD CONSTRAINT uk_profile_principal UNIQUE (tenant_id, principal_id);
-- 恰好一个引用非空（放最后，确保回填已满足）
ALTER TABLE biz_user_profile ADD CONSTRAINT chk_profile_ref_exclusive CHECK (
    (member_id IS NOT NULL AND principal_id IS NULL)
 OR (member_id IS NULL     AND principal_id IS NOT NULL)
);
```

**V009d — 应用切换完成后删除旧列（独立版本，单独可回滚）**

```sql
-- 确认应用代码已不再读写旧弱引用列后执行：
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS ref_type;
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS ref_id;
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS member_id_legacy;
```

> **顺序铁律**：V009a 加列 → V009b 回填+冲突检查 → V009c 建 FK/唯一键/CHECK → V009d 删旧列。**严禁**在回填完成前就加 FK/CHECK，**严禁**把删旧列与建约束放进同一版本。

> **Profile 必存性约束**：V009c 的外键、CHECK 与 UNIQUE 保证 Profile 引用有效、租户一致且**最多一个**——即 `UNIQUE(tenant_id, member_id)` / `UNIQUE(tenant_id, principal_id)` 只防止重复，**不能单独保证 ACTIVE Member/Principal 一定存在 Profile**。存在性属于事务级领域不变量：创建 Member/Principal 与 Profile **必须在同一事务中完成**，Profile 失败则整体回滚；该规则通过**集成测试和一致性巡检**保证。

> **说明**：此处复合外键属于 **平台基座内部表之间** 的约束，不违反 [§7 插件不得外键平台表] 的红线（后者约束的是**插件/跨服务**表）。

> );
> ```
> 上述 `sys_platform_config` 片段只描述合并语义，不是 `platform-tenant` migration 内容。生效配置三层合并为 `user override ?? current tenant override ?? platform profile`。普通插件只通过根 Catalog 已登记的 `ConfigCapability` 读取自身 Manifest 已声明的非敏感类型化配置；租户配置写入和管理由 `platform-tenant` 的 typed contract / internal contract 提供，不新增 `TenantConfigCapability`。

### 5.5 sys_tenant_invitation（租户成员邀请表 — V011）

> 租户成员邀请**必须落独立表**，保存 token **哈希**（绝不存明文）、过期时间、使用状态。首位 `OWNER` 接管邀请与后续租户成员邀请共用基础设施，但必须通过 `invitation_purpose` 选择不同接受策略；**不得**根据“租户是否已有 OWNER”动态推断邀请用途，也**不得**把平台超管伪装成租户 Member。

```sql
CREATE TABLE IF NOT EXISTS sys_tenant_invitation (
    id              BIGINT PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    invitation_purpose VARCHAR(20) NOT NULL,               -- FIRST_OWNER | TENANT_MEMBER
    inviter_type    VARCHAR(20) NOT NULL,                  -- PLATFORM_ADMIN | TENANT_MEMBER
    platform_operator_ref VARCHAR(128),                    -- FIRST_OWNER 发起者的不可透明审计引用；来自已验证 Invocation Context
    tenant_member_id BIGINT,                               -- TENANT_MEMBER 发起者；与 platform_operator_ref 互斥
    target_role     VARCHAR(20) NOT NULL,                  -- OWNER|ADMIN|MEMBER
    invited_email   VARCHAR(190) NOT NULL,                 -- 用于匹配 identity；接受时必须校验邮箱一致
    token_hash      VARCHAR(256) NOT NULL,                 -- 仅存安全 Profile 生成的 verifier
    token_verifier_version VARCHAR(32) NOT NULL,           -- 算法/参数版本标识，支持升级
    status          VARCHAR(20) NOT NULL DEFAULT 'PENDING',  -- PENDING|ACCEPTED|EXPIRED|REVOKED
    expires_at      TIMESTAMPTZ NOT NULL,
    used_at         TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_invite_tenant FOREIGN KEY (tenant_id) REFERENCES sys_tenant(id),
    -- 复合外键：tenant_member_id 必须是【本租户】的 Member，防止邀请记录引用其他租户的 Member
    CONSTRAINT fk_invite_tenant_member FOREIGN KEY (tenant_id, tenant_member_id)
        REFERENCES sys_tenant_member(tenant_id, id),
    CONSTRAINT chk_invite_purpose CHECK (invitation_purpose IN ('FIRST_OWNER', 'TENANT_MEMBER')),
    CONSTRAINT chk_invite_inviter_type CHECK (inviter_type IN ('PLATFORM_ADMIN', 'TENANT_MEMBER')),
    CONSTRAINT chk_invite_status CHECK (status IN ('PENDING', 'ACCEPTED', 'EXPIRED', 'REVOKED')),
    CONSTRAINT chk_invite_target_role CHECK (target_role IN ('OWNER', 'ADMIN', 'MEMBER')),
    CONSTRAINT chk_invite_actor CHECK (
        (invitation_purpose = 'FIRST_OWNER'
             AND inviter_type = 'PLATFORM_ADMIN'
             AND platform_operator_ref IS NOT NULL
             AND tenant_member_id IS NULL
             AND target_role = 'OWNER')
     OR (invitation_purpose = 'TENANT_MEMBER'
             AND inviter_type = 'TENANT_MEMBER'
             AND platform_operator_ref IS NULL
             AND tenant_member_id IS NOT NULL
             AND target_role IN ('OWNER', 'ADMIN', 'MEMBER'))
    )
);
CREATE UNIQUE INDEX uk_invite_token ON sys_tenant_invitation(token_hash);
CREATE INDEX idx_invite_tenant ON sys_tenant_invitation(tenant_id);
CREATE INDEX idx_invite_email ON sys_tenant_invitation(invited_email);
```

> **邀请用途铁律（红线 T-6/T-28 相关）**：`FIRST_OWNER` 只能由已验证、已授权的 Platform Admin 经 `TenantAdministration` internal contract 发起，目标角色固定为 `OWNER`；`platform_operator_ref` 由 L2B/Provider 从 Invocation Context 注入，调用方不得提交，且不得建立到身份 Owner 表的跨 Owner 外键。`TENANT_MEMBER` 只能由该租户持有 `tenant:member:invite` 的 `ACTIVE` 成员发起（默认授予 OWNER 与 ADMIN，§9.8.2），可邀请 `ADMIN` / `MEMBER`；`target_role = OWNER` 的邀请等同任命 OWNER，创建、重发与撤销还须持有只授予 OWNER 的 `tenant:owner:transfer`（`BRX-TENANT-AUTHZ-007`），由 platform-tenant 的 resource policy 判定（v5.1.1）。服务端接受邀请时必须根据记录中的 `invitation_purpose` 选择处理器，不能相信前端传入的用途。

### 5.6 防止删除租户最后一个 OWNER（红线 T-18）

> 每个租户**任意时刻必须至少有 1 个 `ACTIVE` 的 OWNER**。删除/降级/停用最后一个 OWNER 必须被阻断。
> **并发陷阱**：两个 OWNER 在不同事务中**同时**降级时，各自的触发器都"看到对方仍是 ACTIVE OWNER"而放行，提交后租户可能 0 OWNER。**必须先取租户级锁串行化**，再做计数校验。

```sql
CREATE OR REPLACE FUNCTION guard_last_owner() RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'DELETE' AND OLD.member_type = 'OWNER')
       OR (TG_OP = 'UPDATE' AND OLD.member_type = 'OWNER'
           AND (NEW.member_type <> 'OWNER' OR NEW.status <> 'ACTIVE')) THEN

        -- 关键：先取租户级事务锁，串行化同一租户的所有 OWNER 变更，杜绝并发双降级
        PERFORM pg_advisory_xact_lock(hashtext('tenant-owner:' || OLD.tenant_id));

        -- 锁内统计（排除本行）剩余 ACTIVE OWNER；并发事务此时被阻塞，无法绕过
        IF (SELECT COUNT(*) FROM sys_tenant_member
            WHERE tenant_id = OLD.tenant_id AND member_type = 'OWNER'
              AND status = 'ACTIVE' AND id <> OLD.id) = 0 THEN
            RAISE EXCEPTION 'TENANT_LAST_OWNER_PROTECTED: tenant % must keep >=1 active OWNER', OLD.tenant_id;
        END IF;
    END IF;
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_guard_last_owner
    BEFORE UPDATE OR DELETE ON sys_tenant_member
    FOR EACH ROW EXECUTE FUNCTION guard_last_owner();
```

**并发正确性约束：**

1. 所有修改 OWNER 的应用层流程（转移所有权 / 降级 / 移除 / 停用）**必须先取同一租户级锁**——应用层用 `pg_advisory_xact_lock(hashtext('tenant-owner:'||tenantId))` 或对 `sys_tenant` 行 `SELECT ... FOR UPDATE`，使同租户的 OWNER 变更**全序化**。
2. DB 触发器内的 `pg_advisory_xact_lock` 是**兜底**：即使应用层漏锁，触发器仍强制串行化计数校验。
3. 经此双重锁，**任意并发交错下都保证至少保留一个 `ACTIVE` OWNER**。
4. 应用层应提前校验并给出友好错误（如 `TENANT_LAST_OWNER_PROTECTED`），DB 触发器作为最终防线。

### 5.7 新增租户与首位 OWNER 接管分离（红线 T-28）

> 新增租户不是直接创建可登录管理员。**创建租户与首位 OWNER 接管必须分离**：创建租户后状态固定为 `PENDING_ACTIVATION`，不自动创建 OWNER，不创建 `biz_user_profile`，不正式占用租户数量配额。平台超管随后在“租户详情 → 租户管理员”区域发送 `FIRST_OWNER` 邀请；受邀人接受后才在同一事务中创建首位 `ACTIVE OWNER`、创建/确认 Profile、激活租户并占用配额。

**最小实现语义：**

1. **创建租户状态**：租户创建请求只创建 `sys_tenant(status='PENDING_ACTIVATION')` 及必要配置，不创建 `sys_tenant_member` / `biz_user_profile`，不把平台超管写成租户成员。
2. **首位 OWNER 邀请**：平台超管只经 `TenantAdministration` 发起 `FIRST_OWNER` 邀请，`target_role` 由 Owner 固定为 `OWNER`；`platform_operator_ref` 从受信任 Invocation Context 写入，调用方请求不得携带或覆盖。平台超管不得设置、查看或发送用户密码。
3. **后续成员邀请**：首位 OWNER 接管后，租户内持有 `tenant:member:invite` 的 `ACTIVE` 成员（默认为 OWNER 与 ADMIN，§9.8.2）使用同一邀请基础设施发起 `TENANT_MEMBER` 邀请，可邀请 `ADMIN` / `MEMBER`；邀请 `OWNER` 等同任命 OWNER，还须持有 `tenant:owner:transfer`，即只有 OWNER 能邀请 OWNER（v5.1.1）。成员邀请不改变租户状态和租户数量配额。
4. **邀请 Token 安全**：邀请 token 必须一次性、带有效期，数据库仅保存 hash；重发后旧 token 失效；API 不返回明文 token，邀请链接只能通过 `NotificationCapability` 发送。
5. **接受策略分派**：服务端必须根据 `sys_tenant_invitation.invitation_purpose` 选择 `FIRST_OWNER` 或 `TENANT_MEMBER` 接受处理器，不得根据“租户是否已有 OWNER”动态推断，也不得相信前端传入的用途。
6. **登录边界**：租户成员统一经身份协议面的 `tenant-console` 客户端登录，取得 `aud=brix-actor` 的 Actor Token（只存于 BFF）；不得使用平台控制台客户端、Platform Token 或任何平台超管授权进入租户业务上下文。

租户创建流程（伪代码）：

```sql
BEGIN;
-- 可做 License / quota 预检，但不正式占用 used；正式占用发生在 FIRST_OWNER 接受阶段
INSERT INTO sys_tenant (..., status, ...)
  VALUES (..., 'PENDING_ACTIVATION', ...)
  RETURNING id INTO :tenantId;
INSERT INTO platform_tenant_outbox (... event_type, scope, partition_key, payload, ...)
  VALUES (..., 'TenantCreatedPendingActivation', 'PLATFORM', :tenantId, ...);
COMMIT;
```

平台审计不是本事务中的跨 Owner 表写入。`platform-admin` 在取得类型化结果后，以同一 correlation/causation context 调用 `platform-audit` internal contract，由审计 Owner 在独立本地事务中记录原 actor、execution identity、稳定 action/reason 和受影响 tenant；租户事务失败则不得伪造成功审计。

首位 `OWNER` 接管流程（伪代码）：

```sql
BEGIN;
SELECT * FROM sys_tenant_invitation
  WHERE token_hash = :tokenHash
  FOR UPDATE;
-- 校验 purpose=FIRST_OWNER、status=PENDING、expires_at、invited_email 与当前 identity 邮箱一致
SELECT * FROM sys_tenant WHERE id = :tenantId FOR UPDATE;
-- 校验租户 status=PENDING_ACTIVATION，且不存在 ACTIVE OWNER
SELECT used, quota FROM sys_installation_quota
  WHERE installation_id = :installationId FOR UPDATE;
-- 重新校验 License / quota：used < quota，否则 fail-closed
UPDATE sys_installation_quota SET used = used + 1
  WHERE installation_id = :installationId;
INSERT INTO sys_tenant_member (tenant_id, identity_id, member_type, status, ...)
  VALUES (:tenantId, :ownerIdentityId, 'OWNER', 'ACTIVE', ...)
  RETURNING id INTO :ownerMemberId;
INSERT INTO biz_user_profile (tenant_id, member_id, principal_id, ...)
  VALUES (:tenantId, :ownerMemberId, NULL, ...);
UPDATE sys_tenant SET status = 'TRIAL' WHERE id = :tenantId; -- 或 ACTIVE，按 License/试用策略决定
UPDATE sys_tenant_invitation SET status = 'ACCEPTED', used_at = NOW()
  WHERE id = :invitationId;
INSERT INTO platform_tenant_outbox (... event_type, scope, tenant_id, partition_key, payload, ...)
  VALUES (..., 'TenantFirstOwnerAccepted', 'TENANT', :tenantId, :tenantId, ...);
COMMIT;
```

> **一致性要求**：`PENDING_ACTIVATION` 租户允许暂时没有 OWNER；任何可见为 `ACTIVE` / `TRIAL` 的租户，查询其 `sys_tenant_member` 时必须至少存在 1 个 `ACTIVE OWNER`。实现阶段必须提供一致性巡检：发现“ACTIVE/TRIAL 无 OWNER 租户”即安全告警并阻断发布。重复接受同一邀请不得重复创建 Member、Profile 或增加配额。

### 5.8 迁移冲突处理（红线 T-19）

> **禁止静默 `ON CONFLICT DO NOTHING`**。数据迁移遇到冲突（如 V008 迁移 CUSTOMER/GUEST 时主键/唯一键冲突）**必须阻断迁移并生成冲突报告**，由人工裁决后再继续。

```sql
-- V008 迁移前置检查（伪代码，实际用迁移脚本/工具实现）：
-- 1. 扫描 sys_tenant_member 中 member_type IN ('CUSTOMER','GUEST') 的记录
-- 2. 检测其迁移到 sys_tenant_principal 后是否与现有 (tenant_id, identity_id) 冲突
```

### 5.9 迁移语义顺序与白名单

- **语义顺序**：建立 principal → 收窄 member（含冲突阻断）→ Profile 加列 → 分批回填/冲突检查 → 建 FK/唯一键/CHECK → 应用完成切换后删旧列 → 配置字段/表 → 邀请表。实际 Flyway 版本号必须依据每个环境账本选择，本文不得假定 V001～V020 或 Enterprise V100 的发布状态。
- **历史不可变**：已执行文件 raw bytes 和 checksum 不得改写；新变化只新增前滚 migration，并验证 fresh install、每个支持版本升级、失败恢复和并发约束。

## 6. 平台表白名单与隔离边界

> **禁止按 `sys_*` 前缀整体加入白名单。** 白名单是越权面，必须**逐表显式**列入，且仅限**真正的平台全局表**。

### 6.1 白名单（仅这些表绕过 TenantInterceptor）

| 表 | 是否全局 | 说明 |
|----|:------:|------|
| `sys_tenant` | ✅ | 租户注册表本身（无 `tenant_id` 概念，是 tenant 的定义源） |
| `sys_identity` | ✅ | 全局身份，跨租户共享 |
| `sys_platform_admin` | ✅ | 平台超管，不归属任何租户 |
| `sys_platform_config` | ✅ | **平台全局配置**（无 `tenant_id`），可进入白名单 |
| `sys_installation_quota` | ✅ | **部署实例级配额表**（无 `tenant_id`，全实例单行，见 §1.2） |
| `sys_platform_audit_log` | ✅ | **平台审计**（跨租户/平台操作，无单一 `tenant_id`，见 §10.1） |

> **配置表必须拆分（红线 T-15 相关）**：`sys_platform_config`（平台全局）与 `sys_tenant_config`（租户级，带 `tenant_id`，**受隔离**）是**两张独立的表**。**禁止用同一张表同时承担全局配置与租户配置**——否则白名单一旦放行就会泄漏全部租户配置。

> **白名单逐表显式（红线 T-15）**：若未来出现其他 License / Installation 类全局表（如 `sys_license`、`sys_installation`），**必须逐表显式加入上表**；**禁止用表名前缀（`sys_*`）自动放行**。

### 6.2 必须受隔离的"租户关系/配置表"（**不得**进白名单）

`sys_tenant_member`、`sys_tenant_principal`、`biz_user_profile`、`sys_tenant_invitation`、**`sys_tenant_config`** 等**均带 `tenant_id`**，**必须受 `TenantInterceptor` 隔离保护**。理由：它们承载"谁能进哪个租户 / 某租户的配置"，一旦漏过隔离即等于跨租户成员枚举/配置越权。

### 6.3 例外 — 登录期跨租户查询（普通认证流程唯一允许）

登录阶段需要"列出某 identity 在**所有**租户的接入关系"，这是**普通认证流程中唯一允许**的跨租户读取（仅限登录期 Actor 租户发现）：

- 必须走 Auth Owner 的专用、版本化登录发现契约；provider 在自身 Owner context 中执行跨 tenant directory 的最小只读查询，并以稳定 reason `login-tenant-discovery` 记平台审计。该契约不得暴露给普通业务插件。
- **必须**记录审计日志（`identity_id`、查询时间、来源 IP、命中租户数）。
- **仅**返回 `tenant_id / tenant_name / role / roleType / last_access_at` 等**选择所需的最小字段**，禁止返回业务数据。
- **PlatformAdmin 跨租户查询属独立特权链路**：只读数据由租户 Data Owner 发布 typed Query；平台运维动作由 `platform-admin` 通过 descriptor 已声明且 privilege allowlist 批准的内部契约执行。它与本登录发现**互不等同**，不得再表述"登录查询是系统唯一跨租户访问"。
- 详见 [§9.2](#92-登录期跨租户发现专用审计接口)。

## 7. 插件数据引用规则

> **取消"插件业务表对平台表的强制外键"。** 插件与平台、插件与插件、跨服务之间**禁止数据库外键**，改为**不透明引用 + 应用层一致性校验**。

### 7.1 规则

1. 插件业务表**只保存** `tenant_id` + `member_id` / `principal_id` 等**不透明 ID**（无 DB 外键到 `sys_tenant_*`）。
2. 插件**不得**直接查询或 JOIN 平台租户表（`sys_tenant_member` / `sys_tenant_principal`）；引用归属校验必须通过 `platform-tenant` 发布的版本化 `TenantReferenceQuery` 生成客户端完成。
3. 写入/读取时必须由 Runtime 从当前 Invocation Context 注入 tenant scope，并通过 `TenantReferenceQuery{refId, refKind}` 校验不透明引用属于当前 tenant；Query 不接受调用方自行声明的 authority tenantId。
4. **跨插件、跨服务一律禁止数据库外键**（服务可独立部署/独立库，外键会硬耦合并阻断拆分）。

### 7.2 示例（医疗插件自建表）

```sql
-- ✅ 正确：不透明引用，无外键到平台表，自带 tenant_id
CREATE TABLE medical_case (
    id                   BIGINT PRIMARY KEY,
    tenant_id            BIGINT NOT NULL,         -- 受 TenantInterceptor 隔离
    patient_principal_id BIGINT NOT NULL,         -- 不透明引用，无 FK
    doctor_member_id     BIGINT,                  -- 不透明引用，无 FK
    case_number          VARCHAR(50),
    status               VARCHAR(20) NOT NULL,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_mc_status CHECK (status IN ('OPEN','IN_PROGRESS','CLOSED'))
);
-- 应用层：写入前通过生成的 TenantReferenceQuery client
-- 在当前已验证 tenant scope 内校验 patient_principal_id 归属
```

## 8. JWT Token 契约（双轨）

> **v5.0**：以下各类 Token 的 claims 语义不变，另增加 `acr`、`amr`、`auth_time`、`sid`（身份认证专项 BRX-IA-SESSION-003）。Token 由身份协议面的 token 端点签发：Web 客户端的 Access/Refresh Token 只保存在 BFF；Identity Token 只在认证服务内部使用，不交给浏览器应用。

> **v5.1**：租户 Actor/Subject Token 不携带可被信任的权限列表；有效权限由 Runtime 授予表按已验证的 `mtype`/`ptype` 在请求时计算（§9.8，T-30）。Subject Token 不含 `roles` 与 `permissions`；Actor Token 的 `roles` 保留为后续自定义角色的扩展位，本版本不参与授权。

> **JWT 由三段组成：`Header.Payload.Signature`。** `alg` / `typ` / `kid` 属于 **JOSE Header**；`iss` / `aud` / `sub` / `exp` / `tid` 等属于 **Claims（Payload）**。下文**分别**给出 Header 与 Claims，**不得**把两者写进同一个 JSON 对象。

**Actor Token（B 端）— 有效期短（建议 ≤15min），`aud=brix-actor`**

```jsonc
// (1) JOSE Header — 仅放签名/密钥元数据
{
  "alg": "<security-profile-alg>", // 必须命中安全 Profile allowlist
  "typ": "at+jwt",         // token 类型
  "kid": "<key_id>"        // 公钥轮转标识
}
```
```jsonc
// (2) Claims (Payload) — 业务与上下文声明
{
  "iss": "https://auth.brix.com",
  "aud": "brix-actor",                         // B 端专用 audience（C 端不可用）
  "scope": "actor",
  "sub": "<identity_id>",
  "iat": 0, "nbf": 0, "exp": 0, "jti": "<token_id>",
  "tid": "<tenant_id>", "tcode": "<tenant_code>",
  "cid": "<context_id>",                        // 稳定访问上下文 ID（见 §9.3）
  "mid": "<member_id>", "mtype": "ADMIN",      // OWNER | ADMIN | MEMBER
  "uid": "<profile_id>",
  "roles": ["admin"],                          // v5.1：后续自定义角色的扩展位，本版本不参与授权（§9.8）
  "mver": 7                                    // = sys_tenant_member.authz_version 快照（见 §8.2/§5.2）
}
```

**Subject Token（C 端）— `aud=brix-subject`**

```jsonc
// (1) JOSE Header
{ "alg": "<security-profile-alg>", "typ": "at+jwt", "kid": "<key_id>" }
```
```jsonc
// (2) Claims (Payload)
{
  "iss": "https://auth.brix.com",
  "aud": "brix-subject",                        // C 端专用 audience（B 端不可用）
  "scope": "subject",
  "sub": "<identity_id>",
  "iat": 0, "nbf": 0, "exp": 0, "jti": "<token_id>",
  "tid": "<tenant_id>", "tcode": "<tenant_code>",
  "cid": "<context_id>",
  "pid": "<principal_id>", "ptype": "CUSTOMER", // CUSTOMER | GUEST
  "uid": "<profile_id>",
  "pver": 3                                     // = sys_tenant_principal.authz_version 快照（见 §8.2/§5.1）
}
```

**Identity Token（临时 ≤5min，仅用于选上下文/注册）**

```jsonc
// Header
{ "alg": "<security-profile-alg>", "typ": "id+jwt", "kid": "<key_id>" }
```
```jsonc
// Claims
{ "iss": "https://auth.brix.com", "aud": "brix-identity",
  "sub": "<identity_id>", "iat": 0, "nbf": 0, "exp": 0, "jti": "<id>",
  "allowed_actions": ["select_context", "register_tenant"] }
```

**Refresh Token（服务端维护撤销列表 + Family）**

```jsonc
// Header
{ "alg": "<security-profile-alg>", "typ": "rt+jwt", "kid": "<key_id>" }
```
```jsonc
// Claims — 保存稳定 context_id（非一次性 ticket）
{ "iss": "https://auth.brix.com", "aud": "brix-refresh",
  "sub": "<identity_id>", "iat": 0, "nbf": 0, "exp": 0, "jti": "<id>",
  "cid": "<context_id>", "device_id": "<device>", "family": "<family>" }
```

> **四类 Token 必选 Claims 统一**：Actor / Subject / Identity / Refresh Token **均必含** `iss` / `aud` / `sub` / `iat` / `nbf` / `exp` / `jti`；差异仅在业务 claim（`tid` / `cid` / `mid` / `pid` / `scope` 等）。校验见 §8.1。

### 8.1 JWT 校验硬约束（红线 T-20）

1. **算法敏捷性**：只接受安全 Profile 当前 allowlist 中、与 token type/issuer/key metadata 匹配的算法；显式拒绝 `none`、算法降级和不在 allowlist 的算法。算法、参数与轮换不得由插件或本文硬编码。
2. **完整校验**：Header 的 `alg`/`typ`/`kid` 与 Claims 的 `iss`/`aud`/`exp`/`nbf`/`jti` 全部校验；`kid` 必须命中当前有效公钥集（支持轮转）。
3. **B/C 区分靠 audience/scope，不靠 URL 路径**：Actor Token `aud=brix-actor`，Subject Token `aud=brix-subject`；管理 API 强制要求 `aud=brix-actor`，C 端 API 强制 `aud=brix-subject`。**严禁仅凭 `/admin/*` 路径判断权限**。v5.1：租户 Endpoint 以认证策略 `tenant-actor` / `tenant-subject` 声明所属类别（§9.8 `BRX-TENANT-AUTHZ-012`）。
4. **`mid` 与 `pid` 互斥**：签发二选一；校验按 audience + 存在字段分派；不存在混合态。
5. **停用即失效**：Member/Principal 被停用（`DISABLED`/`REVOKED`）后，旧 Token 必须**尽快失效**——通过 (a) Access Token 短 TTL（≤15min）+ (b) `mver`/`pver` 授权版本号校验（见 §8.2）+ (c) `jti` 黑名单。
6. **`tid` 不可篡改**：JWT 非对称签名保证；禁止把 `tid` 作为业务请求参数。

### 8.2 授权版本号校验（`authz_version` ↔ `mver`/`pver`，红线 T-20）

> Token 中的 `mver`/`pver` 是签发时刻 `sys_tenant_member.authz_version` / `sys_tenant_principal.authz_version` 的**快照**。当成员/主体的**状态、角色、权限**发生变化时，对应行的 `authz_version` 自增（见 [§5.1](#51-sys_tenant_principal新增--v007) / [§5.2](#52-sys_tenant_member收窄--完整性--v008)）。

1. 每次受保护请求，鉴权层将 Token 的 `mver`/`pver` 与 DB 当前 `authz_version` 比对（可经短 TTL 缓存）。
2. **不一致即拒绝**（HTTP 401 `STALE_AUTHZ_VERSION`），客户端须重新走 refresh / select-context 取新 Token。
3. 触发自增的事件至少包括：`status` 变更、`member_type`/`principal_type`（角色）变更、权限/角色绑定变更、所有权转移。v5.1：授予表随 Host 制品变化、在请求时展开，模块升级带来的授予变化不触发自增（§9.8 `BRX-TENANT-AUTHZ-008`）。
4. 版本号 + 短 TTL + `jti` 黑名单三者叠加，保证停用/降权在秒级~分钟级生效，且无需在线撤销每一枚 Access Token。

## 9. 租户解析与认证流程

### 9.1 租户解析链 — Header/子域名/Path 仅为"提示"，非授权依据（红线 T-12/T-13）

| 优先级 | 解析器 | 来源 | 性质 | 信任边界 |
|:------:|--------|------|------|----------|
| 100 | `JwtTenantResolver` | JWT `tid`（已验签） | **授权依据** | 唯一可作为授权来源 |
| 150 | `HeaderTenantResolver` | `X-Tenant-Id` | **仅内部可信注入** | 见下方信任规则 |
| 200 | `SubdomainTenantResolver` | Host header | **提示** | 仅用于登录前品牌/租户提示 |
| 250 | `PathTenantResolver` | `/t/{code}/...` | **提示** | 仅用于路由提示 |
| — | Controller 显式处理 | Query `?tenantCode=` | **提示** | 公开注册/邀请，单独校验 |

**`X-Tenant-Id` 信任规则（强制）：**

- **公网入口的 `X-Tenant-Id` 必须由网关删除**（strip）后再转发，防止客户端伪造。
- 仅 **受信任网关** 或经 **mTLS / 服务身份认证** 的内部服务可注入 `X-Tenant-Id`。
- Header / 子域名 / Path 解析出的 `tid` **只能作为登录前提示**（选择哪个品牌、预填哪个租户），**不能作为已认证请求的授权依据**——已认证请求的 `tid` **永远**取自已验签 JWT。
- 当提示来源的 `tid` 与 JWT `tid` **冲突**时，按 [红线 T-10](#12-架构红线) 拒绝（HTTP 400 `TENANT_CONFLICT` + 审计告警）。

### 9.2 登录期跨租户发现（专用 + 审计接口，按入口严格分流）

> 发现接口**按登录入口分流**，B 端只发现 Actor，C 端只发现当前租户的 Subject。v5.0 起，**登录入口固定为身份协议面中两类独立的客户端**：`tenant-console`（B 端）与品牌应用（C 端，绑定唯一租户）；通道由客户端注册决定，**`client_type` 参数不作为登录通道选择依据**，绝不在一次登录中混合两端或跨租户数据。下方流程中的 `/api/auth/login/actor`、`/api/auth/login/subject` 表示认证服务内部的两条认证路径，不再是对外 API。

```text
─── B 端入口（管理控制台 / Actor 登录端点）───
POST /api/auth/login/actor   { phone+smsCode | email+password | oauth }
  → 验证凭证 → identity_id
  → Auth Owner discoverActor(identityId)                  // owner-scoped read + platform audit
       actor_contexts = sys_tenant_member WHERE identity_id=? AND status='ACTIVE'
  → 仅返回 Actor 上下文（绝不含任何 Principal / Subject 信息）
  → 写审计日志: { identity_id, entry:'actor', ip, ts, matched_context_count }

─── C 端入口（品牌 App / 租户入口，tid 已由品牌锁定）───
POST /api/auth/login/subject  { phone+smsCode | ... }   （请求绑定当前租户 tid 提示）
  → 验证凭证 → identity_id
  → AuthnTenantLookupService.discoverSubject(identityId, currentTenantId)  // 强制单租户过滤
       subject_context = sys_tenant_principal
            WHERE identity_id=? AND tenant_id=:current AND status='ACTIVE'
  → 仅返回【当前租户】的 Subject 上下文；不做跨租户聚合
  → 写审计日志: { identity_id, entry:'subject', tenant_id, ip, ts }
```

> - 该接口是 [§6.3](#63-例外--登录期跨租户查询普通认证流程唯一允许) 允许的、**普通认证流程中唯一**的跨租户读取（PlatformAdmin 特权链路除外），且**仅 B 端 `discoverActor` 可跨租户**；C 端 `discoverSubject` **强制单租户过滤**，不允许跨租户聚合。
> - 返回**仅限选择所需字段**（tenant/role/roleType/lastAccessAt），不含任何业务数据。
> - 每个上下文对应一个一次性 `selectionTicket`（见 §9.3），不下发稳定 `contextId`。

### 9.3 选择"访问上下文"协议 — `contextId` 与 `contextSelectionTicket`（解决同租户双身份）

> 同一 Identity 在同一租户可能**同时**是 Actor 和 Subject，`select-context` **不能只传 `tenantId`**（无法区分双身份）。本协议区分两类标识，**生命周期不同**：

| 标识 | 生命周期 | 用途 | 存放位置 |
|------|----------|------|----------|
| **`contextId`** | **长期稳定** | 唯一代表一个 `{ tenant + actor/subject + refId }` 接入上下文 | **Access Token / Refresh Token 的 `cid` claim**（见 §8） |
| **`contextSelectionTicket`** | **短期、一次性** | 登录后选择上下文的临时凭据，用后即焚 | 仅在登录→选择的窗口内传递，**绝不入长期 Token** |

> 设计要点：稳定的 `contextId` 是身份上下文的"主键"（来自 §5.1/§5.2 的 `context_id` 列），可被服务端长期引用、做设备记忆、放进 Token；`contextSelectionTicket` 只是"这一次登录允许选这个上下文"的一次性票据，**防止枚举他人 contextId 与重放**。
> **登录入口已在 §9.2/§9.4 严格分流**：B 端走 `/login/actor` 只产出 Actor 上下文，C 端走 `/login/subject` 只产出当前租户 Subject 上下文。**不存在同时返回 Actor 与多个租户 Subject 的通用入口**。

```text
─── B 端选择（仅 Actor 上下文；员工可属多个租户）───
Phase 1  POST /api/auth/login/actor
  → {
      "step": "SELECT_CONTEXT",
      "identityToken": "<id-jwt, ≤5min, jti=J1>",   // 绑定本次登录
      "contexts": [    // 全部为 actor；每项给一次性 ticket，不暴露稳定 contextId
        { "selectionTicket": "tkt_a1...", "tenantId": "t_a", "tenantName": "A诊所",
          "role": "actor", "roleType": "OWNER",  "lastAccessAt": "..." },
        { "selectionTicket": "tkt_b2...", "tenantId": "t_b", "tenantName": "B医院",
          "role": "actor", "roleType": "MEMBER", "lastAccessAt": "..." }
      ]
    }

─── C 端选择（仅当前租户 Subject；绝不含他租户）───
Phase 1  POST /api/auth/login/subject   （品牌已锁定 tid=t_a）
  → {
      "step": "SELECT_CONTEXT",
      "identityToken": "<id-jwt, ≤5min, jti=J2>",
      "contexts": [    // 仅 tenant=t_a 的 subject；不做跨租户聚合
        { "selectionTicket": "tkt_c3...", "tenantId": "t_a", "tenantName": "A诊所",
          "role": "subject", "roleType": "CUSTOMER", "lastAccessAt": "..." }
      ]
    }
  → 分支（C 端固定）：0 个 → NO_TENANT；1 个 → 自动进入。
     `UNIQUE (tenant_id, identity_id)` 保证同一 Identity 在同租户至多 1 个 Principal，**C 端不展示 Context Selector**（无 ≥2 分支）。

Phase 2 选上下文 POST /api/auth/select-context  Bearer <identityToken>
  Body: { "selectionTicket": "tkt_a1...", "rememberChoice": true }
  → 服务端校验 ticket：① 未过期（≤5min）② 未使用过（一次性）
      ③ 绑定的 identityToken.jti == 当前 identityToken.jti（不止 sub，见下方硬约束）
  → 校验通过 → 取出绑定记录的稳定 context_id（§5.1/§5.2）及 { tenant, role, member/principal, uid }
  → 校验绑定仍有效 + 租户 ACTIVE|TRIAL
  → 签发 Actor/Subject Token（cid=<context_id>）+ Refresh Token（cid=<context_id>）
  → 作废该 ticket（标记已使用）；更新 last_access_at

Phase 3 业务请求 GET /api/v1/...  Bearer <accessToken>
  → 验签(JWT §8.1) + authz_version 校验(§8.2) → TenantContext.set(tid, cid)
  → 按 aud 分派 Member/Principal 校验 → 对象级授权(§9.6) → 全栈隔离(§10)

Phase 4 切换上下文 POST /api/v1/context/switch  Bearer <currentToken>    （仅 Actor Token 可用）
  Body: { "targetContextId": "<context_id>" }     // 切换用稳定 contextId（已认证态，无需 ticket）
  → 切换范围铁律（见红线 [T-26](#12-架构红线)）：
      ① 仅 Actor Token 可切换，且只能切到【同一 identity 的其他 Actor 上下文】
      ② Subject Token 禁止切换：既不可切到 Actor 上下文，也不可切到其他租户（C 端原则上不提供 Context Switch）
      ③ Actor↔Subject 身份转换必须重新进入对应登录入口（/login/actor 或 /login/subject），不走本接口
  → 校验目标 contextId 属于同一 identity、role==actor 且有效 → 重签 Token（旧 jti 入黑名单）
  → 前端 queryClient.clear() + resetState() + 重载配置/品牌/features

Phase 5 刷新   POST /api/auth/refresh  { refreshToken }
  → 校验未撤销 + cid 绑定关系仍有效 → 轮转 RT（旧 RT 立即失效）
  → Family 重放检测：已失效 RT 被重用 → 撤销整个 Family → 强制重登
```

> **v5.0**：Phase 1～2 在认证服务内部执行；Phase 2 校验通过后签发绑定 `cid` 的一次性授权码，Token 由 token 端点签发给 BFF（或原生 App）。Phase 4 切换由控制台经 BFF 发起重新授权（`prompt=none` + 目标上下文），T-26 的范围铁律不变。Phase 5 刷新由 BFF 执行。identityToken 与 selection ticket 不离开认证服务。

**`contextSelectionTicket` 安全硬约束（红线 T-20 相关）：**

1. **绑定 Identity Token 的 `jti`（不止 `sub`）**：ticket 必须与签发它的 `identityToken.jti` 强绑定。仅绑 `sub` 不足——同一身份的另一枚有效 identityToken（或重放的旧 token）也能用同一 ticket。校验时要求 `ticket.bound_jti == identityToken.jti`，否则拒绝。
2. **一次性 + 短 TTL**：单次使用，使用后立即作废；TTL ≤ 5min（不超过 identityToken 寿命）。
3. **防枚举**：ticket 为高熵不可预测随机值（≥128bit），**不得**是自增/可猜的 contextId；服务端按 identity 维度限流，防止暴力探测他人上下文。
4. **防重放**：作废态持久化（Redis/DB），重复提交同一 ticket 返回 409/401 且记审计；identityToken 失效（jti 过期/撤销）后其名下所有 ticket 一并失效。
5. **稳定 `contextId` 不在选择阶段下发**：客户端在选择时只见 ticket；Token 签发后才在 `cid` 中持有稳定 contextId，用于后续切换/记忆。

### 9.4 B 端与 C 端登录逻辑分离

> B 端与 C 端登录入口与可见范围**严格分离**：**B 端只查询并返回 Actor 上下文，C 端只查询当前租户的 Subject 上下文**，C 端绝不暴露用户在其他租户的任何信息。**登录入口固定为** `/api/auth/login/actor` 与 `/api/auth/login/subject` **两个独立端点**；**`client_type` 不作为通道选择依据**。

| 维度 | B 端（Actor 入口，`/login/actor`） | C 端（品牌 App，`/login/subject`） |
|------|-------------------|---------------------------|
| 查询对象 | **仅** `sys_tenant_member`（Actor） | **仅** `sys_tenant_principal`（当前租户 Subject） |
| 跨租户可见性 | **可列出员工所属的多个租户**（走 §9.2 `discoverActor`） | **只能查询当前租户的 Principal** |
| 租户判定 | 登录后选择上下文 | 品牌/子域名已锁定单一 `tid`（仅作提示，仍以服务端绑定为准） |
| 返回信息 | 该 identity 的全部 actor contexts | **仅当前租户**的 subject context |
| 禁止项 | 不返回任何 Principal/Subject 信息 | **禁止返回该用户在其他租户接受服务的任何信息**（租户名、就诊记录、订单等一律不可见） |

> C 端实现要点：品牌 App 调用的发现接口**强制注入当前租户 `tid` 过滤**，`AuthnTenantLookupService.discoverSubject` **只查 `sys_tenant_principal WHERE tenant_id = :current AND identity_id = :id`**，不做跨租户聚合。B 端实现要点：`discoverActor` 只返回 `sys_tenant_member`，绝不附带 Principal。

> **v5.0**：两条入口的载体是身份协议面中的两类客户端与两套托管登录品牌（身份认证专项 BRX-IA-CLIENT-001）；C 端租户由品牌应用的客户端注册锁定（BRX-IA-CLIENT-003）。

### 9.5 同上下文双身份 & 设备记忆

- **同租户双身份**：以稳定 `contextId` 区分（§9.3），按 `tenant_id` 分组、角色标签区分，不显示为重复租户卡片。
- **C 端品牌 App** 直进当前租户 Subject 上下文，**永不弹选择器**（`UNIQUE (tenant_id, identity_id)` 保证同租户至多 1 个 Principal）。Context Selector / Context Switch **仅属 B 端 Actor 多租户场景**。
- **设备记忆**：仅由 Shared Runtime 的受管偏好/安全存储保存不可用于认证的 context preference handle，并结合服务端 `last_access_at` 排序。Plugin Page/Hook 不得直接写 localStorage/sessionStorage；Access/Refresh/selection ticket 永不持久化到浏览器通用存储。
- **受信设备**（v5.0）：免除第二因素的设备凭据由身份认证专项 BRX-IA-MFA-003 定义，与上下文偏好分开存储；二者都不能单独用于认证。

### 9.6 租户内对象级授权（同租户越权防护，红线 T-22）

> **`TenantInterceptor` 只解决"跨租户"，不解决"同租户内用户互相越权"。** 同一租户内，A 用户不得读写 B 用户的 Case / Order / File。租户隔离之上**必须再有对象级授权**。

**强制规则：**

1. **Subject 默认数据范围 = 自己**：Subject（C 端）默认**只能访问与自己 `principal_id` 关联的业务对象**（Case、Order、File、Appointment 等）。访问他人对象一律拒绝（403），除非有显式授权关系（如家庭共享、代理）。
2. **Actor 访问业务对象必须校验 permission + data scope**：Actor（B 端）访问业务对象时，既要校验**操作权限**（permission，如 `case:read`），又要校验**数据范围**（data scope，如"仅本部门 / 仅经手病例 / 全租户"）。角色 ≠ 无限数据范围。
3. **所有客户端传入的业务对象 ID 必须做授权校验**：任何来自请求的 `caseId` / `orderId` / `fileId` 等，**服务端必须校验该对象属于当前租户且当前主体有权访问**，禁止"传了 ID 就返回"（防 IDOR / 越权）。
4. **校验在服务端、靠不可篡改上下文**：授权主体取自已验签 JWT 的 `pid`/`mid` + `tid`，**不信任**请求体内的任何归属字段。

```text
对象级授权判定（每次访问业务对象 objId）：
  1. 加载对象 → 校验 obj.tenant_id == ctx.tid           （跨租户：T-9 拒绝）
  2. if ctx.isSubject():
        allow ⇔ obj.owner_principal_id == ctx.pid
                 OR 存在显式共享授权(objId, ctx.pid)
     else if ctx.isActor():
        allow ⇔ hasPermission(ctx, action)              （permission）
                 AND inDataScope(ctx, obj)               （data scope）
  3. 否则 403 OBJECT_ACCESS_DENIED + 审计
```

> 实现边界：L2B Dispatcher 先执行 Manifest 声明的 permission/resource policy，Plugin Owner 再在自身 domain/app 层使用已验证 actor/subject 与自身 Repository 判定对象归属和 data scope。不得为此在专项中新增未登记 `AuthorizationCapability`，也不得插件裸查后直接返回。

> **v5.1**：第 1、2 条的操作权限与数据范围由 §9.8 的授予表决定。Subject 访问业务对象同样先经 Dispatcher 按授予表校验操作权限，且只能获得 `SELF`；Actor 的数据范围本版本只有 `TENANT` 与 `SELF`，"仅本部门"等组织范围留待后续版本。判定伪代码中 `hasPermission` 与 `inDataScope` 的输入来自 Dispatcher 交给 Handler 的访问判定（§11.2 `BRX-TENANT-CONTRACT-007`），插件不得自行计算权限或解析角色。

### 9.7 租户员工 MFA 策略（v5.0）

[BRX-TENANT-AUTH-001] 全体租户员工（OWNER、ADMIN、MEMBER）一律强制双因素（身份认证专项 BRX-IA-MFA-002）。`sys_tenant.mfa_policy` 只能在此基线之上加强（例如要求防钓鱼因子、缩短受信设备期限），MUST NOT 关闭 MFA；只能由该租户的 ACTIVE OWNER 修改，并写租户审计。

[BRX-TENANT-AUTH-002] OWNER/ADMIN 重置成员的 MFA 因子时 MUST 先再验证、写租户审计，并使该成员的全部会话与受信设备失效；OWNER 本人的重置走平台受理流程（身份认证专项 BRX-IA-RECOVERY-002）。

### 9.8 租户最小 RBAC（v5.1）

> 决策背景：[RFC-003](./rfc/RFC-003-多租户-租户最小RBAC授权模型（Draft）.md)（2026-10-23 裁决）。本节定义租户员工（Actor）与 C 端用户（Subject）的功能级授权和数据范围；对象级授权的其余规则见 §9.6。平台超管的授权以 super-admin 专项为准，不在本节范围。

| 概念 | 定义 | 来源 |
|---|---|---|
| 角色 | Actor：OWNER、ADMIN、MEMBER；Subject：CUSTOMER、GUEST | `sys_tenant_member.member_type` / `sys_tenant_principal.principal_type` |
| 权限码 | 一个可授权操作的稳定 ID | 声明模块 Plugin Manifest 的 `permissions` |
| 授予 | 角色 → 权限码 + 数据范围 | 同一权限条目的 `grants: [{role, scope}]` |
| 授予表 | 已选模块全部授予的不可变汇总 | Runtime 在 H3/B2 构建 |
| 数据范围 | `TENANT`：当前租户的全部对象；`SELF`：与当前调用者关联的对象 | 授予声明；关联口径由资源 Owner 定义 |
| 访问判定 | Dispatcher 交给 Handler 的授权结果：命中的权限与数据范围 | 根 `BRX-RS-MANIFEST-022` 的 permission decision；交付方式见 §11.2 `BRX-TENANT-CONTRACT-007` |

声明示例（节选，权限 ID 为示例）：

```yaml
permissions:
  - id: example:order:read            # 管理接口用，只授予 Actor 角色
    grants:
      - {role: OWNER,  scope: TENANT}
      - {role: ADMIN,  scope: TENANT}
      - {role: MEMBER, scope: SELF}
  - id: example:my-order:read         # C 端接口用，只授予 Subject 角色，只能 SELF
    grants:
      - {role: CUSTOMER, scope: SELF}
endpoints:
  provides:
    - endpointId: example.order.list.v1
      authentication: {mode: required, policyRef: tenant-actor}
      authorization: {permissions: [example:order:read], decision: all}
      tenantContext: {mode: required, sourcePolicyRef: authenticated-tenant}
    - endpointId: example.my-order.list.v1
      authentication: {mode: required, policyRef: tenant-subject}
      authorization: {permissions: [example:my-order:read], decision: all}
      tenantContext: {mode: required, sourcePolicyRef: authenticated-tenant}
```

同一 identity 在同一租户同时持有 Member 与 Principal 时（§3），两个上下文各用一张 Token（T-5），分别按 `mtype` 或 `ptype` 计算有效权限，互不合并。员工能否用员工身份访问自己作为客户的对象，属于业务规则，由资源 Owner 判定并写审计，不在授予表中表达。

#### 9.8.1 条款

[BRX-TENANT-AUTHZ-001] 租户内可授予的权限码 MUST 只来自已装配插件的 Plugin Manifest `permissions` 目录（平台权限按 super-admin 专项管理，不在此列）。权限 ID 在 Host 内 MUST 唯一，重复声明 MUST 在 P0/O0 fail-fast；Endpoint `authorization.permissions` 引用未登记的权限 MUST 在 P3/B2 fail-fast。新增权限 ID SHOULD 以声明模块的命名空间开头。MUST NOT 在数据库中维护第二份可编辑的租户权限目录。

[BRX-TENANT-AUTHZ-002] 本版本租户角色只有内置角色：Actor 角色为 OWNER、ADMIN、MEMBER，取值即 `sys_tenant_member.member_type`；Subject 角色为 CUSTOMER、GUEST，取值即 `sys_tenant_principal.principal_type`。不提供租户自定义角色；租户范围的角色分配（包括 super-admin 4.0 §3.1 规划的 `sys_identity_role_assignment` 租户范围）在本专项定义自定义角色之前 MUST NOT 参与租户授权。Actor Token 的 `roles` claim 不是授权依据。Endpoint 需要按调用者区分访问时 MUST 以权限码声明，MUST NOT 以角色名替代（与 super-admin `BRX-SA-AUTH-006` 一致）。

[BRX-TENANT-AUTHZ-003] 声明权限的模块 MUST 在同一目录条目中声明该权限的默认授予 `grants: [{role, scope}]`。一个权限的授予 MUST 只包含一类角色：全部为 Actor 角色，或全部为 Subject 角色。未声明 `grants` 的权限不授予任何租户角色（默认拒绝）。模块 MUST 只能为自己声明的权限声明授予。

[BRX-TENANT-AUTHZ-004] Runtime MUST 在 H3/B2 期间由已选模块的声明汇总出不可变授予表，与 Host 入口准入快照属于同一代次；相同输入 MUST 得到相同结果（根 `BRX-RS-BOOT-008`）。下列情况 MUST fail-fast：`grants` 引用未知角色或未知范围；重复授予；一个权限的授予混用 Actor 与 Subject 角色；Subject 角色的授予范围不是 `SELF`；`tenant-actor` Endpoint 引用的权限授予了 Subject 角色，或 `tenant-subject` Endpoint 引用的权限授予了 Actor 角色。

[BRX-TENANT-AUTHZ-005] Dispatcher 的授权步骤 MUST 用已验证的角色查授予表得到有效权限与范围（Actor Token 用 `mtype`，Subject Token 用 `ptype`），再按 Endpoint `authorization` 的 `all`/`any` 判定；租户的 Actor Token 与 Subject Token MUST NOT 携带可被下游信任的权限列表；即使出现权限 claim 也 MUST 忽略。拒绝 MUST 在 Handler 前以稳定错误码返回并写安全审计。

[BRX-TENANT-AUTHZ-006] 数据范围本版本只定义 `TENANT`（当前租户的全部对象）与 `SELF`（与当前调用者关联的对象：Actor 为当前成员，Subject 为当前主体；关联口径由资源 Owner 在权限说明中定义）。Subject 角色只能获得 `SELF`（T-22）；Subject 访问本人以外的对象需要显式授权关系（如家庭共享、代理），不在本版本范围。Dispatcher MUST 把命中的最宽范围随访问判定交给 Handler；资源 Owner MUST 在自身 Repository 查询中施加该范围，MUST NOT 把 `SELF` 当作 `TENANT` 处理；声明了权限的 Endpoint 拿不到访问判定时 MUST 拒绝（fail-closed）。插件 MUST NOT 以已弃用的 `AuthContextCapability.getAuthorizedScopes()` 或自行解析的角色作为数据范围来源。

[BRX-TENANT-AUTHZ-007] 仅 OWNER 可执行的动作（修改 `mfa_policy`、转移所有权、任命 OWNER）MUST 以只授予 OWNER 的权限码表达。"ADMIN 不得管理 OWNER"等对象关系约束 MUST 由资源 Owner 的 resource policy 判定，MUST NOT 只靠前端隐藏。

[BRX-TENANT-AUTHZ-008] `member_type`、`principal_type` 或 `status` 变更 MUST 使对应行的 `authz_version` 自增（§8.2）。授予表随 Host 制品变化；模块升级后的授予在 Host 重启后生效，不触发 `authz_version` 自增，也不要求重签 Token。

[BRX-TENANT-AUTHZ-009] BFF 会话接口 MUST 返回由同一授予表、按当前上下文（Actor 或 Subject）计算的有效权限集合，MUST NOT 合并同一 identity 其他上下文的权限；员工控制台与品牌应用的 Route Guard 和操作入口显隐只依据它（frontend `BRX-FE-ROUTE-002`、`BRX-FE-AUTH-002`）。前端隐藏 MUST NOT 被当作授权。

[BRX-TENANT-AUTHZ-010] 成员与主体的角色变更、被拒绝的授权判定 MUST 写租户审计（T-25），MUST NOT 记录 Token 原文或其他凭证材料。

[BRX-TENANT-AUTHZ-011] 资源 Owner 认定为对 C 端公开的数据（如服务目录、门店信息、可预约时段）MAY 由不声明权限码的 C 端 Endpoint 提供：认证策略为 `tenant-subject`，或经版本化 allowlist 审批的匿名访问。这类 Endpoint MUST NOT 返回或修改个人数据及个人的业务对象（如病例、订单、文件）。员工访问同一数据 MUST 走声明权限码的管理接口；修改公开数据的 Endpoint MUST 按权限码授权。

[BRX-TENANT-AUTHZ-012] 要求租户上下文的 Endpoint（`tenantContext.mode=required`）MUST 在 `authentication.policyRef` 中二选一：`tenant-actor`（管理接口，只接受 Actor Token）或 `tenant-subject`（C 端接口，只接受 Subject Token），落实 §8.1 第 3 条与 T-11。同时接受 Actor 与 Subject Token 的认证策略 MUST NOT 用于租户 Endpoint。

#### 9.8.2 租户控制台权限码目录（platform-tenant）

表中填写授予的数据范围，`—` 表示不授予。这些权限只授予 Actor 角色，对应 Endpoint 声明 `tenant-actor`。

| 权限码 | 用途 | OWNER | ADMIN | MEMBER |
|---|---|---|---|---|
| `tenant:profile:read` | 查看本租户基本信息 | TENANT | TENANT | TENANT |
| `tenant:member:read` | 查看成员 | TENANT | TENANT | SELF |
| `tenant:member:invite` | 邀请、重发、撤销成员邀请 | TENANT | TENANT | — |
| `tenant:member:update-role` | 在 ADMIN 与 MEMBER 之间调整 | TENANT | TENANT | — |
| `tenant:member:disable` | 停用、恢复成员 | TENANT | TENANT | — |
| `tenant:member:reset-mfa` | 重置成员的 MFA 因子（须满足 `BRX-TENANT-AUTH-002`） | TENANT | TENANT | — |
| `tenant:owner:transfer` | 任命 OWNER、转移所有权（受 T-18 约束） | TENANT | — | — |
| `tenant:security:update` | 修改 `mfa_policy` 等安全设置（`BRX-TENANT-AUTH-001`） | TENANT | — | — |
| `tenant:audit:read` | 查看租户审计 | TENANT | TENANT | — |

对象关系约束由 platform-tenant 的 resource policy 判定：ADMIN 不能调整、停用或重置 OWNER；ADMIN 只能邀请 ADMIN 或 MEMBER，目标角色为 OWNER 的邀请只有 OWNER 能创建、重发和撤销（§5.5，v5.1.1）；任何人不能降级或停用最后一个 ACTIVE OWNER（T-18）；OWNER 本人的 MFA 重置走平台受理流程（身份认证专项 BRX-IA-RECOVERY-002）。C 端用到的权限由各业务插件另行声明，只授予 Subject 角色。

#### 9.8.4 本版本不做（⏳）

- 租户自定义角色与角色继承。不同岗位（如医生与其他职员）在本版本都是 MEMBER：与对象有关的操作可以用 `SELF` 加资源 Owner 定义的关联区分，与对象无关的功能无法按岗位区分；
- 部门、组织、区域等数据范围；
- ABAC/ReBAC、对象级共享与代理授权（§16）；
- Query/Command/Task 的按角色授权，本版本保持各自的 Manifest access policy；
- 平台超管授权的统一，由 super-admin 下一版评估。

## 10. 全栈租户隔离

> **隔离不止于 SQL。** 任一基础设施漏过 tenant 即构成越权面。以下为最小实现必须覆盖的隔离面（红线 T-14）。

| 基础设施 | 隔离要求 | 实现要点 |
|----------|----------|----------|
| **关系数据库** | Repository/Unit of Work 自动绑定 tenant policy | PersistenceCapability 代理 + L2C tenant policy；插件无裸 SQL/连接 |
| **缓存** | Key 自动带 tenant namespace | Cache Capability/L2C 生成 `{tid}:{owner}:{domain}:{key}`；插件不拼接全局裸 Key |
| **EventBus** | canonical Envelope 的 `scope=TENANT` 时 `tenantId` 必填 | L2B 校验 Envelope 后构造 EventInvocation；Plugin 不接触 Kafka/Rabbit |
| **对象存储** | namespace + 下载授权校验 tenant | ObjectStorage Capability/L2C 映射受控路径；插件不接触 MinIO/S3 client |
| **Scheduler / 异步执行** | Runtime 构造并在完成、异常、取消后释放 Invocation Context | Managed Task/Capability；禁止插件线程池、`@Scheduled` 和 TaskDecorator 自管 |
| **消息消费** | L2B 从已验证 canonical Envelope 构造 EventInvocation | Handler 完成后 Runtime 清理；插件不从 broker header set/clear context |
| **搜索索引** | 文档带 `tenantId`，查询强制过滤 | 索引 schema 含 `tenantId`；查询注入过滤器 |
| **导出 / 报表** | 导出范围限定当前 tenant | 导出服务复用 TenantContext，禁止跨租户聚合 |
| **审计日志** | 租户业务审计每条含 `tenantId`；平台/跨租户操作走独立 Platform Audit | 见 §10.1 |

> **上下文清理是硬约束**：线程池复用线程，若异步/消费任务完成后残留 context，会把上一个租户泄漏给下一个任务。L2B/L2C 可以内部使用 ThreadLocal/Reactor Context，但必须在 CompletionStage 完成、异常或取消后清理；插件不得取得、set/clear 或把这些载体作为正确性依据。

### 10.1 审计分层 — 租户审计 vs 平台审计（红线 T-25）

> **一张审计表无法同时正确表达"租户内业务操作"与"跨租户/平台操作"。** 强行用单一 `tenant_id` 绑定跨租户审计会丢真相（跨租户操作没有唯一 tenant）。因此**拆两套审计**：

| 审计类型 | 表 | `tenant_id` | 记录内容 |
|----------|----|:-----------:|----------|
| **租户目录审计** | `biz_tenant_audit_log` | **NOT NULL** | `platform-tenant` Owner 内的成员、主体、邀请、授权和生命周期变更 |
| **平台审计** | `sys_platform_audit_log` | **可空 / 多值** | `platform-audit` Owner 持有；登录发现、平台超管跨租户运维、License 与红线治理 |

```sql
-- 租户业务审计：强制单租户绑定
CREATE TABLE IF NOT EXISTS biz_tenant_audit_log (
    id          BIGINT PRIMARY KEY,
    tenant_id   BIGINT NOT NULL,                 -- 强制 NOT NULL
    actor_ref   VARCHAR(64),                     -- member_id / principal_id
    action      VARCHAR(100) NOT NULL,
    object_ref  VARCHAR(128),
    detail      JSONB,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_tenant_audit_tenant ON biz_tenant_audit_log(tenant_id);  -- 红线 T-1：租户业务表 tenant_id 必建索引
CREATE TABLE IF NOT EXISTS sys_platform_audit_log (
    id            BIGINT PRIMARY KEY,
    operator_ref  VARCHAR(64) NOT NULL,          -- platform_admin_id / identity_id
    action        VARCHAR(100) NOT NULL,         -- LOGIN_TENANT_DISCOVERY | CROSS_TENANT_QUERY | LICENSE_CHANGE ...
    affected_tenants JSONB,                      -- 命中/影响的租户集合（0..N），不绑单一 tenant_id
    detail        JSONB,
    ip            VARCHAR(64),
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**约束：**

1. `platform-tenant` 自身目录操作在同一 Owner 本地事务写其受托 `biz_tenant_audit_log`，`tenant_id NOT NULL`；其他业务 Plugin 的审计由各自 Owner 持有，不得跨表写入本表。
2. **登录期跨租户发现 / 平台超管跨租户查询 / License 与红线治理操作**写 `sys_platform_audit_log`，**不得**硬塞一个 `tenant_id`，用 `affected_tenants` 记录 0..N 个受影响租户。
3. `sys_platform_audit_log` 属平台全局表（白名单），由平台审计 Data Owner 唯一拥有；仅 `platform-admin` 可通过 descriptor 声明并经 privilege allowlist 批准的内部契约读取，禁止直接 Repository/Service 注入。
4. `detail` 与 `affected_tenants` 必须遵守根蓝图数据分类和脱敏规则，禁止写入 secret、credential、原始 token、密码、MFA secret 或未获批准的 PII。
5. `platform-admin` 写平台审计时，L2B 代理必须挂起调用方事务，由平台审计 Data Owner 在自身 context 的独立本地事务中提交；不得跨 Owner 传播连接、`EntityManager` 或 Session。
6. 本专项不新增 Timeline 表、Timeline Capability 或跨 Owner 投影。若产品需要租户生命周期 Timeline，必须由明确 Owner 订阅 canonical Integration Event 构建自有只读投影，声明延迟、重建、授权和 tenant scope；Timeline 不得成为第二权威写模型，也不得替代审计或 Outbox。

## 11. 能力契约（runtime-sdk-api）

> 接口签名是契约红线：演进只能 (a) 新增带 `default` 的方法，或 (b) 新增可选 Capability。破坏性变更走 [§13 红线变更治理](#13-红线变更治理)。

### 11.1 TenantContext 架构分层（红线 T-21）

| 层 | 职责 | 内容 |
|----|------|------|
| **Layer 2A**（`runtime-sdk-api`） | **仅定义** | 根蓝图目录中的 `TenantContextCapability`、租户/访问上下文不可变模型，以及租户领域 typed Query/Command/Event Schema |
| **Layer 2B**（Runtime） | **统一解析与策略代理** | 在 HTTP/Query/Command/Event/Task Dispatcher 边界验证 tenant/scope，并构造不可变 Invocation Context；向插件注入绑定 module identity 的 `TenantContextCapability` 代理 |
| **Layer 2C**（Adapter） | **基础设施映射** | 仅实现数据库、消息、缓存、对象存储等 tenant 隔离映射；不得向插件暴露 ThreadLocal、Servlet、Broker SDK 或底层客户端 |

**上下文传播矩阵（L2B Runtime 统一控制，L2C Adapter 仅消费经验证上下文）：**

| 运行模型 | 传播方式 | 清理 |
|----------|----------|------|
| HTTP（Servlet/WebFlux） | L2B Dispatcher 验证入口声明、Token 与 tenant hint 后构造 `EndpointInvocation` | 以调用完成、异常或取消为边界释放；Handler 不接触 Servlet/Reactor 原始上下文 |
| Query | L2B Query Gateway 从调用方 Invocation Context 派生 `QueryInvocation.scope` | `CompletionStage` 结束后释放，不使用插件 ThreadLocal |
| Command/Event | L2B Relay 验证 Envelope 的 scope/tenant/publisher 后构造 `CommandInvocation` / `EventInvocation` | 投递完成后释放；Handler 不自行读取消息头 |
| Scheduler Task | L2B Scheduler 根据 Manifest 的 scope/execution identity 策略构造 `TaskInvocation` | 任务完成、异常或取消后释放；禁止 `@Scheduled` 旁路 |
| 基础设施异步操作 | Runtime 管理的 Capability 代理显式传递不可变 Invocation Context | 受管资源账本负责有界停止和清理 |

> 兼容实现内部 MAY 使用 ThreadLocal 或 Reactor Context 作为 L2B 私有载体，但它不是插件契约，MUST NOT 由插件 set/clear、读取或作为正确性依据。

### 11.2 后端契约（Layer 2A）

```java
/**
 * Root Catalog 中唯一的租户上下文 Capability。
 * Runtime creates and verifies the context; plugins never parse or replace it.
 */
public interface TenantContextCapability {
    String getCurrentTenantId();              // @since 0.1
    Tenant getCurrentTenant();                // @since 0.1
    void   requireActiveTenant();             // @since 0.1

    // --- B2B2C 双轨 ---
    String getCurrentRole();                  // "actor" | "subject"
    String getCurrentRoleType();              // OWNER/ADMIN/MEMBER | CUSTOMER/GUEST
    String getCurrentRefId();                 // Actor→memberId, Subject→principalId
    String getCurrentUserId();                // biz_user_profile.id
    default boolean isActor()   { return "actor".equals(getCurrentRole()); }
    default boolean isSubject() { return "subject".equals(getCurrentRole()); }

    default boolean isFeatureEnabled(String key) { return false; }  // fail-closed
}
```

[BRX-TENANT-CONTRACT-001] `TenantContextCapability` 只返回 Runtime 已验证的当前 tenant、scope、actor、subject 和隔离上下文，不提供租户列表、成员、邀请、配额、生命周期或领域 CRUD。插件通过 `PluginContext.require/find` 取得其 Manifest 已声明的代理；不得直接注入实现。

[BRX-TENANT-CONTRACT-002] 本专项不定义 `TenantDirectoryCapability`、`TenantQuotaCapability`、`TenantConfigCapability`、`BusinessObjectCapability`、`AdminCapability` 或 `PlatformAdminCapability`。新增平台 Capability 必须先经 Root RFC 登记到 Capability Catalog；专项蓝图不能以“底座必需”为由创建目录外接口。

租户领域公开契约属于 `platform-tenant-api` 的 Plugin Public Contract，不属于平台 L2A Capability：

| 类型 | Schema/契约 | 作用域与语义 |
|---|---|---|
| typed Query | `TenantReferenceQuery` | 在 Runtime 注入的当前 tenant scope 内校验 `refId + RefKind`；只读，不接受 authority tenantId |
| typed Query | `TenantDirectoryQuery` | Owner 的租户/Member/Principal/邀请只读 DTO；调用方 scope/access policy 由 Manifest 声明 |
| typed Query | `TenantUsageQuery` | 当前 tenant，或经批准的 platform-operational 调用方的类型化用量 |
| typed Command | `TenantMemberCommand` | 跨 Plugin 成员状态变更意图；异步、唯一 Owner、canonical sender Outbox |
| typed Event | `TenantFirstOwnerAccepted` | 首位 OWNER 已提交事实；`CRITICAL` |
| typed Event | `TenantStatusChanged` | 租户状态已提交事实；可靠性由版本化 Schema 固定 |

[BRX-TENANT-CONTRACT-003] `TenantReferenceQuery` 的请求必须显式包含 `RefKind=MEMBER|PRINCIPAL`，因为两类 ID 可能重复；不得按 ID 猜类型。L2B Query Gateway 从 Invocation Context 派生 tenant scope，在 Owner 独立 read-only Unit of Work 中执行，并挂起调用方写事务。

[BRX-TENANT-CONTRACT-004] 当前租户的非敏感类型化配置通过根 Catalog 的 `ConfigCapability` 读取 Manifest 已声明 key；Secret 通过 `SecretCapability`。租户配置管理仍由 Owner typed contract 或 `TenantAdministration` 提供。

[BRX-TENANT-CONTRACT-005] 平台只读租户数据使用 descriptor 声明的 typed Query；平台运维写使用 `brix.internal.tenant.administration`。`platform-admin` 的 descriptor 必须声明 `internalContracts.requires`、Brix Range v1、`required` 和 privilege allowlist，O1/H3 缺失、重复、越权或版本不匹配均 fail-fast。

[BRX-TENANT-CONTRACT-006] 预期失败使用继承根级 `BrixException` 的稳定错误目录。领域异常只携带 `ErrorCode`、批准的 immutable `safeParameters` 和 cause；traceId 由 L2B Error Boundary 写入外部 Error Envelope、结构化日志和审计，不进入 domain exception。

[BRX-TENANT-CONTRACT-007] 授权结果的交付（v5.1）：Dispatcher 通过 `EndpointInvocation` 的可选访问判定，把命中的权限与数据范围交给 Handler（§9.8 `BRX-TENANT-AUTHZ-006`）。根 §5.4 对 `EndpointInvocation` 的要求是"至少提供"，根 `BRX-RS-MANIFEST-022` 已规定 Dispatcher 向 Handler 传递 permission decision；该字段按根 `BRX-RS-CAP-019`/`020` 作为 L2A Minor 扩展引入，可选且缺省语义明确（缺省表示该 Endpoint 未声明权限码），不新增 Capability。本版本据此认定它不属于 §13 第 6 条所指的根级 Envelope 变更，不需要先行 Root RFC。插件 MUST NOT 自行计算权限。

### 11.3 前端契约（遵循 frontend 1.2）

```typescript
// 前端契约按 B/C 身份分层，明确表达切换能力归属

/** 共同字段：两端都有 */
interface TenantContextBase {
  tenantId: string;
  tenant: TenantInfo;
  currentContext: {
    contextId: string;          // 稳定访问上下文 ID（= Token cid）
    // role 不在 currentContext 中——顶层 role 即判别字段，防止两处不一致
    roleType: string;          // OWNER|ADMIN|MEMBER | CUSTOMER|GUEST
    refId: string;             // memberId | principalId
    userId: string;
    displayName: string;
  };
  isFeatureEnabled: (feature: string) => boolean;
}

/** B 端 Actor：支持多上下文切换 */
interface ActorTenantContextState extends TenantContextBase {
  role: 'actor';                              // 顶层判别字段（法作 narrow 类型）
  availableContexts: AccessContextOption[];   // 该 identity 在各租户的 Actor 上下文
  switchContext: (contextId: string) => Promise<void>;  // 切到同一 identity 其他 Actor 上下文（T-26）
}

/** C 端 Subject：不提供切换（UNIQUE(tenant_id,identity_id) 保证单租户至多 1 个 Principal） */
interface SubjectTenantContextState extends TenantContextBase {
  role: 'subject';                            // 顶层判别字段
  // 无 availableContexts / switchContext
}

type TenantContextState = ActorTenantContextState | SubjectTenantContextState;

// useTenant() is provided by the shared frontend runtime.
declare function useTenant(): TenantContextState;
```

租户页面的依赖方向固定为：

```text
Page → Hook/ViewModel → Repository → HttpCapability/generated typed Query client
```

[BRX-TENANT-UI-001] Page 只渲染和绑定事件；Hook/ViewModel 负责加载、取消、重试、分页、表单校验、重复提交阻断和稳定错误；Repository 负责 DTO/Schema/错误映射，只能使用 Runtime 注入的 `HttpCapability` 或生成 typed client。任何层都不得解析 JWT、取得裸 Token、直接 `fetch/axios` 或跨插件导入 Repository。

[BRX-TENANT-UI-002] Platform Tenant UI 只使用 Platform Token，租户管理 UI 只使用 Actor Token，Subject UI 只使用 Subject Token；v5.0 起浏览器端经 BFF 会话使用，前端不持有 Token。Route/Guard 只依据 Auth Capability 的已验证 session/scope/permissions；切换上下文必须清空 query cache、业务状态和旧路由准入。v5.1：权限只来自 BFF 会话接口按当前上下文计算的有效权限（§9.8 `BRX-TENANT-AUTHZ-009`）。

[BRX-TENANT-UI-003] 所有组件和反馈必须经 BrixUI/useUI；异步页面必须覆盖首次加载、刷新、可重试错误、403、空状态、成功、取消和重复提交。邀请接受页设置 `Referrer-Policy: no-referrer`，安全 token 只在完成流程所需的最短内存生命周期存在。

| 前端模块/页面 | Page | Hook/ViewModel | Repository | Route/Guard |
|---|---|---|---|---|
| Platform tenant list/detail | `PlatformTenantListPage` / `PlatformTenantDetailPage` | `usePlatformTenantList/Detail` | `PlatformTenantRepository` → HttpCapability | `/platform/tenants/**` + PlatformAuthGuard + concrete permissions |
| 创建待激活租户 | 详情内受控 Form | `useCreatePendingTenant` | `PlatformTenantRepository.createPending()` | 不提交 ownerIdentityId；重复提交阻断 |
| FIRST_OWNER 发起/重发/撤销 | 详情邀请区 | `useFirstOwnerInvitation` | `PlatformTenantRepository` | Platform Token + invite permission；不显示 token/URL |
| FIRST_OWNER 接受 | 托管设置/接受页（身份协议面） | — | 租户 Owner 的接受接口 | 不在 `/platform/**`；no-referrer；token memory-only（身份认证专项 BRX-IA-ONBOARD-002） |
| Actor context selector/switcher | 选择页在身份协议面的托管登录中；控制台只保留切换入口 | `useActorContexts`（切换经 BFF） | BFF 会话接口 | Actor-only Guard；切换后清空 cache/state |

### 11.4 契约失败与预算策略

| 契约 | Deadline/SLO 来源 | 失败行为 |
|---|---|---|
| `TenantContextCapability` | Host Profile + Capability contract | 缺失或非法上下文抛稳定 `BrixException`，fail-closed |
| typed Query | Manifest consumer timeout policy + 平台硬上限 | not-found=empty；Provider 缺失=`PROVIDER_MISSING`；超时/拒绝不伪装 empty |
| typed Command | Manifest retry/idempotency policy | durable receipt 仅表示发送方 Outbox 已提交，不表示业务完成 |
| `ConfigCapability` | Catalog contract + Manifest key declaration | 未声明/类型不匹配拒绝；feature 缺失按明确 fail-safe 默认 |
| `TenantAdministration` | operational descriptor + privilege allowlist | 未声明、未授权或 Provider 不唯一在 O1/H3 fail-fast |

### 11.5 跨租户参数与运维约束（红线 T-23）

1. 普通插件的租户操作不接受作为 authority 的任意 `tenantId`；作用域来自 Runtime 构造的 Invocation Context。业务 DTO 中需要 tenant 标识时只能用于一致性断言，冲突必须拒绝。
2. **跨租户只读查询/聚合必须由对应 Data Owner 发布版本化 typed Query**；`platform-admin` 只能按 descriptor 的 `queries.consumes`、scope/access policy 和 Runtime 构造的 Invocation Context 调用，每次调用记 Platform Audit（§10.1）。
3. **跨租户运维写动作必须通过 Data Owner 的版本化内部契约**；`platform-admin` 仅可经 `OperationalContext` 调用 descriptor `internalContracts.requires` 已声明且 privilege allowlist 批准的唯一 Provider。普通插件不得消费、枚举或查找内部契约。
4. 禁止定义本节已列出的未登记 Capability 或任何通用跨租户 Capability；构建期以 Catalog diff、API signature、artifact graph 和依赖白名单阻断。
5. `TenantAdministration` Provider 在自身 Owner context 开启独立本地事务，不传播 operational caller 的连接、EntityManager/Session 或 Unit of Work。

### 11.6 事件、Outbox 与 Inbox（红线 T-24）

| 类型 | 边界 | 交付语义 |
|---|---|---|
| Domain Event | `platform-tenant-core` 内部 | 可携带领域对象，不构成跨 Plugin 契约 |
| Integration Event | 跨 Plugin 已提交事实 | 版本化 Schema + 根蓝图 canonical Envelope；CRITICAL/STANDARD 使用 transactional Outbox |

[BRX-TENANT-EVENT-001] 本专项不得声明 Java `EventEnvelope`、broker header 形状或第二套消息框架。所有 Integration Event 必须使用根蓝图统一 Envelope，完整包含 `eventId`、`eventType`、`schemaVersion`、`occurredAt`、`producerPluginId`、`scope`、条件必填 `tenantId`、`correlationId`、`causationId`、W3C trace context、`partitionKey` 和 `payload`。

[BRX-TENANT-EVENT-002] `TenantFirstOwnerAccepted` 是 `CRITICAL` 已提交事实。邀请接受的业务写、Owner 受托审计和 canonical Outbox record 必须在 `platform-tenant` 同一本地事务中提交；不得在事务内直接发送 broker 消息。

[BRX-TENANT-EVENT-003] Manifest `storageId` 固定为 `platform_tenant`，canonical 表名为 `platform_tenant_outbox` / `platform_tenant_inbox`，发布后不可变。Relay 只获得受托表最小权限，不读取租户业务表。

[BRX-TENANT-EVENT-004] Relay 重试和同一事实重放保持 `eventId`。Consumer 以 `(handlerId,eventId)` 持久化 Inbox 去重，并把去重与自身业务副作用放在同一 Consumer Owner 本地事务。Brix 只声明 at-least-once，不声明 Exactly Once 或全局顺序。

[BRX-TENANT-EVENT-005] Event Subscription 只在 Manifest 声明并由 Runtime 创建 Handler/受管订阅。Plugin core/server 不得依赖 Kafka/Rabbit SDK、topic 字符串、`@KafkaListener`、`@RabbitListener` 或 broker message 类型。

### 11.7 Runtime Entry、Manifest 与启动边界

[BRX-TENANT-ENTRY-001] `platform-tenant-server` 在固定路径 `META-INF/brix/plugin-manifest.yaml` 提供唯一 YAML Manifest；不得保留 JSON/代码 descriptor 第二 SSoT。HTTP、Query、Command、Event 和 Task 的完整入口集合必须在 Manifest 声明。

[BRX-TENANT-ENTRY-002] 唯一 `BrixPlugin` provider 的 `configure(PluginBootstrapContext)` 只登记 Manifest 已声明的 Handler/Task Factory，不获取 Capability/PluginContext、不创建 Handler、不访问业务 Service/Repository、不启动线程/订阅/Task、不发布入口。Factory 只在 B2 后通过 `create(PluginContext)` 取得已声明 Capability。

[BRX-TENANT-ENTRY-003] 禁止 Spring `@RestController`/`@RequestMapping` 自动发布、ComponentScan 组装、`ApplicationContext`/`BeanFactory` 查找、静态 Registry/Holder、直接 Handler Bean 注入、`@Scheduled`、broker listener 和 Host fallback。

[BRX-TENANT-ENTRY-004] 所有 Endpoint/Query/Command/Event/Task 在 B3/P8 前保持 `UNPUBLISHED`。首次发布以 Host 完整入口代次原子提交；Drain/Fatal 先原子关闭全部新准入，再等待 in-flight，随后有界 `onStop` 并由 L2B 资源账本逆序释放受管资源。

[BRX-TENANT-ENTRY-005] FIRST_OWNER 接受入口必须由 Manifest 声明，`tenantContext.mode=forbidden`（authority tenant 来自锁定邀请，不来自调用方 tenant context）、authentication=verified Actor identity、authorization=版本化 acceptance policy、idempotency=required。调用方不得提交或覆盖 tenant authority、purpose、inviter type、platform operator ref、target role 或 owner member id。

| **T-24** | Integration Event 只使用根蓝图 canonical Envelope，完整字段、scope/tenant 条件和 Outbox/Inbox 语义不得由专项或 broker 私有信封重定义 | Schema compatibility + relay/replay tests | 阻断发布 |
| **T-25** | 审计分层：租户业务审计 `tenant_id NOT NULL`；跨租户/平台操作走独立 Platform Audit，禁止强绑单一 tenantId | Schema lint + 审计写入测试 | 阻断发布 |
| **T-26** | 上下文切换范围：仅 Actor Token 可切换且只能切到同一 identity 的其他 Actor 上下文；Subject Token 禁切（不可切 Actor、不可跨租户）；Actor↔Subject 转换必须重走对应登录入口 | 切换接口授权测试 + 越权用例 | 切换拒绝 + 审计 |
| **T-27** | 租户状态变迁与配额 `used` 必须同事务原子变更，且先 `SELECT FOR UPDATE` 锁 `sys_installation_quota` 配额行；恢复租户必先检查并预占名额 | 配额并发测试 + 事务原子性测试 | 阻断发布 |
| **T-28** | 新增租户必须保持 `PENDING_ACTIVATION`，不得自动创建 OWNER；首位 `OWNER` 必须经 `FIRST_OWNER` 邀请接管，并在接受事务内创建 `ACTIVE OWNER` + Profile、激活租户、占用配额；禁止平台超管伪装成租户 Member | 租户创建测试 + 邀请接受事务测试 + 幂等/重放测试 + 一致性巡检 | 阻断发布 + 安全告警 |
| **T-29** | 租户权限码只来自已装配模块的声明目录；Endpoint 的权限判定只用权限码、不用角色名；声明的权限未授予即拒绝（v5.1） | Manifest/授予表校验 + Dispatcher 负例测试 | 启动阻断 / 403 |
| **T-30** | 租户 Actor 与 Subject 的有效权限只由 Runtime 授予表根据已验证角色（`mtype`/`ptype`）计算；Token 中的权限列表不得作为授权依据（v5.1） | 签发与校验负例测试 | 签发拒绝 / 校验拒绝 |

## 14. 数据隔离策略（演进路径 + 可选 RLS 第二道防线）

### 14.1 隔离级别演进

| 级别 | 实现 | 版本 | 触发条件 |
|------|------|:----:|----------|
| **Row-Level** | `tenant_id` 字段 + 拦截器自动过滤；`TenantSqlGuardInterceptor` 防绕过 | **最小实现（默认）** | 默认 |
| Schema-Level | 动态 `search_path` / `SET SCHEMA` | v2.0+ | 中大租户 / 合规 |
| Database-Level | 动态数据源路由 | 企业版按需 | 数据主权 / 独立部署 |

> 所有隔离方案统一经 `TenantContextCapability` 与绑定 module identity 的基础设施 Capability 策略代理生效，插件代码零感知底层隔离实现。

### 14.2 可选 PostgreSQL RLS（应用层之外的第二道防线，红线相关 T-2/T-9）

> 通用版本以应用层 `TenantInterceptor` 为主隔离手段。在 **PostgreSQL** 上可额外启用 **行级安全（RLS）Adapter** 作为**数据库层兜底**——即使应用层出现遗漏，数据库仍强制隔离。

```sql
-- 启用 RLS（以 medical_case 为例）
ALTER TABLE medical_case ENABLE ROW LEVEL SECURITY;
ALTER TABLE medical_case FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON medical_case
    USING (tenant_id = current_setting('brix.tenant_id')::BIGINT);
-- 每个请求在连接上 SET LOCAL brix.tenant_id = '<tid>'（由 RLS Adapter 注入）
```

**RLS 硬约束：**

1. **医疗等高敏感部署建议启用 RLS**（合规与纵深防御）。
2. RLS Adapter 在每个事务开始时 `SET LOCAL brix.tenant_id`，与 `TenantContext` 同源。
3. **生产数据库账号禁止拥有绕过 RLS 的权限**（不得为 superuser / `BYPASSRLS`）；迁移/运维用单独受控账号。
4. RLS 是**第二道防线**，不替代应用层隔离；两者并存。

## 15. 配额与 License 失败策略（统一 fail 语义）

> 取消"放行默认值"。`checkQuota()` 旧设计（默认返回 `true`）**已删除**，改为 `requireQuota()` 显式抛异常。

| 校验类型 | 失败策略 | 说明 |
|----------|:--------:|------|
| 安全隔离校验（tenant/JWT/越权） | **fail-closed** | 任何异常 → 拒绝请求 |
| License 上限（租户数/席位） | **fail-closed** | 不满足 → 拒绝新增（不影响存量，见 §1） |
| 硬配额（maxUsers/maxPrincipals） | **fail-closed** | 超限 → `QuotaExceededException` |
| 非关键统计 / 用量计数 | **fail-open + 必须告警** | 计数失败不阻断主流程，但必须打点告警 |

> **绝不允许**安全或上限类校验"出错即放行"。仅**非关键统计**允许 fail-open，且必须触发告警，禁止静默吞错。

## 18. 运行壳架构对齐

| 运行壳层 | 多租户构件 | 职责 |
|----------|-----------|:----:|
| **Layer 1 Plugin API** | `TenantReferenceQuery`、`TenantDirectoryQuery`、`TenantUsageQuery`、`TenantMemberCommand`、tenant Integration Event Schema，以及受限 provider-binding 的 `TenantAdministration` 实现入口 | **Owner 公共/内部契约，不是平台 Capability** |

| **Layer 2C Adapter** | 数据库、Cache/EventBus/ObjectStorage/Search 与可选 RLS 的 tenant 隔离映射；不得向插件暴露 SDK/client 或上下文载体 | **基础设施实现** |

| **前端 Shared Runtime** | `useTenant()`、Auth/Route/Guard、HttpCapability（经 BFF 会话）、BrixUI/useUI | **frontend 1.2 唯一共享运行时** |

> 对插件开发者：当前 tenant context 通过 Catalog Capability 获取，领域协作通过 generated typed contract 完成；插件零感知 Owner 存储和 L2C 隔离实现，禁止直接依赖平台租户表、Owner Entity/Repository/Service 或跨服务外键。
