## 0. 结论摘要

1. **目标**：
   - P-1 `login-tenant-discovery`、P-3 `first-owner-invitee-setup-fanout` 每使用一次，就在 `sys_platform_audit_log` 留一条平台审计；审计写不进去，这次使用就失败（fail-closed）。
   - 同时把这张表从 platform-identity 交给 super-admin 4.0 规定的唯一 Owner `platform-audit`。
2. **写入路线（推荐）**：Runtime 作为平台审计表的登记受托写入方（Custodian）。
   - 根 DATA-006 已点名"审计写入器"可以作为 Custodian 访问受托运行表；DATA-004 把平台审计列为平台受托表。
   - L2B 定义写入端口，L2C 持久化适配器实现。做法与现有的 Outbox relay（`OutboxMessageStore` + `JdbcOutboxMessageStore`）相同。
   - L2B 不引用任何平台模块，不新增 L2A Capability，L2B 和身份协议面都不消费内部契约。
   - platform-audit 在自己的 Manifest 里登记这项受托写入：只能 INSERT，只能写两个策略动作，只能写列出的列。
3. **事务与 fail-closed**：每条记录在只写平台审计表的独立本地事务中提交，调用方事务挂起（与 DATA-029、HOST-020 同一规则）。
   - P-1：读完成员记录后、把结果交给调用方之前写审计。写失败则丢弃结果并报错。
   - P-3：在 platform-tenant 的事务提交之前写审计。写失败则该事务回滚。
4. **platform-audit 拆分**：新建 platform-commons 下的 L1 Data Owner `platform-audit`，接管表、Schema、迁移和写规则。存量行原地保留，按 expand / migrate / contract 三步转移（§3.4）。
5. **内部契约** `brix.internal.platform.audit`（`PlatformAuditAdministration` 1.0.0）：按 super-admin §2.1 实现"平台审计写入和受限查询"。唯一消费方是 platform-admin（经 `OperationalContext`）。
6. **待你确认**：6 个决定 D1～D6（§7）。另有一处蓝图解读需要在 RFC 中确认：super-admin §1.3a 红线"所有审计写入只能经内部契约"的适用范围（§2.1）。
7. **需要批准**（§8）：
   - R1：一份根级 Minor RFC（RFC-008）：受托写入的登记格式、Runtime 策略审计写入器、策略审计的失败语义与同步阻断范围；
   - R2：一条有期限的豁免：拆分期间 platform-identity 继续直接写自己的审计行。
8. **施工**：分 4 期（§9）。建议等 `claude/tenant-isolation-l2c` 合并后另开分支，不与 RFC-007 绑在一起。

### 2.1 需要确认的一处解读

super-admin §1.3a 的红线写着："所有审计写入只能经已声明、已授权的内部契约"。

- **按全局理解**：任何人写平台审计都必须经内部契约。而 C-3 规定只有 platform-operational 能消费内部契约，multi-tenant §6.3、§6.4 又要求不经过 platform-admin 的登录发现写平台审计。三者无法同时满足，并且任何路线都做不到。
- **按 platform-admin 理解**：这条红线的主语与 §1.3a 表中的"调用方"都是 platform-admin，说的是 platform-admin 的审计写入。同一份蓝图的 AUDIT-001 也承认存在"受托写入"，根 DATA-006 点名了"审计写入器"。这样理解，各份 ACTIVE 蓝图互不冲突。

本方案按第二种理解设计，并请 R1 在批准时明确写下这一点（§8）。若评审认定是第一种，就需要先修订 super-admin，本方案停在 R1 之前。

### 3.1 模块

| 项 | 内容 |

| 定位 | L1 Plugin Data Owner，与 platform-identity、platform-tenant 同类：唯一 `BrixPlugin` provider，唯一 `plugin-manifest.yaml` |

- 租户过滤的分类不变：`sys_platform_audit_log` 仍是 multi-tenant §6.1 登记的全局表。受托写入登记只决定谁能写，与租户过滤无关。
- 现在 L2C 的 `OwnerDirectory` 已经从 Manifest 的 `data.outbox`、`data.inbox` 读出受托表。受托写入登记沿用这个读取方式。

### 3.3 Schema 归属与迁移

- 新建 Flyway 位置 `db/migration/platform-audit`，历史表是 `flyway_schema_history_platform_audit`。
- 在 brix-enterprise 主机的迁移顺序里，把 `platform-audit` 放在 `platform-identity` 之后。
- platform-identity 的 `V001`、`V002` 视为已执行，**不改**（C-11）。`V002` 本身就是给已有数据库补的前滚迁移。迁移哈希台账中把它们记为"所有权转移前由 platform-identity 建表"。

platform-audit 的迁移都是 expand，采用单 DCP 布局，与 platform-identity 一致：

| 版本 | 内容 | 说明 |
|---|---|---|
| `V001__platform_audit_adopt_table` | `CREATE TABLE IF NOT EXISTS sys_platform_audit_log`，定义与 identity `V001` + `V002` 的结果完全一致；两个索引用同名 `IF NOT EXISTS` | 接管。现有库上是空操作；fresh install 时不论哪个模块先执行，都得到同一张表 |
| `V002__platform_audit_policy_use_fields` | 新增可空列 `trace_id`、`execution_identity`、`reason_code`、`source_ip`、`user_agent`；新增 `writer VARCHAR(64) NOT NULL DEFAULT 'platform-identity'`；新增按动作的 CHECK（见下） | 只增不改。现有行的新列为空，`writer` 取默认值 |

`writer` 记录这一行由哪个登记的写入方写入：

- `platform-audit`：Owner 自己（内部契约的写入）；
- `runtime.tenant-policy-audit`：Runtime 的受托写入（§5）；
- `platform-identity`：拆分期间的过渡写入（§3.4）。现有行也都是它写的。

按动作的 CHECK 只用比较、`IN` 与 `IS NULL`，在可移植 DDL 子集之内：

```sql
-- 受托写入方只能写登记的两个动作
CHECK (writer <> 'runtime.tenant-policy-audit'
       OR action IN ('LOGIN_TENANT_DISCOVERY', 'FIRST_OWNER_INVITEE_SETUP_FANOUT'));
-- 策略审计必须带操作者、traceId 和稳定 reason
CHECK (action NOT IN ('LOGIN_TENANT_DISCOVERY', 'FIRST_OWNER_INVITEE_SETUP_FANOUT')
       OR (operator_identity_id IS NOT NULL AND trace_id IS NOT NULL AND reason_code IS NOT NULL));
```

现有行没有这两个动作，加约束时的校验能通过。

### 3.4 存量行：expand / migrate / contract

存量行不复制，也不换表；所有权的转移是逻辑上的。审计行不可修改，所以新列**不回填**：traceId、IP 这些值无法事后补得真实。

| 步骤 | 内容 | 表的写入方 | 退出条件 |
|---|---|---|---|
| **E（expand）** | platform-audit 上线：V001 接管、V002 加列；内部契约可用；受托写入登记生效 | platform-audit、Runtime 受托写入、platform-identity（过渡） | 新旧写入方同时工作；查询契约能读出存量行与新行 |
| **M（migrate）** | platform-identity 的审计改走 platform-audit（D3：身份 Owner 的 Outbox → platform-audit 订阅） | platform-audit、Runtime 受托写入 | platform-identity 不再写这张表，豁免 R2 关闭 |
| **C（contract）** | 删除 platform-identity 的 `PlatformAuditLogEntry`、Repository、`AuditService`、`AuditEvent`；`ALTER COLUMN writer DROP DEFAULT`；守卫改为"这张表只由 platform-audit 的持久化单元映射" | 同上 | 架构测试通过 |

- **E 期的过渡写入**：platform-identity 继续在自己的事务里写自己的审计行。它的实体不映射 `writer`，由数据库默认值标成 `platform-identity`，所以这一期不用改 platform-identity 的代码。这一期违反 C-1、C-8，需要有期限的豁免 R2。
- **为什么不在 E 期就切走 platform-identity**：
  - 它的审计要与变更一起提交。改成同步调用 platform-audit，变更回滚时会留下"变更已发生"的错误记录。
  - 又不丢又不错的做法是 Outbox（C-7），可身份 Owner 还没有 Outbox。租户隔离方案 §13.1 第 5 条（补发事件的可靠投递）也在等它。
- **回滚**：E 期只加可空列和带默认值的列。退回旧版本代码不受影响，旧代码不写这些列。

### 3.5 守卫与登记

- **主机契约测试**：brix-enterprise 的 `OwnerPersistenceIsolationContractTest` 把 platform-audit 纳入分类。C 期起增加"一张表只被一个 Owner 的持久化单元映射"。现在适配器按实体类判断 Owner，两个 Owner 映射同一张表不会被发现。
- **架构测试**：
  - runtime-orchestrator 不依赖 platform-audit；
  - platform-admin 只依赖 `platform-audit-api`，并且只经 `OperationalContext` 取契约；
  - 身份协议面适配器仍只依赖 L2A。
- 更新 `DataOwnerPhase4Test` 中过时的夹具。

## 4. 内部契约 `brix.internal.platform.audit`

### 4.1 契约形状（示意，签名在施工中定）

```java
package io.brix.platform.audit.internal;

public interface PlatformAuditAdministration {

    /** 追加一条平台审计；在审计 Owner 自己的本地事务中提交，调用方事务由 L2B 代理挂起。 */
    PlatformAuditRecordId record(RecordPlatformAuditCommand command);

    /** 平台控制台的受限查询：按时间倒序分页，可按动作、操作者、时间范围过滤。 */
    PlatformAuditPage query(PlatformAuditQuery query);
}
```

- 命令字段对应 super-admin §5：`action`、`actorIdentityId`、`executionIdentity`、`targetType/targetId`、`affectedTenants`、`result/reasonCode`、`traceId`、脱敏后的 `ip/userAgent`。
- Owner 按 §5 与 AUDIT-001 校验：动作必须在目录内；不接受密码、token、完整邮箱、URL 等内容；校验失败抛稳定错误，不吞异常（C-10）。
- `traceId` 由 platform-admin 从本次调用的 Invocation Context 取得。Owner 不读线程上下文。
- `query` 的结果映射到现有的 `PlatformAuditLogDto`。存量行的新字段为空，显示为"未记录"。
- `PlatformAuditLogDto.actorUsername` 需要身份数据，而 platform-audit 不能连 platform-identity 的表（根 DATA-003）。由 platform-admin 经身份契约补上，或者从 DTO 中去掉。

### 4.2 消费方

| 消费方 | 方式 | 用途 |
|---|---|---|
| platform-admin | `platform-operational.yaml` 的 `internalContracts.requires` 增加本契约：`versionRange: ">=1.0.0 <2.0.0"`、`required: true`、allowlist `platform-admin.platform-audit`；经 `OperationalContext.requireInternalContract()` 取得 | • `GET /api/platform/audit-logs`（`platform:audit:read`，super-admin §6）<br>• 记录自身的定向运维操作（super-admin §5；multi-tenant §6.4 第 4 行、§10.1 第 5 条、T-3） |

| 调用方 | 为什么不行 | 它的平台审计怎么写 |
|---|---|---|

## 5. 策略使用的平台审计写入

### 5.1 路线比较

| 路线 | 做法 | 蓝图 | 覆盖 | 结论 |
|---|---|---|---|---|
| **A** 新增 L2A Capability | 例如 `PlatformAuditCapability`，由 platform-audit 实现，L2B（以及身份协议面）调用 | 新的平台 Capability，要进 Catalog、走根级 RFC（C-6）。L2A Capability 默认是插件面能力，任何声明它的插件都能写平台审计，所以还要定义"只给平台调用方"的新可见性规则 | P-1、P-3；身份协议面也能用 | 可行。代价是新增一个插件面接口和新的可见性语义，安全评审的范围最大 |
| **B** 身份协议面写 | `HostedLoginController`、`BffController` 调完发现接口后自己写 | 身份协议面只能用 L2A（C-5），所以要先有 A；它也不能消费内部契约 | 只有 P-1。P-3 在 L2B 的事件投递中，与身份协议面无关 | 不选。策略由 L2B 授予，审计却要每个调用方记得写，漏写就等于不审计 |
| **C** L2B 调内部契约 | Runtime 直接用 `brix.internal.platform.audit` | 违反 C-3、C-4：契约类型在 L1，消费方只能是 `OperationalContext`。要改根级内部契约 SPI | P-1、P-3 | 不选 |
| **D** Runtime 受托写入（**推荐**） | L2B 端口 + L2C 实现，写入 platform-audit 登记的受托记录 | 根 DATA-006 点名"审计写入器"可作 Custodian，DATA-004 把平台审计列为平台受托表；super-admin AUDIT-001 写明"受托写入边界由根蓝图和审计 Owner 定义"。缺的是登记格式和失败语义（R1） | P-1、P-3，以及将来新增的策略 | 推荐 |
| **E** Outbox / Integration Event | 被访问的 Owner 在事务内写一条"策略已使用"事件，platform-audit 订阅入库 | 符合 DATA-029。但事实的生产者是 Runtime 而不是插件，Runtime 自己发事件没有定义；P-1 是只读事务，写 Outbox 要改成读写；入库是最终一致 | P-1、P-3 | 不选。它适合 platform-identity 自己的审计（§3.4） |
| **F** 被访问的 Owner 写 | platform-tenant 在发现接口和补发 Handler 中写 | 策略由 Runtime 绑定，插件看不到（租户隔离方案 §3.2）；插件也不能消费内部契约 | P-1、P-3 | 不选 |

**D 与 A 怎么取舍**：两者都满足"独立于调用方事务提交、调用方挂起"（DATA-029）。

- A：写入由 Owner 自己的代码执行。代价是新增一个插件面接口，并且要在根蓝图里引入"受限 Capability"。
- D：写入由登记的 Custodian 执行，不新增接口。写规则仍由 Owner 定：登记中的列、动作、记录 Schema，加上 §3.3 的数据库约束。代价是同一张表有两条写入路径，表结构演进时要保持受托 INSERT 兼容。这与 Outbox 表的处理方式相同。

### 5.2 推荐方案：Runtime 策略审计写入器

```text
L2B runtime-orchestrator
  TenantAccessBoundary（P-1）、InviteeSetupEventDelivery（P-3）
    └─ PolicyAuditWriter（L2B 端口，不进 L2A，插件拿不到）
         record(PolicyUseRecord)   // 只接受类型化字段，没有自由文本

L2C infra-adapter-persistence-jpa
  JdbcPolicyAuditWriter implements PolicyAuditWriter
    ├─ 启动时读取 platform-audit Manifest 的受托写入登记，校验表、列、动作
    ├─ 用共享事务管理器开 REQUIRES_NEW：挂起调用方事务，单独提交
    └─ 固定列清单的 INSERT；不读、不改、不删
```

- **为什么放在持久化适配器**：Owner 事务的挂起与开启已经在这里（`OwnerUnitOfWork` 跨 Owner 时用 REQUIRES_NEW），连接池与事务管理器也在这里。
- **为什么不用 JPA 实体**：L2C 不能引用 platform-audit 的实体类。用 JDBC 也避免同一张表在持久化单元中出现两次映射。
- **主键**：与 platform-audit 用同一个 ID 生成来源（Runtime 的 `IdGeneratorCapability`），避免两个 Snowflake 实例用同一个 worker id 而撞号。施工中确认主机是否已提供这个 Capability。
- **数据库身份**：根 DATA-038 建议 Custodian 使用只覆盖受托表与所需操作的身份。目前全部模块共用一个账号（RFC-001 §8 第 7 条），先由 §3.3 的 CHECK 兜底；拆分账号随 RFC-001 的计划进行。

### 5.3 记录内容

| 列 | P-1 `LOGIN_TENANT_DISCOVERY` | P-3 `FIRST_OWNER_INVITEE_SETUP_FANOUT` |
|---|---|---|
| `operator_identity_id` | 登录事务中已认证的身份 | 完成设置的身份（事件中的 `identityId`） |
| `execution_identity` | `runtime:policy:login-tenant-discovery` | `runtime:policy:first-owner-invitee-setup-fanout` |
| `reason_code` | `login-tenant-discovery`（§6.3 的稳定 reason） | `first-owner-invitee-setup-fanout` |
| `resource_type` / `resource_id` | `SELF` / 空 | `INVITATION` / 空（可能涉及多条邀请） |
| `affected_tenants` | 返回的成员记录所属的租户 | 适配器在本次事务中为策略绑定的租户 |
| `context` | `{entry: login 或 switch, matched}` | `{subscriptionId}` |
| `success` / `error_code` | `true` / 空 | `true` / 空；Handler 失败时见 §5.4 |
| `trace_id` | 当前 trace；没有时先创建关联 ID（与根 ERROR-013 同一规则） | 同左 |
| `source_ip` / `user_agent` | 按安全 Profile 的请求元数据策略脱敏（super-admin §5）；UA 按策略可选 | 空：没有请求 |
| `writer` | `runtime.tenant-policy-audit` | 同左 |
| `created_at` | 服务端时间 | 同左 |

- 满足 §6.3 对登录发现审计的要求：身份、时间、来源 IP、命中租户数。
- 不记录 P-3 的键（邀请邮箱）、token、租户名或成员 ID（C-9）。邮箱用身份 ID 代替。
- **来源 IP 从哪里来**：身份协议面不经过 Dispatcher（根 MANIFEST-021 的唯一例外），L2B 边界拿不到请求。
  - 给 `TenantAccessCapability` 增加 `default` 方法 `getActiveMemberships(Long identityId, DiscoveryContext context)`（CAP-019）。`DiscoveryContext` 只含来源地址、用途（login/switch）和客户端类别；缺省实现调用旧方法。
  - 两个调用点（`HostedLoginController`、`BffController`）改用新方法。旧方法仍可用，但记录中的来源 IP 为空。
- **受影响的租户从哪里来**：P-1 从返回的成员记录中取。P-3 需要 L2C 在事务内为策略绑定的租户集合：在 L2B 与 L2C 之间的私有载体（`TenantScopes`）上增加回报，不进 L2A。

### 5.4 fail-closed 的落点

**P-1（只读）**

```text
TenantAccessBoundary.invoke
  1. TenantScopes.within(P-1) → platform-tenant 只读 Unit of Work → 成员记录
  2. writer.record(...)                 // 独立本地事务；此时没有活动事务要挂起
  3. 第 2 步成功，才把第 1 步的结果返回给身份协议面
```

- 写审计失败：抛稳定错误，结果丢弃。身份协议面按现有的异常处理返回通用错误，不透露原因。
- 读失败：不写审计。违规本身已有 `tenant.isolation.violation` 安全日志。

**P-3（读写，在身份事务提交后的回调中执行）**

```text
InviteeSetupEventDelivery.onSetupCompleted（AFTER_COMMIT）
  TenantScopes.within(P-3) → platform-tenant.unitOfWork().required(
      1. handler.handle(event)          // 重新生成邀请 token，同步发邀请邮件
      2. writer.record(...)             // 挂起 platform-tenant 的事务，单独提交
  ) → 3. platform-tenant 提交
```

- **写审计失败**：platform-tenant 回滚，新 token 没有保存，已发出邮件中的链接随之失效。邀请仍是 PENDING，平台超管可以重发。
- **审计已提交，但第 3 步失败**：多出一条"策略已使用"。跨租户读取确实发生过，这条记录是真的，可以接受。
- **为什么不放在第 3 步之后**：那时邮件已发、变更已提交，审计写失败也阻断不了什么。
- **为什么不先写一条"开始"记录**：会让每次使用产生两行。上面的顺序已经保证"没有审计，就没有持久的跨租户写入"。
- **Handler 失败**：回滚后补写一条 `success=false` 和稳定错误码。这一条尽力而为：它也写不进去时，只记错误日志，不覆盖原始异常。
- **不影响设置完成本身**：回调中的异常由框架记录，不会回到设置请求。租户隔离方案 §13.2 第 2 条在端到端中看到的就是这个行为：回调失败时设置已完成，只是没有发邮件。施工中用测试把它固定下来。

两条路径的写入失败使用同一个新的稳定错误码（例如 `audit.policy_use_write_failed`），按 CAP-021、ERROR-012 作为 Minor 扩展。

### 5.5 启动期校验与可观测性

- **启动期校验**：只要主机里有会用到 P-1 或 P-3 的组件（`TenantAccessCapability` 的 Bean，或引用 P-3 的 Manifest 订阅），就必须能解析到覆盖相应动作的受托写入登记，否则主机启动失败。不能拖到第一次登录才失败。
- `tenant.policy.used` 日志保留，增加审计记录 ID。它不再是审计的依据。
- 增加写入失败的计数指标，标签只有策略和原因（OTEL-006），并接告警。

## 7. 需要你确认的决定

### D1：策略审计由谁写

**推荐：路线 D，Runtime 作为登记的受托写入方（§5.2）。**

- 根蓝图已有这个角色（DATA-006），不新增插件面接口；
- L2B 不依赖平台模块，身份协议面仍然只用 L2A；
- 策略由 Runtime 授予，审计也由 Runtime 写，不会漏写；
- 需要 R1 定下登记格式与失败语义，并确认 §2.1 的解读。

**备选：路线 A，新增 L2A Capability，由 platform-audit 执行写入。**

- 写入代码只有一份，身份协议面将来也能用；
- 代价：新增插件面接口，还要在根蓝图中定义"只给平台调用方"的可见性，根级 RFC 的评审范围更大。

### D2：fail-closed 的落点

**推荐：按 §5.4。** P-1 在返回结果前写；P-3 在 platform-tenant 提交前写；P-3 的 Handler 失败时补写 `success=false`。

**备选：先写"开始"记录，执行后再写"结束"记录。** P-3 发邮件之前的阶段也有记录；代价是每次使用两行，读取时还要配对。

### D3：拆分期间 platform-identity 自己的审计

**推荐：**

- E 期按豁免 R2 继续直接写，只靠数据库默认值标出 `writer`，不改代码；
- M 期改为身份 Owner 的 Outbox → platform-audit 订阅，然后删除旧组件。

理由：保持"审计与变更一起提交"；身份 Owner 的 Outbox 也能解决 D2-A 补发事件的可靠投递（租户隔离方案 §13.1 第 5 条）。

**备选 B：先给身份 Owner 做 Outbox，再拆 platform-audit。** 不需要豁免，但策略审计要等更久。

**备选 C：platform-identity 同步调用 platform-audit。** 只能走新的 L2A Capability（插件不能用内部契约），并且变更回滚时会留下错误的记录。不推荐。

### D4：platform-audit 的模块形状

**推荐：三个 artifact（api/core/server），符合根 MANIFEST-005。** platform-admin 只依赖 `-api`，不再像现在这样依赖整个 Owner 制品。

**备选：单个 artifact，与 platform-identity、platform-tenant 的现状一致。** 省事，但又多一处 MANIFEST-005 偏差。

### D5：表结构与存量行

**推荐：按 §3.3 与 §3.4。** 只加列，不回填；`writer` 用默认值标出存量行与过渡期的写入；按动作的 CHECK 只约束新动作。

**备选：新建一张 platform-audit 自己的表，把存量行复制过去，旧表冻结。** 所有权更干净；但要复制审计数据，查询要跨两张表或等复制完成，切换期间平台超管的审计页不完整。

另有一处表述差异请一并确认：

- multi-tenant §10.1 的示意 DDL 是 `operator_ref NOT NULL`；
- super-admin §5 规定匿名 Bootstrap 请求的 actor 为空，现有表的 `operator_identity_id` 也可空。

本方案的两类策略记录都有非空的 actor，不受影响。建议在 super-admin 的重基线复核中统一，本方案不改这一列。

### D6：本期范围与分支

**推荐：**

- 本期做 §9 的 P1、P2：platform-audit 的 E 期（模块、迁移、契约、受托登记），加上策略审计写入。
- platform-admin 的审计查询入口和自身操作审计（super-admin §13 的 P-8）作为下一个切片 P3。
- 身份 Owner 的 Outbox 与 M、C 期作为 P4，另立计划。
- 新分支等 `claude/tenant-isolation-l2c` 合并后从主干切出，不与 RFC-007 绑在一起。
  - 那个分支上策略使用只写日志，是租户隔离方案已经记录的过渡状态。
  - 合并它不会让现状变差：主干上的登录发现同样只有日志。

**备选：继续叠在 `claude/tenant-isolation-l2c` 上，一起合并。** 登录发现一上线就有平台审计；代价是合并要同时等 RFC-007 与 R1。

## 8. 需要批准的事项

### R1：根级 Minor RFC（RFC-008，待起草）

按根 §12.2"新增向后兼容的 Manifest"走 Minor RFC，需要 architecture、security、SRE 批准。内容：

1. **受托写入的登记格式**：Owner 在 Manifest `data` 段声明受托写入（表、写入方 ID、允许的操作、列、记录 Schema 引用、动作），落实 DATA-004、DATA-006 要求的"显式登记"。现在 `data` 段只有 outbox/inbox。
2. **Runtime 策略审计写入器**：作为 DATA-006 所说的"审计写入器"登记，范围限定为 multi-tenant §6.4 登记项的平台审计。
3. **失败语义与同步阻断范围**：对登记的跨租户策略，审计写入失败即本次使用失败；P-1 在返回结果前、P-3 在 Owner 事务提交前写入。super-admin AUDIT-001 要求这类语义由根蓝图和审计 Owner 定义，根蓝图目前没有写。
4. **记录 Schema 的版本与兼容**：Owner 演进表结构时受托 INSERT 的兼容规则；各字段的数据分类（SECURITY-008）。
5. **解读确认**：super-admin §1.3a 红线"所有审计写入只能经内部契约"指 platform-admin 的写入（§2.1）。若评审不同意，需要先修订 super-admin。

若 D1 选 A，R1 改为"新增受限平台 Capability"的根级 RFC（C-6），第 1、2 条不再需要。

### R2：拆分期豁免（控制平面记录，按根 GOVERNANCE-013）

- 规则：根 DATA-001、DATA-027；super-admin §1.3a。
- 制品：platform-identity 的 `PlatformAuditLogEntry`、`PlatformAuditLogRepository`、`RepositoryPlatformIdentityAuditService`。
- 补偿控制：`writer` 标记；只追加不修改；P4 完成后删除。
- 到期日：随 P4 的计划确定。D3 选 B 时不需要这条豁免。

### 不需要 RFC 的部分

| 事项 | 理由 |
|---|---|
| 新建 platform-audit 与 `PlatformAuditAdministration` | 实现 super-admin §1.3a、§2.1 已冻结的内容 |
| `TenantAccessCapability` 的新默认方法、新错误码 | CAP-019、CAP-021 的 Minor 扩展；租户隔离施工中同类改动也没有走 RFC |
| 表加列与 CHECK | Owner 的前滚迁移。补的是 super-admin §5 已经要求的字段，不改变 T-25 的语义：不绑定单一 `tenant_id`，`affected_tenants` 仍是 0..N |
| multi-tenant §6.3、§6.4 的措辞 | §6.4 只规定记什么动作，没有规定由谁写；§6.3 的"provider 记平台审计"由 Runtime 在该契约的调用边界上代为写入。只有评审认为必须由 platform-tenant 自己写时，才需要一个 multi-tenant Patch |

**时序**：

- R1 批准前，可以做 P1 中与受托登记无关的部分；
- P2 合并前需要 R1；
- E 期上线前需要 R2。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 审计写入失败导致登录失败（fail-closed） | 平台审计与业务表在同一数据库，数据库故障时登录本来就不可用；写入失败计数接告警 |
| 同一张表有两条写入路径，演进时受托 INSERT 失效 | 受托记录 Schema 版本化（R1 第 4 条）；platform-audit 的迁移测试包含受托写入 |

| 每次登录多一次写入 | 单行 INSERT，开销可以忽略 |
| P-3 回滚后，已发出邮件中的链接失效 | 作为已知行为记录；平台超管重发即可，与现在 Handler 失败时相同 |

### 13.1 与方案的差异

1. **主机原来没有 `IdGeneratorCapability`，施工中补上**（§5.2 的待确认项）
   - §5.2 要求 Owner 与 Runtime 受托写入用同一个 ID 来源，即 `IdGeneratorCapability`，并请施工时确认主机是否已提供。结论是没有：brix-enterprise 主机没有组装 `infra-adapter-idgen`，任何模块也没有用过这个 Capability。
   - 施工改为在主机组装 `infra-adapter-idgen`（Snowflake），并把 `IdGeneratorCapability` 列为主机的必需 Capability。platform-audit 的实体不再用数据库生成主键，记录 id 由服务从这个 Capability 取得；受托写入登记加上 `id` 列，写入器同样从这个 Capability 取 id。表的 id 是 BIGINT，所以生成器必须给出数字 id；不是数字时，启动检查就失败。
   - 拆分期间 platform-identity 仍用自己的 Snowflake 生成器写同一张表。两个生成器的节点位都在第 12–21 位：platform-identity 是 worker id 1，主机的生成器是 datacenter 1 × 32 + worker 1 = 33，所以两者生成的 id 不会相同。主机配置里写明了这条约束。
   - 最初的实现曾用数据库序列生成 id（V002 建序列并设为默认值）。它违反根 DATA-024（`GeneratedValue` 不在白名单内，主键由应用侧经 `IdGeneratorCapability` 生成），brix-enterprise 主机契约测试在部署前发现了这个问题（见 13.2）。V002 在任何持久数据库上都还没有执行过，所以直接改掉，不另加迁移。
2. **CHECK 比 §3.3 更严**
   - 方案只限制"受托写入方只能写两个策略动作"。施工改为双向：`(action IN (两个策略动作)) = (writer = 'runtime.tenant-policy-audit')`，其他写入方也不能写这两个动作。
   - 只用比较和 `IN`，仍在可移植 DDL 子集之内。
3. **不记录 User-Agent**
   - §5.3 写的是"UA 按策略可选"。`DiscoveryContext` 只带来源地址、用途和客户端类别（`hosted-login`、`bff`），`user_agent` 列留空。
   - 客户端类别记在 `context.client`；P-3 的订阅记在 `context.subscription`（§5.3 写作 `subscriptionId`）。
4. **`/bff/session` 也是一次 P-1**
   - 会话接口要列出可切换的租户，所以每次读取会话都写一行，`entry=switch`、`client=bff`。登录写 `entry=login`、`client=hosted-login`。
   - 控制台每次加载都会读会话，行数随之增长。是否改为只在登录和切换时写，留作后续决定。
5. **日志带 trace，不带审计记录 id**（§5.5）
   - 受托写入只能 INSERT，不能读（DATA-045），拿不到数据库生成的 id。
   - `tenant.policy.used` 日志和审计行带同一个 traceId，用它关联。
6. **登记在第一次使用前校验**
   - 方案写的是启动时校验。施工中，写入器在第一次被问到登记时才解析并校验它（只有一个 Owner 登记、写入的列全部授权、只有 INSERT、记录 Schema 能解析、该 Owner 的实体映射了这张表）。
   - 主机里有 `TenantAccessCapability` 时，Runtime 的启动检查会立即触发这次校验，并要求两个策略动作都被覆盖，否则启动失败。
   - 没有 `TenantAccessCapability` 却有 P-3 订阅的主机，不会在启动时失败，而是在使用时以 `audit.policy_use_write_failed` 失败（仍是 fail-closed）。P-3 唯一的 Handler 在 platform-tenant，它同时提供 `TenantAccessCapability`，所以目前不会出现这种主机。
7. **错误类型**
   - 新增 L2A 异常 `PolicyAuditException`，稳定错误码 `audit.policy_use_write_failed`（命名空间 `audit`，与 ERROR-012、DATA-047 一致）。没有加进 `PersistenceCapabilityException`：那里的错误码只允许 `persistence.*`。
8. **Owner 归属按打包的 Maven 描述判断**
   - platform-audit 的实体在 `-core`，Manifest 在 `-server`。适配器把 `-api`、`-core` 归给在 `modules` 中列出它们的 Manifest，依据是构件里的 `META-INF/maven/{groupId}/{artifactId}/pom.properties`，并核对版本。
9. **共享环境的来源地址是代理地址**
   - 共享环境的请求经 Caddy 和 Docker 网关进来，后端没有配置可信的转发头，`source_ip` 是代理一侧的地址（掩码后），不是用户的真实地址。
   - 要记录真实地址，需要先确定可信代理和转发头的处理，留作后续。

### 13.2 部署前发现并修正的问题

brix 的单元测试都通过后，组装后的主机还暴露了四个问题，都在部署前修正。前三个由 brix-enterprise 的主机契约测试发现（它用打包后的构件组装主机），第四个由部署用 jar 的一次性端到端检查发现：

1. **持久化适配器拒绝 platform-audit 的持久化单元**：实体用数据库序列生成主键，违反 DATA-024。修正见 13.1 第 1 条。
2. **内部契约绑定不上**：主机只把 `brix.capability.required` 中列出的类型注册进 Capability 注册表，平台 Owner 的内部契约实现也靠这个列表注册。platform-audit 的 `PlatformAuditAdministration` 不在列表里，`brix.internal.platform.audit` 绑定时找不到它，主机会启动失败。已加入列表；契约测试的注册表夹具也补上了它。
3. **主机组合测试**：断言中 platform-identity 的迁移注释仍是"持有 `sys_platform_audit_log`"，已改为新的归属，并加上 platform-audit、`infra-adapter-idgen` 和两个 Capability 的断言。
4. **Runtime 启动时的 Manifest Schema 校验拒绝 `data.custodialWrites`**：Runtime 启动时用内置的 JSON Schema 校验每个插件 Manifest。P2 只扩展了 Manifest 模型和它的 Java 校验器，内置 Schema 的 `data` 部分不认识这个字段，于是主机启动失败。已按根蓝图附录 A 在两份 Schema（devtools 的编写副本和内置副本）中定义受托写入登记：`table`、`custodian`、`operations`、`columns`、`recordSchemaRef` 必填，`actions` 可选，`operations` 只能是 INSERT，`custodian` 只能是 `runtime.tenant-policy-audit`（brix `29e7bcb`）。主机契约测试另加了一项，对主机类路径上的每个平台插件 Manifest 做同样的启动校验，以后同类问题在构建时就能发现。
