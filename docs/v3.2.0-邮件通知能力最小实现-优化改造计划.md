## 0. 目标与边界

### 0.1 当前问题

当前平台通过 `NotificationCapability.sendSetupLink(email, setupUrl, purpose)` 发送平台超管首次设置和密码重置链接，默认实现 `EmailSetupLinkNotifier` 直接使用 Spring Mail，并在 Java 代码中写死主题和正文。

当前实现已有两项可保留基础：

1. 业务服务依赖 `NotificationCapability`，没有直接依赖 SMTP 协议。
2. API 不返回明文密码、setup token 或 setup URL，敏感链接只通过邮件侧信道发送。

v3.2.0 只解决以下三个问题：

1. 将邮件投递与业务、模板渲染分离，使 SMTP 将来可替换为 Gmail API、SES 等实现。
2. 将 setup-link 专用接口扩展为通用模板邮件接口，供未来租户邀请、员工邀请和密码重置复用。
3. 将主题和正文从 Java 代码迁移到可配置的多语言模板文件。

### 0.2 本期最小交付

v3.2.0 必须交付：

- 一个通用且精简的 `NotificationCapability.send(NotificationRequest)` 契约。
- 对现有 `sendSetupLink(...)` 的二进制和行为兼容。
- 一个固定模块 `platform-notification`，负责校验、模板解析、渲染和发送编排。
- 一个独立 SMTP Adapter，继续支持当前虚拟 SMTP、Mailpit、Gmail SMTP 和企业 SMTP。
- `zh-CN`、`en-US` 两套平台超管默认纯文本模板。
- classpath 默认模板和外部目录覆盖模板。
- 发送失败 fail-closed、脱敏日志、基础指标和生产 SMTP 安全校验。

### 0.3 明确不进入本期

以下能力不属于 v3.2.0，不得以“预留”为理由加入 DTO、数据库或实现：

- Gmail API、AWS SES、SendGrid API Adapter。
- 数据库模板表、模板管理 API、模板管理 UI、租户模板覆盖。
- HTML 邮件、富文本编辑、图片资源和附件。
- 通知记录表、投递回调、退信/投诉状态同步。
- Outbox、异步队列、自动重试和死信队列。
- 短信、站内信、移动推送等多通道。
- 优先级、定时发送、批量发送和业务幂等键。
- 营销邮件、订阅偏好、退订中心和 A/B 测试。

## 1. 冻结结论

| 事项 | v3.2.0 决策 |
|------|-------------|
| 业务契约 | `NotificationCapability.send(NotificationRequest)`，仍保留 `sendSetupLink(...)` |
| 通知通道 | 只实现 EMAIL，不在请求中增加 channel 字段 |
| 默认 Provider | SMTP / Spring Mail |
| 非 SMTP Provider | 本期不实现，通过 Adapter 契约测试证明可替换性 |
| 模板格式 | UTF-8 JSON 文件，严格命名变量，只支持纯文本 |
| 模板位置 | classpath 默认模板 + 可选外部目录覆盖 |
| 模板修改生效 | 修改外部文件后重启应用；本期不做运行时热更新 |
| 多语言 | 只支持 `zh-CN`、`en-US` |
| 模板引擎 | 内置严格占位符渲染器，不引入表达式或脚本引擎 |
| 发送方式 | 同步、单次尝试、3 秒超时、失败抛统一异常 |
| 持久化 | 不新增通知或模板数据库表 |
| 可观测性 | 脱敏结构化日志 + Micrometer 指标 |
| HTML | 不支持 |
| 租户覆盖 | 不支持；未来新增时不改变现有业务调用契约 |

| 来源 | 与本期相关的官方实践 | v3.2.0 落地 |

## 3. 设计原则与红线

### 3.1 原则

| # | 原则 | 落地含义 |
|---|------|----------|
| N-P1 | Capability Contract 优先 | 业务只依赖 L2A 的通知契约 |
| N-P2 | 投递 Adapter 可替换 | SMTP 细节只存在于 SMTP Adapter |
| N-P3 | 模板与业务分离 | 业务只选 templateKey 并提供变量 |
| N-P4 | 最小契约 | 不为未实现的通道、优先级、回调和幂等增加字段 |
| N-P5 | 安全链接不外泄 | Token、完整 URL、邮件正文不出响应、不入日志、不入审计 |
| N-P6 | 默认模板可恢复 | classpath 默认模板始终随制品发布；外部配置错误必须阻止启动，修正或移除后可恢复默认模板 |
| N-P7 | 渐进兼容 | 现有接口、API 响应和 fail-closed 行为保持兼容 |
| N-P8 | Provider 行为一致 | 所有 Adapter 接收同一已渲染纯文本邮件，不改变业务语义 |

### 3.2 红线

| # | 红线 | 校验方式 |
|---|------|----------|
| N-R1 | 业务、Controller 和插件不得 import JavaMail、Gmail、SES、SendGrid SDK | ArchUnit |
| N-R2 | Host 不得包含通知业务、模板或 Adapter 实现 | ArchUnit / 代码评审 |
| N-R3 | 任何 profile 都不得记录 raw token、完整 setupUrl/inviteUrl/resetUrl、正文或 variables | 日志捕获测试 |
| N-R4 | API 和异常不得返回 raw token、完整安全链接或 Provider 原始异常 | DTO / 异常映射测试 |
| N-R5 | 模板只能使用声明过的变量，缺失或多余变量均拒绝发送 | 渲染单测 |
| N-R6 | 模板不允许条件、循环、方法调用、文件包含或代码执行 | 模板语法测试 |
| N-R7 | URL 必须由服务端可信 base URL 构造，生产环境必须为 HTTPS | 配置校验测试 |
| N-R8 | 邮件不得作为生产 MFA 因子 | 安全评审 |
| N-R9 | 外部投递只能单次尝试且总超时不超过 3 秒 | 配置与集成测试 |

## 5. Capability 契约

### 5.1 NotificationRequest

```java
public record NotificationRequest(
        Long tenantId,
        String recipientEmail,
        String templateKey,
        String locale,
        Map<String, String> variables
) {}
```

字段规则：

- `tenantId`：平台级通知为 `null`；未来租户通知使用系统 `BIGINT` tenant ID。
- `recipientEmail`：必填、最长 320 字符；使用与现有 DTO `@Email` 一致的 Bean Validation 规则，并额外拒绝 CR/LF 和控制字符。
- `templateKey`：必填；必须匹配 `[a-z][a-z0-9]*(\.[a-z][a-z0-9-]*)+`。
- `locale`：可空；非空时只接受规范化后的 `zh-CN` 或 `en-US`。
- `variables`：必填、不可变，只允许 `String` 键值；不得覆盖为 `to/from/subject/templateKey` 等基础字段。

`NotificationRequest` 的 compact constructor 必须执行 `Map.copyOf(variables)`，拒绝空 Key、空值和非法变量名。必须覆盖默认 `toString()`，只输出 tenantId、脱敏 recipient、templateKey、locale 和变量 Key 集合，绝不输出变量值。

请求中不包含 `channel`、`category`、`priority`、`idempotencyKey`、`provider`、`traceId`。Trace ID 和 correlation ID 由现有可观测上下文获取，不由业务重复传递。

### 5.2 NotificationCapability

```java
public interface NotificationCapability {

    void sendSetupLink(String email, String setupUrl, String purpose);

    default void send(NotificationRequest request) {
        NotificationRequests.validateCompatibilityRequest(request);
        switch (request.templateKey()) {
            case NotificationTemplateKeys.PLATFORM_ADMIN_SETUP_INITIAL ->
                    sendSetupLink(
                            request.recipientEmail(),
                            request.variables().get("setupUrl"),
                            "INITIAL_SETUP");
            case NotificationTemplateKeys.PLATFORM_ADMIN_PASSWORD_RESET ->
                    sendSetupLink(
                            request.recipientEmail(),
                            request.variables().get("setupUrl"),
                            "PASSWORD_RESET");
            default -> throw new UnsupportedNotificationTemplateException(request.templateKey());
        }
    }
}
```

兼容规则冻结如下：

1. 不改变现有 `sendSetupLink(...)` 签名。
2. 新增 `send(...)` 必须是 default 方法，确保旧实现仍可加载。
3. default 方法只兼容当前两个平台超管模板，其他模板对旧实现明确失败。
4. 新 `NotificationApplicationService` 同时实现两个方法；`sendSetupLink(...)` 按 purpose 映射 templateKey，仅携带 `setupUrl` 变量，再调用其自身 `send(...)`。
5. 禁止在两个方法之间形成递归委派。
6. v3.2.0 不引入 `NotificationReceipt`；成功正常返回，失败抛统一异常。

### 5.3 模板 Key

本期生产资源只包含：

```java
public final class NotificationTemplateKeys {
    public static final String PLATFORM_ADMIN_SETUP_INITIAL =
            "platform.admin.setup.initial";
    public static final String PLATFORM_ADMIN_PASSWORD_RESET =
            "platform.admin.setup.password-reset";
}
```

以下 Key 仅冻结命名，待对应业务功能开发时再增加模板资源和验收，不属于本期交付：

| 未来场景 | templateKey |
|----------|-------------|
| 首位租户 OWNER 邀请 | `tenant.owner.invitation.initial` |
| 租户管理员邀请 | `tenant.admin.invitation` |
| 租户员工邀请 | `tenant.member.invitation` |
| 用户密码重置 | `identity.password-reset` |
| 密码重置完成通知 | `identity.password-reset.completed` |

### 5.4 统一异常

| 异常 | 稳定错误码 | 含义 |
|------|------------|------|
| `InvalidNotificationRequestException` | `NOTIFICATION_REQUEST_INVALID` | 收件人、Locale、变量或模板 Key 不合法 |
| `NotificationTemplateException` | `NOTIFICATION_TEMPLATE_INVALID` | 模板不存在、格式错误或渲染失败 |
| `NotificationDeliveryException` | `NOTIFICATION_DELIVERY_FAILED` | Adapter 超时或 Provider 拒绝 |
| `NotificationProviderUnavailableException` | `NOTIFICATION_PROVIDER_UNAVAILABLE` | 没有可用生产 Adapter |

对外错误响应只暴露稳定错误码，不暴露 SMTP host、账号、收件地址、模板正文或 Provider 原始异常。

## 6. 模板规范

### 6.1 文件布局

classpath 默认模板固定放置于：

```text
platform-notification/src/main/resources/notification-templates/
  platform.admin.setup.initial/
    zh-CN.json
    en-US.json
  platform.admin.setup.password-reset/
    zh-CN.json
    en-US.json
```

外部覆盖目录保持相同相对结构：

```text
${brix.notification.templates-dir}/
  {templateKey}/{locale}.json
```

`templates-dir` 只能由部署配置提供，业务请求不得传入文件路径。解析后路径必须仍位于配置目录内，防止目录穿越。

### 6.2 JSON Schema

每个模板文件只允许以下字段，未知字段导致启动失败：

```json
{
  "templateKey": "platform.admin.setup.initial",
  "locale": "zh-CN",
  "subject": "完成 Brix 平台管理员设置",
  "textBody": "你好，\n\n请打开以下链接设置密码并绑定 MFA：\n{{setupUrl}}\n\n此链接只能使用一次，并将在短时间后过期。",
  "requiredVariables": ["setupUrl"]
}
```

字段约束：

- `templateKey` 和 `locale` 必须与文件路径一致。
- `subject` 渲染后长度为 1-200，禁止 CR/LF 和控制字符。
- `textBody` 渲染后长度为 1-65536。
- `requiredVariables` 不得重复，必须与 subject/textBody 实际引用集合完全一致。
- JSON 使用 UTF-8，单个文件不得超过 128 KiB。
- 模板只允许纯文本；出现 `<html`、`<body`、`<script`、`<!DOCTYPE` 或 MIME `text/html` 标记时启动失败。

### 6.3 严格占位符语法

本期只支持命名占位符：

```text
{{variableName}}
```

变量名必须匹配 `[A-Za-z][A-Za-z0-9]*`。不支持三花括号、条件、循环、注释、函数、嵌套属性、文件包含或表达式。

`StrictTextTemplateRenderer` 必须：

1. 先解析全部占位符并与 `requiredVariables` 做集合等值校验。
2. 请求变量缺失或出现未声明变量时失败。
3. 使用字面量替换，变量中的 `$`、反斜杠和花括号不得被二次解释。
4. 渲染后仍存在 `{{` 或 `}}` 时失败。
5. 不记录模板正文、变量值或渲染结果。

### 6.4 模板解析与 Locale 回退

有效 Locale 按以下顺序确定：

1. 请求显式 `locale`。
2. 有租户上下文时使用 `TenantConfigCapability.getEffectiveLocale()`。
3. `brix.notification.default-locale`，默认 `zh-CN`。

只支持 `zh-CN` 和 `en-US`。请求显式传入其他 Locale 时抛 `InvalidNotificationRequestException`；租户配置为不支持的 Locale 时回退平台默认 Locale，并记录不含 PII 的 warning 指标。

对确定后的每个候选 Locale，模板查找顺序为：

1. 外部目录 `{templateKey}/{locale}.json`。
2. classpath `{templateKey}/{locale}.json`。

若目标 Locale 不存在，则按同样顺序回退 `en-US`。`en-US` classpath 默认模板缺失时应用启动失败。

外部模板在启动时一次性加载并完整校验。任一外部文件无效时应用启动失败，不允许静默忽略错误配置；删除外部覆盖文件并重启后恢复 classpath 默认模板。

## 7. 发送编排与事务

### 7.1 同步流程

```text
业务事务
  -> 创建/更新业务数据
  -> 生成一次性 token，数据库只保存 hash
  -> 使用可信 base URL 构造完整链接
  -> NotificationCapability.send(request)
      -> 校验请求
      -> 解析 Locale 和模板
      -> 严格渲染纯文本主题/正文
      -> EmailDeliveryAdapter.send(email)
          -> SMTP 单次投递，最长 3 秒
      -> 记录 accepted 指标和脱敏日志
  -> 提交业务事务
  -> 返回现有 setupLinkSent=true 响应
```

### 7.2 冻结事务语义

1. v3.2.0 延续当前同步 fail-closed 行为，SMTP 调用发生在调用方业务事务提交前。
2. SMTP 失败时抛 `NotificationDeliveryException`，调用方业务事务回滚，API 不返回成功。
3. 本期不新增 `sys_notification_log`，避免失败状态随业务事务回滚造成伪审计。
4. SMTP 接受邮件只表示 Provider 接受投递，不表示到达收件箱。
5. 不在应用层自动重试。管理员可通过现有重发操作生成新 Token，重发前作废旧 Token。
6. 已知残余窗口：SMTP 已接受邮件后，数据库提交仍可能失败，导致邮件中的链接不可用。v3.2.0 接受该低概率窗口，用户通过重发获取新链接。
7. 如果未来业务要求数据库与投递请求原子一致，必须单独立项引入 Outbox；不得在本期同步流程上增加隐式异步或重试。

### 7.3 不同调用场景的失败响应

- 平台管理员主动创建管理员、重置管理员密码、重发邀请：发送失败可返回稳定的内部错误码，保持 fail-closed。
- 未来匿名“忘记密码”接口：无论账号是否存在、模板是否发送成功，对外都返回相同文案、HTTP 状态和近似处理时间，内部记录脱敏失败指标。
- 匿名重置请求必须按账号散列和来源执行限流，防止账号枚举和邮件轰炸；具体阈值由身份模块安全配置冻结，不属于 NotificationCapability。

## 8. EmailDeliveryAdapter 与 SMTP

### 8.1 Adapter 契约

该接口属于 `platform-notification` 的内部 SPI，不进入 `runtime-sdk-api`：

```java
public interface EmailDeliveryAdapter {
    void send(EmailMessage email) throws NotificationDeliveryException;
    String providerCode();
}

public record EmailMessage(
        String notificationId,
        String from,
        String to,
        String subject,
        String textBody
) {}
```

`notificationId` 由 `NotificationApplicationService` 生成 UUID，只用于日志和指标关联，不返回业务调用方。

`EmailMessage` 必须覆盖默认 `toString()`，只输出 notificationId 和脱敏收件人；不得输出 From、完整 To、Subject 或 Body。异常不得把完整 `EmailMessage` 作为 message 或 cause context。

未来 Provider 只能实现该接口。业务模块、`NotificationRequest` 和模板格式不得因 Provider 改变。

### 8.2 SMTP 实现

`SmtpEmailDeliveryAdapter` 使用 Spring `JavaMailSender` 和纯文本 `SimpleMailMessage`。它负责：

- 使用 `brix.notification.from` 作为唯一可信 From。
- 设置单个 To、Subject 和纯文本 Body。
- 将 Spring Mail / Jakarta Mail 异常包装为 `NotificationDeliveryException`。
- 不在异常消息中拼接 SMTP 密钥、完整邮箱、Subject 或 Body。
- 不做重试，不维护投递状态。

### 8.3 Bean 装配

- `NotificationApplicationService` 使用 `@ConditionalOnMissingBean(NotificationCapability.class)` 提供默认能力。
- 默认能力和 SMTP Adapter 只在 `brix.notification.enabled=true` 时装配。
- SMTP Adapter 使用 `@ConditionalOnProperty(name="brix.notification.provider", havingValue="smtp", matchIfMissing=true)`。
- SMTP Adapter 使用 `@ConditionalOnMissingBean(EmailDeliveryAdapter.class)`，未来加入其他 Adapter 时可替换。
- production 启动时没有 `EmailDeliveryAdapter` 必须失败。
- 本期移除 `LoggingNotificationCapability` 的自动装配；所有开发环境通过 Mailpit 或虚拟 SMTP 查看邮件。

## 9. 配置规范

```yaml
brix:
  notification:
    enabled: true
    provider: smtp
    default-locale: zh-CN
    templates-dir: ${BRIX_NOTIFICATION_TEMPLATES_DIR:}
    from: security@example.com

spring:
  mail:
    host: ${SMTP_HOST:mailpit}
    port: ${SMTP_PORT:1025}
    username: ${SMTP_USERNAME:}
    password: ${SMTP_PASSWORD:}
    properties:
      mail.smtp.connectiontimeout: 3000
      mail.smtp.timeout: 3000
      mail.smtp.writetimeout: 3000
```

production profile 额外强制：

```yaml
spring:
  mail:
    properties:
      mail.smtp.starttls.enable: true
      mail.smtp.starttls.required: true
      mail.smtp.ssl.checkserveridentity: true
```

生产启动校验必须确认：

- `brix.notification.enabled=true`。
- provider 只能为 `smtp`。
- From、SMTP host、username 和 password 非空。
- 三项连接/读/写超时均存在且不超过 3000 ms。
- STARTTLS、STARTTLS required 和证书主机名校验均为 true。
- `templates-dir` 非空时目录存在、可读且不是 classpath 或临时上传目录。

配置兼容期内，From 的读取优先级固定为 `brix.notification.from`，其次为旧 `brix.platform.admin.setup.mail-from`。使用旧配置时只记录 deprecated 配置 Key，不记录配置值；两个配置均为空时启动失败。

SPF、DKIM、DMARC、PTR 和发送域身份由部署环境配置，应用无法可靠自动创建。生产发布清单必须保存对应 DNS/Provider 验证证据；最低要求为 SPF、DKIM、DMARC `p=none` 或更严格策略。

## 10. 安全规则

### 10.1 Token 与 URL

- setup/reset/invite Token 使用密码学安全随机源，足够长、单次使用、带有效期。
- 数据库只保存 Token hash，不保存原文或完整 URL。
- URL 只能使用服务端配置的可信 base URL 构造，不读取请求 Host header。
- production base URL 必须为 HTTPS，且 Host 必须在显式白名单中。
- 重发前必须作废同一用户、同一 purpose 的旧 Token。
- Setup、Invite 和 Reset 页面必须设置 `Referrer-Policy: no-referrer`，防止查询参数中的 Token 通过 Referer 泄漏。

### 10.2 日志与指标

任何 profile 均禁止记录：

- 完整邮箱地址。
- raw token 或完整安全 URL。
- `variables` Map。
- Subject、Body 或渲染结果。
- SMTP 用户名、密码或 Provider 原始响应正文。

允许的结构化日志字段：

- `notificationId`
- `templateKey`
- `locale`
- `tenantId`，平台通知为空
- `providerCode`
- `recipientMasked`，例如 `a***@example.com`
- `result=accepted|failed`
- 稳定 failure code
- 当前 traceId/correlationId

### 10.3 指标

固定指标：

```text
brix.notification.render.total{templateKey,locale,result}
brix.notification.send.total{templateKey,provider,result}
brix.notification.send.duration{provider}
```

标签不得包含 tenantId、notificationId、邮箱、异常消息或其他高基数字段。

## 13. 最小验收标准

### 13.1 架构

- 业务模块无 JavaMail、Gmail、SES、SendGrid SDK import。
- Host 无通知业务和 Adapter 实现。
- `platform-notification` 不依赖 `platform-admin` 或 `platform-tenant`。
- 业务只通过 `NotificationCapability` 发送邮件。
- 替换为测试 Adapter 时业务代码和模板不修改。

### 13.2 兼容性

- 现有 `sendSetupLink(...)` 调用和旧实现可继续编译、加载、运行。
- create/reset/bootstrap API 响应结构不变。
- SMTP 失败时现有平台超管业务事务回滚并返回稳定错误码。
- 旧 `brix.platform.admin.setup.mail-from` 在一个版本兼容期内仍可读取。

### 13.3 模板

- 四个默认模板资源全部存在并通过启动校验。
- Java 代码中不再包含邮件 Subject 或 Body 文案。
- 缺失变量、多余变量、未知字段、非法占位符、Subject CR/LF 均拒绝发送。
- Locale 回退和外部覆盖行为与第 6.4 节一致。
- SMTP 对所有模板统一发送纯文本。

### 13.4 安全

- API、日志、审计和异常均不包含密码、raw token、完整 URL、Body 或 variables。
- Token 单次使用、过期失效、重发作废旧 Token。
- URL 使用可信 HTTPS base URL，不依赖 Host header。
- Setup、Invite 和 Reset 页面设置 `Referrer-Policy: no-referrer`。
- 未来匿名密码重置接入时必须具备统一响应和限流测试。
- production 不存在 Logging/Fake/InMemory 通知 Adapter。

### 13.5 投递与运维

- Mailpit/虚拟 SMTP 集成测试成功。
- 连接、读取、写入超时均不超过 3 秒，应用层不重试。
- production 强制 STARTTLS 和证书主机名校验。
- accepted/failed 日志完成脱敏，指标标签无 PII 和高基数字段。
- 生产部署已有 SPF、DKIM、DMARC 和可信 From 验证证据。

## 15. 后续版本触发条件

下列能力只有满足明确业务条件后才能立项，不能提前进入 v3.2.0：

| 能力 | 触发条件 |
|------|----------|
| Gmail API / SES Adapter | 已确定生产 Provider，SMTP 不满足认证、配额或运维要求 |
| 数据库模板与管理 API | 明确要求无需重启即可在线修改模板，并完成权限与审计设计 |
| 租户模板覆盖 | 产品明确允许租户品牌化，并完成模板安全治理 |
| HTML 邮件 | 已有视觉模板需求并确定 HTML 清洗、multipart 和客户端兼容策略 |
| Provider callback | 已选择提供标准事件的 Provider，并要求追踪退信/投诉 |
| Outbox | 业务不再接受“邮件已接收但事务提交失败”的残余窗口，或需要可靠异步重试 |
| 通知记录表 | 出现跨请求投递历史查询、合规留存或客服排查需求，并先冻结留存与删除策略 |

新增上述能力时，应扩展 Adapter 或内部实现；除非出现已评审的新通道需求，不得破坏本期 `NotificationRequest` 业务语义。

## 18. 冻结决策记录

| 决策 | 结论 |
|------|------|
| 是否建设完整通知中心 | 否 |
| 是否实现非 SMTP Provider | 否，只冻结 Adapter 边界并做替换测试 |
| 是否增加数据库模板 | 否，使用 classpath + 外部目录 |
| 是否允许运行时在线修改模板 | 否，修改文件后重启生效 |
| 是否支持租户模板覆盖 | 否，未来单独评审 |
| 是否支持 HTML | 否，本期所有 Provider 统一纯文本 |
| 是否保存通知记录 | 否，使用脱敏日志和指标 |
| 是否引入 Outbox 或自动重试 | 否，保留同步 fail-closed 并接受已记录残余窗口 |
| 是否返回 NotificationReceipt | 否，成功返回 void，失败抛统一异常 |
| 是否允许开发日志输出 setupUrl | 否，任何 profile 都禁止，开发使用 Mailpit |
| 是否保留 `sendSetupLink(...)` | 是，至少保留至下一次明确的主版本兼容评审 |

本文没有待施工团队选择的开放问题。新增范围或改变冻结决策必须先更新本文。
