## 0. 结论摘要

1. **目标**：由 Runtime 决定"这次调用能看哪个租户"，持久化适配器在 ORM 层自动执行。插件代码不写租户条件，也不接触租户上下文（DATA-040、T-21）。
2. **三道防线**：
   - **主手段**：ORM 自动过滤读取，并校验写入（DATA-040）。
   - **兜底**：SQL 语句校验器。无法证明安全的语句一律拒绝。
   - **可选第二道**：PostgreSQL RLS（§14.2）。本方案只保证将来能接上，不施工。
3. **跨租户访问**：现在由插件用注解给自己开豁免（7 处），改为由 Runtime 按登记的策略授予。7 处的去向：
   - 3 处改为在确定的租户内访问，其中 1 处是平台超管建租户；
   - 2 处归入命名策略；
   - 1 处（C 端跨租户发现）违反 §9.2，作废；
   - 1 处是没有调用方的遗留代码，删除。

   另有 2 处没加注解、但同样不按租户访问（接受邀请、设置完成后补发邀请），也归入策略。共 3 条策略（§3.5）。
4. **行为不变**：登录、选租户、切换、邀请、接受邀请、平台超管操作的结果都不变。唯一新增的是登录发现会写平台审计；§6.3 本来就要求，目前只写了日志。（施工结果：平台审计写入本期未实现，仍只写日志，见 §13 第 2 条。）
5. **待你确认**：3 个决定 D1～D3（§7）。
6. **需要 RFC**（§8）：
   - R1：一个小的 multi-tenant Patch；
   - R2：一份根级安全 RFC，提前停用 3 个只能跨租户工作的 L2A 方法。这 3 个方法当前都没有运行中的调用方。
   - R3（施工中补充）：RFC-007，提前停用 2 个按 contextId 查找的 L2A 方法，见 §13 第 1 条。
7. **施工**：分 4 期（§9），每期可单独验证。主机装配的企业业务插件不在本期；它们改用 PersistenceCapability 后自动纳入。

## 1. 现状

### 1.1 现在的隔离是怎么工作的

platform-tenant 在共享的 EntityManagerFactory 上注册了一个组合 `StatementInspector`（`TenantInterceptorConfig`，经 `HibernatePropertiesCustomizer` 注册）。每条 SQL 先过"守卫"，再过"改写器"：

- **改写器 `TenantInterceptor`**：从 platform-common 的 `TenantContext`（一个 ThreadLocal）取租户，往 SQL 里拼 `tenant_id = …`。
  - 生产中没有任何代码写这个 ThreadLocal。唯一的写入点 `TenantFilter` 没有注册成过滤器；`TenantCapabilityImpl.setCurrentTenantId` 没有调用方。
  - **所以改写器从不生效。**
- **守卫 `TenantSqlGuardInterceptor`**：用正则判断 SELECT/UPDATE/DELETE 的 WHERE 里有没有 `tenant_id =`。没有就抛 `TenantSqlViolationException`。
- **跨租户**：在方法上加 `@CrossTenantAccess`。platform-tenant 自带的切面在调用期间把一个静态 ThreadLocal 设成"豁免"，守卫看到后整体放行。

所以今天真正的隔离手段是：**开发者在每个查询里手写 `tenantId` 条件，守卫只检查"写了没有"。**

### 1.2 问题

| # | 问题 | 证据 | 不符合 |
|---|---|---|---|
| 1 | **正确性依赖手写条件。** 守卫只看"有没有写 `tenant_id =`"，不看值是不是当前租户。platform-tenant 租户表上 46 个自定义查询中，35 个靠调用方传入的 `tenantId` 参数 | 附录 B | DATA-040；专项 §11.5 第 1 条 |

### 1.3 相关但不在本方案内的现状

**企业业务插件**：主机装配了 10 个企业业务插件，其中 9 个有自己的表。

- 它们仍由 Spring 创建 Repository，并使用 `@Transactional`。
- 共约 130 个查询方法，约 40 个没有任何租户条件，其中 intake 的 19 个全部没有。
- 它们的租户 ID 来自 `TenantCapability.getCurrentTenantId()`，而这个值在生产中从未被设置。

本方案不改它们（见 D3），只保证它们现在的行为不变。

**其他**：

- platform-auth 的 `auth_refresh_token`、`auth_context_selection_ticket` 也由 Spring 创建 Repository。它们属于 platform-auth 的旧登录流程；其中刷新令牌表仍被 EX-2026-002 下的平台登录使用。
- Hibernate 二级缓存没有开启。

## 2. 设计原则（不变量）

| # | 不变量 | 依据 |
|---|---|---|
| I-1 | 租户权威只来自 Runtime 已验证的上下文：令牌 `tid`、事件信封、平台内部契约的类型化目标。插件不能设置、切换或清除 | T-4、T-21、DATA-011、ERROR-006 |

## 3. 总体设计

### 3.1 分层职责

```text
L2B Runtime（runtime-orchestrator）
  Dispatcher / 内部契约代理 / 能力代理 / 事件投递
    └─ 按入口声明解析"数据范围"（DataScope）
         └─ 打开 Owner Unit of Work 时交给 L2C（L2B↔L2C 内部接口，不进 L2A）

L2C 持久化适配器（infra-adapter-persistence-jpa）
  ├─ 表分类登记：启动时把每张表归为租户表、全局表或受托表；归不了类就启动失败
  ├─ 读：ORM 过滤（由适配器程序化登记 Hibernate filter，插件实体零注解）
  ├─ 写：用 Hibernate 实体事件校验租户归属
  ├─ 兜底：语句校验器（StatementInspector，只判断，不改写）
  └─ （可选，后续）RLS：每个事务执行 SET LOCAL brix.tenant_id

插件
  只用 PersistenceCapability 的 Repository 与 UnitOfWork；不写租户条件，不碰租户上下文
```

### 3.2 数据范围

数据范围（DataScope）是 L2B 与 L2C 之间的内部概念，不进入 L2A，插件看不到。

| 种类 | 含义 | 对租户表 | 对全局表 |
|---|---|---|---|
| **租户** `TENANT(t)` | 只能访问租户 t | 读：自动加 `tenant_id = t`<br>写：必须属于 t，`tenant_id` 不可改 | 按各 Owner 规则 |
| **策略** `POLICY(p)` | 登记的跨租户策略 p（见 §3.5） | 只能按策略的键访问策略列出的表；命中的行决定之后可访问的租户集合 | 按策略 |
| **无租户** `NONE` | 平台登录、`tenantContext=forbidden` 等 | 一律拒绝（`TENANT_SCOPE_REQUIRED`） | 按各 Owner 规则 |

### 3.3 范围从哪里来

| 入口 | 范围 | 来源 |
|---|---|---|
| HTTP Endpoint，`tenantContext.mode=required` | `TENANT(tid)` | Dispatcher 已从令牌取得并验证的 `tid`（即 `EndpointInvocation.tenantId`） |
| HTTP Endpoint，`forbidden`，或 `optional` 且无租户 | `NONE`；若声明了 `sourcePolicyRef`，则为该 `POLICY` | Manifest（根 MANIFEST-017 已有该字段） |
| 事件、命令 | 信封 `scope=TENANT`：`TENANT(tenantId)`<br>`scope=PLATFORM`：`NONE`，或 `scopePolicyRef` 指定的策略 | 信封与 Manifest（MESSAGE-021、MANIFEST-025） |
| Task | 由 `scopePolicyRef` 决定 | Manifest |
| 平台内部契约 | 参数标明了目标租户：`TENANT(目标)`，即"平台定向"<br>创建租户：`TENANT(本事务新建的租户)`<br>接受邀请 `acceptFirstOwnerInvitation`：策略 P-2<br>只读全局表的方法：`NONE` | 类型化目标（§6.1）；按方法登记 |
| 身份协议面调用 `TenantAccessCapability` | 每个方法一条固定规则（§5） | L2B 中与该 L2A 契约一起版本化的规则表 |
| 插件在入口之外自己打开的 Unit of Work | `NONE` | — |

最后一行保证：没经过 Runtime 入口的代码碰不到租户数据（DATA-028）。

### 3.4 绑定与收窄

1. 范围在 Owner Unit of Work 打开时绑定。同一 Owner 内嵌套的 `required`/`readOnly` 片段继承同一范围，不能更改。
2. 调用另一个 Owner 时，当前事务被挂起（DATA-029、HOST-020）；被调方的范围由调用边界重新确定。
3. 唯一允许的变化是 `POLICY` 的单向收窄：
   - 策略按键查到的行决定一个租户集合；
   - 之后，其它租户表只能在该集合内访问，写入也只能落在该集合内；
   - 集合只会加入策略键命中的行所属的租户，插件不能自己加租户。
4. 不同范围之间从不共享持久化上下文（一级缓存）。

### 3.5 跨租户策略

策略由平台登记并版本化。插件只能在 Manifest 中引用策略，不能定义策略。

| 策略 | 依据 | 键与提供者 | 可访问的租户表 | 读写 | 审计 |
|---|---|---|---|---|---|
| **P-1** `login-tenant-discovery` | §6.3、§9.2、identity-auth FLOW-002/004、T-26 | `identity_id`：身份协议面传入登录事务里已认证的身份，L2B 把它绑定为过滤值 | `sys_tenant_member` | 只读。浏览器只拿到租户名和一次性 ticket（现状不变） | 平台审计 `LOGIN_TENANT_DISCOVERY`：身份、来源 IP、命中租户集合 |
| **P-2** `first-owner-invitation-resolution` | ENTRY-005、§5.7 接受伪代码、identity-auth ONBOARD-002 | `token_hash`：由请求中的一次性 token 计算，持有 token 即有权查看。适配器只允许按这个唯一键做等值查询，最多 1 行 | 只读形式：`sys_tenant_invitation`<br>读写形式：锁定邀请后，该租户内 platform-tenant 的全部租户表 | 托管邀请页只读；接受入口读写 | 沿用现有的接受事务内租户审计与 Outbox |
| **P-3** `first-owner-invitee-setup-fanout`（取决于 D2） | 待 R1 登记 | `invitee_email`：L2B 投递事件时，按事件中的身份向身份 Owner 取得其邮箱，并绑定为过滤值；插件不能指定 | `sys_tenant_invitation`（仅 FIRST_OWNER、PENDING）<br>命中租户内的 `sys_tenant_member`（只读）和租户审计 | 只能修改命中的邀请 | 平台审计 `FIRST_OWNER_INVITEE_SETUP_FANOUT`：身份、受影响的租户 |

"平台超管定向操作"不是策略，它就是 `TENANT(目标)`：一次只能操作一个租户。审计照 super-admin 的现有规定，由 platform-admin 拿到结果后写平台审计。

## 4. 适配器机制

### 4.1 表分类登记

Owner 持久化单元创建时（P4/O4），为每个映射到实体的表分类：

| 分类 | 条件 | 规则 |
|---|---|---|
| **租户表** | 有 `tenant_id` 列 | 必须 `NOT NULL`（T-1）<br>不得开启二级缓存<br>不允许给租户列赋值的批量 UPDATE，也不允许 `insert … select`（见 4.3） |
| **全局表** | 没有 `tenant_id`，且在平台全局表清单中 | 清单与 multi-tenant §6.1 一一对应（见 R1）<br>业务插件不能有全局表 |
| **受托表** | Manifest `data.outbox` / `data.inbox` 声明的表 | `tenant_id` 可空<br>写入时校验与范围一致；按消息标识读取 |

以下情况都启动失败（fail-closed，T-15）：

- 表归不了类；
- 租户表的 `tenant_id` 可空；
- 租户表开了二级缓存。

### 4.2 读：ORM 过滤

- **登记**：适配器在构建 EntityManagerFactory 时，为每个租户表实体登记 Hibernate filter。
  - 租户过滤：`tenant_id in (:tenants)`；
  - 策略键过滤：P-1、P-3 的过滤值由 L2B 绑定（§3.5）。P-2 的键是请求中的秘密 token，不做过滤，由语句校验器强制"只能按 `token_hash` 等值查询"；
  - 插件实体不加任何注解，因此不用改 DATA-024 的白名单。
- **启用**：打开 Unit of Work 时，按范围启用相应的 filter。
- **同步**：每次 Repository 调用前，`OwnerRepositoryInterceptor` 按当前范围（包括策略收窄后的租户集合）同步一次 filter。
- **必须覆盖的查询形态**（P0 逐项证明）：
  - 派生查询、JPQL、Specification；
  - `findById` / `getReferenceById`；
  - 懒加载的关联与集合；
  - 分页查询及其 count 查询；
  - `@Lock` 查询；
  - count / exists。

  证明不了的形态，在租户表上启动期拒绝。

### 4.3 写：实体级校验

- 用 Hibernate 的 insert/update/delete 事件监听校验：
  - 实体的 `tenant_id` 必须在当前范围内；
  - 修改时必须与原值一致；
  - `NONE` 和只读策略下，拒绝写租户表。
- Hibernate 按主键生成的 UPDATE/DELETE 不带租户条件，所以这类写入的正确性由上述监听保证。
- JPQL 批量 UPDATE/DELETE 会绕过实体事件。P0 证明 Hibernate 会给它们的 WHERE 加上租户过滤，所以允许使用。但有两种写法会越界，在租户表上启动期拒绝（校验 Repository 时发现即失败）：
  - 给租户列赋值的批量 UPDATE：过滤只限定改哪些行，赋值本身能把行移到别的租户；
  - HQL `insert … select`：插入的行可以落在任意租户。

  platform-tenant 目前没有这两种写法；企业插件迁移时逐个检查。
- 租户列映射为 `updatable = false` 时，修改它的值不会触发更新事件，也不会写入数据库（P0 已验证）。这不破坏隔离，但会让这个错误无声无息。

### 4.4 兜底：语句校验器

它替换现在的正则守卫，只判断，不改写：

- **SELECT**：每个出现的租户表别名都必须带当前范围要求的谓词（租户条件或策略键）。`NONE` 下出现租户表即拒绝。
- **UPDATE/DELETE**：租户表上的语句必须满足以下之一：
  - 带租户过滤（批量形式）；
  - 按主键的实体级语句。它的租户归属由 4.3 的监听保证。
- **INSERT**：只接受实体级的 `insert … values`。
- **方言差异**：PostgreSQL 上的悲观写锁渲染为 `for no key update of <别名>`，H2 上是 `for update`，校验器两种都要识别。
- **认不出来的语句**：只要涉及租户表就拒绝。
- **开销**：校验结果按"范围种类 + SQL 文本"缓存。SQL 是参数化的，开销可以忽略。
- **依赖**：优先不引入新的第三方依赖。若需要 SQL 解析库，按 S-7/S-8 走依赖评审。
- **Owner 单元之外的语句**：platform-auth、企业插件等模块仍由 Spring 创建 Repository，它们的语句沿用现有守卫规则，行为不变。最后一个这样的模块迁完后，删除这套旧规则。

### 4.5 L2B 与 L2C 之间

- **交接**：L2B 打开 Owner Unit of Work 时，把范围一并交给 L2C。
  - 做法是扩展 runtime-orchestrator 内部的 `OwnerPersistenceProvider` 和 `EndpointInvocationBoundary`。
  - 不改 L2A 的 `PersistenceCapability` / `UnitOfWork`，DATA-043 冻结的签名不动。
- **载体**：范围在 L2C 内挂在事务同步资源上，与现在的 `OwnerTransactionScope` 同一做法。
  - 事务完成、回滚或挂起时，范围随之解除。
  - 这是 L2B/L2C 的私有载体，插件不可见（专项 §11.1）。

### 4.6 错误、日志、审计

- **错误码**：新增两个稳定错误码 `persistence.tenant_scope_required`、`persistence.tenant_scope_violation`。
  - 实现上是给 `PersistenceCapabilityException.Code` 增加枚举值。CAP-021 规定枚举不是封闭集合，所以这属于 Minor 扩展。
  - Dispatcher 按稳定错误目录映射它们（MANIFEST-022），响应中不出现表名、SQL 等内部细节。
- **每次违规都记录**：
  - 结构化安全日志：Owner、范围种类、表名、SQL 指纹，不记参数值；
  - 计数指标：标签只有 Owner、范围种类、原因；
  - 告警。
  - **施工状态**：日志与计数已实现，告警自 2026-10-28 第二次部署起已接通，见 §13 第 3 条。计数比上面多一个 `code` 标签（稳定错误码）。
- **策略审计**：P-1、P-3 的调用结束后，L2B 请平台审计 Data Owner 记一条平台审计。
  - 写入在该 Owner 自己的独立本地事务中提交，调用方事务挂起，与专项 §10.1 第 5 条的做法相同。
  - 审计写入失败时，本次策略调用也失败（fail-closed）。
  - **施工状态**：2026-10-28 第三次部署起已实现。按平台审计方案的 D1，由 Runtime 策略审计写入器在平台审计 Owner 的受托写入登记下直接写入，不经 Owner 的内部契约；独立事务与 fail-closed 语义同上。见 §13 第 2 条。
- **影子模式**：Local Profile 可以开启影子模式（只记录，不拦截），供开发排查；Standalone/Production Profile 启动时拒绝这个设置。

### 4.7 RLS（不施工）

本方案保证 RLS 将来可以直接接上：

- 范围在事务开始时就已确定，RLS 适配器用同一个范围执行 `SET LOCAL brix.tenant_id`；
- 策略范围需要另写按键的 RLS 策略。

施工放在多租户 Phase 6：先影子模式，再强制。

## 7. 需要你确认的决定

### D1：ORM 层的主机制

**推荐：由适配器程序化登记 Hibernate filter，并用实体事件校验写入。**（P0 已确认可行，见附录 C。）

- 能表达三种限制：按租户、按策略键（身份、token、邮箱）、按收窄后的租户集合。
- 插件实体不加注解，DATA-024 白名单不动。
- 是 DATA-040 点名允许的实现方式之一。

**不选 Hibernate 租户鉴别列（`@TenantId`）：**

- 它只有"限定一个租户"和"完全不过滤"两种状态。跨租户策略只能开成"看全部租户"，做不到按键的最小授权。
- 在插件实体上加 `@TenantId`，还要先改 DATA-024 的白名单，那需要根级 RFC。

**不选改写 SQL 文本**：现在的改写器就是这种做法，它对连接、子查询、别名都不可靠。

**P0 发现问题时的处理**：

- 若 P0 证明 filter 在某些查询形态上不可用，这些形态在租户表上启动期禁止。
- 若禁止的范围大到影响现有功能，P0 停下来，回到你这里重新决定。

### D2：受邀人完成设置后补发邀请（§5 第 8 行）

**现状**：

1. 平台超管邀请一个还没有账号的邮箱时，系统先发设置链接。
2. 对方完成设置后，身份服务发出一个进程内事件。
3. platform-tenant 收到后，按该邮箱找出所有待接受的 FIRST_OWNER 邀请，重新生成 token，发出邀请邮件。

第 3 步是按邮箱跨租户查询，现有蓝图没有条款覆盖它。

**A（推荐）：登记为策略 P-3。**

- 键是"刚完成设置的身份的邮箱"，来自身份 Owner 已提交的事实，不来自请求。
- 只能看到、修改发给这个邮箱的待接受 FIRST_OWNER 邀请；每次使用写平台审计。
- 改动小，行为不变。
- 需要 R1 把它写进 §6.3。
- 同时把这条进程内事件改成 Runtime 管理的投递（§6.2），去掉 platform-tenant 里最后一处 Spring 事务依赖。

**B：设置流程携带邀请引用（租户和邀请 id）。**

- 设置完成后只处理这些邀请，每个都在自己的租户范围内，不需要跨租户读。
- 代价：要改身份侧 setup token 表和 L2A 契约，涉及两个 Owner，还涉及 super-admin §15.2 的表语义。改动大得多。

**关联**：你之前问过"第二封邀请邮件是否必要"。如果以后改成设置完成后直接进入接受，A 和 B 都不再需要，P-3 可以整条删除。

### D3：本期范围

**推荐**：本期只做 Runtime/适配器机制，以及平台模块的改造：

- platform-tenant；
- platform-identity 的表分类；
- 身份协议面与令牌校验的调用点。

企业业务插件按 platform-tenant 第 1 步的做法，逐个改用 PersistenceCapability 后自动纳入新机制，另立计划。在那之前，适配器对它们沿用现有守卫规则，行为不变。

**备选：本期同时迁移企业插件。** 工作量会成倍增加：约 40 个查询没有任何租户条件，还有多处批量更新需要逐个改写和测试，会拖慢平台侧上线。

## 8. 需要 RFC 的事项

### R1：multi-tenant 5.1.2（预计 Patch）

按专项 §13 走 RFC-005，需要 architecture、security、SRE 批准。

1. **补全 §6.1 白名单**：补入 `sys_setup_token`、`sys_bootstrap_state`。

   - 同时写明：§6.1 就是适配器的全局表登记清单，两者一一对应。
2. **§6.3 改为穷举的"跨租户访问策略登记表"**，每条写明键、可访问的表、读写和审计：

### R2：根级安全 RFC，提前停用 3 个 L2A 方法

- **对象**：`TenantAccessCapability` 的 `getActivePrincipalships`、`touchMemberAccess(Long)`、`touchPrincipalAccess(Long)`。
- **为什么需要 RFC**：CAP-023 规定，弃用方法要保留到下一个 Major；只有安全问题可以经安全 RFC 缩短，并且必须提供迁移说明。
- **理由**：这 3 个方法只能靠跨租户访问才能工作，第一个还直接违反 §9.2。若照常保留，新机制就得为它们另开跨租户豁免，正好与本方案的目标相反。
- **影响**：当前没有运行中的调用方；迁移说明见 §6.1。
- **若不批准**：为它们各登记一条"遗留"策略，保留到下一个 Major，并记为已知技术债。

### R3：根级安全 RFC，提前停用 2 个按 contextId 查找的 L2A 方法（施工中补充）

- **对象**：`TenantAccessCapability` 的 `findMembershipByContextId`、`findPrincipalshipByContextId`。
- **为什么需要 RFC**：§6.1 原计划在弃用期内把它们映射到 P-1，这一点不成立（§13 第 1 条）。新机制下它们调用即失败，等于缩短 CAP-023 的弃用期。
- **影响**：主干上 6 个调用点都是运行中的路径，本期已全部改用带租户的新方法。
- **文件**：[RFC-007](rfc/RFC-007-运行壳-提前停用两个按contextId查找的L2A方法（Draft）.md)，已于 2026-10-27 批准（architecture-committee、security、SRE）。

**时序**：

- R1、R2 批准前可以先做 P0。

## 11. 风险与对策

| 风险 | 对策 |

## 13. 施工记录与偏差（2026-10-27）

P1、P2 在 brix 与 brix-enterprise 的分支 `claude/tenant-isolation-l2c` 上提交，2026-10-28 快进合并到两个仓库的 main，未推送，同日部署到共享环境。brix 的提交依次是 `3082ea6`（L2A）、`edd0677`（L2B）、`8885812`（L2C 适配器）、`ed8bf0b`（platform-tenant、platform-admin）、`dd8abbf`（身份协议面与令牌校验），之后 `4bd58d4` 补上违规计数（第 3 条）。下面记录与本方案的偏差、遗留项和验证结果。

### 13.1 偏差与遗留项

1. **按 contextId 查找的两个方法（更正 §6.1）**
   - 原计划：弃用期内由 L2B 映射到 P-1，继续可用。
   - 不成立的原因：5.1.2 §6.4 中 P-1 的键是 `identity_id`，只读 `sys_tenant_member`。按 contextId 查找没有这个键；`findPrincipalshipByContextId` 读的 `sys_tenant_principal` 也不在 P-1 的表内。§6.4 没有其他登记。
   - 施工结果：两个方法没有租户范围，调用即以 `persistence.tenant_scope_required` 失败。平台的 6 个调用点已全部改用 `findMembershipByContext`、`findPrincipalshipByContext`。
   - 这等于缩短 CAP-023 的弃用期，需要 R3（[RFC-007](rfc/RFC-007-运行壳-提前停用两个按contextId查找的L2A方法（Draft）.md)）。RFC-007 已于 2026-10-27 批准（architecture-committee、security、SRE，决定记录 `user-authorization:2026-10-27:rfc-007`）。
2. **策略审计只写日志（§4.6 未实现；2026-10-28 第三次部署后已写平台审计）**
   - super-admin 4.0 §1.3a 规定平台审计由唯一的 `platform-audit` Data Owner 持有，并提供内部契约 `brix.internal.platform.audit`（`PlatformAuditAdministration`）。代码中二者都不存在：`sys_platform_audit_log` 目前由 platform-identity 写入，没有可供 L2B 或身份协议面调用的契约。
   - 本期每次使用 P-1、P-3 都写一条结构化审计日志（logger `brix.tenant.isolation.audit`，事件 `tenant.policy.used`）；P-2 绑定租户时写 `tenant.policy.bound`。
   - 在 platform-audit Owner 落地并接上之前，不能宣称满足 multi-tenant §6.3 与 identity-auth AUDIT-001 关于登录发现写平台审计的要求。§9 P3、§10 中"登录发现有平台审计记录"的检查，暂以这条日志代替。
   - **已接上（2026-10-28 第三次部署）**：platform-audit Owner 已拆出，P-1、P-3 的每次使用都由 Runtime 策略审计写入器（`runtime.tenant-policy-audit`，根 DATA-045～DATA-047）写入 `sys_platform_audit_log`，写不进去这次使用就失败。日志 `tenant.policy.used` 保留，与审计行带同一个 traceId。施工与验证见[平台审计 Owner 拆分设计方案](v4.0-平台超管-平台审计Owner拆分与策略使用审计-设计方案.md) §13。共享环境已于 2026-10-28 16:21 核对：负责人登录员工控制台后，登录和读会话各写了一行登录发现审计，日志有同 trace 的 `tenant.policy.used`。
3. **违规计数与告警（§4.6，2026-10-28 补上计数和规则）**
   - **每次违规只记一次**：
     - 记录点在适配器发现违规的地方：语句校验器、写入校验、租户绑定，以及 Owner 单元之外的旧规则；
     - 每次写一条结构化安全日志，事件 `tenant.isolation.violation`。日志带 reason、Owner、范围种类、错误码，以及表名或 SQL 指纹，不记参数值；
     - 同时给计数器 `brix.tenant.isolation.violations` 加 1。
     - 之前，写入校验和租户绑定的违规没有日志；在 Owner 事务里遇到其他模块的语句时会记两条。现在都改为只记一次。
   - **计数器标签**：
     - `owner`、`scope`（范围种类）；
     - `reason`：`statement`、`entity-write`、`tenant-binding`、`legacy-statement`；

### 13.2 端到端发现并已修复的问题

三处都是单元测试没有覆盖到的组合，已在适配器中修复，并补了回归测试：

1. **`tenant_id` 作主键的表无法分类**
   - platform-tenant 的 `platform_tenant_first_owner_projection` 每个租户一行，`tenant_id` 就是主键。适配器只在普通属性里找租户列，因此把它判为"没有 `tenant_id` 的未登记表"，主机启动失败。
   - 修复：主键是 `tenant_id` 时按租户表处理；写入校验从实体 id 取租户。读过滤本来就按表的列登记，不受影响。
   - 回归：一致性测试新增"租户键主键"一项；brix-enterprise 的主机契约测试新增 `OwnerPersistenceIsolationContractTest`，在主机组装处对 platform-tenant、platform-identity 的全部实体做启动期分类。
2. **提交回调里先后打开两个 Owner 的 Unit of Work 时，第二个失败**
   - 场景：身份 Owner 提交后，D2-A 的投递先向身份 Owner 取邮箱（一个只读事务），再打开 platform-tenant 的事务。
   - 原因：第一个嵌套事务结束时，Spring 把线程上的"有实际事务"标记清掉，而外层已完成事务的 EntityManager 还绑定着。`OwnerUnitOfWork` 把它误当成请求级 EntityManager 解绑，留下的 JDBC 连接让第二个事务报 "Pre-bound JDBC Connection found"。结果是设置完成后不发邀请邮件。
   - 修复：仍与事务同步的 EntityManager 不再解绑，交给 Spring 照常挂起。
   - 回归：`OwnerUnitOfWorkTest` 新增对应用例；去掉修复后该用例失败。
3. **策略范围被同一调用链中其他 Owner 的事务继承**
   - 场景：P-3 的 Handler 在 platform-tenant 的事务中调用 platform-identity 的能力取邮箱，后者打开自己的只读事务。
   - 原因：Runtime 请求的范围对线程上的整条调用链生效。适配器原先遇到"不属于本 Owner 的策略"直接报错，补发因此失败。
   - 修复：登记的策略只对其 Owner 生效（§6.4）。其他 Owner 在策略生效期间打开的事务没有租户范围，只能访问自己的全局表。已验证的租户范围仍对同一请求涉及的所有 Owner 生效。
   - 回归：新增 `TenantScopeStateTest`。

## 附录 C：P0 验证结论（2026-10-27）

**范围与证据**：

- 环境：Hibernate 7.4.5.Final，Spring Data JPA；在 H2（PostgreSQL 模式）和参考 DCP PostgreSQL 15 上各跑一遍，30 项测试全部通过，两库结果一致。PostgreSQL 用的是一次性容器，用完即删。
- 测试：brix 仓库 `infra-adapters/.../infra-adapter-persistence-jpa/src/test/java/io/infra/adapter/persistence/jpa/tenancy/TenantFilterConformanceTest.java`。每次运行的 SQL 与行为记录写到该模块的 `target/p0-tenancy-<库>.txt`。
- 数据：两个租户放了看起来相同的数据，并故意放入引用另一租户的行（文档指向另一租户的文件夹、笔记挂在另一租户的文档下）。缺少过滤时，结果里会多出另一租户的行。
- 原型：过滤登记与写入校验的原型只放在测试代码里，用一个配置项开启；该模块原有的 32 项测试不受影响，模块合计 62 项全部通过。

**接入点**：Hibernate 在绑定完注解实体之后、构建 persister 之前，依次调用各个 `AdditionalMappingContributor`。适配器在这一步给实体和集合的映射登记 filter，插件实体不需要任何 Hibernate 注解，DATA-024 白名单不动。写入校验用 `Integrator` 注册 insert/update/delete 事件监听。

| 形态 | 结果 | 渲染出的条件（示例） |
|---|---|---|
| 派生查询、count、exists | 过滤 | `pd1_0.tenant_id in (?) and pd1_0.title=?` |
| 分页查询及其 count | 过滤 | 两条语句都带 `pd1_0.tenant_id in (?)` |
| 接口投影、JPQL 实体与标量查询、Specification 及其 count | 过滤 | 同上 |
| `findById`、`findAllById`、`existsById` | 过滤 | `pd1_0.id=? and pd1_0.tenant_id in (?)` |
| `getReferenceById` 指向另一租户 | 访问时抛 `EntityNotFoundException`，拿不到数据 | 按主键加载时带过滤 |
| 懒加载 to-one 指向另一租户 | 抛 `EntityNotFoundException`，拿不到数据 | 同上 |
| 懒加载集合 | 只返回本租户的子行 | `n1_0.doc_id=? and n1_0.tenant_id in (?)` |
| 显式 join、fetch join | 被连接的实体也过滤 | — |
| 子查询 | 过滤 | — |
| `@Lock(PESSIMISTIC_WRITE)` | 过滤 | H2：`… for update`；PostgreSQL：`… for no key update of <别名>` |
| 批量 UPDATE、DELETE | 只影响本租户的行 | `update p0_doc pd1_0 set title=? where pd1_0.tenant_id in (?)` |
| **给租户列赋值的批量 UPDATE** | **会把行移到另一租户** | 过滤只限定改哪些行 → 启动期禁止 |
| **HQL `insert … select`** | **插入的行可以落在任意租户** | 不触发实体事件 → 启动期禁止 |
| 全局表 | 不过滤 | — |
| 租户集合 {1, 2} | 两个租户的行都可见 | 策略收窄后的集合按此执行 |
| 按身份键、按邮箱键过滤（P-1、P-3 的形态） | 只看到该键在各租户中的行 | `identity_id = ?`、`invitee_email = ?` |
| 按秘密键查找后，在同一 Unit of Work 内收窄到该租户（P-2 的形态） | 收窄后只看到该租户 | 查找语句为 `pi1_0.token_hash=? for update` |
| 开启过滤前已加载进持久化上下文的实体 | 开启过滤后仍能用 `find` 拿到 | 证明 §3.4 第 4 条必要：不同范围不得共享持久化上下文 |
| 不开启任何过滤 | 不做任何限制 | 证明 `NONE` 必须由校验器和写入监听拒绝，不能靠 filter |
| 新增行属于另一租户 | 写入监听拒绝，数据库没有该行 | — |
| 修改可更新的 `tenant_id` | 写入监听拒绝 | — |
| 修改 `updatable = false` 的 `tenant_id` | 不报错，也不写入 | 隔离不受影响（见 4.3） |
| `deleteById` 另一租户的行 | 什么也不做 | 删除前的按主键查找已被过滤 |
| 删除指向另一租户的引用 | 抛 `EntityNotFoundException`，行仍在 | — |

**结论**：D1 成立。§4.3 原先"租户表上禁止所有批量 UPDATE/DELETE"的规则放宽为只禁止两种会越界的写法；其余结论与 §4 一致。
