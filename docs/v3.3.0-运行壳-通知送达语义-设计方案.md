> **状态**：已批准（2026-11-08 负责人按推荐批准 D103～D108）。后续各点排在标准链路收尾方案 §11 第 14a、14b 点和 §11.1 队列。送达语义（D103、D105、D106、D108）写进 RFC-012，随根 3.4.0 发布后才能施工；D104（发送超时）是现行根 `BRX-RS-RESILIENCE-001` 已经要求的，可以先做

## 0. 结论

1. 文档说"邮件在事务提交后发送"，代码不是这样：三处发信都在业务事务里同步走 SMTP，在提交之前。
2. 现在的做法有一个好处：SMTP 拒收时，这次写入整个回滚（fail-closed），调用方马上知道。问题有三个：
   - 发信之后，同一个事务里还有写入（消费 Bootstrap 会话、写审计事实、保存端点答案）。其中任何一步失败，或者提交失败、进程崩溃，邮件已经发出，链接里的令牌却从没生效；同一个键重试还会再发一封。
   - SMTP 没有超时，连接、读、写都会无限等待，违反根 RESILIENCE-001。SMTP 卡住时，请求线程和数据库锁一直被占着。
   - 怎样算发成功、失败后怎么补救，没有一份 ACTIVE 文档写明。super-admin NOTIFY-003 把它交给"活动通知专项"，现在没有这份专项。
3. 推荐（§3）：
   - 保持同步、fail-closed，但把发信挪到 Unit of Work 提交前的最后一刻；
   - 给 SMTP 加超时；
   - 写明残余窗口；
   - 不经 Outbox，不自动重试；
   - 规则随根 3.4.0 写进根，super-admin 引用它。
4. Owner 的代码不用改，发信时机由 `NotificationCapability` 的实现保证。
5. 批准后按 §6 拆成小点。

## 1. 现状

### 1.1 有哪些通知

| 通知 | 模板 | 发信的 Owner | 什么时候发 | 链接里的令牌 |
|---|---|---|---|---|
| 首位超管的设置链接 | `platform.admin.setup.initial` | platform-identity | `create-first-admin`（Bootstrap） | 在查询串 `?token=`（见 §5） |
| 首位 OWNER 受邀人的身份设置邮件 | `tenant.owner.setup.initial` | platform-identity，由 platform-tenant 调用 | 建邀请、重发邀请，且受邀邮箱还没有已激活的身份 | 在片段 `#token=` |
| 首位 OWNER 邀请邮件 | `tenant.owner.invitation.initial` | platform-tenant | 建邀请、重发邀请（身份已激活）；受邀人完成身份设置后补发（事件 `FirstOwnerInviteeSetupCompleted`） | 在片段 `#token=` |
| 超管的设置与重置链接 | `platform.admin.setup.initial`、`platform.admin.setup.password-reset` | platform-identity | 新建超管、重置凭证，端点还没做 | — |
| 以后要有的 | — | — | 租户成员邀请（multi-tenant §5.5，没做）；身份认证 ABUSE-002 的安全通知：新设备登录、凭证变更、MFA 重置、会话撤销（M1 计划登记为没做） | 安全通知不带令牌 |

### 1.2 现在怎么发

- `NotificationCapability.send` 在调用方线程上渲染模板、走 SMTP，失败时抛 `NotificationException`（`NotificationApplicationService`）。
- 三处都在 Owner 的 Unit of Work 里调用，都在提交之前：
  - `createFirstAdmin`：发信之后还要消费 Bootstrap 会话、写两条审计事实，然后由端点保存答案、提交；
  - 建邀请、重发邀请：发信之后由端点保存答案、提交；
  - 设置完成后补发：在事件 Handler（`FirstOwnerInviteeSetupCompletedHandler`）的 Unit of Work 里重签令牌、发信，再与 Inbox 一起提交。
- SMTP 没有超时：主机只设了认证和 STARTTLS（`SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH`、`..._STARTTLS_ENABLE`、`..._STARTTLS_REQUIRED`），连接、读、写超时都没设。JavaMail 这三项的默认值是无限等待。
- 回答和日志：`create-first-admin` 只回 id、identityId 和 `setupLinkSent`；日志只记脱敏的收件人和模板，满足 NOTIFY-001。

### 1.3 后果

| 情形 | 现在 |
|---|---|
| SMTP 拒收或报错 | 这次写入回滚，调用方拿到错误，可以重试。这是对的 |
| 发信之后的写入失败，或者提交失败、进程崩溃 | 邮件已经发出，令牌从没生效，链接打不开；同一个键重试按第一次处理，再发一封 |
| SMTP 卡住 | 请求线程和事务一直等，锁也不放：租户行锁、配额锁、Bootstrap 单例锁 |
| 事件路径上 SMTP 失败 | Handler 失败，按事件的重试策略重试，每次一个新链接；用完次数后停放 |

### 1.4 蓝图怎么说

- 根 3.3.0：`NotificationCapability` 只出现在 Capability Catalog 的"外部集成"一行，没有写送达语义。RESILIENCE-001 要求所有同步边界都有 deadline。
- super-admin 4.0.1：
  - OWNER-005：通知由处理身份或邀请令牌的 Data Owner 编排；
  - NOTIFY-001：安全链接只经受管侧信道发送，回答、日志、审计、Trace、指标里都不能有令牌、完整 URL、正文或变量；
  - NOTIFY-002：不许有假的通知 Adapter；
  - NOTIFY-003：邮件不是 MFA；SMTP 接受不等于送达；同步 fail-closed 和提交后的残余窗口由活动通知专项唯一声明，不得同时保留隐式的 Outbox 或重试；
  - §15.4 末段：邮件提交失败和提交后的残余窗口只按活动通知专项处理，不得靠返回 URL、打日志或假 Adapter 补偿。
- multi-tenant 5.1.3 §5.7：邀请链接只能经 `NotificationCapability` 发送，重发后旧令牌失效。
- frontend 1.2.1 ROUTE-004、FE-7：令牌不进查询串。
- identity-auth 1.0.1 ABUSE-002：安全事件要通知身份持有人。

## 2. 业界做法

2026-11-08 查阅：

- [事务性 Outbox](https://microservices.io/patterns/data/transactional-outbox)：消息与业务数据在同一个事务里落库，再由 Relay 发出。提交了才发、发了就说明提交了；代价是至少一次，要处理重复。
- [Spring 的事务绑定事件](https://docs.spring.io/spring/reference/data-access/transaction/event.html)：默认在提交之后执行；那时事务已经结束，之后的失败不能让它回滚。
- [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)：一次性令牌要够长，与用户绑定，用过即作废，安全存放，有过期时间。
- JavaMail 的 SMTP 连接、读、写超时默认都是无限。[Atlassian 的 Jira 就因此出现过邮件队列卡住](https://support.atlassian.com/jira/kb/jira-notifications-piling-up-in-the-mail-queue-due-to-smtp-server-infinite-timeout-setting/)，修法是把超时设成 10 秒。

放到 Brix：

- Outbox 能做到不丢邮件，但链接里的原始令牌要么放进 Outbox，违反"令牌只存哈希"；要么发信时再签令牌，Relay 要回调 Owner。对现在这几封低频的管理邮件来说太重。
- 提交后再发可以避免死链接。但写入已经提交，SMTP 失败时调用方拿到的是成功，就要另做送达状态和重发入口。这也不符合 NOTIFY-003 写的"同步 fail-closed"。

## 3. 决定（推荐）

| 编号 | 推荐 | 备选（不推荐） |
|---|---|---|
| D103 送达语义 | 同步、fail-closed。在 Unit of Work 里调用时，邮件在提交前的最后一刻发出：所有写入（含审计事实和端点答案）都已写进数据库之后、提交之前。SMTP 拒收、报错或超时，这次写入回滚，调用方拿到稳定错误。不在 Unit of Work 里调用时立刻发。时机由 `NotificationCapability` 的实现保证，Owner 的代码不用动 | B 提交后再发，加送达记录和显式重发：没有死链接，SMTP 也不在事务里；但 SMTP 失败时写入已经提交、调用方拿到成功，每个 Owner 要加送达记录表和"未送达、重发"界面，也不符合 NOTIFY-003 的"同步 fail-closed"。C 事务性 Outbox 加自动重试：不丢邮件，但原始令牌要么落库，要么发信时回调 Owner 重签；NOTIFY-003 也不许隐式的 Outbox 或重试。D 维持现状：发信之后还有写入，死链接的窗口更大 |
| D104 发送时间上限 | SMTP 的连接、读、写各设超时，建议连接 5 秒、读写各 10 秒；整次发送不超过调用方剩下的截止时间。超时按发送失败处理（fail-closed）。根 RESILIENCE-001 已经要求，不等 RFC，可以先做 | 无限等待：SMTP 卡住时请求线程和数据库锁一直被占着 |
| D105 残余窗口与重试 | 写明：发信之后提交失败（数据库故障、进程崩溃）时，这封邮件里的链接从没生效；调用方重试会再发一封，只有最新一封里的链接能用。通知能力自己不重试。端点按结果重放，提交之后再重试不会再发信。事件路径按事件的重试策略重试，每次一个新链接，用完次数后停放，由运维重放事件或重发 | 通知能力自己重试几次：重试会拉长事务和持锁的时间，失败时调用方等得更久，重复的邮件也更多 |
| D106 令牌与内容 | 原始令牌只在内存和邮件正文里；链接里的令牌放在片段 `#token=`（FE-7）；回答、日志、审计、Trace、指标里没有令牌、链接、正文和变量（NOTIFY-001） | — |
| D107 可观测 | 按模板和结果（送出、拒收、超时）计数、计时；失败记 WARN，带脱敏的收件人、模板和 traceId，不记正文；拒收率可以告警 | 只记日志：看不出趋势，也不好告警 |
| D108 规则写在哪里 | 随根 3.4.0 那一批出 RFC-012：根在 `NotificationCapability` 下加一条送达语义（D103～D107 的要点）；super-admin 4.0.2 的 NOTIFY-003 和 §15.4 末段改为按根的这一条执行。暂不另立通知专项，等要做渠道、偏好、退信处理时再立 | 另立通知专项蓝图 v1.0：要新的蓝图、新的注册表领域和整套审批，而内容现在只有这几条。或者只改 super-admin：多租户、身份认证的通知就没有依据 |

## 4. 对接口和回答的影响

- `NotificationCapability` 的方法签名不变。
- 在 Unit of Work 里调用 `send()`，它返回时邮件还没发出；发送失败会在提交时抛出。调用方不能在 `send()` 之后据此判断"已送出"。
- `create-first-admin` 的 `setupLinkSent`：提交成功就说明邮件已经交给 SMTP，含义不变。
- 重发：邀请的重发已经会作废旧令牌（multi-tenant §5.7）。超管设置链接的重发，随超管的重置凭证端点一起做。

## 6. 批准后的点

1. SMTP 超时和发送指标（D104、D107）：现行 RESILIENCE-001 已经要求，不等 RFC，批准后就能做。2026-11-09 完成（标准链路收尾方案 §10.39）。
2. RFC-012 起草，并入根 3.4.0 那一批的审批（§11.1 队列里的那一项）。2026-11-09 起草（[RFC-012](rfc/RFC-012-运行壳-通知的送达语义（Draft）.md)，标准链路收尾方案 §10.40）。起草时核对出一处要写得更准：跨 Owner 发信时（首位 OWNER 受邀人的身份设置邮件），发信的 Owner 先于调用方提交，调用方之后失败，链接是有效的，不是 D105 说的"从没生效"；RFC-012 的残余窗口按此写明。
3. `NotificationCapability` 在 Unit of Work 里改为提交前最后一刻发信（D103）：根 3.4.0 发布后做。标准链路收尾方案 §8 第 3 项和 Kafka 方案 §3.1 里"提交后发送"的错误说法，已在起草本稿时注明。2026-11-14 完成（标准链路收尾方案 §10.67）。
4. 首位超管的设置链接：按新语义核对，包括结果重放、SMTP 拒收时回滚、提交失败的残余窗口。2026-11-16 完成（标准链路收尾方案 §10.68）：代码不用改，一次性回归加了 SMTP 拒收、提交失败两段。
5. 首位 OWNER 的邀请邮件与身份设置邮件（建邀请、重发邀请）：同上。2026-11-16 完成（标准链路收尾方案 §10.69～§10.71，切成 Q13a～Q13c）：代码不用改，一次性回归加了新套件 e2e-pq13。
6. 设置完成后补发邀请（事件路径）：同上，包括重试和停放。
7. 以后出现时各成一点：超管的新建与重置链接、租户成员邀请、身份认证 ABUSE-002 的安全通知（不带令牌，可以走事件 Outbox）。
