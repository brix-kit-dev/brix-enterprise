> **版本**：4.0
> **日期**：2026-07-27
> **架构状态**：Freeze Candidate
> **实施状态**：pending
> **兼容代际**：2

本文只定义租户身份、隔离、上下文、数据所有权、邀请、配额和 T-x 红线。Capability Catalog、Plugin/Operational SPI、Runtime Entry、Event Envelope、错误、Outbox、Host 和供应链语义完全继承活动根蓝图。

## 1. 唯一所有权与模块边界

[BRX-TENANT-OWNER-001] OSS `platform-tenant` 是平台租户目录的唯一 Data Owner，唯一拥有：

- `sys_tenant`
- `sys_tenant_member`
- `sys_tenant_principal`
- `biz_user_profile`
- `sys_tenant_invitation`
- `sys_tenant_config`
- `sys_installation_quota`
- 与上述聚合相关的 schema、migration、Repository contract、本地事务、审计和 canonical Outbox/Inbox

[BRX-TENANT-OWNER-002] 目标后端物理形状为：

```text
platform-tenant-api     moduleKind=plugin-api
platform-tenant-core    moduleKind=plugin-core
platform-tenant-server  moduleKind=plugin-server
```

它属于 OSS 官方 L1 Plugin，位于 `platform-commons` 的安全基座产品范围；`plugin-server` 通过唯一 `BrixPlugin` ServiceLoader provider 和唯一 `META-INF/brix/plugin-manifest.yaml` 进入 Runtime。

[BRX-TENANT-OWNER-003] Enterprise `app-tenant` 可拥有企业租户扩展、展示模型或业务配置，但不得拥有第二套平台租户目录、成员/邀请权威写模型、平台超管路由或 `sys_*` 表的写权限。`app_tenant_*` 已有资产必须根据环境账本采用前滚迁移、只读兼容或明确归档；禁止静默双写或直接删除。

[BRX-TENANT-OWNER-004] Host 只静态组装 Runtime、Adapter、`platform-tenant` Plugin 和其他选定模块，不承载租户 Service、Repository、Controller、数据转换或按插件分支。

## 2. 身份模型

```text
Identity (global)
  ├─ Tenant Member / Actor
  │    OWNER | ADMIN | MEMBER
  └─ Tenant Principal / Subject
       CUSTOMER | GUEST

Member or Principal
  └─ exactly one tenant-scoped Profile
```

[BRX-TENANT-IDENTITY-001] Platform Admin、Actor 和 Subject 是不同授权上下文。Platform Admin 不是 tenant member，Platform Token 不得进入租户上下文。

[BRX-TENANT-IDENTITY-002] Member 与 Principal 必须物理分离。同一 Identity 可在同一租户同时拥有 Actor 和 Subject context；两者使用不同 contextId、audience、scope 和授权版本。

[BRX-TENANT-IDENTITY-003] `context_id` 是服务端生成、全局唯一且不可变的访问上下文 ID。登录选择阶段只返回高熵、短 TTL、一次性且绑定 identity-token jti 的 selection ticket，不暴露可枚举的稳定 contextId。

[BRX-TENANT-IDENTITY-004] Profile 与 Member/Principal 在同一 Owner 本地事务内创建，必须满足同 tenant、恰一引用、唯一关系。插件不得对平台租户表建立外键。

## 3. TenantContext 与领域契约

[BRX-TENANT-CONTRACT-001] 插件面唯一租户上下文 Capability 是根 Catalog 已登记的 `TenantContextCapability`。它只返回 Runtime 已验证的 tenant、scope、actor、subject 和隔离上下文；不提供租户列表、成员、配额、生命周期或领域 CRUD。

[BRX-TENANT-CONTRACT-002] 本专项不定义 `TenantDirectoryCapability`、`TenantQuotaCapability`、`TenantConfigCapability`、`BusinessObjectCapability`、`AdminCapability` 或 `PlatformAdminCapability`。新增平台 Capability 必须先经根级 RFC 进入 Capability Catalog。

租户领域跨边界契约冻结为：

| 类型 | 契约 | 语义 |
|---|---|---|
| typed Query | `TenantReferenceQuery` | 只读校验 opaque member/principal ref 属于当前 tenant |
| typed Query | `TenantDirectoryQuery` | Owner 范围的租户/成员/邀请只读 DTO |
| typed Query | `TenantUsageQuery` | 当前 tenant 或获批平台调用方的类型化用量 |
| typed Command | `TenantMemberCommand` | 跨 Plugin 成员状态变更意图，异步可靠 |
| typed Event | `TenantFirstOwnerAccepted` | 首位 OWNER 已提交事实，CRITICAL |
| typed Event | `TenantStatusChanged` | 租户状态已提交事实，STANDARD/CRITICAL 由 Schema 冻结 |

[BRX-TENANT-CONTRACT-003] 普通插件通过生成的 typed Query client 校验不透明引用，不得直接查询/JOIN `sys_tenant_*`、调用内部 HTTP 或传入任意 tenantId 绕过当前 Invocation Context。

[BRX-TENANT-CONTRACT-004] 当前租户配置通过根 Catalog 的 `ConfigCapability` 读取插件已声明、非敏感、类型化配置；Secret 通过 SecretCapability。租户领域配置管理仍由 Owner 的 typed contract 提供，不新增专项平台 Capability。

[BRX-TENANT-CONTRACT-005] 平台运维读取使用 typed Query；平台运维写入只通过 `platform-admin` 的 OperationalContext 调用 `brix.internal.tenant.administration`。普通 Plugin 不得消费、枚举或查找 internal contract。

## 4. Runtime Entry 与 Manifest

[BRX-TENANT-ENTRY-001] `platform-tenant-server` 的所有 HTTP、Query、Command、Event 和 Task 入口必须在唯一 YAML Manifest 声明，并由 `BrixPlugin.configure(PluginBootstrapContext)` 登记 Handler/Task Factory。

[BRX-TENANT-ENTRY-002] 禁止 Spring Controller 自动发布、ComponentScan 装配、`ApplicationContext`/BeanFactory 查找、静态 Registry、直接 Handler Bean 注入和 `@Scheduled`/消息监听器旁路。

[BRX-TENANT-ENTRY-003] 所有 Invocation Context 由 L2B 构造为不可变对象。Handler 不从 ThreadLocal、Servlet、JWT、Header、broker message 或 Spring Context 重新解析 tenant、actor、subject、Trace、deadline 或幂等信息。

[BRX-TENANT-ENTRY-004] B3/P8 前完整入口集保持 UNPUBLISHED；Drain/Fatal 先原子关闭 HTTP/Query/Command/Event/Scheduler 新准入，再等待 in-flight。

FIRST_OWNER 接受入口冻结为：

```text
POST /api/v1/tenant-invitations/first-owner/accept
authentication: verified Actor identity
tenantContext: forbidden for authority; tenant derived from locked invitation
authorization: first-owner-invitation-accept
idempotency: required
```

调用方不能提交或覆盖 tenant authority、purpose、inviterType、platformAdminId、targetRole 或 owner member id。

## 5. 租户创建与 FIRST_OWNER

[BRX-TENANT-FIRST-001] 平台创建租户只创建 `PENDING_ACTIVATION` 租户和必要配置，不创建 Member/Profile，不占正式配额，不把平台超管写成 tenant member。

[BRX-TENANT-FIRST-002] `FIRST_OWNER` 邀请只能由已验证 Platform Admin 经 allowlist internal contract 发起，目标角色由服务端固定为 OWNER。邀请只保存 token hash、purpose、inviter type/id、目标邮箱、状态、有效期和审计字段。

[BRX-TENANT-FIRST-003] 重发必须作废旧 token并生成新 token；撤销只允许 PENDING；raw token 和完整 URL 只能经 Owner 编排的 NotificationCapability 侧信道发送，任何 profile 均不得通过响应或日志返回。

[BRX-TENANT-FIRST-004] 接受事务固定锁顺序：

1. 按 token hash `FOR UPDATE` 锁 invitation；
2. 按 tenantId `FOR UPDATE` 锁 tenant；
3. 按 installationId `FOR UPDATE` 锁 quota；
4. 校验 purpose、状态、有效期、邮箱和当前 Identity；
5. 校验 tenant 仍为 PENDING_ACTIVATION 且无 ACTIVE OWNER；
6. 校验并占用 quota；
7. 创建 ACTIVE OWNER；
8. 创建/确认唯一 Profile；
9. tenant 转为 ACTIVE 或 TRIAL；
10. invitation 转为 ACCEPTED；
11. 写 Owner 审计；
12. 将 `TenantFirstOwnerAccepted` CRITICAL Event 写入 canonical Outbox；
13. commit。

[BRX-TENANT-FIRST-005] 任一步失败必须整体回滚。重复/并发接受最多一个产生副作用；配额不足、邮箱不匹配、邀请过期/撤销、已存在 OWNER 均不得留下部分状态。

[BRX-TENANT-FIRST-006] ACTIVE/TRIAL tenant 必须至少有一个 ACTIVE OWNER。PENDING_ACTIVATION 可暂时无 OWNER。所有 OWNER 降级、停用、删除和转移必须以 tenant 行锁或等价确定性锁串行化，禁止先 COUNT 后写的 TOCTOU。

## 6. 配额与 License

[BRX-TENANT-QUOTA-001] 配额主体固定为 installation_id。只有 ACTIVE/TRIAL tenant 计入 used；PENDING_ACTIVATION、DISABLED、ARCHIVED 不计入。

[BRX-TENANT-QUOTA-002] 任何改变 ACTIVE/TRIAL 数量的状态迁移必须在 Owner 同一本地事务内先锁 quota 行，再原子更新 tenant 和 used。恢复时必须先校验容量，失败即拒绝。

[BRX-TENANT-QUOTA-003] License/硬配额失败必须 fail-closed，只阻止新增或恢复，不删除、停用或泄露既有租户数据。安全隔离、JWT 校验、审计和防泄漏不得作为付费开关。

## 7. Token 与上下文选择

Token 最小分类：

| Token | audience | scope | 必要上下文 |
|---|---|---|---|
| Actor Access | `brix-actor` | actor | tid, cid, mid, mtype, mver |
| Subject Access | `brix-subject` | subject | tid, cid, pid, ptype, pver |
| Identity Selection | `brix-identity` | identity | sub, jti, allowed action |
| Refresh | `brix-refresh` | refresh | sub, cid, family, device |

[BRX-TENANT-TOKEN-001] 每类 Token 必须校验允许算法、typ、kid、iss、aud、sub、iat、nbf、exp、jti。算法集合和密钥轮换由安全 Profile 管理，专项不得让插件自行解析 JWT。

[BRX-TENANT-TOKEN-002] Actor Token 与 Subject Token 的 mid/pid 必须互斥。状态、角色或权限变化必须增加授权版本；Token 版本不一致立即拒绝。

[BRX-TENANT-TOKEN-003] Actor 登录只发现该 Identity 的 Actor contexts；Subject 登录只发现当前品牌/租户的 Subject context，不得跨租户聚合。

[BRX-TENANT-TOKEN-004] Context switch 仅允许 Actor 切到同一 Identity 的其他有效 Actor context。Subject 不得切换租户或转成 Actor；Actor/Subject 转换必须重走对应登录入口。

[BRX-TENANT-TOKEN-005] Header、subdomain、path 和 query 只能作为登录前提示。认证请求的 tenant authority 只来自 Runtime 已验证的 Token/Invocation Context；冲突必须拒绝并审计。

## 8. 全栈隔离

[BRX-TENANT-ISOLATION-001] 所有租户业务表必须具有非空 tenant_id 和索引；每次 Repository/Unit of Work 必须绑定 plugin identity、tenant/actor context 和 deadline。

[BRX-TENANT-ISOLATION-002] 数据库、缓存、对象存储、搜索、消息、Task、导出和审计必须使用同一已验证 tenant scope。隔离映射属于 L2C Adapter；插件不得接触 DataSource、Redis/Kafka/MinIO client、原生 SQL 或基础设施 SDK。

[BRX-TENANT-ISOLATION-003] Runtime 可在内部使用 ThreadLocal/Reactor Context 等载体，但插件不得 set/clear、读取或把它作为正确性依据。Runtime 在 CompletionStage 完成、异常或取消后负责清理。

[BRX-TENANT-ISOLATION-004] 对象级授权独立于 tenant 过滤：

- Subject 默认只能访问自身 principal 关联对象；
- Actor 必须同时满足 permission 和 data scope；
- 客户端传入的对象 ID 必须验证 tenant ownership 和 caller access；
- IDOR 拒绝必须审计。

[BRX-TENANT-ISOLATION-005] PostgreSQL RLS 可作为 L2C 纵深防御 Adapter，但不能替代应用层隔离；生产业务账号不得拥有 BYPASSRLS。

## 9. 事件、Outbox 与 Inbox

[BRX-TENANT-EVENT-001] 本专项不定义第二个 EventEnvelope。所有 Integration Event 必须使用根蓝图统一 Envelope，包含 eventId、eventType、schemaVersion、occurredAt、producerPluginId、scope、条件 tenantId、correlationId、causationId、W3C trace context、partitionKey 和 payload。

[BRX-TENANT-EVENT-002] `TenantFirstOwnerAccepted` 是已提交事实，可靠性为 CRITICAL。业务写、邀请接受、审计受托记录和 Event Outbox record 必须位于同一 Owner 本地事务。

[BRX-TENANT-EVENT-003] Manifest `storageId` 固定为 `platform_tenant`。canonical 表名为 `platform_tenant_outbox` 和 `platform_tenant_inbox`；已发布后不得改变。

[BRX-TENANT-EVENT-004] Relay 重试保持 eventId；Consumer 以 `(handlerId,eventId)` 持久化 Inbox 去重，并将去重与业务副作用放在同一 Consumer Owner 本地事务。Brix 不声明 Exactly Once。

[BRX-TENANT-EVENT-005] 插件不得出现 Kafka/Rabbit listener、topic 字符串或 broker SDK。订阅由 Manifest 声明并由 Runtime 管理。

## 10. 审计与敏感数据

[BRX-TENANT-AUDIT-001] 租户业务审计必须绑定单一 tenantId，由租户审计 Owner 管理。平台/跨租户审计由 platform-audit Owner 管理，可记录受影响 tenant 集合，但不得伪造单一 tenant authority。

[BRX-TENANT-AUDIT-002] 审计、日志、Trace、指标和错误不得包含密码、Token、MFA secret、完整邀请/设置 URL、正文、variables、未批准 PII 或内部堆栈。

[BRX-TENANT-AUDIT-003] 登录期跨租户 Actor discovery 是显式、最小字段、可审计的 Auth Owner 查询，不赋予业务插件跨租户读取权限。

---

## 11. Flyway 与数据迁移

[BRX-TENANT-MIGRATION-001] 已执行的 migration 原始字节不可变。不得修改、重命名、复用版本或使用 repair 掩盖 checksum 差异。

[BRX-TENANT-MIGRATION-002] 在取得每个共享/正式环境 `flyway_schema_history` 前，不得假设 OSS V001-V020 或 Enterprise V100 的发布状态。新迁移只能选择所有环境均安全的下一单调版本。

[BRX-TENANT-MIGRATION-003] `app_tenant_*` 与 `sys_tenant*` 数据必须先形成数据量、引用方、外部契约和 owner 账本，再批准前滚映射。冲突必须阻断并产报告，禁止 `ON CONFLICT DO NOTHING` 静默丢数据。

[BRX-TENANT-MIGRATION-004] 每次迁移必须验证 fresh install、从每个支持版本升级、失败恢复、并发约束和已发布文件 raw hash。

## 12. 前端边界

[BRX-TENANT-UI-001] 租户前端遵循 `Page → Hook → Repository → HttpCapability`，组件只经 BrixUI/useUI。不得直接 fetch/axios、解析 JWT 或持久化安全 Token。

[BRX-TENANT-UI-002] Platform Tenant UI 只使用 Platform Token；租户成员 UI 只使用 Actor Token；Subject UI 只使用 Subject Token。切换上下文必须清空缓存和状态。

[BRX-TENANT-UI-003] 创建租户页面不得提交 ownerIdentityId；租户详情必须显示 PENDING_ACTIVATION 和 FIRST_OWNER 邀请状态，并提供受权限控制的发起、重发、撤销操作。

[BRX-TENANT-UI-004] 邀请接受页设置 `Referrer-Policy: no-referrer`，提供加载、错误、已接受、过期、撤销、邮箱不匹配和重复提交状态。

## 14. 验收与状态迁移

候选转为 ACTIVE 前必须：

1. architecture、security、SRE 批准本文、公开 typed contract、internal contract 和迁移策略；
2. 登记 raw SHA-256、Git blob、不可变 commit 和生效日期；
3. 旧 `multi-tenant 3.1.3` 转为 SUPERSEDED；
4. `multi-tenant 4.0` 成为唯一 ACTIVE multi-tenant；
5. 完成 Capability 禁止项、统一 Envelope、Owner 边界、Manifest/Factory、隔离、Token、FIRST_OWNER 并发、Outbox/Inbox、Flyway 和前端分层正反例；
6. 明确实际执行的测试数量；
7. 在全部实施门禁通过前保持 `implementationStatus=pending`，不得标记 Implementation Accepted/GA。
