## 0. 结论摘要

- **P4 的前提不存在**：可靠事件只有"发出去"的一半。platform-tenant 在自己的事务里写 Outbox，Relay 发到 Kafka，之后没有任何代码消费；Runtime 的持久 Inbox 分发器只在测试中构造过；Relay 只支持一张 Outbox 表。
- 所以 P4 分两步：先按根 MESSAGE-017～029 建好**消费链路**并通过发布门禁测试，再把身份 Owner 接上：
  - 身份 Owner 有自己的 Outbox，在变更事务里发布审计事实和"受邀人设置完成"；
  - platform-audit 经 Inbox 订阅审计事实并写行，platform-identity 不再直接写 `sys_platform_audit_log`；
  - platform-tenant 经 Inbox 订阅"设置完成"，补发（P-3）变成可靠投递；
  - C 期删除旧组件，关闭 EX-2026-003。
- 推荐的传输是**进程内投递**：Relay 认领 Outbox 行后在同一进程里交给订阅方的持久 Inbox，订阅方提交后才标记已发布。当前唯一的部署形态是单进程 Standalone 主机，这样不依赖 Kafka 消费端，链路能端到端测试。Kafka 回环留作服务拆分时的选项（§6 D11）。

## 1. 现状（2026-10-28 调查）

| 部分 | 现状 |
|---|---|
| 生产端 | platform-tenant 的 `PlatformTenantReliableEventBusCapability` 在 Owner 事务里写 `platform_tenant_outbox`；只认 `TenantFirstOwnerAccepted` 一种事件，身份 Owner 不能直接复用 |
| Relay | `OutboxRelay` 按租约认领、发送、标记或停放；存储 `JdbcOutboxMessageStore` 只有一个表名（默认 `platform_tenant_outbox`），只认领 CRITICAL/STANDARD；它的 `append` 漏写了租户 DDL 中非空的 `event_type` |
| 传输 | 只有 Kafka（`CanonicalKafkaOutboxTransport`，主题取自事件类型）。共享环境运行 Kafka，主机默认开启 |
| 消费端 | 没有 Kafka 消费端，没有事件 Inbox 存储（只有命令的 `JdbcCommandInboxStore`）。`PersistentInboxEventDispatcher` 只在测试里构造。platform-tenant 的投影服务是一个没人调用的 Bean |
| 跨 Owner 的唯一投递 | `InviteeSetupEventDelivery`：身份事务提交后在进程内（`AFTER_COMMIT`）交给 platform-tenant 的 Handler，没有 Inbox，没有重试；进程在两者之间崩溃就丢失这次补发 |
| platform-identity | 清单 `publishes: []`、`subscribes: []`，没有 Outbox/Inbox 表；`FirstOwnerInviteeSetupCompletedEvent` 用 Spring 的 `ApplicationEventPublisher` 发布；审计经 `AuditService` 直接写 `sys_platform_audit_log`（EX-2026-003） |
| 测试 | 都是半截：生产端的事务测试、Relay 的内存测试、Inbox 去重的直接调用测试；没有"生产 → Relay → 传输 → Inbox"的端到端测试 |

## 2. 约束

- **根 3.3.0**：
  - MESSAGE-017/018：CRITICAL/STANDARD 必须用事务 Outbox；MESSAGE-020：只对它们承诺至少一次，不承诺恰好一次。
  - MESSAGE-021：envelope 字段；`eventId` 是去重身份，重试和重放不变；PLATFORM 作用域不得带租户。
  - MESSAGE-022：没有活动本地事务时发布 CRITICAL/STANDARD 必须立即失败。
  - MESSAGE-023：每个 Owner 在自己的 schema 中拥有 `{storage_id}_outbox`、`{storage_id}_inbox` 及其迁移。
  - MESSAGE-024：Relay 是最小权限的受托平台服务，不读业务表。
  - MESSAGE-025：消费方按 `(handlerId, eventId)` 去重，去重记录与业务副作用在同一本地事务。
  - MESSAGE-026～028：版本化表结构、保留与清理；只按 `partitionKey` 保序；重试耗尽进停放区，可观测、可审计、可人工重放。
  - §6.5 第 8 条：事务内发布测试、故障注入、重复消费测试是发布门禁。
  - MESSAGE-029、MANIFEST-025/026：清单与 Handler 一一对应；CRITICAL/STANDARD 订阅必须用持久 Inbox 幂等。
  - DATA-008：一个事务只改一个 Owner 的数据及它自己的 Outbox、Inbox、审计记录。DATA-029：独立提交的副作用走 Outbox 或 Owner 契约。
- **identity-auth 1.0.1**：OWNER-001（认证事件归 platform-identity）、AUDIT-001（平台客户端事件与跨租户事件写平台审计）。
- **super-admin 4.0.1**：§1.3a（platform-audit 是 `sys_platform_audit_log` 的唯一 Owner）、§5、AUDIT-001（审计不记密码、token、完整邮箱等）。
- **multi-tenant 5.1.3**：§6.4 P-3 的访问键由 Runtime 按身份 Owner 已提交的事实取得并绑定；T-25（平台审计与租户审计分开）。

## 3. 消费链路（P4a）

```text
Owner 事务：业务写 + {storage}_outbox 行（同一本地事务）
        │ 提交
        ▼
OutboxRelay（每个 Owner 的 Outbox 表各一个认领循环，租约认领）
        │ 进程内传输（D11 推荐）
        ▼
订阅方 Owner 的 Unit of Work：
    {storage}_inbox 插入 (handlerId, eventId)   ← 重复则跳过
    Handler 业务写
    提交
        │ 成功
        ▼
Relay 把 Outbox 行标记为 PUBLISHED；失败则按退避重试，耗尽进停放区
```

- **多 Owner 的 Relay**：从启用的清单中读出每个 Owner 的 `data.outbox`，每张表一个存储实例与认领循环；不再用单一的表名配置（D12）。
- **进程内传输**：实现 Relay 的传输接口，把消息交给 Runtime 的持久 Inbox 分发器；分发器按清单的 `events.subscribes` 找到 Handler，在订阅方 Owner 的 Unit of Work 中执行"去重记录 + 副作用"。
- **事件 Inbox 存储**：L2C 新增按 Owner 的 JDBC 事件 Inbox 存储，表名取自订阅方清单的 `data.inbox`。
- **停放与重放**：重试耗尽的 Outbox 行置为 PARKED，计数并告警；提供只读的停放列表和人工重放入口（按 eventId，不改变 eventId）。
- **至少一次的证明**：Relay 只在订阅方提交后标记已发布；订阅方提交后、标记前崩溃，重启后重发，Inbox 去重跳过。
- **发布门禁测试**：事务内发布（回滚则没有 Outbox 行）、故障注入（订阅方抛错、提交后崩溃、Relay 中途停止）、重复消费（同一 eventId 投递两次只生效一次）、停放与重放，在一次性 PostgreSQL 上端到端运行。

## 4. 身份 Owner 接入（P4b、P4c、P4d）

### 4.1 身份 Owner 的 Outbox（P4b）

- 迁移：platform-identity 新增 `platform_identity_outbox`、`platform_identity_inbox`（与 platform-tenant 同一平台表结构，MESSAGE-026）。
- 清单：`data.outbox`/`data.inbox`；`events.publishes` 声明两个事件，可靠性 CRITICAL。
- 发布：推荐由持久化适配器提供通用的 Owner Outbox 发布（D13）：在当前 Owner 的 Unit of Work 中把事件写入该 Owner 的 Outbox，没有活动事务时立即失败（MESSAGE-022）。platform-tenant 的专用实现以后再迁过来。

### 4.2 审计事实事件与 platform-audit 的 Inbox（P4c）

- 事件 `IdentityAuditFactRecorded`（`brix://schemas/platform-identity/identity-audit-fact/1.0.0`，PLATFORM 作用域）：只有类型化字段——动作、操作者、执行身份、目标、受影响租户、结果、稳定原因与错误码、trace、脱敏后的来源地址。不含密码、token、完整邮箱（AUDIT-001）。
- platform-identity 现有的 `AuditService.log` 调用点改为在同一事务里发布这个事件；"审计与变更一起提交"的语义保持不变（D14）。
- platform-audit 订阅它，在自己的 Unit of Work 中经 Inbox 去重后写一行，id 来自 `IdGeneratorCapability`，写入方 `platform-audit`（D15）。
- 迁移期间两条路径不能并存写同一事实：切换在同一个版本内完成（发布事件 + 删除直接写入）。

### 4.3 受邀人设置完成的可靠投递（P4d）

- 事件 `FirstOwnerInviteeSetupCompleted` 改由身份 Owner 的 Outbox 发布；platform-tenant 的订阅改为持久 Inbox。
- Runtime 在投递时照旧绑定 P-3 范围（访问键按身份 Owner 已提交的事实取得），并照旧在 platform-tenant 提交前写策略审计（DATA-047）。
- `InviteeSetupEventDelivery` 的进程内 `AFTER_COMMIT` 路径删除。补发失败重试，耗尽后停放可重放；不会再因为进程崩溃丢失（D16）。

### 4.4 C 期

- 删除 platform-identity 的 `PlatformAuditLogEntry`、Repository、`AuditService`、`AuditEvent`。
- `sys_platform_audit_log.writer` 去掉默认值（新迁移）；守卫改为"这张表只由 platform-audit 的持久化单元映射"。
- 存量行保持原样（写入方 `platform-identity`），不回填。
- 在控制平面关闭 EX-2026-003（登记关闭证据：迁移、测试、端到端结果）。

以下是确认前的比较，保留作依据。

### D11：消费链路的传输

- **推荐 A：进程内投递**。Relay 认领后在同一进程交给订阅方的持久 Inbox；订阅方提交后才标记已发布。不依赖 Kafka 消费端，链路能端到端测试，符合当前单进程 Standalone 的部署形态。多实例时同一行只会被一个实例认领（租约），Inbox 去重兜底。Kafka 传输保留，用于将来对外发布。
- 备选 B：Kafka 回环。Relay 发 Kafka，新建 L2C 的 Kafka 消费端再交给持久 Inbox。为服务拆分做准备，但要处理消费组、位移、停放主题，测试也更重；共享环境的正确性要依赖 Kafka。

### D12：Relay 读哪些 Outbox

- **推荐：从启用的清单读出每个 Owner 的 `data.outbox`**（清单是唯一来源）。
- 备选：在主机配置里列出表名。会形成第二个来源，容易与清单不一致。

### D13：身份 Owner 怎么写 Outbox

- **推荐：持久化适配器提供通用的 Owner Outbox 发布**，按当前 Owner 的 Unit of Work 写入它自己的 Outbox。以后 platform-tenant 也改用它。
- 备选：照 platform-tenant 的做法给 platform-identity 再写一份专用实现。快，但重复，而且每个 Owner 都要再写一遍。

### D14：身份审计用什么事件

- **推荐：一个类型化的"审计事实"事件**，字段与平台审计记录一一对应。它的唯一用途就是审计，platform-audit 订阅后写行。
- 备选：按领域事件拆（身份激活、锁定、引导会话等），platform-audit 逐个映射。事件多、映射分散，目前也没有别的订阅方。

### D15：platform-audit 写的行，`writer` 记什么

- **推荐：`platform-audit`**。`writer` 记的是谁写了这一行；事实来自哪个 Owner 由动作本身说明。C 期去掉默认值后，表里只有 `platform-audit` 与 `runtime.tenant-policy-audit` 两种新写入方。
- 备选：记 `platform-identity`（事实的来源）。与迁移前的存量行一致，但 `writer` 就不再是"写入方"了。

### D16：补发的可靠投递是否放在 P4

- **推荐：放在 P4（P4d）**。用的是同一条链路，顺带关闭租户隔离方案 §13.1 第 5 条。
- 备选：P4 只做审计迁移，补发另做。

## 7. P4a 施工计划（2026-10-28，负责人同日确认按此范围继续）

### 7.1 施工前的新发现

逐个读过消息相关代码后，P4a 的工作量比 §3、§5 估计的大：

1. **共享环境的 Relay 从未运行过**。`platform_tenant_outbox` 里有 1 行 `TenantFirstOwnerAccepted` 一直是 PENDING，日志里没有 Relay。原因很可能是持久化存储的自动配置用了 `@ConditionalOnBean(DataSource, PlatformTransactionManager)` 却没有声明排在数据源配置之后，存储 Bean 没有注册，Relay 也就没有启动。
2. **Outbox 存储有两处会在真实库上失败的缺陷**：`append` 没写非空的 `event_type`；payload 以字符串绑定到 JSONB 列。目前没有调用方，所以没暴露。另外，标记已发布失败时，整批消息会卡到租约过期。
3. **持久 Inbox 分发器没有接线**，而且只有一个 Unit of Work；每个订阅方要在自己的 Owner 事务里去重并处理。没有事件 Inbox 存储（只有命令的）。
4. **插件事件 SPI 与根蓝图不一致**。根 CAP-025 与 §5 规定 `EventHandler<E>#handle(EventInvocation<E>)`（含 Envelope、发布方判定、Trace、截止时间、取消信号、投递次数），绑定用 `bindEventHandlerFactory`；SDK 里仍是 `void handle(E)` 与 `bindEventHandler`，`EventInvocation`、`PublisherDecision`、`TraceContext`、`CancellationSignal`、`HandlerFactory` 都不存在。只有 ACTIVE 蓝图能指导新代码，所以新的投递链路必须按根的 SPI 写。
5. **没有事件 payload 的编解码**：`IntegrationEvent` 每次构造都生成新的 eventId，不能从 payload 还原；也没有 Schema 注册。
6. **platform-tenant 的投影服务自己写 Inbox 回执**，与 Runtime 通用 Inbox 的键相同，两者会冲突；它的订阅引用的 `scopePolicyRef` 也不是登记的策略。

### 7.3 事件 SPI 与投递的细节

根 §5 给出了接口形状，没有规定的细节在这里定：

- **Handler**：`EventHandler<E>#handle(EventInvocation<E>)` 返回 `CompletionStage<Void>`，`E` 是 payload 类型。Handler 由 `HandlerFactory#create(PluginContext)` 创建，经 `PluginBootstrapContext#bindEventHandlerFactory(handlerId, factory)` 绑定；旧的 `bindEventHandler` 删除。
- **payload 解码**：Runtime 读 Handler 类上 `EventHandler<具体类型>` 的类型参数，把 Outbox 行的 payload JSON 解成这个类型。解析不出具体类型（例如 lambda）时，插件启动即失败。payload 的 `schemaVersion` 不在订阅的 Schema 范围内时，这条消息停放，不交给 Handler。
- **发布方判定**（`PublisherDecision`）：一个事件类型只能由在清单 `events.publishes` 中声明它的插件发布。Envelope 的 `producerPluginId` 与之不符时停放，不投递；投递时 `PublisherDecision` 带上发布方与订阅的 `publisherPolicyRef`。
- **Trace**（`TraceContext`）：取 Outbox 行的 `traceparent`/`tracestate`；没有时 Runtime 生成一个新的 W3C traceparent（与根 ERROR-013 同一规则）。
- **截止时间与取消**：截止时间为投递开始时间加 Relay 租约时长的一半，保证 Handler 在租约到期前结束；`CancellationSignal` 在 Relay 停止时置位。
- **租户范围**：TENANT 作用域的事件，订阅方的 Unit of Work 绑定 Envelope 中的租户；PLATFORM 作用域的事件不绑定租户，除非订阅的 `scopePolicyRef` 是登记的跨租户策略（如 P-3），此时按策略绑定。
- **投递结果**：所有匹配的订阅方都提交（或因 Inbox 去重而跳过）后，Relay 才把 Outbox 行标记为已发布；任一订阅方失败，整条消息稍后重试，已提交的订阅方靠 Inbox 去重不重复执行。

## 10. P4b 施工计划（2026-10-29，负责人同日确认按此范围施工）

### 10.1 施工前的新发现

1. **主机的全局 EventBus 是 platform-tenant 的专用总线**。`TenantAutoConfiguration` 把 `PlatformTenantReliableEventBusCapability` 注册成一个 `EventBusCapability` Bean。Kafka、内存、Webhook 三个适配器都只在"还没有 `EventBusCapability` Bean"时才创建自己的总线，于是都被它挡住；`CapabilityAutoConfiguration` 又按类型取第一个 Bean 登记。共享环境的启动日志证实 `EventBusCapability -> PlatformTenantReliableEventBusCapability`。结果：除 platform-tenant 的首位所有者事件外，任何模块经 Runtime 取到 EventBus 发布集成事件都会失败，例如企业仓存储模块上传头像后的 `AvatarUploadedEvent`。共享环境的日志里这些路径目前没有被用到。
2. **SDK 的 `IntegrationEvent` 早于根的 envelope**：事件类型是 Java 类名，没有作用域，也没有单独的 payload，而通用发布需要这三样（根 MESSAGE-021）。platform-tenant 的专用实现靠首位所有者事件自己的 `eventTypeId()`、`payload()` 绕过去。
3. **两种取用方式并存**：platform-tenant、platform-identity 的服务仍由框架容器装配，持久化能力经适配器按"类所在构件的 Owner"注入；插件 Handler 则按根 CAP-025 只经 `PluginContext` 取能力。通用总线两条路都要能取到，而且不能再挡住主机的总线。

### 10.2 施工步骤

| 步 | 内容 |
|---|---|
| a | L2A：`IntegrationEvent` 只增不改，加 `eventTypeId()`（默认类名去掉 `Event` 后缀）、`scope()`（带租户为 TENANT，否则 PLATFORM）、`payload()`（默认不可经 Outbox 发布，子类返回类型化 payload） |
