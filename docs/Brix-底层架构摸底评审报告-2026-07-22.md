## 1. 执行摘要

本次评审的总体结论是：

**Brix 代码资产尚未全面失控，但架构治理、发布控制、版本基线和若干关键安全边界已经局部失控。**

当前实现不是以 v3.0.10 为唯一主模型，而是以下三类架构同时存在：

1. v3.0.6/v3.0.9 时期的 `RuntimeContext + Spring Component + AbstractModule` 插件模型；
2. 已部分落地的 v3.1.3 Identity/Member/Principal/Profile 与多租户能力；
3. 少量按照 v3.0.10 建设的 Capability、前端分层、Header 剥离和 Outbox 组件。

由于三代模型并存，文档、代码、守护规则和 CI 对“什么才是合规实现”没有形成唯一答案。

本轮确认四个 P0 发布阻断项：

- 公开租户注册接口信任客户端提交的 `ownerIdentityId`，并自动激活租户；
- 已发布的 Flyway V003/V009 迁移被修改；
- Booking/Case 等状态事件在业务事务内通过默认 EventBus 同步直发 Kafka，未强制进入 Transactional Outbox；
- Gateway 在生产配置缺失时接受仓库中公开的默认 API Key/Secret。

因此：

- 当前版本不适合直接发布；
- 不建议继续增加新的业务功能和数据库迁移；
- 可以继续进行 P0/P1 修复、迁移兼容验证和机器化守护建设；
- `architecture-guard` 当前只能评为“部分有效”，不能单独作为可信合并门禁。

综合评分为 **42/100**。解决本报告列出的 P0/P1 并补齐守护后，合理目标约为 **90/100**。

## 3. 当前实际架构

### 3.1 当前后端主模型

```text
Spring Boot Host / 独立 Application
        │ ApplicationContext 扫描
        ▼
@Component + @Module + AbstractModule
        │ 注入 RuntimeContext
        ▼
插件 Core（Service + JPA Entity/Repository + 事务）
        │
        ├── EventBusCapability ── 默认同步 Kafka send
        ├── Auth/Storage/Config/Observability Capability
        └── Spring Data JPA / PostgreSQL / Flyway
```

代表性证据：

- Enterprise `app-booking/booking-core/.../BookingModule.java:10-75` 使用 Spring `@Component`、`AbstractModule` 和 `RuntimeContext`；
- Enterprise `app-case/case-app/.../CaseApplication.java:48-70` 主动扫描 app/runtime/platform，并从 ApplicationContext 获取 `RuntimeContext`；
- 11 个商业插件 core 直接依赖 `spring-boot-starter-data-jpa`；
- 实际插件中没有发现 v3.0.10 要求的 `BrixPlugin`、`PluginContext`、ServiceLoader provider 主链。

### 3.2 v3.0.10 目标模型

```text
Ultra-thin Host
        │ ServiceLoader
        ▼
{name}-server 中唯一 BrixPlugin
        │ onStart(PluginContext)
        ▼
PluginContext.capability(...) 唯一能力入口
        │
        ├── L2A Capability Contract
        ├── L2B Runtime 编排
        └── L2C 可替换 Adapter
```

当前偏差不是局部实现缺陷，而是插件生命周期和装配模型尚未迁移到根蓝图定义的唯一模型。

### 3.3 前端模型

平台超管前端主链基本符合：

```text
Page → Hook → Repository → HttpCapability
```

但仍存在两类例外：

- OSS `platform-auth-service-web/src/services/createPlatformAuthService.ts` 多处直接调用 `fetch`；
- OSS `platform-tenant-mobile/src/MobileTenantProvider.tsx:102,119` 在 Provider 中直接请求后端。

这会导致 Token、Trace、重试、错误归一化和租户切换后的缓存清理形成多套行为。

## 5. 主要问题清单

## 5.1 P0 发布阻断项

### F-001：公开租户注册信任客户端身份

- 等级：P0
- 置信度：确认
- 证据：OSS `TenantRegistrationController.java:40-45,67-71,120-165`；`RegisterTenantRequest.java:72-79`
- 违反规则：T-4、T-9、T-13、T-28

`/api/public/tenant` 无需认证，并直接信任请求体中的 `ownerIdentityId`。服务随后创建 OWNER 并自动激活租户。

影响：未认证调用者可以冒用任意已存在 identity 创建租户、建立错误 OWNER 关系，并耗尽实例租户配额。

最低修复方向：

- 身份只允许来自已验证 Access Token 的 `sub`；
- 删除请求体中的身份裁决字段；
- 新租户只创建为 `PENDING_ACTIVATION`；
- 首位 OWNER 通过 `FIRST_OWNER` 邀请接管；
- 增加未认证、伪造 identity、重放和配额耗尽 E2E。

### F-002：已发布 Flyway 迁移被改写

- 等级：P0
- 置信度：确认
- 证据：`git diff fd0f3be..HEAD` 显示 OSS V003、V009 被修改；V020 又声明不改 checksum
- 违反规则：A-15、T-19

受影响文件：

- `platform-tenant/.../V003__create_sys_tenant_member.sql`；
- `platform-tenant/.../V009__create_biz_user_profile.sql`；
- `platform-tenant/.../V020__phase1_data_model_convergence.sql`。

影响：已执行旧版迁移的安装实例会在 Flyway validate 时 checksum 失败；如果通过关闭校验绕过，不同实例将拥有同版本号、不同 schema。

最低修复方向：恢复 V003/V009 的已发布内容；所有收敛使用新的单调迁移；CI 增加 Git 历史迁移哈希和从每个历史版本升级的验证。

### F-003：关键状态事件绕过 Transactional Outbox

- 等级：P0
- 置信度：确认
- 证据：OSS `KafkaEventBusCapability.java:325-381`；Enterprise `BookingServiceImpl.java:201,286,303,327,337,375,385,407`
- 违反规则：A-10、T-24

默认 `publishIntegration()` 直接执行 `KafkaTemplate.send(...).get()`。Booking/Case 状态事件在数据库事务内调用该方法，但没有标记 `@CriticalEvent`，因此不会被 Outbox AOP 拦截。

影响：

- Kafka 成功而数据库随后回滚，会产生幽灵事件；
- 数据库事务成功而发送失败，会造成外部状态缺失；
- Broker 延迟会占用业务线程和数据库事务。

最低修复方向：状态、库存、租户状态和权限事件必须强制归为 CRITICAL 并写同库 Outbox；Host 启动期验证 CRITICAL→支持 Outbox；增加事务回滚、Broker 故障和重复投递测试。

### F-004：生产允许公开的默认 API Key/Secret

- 等级：P0
- 置信度：确认
- 证据：OSS `platform-gateway/src/main/resources/gateway/security.yml:111-136`；`ApiKeyAuthProperties.java:99-145`
- 违反规则：S-4、A-23、T-17

Gateway 为 frontend、plugin-engine、plugin-service、mobile 提供公开的 `CHANGE-ME-*` 默认 Key/Secret。启动校验只验证非空、重复和长度，不拒绝占位符。

影响：生产环境遗漏变量时仍能启动，攻击者可以直接使用仓库中的已知凭证。

最低修复方向：生产配置不得提供默认 secret；启动期拒绝缺失、占位符和已知开发凭证；增加 prod profile 反例测试和 secret scanner。

## 5.2 P1 高成本与重大可靠性风险

### F-005：插件生命周期未按 v3.0.10 落地

当前仍由 Spring `@Component`、`RuntimeContext` 和 `AbstractModule` 负责装载；不存在有效的 `BrixPlugin + PluginContext + ServiceLoader` 主链。

继续扩展会使每个新插件都成为未来迁移对象。建议先选择一个插件完成端到端垂直切片，再形成批量迁移模板。

### F-006：FIRST_OWNER 接管模型未实现

OSS `TenantProvisioningServiceImpl.java:199-283` 创建租户后立即创建 OWNER/Profile；`PlatformTenantController.java:173-174` 将平台操作员作为 owner。V020 邀请表缺少 `invitation_purpose`、`inviter_type`、`platform_admin_id`。

这违反 T-28，并使平台超管被错误建模为租户成员。

### F-007：新旧两套 JWT/OAuth 身份模型可同时运行

Enterprise `JwtTokenService` 虽已废弃仍是 Spring `@Service`；`OAuth2ServiceImpl` 仍基于旧 `auth_user` 签发 Token。新平台 `JwtValidator` 对缺失 token type、role、cid 和非数值 sub 存在兼容性放行。

如果两套服务共用 issuer/key/audience，旧 Token 可能绕过 Member/Principal 授权版本与上下文校验。生产应先证明旧栈关闭或完全密钥隔离，再迁移 OAuth 到 `sys_identity`。

### F-008：审计分表只完成 DDL，运行时仍使用共享表

V020 创建了 `biz_tenant_audit_log` 和 `sys_platform_audit_log`，但运行时 `AuditLog` 仍映射 `biz_audit_log`，tenant 可空；Platform Audit Controller 读取相同仓储。

需要建立明确的 Tenant Audit 与 Platform Audit Capability/Repository，并禁止平台操作写 tenant audit、禁止 tenant audit 的 tenant_id 为空。

### F-009：SQL 租户守护不是完整的 fail-closed

`TenantInterceptorConfig` 主要通过 Hibernate StatementInspector 装配，无法覆盖所有 JdbcTemplate/直接数据库访问；`TenantInterceptor` 对 JOIN、UNION、子查询、INSERT 和 SQL 解析失败的覆盖有限。

随着复杂查询增加，这会从局部缺口演变为系统性跨租户风险。

### F-010：上下文选择 Ticket 可以并发重复消费

`ContextSelectionTicketRepository` 使用普通查询，没有悲观锁、乐观版本或原子条件更新。消费逻辑采用读后写；并发事务可能同时看到 `consumed_at IS NULL`。

同时，旧 `/select-tenant` 入口仍可绕过 selection ticket/JTI 协议。

### F-011：存在第二套信任原始 Header/参数的 TenantContext

`TenantHeaderFilter` 默认注册并信任 `X-Tenant-ID`、`X-User-ID`，甚至回退请求参数 `tenantId`。虽然正常网关会剥离这些 Header，但直连服务和内部错误路由仍有伪造风险。

TenantContext 应收敛为一个基于已验证 SecurityContext 的 resolver；Header、子域名和 Path 只能作为提示，并在冲突时拒绝。

### F-012：architecture-guard 产生错误安全感

守护有 42 条细粒度 ArchUnit 规则，但：

- `CoreProfileV2` 仍明确按 v3.0.9 放行 JPA；
- 已存在的 `MarkerBasedPluginRule` 没有进入 PluginProfile；
- 不检查 BrixPlugin/PluginContext/ServiceLoader；
- 不检查 Flyway 历史不可变性、FIRST_OWNER、Ticket 并发、审计分表、生产默认凭证；
- OSS architecture workflow 的“architecture unit tests”只执行 TypeScript ESLint 测试；
- 重大架构偏差能够通过商业插件的 45 条 ArchUnit 规则；
- tenant-core 又因没有匹配类而发生误报。

结论只能是“部分有效”。

### F-013：前端仍有直接网络调用

`createPlatformAuthService.ts` 和 `MobileTenantProvider.tsx` 绕过 HttpCapability。需要将所有网络访问收敛到 Repository→HttpCapability，并在整个 workspace 启用禁止 raw fetch/axios 的 ESLint 规则。

## 7. 多租户实现评价

当前多租户实现并非全盘失败，已有若干正确基础：

- Identity、Member、Principal、Profile 已开始形成分层；
- JWT 已支持 audience、tenant/context 和授权版本等新字段；
- Gateway 默认剥离 `X-Tenant-Id/X-User-Id/X-Role` 等敏感 Header；
- 租户白名单采用逐表显式配置，而非整体放行 `sys_*`；
- 最后一个 ACTIVE OWNER 有数据库约束方向；
- 实例配额通过单行 `SELECT FOR UPDATE` 串行化低频激活/恢复事务；
- 对象存储路径、元数据查询和 Avatar 缓存键包含 tenant；
- 平台超管前端的 Page→Hook→Repository 主链较清晰。

但当前公开注册、FIRST_OWNER 缺失、上下文双轨、SQL Guard 缺口和旧 Token 栈使其尚未达到“生产可用且可长期演进的最小实现”。

实例配额的全局行锁属于低频且有意的强一致性设计，在当前开源版小配额场景不构成需要提前分布式化的瓶颈。

## 9. 性能与扩展性

### 已确认问题

- Outbox 发送器在数据库事务中同步等待 Kafka，延长事务并占用连接；
- Outbox 多实例领取不原子，会造成重复发送和无效竞争；
- 统一 `event_outbox` 与 v3.0.10 的插件 schema 所有权模型不一致；
- Tenant SQL Guard 每条 SQL 都有解析/正则成本，同时复杂语句仍可能逃逸。

### 高概率风险

- 插件 Core 广泛 JPA 化会使实体扫描、Repository 初始化和启动内存随插件数量增长；
- 共享 Outbox 单表可能形成写入和扫描热点；
- 同步 Kafka 发布会将 Broker 故障扩散到业务线程和数据库事务。

### 需要压测验证

- Outbox 在 1/4/8 个实例下的重复率、P95 延迟与积压恢复时间；
- QueryCapability bulkhead 是否真正与 Web 线程池隔离；
- 高 tenant 基数下的缓存、审计和对象存储索引效果；
- 插件数量增长时的启动时间、Bean 数、Metaspace 和常驻内存；
- 真实 N+1、无界分页和连接池竞争。

本轮没有足够证据把所有理论风险都定性为已发生故障。

---

## 10. architecture-guard 专项结论

结论：**部分有效，只能发现部分违规。**

### 10.1 A-x/S-x 覆盖摘要

| 状态 | 红线 |
|---|---|
| 有一定机器化覆盖 | A-1、A-2、A-6～A-13、A-18～A-21、S-1、S-2、S-5～S-8 |
| 只有局部实现或非独立门禁 | A-3、A-5、A-17、A-20、S-3、S-9 |
| 基本未实现机器门禁 | A-4、A-14～A-16、A-22、A-23、S-4 |
| 已确认守护漏报 | A-10、A-15、A-21、A-23、S-4 |

### 10.2 T-x 覆盖摘要

- 有部分机器检查：T-7、T-12、T-15、T-18、T-20、T-21、T-27；
- 有实现或测试但不是完整门禁：T-1～T-5、T-8～T-11、T-13～T-17、T-22～T-26；
- 当前明确失败或严重缺失：T-2、T-4、T-19、T-24、T-25、T-28。

### 10.3 主要治理缺口

- 新模块需要手工添加 ArchitectureTest，可能通过遗漏测试文件逃逸；
- 规则大量基于包名和类型名，无法验证真实运行生命周期；
- 缺少“故意违规代码一定使 CI 失败”的系统性反例 fixture；
- Java guard 没有作为 dedicated architecture job 执行；
- 无法从源码确认 GitHub 分支保护是否将相关 workflow 设为 required check；
- guard 自身 POM 运行结果为 `Tests run: 0`。

## 11. 修复路线

### 第一阶段：立即止血

在本阶段完成前禁止发布：

1. 封闭或下线公开租户注册，身份只取自已验证 Token；
2. 恢复 V003/V009，使用新迁移前滚；
3. 生产启动拒绝默认/占位 API Key 和 Secret；
4. 所有状态、库存、权限、租户状态事件强制走 Outbox；
5. 禁用或密钥隔离旧 OAuth/JWT；
6. 将以上场景做成负向 CI 测试。

### 第二阶段：恢复架构边界

1. 用一个真实插件完成 `BrixPlugin + PluginContext + ServiceLoader` 垂直切片；
2. 实现 `PENDING_ACTIVATION → FIRST_OWNER 接受事务 → ACTIVE`；
3. 拆分 Platform Audit 和 Tenant Audit；
4. 收敛唯一 TenantContext resolver；
5. 原子消费 selection ticket，移除旧 `/select-tenant`；
6. 修复 Outbox 多实例 claim 和插件 schema 所有权；
7. 将前端所有网络访问收敛到 Repository→HttpCapability。

### 第三阶段：机器化守护

1. 按 v3.0.10 A/S 和 v3.1.3 T 编号重建规则清单；
2. Java guard、ESLint、Schema lint、Flyway history lint 分别成为独立 required check；
3. 存在插件 manifest/POM 却缺 ArchitectureTest 时直接失败；
4. 每条红线至少提供一个故意违规的反例 fixture；
5. 增加迁移历史哈希、生产依赖树、默认 secret、BrixPlugin provider、typed query、事件可靠性检查；
6. 修复 guard 自身零测试和 thin module 空匹配误报。

## 14. 无法确认的问题

以下事项需要运行环境或外部配置证据：

- 生产是否覆盖了全部 Gateway Key/Secret；
- 旧 OAuth/JWT 与新平台认证是否共用 key、issuer、audience；
- V003/V009 是否已在客户或生产数据库执行，需要 `flyway_schema_history`；
- GitHub 是否将 architecture、coverage、dependency scan 设为 required checks；
- 实际 Host 是否装载 Outbox artifact 和 AOP；
- 多实例 Outbox、Tenant SQL Guard 和 Ticket 并发的生产表现；
- 搜索、导出和异步线程的全栈 tenant 传播；
- T-22 对象级授权是否覆盖所有商业业务对象；
- 真实 N+1、连接池、启动时间和内存占用。

## 15. 最终裁决

### 当前 Brix 架构是否已经失控？

没有全面失控，但发布治理、版本 SSoT、迁移不可变性、事件一致性和关键安全边界已经局部失控。

### 当前代码是否主要按照 v3.0.10 落地？

不是。当前主模型仍是旧 RuntimeContext/Spring 插件模型，只叠加了部分新 Capability 和多租户实现。

### architecture-guard 是否可信？

只能部分信任。它能发现部分直接依赖违规，但不能证明 v3.0.10 已落实，也不能作为唯一合并或发布依据。

### 是否存在未来必须付出巨大代价的设计问题？

存在，主要集中在插件生命周期、身份双模型、Flyway 历史、审计模型、插件 Core JPA 化和事件可靠性分类。

### 修复到什么程度后才适合继续开发新功能？

至少必须：

1. 关闭 F-001～F-004 全部 P0；
2. 完成 F-005～F-012 的核心边界收敛；
3. 为上述问题建立可在 CI 中失败的反例测试；
4. 使冻结基线、守护规则、模板和 CI 全部指向同一架构版本。

完成这些条件后，Brix 才适合恢复以新增业务功能为主的开发节奏。
