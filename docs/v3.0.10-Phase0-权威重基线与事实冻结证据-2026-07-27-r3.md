## 2. Phase 0 冻结裁决

1. OSS `platform-tenant` 唯一拥有平台租户目录、成员、主体、邀请、配置、配额及其
   migration、Repository contract、本地事务、租户审计和 canonical Outbox/Inbox。
2. Enterprise `app-tenant` 只拥有企业扩展、展示模型或业务配置；不得写 `sys_*`、形成第二
   权威租户目录、双写成员关系或声明 `/api/platform/**`。
3. 平台租户运维写路径唯一为
   `platform-admin OperationalContext → brix.internal.tenant.administration →
   io.brix.platform.tenant.internal.TenantAdministration 1.0.0 →
   platform-tenant Owner local transaction`。
4. `platform-admin` 只能消费 descriptor 已声明且 privilege allowlist 批准的内部契约；
   不得直接注入 Owner Repository、Entity、Mapper、Service 或传播调用方事务。
5. Platform Token、Actor Token 与 `BOOTSTRAP_SETUP` 安全域互相隔离。Platform Token
   不含 tenant/member/Actor/Subject context；`BOOTSTRAP_SETUP` 是短期、一次性、
   专用 audience/scope 的 session，不是 Platform Token。
6. `/api/platform/**` 只可由 L2B Dispatcher 发布的 platform-operational Runtime Entry
   承载；B3/O8 前必须保持不可准入。Spring Controller 与 `ApplicationRunner` 不是备选路径。
7. 邮件本期事务语义唯一为 Data Owner 本地事务内同步单次调用、失败回滚；不新增事件、
   Outbox、重试队列或假成功状态。未来改为可靠异步必须另行评审。
8. Flyway 只允许前滚。任何已发布 migration 不得改 checksum、静默删除或用 `repair`
   掩盖差异。

以上是文档裁决，不是当前代码已经合规的声明。父计划 §3.1 的 C-01 至 C-15 仍是实现偏差
清单，必须由后续独立 Phase 按顺序关闭；Phase 0 不修改运行时代码来伪造关闭状态。

## 5. 生产级最小证据实现

| 文件 | 分层 | 责任 |
|---|---|---|
| `.github/workflows/phase0-supply-chain.yml` | support / CI | 精确 commit 构建 Host，生成 SPDX SBOM，签发并在线校验 provenance、SBOM 和自定义 binding attestation |
| `scripts/phase0_evidence.py` | support / evidence contract + verifier | Flyway 脱敏、Flyway 11 checksum、制品/部署/commit/BOM 绑定、Sigstore 校验和最终 fail-closed 判定 |
| `scripts/collect_phase0_flyway_history.sh` | support / environment collector | 只读查询两张明确 history 表，不接收命令行凭据，临时 CSV 退出即删除 |
| `scripts/test_phase0_evidence.py` | support / tests | 覆盖字段 allowlist、secret 排除、digest、checksum、迁移前缀、Git dirty tree 和源码 binding 负向门禁 |
| `docs/phase0-evidence/README.md` | support / runbook | DBA 最小权限、可信 CI、部署字节取证、clean audit worktree 和完整环境清单操作规程 |
| `docs/phase0-evidence/.gitignore` | support / evidence hygiene | 排除 JAR、原始/敏感证据和本地闭环产物 |

实现具有以下硬门禁：

1. Flyway CSV 只接受固定九列；host、database、user、`installed_by` 和 credentials 不进入
   输出。失败行、重复/非连续 rank、非 SQL、版本缺口、顺序或 checksum 不一致均失败。
2. 迁移源按数值版本排序；同时记录 Flyway 11 signed CRC-32 和 raw-byte SHA-256。
3. artifact binding 必须同时存在 SLSA v1 provenance 与 SPDX 2.3 SBOM attestation，并
   绑定 JAR raw bytes、SBOM、两个仓库 commit、origin 和根 BOM/lock digest。
4. binding JSON 本身作为自定义 predicate 再签名。最终校验重新调用
   `gh attestation verify`，校验证书、时间戳、source digest、signer workflow、
   predicate type 和非 self-hosted runner。
5. 最终校验要求两个 clean audit checkout 与签名 binding 的 origin、commit、BOM
   完全一致，防止以任意或已修改的迁移目录替代出证源码。
6. 每个声明环境必须同时存在两个 Flyway 账本和实际部署字节 binding；任一输入缺失、
   digest 不同或环境重复均失败。工具不提供 `--skip`、假数据或降级 PASS。

## 6. tenant、权限、审计、事件与 UI 说明

- `tenant_id`：本 Phase 不读写业务表，也不创建租户数据。工具仅核对迁移账本；唯一 Owner
  与租户隔离规则冻结在 multi-tenant 4.0。
- 权限：数据库采集账号只允许两张 Flyway history 表 `SELECT`；GitHub workflow 使用最小
  contents/id-token/attestation/artifact metadata 权限；没有新增业务权限接口。
- 审计：本 Phase 形成供应链与环境证据，不写 `biz_audit_log`、
  `biz_tenant_audit_log` 或 `sys_platform_audit_log`。当前运行态审计分表情况仍待真实核验。
- 事件、Outbox、Timeline：不产生跨插件业务事件，不新增 Outbox/Inbox/Timeline 表或流程。
  Owner/Event 语义只在 ACTIVE 蓝图中冻结，不以脚本模拟。
- Flyway：不新增、不修改、不执行 migration；只读采集并比对既有 V001-V020/V100。
- Manifest：不新增或修改。Phase 0 工具不是 Plugin/Runtime Entry。
- 前端：不涉及页面、表单、路由、登录或用户操作，因此没有 Page/Hook/Repository/
  Route/Guard/UI 变更，也不需要读取 `PROMPT.md` 执行视觉设计。
