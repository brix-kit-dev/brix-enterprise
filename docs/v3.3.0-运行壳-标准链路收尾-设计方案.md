## 0. 结论摘要

标准链路指根 §6.1 唯一通信决策表的四条跨插件通道（typed Query、typed Command、Integration Event、ExternalHttp），加上各入口交给 Handler 的调用上下文（根 §5.3、§5.4 的冻结 ABI），以及证明没有旁路的门禁（A-9、A-10、A-11、A-22，附录 A 的 MESSAGE 组）。现状：

- **事件**已收口（K1～K25，已部署）。**查询**在分支上完成，差连接池三项措施。
- **命令**链路能跑，但插件面是字符串类型，Owner 一侧不读策略、不判定访问，业务幂等键不含租户与发送方，没有示例。
- **ExternalHttp** 没有实现，只有接受任意 URL 的旧 `HttpCapability`。
- **任务入口**没有实现：任务被创建后没有任何地方调度它。**HTTP 入口**缺类型化输入输出、Schema 校验、截止时间执行、隔离与幂等，重叠路由到请求时才报错，原始 `Authorization` 头交给了 Handler。
- **门禁**：20 个模块的 `@ArchTest` 从未运行；CI 不跑需要 PostgreSQL 的消息测试；事件与命令没有 Schema 兼容检查；platform-identity、platform-tenant 直接依赖 platform-auth 插件。

本方案分 8 组施工（L1～L8），约 22～25 个工作日，每组单独提交、单独验证。做完以后，主线迁移的插件对每个入口、每条通道都按定型的契约写，不再需要返工。

## 2. 约束

1. 只有 ACTIVE 蓝图指导施工；不改冻结蓝图，需要改的列入 §8。
2. 兼容（CAP-019～023）：Minor 里 Java 接口只能经有稳定缺省语义的 default 方法、扩展子接口或新接口增加行为；新字段可选、有缺省语义；弃用项标注替代项、引入版本与 4.0 移除；移除只进下一个 Major。
3. 迁移只追加（DATA-019）；表结构变化随启动期表结构检查一起更新。
4. 共享机：Maven 离线构建，限堆、串行、看门狗；需要 PostgreSQL 的测试用一次性容器（127.0.0.1:25433），不碰共享库；企业仓按分支构件验证时先备份 `~/.m2`、跑完立即按 sha256 恢复；部署从原始检出构建，要负责人批准。

## 3. 关闭标准

1. L1～L8 完成，D47～D63 按推荐落实，或负责人另有决定并已落实。
2. 每条通道都有类型化契约（查询、命令由 Schema 生成；事件为对照 Schema 检查的 record），清单策略在启动期解析、在运行期执行，一致性测试在两种传输上通过，并在 CI 的 PostgreSQL 上运行。
3. HTTP、Query、Command、Event、Task 每个入口交给 Handler 的都是 Runtime 构造的调用对象，带范围、身份、截止时间与取消信号；每个入口里都能使用四条通道。HTTP 的签名差异只剩 §4.7 记录的兼容子接口，4.0 时消除。
4. 门禁：声明了 `@ArchTest` 的模块都实际运行；守卫覆盖插件与平台模块的 A-1、A-9、A-11、A-22 与 LIFE-010；`getEventBus()` 不能新增；冻结的存量违规已列给负责人。
5. 平台模块之间没有插件对插件的直接依赖。
6. 作者文档、变更记录、脚手架覆盖每条通道与每个入口。
7. brix 全量回归、企业仓 verify、一次性环境回归通过；两仓分支已提交；合并与部署按负责人要求进行。

### 10.1 L1 查询收尾（brix `a2da1ad`）

- 懒取连接：Host 的 Hibernate 拿到包着连接池的 `LazyConnectionDataSourceProxy`（经 `HibernatePropertiesCustomizer` 设 `jakarta.persistence.nonJtaDataSource`）；事务管理器与适配器的 JDBC 访问仍用连接池本身，同一事务里两者用会话的同一个连接。`brix.persistence.lazy-connections=false` 可关。
- 取连接限时：查询 Provider 的只读 Unit of Work 取连接最多等到剩余截止时间（`ConnectionAcquisition`：计时器到时中断等待，中断不会残留到等待之外）。与方案的出入：连接池一直占满时，等待用完了截止时间，返回 `query.deadline_exceeded`，而不是方案写的 `query.provider_failed`；连接池自己的超时先到时才是暂时性的 `query.provider_failed`。归为超时更准确。
- 启动检查：HikariCP 池小于"每个 Relay、每个消费者、每层查询各一个，再加一个请求"时 WARN `event=connection_pool.too_small`，否则 INFO 记录比较结果。
- `TenantDirectoryCapability` 标为弃用、4.0 移除；守卫里指向它的提示改为指向 `platform-tenant.tenant-reference`；作者文档补"先查询、后写入"；变更记录。
- 验证：新增 13 个测试。`LazyConnectionsAutoConfigurationTest` 在 Spring Boot 自带的 HikariCP 上证明三件事：第一条语句前不占连接；关掉以后开事务即占；池被占满时 300 毫秒的截止时间内失败，不等 30 秒。brix 全量回归 1416 个测试，失败 0。

### 10.4 L4 命令补齐（brix `c6c7d40`）

- 契约：生成器读 `META-INF/brix/commands/<commandType>/<version>.json`，为请求 Schema 生成 record（构造时按 Schema 校验，带 builder），为插件生成 `<Plugin>Commands` 的 `CommandType<C>` 常量；`contracts.api` 记录 `command` 行。查询契约的版本规则同样适用。
- SDK（L2A）：`CommandType<C>`、`CommandClient<C>`（`submit(payload, idempotencyKey)`，可另给分区键）、`CommandCapability.client(...)`（default 方法，旧实现照常编译）。`CommandInvocation` 加 `access`（`AccessDecision`）与 `idempotency`（`IdempotencyContext`），保留原构造器；`CommandEnvelope` 加 `actorId`；`CommandSubmitException` 加 `command.access_denied`。`submit(CommandRequest)` 标为弃用、4.0 移除。
- 发送方：Runtime 给每个发命令的插件一个 `PluginCommandCapability`。只给 `commands.consumes` 里声明、版本在范围内的命令发客户端；租户取当前调用的范围（调用之外是平台命令），发送方与版本由 Runtime 记录，插件不能指定。Owner 的 access 是 `on-behalf-of:<perm>` 时，提交时按调用方用户的权限判定，信封记录用户。Host 上没有 Owner 时提交立即失败（`command.provider_missing`），不写 Outbox。查询里不能发命令。
- Owner：投递前按 access 策略判定，`on-behalf-of` 的命令没有用户时永久失败，停放为 `COMMAND_ACCESS_DENIED`。业务幂等键按"发送方｜租户｜发送方给的 scope"唯一。
- 清单与启动：provides 必须声明 scope、access、timeout、concurrency、retry、idempotency 六个策略，consumes 必须声明 required、versionRange、timeout、retry、idempotency；发送方必须声明 `CommandCapability` 与 `data.outbox`，Owner 必须声明 `data.inbox` 与 `PersistenceCapability`；未知策略启动失败。插件有命令总线时，`CommandCapability` 通过启动期能力校验。
- 示例：sample-orders 提供 `sample-orders.cancel-order`（订单加 `status`、`cancel_reason`，迁移 V2；订单详情显示状态）。sample-shipping 新增 `POST /api/sample-shipping/shipments/{orderId}/refuse`：在自己的 Unit of Work 里发命令，返回 202 与 commandId。sample-shipping 只依赖 sample-orders-api。
- 文档：作者文档"事件与命令"改为类型化命令（提供、发送、策略、错误码）；能力契约、v2 迁移、示例、后端指南同步；变更记录；脚手架清单模板与 README 注释。

与方案的出入：

1. 策略名。方案 L4.3 写的是命令专用名：timeout 与 concurrency 用 `command-standard`，retry 用 `command-transient-retry`，idempotency 用 `command-key`。实际沿用事件订阅已有的目录：timeout、retry 用 `event-standard`，concurrency 用 `partition-serial`，idempotency 用 `persistent-inbox`。
   - 理由：命令与事件走同一条 Relay、同一个消费者、同一个 Inbox，这些策略落到同一组 Host 设置上。另起一套名字，只是一组必须永远与事件保持一致的同义词。
   - 对命令而言，`persistent-inbox` 包含业务幂等键表。
   - 根 MANIFEST-025/026 只规定字段，不规定取值。
   - 负责人如果要命令专用名，可以作为别名加进目录，已写的清单不受影响（§8 第 11 项）。
2. 幂等键。方案 L4.5 写的是追加迁移、改主键。实际没有改表结构：Owner 把"发送方｜租户｜发送方的 scope"写进已有的 `idempotency_scope` 列，超过 128 字符时存 SHA-256；唯一约束不变。因此表结构检查不用改，已有数据也不用迁移，§9 里"命令幂等表改主键"这条风险随之消失。
3. `CommandRequest.forTenant` 没有单独弃用。插件交出 `CommandRequest` 的唯一入口是 `submit(CommandRequest)`，它已经弃用；Runtime 内部仍用 `CommandRequest` 在客户端与总线之间传递。
4. L4.4 的"timeout、retry 真正生效"。命令投递沿用事件投递的截止时间、重试与停放，是同一套代码，所以生效方式与事件一致。命令没有单独的数值。

### 10.5 L5 契约兼容门禁（brix `97b251f`）

- 一套工具覆盖三类契约：
  - 新增事件契约文件 `META-INF/brix/events/<eventType>/<version>.json`，写明 eventType、version 和 payload。
  - 生成器按契约子集、按同一 Major 里的早先 Minor 检查事件载荷 Schema，`contracts.api` 记录事件。
  - 载荷 record 仍然手写，由 `EventSchemaContract` 对照。它另外要求每个发布的事件都有契约文件，并且契约文件指向同一个 Schema。
- 已发布版本锁定：
  - `contracts.api` 记录查询、命令、事件用到的每个已发布 Schema 版本的内容哈希：规范化 JSON 的 SHA-256，成员按名称排序，去掉无意义的空白。
  - 改动已发布的文件会丢掉这一行，构建失败，并提示：已发布的版本不能改，请发布新版本（文档修正用 Patch），原文件保留不动。
- Minor 规则：
  - 可以加可选字段（原来就允许），也可以在枚举末尾加值；改动、重排、删除都要出新 Major。
  - 运行时：命令与事件经 `MessagePayloads` 解码。接收方类型不认识的枚举值读成 null：可选字段为空；字段是必填时，载荷无效并停放。
  - 生成的枚举注释与这一行为一致。
- L5.4：
  - sample-orders-api 加两个事件契约。
  - platform-tenant 的 `TenantFirstOwnerAccepted` Schema 连同契约文件移到 platform-tenant-api。运行时按类路径找文件，所以不受影响。
  - platform-identity 没有 api 构件，在自身构建里加 `ContractSourcesTest` 和 `contracts.api`。
- 文档：查询指南的"变更契约"规则、事件指南的事件契约文件；变更记录。

与方案的出入：

1. 事件载荷里的数组不要求 `maxItems`。platform-identity 已发布的 `identity-audit-fact` 1.0.0 有一个不设上限的数组；补上限属于收紧输入，按根 §4.4 要出新 Major。查询结果和命令请求仍然要求上限，查询方案 §5.6 的理由只适用于它们。
2. 子集接受类型列表 `["<type>", "null"]`，只限可选字段。platform-identity 已发布的 Schema 是这样写的，语义与可选字段相同。
3. 方案没写事件契约的形式，现在加了一个契约文件，与查询、命令的契约文件对称。运行时的依据仍是清单里的 `events.publishes`，两者是否一致由 `EventSchemaContract` 保证。
4. 只锁定三类契约用到的 Schema。端点的请求、响应 Schema 不锁定：L5 的范围是三类契约。

### 10.6 L6 任务入口（brix `704f8c3`；企业仓 `4bcb0cf`）

- SDK（L2A）：
  - 新增 `TaskInvocation`（根 §5.3 的 11 个字段，进入任务前检查）和 `ExecutionIdentity`。
  - `ManagedTask.execute(TaskInvocation)` 以 default 方法加入；`run()` 弃用，4.0 移除。
  - 两个方法都是 default，所以已编译的、实现 `run()` 的任务照常运行；两个方法都没实现的任务在启动时拒绝（D56）。
- 清单与启动：
  - 运行时读 `tasks.provides`；九个字段必填，id 唯一。
  - 可选字段 `transaction`（required、read-only、none；DATA-028）；在 Unit of Work 里运行的任务需要 PersistenceCapability。两份清单 Schema 同步。
  - 启动时按策略目录和 Host 上限解析策略：名字未知、或触发比 `brix.tasks.min-interval` 更频繁，插件启动失败。
  - 声明与 Factory 双向一致；`task-trigger` 需要 `data.storageId`。
- 调度器 `RuntimeTaskScheduler`（L2B）：
  - Host 入口发布后才开始触发，每次触发重新查找任务。
  - 随 Host 停止：先不再触发，再给在途运行 drain 超时，最后取消。
  - 触发：`every:<时长>`（按纪元对齐）与 `cron:<表达式>`（UTC）。
  - `task-no-overlap`：上一次没跑完的触发跳过并计数。
  - 每次尝试有截止时间，到时由单独的线程设取消信号并中断；`task-transient-retry` 按倍增退避重试。
  - 运行在模块的 Unit of Work 里，平台范围，以模块身份。
  - `task-trigger` 在 Owner 的 `{storageId}_task_run` 表里认领 `(taskId, triggerId)`，认领的插入先于运行提交；`task-instance-local` 每台主机都运行。
  - 日志 `event=task.*`，指标 `brix.task.*`；完成的运行按保留期清理。
- 持久化：规范表 `{storageId}_task_run`（平台迁移、独立 schema history、启动期结构检查）和 `JdbcTaskRunClaims`。
- 运维模块：任务声明带上策略，走同一个调度器；只能 `task-instance-local`，不开 Unit of Work。
- 企业主机告警（企业仓 `4bcb0cf`）：
  - `BrixTaskFailing`：各主机的连续失败相加达到 3。
  - `BrixTaskOverdue`：所有主机最近一次成功距今超过三个触发间隔。
  - `BrixTaskClaimFailing`：无法认领触发。
  - promtool 测试通过。
- `SchedulingCapability` 和 `RuntimeContext.getScheduling()` 弃用，4.0 移除（MANIFEST-026，D63）。
- 示例与文档：sample-orders 的 heartbeat 任务；作者文档"任务"一章；后端指南与事件指南、变更记录、脚手架同步。

与方案的出入、发现：

1. `ManagedTask` 不再是函数式接口。D56 要求两个方法都有 default 实现、启动时检查，只能这样做到。以 lambda 实现 `run()` 的源码不再能编译，二进制兼容不受影响。两仓里只有 SDK 自己的契约测试这样写，已改。
2. 认领单独提交，在运行之前（锁行做法，与 ShedLock 同类），不与任务的 Unit of Work 共用事务。
   - 好处：运行期间不持有行锁。
   - 代价：一次失败的运行不会被别的主机接手，由下一个触发照常运行。
3. 平台范围的任务只碰得到插件的全局表。按租户运行的任务按 D47 留到第一个需要它的插件，所以示例任务不碰数据（`transaction: none`）。
4. 方案列的指标是 `brix.task.runs`、`brix.task.skipped`、`brix.task.running`。为了告警另加了 `brix.task.last.success`、`brix.task.interval`、`brix.task.consecutive.failures`。
5. 发现：端点 Handler 本来就运行在 Runtime 开的 Unit of Work 里（DATA-028）。L4 的示例和指南误写成端点要自己开，已更正（brix `dfff974`）。
6. 企业仓的分支构件 verify 从这一组起也安装 infra-adapter-database（平台迁移在其中）。

### 10.7 L7 HTTP 入口契约

L7 分两次提交：L7a 是会改变 Handler 写法的部分，L7b 是 Runtime 一侧的部分。

#### L7a Handler 形状与契约（brix `e976b91`）

- SDK（L2A）：
  - `TypedEndpointHandler<B, R>` 就是根 §5.4 的 `CompletionStage<R> handle(EndpointInvocation<B>)`（D58）。
  - `EndpointInvocation` 加取消信号和 `withBody`，保留原构造器。
  - `ErrorCategory`，以及 `ErrorCode.category()`（default，缺省 `INTERNAL`）。
  - 分页约定 `PageRequest`、`Page`（`io.runtime.sdk.page`；page 从 1 起，size 上限 100，D61）。
- 清单：
  - `response.status`（200、201、202、204）写进校验器、描述符和两份清单 Schema。
  - 端点幂等 `required`、`optional` 让插件启动失败，运维描述符同样处理（D47、L7.7）。
- Dispatcher，对类型化 Handler：
  - 请求：POST、PUT、PATCH 取请求体，其他方法取查询参数，再加上路径变量；按请求 Schema 的属性转换类型。
  - 校验：在访问检查之前按请求 Schema 校验（MANIFEST-022 的顺序），失败为 400 `endpoint.invalid_request`，只带字段路径与规则名，不带值。
  - 读成 `B`：类在 implements 里写明 `B`；lambda 拿到 JSON。
  - 等待：按截止时间等待；到时设取消信号、回滚，返回 504 `endpoint.deadline_exceeded`。
  - 响应：在 Unit of Work 内按响应 Schema 校验，不符则记录、回滚，返回 500 `platform.unknown`；成功按声明的状态码返回，204 不带正文。
  - 启动检查：类型化端点的 Schema 不在插件类路径上时，插件启动失败。Schema 之间的 `brix://` 引用按类路径解析。
- 错误映射：`BrixException` 按类别给状态码，未映射的异常一律 `platform.unknown`，原因只进日志。
- 示例：sample-orders、sample-shipping 的端点改成新形状。
  - 错误码带类别：`sample-orders.order_invalid`、`sample-orders.order_not_found`、`sample-shipping.shipment_not_found`。
  - 下单返回 201，拒收返回 202。
  - 端到端测试覆盖了违反 Schema 的请求。
- 文档：作者文档"端点"一章；后端指南、事件指南、示例页同步；变更记录；脚手架。

与方案的出入、发现：

1. L7.7 的前提不成立。方案以为没有端点声明 `required`，实际上有九个：platform-admin 八个，platform-tenant 的 first-owner 接受一个。
   - Runtime 从没执行过这项声明：没有幂等键校验，也没有结果重放，这违反根 MANIFEST-018。
   - 现在改为 `not-applicable`，行为不变，缺口从无声变为显式。这些 Handler 靠业务键幂等。
   - 端点结果重放什么时候做，交负责人决定（§8 第 12 项）。
2. platform-tenant 的两个端点没有改成新形状（L7.9 的一部分）。
   - 它们清单里引用的四个 Schema 文件（first-owner 接受的请求与响应、session 的请求与响应）都不存在。
   - 改形状就要补 Schema。session 端点在每次租户登录时都会调用，Schema 有一点不对就会变成 500。
   - 这需要能跑租户与 super-admin 的端到端，而 127.0.0.1:25432 仍被占用，所以留到端口空出后再做。旧形状照常工作。
3. 根 MANIFEST-022 把 Schema 校验放在认证之前，本次照做。不过认证本身（令牌校验）在 Host 过滤器里已先做完，Dispatcher 里的是访问检查。
   - 常见做法是先认证、再校验请求，以免向未认证者透露字段结构。
   - 可作为 RFC 建议提给负责人，未改蓝图。
4. CRUD 示例页仍是旧形状，页首加了说明。旧形状 `EndpointHandler` 不校验请求与响应，4.0 时改为根签名。

#### L7b Runtime 一侧（brix `373eaf1`）

- 路由（L7.4，根 MANIFEST-023）：
  - 路径模板：变量占整段，名字以字母开头。同一方法下，只在变量名、重复或结尾斜杠、大小写、百分号编码上不同的两条路由算同一条，Host 启动失败。
  - 匹配：字面段按解码后的原文比较。几条都匹配时，在第一个不同的段上是字面段的那条胜出。
  - app-tenant 的 `GET /api/v1/tenants/by-code/members` 现在进 by-code；原来两条都匹配，返回 404。
  - 路径变量交给 Handler 时已解码。编码坏掉、或含 `.`、`..` 段的请求不匹配任何路由。
  - 保留前缀：插件声明 `/api/platform/**` 时 Host 启动失败（根 LAYER-017）；任何端点声明 `/oauth2/**`、`/.well-known/**`、`/auth/**`、`/bff/**` 时 Host 启动失败（根 SECURITY-011）。
- 截止时间与隔离（L7.5，D60）：
  - `timeout.policyRef` 的目录：`endpoint-default` 是 Host 的端点截止时间（缺省 30 秒），也是另两个的上限；`interactive-read` 缺省 10 秒；`interactive-write` 缺省 15 秒。Host 在 `brix.runtime-shell.endpoints` 下可改，超过上限时启动失败。
  - 未知的名字让插件或运维模块启动失败。
  - 插件的事务取剩余时间：语句和取连接的等待都在截止时间结束。JPA 适配器的 `requiredWithin` 与查询用的 `readOnlyWithin` 是同一机制。已过截止时间就不开事务，返回 504。
  - 每个端点同时最多 64 个调用（可改）。再来一个时，在 Handler 之前立即返回 503 `endpoint.rejected`，其他端点不受影响。
  - 指标：`brix.endpoint.calls`（按 module、endpoint、outcome）和 `brix.endpoint.in_flight`。
- 安全与 Trace（L7.6）：
  - Handler 看不到 `Authorization`、`Proxy-Authorization`、`traceparent`、`tracestate`、`baggage`、`x-trace-id`。
  - HTTP 调用方是不可信上游（根 OTEL-002、OTEL-004）：
    - 每次调用开一个新 trace；
    - 格式合法的 `traceparent` 只作为 link，不作 parent；
    - `tracestate`、`x-trace-id` 不再使用。
  - `EndpointInvocation.traceId()` 是 Runtime 的 trace id。
  - 调用期间发出的 Query、Command、Event 和日志（MDC 的 `traceparent`、`traceId`）都带这次调用的 trace。
  - OTel 适配器给每次调用记一个 SERVER span：
    - 名字是方法加路由模板；
    - 属性有方法、路由、模块、端点和状态码；
    - 5xx 标为错误。
  - 错误信封带 `traceId`（根 ERROR-013）。
- 文档：端点一章加了"路由""截止时间与限制""Trace""Host 设置与指标"；变更记录也已更新。

与方案的出入、发现：

1. L7.6 的 setup-token、bootstrap-setup 校验没有挪到 Dispatcher。
   - 这两种入口用一次性令牌，由身份 Owner 校验并作废（super-admin 蓝图 BRX-SA-SEC-003）。platform-admin 的 Handler 只把令牌原样交给 platform-identity，不解析。
   - 如果 Dispatcher 先校验、Handler 再消费，"校验"和"作废"就分成两步，中间有重放窗口。要这样做，internal contract 得提供"校验并占用"。
   - 这项改动要跑 super-admin 的端到端（初始化与登录），而 127.0.0.1:25432 仍被占用。
   - 所以只有这两种入口的 Handler 还能看到 `Authorization`，其他入口都看不到。是否挪到 Dispatcher，交负责人决定（§8 第 14 项）。
2. 从 HTTP 端点发出的事件和命令，原来不带请求的 trace：MDC 里没有 `traceparent`，Outbox 每次随机生成一个。现在带上了。
3. 根 MANIFEST-022 要求 Dispatcher 维护有界指标，方案 L7.5 没写，本次加了两个。
4. 旧形状 Handler 是同步的，Dispatcher 不能中途停止等待。不过它的事务、取连接和下游 Query 都在截止时间结束。
5. 找不到路由的 404 仍由 Spring 的错误处理返回，不带错误信封和 `traceId`：trace 在找到路由之后才开始（根 MANIFEST-022 的顺序）。
   - 改成信封会改变所有未知路径的响应，宿主若依赖错误页回退会受影响，所以未改。
6. 根 §4 中 `timeout` 的"可选的更严格 Endpoint 上限"没有实现，只认 `policyRef`。

### 10.8 L8 ExternalHttp（brix `f884ae9`；企业仓 `c0b113a`）

- SDK（L2A）：
  - `ExternalHttpCapability.service(id)` 返回只能访问该服务的客户端。`send(ExternalHttpRequest)` 同步返回 `ExternalHttpResponse`，任何状态码都是响应。
  - 请求只有方法、服务内路径、查询参数、请求头和正文：
    - 路径不能带主机、`..`、查询或片段；
    - 请求头不能带 `Authorization`、`Cookie`、`Host`、Trace 头和连接头。
  - `BrixExternalHttpException` 有六个码，各带类别：`external_http.undeclared_service`、`target_forbidden`、`deadline_exceeded`、`circuit_open`、`rejected`、`failed`。
  - `ExternalHttpModules.forModule(moduleId)` 给 Host 用 Spring 装配的平台代码用（见下文第 2 项）。
  - `HttpCapability` 弃用，4.0 移除（D63）。
- 清单：`externalServices[]` 新增三个必填项 `timeoutPolicyRef`、`retryPolicyRef`、`concurrencyPolicyRef`；`authPolicyRef` 只认 `none`。Java 校验器和两份 Schema 一起改了。
- 策略目录（未知名字让插件启动失败）：
  - `external-default`：Host 的外部调用超时，缺省 5 秒。
  - `external-no-retry`：不重试。
  - `external-idempotent-retry`：GET、HEAD、PUT、DELETE 没有响应、或返回 502、503、504 时重试。最多 3 次，间隔从 100 ms 起倍增，不超过截止时间。
  - `external-standard`：每个插件对每个服务同时最多 16 个调用。
- Host 目录与目标策略（L8.3，根 ERROR-014、A-11）：
  - 目录项是 `brix.external-services.<baseUrlRef>.base-url`。生产 Profile 只接受 https；地址带用户信息、查询或片段时 Host 启动失败。
  - 拒绝这些地址：回环、通配、链路本地（含云元数据地址）、组播、本机网卡地址，以及 `brix.external-http.self-addresses` 列出的本机对外地址。
  - 插件启动时检查一次，命中则插件启动失败；之后每次尝试前再检查。
  - 目录里没有地址的服务照常启动，调用时报 `undeclared_service`。
- 网关（L8.4）：
  - 截止时间取 Host 超时与当前调用截止时间中较早的一个。
  - 按（插件，服务）熔断：最近 20 次里至少 10 次、且一半失败时打开 30 秒。并发上限也按（插件，服务）计。
  - 只对幂等方法重试；响应大小有上限（缺省 1 MiB）；不跟随重定向。
  - 记 CLIENT span 并带 `traceparent`；指标 `brix.external_http.calls`。
  - Query 执行中只允许 GET、HEAD（根 MESSAGE-002）。
- platform-auth（L8.5）：
  - 清单声明 `google-oauth-jwks`，`GoogleIdTokenVerifier` 改走这个服务。
  - 企业仓 Host 目录加了 `https://www.googleapis.com`，可用 `GOOGLE_OAUTH_JWKS_BASE_URL` 覆盖。
- 文档：作者文档"调用外部服务"；变更记录；ArchUnit 规则的提示改为 `ExternalHttpCapability`。

与方案的出入、发现：

1. 传输放在 Runtime（L2B）里作缺省实现，不是方案写的 L2C 适配器。
   - 目标检查、截止时间、熔断、重试都在网关里，传输只负责收发字节。
   - Host 可以提供自己的 `ExternalHttpTransport` Bean 替换它。
2. platform-auth 的 Google 联合登录是 Host 用 Spring 装配的代码，不在插件 Context 里。
   - 它经 `ExternalHttpModules.forModule("platform-auth")` 取客户端，仍然只能调用 platform-auth 清单声明的服务。
   - 这条通道只给平台代码，业务插件经 `PluginContext` 取能力。
3. Host 目录按 `baseUrlRef` 取地址，不按方案写的 `id`。这样代码里用的 `id` 与部署地址分开，两个插件也可以共用一个目录项。
4. 目标检查在发送前解析一次地址，连接时 JDK 客户端还会再解析。两次之间 DNS 被改指（DNS rebinding）的情况拦不住，文档已写明。
5. `authPolicyRef` 只支持 `none`。需要凭证（API key、OAuth 客户端凭证）的外部服务要等 SecretCapability 上的认证策略，留到第一个需要它的插件。
6. 对共享环境的影响：部署后，"使用 Google 登录"改经新通道取公钥。`GOOGLE_OAUTH_CLIENT_ID` 为空时联合登录不启用，不受影响。
