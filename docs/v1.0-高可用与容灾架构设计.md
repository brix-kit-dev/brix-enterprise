# Brix Platform：高可用与容灾架构（占位文档）

> **版本**: v1.0（占位）  
> **日期**: 2026-04-26  
> **状态**: ⏸ MVP 阶段不实施 — 仅记录触发条件与设计要点  
> **关系**: 从 [v3.0.10-运行壳架构设计蓝图.md](./v3.0.10-运行壳架构设计蓝图.md) §15 抽离，避免污染主蓝图。

---

## 1. 决策与背景

**当前决策（2026-04-25）**：高可用与容灾**不在当前 MVP 范围**（v0.1 ~ v1.2）。

当前阶段以 **单可用区部署 + 应用层无状态 + 云厂商托管中间件（RDS / Redis / Kafka）默认 HA** 即可满足业务诉求，无需引入多活、跨地域容灾等复杂架构。

本文档为**占位文档**，待触发条件满足后正式扩写。

---

## 2. 重启设计的触发条件

出现以下任一信号时，重启高可用与容灾的设计与落地：

1. 单租户 SLA 要求高于 **99.9%**（年停机 < 8.76 小时）；
2. 接入金融、医疗、政务等强合规客户；
3. 出现跨地域客户的数据主权 / 合规诉求；
4. 发生过一次造成实质业务损失的可用性事件（事后复盘判定）。

任一触发条件满足后，由平台架构组负责正式启动本文档的扩写。

---

## 3. 占位要点（备忘）

未来设计需覆盖以下要点，避免遗漏：

- **可用性目标分级**：按服务关键度划分 P0 / P1 / P2 的 SLO（API 可用率、P99 延迟、RTO、RPO）。
- **多活架构选型**：同城双活 vs 异地多活 vs 单元化（按租户分片）的权衡矩阵。
- **数据备份与恢复**：自动备份策略、PITR（Point-in-Time Recovery）、跨区域复制、定期恢复演练。
- **故障转移**：组件级（Pod 健康检查、DB 自动选主）+ 站点级（DNS 健康检查、流量切换）+ 标准化 Runbook。
- **可观测性集成**：Prometheus（Metrics）+ Loki（Logs）+ Tempo（Traces）+ OTel Collector + Grafana 统一可视化与告警升级链。
- **租户维度 SLA**：单租户 QPS / 错误率 / 响应时间监控，支撑分级 SLA 商业化。

## 附录：术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| RTO | Recovery Time Objective | 故障恢复时间目标 |
| RPO | Recovery Point Objective | 数据恢复点目标（可接受数据丢失量） |
| 主从架构 | Active-Standby | 一主一备，故障时切换 |
| 双活架构 | Active-Active | 多站点同时服务，自动容灾 |
| 单元化 | Unit-Based | 按租户分片部署独立单元 |
| SLO | Service Level Objective | 服务等级目标 |
| SLA | Service Level Agreement | 服务等级协议 |
| PITR | Point-in-Time Recovery | 时间点恢复 |
