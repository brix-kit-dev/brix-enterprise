## 2. 改造目标

前端必须与后端运行壳保持同构原则: 后端能力由 Manifest/descriptor 声明并由 Host Shell 组合，前端能力也必须由 UI Manifest 或 Host Composition 声明并由唯一 Shared Runtime 组合。

目标形态:

- L3 Host 只负责静态装配、Runtime 单例提供、路由快照消费和 Runtime mount。
- L2B Shared Runtime / Router / Auth / Orchestrator 负责 Manifest 加载、校验、准入、运行时能力注入和安全上下文。
- L1 插件只声明 UI 能力并实现 `Page -> Hook/ViewModel -> Repository -> HttpCapability`。
- 平台管理前端 `platform-admin-web` 不再以 TypeScript route/menu 数组供 Host 直连组装，而是提供受校验的 UI Manifest / Platform UI Composition 声明。
- `http://localhost:3001/platform/login` 这类入口必须从已校验路由快照产生: Host 识别 public platform route, 选择 `Platform` 身份上下文, 注入 Auth/Http/UI Capability, 渲染登录 Page；Host 不直接导入页面、Hook、Repository 或手工判断平台角色。

## 4. 蓝图红线

前端分层:

- Page/View 不得 `fetch`、`axios`、拼 URL、直接 import Repository、解析 JWT 或读取裸 Token。
- Hook/ViewModel 不得构造传输 URL、访问浏览器全局凭证或绕过 Repository。
- Repository 只能经 Runtime 注入的 `HttpCapability` 或生成 typed Query client 访问后端。
- 允许依赖方向仅为 `Page -> Hook/ViewModel -> Repository -> Capability Contract`。

共享运行时:

- 每个 UI Host 只能有一个 React realm、Router、Auth、Theme、I18n、State 和 UI Contract。
- 官方/同 JS 权限域插件必须从 `@brix-sdk/shared-runtime-*` 和 Runtime SDK 获取能力。
- 插件不得打包第二份 React/Router，不得初始化第二套 Auth/OTel runtime。

路由与 Guard:

- 路由必须来自已校验的 UI Manifest 或 Host Composition。
- 业务代码不得拼装未知 remote。
- 无实现、无权限或缺 Host 能力时必须隐藏入口，不得加载空壳页面。
- Guard 只能依据 Auth Capability 返回的已验证 scope、permissions 和 session state 判定。
- Guard 不得解析 JWT，不得仅依赖角色字符串，不得把前端隐藏当成后端授权。

Platform / Actor / Subject / Bootstrap:

- Platform Token 只进入 `/platform/**` 正式控制面。
- Actor Token 只进入租户管理和业务上下文。
- Subject Token 不得进入 Actor 管理路由。
- `BOOTSTRAP_SETUP` 只进入显式 bootstrap/setup 路由。
- setup/reset/invite/bootstrap 相关安全 token 不得进入 localStorage、sessionStorage、日志、遥测、错误消息或持久化状态。

## 5. 当前代码偏差

### 5.1 Host 直连 `platform-admin-web` 路由和菜单

现状:

- `host-shell-standalone-web/src/App.tsx` 直接 import `createPlatformAdminPublicRoutes` 和 `platformAdminMenus`。
- `host-shell-standalone-web/src/config/routes.config.tsx` 直接 import `platformAdminProtectedRoutes`、`PLATFORM_ADMIN_PERMISSIONS`、`PLATFORM_ADMIN_ROUTES`、`PLATFORM_ROLE_CODE`。
- `platform-admin-web/src/module.ts` 以 TypeScript 数组声明 public/protected routes 和 menus。

偏差:

- 路由和菜单没有以 UI Manifest / Host Composition 作为唯一声明源。
- Host 被迫理解 platform-admin 的内部 route/menu 结构。
- 前端与后端 descriptor/Manifest 组合原则未完全对齐。

目标:

- `platform-admin-web` 提供 `ui-manifest.yaml` 或 platform 专用 `platform-ui-operational.yaml`。
- Host 只加载并校验 route snapshot，不 import platform-admin route/menu 数组。
- `platform-admin-web/src/module.ts` 只允许保留 manifest 生成的窄适配入口；迁移完成后删除硬编码 routes/menus。

### 5.2 Host 内存在平台角色/权限字符串准入判断

现状:

- `routes.config.tsx` 中 `isPlatformAdminUser()` 读取 `role`、`roles`、`permissions`，并据此决定 `/dashboard` 是否跳转 `/platform`。

偏差:

- Guard/route admission 不应由 Host 手写角色字符串判断。
- 蓝图要求 Guard 只依据 Auth Capability 返回的已验证 session/scope/permissions/context。

目标:

- Auth Capability 提供 `getVerifiedSession()` / `getActiveContext()` / `canAccessRoute(routePolicy)` 等稳定 API。
- Host 只把 route policy 交给 Auth/Router Capability 判定。
- 删除 `isPlatformAdminUser()` 及所有 Host 内 platform role/permission 常量依赖。

### 5.3 platform-admin Guard 解析 JWT

现状:

- `platform-admin-web/src/guards/auth-scope.ts` 调用 `auth.getToken()` 并通过 `atob`/`JSON.parse` 解码 JWT payload。
- `TenantAuthGuard.tsx` 等 Guard 消费 `isPlatformAccessToken` / `isTenantAccessToken`。

偏差:

- 蓝图明确禁止插件或 Guard 自行解析或 introspect Token。
- 裸 token 暴露给业务 UI 边界，削弱 Platform/Actor/Subject/Bootstrap 隔离。

目标:

- `AuthCapability` 返回已验证的认证上下文和 scope 分类。
- Guard 只读 `AuthCapability` 的验证结果，不接触 token 字符串。
- 删除 `auth-scope.ts` 与其测试，替换为 Auth Capability contract 测试。

### 5.4 本地插件 inline routes/menus 仍可绕过 UI Manifest

现状:

- `runtime-orchestrator-web/src/hooks/usePluginMenu.ts` 仍保留 `convertLocalPluginMenus()` 和 `convertLocalPluginRoutes()`，允许 `LocalPluginConfig` 内联声明菜单和路由。
- `host-shell-standalone-web/src/config/host.config.ts` 当前 local plugin registry 主要指向 `manifestUrl`，但类型和聚合逻辑仍允许无 manifest 回退。

偏差:

- UI Manifest 不是路由/菜单唯一入口。
- 本地开发路径可绕过 manifest/export/route/permission 双向一致性。

目标:

- local dev plugin 也必须提供 `ui-manifest.json`。
- 移除 inline routes/menus fallback。
- `LocalPluginConfig` 收缩为 identity、remoteEntry、manifestUrl、runtime range、health policy 等运行时元数据。

### 5.5 Manifest 加载和 remote health check 直接使用 browser `fetch`

现状:

- `runtime-orchestrator-web/src/hooks/usePluginDiscovery.ts` 的 `checkPluginHealth()` 直接 `fetch(remoteEntry)`。
- `runtime-orchestrator-web/src/services/manifest-loader.ts` 的 `checkPluginReachable()` 等 manifest 加载路径直接使用 browser `fetch`。

偏差:

- L1 业务数据访问必须经 `HttpCapability`；L2B manifest asset 加载虽然不等同业务 HTTP，但当前缺少显式 Capability 边界、DLP 约束和可观测策略。

目标:

- 新增或固化 `ManifestTransportCapability` / `RuntimeAssetFetchCapability`，仅用于匿名静态 manifest 和 remoteEntry 探测。
- 该能力禁止携带 bearer/refresh token，固定 timeout、cache、origin allowlist、trace 和错误脱敏。
- L1 插件代码仍严禁任何直接 `fetch`/`axios`。

### 5.6 `platform-admin-web` 公开导出内部 Page/Hook/Repository

现状:

- `platform-admin-web/package.json` 导出 `./pages`、`./hooks`、`./repositories`、`./constants`。

偏差:

- 外部消费者可绕过插件声明入口和运行时组装边界。
- Host 或其他插件存在直接导入内部页面/Hook/Repository 的制度性入口。

目标:

- 发布 API 只保留 package root、manifest identity、生成 contract 类型和必要测试 fixture。
- 删除 `./pages`、`./hooks`、`./repositories` 的公开 exports。
- 内部测试需要直连时使用包内相对路径或 test-only export，不能进入发布制品。

### 5.7 Platform public route session install 由 Host 回调耦合

现状:

- `App.tsx` 通过 `createPlatformAdminPublicRoutes({ onLoginSuccess })` 把 platform login 成功后的 session install 回调注入到 platform-admin 页面。

偏差:

- Host 参与 platform-admin 登录流程细节，破坏 Auth Capability 对 session 生命周期的统一所有权。

目标:

- 登录 Page 调用 Repository 后，只把稳定登录结果交给 Auth Capability。
- Auth Capability 负责 Platform session install、MFA challenge 内存态、token 生命周期和 context switch cleanup。
- Host 只响应 Auth/Router state 变化，不接触 access/refresh token。

### 5.8 页面错误边界存在内部错误泄漏风险

现状:

- `platform-admin-web/src/module.ts` 的 `RouteErrorBoundary` 将 `error.message` 直接渲染到页面，并 `console.error` 输出错误对象。

偏差:

- 蓝图要求用户可见错误不得暴露原始堆栈、内部类名、Token、完整安全 URL、PII 或 Provider 原始消息。

目标:

- Route chunk 失败统一映射为稳定安全错误。
- 页面只显示安全 message 和 traceId。
- 详细错误只进入受管日志，执行 DLP 规则。

### 5.9 发布制品门禁不足

现状:

- 已有 `ui-manifest.yaml`、shared runtime、MF 配置相关代码，但缺少统一的 route snapshot、manifest/export 双向一致、federation artifact identity、browser DLP、release artifact no-link 检查作为必过门禁。

偏差:

- 蓝图明确说明 grep、`pnpm why` 或单一 ESLint 不能证明 deployed bundle 的 runtime、route、permission 或安全上下文正确。

目标:

- 建立 frontend release gate: schema、route snapshot、runtime singleton、MF artifact、browser DLP、SCA/license/SBOM/signature/provenance、no `link:`/workspace release dependency。

## 6. 目标路由模型

### 6.1 声明源

所有前端路由只允许来自两类声明:

- L1 业务插件: `ui-manifest.yaml`
- 平台运维 UI: `platform-ui-operational.yaml` 或 Host Composition 中引用的受管 platform UI manifest

最小字段:

- module identity: `id`, `version`, `kind`, `owner`
- runtime range: React/Router/Auth/Theme/I18n/UI Contract/BOM range
- routes: `path`, `pageId`, `component`, `guardPolicy`, `authContext`, `permissions`, `requiredHostCapabilities`, `requiredViewMode`
- menus: `id`, `titleKey`, `icon`, `pageId`, `permission`, `order`
- pages: exported component id 与实际 federation expose / build export 双向一致
- security: token handling policy, referrer policy, DLP policy
- escape hatches: 专业组件、第三方 UI、独立 origin iframe 例外声明

### 6.2 Host 启动序列

1. Host 启动唯一 Shared Runtime。
2. Runtime 读取 Host Composition。
3. Runtime 发现 L1 UI Manifest 与 platform UI manifest。
4. Validator 校验 manifest schema、BOM range、permissions、routes、exports、requiredHostCapabilities。
5. Router Capability 生成 route snapshot。
6. Auth Capability 基于 verified session/context 过滤 route snapshot。
7. Host 渲染 route snapshot；无实现、无权限、无 Host 能力的入口不出现。
8. 页面加载时由 Runtime 注入 UI/Auth/Http/Query Capability。

### 6.3 `/platform/login` 示例

以 `http://localhost:3001/platform/login` 为例:

1. Browser 请求 Host 静态前端制品，Host 只提供单一 React/Router/Auth/Theme/I18n/UI Contract。
2. Router 从已校验 route snapshot 匹配 `/platform/login`。
3. route metadata 标记 `authContext=PLATFORM`, `guardPolicy=publicPlatformLogin`, `layout=minimal`, `referrerPolicy=no-referrer`。
4. Router 渲染 platform login Page，但 Host 不 import 页面文件；组件来自 manifest 声明的 expose 或构建期生成 route component registry。
5. Page 只绑定表单事件，调用 `usePlatformLogin()`。
6. Hook/ViewModel 管理 loading、field errors、server stable error、double-submit、cancel/unmount。
7. Repository 使用 Runtime 注入的 `HttpCapability.post()` 调用后端契约路径。
8. Auth Capability 处理 MFA challenge 或 Platform session install；token 不进入 query、storage、日志、telemetry 或 Host callback。
9. Router 根据 Auth Capability 的 verified session/context 跳转 `/platform/login/totp` 或 `/platform`。

## 7. 分阶段改造

### Phase 0: 只读盘点与门禁定义

交付:

- 生成当前 Host routes、platform-admin routes、plugin UI manifests 的 route inventory。
- 生成当前 direct import、direct fetch、JWT parse、public exports、inline local route/menu 的违规清单。
- 定义 `frontend-route-snapshot` 和 `frontend-layered-arch` 检查规则。

验收:

- `python3 scripts/validate_architecture_baseline.py --require-active --check-instructions` 通过。
- 清单列出所有违规文件、符号、导入关系和目标删除 Phase。
- 不修改运行时代码。

### Phase 1: Manifest 契约与 platform-admin UI 声明

交付:

- 新增 platform-admin UI manifest。
- schema 覆盖 route、menu、guardPolicy、authContext、permissions、requiredHostCapabilities、referrerPolicy。
- manifest 与实际 page exports 双向一致测试。

验收:

- platform-admin 所有 public/protected routes 可由 manifest 生成 route snapshot。
- `platform-admin-web/src/module.ts` 中 route/menu 数组标记为 deprecated，并由生成结果兼容输出。
- Host 行为暂不切换，避免一次性破坏运行时。

### Phase 2: Host 路由装配迁移

交付:

- Host 从 route snapshot 渲染 platform-admin 和业务插件路由。
- 删除 Host 对 `platformAdminMenus`、`platformAdminProtectedRoutes`、`PLATFORM_ROLE_CODE`、`PLATFORM_ADMIN_PERMISSIONS` 的依赖。
- 删除 `isPlatformAdminUser()`。
- `/dashboard` 默认跳转由 Auth/Router Capability policy 决定。

验收:

- `host-shell-standalone-web` 中无 platform-admin route/menu/role 常量 import。
- `/platform/login`、`/platform/login/totp`、`/platform/setup`、`/platform/bootstrap`、`/platform` 均来自 route snapshot。
- 无权限或缺 Host ability 时菜单和路由入口隐藏，不渲染空壳。

### Phase 3: Guard 与 Auth Capability 对齐

交付:

- Auth Capability 增加 verified platform/actor/subject/bootstrap context API。
- Platform/Tenant/Bootstrap/Setup Guard 只消费 Auth Capability 验证结果。
- 删除 `platform-admin-web/src/guards/auth-scope.ts` 和 `auth-scope.test.ts`。

验收:

- 前端 Guard 无 `atob`、`JSON.parse(jwt payload)`、`auth.getToken()`、scope 字符串手解码。
- Platform Token 不能进入租户 route；Actor/Subject Token 不能进入 `/platform/**`。
- setup/bootstrap/MFA challenge 只保留最短内存态，并通过浏览器 DLP 测试。

### Phase 4: L1 分层与公开 API 收缩

交付:

- 删除 `platform-admin-web/package.json` 的 `./pages`、`./hooks`、`./repositories` 发布 exports。
- 保留 package root、manifest/contract 类型和必要生成物。
- 新增或收紧 ESLint/architecture guard: Page 不得 import Repository, Hook 不得构造 URL, Repository 不得 direct fetch/axios。

验收:

- Host 和其他插件无法通过 package export 直接消费 platform-admin 内部页面、Hook、Repository。
- 所有用户可见 platform-admin 页面仍满足 `Page -> Hook/ViewModel -> Repository -> HttpCapability`。
- 测试报告必须显示非零测试数量，不能只接受 `BUILD SUCCESS` 或空跑。

### Phase 5: Runtime asset transport 与本地插件清理

交付:

- 引入 `ManifestTransportCapability` 或等价 Runtime asset fetch bridge。
- remoteEntry health check 和 manifest load 统一走 Runtime 受管 transport。
- 删除 inline local routes/menus fallback。
- local dev plugin 必须提供 `ui-manifest.json`。

验收:

- L1 插件无 direct fetch/axios。
- L2B manifest asset 请求不携带 bearer/refresh token，具备 timeout、origin allowlist、trace 和安全错误映射。
- `LocalPluginConfig` 不再允许声明 routes/menus。

### Phase 6: Federation 与发布制品门禁

交付:

- Host/Remote shared 配置由前端 BOM 生成。
- 检查 React/ReactDOM/Router `singleton=true`, `strictVersion=true`, `import=false`, no `eager=true`。
- 检查 federation manifest、构建产物、runtime 实例身份。
- 检查 release artifact 不含 `link:`、`workspace:*` 或绝对路径依赖。

验收:

- 浏览器运行时证明只有一个 React realm、Router、Auth、Theme、I18n、UI Contract。
- `pnpm why`、grep、ESLint 只能作为辅助证据，必须有 deployed bundle / artifact 证据。
- SCA、license、SBOM、signature、provenance 通过。

## 8. 验收门禁

每个实施 Phase 至少提供:

- 架构基线: `python3 scripts/validate_architecture_baseline.py --require-active --check-instructions`
- 分层检查: no Page direct Repository, no Hook URL, no Repository direct fetch/axios, no L1 raw token/JWT parse
- 路由检查: manifest schema, route snapshot, manifest/export/route/permission 双向一致
- Host 检查: Host 不 import L1 pages/hooks/repositories/route arrays/menus
- Guard 检查: Platform/Actor/Subject/Bootstrap context 隔离负例
- DLP 检查: setup/reset/invite/bootstrap/MFA token 不进入 storage、query、logs、telemetry、error UI
- Runtime 检查: 单 React realm、Router、Auth、Theme、I18n、State、UI Contract
- Federation 检查: singleton/strictVersion/import:false/no eager/BOM generated shared config
- Artifact 检查: lock integrity、license、SCA、SBOM、signature、provenance、no `link:`/workspace release dependency
- Test evidence: 报告必须包含非零测试数量和失败明细；不得以空跑或单一 grep 作为验收。

## 9. 停止规则

出现以下任一情况必须停止施工:

- 架构基线校验失败、hash mismatch、ACTIVE 版本冲突或 `rebaseRequired=true` 阻断验收声明。
- route manifest 与实际 export/permission 不一致。
- Host 仍依赖 L1 route/menu/internal page/hook/repository。
- Guard 仍解析 JWT 或读取裸 token。
- setup/bootstrap/MFA/reset/invite token 泄漏到 URL、storage、日志、遥测或错误 UI。
- 后端 Runtime Entry 缺失但前端仍显示入口或加载空壳。
- 测试报告为 0 tests，或只有辅助 grep/ESLint 没有 runtime/artifact/browser 证据。

## 10. 实施顺序建议

优先顺序:

1. Phase 0 先建立事实清单和自动化门禁。
2. Phase 1 先让 platform-admin 拥有声明式 UI Manifest。
3. Phase 2 再切 Host route assembly。
4. Phase 3 收口 Auth/Guard/token 生命周期。
5. Phase 4 收缩 L1 公开 API。
6. Phase 5 清理本地插件 fallback 和 Runtime asset transport。
7. Phase 6 补齐 federation/release artifact 证据。
8. Phase 7 删除旧代码和文件。

不得跨 Phase 删除代码；删除只在对应替代路径和验证证据已经存在后执行。
