## 2. 执行摘要

结论不是“现有 Guard 少了若干规则”，而是当前 `platform-devtools` 已经形成五套相互松散、来源不一致的守护机制：Java ArchUnit、前端 ESLint、JSON/YAML Schema、迁移扫描器和脚手架；它们没有共享机器可读的 requirement registry，也没有由 ACTIVE lock 驱动版本、适用 artifact、执行器和证据状态。

当前最严重的问题有四类：

1. **裁决源失真**：代码和文档同时保留 v3.0.7、v3.0.8、v3.0.9、“8 条”“9 条”“13 条”多套旧词汇；Java 入口仍明确提供 v3.0.9 profile 和“Host 可直接使用 Adapter/Spring”的旧裁决。
2. **证明能力失真**：以包名、目录名、类名和行数启发式代替 `moduleKind`、artifact graph、descriptor、启动期双向一致性和运行契约；大量 `allowEmptyShould(true)` 可在目标选中数为 0 时静默通过。
3. **规则接线失真**：存在“规则类和自测”，但没有接入 consumer profile 或 CI；部分核心规则实际上是占位永真规则。`BUILD SUCCESS` 只能证明 Guard 自测通过，不能证明被守护 artifact 对齐基线。
4. **生产者反向污染**：`create-brix` 仍生成 `module-manifest.yaml`、`startup-order`、Spring Controller/自动扫描/JPA Repository 装配以及违反 BrixUI 的前端代码，使脚手架持续制造 Guard 应该阻止的结构。

因此，当前程序应被定义为“若干历史负向检查与迁移扫描的集合”，不能定义为 v3.0.10 架构合规系统。可保留已经有价值的 forbidden API/依赖规则实现，但必须重建控制面、artifact 分类、执行器分工、测试证据和 CI 接线。

## 3. 范围与非目标

### 3.1 本次覆盖

- `packages/@brix/platform-devtools/architecture-guard`
- `packages/@brix/platform-devtools/eslint-config-architecture`
- `packages/@brix/platform-devtools/schemas`
- `packages/@brix/platform-devtools/clean-baseline-scan`
- `packages/@brix/platform-devtools/@brix/create-brix`
- 两仓库与上述工具相关的 Architecture CI、consumer `ArchitectureTest` 和 Host profile
- 必须由 Runtime/数据库/浏览器/发布系统承担、但目前被误认为可由静态 Guard 证明的门禁

### 3.2 本次不做

- 不修改 ACTIVE 蓝图或 lock 状态。
- 不在本文阶段修改 Guard 实现、Runtime、Host、业务插件或数据库。
- 不把 Guard 自测通过解释为真实 Host、数据库、Broker、浏览器或供应链验收。
- 不把架构守护硬编码为某个具体业务流程的正确性测试；具体业务只作为 ACTIVE 专项红线的验收样本，不能反向决定通用守护规则。
- 不一次性将所有历史模块强行切换为 fail-closed；每个 Phase 单独交付、验收后再进入下一 Phase。

### 3.3 架构守护通用性原则

架构守护的职责是验证任意具体业务是否符合 ACTIVE 架构设计，而不是替代业务模块自身的领域测试。通用 Guard 只能面向分层、artifact/moduleKind、Manifest/descriptor、Data Owner、事务、可靠消息、安全上下文、Host/Runtime 边界、前端调用链和发布证据等架构红线建立可复用规则。

当 ACTIVE 专项蓝图指定 `FIRST_OWNER`、平台超管、租户隔离等具名流程时，这些流程只能作为专项 acceptance fixture：用于证明通用机制和专项红线已经闭合，例如唯一 Data Owner、Owner 本地事务、跨 Owner 禁止 FK/JOIN/write、Outbox/Inbox 幂等、Platform Operational 最小权限和入口准入。Guard 不得把这些业务名词固化为所有业务都必须实现的规则，也不得用业务 happy path 代替架构边界负例。

## 6. 现有规则处置建议

### 6.1 保留并重新登记

以下实现模式可保留，但必须绑定具体 requirement id、artifact scope、正负例和 target cardinality：

- `NoDirectHttpClientsRule`、`NoMiddlewareClientsRule` 中明确的 forbidden API 检查。
- 对 `ApplicationContext`、`BeanFactory`、`CapabilityRegistry`、裸连接、线程、Scheduler、Spring MVC/Listener 的 bytecode 禁令。
- OSS → Enterprise 的跨仓库依赖/资源负向扫描。
- 固定 Manifest/descriptor 资源路径检查，但要升级为 artifact 级唯一性检查。
- ESLint 中 Page 不直连 Repository、Repository 不直用 fetch/axios、禁止 vendor UI import 的 AST 基础实现。
- `clean-baseline-scan` 作为迁移 inventory 工具继续存在，但输出不能记为 ACTIVE 合规证据。

### 6.2 必须重写

- `PluginProfile`、`HostProfile`、`OperationalProfile`、`SdkProfile`、`CommonsProfile`：改为 moduleKind/artifact-aware execution plan。
- Data Ownership：拆成 bytecode、Schema registry、SQL/migration、数据库权限和事务集成五类证据。
- Plugin Manifest/Operational descriptor Schema 与 validator。
- 前端 target selection、waiver、BrixUI、contract client、Federation artifact 门禁。
- 两仓库 workflow 与 consumer coverage 生成逻辑。

### 6.3 应退役

- `CoreProfileV2` 及所有 v3.0.9 Phase 命名。
- “Host relaxed profile”及允许 Host 源码直接使用 Adapter/Spring Container 的说明。
- `DataOwnershipRule.noCrossPluginRepositoryAccess()` 占位实现。
- 以已知插件包清单代替 artifact graph 的规则。
- 以行数/复杂度单独阻断架构 MUST 的规则。
- 把 `module-manifest.yaml` 当 ACTIVE 输入的 Schema、模板和文档。
- 仅靠文件名自动生效的 dev/pact 豁免。

### 6.4 移交到正确执行器

| 需求类型 | 责任执行器 | ArchUnit/ESLint 角色 |
|---|---|---|
| moduleKind、POM/pnpm DAG、OSS/商业边界 | artifact graph verifier | 只补充 import/bytecode 证据 |
| Manifest/descriptor 结构、唯一资源、版本/策略 | Schema + artifact validator | 只检查代码引用禁令 |
| Manifest ↔ Factory、SPI ABI、B0-B3、P0-P8/O0-O8 | Runtime startup validator + contract tests | 检查显式 forbidden API |
| Data Owner、SQL、migration、事务、Outbox/Inbox receipt | Schema registry + SQL lint + DB/故障集成测试 | 检查裸持久化 API 与跨 artifact 类型引用 |
| Federation、单实例 Runtime、路由快照、Guard/DLP | bundle validator + browser/Host E2E | 检查源码导入和调用形状 |
| SBOM、license、SCA、digest、签名、provenance | release/supply-chain gate | 不承担证明 |

## 7. 目标架构

### 7.1 单一控制面

建议新增机器可读 registry，例如：

`packages/@brix/platform-devtools/architecture-governance/requirements.registry.yaml`

每条 requirement 至少包含：

```yaml
id: BRX-RS-A-14
baseline: runtime-shell@3.0.10
scope:
  moduleKinds: [plugin-api, plugin-core, plugin-server, host, adapter]
owner: architecture-governance
executors:
  - artifact-graph
tests:
  positive: [module-kind-complete]
  negative: [missing-module-kind, name-only-classification]
enforcementStatus: missing-blocking
evidence: []
```

registry 必须由 ACTIVE lock 校验：未知版本、CANDIDATE 输入、漏掉适用专项、没有 owner/test/status、证据过期或 consumer coverage 不完整均失败。蓝图 clause 仍是规范 SSoT；registry 只是可执行映射，不能改写规范。

### 7.2 执行流水线

1. **Baseline Resolver**：校验 lock/hash/status，解析根蓝图与适用专项。
2. **Inventory Builder**：扫描 Maven/pnpm artifact、moduleKind、Manifest/descriptor、Composition、Host 和 UI artifact。
3. **Plan Compiler**：按 registry 为每个 artifact 生成必需执行器和规则，不允许 consumer 手工降级 profile。
4. **Executors**：Java bytecode、TS AST/type graph、Schema、artifact DAG、Runtime startup、DB/reliability、browser、supply chain。
5. **Evidence Aggregator**：输出稳定 JSON/SARIF/Markdown，记录 selected targets、通过/失败/缺失/豁免和证据定位。
6. **Acceptance Gate**：只有所有适用要求为 `enforced + passing` 且证据未过期，才允许进一步评估 Implementation Accepted；任何 missing/partial/failing/过期豁免均阻断。

### 7.3 结果状态

统一使用：

- `missing-blocking`：执行器、测试、接线或证据不存在。
- `partial`：只能证明要求的一部分。
- `failing`：执行器有效且发现违规。
- `waived-until`：满足 GOVERNANCE-013 的临时人工门禁；P0/P1 不得凭此进入 GA。
- `enforced-passing`：适用 scope、正负例、consumer coverage 与证据全部有效。
- `not-applicable`：由 registry + artifact metadata 计算，必须给出原因，不能由项目自行声明。

## 9. 分 Phase 改造计划

每次只实施并验收一个 Phase。当前 Phase 未验收，不得进入下一 Phase。

### Phase 0：冻结旧入口并建立可审计清单

**目标**：停止新增旧规则、旧模板和无登记豁免；不改变 consumer 的阻断结果。

**交付**：

- requirement registry 最小骨架，登记 A-1～A-26、S-1～S-11、FE/SA/T 红线和规范 MUST clause group。
- 当前所有 Java/ESLint/Schema/CI 规则的 `wired/unwired`、scope、target count、test、status 清单。
- 所有版本化旧术语标记为 `legacy/migration-only`。
- `create-brix` 对 legacy 模板给出 fail-fast 提示，禁止继续生成新违规项目。

**验收**：registry completeness test 能发现缺 id、owner、tool、test、status、evidence；未改变的缺口仍显示 `missing-blocking`，不得伪装成 PASS。

### Phase 1：Descriptor、moduleKind 与 artifact graph

**目标**：先解决“守护对象是谁、声明是什么”。

**交付**：

- 修正 Plugin/Operational/UI Schema；废止 ACTIVE `module-manifest.yaml`。
- Maven/pnpm/moduleKind inventory 与 artifact DAG verifier。
- Manifest/descriptor 固定路径、唯一资源、同 artifact provider 关联。
- 自动生成每个 artifact 的执行计划，移除手工 relaxed profile 选择。

**验收**：正负 fixture 覆盖缺 moduleKind、命名伪装、重复 Manifest/provider、Plugin requires internal contract、旧 routes/tasks 缺失、跨层/跨仓依赖与 DAG 环。

### Phase 2：Java 静态边界执行器

**目标**：将 ArchUnit 收敛为可靠的 bytecode 证明器。

**交付**：

- 按 moduleKind 重建 plugin-api/core/server、host、adapter、sdk、operational 静态规则。
- 移除永真/空目标规则；每条规则输出 target cardinality。
- 补齐 Spring 容器、L2B/internal、持久化、线程/资源、HTTP/中间件、Spring MVC/Scheduled 等负向 API。
- 退役旧 CoreV2/Host relaxed/硬编码插件包规则。

**验收**：每条 static requirement 有至少一个正例、一个独立负例和一个“目标为空必须失败”用例；所有适用 Maven artifact 被执行计划覆盖。

### Phase 3：Runtime 启动与 Operational 契约

**目标**：关闭静态工具无法证明的 A-5/A-17/A-24/A-25/A-26。

**交付**：

- Plugin/Operational SPI ABI、唯一 provider、descriptor ↔ Factory 双向一致性。
- P0-P8/O0-O8、B0-B3、统一 Host 入口代次、原子 Publish/Drain/Fatal、资源账本与逆序清理测试。
- platform-admin Composition、internal contract、allowlist、`/api/platform/**` 唯一 Dispatcher 测试。
- 根蓝图 GOVERNANCE-021/022 的正负契约矩阵。

**验收**：每个负例断言稳定诊断码、Host 不 Ready、五类入口均未错误发布、无资源残留；不能用 Spring Context/Controller/MockMvc 2xx 替代。

### Phase 4：Data Owner、事务与可靠消息

**目标**：关闭 A-8/A-10/A-13/A-15 与多租户 Owner 边界。

**交付**：Schema registry、SQL/migration lint、hash ledger、DB privilege test、Owner transaction + Outbox + Relay + Inbox duplicate/fault/receipt tests；以 `FIRST_OWNER` 仅作为 Multi-tenant 4.0 专项 acceptance fixture，验证 `platform-tenant` 唯一 Data Owner、`TenantAdministration` internal contract、Owner 本地事务、配额锁、Outbox 原子提交和 `platform-admin` 非租户成员边界，不把 `FIRST_OWNER` 固化为通用 Guard 业务规则。

**验收**：跨 Owner FK/JOIN/write、raw persistence、已发布 migration 修改、receipt 早于 commit、重复投递非幂等均被真实阻断；明确区分 PostgreSQL/目标数据库证据与内存测试。

### Phase 5：Frontend 与 Runtime/Host 边界

**目标**：关闭 FE-1～FE-12、A-7/A-18/A-19 及前端相关 S 组。

**交付**：完整 AST/type graph、generated client/HttpCapability、BrixUI、UI Manifest ↔ Federation exports/routes/permissions、匿名受治理 asset transport、Guard/DLP、route snapshot 和 Runtime identity tests。

**验收**：源码负例、构建制品负例、浏览器 Runtime/Host E2E 分别通过；不得用 ESLint 通过替代 deployed bundle/Host 证据。

### Phase 6：供应链、CI、豁免与证据聚合

**目标**：让每次 CI 结果可重放、可审计、可阻断。

**交付**：两仓库统一 evidence schema、SARIF/JSON 报告、consumer coverage、SBOM/license/SCA/lock/digest/signature/provenance、到期豁免门禁、release acceptance 汇总。

**验收**：漏执行 artifact、缺证据、过期豁免、未签名/未锁定制品均失败；只有 registry 中全部适用项 `enforced-passing` 才允许提交 Implementation Accepted 评审。

### Phase 7：脚手架与存量迁移

**目标**：保证新生成项目默认合规，并按 artifact 逐个迁移存量。

**交付**：新 Plugin/Operational/UI 模板、生成后 smoke/negative tests、legacy scanner 报告、按模块的迁移批次和到期计划。

**验收**：从空目录生成的最小插件能通过 Phase 1～6 的全部适用门禁；存量模块不得通过全局永久豁免一次性“绿化”。

### 11.2 每个 Phase 的最小证据标准

## 12. 风险与迁移策略

| 风险 | 处理方式 |
|---|---|
| 一次 fail-closed 暴露大量存量违规 | 先完成 Phase 0 inventory；按 artifact/requirement 分批，缺失始终保留 `missing-blocking`，不做永久全局豁免 |
| 新旧 Schema 双轨形成第二 SSoT | ACTIVE validator 只接受固定 Plugin/Operational/UI descriptor；旧格式仅由 migration scanner 读取 |
| Guard 重写再次复制蓝图文本 | registry 只映射稳定 clause id，版本由 lock 解析；禁止在规则注释中维护另一份红线全文 |
| 静态门禁误报 | 以 artifact metadata 缩小 scope；每条规则增加正例和 N/A 判定；人工豁免必须有到期与补偿控制 |
| Runtime/DB/browser 测试成本高 | 分层执行：PR 快速负例、nightly/merge 集成、release 真实 Host 与供应链；状态不可因执行慢而虚报 enforced |
| 两仓库规则漂移 | 规则与 registry 只在 OSS control package 定义；Enterprise 只消费已发布、hash-locked 版本和自身证据 |

## 13. 最终裁决与验收清单

当前裁决：**架构守护程序与 ACTIVE v3.0.10 基线存在系统性偏差，必须改造；现有结果只能作为局部静态/AST 自测证据，不能作为 Runtime Shell 架构合规证明。**

进入 Implementation Accepted 评审前，至少必须满足：

- [ ] ACTIVE lock 驱动唯一 requirement registry，根蓝图和三个专项全部映射。
- [ ] 每条要求有 id、scope、owner、executor、test、status、evidence。
- [ ] 所有 Brix artifact 以 moduleKind/descriptor/artifact graph 分类，无手工 relaxed profile。
- [ ] 无空目标静默 PASS、永真占位规则和未接线却标 PASS 的规则。
- [ ] Plugin/Operational/UI Schema 与固定资源路径、SPI/provider/factory 双向一致。
- [ ] B0-B3、五类入口原子发布/摘除、Fatal/Drain/资源清理有启动契约证据。
- [ ] Data Owner、事务、migration、Outbox/Inbox 有数据库与故障证据。
- [ ] Frontend 源码、Federation 制品、浏览器 Runtime/Host 证据分别成立。
- [ ] Super Admin 与 Multi-tenant 专项红线全部有独立证据。
- [ ] SBOM/license/SCA/lock/digest/signature/provenance 发布门禁有效。
- [ ] `create-brix` 新生成项目不再产生 legacy/违规结构。
- [ ] 两仓库 consumer coverage 为 100%，所有过期豁免自动失败。

在上述条件关闭前，正确状态是 `missing-blocking` / `partial` / `failing`，不得标记 `enforced`、Implementation Accepted 或 GA。
