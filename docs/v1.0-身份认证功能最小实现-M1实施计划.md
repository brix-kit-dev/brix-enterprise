> **文档类型**：实施计划（非规范）。权威顺序低于 ACTIVE 根蓝图与专项蓝图；冲突时以蓝图为准，并停止施工、回报冲突。
> **依据基线**：runtime-shell 3.2.0（根）、identity-auth 1.0、multi-tenant 5.1、super-admin 4.0、frontend 1.2（均为 ACTIVE）
> **决策背景**：[RFC-002](./rfc/RFC-002-身份认证-统一登录架构与认证专项（Draft）.md) 第 9 节与附录 C

> **状态**：切片 0 完成；切片 1、2 已部署到共享环境（2026-10-24），待负责人验收（见第 9 节）

## 1. 目标与验收

身份认证专项 §13 的 M1：身份提供方 Adapter、托管登录（先识别账号、密码 + TOTP、选租户、setup）、BFF 会话；员工登录 → 选租户 → 进入控制台；平台控制台迁入。

M1 验收门禁：IA-1、IA-2、IA-6；浏览器不出现 Token（根 S-20、前端 FE-13）；端到端流程。每次只实施一个最小垂直切片，当前切片验收后再进入下一个。

## 2. 现状（2026-10-23 盘点）

- 登录全部是控制台内的表单；登录接口在响应体返回 Token，前端存在 sessionStorage 并以 Bearer 头发送。
- 没有授权服务器、OIDC 端点、托管登录页、BFF、会话 Cookie、passkey；刷新 Token 没有对外接口，也没有重放检测。
- `EndpointResponse` 不能设置响应头，所以 BFF 端点必须落在身份协议面（根 `BRX-RS-SECURITY-011` 的唯一例外），不能做成插件 Runtime Entry。
- CORS 默认允许任意来源携带凭证；改用 Cookie 会话前必须改为同源。
- 可复用：身份模型（`sys_identity` 等）、`TotpCapability`、`PasswordCapability`、`ContextSelectionTicketService`、员工所属租户发现、RSA 签名密钥、前端 `AuthCapabilityImpl` 与控制台布局、`infra-adapter-redis`。
- Spring Boot 4.1.1 管理的 Spring Security 7.1.1 自带 `spring-security-oauth2-authorization-server` 与 `spring-security-webauthn`；首次使用需联网下载。

## 4. 切片 1：员工单租户登录闭环

**可见结果**：员工在员工控制台点登录 → 跳到托管登录页 → 账号 → 密码 → TOTP → 只属于一个租户时自动进入员工控制台，页面显示租户、身份与有效权限；浏览器里没有任何 Token。

**后端**

1. 新建 L2C 模块 `infra-adapter-identity-provider`（brix）：内嵌 Spring Authorization Server；独立的安全过滤链只匹配 `/oauth2/**`、`/.well-known/**`、`/auth/**`、`/bff/**`，不影响 `/api/**`；只经 L2A 契约访问身份与租户数据（`BRX-IA-LAYER-001`）。
2. 客户端注册：`tenant-console`，机密客户端，授权码 + PKCE（S256），redirect URI 精确登记。
3. 托管登录后端：先识别账号（账号不存在时流程、响应与耗时不可区分）→ 密码 → TOTP（员工一律 `brix:aal2`）→ 登录期发现（`discoverActor`）：1 个上下文自动选中，0 个提示"尚未加入任何租户"。
4. Token 定制：沿用 multi-tenant §8 的 Actor Token claims，增加 `acr`、`amr`、`auth_time`、`sid`；签名密钥增加 `kid` 并发布 JWKS；Token 内不带权限列表（T-30）。
5. BFF：`/bff/login`、`/bff/callback`、`/bff/session`（身份、上下文、有效权限，有效权限来自 Runtime 授予表）、`/bff/logout`；Token 加密存 Redis；浏览器只持有 `__Host-` 前缀、`HttpOnly`、`Secure`、`SameSite` 会话 Cookie。
6. Dispatcher 会话认证：`/api/**` 请求带会话 Cookie 时，从 BFF 会话取 Access Token 并按现有校验链验证；改变状态的请求校验 CSRF 自定义请求头。
7. CORS 改为同源。

**前端**

8. 托管登录前端模块（platform-commons 下独立模块，由身份协议面在 `/auth/**` 提供）：账号页、密码页、TOTP 页、"尚未加入任何租户"页；BrixUI；严格 CSP 与 `frame-ancestors 'none'`；禁止第三方脚本。
9. 员工控制台外壳（最小）：未登录跳 BFF；登录后显示租户、身份、有效权限；退出。
10. 本地开发代理增加四个保留前缀的转发。

**测试**：IA-1（端点清单无"凭证换 Token"的员工入口，豁免项除外）、IA-2（控制台制品无凭证输入）、IA-6（三类 audience 互不接受）、S-20（响应、URL、Cookie、浏览器存储中无 Token 的端到端检查）。

## 5. 跨切片要求与待定事项

- **移动端**：托管登录页与员工控制台按移动优先实现；响应式折叠属于 Shell 层（frontend 1.2 §3.4），断点取设计令牌。
- **HTTPS 与域名**：`__Host-`/`Secure` Cookie 和 WebAuthn 都要求安全上下文。经 SSH 隧道访问 `localhost` 可以开发测试；手机经公网 IP 的 HTTP 访问无法使用新登录；正式测试需要域名 + HTTPS。

### 7.2 契约变更（L2A Minor，向后兼容，均为默认方法或可选字段）

- `JwtIssuerCapability`：`issueActorAccessToken(request, AuthenticationContext)`、`issueOidcIdToken`、`publicJwkSet`；旧方法与旧 Token 有效期不变（豁免期内的旧流程继续使用）。
- `IdentityAccountCapability`：`isTotpEnabled`、`verifyTotp`（TOTP 只在身份 Owner 内校验，密钥不出 Owner）；`TotpCapability.matchTimeStep`。
- `AccessDecision.effectivePermissions`：Dispatcher 随授权结果交给 Handler 的"当前上下文全部有效权限"（同一授予表），用于落实 multi-tenant 5.1 `BRX-TENANT-AUTHZ-009`；接口本身的授权判定仍只含它声明的权限。沿用 `BRX-TENANT-CONTRACT-007` 的 L2A Minor 方式，未新增 Capability；**需负责人确认后在下一版专项蓝图中登记**。
- platform-tenant 新增只读 Endpoint `GET /api/tenant/session`（`tenant-actor`，`tenant:profile:read`）。
- 数据：platform-identity `V003` 增加 `sys_identity.mfa_last_used_step`，同一 TOTP 验证码只能用一次（RFC 6238 §5.2）。

### 7.3 端到端验证（2026-10-23，临时隔离环境）

用新构建的主机 jar 在临时 Postgres/Redis/MinIO 容器上启动（启用身份提供方，issuer 为 `http://localhost:13001`），前端开发服务器 13001 端口，测试员工（MEMBER，密码 + TOTP）经 Playwright（手机视口）走完：匿名访问 `/tenant` → 托管登录 → 错误密码统一提示 → TOTP → 回到 `/tenant` 显示租户、身份与有效权限（MEMBER：`app-booking:template:read`、`tenant:member:read`、`tenant:profile:read`）→ 会话 Cookie 为 `__Host-`/HttpOnly/Secure/SameSite=Strict → 浏览器收到的 40 个响应、Cookie 与存储中均无 JWT（S-20）→ 同源 API 经会话认证、缺 CSRF 头的写请求返回 403 → 退出后 BFF 会话与登录会话都结束。共 16 项检查全部通过。

验证中发现并修复的既有问题：platform-tenant 的 `findMembershipByContextId`/`findPrincipalshipByContextId` 与 `IdentityValidationFilter` 在没有租户上下文时被租户 SQL 守卫拒绝（前者补只读跨租户声明，后者改为按 Token 的租户校验成员/主体），否则任何带 `mid`/`cid` 的员工 Token 调用 `/api` 都会返回 500。

## 8. 切片 2 实施记录（2026-10-23）

**可见结果**：属于多个租户的员工在托管登录页选择租户后进入员工控制台；控制台首页的"切换租户"可切到同一身份的其他租户，不用再输入密码；退出后 BFF 会话、Refresh Token 与登录会话全部结束。

### 8.1 已实现

| 计划项 | 实现 | 证据 |
|---|---|---|
| 多租户选择页 | TOTP 通过后有 2 个及以上 ACTIVE Actor 上下文时进入"选择租户"：每个选项是一次性 selection ticket（256 位随机，只存 SHA-256 摘要，5 分钟有效），绑定本次登录事务、身份与签发批次；页面只显示租户名、编码与成员类型，浏览器拿不到 contextId（multi-tenant 5.1 §9.3）；票据重复使用返回 409 `ticket_used` 并审计 `identity.login.ticket_replayed`，失效返回 401 `ticket_invalid`，页面自动换新票据；按身份限流（15 分钟 10 次） | `staffOfSeveralTenantsChooseWithOneTimeTicketsAndNeverSeeContextIds`、`SelectionTicketsTest`、`HostedLoginApp.test.tsx` |
| 切换租户 | `POST /bff/switch`（校验 `X-Brix-CSRF`）：目标必须是同一身份的另一个 ACTIVE Actor 上下文（T-26），否则 403 `context_not_available`；BFF 为本登录会话（`sid`）登记一次性切换意图后发起带 `prompt=none` 与 `brix_context` 的授权请求，身份协议面只在用掉匹配意图时于登录会话内换成目标上下文并签发新 Token（登录会话 Cookie 为 SameSite=Lax，跨站链接单独无法触发切换），有效权限按新上下文重新计算；新 BFF 会话建立后撤销旧会话的 Refresh Token；登录会话已结束时（`login_required`）转为正常登录 | `aSwitchSilentlyReauthorizesForAnotherContextOfTheSameIdentity`、`contextsOfAnotherIdentityCanNeverBeSwitchedTo`、`anotherSiteCannotSwitchTheContextOfALoginSessionWithACraftedLink`、`aSilentSwitchWithoutALoginSessionGoesThroughLoginAgain` |
| Refresh Token 重放 | 已轮换的 Refresh Token 再次出现时撤销整个授权（Family）并结束对应登录会话（`sid`），只能重新登录；审计 `identity.token.refresh_replay` | `reusingARotatedRefreshTokenEndsTheWholeFamilyAndTheLoginSession` |
| 全面注销 | `/bff/logout` 撤销 Refresh Token、删除 BFF 会话、撤销 `sid` 并结束登录会话；`sid` 已撤销或超过绝对时长（默认 12 小时）的登录会话在下一次请求时结束，不再签发 Token | 端到端"退出后登录会话也结束" |
| 前端 | `/bff/session` 增加 `contexts`（当前身份的全部 ACTIVE Actor 上下文）；platform-auth-web `BffTenantCapability` 以 BFF 会话实现 `TenantCapability`（可用上下文、切换），只跟随同源跳转；platform-tenant-web `useActorContexts` 与首页"切换租户"卡片；托管登录"选择租户"页 | `BffSessionAuthState.test.ts`、`TenantConsoleHomePage.test.tsx`、runtime profile 测试 |

### 8.2 接口变更

- 无 L2A 契约变更。
- 身份协议面新增 `POST /auth/api/select`、`POST /bff/switch`；`/bff/session` 增加 `contexts`；授权请求自定义参数 `brix_context` 只在已有登录会话且 BFF 登记了对应切换意图时生效，签发前再次核对它与登录会话的上下文一致。

### 9.2 部署后修正

| 问题 | 修正 | 证据 |
|---|---|---|
| 旧平台登录连续失败 5 次，会把整个身份置为 `LOCKED`。托管登录和 `tenant-console` 的 Token 签发只接受 `ACTIVE`，所以平台入口的锁也挡住了员工入口；托管登录又从不解锁，锁过期后照样挡着。共享库唯一的员工就是这样：10-21 被锁，15 分钟的锁早已过期，却一直无法用新登录。这不符合根 `BRX-RS-SECURITY-014`：锁只作用于发生失败的入口和凭证，并且到期自动解除 | 员工入口接受 `ACTIVE` 和 `LOCKED`（本入口自己按"账号 + 来源"限流），仍拒绝 `PENDING_SETUP` 和 `DISABLED`，答复与密码错误相同（IA-7）。两个因素都通过后，清除已经过期的锁，与旧登录一致。续期按同一规则，平台入口的锁不再结束员工会话（brix `8fd99e0`） | `aLockSetByAnotherEntryDoesNotKeepStaffOut`、`anExpiredLockIsClearedOnlyAfterBothFactors`、`identitiesThatAreDisabledOrNotSetUpNeitherSignInNorRenewTokens` |
| 非 clean 构建会把以前的 UI 打包文件一起打进 jar；没先构建 UI 时 jar 里没有 UI，构建却照常成功 | 每次构建先删掉上次的 UI 文件；部署构建加 `-Dbrix.requireHostedLoginUi`，没有 `dist/` 时直接失败（brix `42b5fae`） | 实测三种情形：无 UI 的普通构建通过；无 UI 的部署构建失败；有 UI 时 jar 与 `dist/` 完全一致 |
| `start-frontend.sh --force` 只停 pnpm，rspack-node 留下来占着 3001；按端口清理的匹配从不生效 | 停整个进程组，先核对 PID 仍在应用目录下运行，防止重启后误停别的程序；按 `ss -Hltnp` 找占端口的进程，并等待端口释放（brix-enterprise `cc8e60a`） | 临时进程组实测 |

旧平台登录在 EX-2026-002 期间仍按身份加锁；锁住期间，旧的平台入口和 FIRST_OWNER 受邀页的旧接口（EX-2026-001）仍会拒绝该身份。切片 3、4 删除这些旧接口后，就不再有地方设置 `LOCKED`。"限流取代锁定"和 IA-5 门禁按身份认证专项 §13 在 M2 验收。
