## 0. 结论与施工时机

现在是规范化 Outbox 调用链的合适时点。

`platform-admin` 完成 operational 化后，上游调用边界已经收敛为：

```text
L2B Dispatcher
  -> platform-admin Handler
  -> OperationalContext
  -> allowlist internal contract
  -> 唯一 Data Owner 本地事务
```

Outbox 应当在这个稳定边界之后、Bootstrap/FIRST_OWNER 流程继续扩大之前完成最小可靠闭环。这样可以避免 Phase 5/6 继续依赖当前的 Repository 直写、L2C AOP 和 Kafka 专用 Outbox，降低后续迁移成本。

施工顺序建议冻结为：

1. 先完成并绑定现有 Phase 4 的独立验收 commit 和证据，不把未提交工作树状态视为 Accepted；
2. 暂停进入会新增 CRITICAL/STANDARD Event 的业务切片；
3. 完成本计划 M0-M4，打通 `TenantFirstOwnerAccepted` 的 Producer Outbox、Relay、Consumer Inbox 最小闭环；
4. 再继续 Bootstrap/FIRST_OWNER 主计划的 Phase 5/6；
5. M5 补齐 typed Command 共用链路后，才可声称根蓝图 A-10 整体合规。

如 Phase 5 不新增 Integration Event，可在组织上并行准备领域逻辑和测试夹具，但不得与 Outbox Runtime 公共模块同时形成不可独立验收的混合提交。

## 1. 目标与非目标

### 1.1 本次目标

1. 建立唯一、显式、可验证的可靠事件调用链；
2. 将可靠性决策从 L2C AOP 和事件类注解迁移到 Manifest + L2B Runtime 策略；
3. 保证 Owner 业务写与 canonical Outbox record 在同一本地事务中提交或回滚；
4. 保证 Relay 只处理已提交记录，崩溃恢复后不会丢失待投递事实；
5. 接受 Relay 重复发送，以 Consumer Owner 持久化 Inbox 消除重复副作用；
6. 保持插件只依赖 L2A Capability Contract，不感知 Kafka、Topic、轮询器或 CDC；
7. 保持 Outbox/Inbox 表由唯一 Data Owner 拥有，L2B Relay 仅作为最小权限 Custodian；
8. 用一个真实 CRITICAL Event 完成事务、崩溃、重复投递和重放验证；
9. 为 typed Command 复用同一 canonical message substrate 预留结构，但不在首个切片中实现完整命令结果工作流；
10. 建立足以支撑 Brix 底座的最小监控、parking lot 和人工重放能力。

### 1.2 本次非目标

本次不做：

1. 不声明 Exactly Once，不引入 XA/2PC 或跨 Owner 分布式事务；
2. 不承诺全局顺序，只允许相同 `partitionKey`/aggregate 范围内的顺序策略；
3. 不在首个切片引入 Debezium、数据库逻辑复制或 CDC 运维体系；
4. 不同时落地 Kafka、RabbitMQ、SQS 等多个 Broker Adapter；
5. 不建设 Outbox 管理 UI、复杂搜索、批量编辑或业务补偿平台；
6. 不批量迁移全部历史 Integration Event；
7. 不把 Domain Event 统一改造成 Integration Event；
8. 不用 Event Sourcing 替代现有业务模型；
9. 不把邮件通知纳入本 Outbox；邮件事务语义继续由活动通知计划唯一声明；
10. 不允许插件直接调用 Outbox Repository、Relay、KafkaTemplate 或 Broker SDK；
11. 不允许 `platform-admin` 或 internal contract consumer 直接写 Data Owner Outbox；
12. 不以单元测试 mock 到一次 `repository.save()` 作为可靠消息闭环证明。

## 3. 当前实现基线与差距

### 3.1 可保留资产

| 资产 | 当前价值 | 处置 |
|---|---|---|
| `EventBusCapability` | 已形成插件可见 L2A 发布入口 | 保留入口，修正可靠性契约和 L2B Provider |
| Manifest `data.storageId/outbox/inbox` | 已能声明 Owner canonical 表 | 保留并补启动期一致性校验 |
| `platform_tenant_outbox/inbox` | 已建立 Owner 自有表名和迁移起点 | 以前滚 migration 补齐 canonical 字段和约束 |
| `FirstOwnerInvitationService` 同事务写业务与 Outbox | Producer 原子性方向正确 | 改为调用 Owner-scoped `EventBusCapability`，删除业务服务对 Outbox Repository 的直接依赖 |
| Kafka Adapter | 已有 Broker 发送、Topic 解析和基础指标 | 降为 L2C transport，不再拥有可靠性策略和 canonical Outbox |
| Outbox 失败/重试测试样例 | 可复用部分测试夹具 | 重写为真实事务、并发 claim、崩溃和重复投递测试 |

### 3.2 必须关闭的差距

| ID | 当前证据 | 风险 | 目标 |
|---|---|---|---|
| O-01 | `EventBusCapability` 对全部 Integration Event 笼统声明 at-least-once | BEST_EFFORT 语义与根蓝图冲突 | 按 Manifest reliability 分级 |
| O-02 | `CriticalEventOutboxAspect` 在 L2C 通过 AOP 决定可靠性 | 策略隐式、可因 Bean/AOP 未激活而静默直发 | L2B 显式策略代理，缺失依赖 fail-fast |
| O-03 | `infra-adapter-kafka-outbox` 使用全局 `event_outbox` | 绕过 Owner `storageId` 与 canonical 表所有权 | 只使用 Owner `{storage_id}_outbox` |
| O-04 | Outbox Publisher 同时持有 JPA 与 Kafka | L2C 把事务协调、Relay 和 Broker 实现耦合在一起 | L2B 协调，L2C 分别映射存储与 transport |
| O-05 | `processOutbox()` 在数据库事务中同步等待 Kafka | 长事务、锁放大、恢复语义不清 | 短 claim、事务外发送、短 finalize |
| O-06 | 当前 claim 缺少可恢复 lease | 进程在 PROCESSING 状态崩溃可能形成永久滞留 | `claimOwner/claimUntil` 到期可回收 |
| O-07 | Broker ack 后数据库状态提交失败 | 事件会重复发送 | 明确 at-least-once，并由 Inbox 去重 |
| O-08 | `platform_tenant_outbox` 缺少完整 canonical envelope 字段 | scope、producer、causation、W3C trace 不可完整恢复 | 前滚补齐根蓝图字段 |
| O-09 | `ManifestDrivenEventDispatcher` 默认进程内 Map 去重 | 重启、扩容和并发时重复副作用 | Consumer Owner 持久化 Inbox |
| O-10 | Consumer 去重与业务 Handler 不在同一事务 | Inbox 成功但业务失败，或业务成功但 Inbox 丢失 | Inbox insert、业务写、结果 Outbox 同 Owner 本地事务 |
| O-11 | Manifest event declaration 只有 id/version | 无法声明 reliability、retry、idempotency 和 handler policy | 扩展 Schema/模型/启动校验 |
| O-12 | 现有测试主要为 mock/分支测试 | 不能证明提交、回滚、崩溃和重复语义 | Testcontainers/真实 DB + fake transport fault tests |

当前 `V021__phase3_first_owner_internal_contract.sql` 是否允许改写，必须由环境账本、发布 commit 和 migration hash 证明。无法证明“从未进入共享/保留环境”时，只能新增单调前滚 migration，本计划不预设具体版本号。

## 4. 国际实践对齐与 Brix 取舍

### 4.1 共同基线

AWS Transactional Outbox 指南明确指出，业务数据库写与消息发送是不可安全组合的 dual write；应在同一数据库事务写业务状态和 Outbox，由独立进程发送，且消费者必须处理重复消息。Microsoft Azure Architecture Center 采用相同边界，并强调后台 worker/change feed、重复投递和幂等处理。Debezium Outbox Event Router 进一步验证了唯一 event ID、aggregate/event key、Outbox 专用捕获和 trace context 的可操作性。

Brix 采用这些共同原则：

1. 原子边界是 `business state + outbox record`；
2. Broker send 必须发生在业务事务提交后；
3. Producer 不因 Broker 暂时不可用而丢失已提交事实；
4. Relay 必须允许崩溃恢复和重复发送；
5. Consumer 必须以稳定 message ID 持久化去重；
6. 相同 aggregate 的顺序通过稳定 `partitionKey` 表达；
7. 可靠性是端到端属性，不能由 Producer Outbox 单点宣称。

### 4.2 当前阶段的最小取舍

| 设计点 | 本阶段选择 | 原因 |
|---|---|---|
| Relay 机制 | 数据库 polling + lease | 运维面最小，易于故障注入；CDC 延后 |
| 交付语义 | at-least-once | 可被数据库/Broker/Consumer 共同证明 |
| 去重位置 | Consumer Owner canonical Inbox | Broker 去重不能替代业务副作用幂等 |
| 顺序 | 相同 `partitionKey` 尽力保持 | 不承担全局顺序成本 |
| Transport | 先复用 Kafka Adapter | 验证 L2C 可替换边界，不同时建设多 Broker |
| 状态管理 | `PENDING/IN_FLIGHT/PUBLISHED/PARKED` + lease | 足够支持并发、恢复、告警和人工重放 |
| 管理能力 | 指标、结构化日志、受控 CLI/运维动作 | 暂不建设 UI |
| Payload | canonical envelope + JSON payload | 与当前 Java/JPA/PostgreSQL 基线兼容 |

## 5. 唯一目标调用链

### 5.1 Producer 主链

```text
HTTP / Query / Command / internal contract Runtime Entry
  -> L2B Dispatcher / Gateway
  -> Owner Handler / Owner application service
  -> Owner local Unit of Work begins
  -> business writes
  -> Owner-scoped EventBusCapability.publishIntegration(event)
       -> L2B Reliable Event Policy
          1. resolve producer plugin identity
          2. validate Manifest publishes declaration + schema + reliability
          3. validate active Owner Unit of Work for CRITICAL/STANDARD
          4. build immutable canonical Event Envelope
          5. resolve Manifest storageId and canonical outbox registration
          6. append Outbox record through current Owner Unit of Work
  -> Owner audit write
  -> commit business + audit + Outbox atomically
  -> caller receives local business result
```

这里没有 `Plugin -> Adapter -> Plugin API` 的反向调用。正确依赖方向是：

```text
L1 Plugin
  -> L2A EventBusCapability
     -> L2B policy proxy / ReliableMessageCoordinator
        -> L2C persistence protocol mapping
```

插件只表达“发布什么事实”；L2B 决定“是否必须持久化、写入哪个 Owner canonical Outbox、何时允许返回”；L2C 只实现数据库协议，不向插件暴露 Repository、连接或动态表操作。

### 5.2 Relay 主链

```text
L2B OutboxRelay managed task
  -> Schema Registry enumerates registered Owner outboxes
  -> L2C canonical store atomically claims due rows
       PENDING -> IN_FLIGHT
       set claimOwner / claimUntil / attemptCount
  -> claim transaction commits
  -> L2B resolves event contract, subscriptions and transport route
  -> L2C Broker Adapter publishes canonical envelope
  -> Broker confirms acceptance
  -> L2C canonical store short transaction:
       IN_FLIGHT -> PUBLISHED
       set publishedAt
```

失败路径：

```text
send failed
  -> retry budget remains:
       IN_FLIGHT -> PENDING
       availableAt = backoff + jitter
       record stable error class/code
  -> retry budget exhausted or permanent schema/routing error:
       IN_FLIGHT -> PARKED
       emit alert + audit evidence

process crashed after claim
  -> claimUntil expires
  -> another Relay instance reclaims row

broker accepted but finalize failed
  -> lease expires
  -> row is sent again with the same eventId
  -> Consumer Inbox removes duplicate side effects
```

### 5.3 Consumer 主链

```text
Broker Adapter receives canonical envelope
  -> L2B Event Dispatcher
     1. validate envelope and schema compatibility
     2. resolve Manifest subscription and stable handlerId
     3. reconstruct immutable EventInvocation context
     4. open Consumer Owner local Unit of Work
     5. insert canonical Inbox(handlerId, eventId)
        -> unique conflict: duplicate, skip Handler and commit/ack
     6. invoke Handler
     7. write Consumer Owner business side effects
     8. append any resulting Event Outbox records
     9. commit Inbox + side effects + resulting Outbox
  -> only after commit succeeds: acknowledge broker delivery
```

Handler 失败时必须回滚 Inbox insert 与业务副作用，使 Broker/Runtime 能够安全重试。业务成功但 broker ack 丢失时，重复投递由 `(handlerId,eventId)` 唯一键收口。

### 5.4 internal contract 与 Outbox 的关系

internal contract 是平台运维写入 Data Owner 的受限入口，不是 Outbox API：

```text
platform-admin
  -> OperationalContext.requireInternalContract(...)
  -> TenantAdministration provider
  -> platform-tenant local transaction
  -> business write
  -> Owner-scoped EventBusCapability
  -> canonical Outbox append
```

以下路径全部禁止：

```text
platform-admin -> PlatformTenantOutboxRepository
platform-admin -> OutboxRelay
internal contract DTO -> Outbox entity / table / transaction handle
Plugin -> infra-adapter-kafka-outbox
Plugin -> KafkaTemplate / topic
L2C AOP -> 静默改变可靠性
```

## 6. 分层职责

| 层 | 负责 | 禁止 |
|---|---|---|
| L1 Data Owner Plugin | 事实 Schema、业务时机、payload、partitionKey、业务事务、Outbox/Inbox migration 所有权 | Broker SDK、Topic、Relay、跨 Owner 表、直接依赖 L2B/L2C |
| L2A Contract | `EventBusCapability`、可靠性枚举、immutable Event Envelope/Invocation、稳定错误 | Registry、Repository、Poller、Broker client |
| L2B Runtime | Manifest 校验、可靠性策略、envelope 构造、UoW 感知、Outbox/Inbox 协调、Relay、Dispatcher、retry/parking/readiness | 读取 Owner 业务表、包含 Kafka/Rabbit 厂商逻辑 |
| L2C Persistence mapping | canonical 表 append/claim/finalize、数据库方言、连接和最小权限 | 决定业务可靠性、读取业务表、暴露 raw handle |
| L2C Broker Adapter | canonical envelope 到 Broker record 的映射、发送确认、消费和 ack/nack | 拥有 Outbox 表、决定 Handler、重写 eventId |
| L3 Host | 静态组装 L1/L2B/L2C 和 Profile | 业务分支、Outbox Service、Repository、Topic 配置硬编码 |

Outbox/Inbox 表仍由 Data Owner 拥有。L2B Relay 和受管持久化实现只是 Schema Registry 明确登记的 Custodian，只获得所需表和操作的最小权限。

## 7. 最小契约与数据模型

### 7.1 可靠性声明

Manifest `events.publishes[]` 最少增加：

```yaml
events:
  publishes:
    - id: TenantFirstOwnerAccepted
      version: 1.0.0
      reliability: CRITICAL
```

Manifest `events.subscribes[]` 最少声明：

```yaml
events:
  subscribes:
    - subscriptionId: tenant-first-owner-projection
      eventType: TenantFirstOwnerAccepted
      schemaRange: ">=1.0.0 <2.0.0"
      handlerId: tenant-first-owner-projection.v1
      retryPolicyRef: event-standard
      idempotencyPolicyRef: persistent-inbox
```

约束：

1. CRITICAL/STANDARD publisher 必须声明 `data.storageId/outbox`；
2. CRITICAL/STANDARD subscriber 必须声明 `data.storageId/inbox`；
3. `@CriticalEvent` 不再是可靠性 SSoT；
4. Manifest、生成 Schema、Factory binding 和 Handler ID 必须双向一致；
5. BEST_EFFORT 不得引用 persistent-delivery SLO，也不得驱动正确性关键状态。

### 7.2 canonical Event Envelope

每条可靠事件必须持久化以下字段：

| 字段 | 约束 |
|---|---|
| `eventId` | 全局唯一；Relay retry/replay 保持不变 |
| `eventType` | 版本化公共事实类型，不使用 Java FQCN 作为 wire SSoT |
| `schemaVersion` | 与 Manifest/Schema Registry 兼容 |
| `occurredAt` | 事实发生时间，不以 Relay 时间替代 |
| `producerPluginId` | 由 Runtime 注入，插件不得伪造 |
| `scope` | `PLATFORM` 或 `TENANT` |
| `tenantId` | TENANT 必填；PLATFORM 不得伪造 |
| `correlationId` | 端到端关联 ID |
| `causationId` | 直接原因 message/event ID，可为空但语义明确 |
| `traceparent` | W3C Trace Context |
| `tracestate` | 可选 W3C Trace Context |
| `partitionKey` | 非空；定义局部顺序范围 |
| `payload` | 只包含批准的版本化业务事实字段 |

Envelope 必须由 L2B 从受信任 Invocation/Plugin Context 构造。插件可提供 payload 与业务 partition key，不得覆盖 producer identity、scope、tenant、access decision、trace 或 delivery attempt。

### 7.3 canonical Outbox 最小字段

平台版本化 Schema 至少包含：

```text
message_id             PK
message_kind           EVENT | COMMAND
message_type
schema_version
reliability            CRITICAL | STANDARD
producer_plugin_id
scope
tenant_id              nullable by scope rule
partition_key
occurred_at
correlation_id
causation_id
traceparent
tracestate
payload
status                 PENDING | IN_FLIGHT | PUBLISHED | PARKED
available_at
attempt_count
claim_owner
claim_until
published_at
last_error_code
created_at
```

最低约束：

1. `message_id` 唯一且不可更新；
2. `partition_key`、`payload`、`occurred_at`、`producer_plugin_id` 非空；
3. scope 与 tenantId 组合有数据库 CHECK；
4. 只允许受控状态迁移；
5. claim 必须原子且有 lease；
6. 不保存 Kafka Topic 作为业务契约；transport route 由 L2B 根据 Manifest/Schema Registry 解析；
7. payload/envelope 进入 PUBLISHED 后不可修改；
8. 清理只删除超过保留期且已 PUBLISHED 的记录；PENDING/IN_FLIGHT/PARKED 不得被普通清理任务删除。

### 7.4 canonical Inbox 最小字段

```text
handler_id
message_id
message_kind
message_type
schema_version
processed_at
PRIMARY KEY (handler_id, message_id)
```

Inbox insert、Handler 业务副作用和 Handler 产生的新 Outbox 必须在同一 Consumer Owner 本地事务。首次处理失败应整体回滚，不保留会阻止后续重试的“已处理”记录。

### 7.5 状态与重放

```text
PENDING
  -> IN_FLIGHT
     -> PUBLISHED
     -> PENDING   (transient failure + backoff)
     -> PARKED    (budget exhausted/permanent failure)

IN_FLIGHT --lease expired--> PENDING/reclaim
PARKED --audited replay--> PENDING
```

人工重放必须：

1. 需要受控 operational privilege；
2. 记录操作者、原因、原状态、时间和 trace；
3. 保持原 `eventId/messageId`；
4. 不允许修改 payload 来伪装同一事实；
5. 如需修正事实，必须发布具有新 eventId 的新事件。

## 8. Readiness、失败和可观测性

### 8.1 Readiness

CRITICAL/STANDARD publisher 只有在以下条件同时满足时才 Ready：

1. `EventBusCapability` 的 L2B reliable Provider 已绑定；
2. Manifest 的 storageId/outbox 与 Schema Registry 一致；
3. Owner canonical Outbox 可在本地事务中持久化；
4. Relay 能接受并恢复已提交记录；
5. 所需 L2C persistence/transport Adapter 已通过版本和质量解析。

Broker 短暂不可用不应立即让 Producer 无法提交业务和 Outbox；Relay backlog、最老待投递年龄或 parking 数量超过 Profile 硬阈值时，按明确策略降级 readiness/告警。缺少 Outbox、Schema 不兼容或无法持久化时必须 fail-closed。

### 8.2 最小指标

至少提供以下低基数指标：

```text
brix.outbox.pending.count{storageId,reliability}
brix.outbox.oldest.age{storageId,reliability}
brix.outbox.publish.total{storageId,eventType,result}
brix.outbox.retry.total{storageId,eventType}
brix.outbox.parked.count{storageId,eventType}
brix.outbox.claim.expired.total{storageId}
brix.inbox.duplicate.total{storageId,handlerId,eventType}
brix.event.handler.total{handlerId,eventType,result}
```

禁止把 tenantId、eventId、email、payload 或 raw error 作为指标 label。eventId/traceId 只进入受控结构化日志和审计。

### 8.3 最小告警

1. CRITICAL oldest pending age 超过 SLO；
2. PARKED 出现任何 CRITICAL 记录；
3. claim lease 反复过期；
4. 同一 eventType retry 激增；
5. Inbox duplicate 比例异常升高；
6. Relay 无法访问某个 required Owner canonical Outbox；
7. Schema/Manifest/Handler binding 在启动期不一致。

## 9. 分阶段实施计划

每个里程碑必须单独提交、单独验收。前一里程碑未 Accepted 前不得进入下一里程碑。

### M0：Phase 4 锚定与契约冻结

目标：确定施工起点，避免在脏工作树上混入 Outbox 公共改造。

任务：

1. 绑定 Phase 4 独立 commit、测试结果和工作树范围；
2. 核对现有 migration 环境账本，裁决 V021 可否修改或必须前滚；
3. 冻结可靠性枚举、canonical envelope、Outbox/Inbox 字段和状态机；
4. 冻结 `TenantFirstOwnerAccepted` Schema、scope、partitionKey 和 payload；
5. 明确 Kafka 为首个 transport，CDC 为 Deferred；
6. 输出受影响模块和依赖图，确认不新增 Plugin -> L2B/L2C 依赖。

退出条件：

1. Phase 4 与 Outbox 改造没有混合 commit；
2. migration 处置有可审计依据；
3. 契约评审通过；
4. 本计划获得明确 Guiding 授权。

### M1：L2A 契约、Manifest 与启动门禁

目标：让可靠性成为显式声明和 Runtime 可验证契约。

主要改造面：

| 模块 | 动作 |
|---|---|
| `runtime-sdk-api` | 修正 EventBus 可靠性语义；增加可靠性与 immutable envelope contract |
| `runtime-manifest` | 扩展 event publish/subscribe policy 模型 |
| `platform-devtools/schemas` | 扩展 YAML Manifest Schema |
| `runtime-orchestrator` | 增加声明/Factory/Handler/storage 双向校验 |
| `architecture-guard` | 增加 A-10、无 L2C AOP 可靠性、无插件 Outbox Repository/Broker SDK 规则 |

退出条件：

1. CRITICAL/STANDARD 缺 outbox/inbox 声明时启动失败；
2. BEST_EFFORT 不再宣称 at-least-once；
3. event type/version/reliability 与 Manifest 不一致时 fail-fast；
4. 插件不能依赖 Outbox/Relay/Broker 实现；
5. 两份活动 Manifest Schema 字节一致或由单一生成源证明一致。

### M2：Producer transactional Outbox

目标：实现唯一 Producer 调用链和 Owner 同事务持久化。

任务：

1. 在 L2B 实现 reliable EventBus policy proxy；
2. 绑定当前 Owner UoW、plugin identity、scope、tenant 和 trace；
3. 对 CRITICAL/STANDARD 无活动本地事务调用 fail-fast；
4. 通过受管 persistence 路径 append Owner canonical Outbox；
5. 以前滚 migration 补齐 `platform_tenant_outbox` canonical 字段和约束；
6. 将 `FirstOwnerInvitationService` 从 Outbox Repository 直写迁移到 Owner-scoped EventBusCapability；
7. 删除 `TenantFirstOwnerAccepted` 生产路径对 Kafka Topic、L2C Outbox 和 AOP 的依赖；
8. 证明业务写失败、Outbox 写失败、事务 rollback 都不会产生 phantom event。

退出条件：

1. FIRST_OWNER 业务状态与 Outbox 要么一起提交，要么一起回滚；
2. commit 前没有 Broker send；
3. Outbox record 含完整 canonical envelope；
4. platform-admin/internal contract consumer 不可取得 Outbox Repository；
5. 真实数据库事务测试通过。

### M3：L2B Relay 与 L2C Kafka transport

目标：可靠投递已提交 Outbox，并支持多实例和崩溃恢复。

任务：

1. 实现 L2B managed `OutboxRelay`；
2. 实现原子 claim、lease、backoff、jitter、retry budget 和 parking；
3. 将 Broker publish 抽象为 L2B 内部 transport 边界；
4. 让 Kafka Adapter 只负责 canonical envelope 到 Kafka record 的映射与确认；
5. 使用 `partitionKey` 作为 Kafka key；
6. 保持 retry/replay eventId 不变；
7. 增加 backlog、oldest age、retry、parking、lease 指标；
8. 将 Relay 纳入 Runtime managed resource、Drain 和 fatal/readiness 边界。

退出条件：

1. 两个 Relay 实例不会同时持有同一有效 lease；
2. 进程在 claim 后、send 前、send 后、finalize 前崩溃均可恢复；
3. Broker accepted/finalize failed 会重复但不丢失；
4. retry exhausted 进入 PARKED 并可审计重放；
5. Relay 不读取任何 Owner 业务表。

### M4：Consumer persistent Inbox 与首个 E2E

目标：完成端到端 at-least-once + idempotent side effect 闭环。

任务：

1. 用 Runtime Event Dispatcher 替换生产路径的进程内幂等 Map；
2. 以前滚 migration 补齐 canonical Inbox；
3. 将 Inbox insert、Handler、副作用、结果 Outbox 放入同一 Consumer Owner 本地事务；
4. broker ack 必须晚于 Consumer transaction commit；
5. 增加重复投递、并发投递、Handler rollback、ack 丢失测试；
6. 为 `TenantFirstOwnerAccepted` 建立一个最小、真实且有业务意义的测试订阅者；
7. 完成真实 PostgreSQL/KingbaseES 兼容范围内的数据库验证和 Kafka 集成验证；
8. 绑定运行日志、指标和数据库状态证据。

退出条件：

1. 同一 `(handlerId,eventId)` 并发投递只产生一次业务副作用；
2. Handler 失败后 Inbox 与副作用一起回滚，后续可重试；
3. Consumer commit 后 ack 丢失不会重复副作用；
4. 从 FIRST_OWNER commit 到 Consumer side effect 的真实闭环通过；
5. 可明确声明该事件链满足 at-least-once，不声明 Exactly Once。

### M5：typed Command 共用 substrate

目标：补齐根蓝图 A-10 的可靠 Command 部分，不另建第二套 Outbox。

任务：

1. 复用同一 canonical Outbox/Relay/Inbox 和 `message_kind=COMMAND`；
2. 实现 sender Outbox、`durableReceipt` after-commit 和 rollback exceptional completion；
3. Handler 以 `(handlerId,commandId)` 去重；
4. 业务幂等另以 `(handlerId,idempotencyScope,idempotencyKey)` 保存结果；
5. 保持 commandId/idempotencyKey 跨 retry/replay 不变；
6. 增加 Handler offline、恢复、重复 Command 和 Receipt 时序测试。

退出条件：

1. Receipt 从不早于 sender Outbox commit；
2. Handler offline 不丢 Command；
3. 重复 Command 不重复产生副作用；
4. Event 与 Command 没有并列 Relay/Inbox 基础设施；
5. M1-M5 全部通过后才可申请 A-10 Implementation Accepted。

### M6：旧链路退役与治理收口

目标：删除双实现和无法证明的可靠性声明。

任务：

1. 退役 `CriticalEventOutboxAspect`；
2. 退役全局 `event_outbox` 生产路径；
3. 将 `infra-adapter-kafka-outbox` 拆除或收敛为不拥有策略的兼容层；
4. 删除生产默认 `InMemoryIdempotencyStore`；
5. 更新 README、示例、Capability 文档和架构守卫；
6. 扫描插件中的 Kafka/Rabbit/JMS/StreamBridge/Topic/Outbox Repository 旁路；
7. 绑定 commit、制品 digest、SBOM、签名和 provenance；
8. 更新 Bootstrap/FIRST_OWNER 主计划的验收引用，但不改写历史验收事实。

退出条件：

1. 生产 classpath 不存在两套 Outbox SSoT；
2. 所有可靠事件都可从 Manifest 追踪到 Outbox、Relay、subscription、Inbox 和 Handler；
3. 文档、代码、Schema、migration 和运行证据一致；
4. full-repo 与真实 Host 验收结果分别记录，不用局部测试替代。

## 11. 验收矩阵

| 层级 | 最低验证 | 能证明 | 不能替代 |
|---|---|---|---|
| Contract | API/ABI、Schema、Manifest validator tests | 契约可解析、声明一致 | 数据库事务 |
| Architecture | dependency graph、ArchUnit、source/bytecode scan | 无 Plugin -> L2B/L2C/Broker/Outbox 旁路 | 运行时 AOP/Bean 激活 |
| Producer transaction | 真实 DB integration test | business + Outbox commit/rollback 原子性 | Relay 投递 |
| Relay | 多实例 claim + fault injection | lease、恢复、重试、parking | Consumer 幂等 |
| Consumer | 真实 DB duplicate/concurrency test | Inbox 与副作用原子性 | Broker ack 行为 |
| Adapter | Kafka integration/contract test | key/header/envelope/ack 映射 | 端到端业务正确性 |
| Host E2E | required composition + real HTTP/DB/Kafka | 完整运行链和 readiness | full-repo 回归 |
| Full repo | Maven/前端/guard/CI required checks | 回归与治理门禁 | 真实环境长期 SLO |

### 11.1 必测故障点

1. business write 后、Outbox append 前抛错；
2. Outbox append 成功后、Owner commit 前抛错；
3. Owner commit 成功后进程退出；
4. Relay claim 后进程退出；
5. Broker send 超时但实际已接受；
6. Broker accepted 后 Outbox finalize 失败；
7. lease 到期后另一个 Relay reclaim；
8. 同一 eventId 并发投递到同一 Handler；
9. Inbox insert 后 Handler 抛错；
10. Handler side effect 后 Consumer commit 失败；
11. Consumer commit 成功后 broker ack 丢失；
12. retry budget 耗尽进入 PARKED；
13. PARKED 人工重放保持 eventId；
14. Schema 不兼容、scope/tenant 非法或 Handler 未声明；
15. required Outbox/Inbox/Relay/Adapter 缺失时启动/readiness fail-closed。

### 11.2 最低验收证据

每个里程碑报告必须记录：

1. 两个仓库的精确 commit 与工作树状态；
2. 变更文件清单和 Phase 归属；
3. migration ledger、hash、fresh/upgrade/recovery 结果；
4. 实际执行测试数，禁止只写 `BUILD SUCCESS`；
5. targeted/module/full-repo/real Host/Kafka 验证范围；
6. 故障注入点和数据库最终状态；
7. 相同 eventId 的 Producer、Relay、Broker、Inbox、Handler 关联证据；
8. 未执行项、环境限制和残余风险；
9. 制品 digest、SBOM、签名和 provenance。

## 12. 发布、回滚与数据治理

1. migration 只允许单调前滚；已进入共享/保留环境的 migration 不得修改；
2. expand 阶段可双读旧字段，但不得双写两套 Outbox 并同时声称权威；
3. 切换必须以 Host composition/Profile 和 Runtime readiness 原子完成；
4. 旧 Relay 退役前必须证明不存在未处理记录；
5. PENDING/IN_FLIGHT/PARKED 数据不得因应用回滚或普通清理丢失；
6. transport 回滚不能把可靠事件降级为 BEST_EFFORT；
7. 无法恢复 reliable substrate 时 required Host 应保持 not-ready/fatal，而不是静默直发；
8. Outbox payload 的 PII/secret 分级、加密、保留和删除遵循 Owner 数据治理规则；
9. 清理 job 必须有批量上限、索引、超时、指标和失败恢复；
10. 人工重放是特权 operational 动作，不通过业务插件或数据库脚本作为正式入口。

## 13. 风险与控制

| 风险 | 等级 | 控制 |
|---|---:|---|
| 把 Outbox 写成第二个插件可见 Capability | P0 | Outbox/Relay/Inbox 保持 L2B internal；插件只见 EventBus/Command |
| L2B 动态访问任意 Owner 表 | P0 | Schema Registry + storageId + Custodian 最小权限 + 负向 DB 测试 |
| AOP 未激活导致 CRITICAL 直发 | P0 | 删除 AOP SSoT；L2B 显式策略和启动 fail-fast |
| 全局 event_outbox 与 Owner outbox 并存 | P0 | M6 前完成账本和未处理记录迁移/退役证明 |
| Broker ack/DB finalize 窗口造成重复 | P1 | 明示 at-least-once + Consumer persistent Inbox |
| PROCESSING 记录永久卡死 | P1 | lease + expiry + reclaim |
| Handler 先记 Inbox 后业务失败 | P0 | Inbox 与副作用同一事务，失败整体回滚 |
| eventId 被重放工具重写 | P0 | 数据库/Runtime 不变约束 + replay contract test |
| Outbox payload 成为敏感数据长期副本 | P1 | payload whitelist、保留期、加密与日志 DLP |
| polling 对业务库造成压力 | P1 | 索引、batch、SKIP LOCKED/方言等价能力、backoff、指标；CDC 延后评估 |
| Phase 5/6 与 Runtime 公共改造混交 | P1 | 独立里程碑、独立 commit、前置验收门禁 |

---

## 14. 完成定义

只有以下条件全部满足，才能称为“Outbox Event 最小可靠闭环完成”：

1. CRITICAL/STANDARD Event 可靠性由 Manifest + L2B 策略唯一决定；
2. 插件只经 `PluginContext -> EventBusCapability` 发布；
3. Owner 业务写、审计和 canonical Outbox 同一本地事务；
4. 事务 rollback 不产生可投递事件；
5. Broker send 发生在 Owner commit 后；
6. Relay 可多实例 claim、lease 恢复、退避重试和 PARKED；
7. broker accepted/finalize failed 不丢事件；
8. Consumer Inbox 以 `(handlerId,eventId)` 持久化去重；
9. Inbox、Handler 副作用和结果 Outbox 同一 Consumer Owner 本地事务；
10. broker ack 晚于 Consumer commit；
11. retry/replay 保持 eventId；
12. `TenantFirstOwnerAccepted` 真实 E2E 和全部关键故障点通过；
13. 全局 `event_outbox`、L2C reliability AOP 和生产内存幂等路径已退出主链；
14. readiness、指标、告警、parking 和受控重放可运行；
15. targeted/module/full-repo/real runtime 证据边界清楚；
16. 验收绑定不可变 commit、migration hash、制品和供应链证据。

完成上述 Event 闭环仍不等于 A-10 整体完成。只有 M5 reliable typed Command 的 sender Outbox、durableReceipt、Provider Inbox 和业务幂等全部验收后，才能申请 A-10 Implementation Accepted。
