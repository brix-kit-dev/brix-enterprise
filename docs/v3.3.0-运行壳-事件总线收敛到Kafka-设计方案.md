## 0. 结论摘要

- **Kafka 跑通只是第一步。** 平台模块的 3 种事件已经走统一链路（Owner Outbox → Relay → 投递核心 → Inbox），把 Relay 的传输换成 Kafka 并补上消费端，它们就收敛到 Kafka。企业插件走的是另一条路：主机打包的 9 个插件里，8 个还不是 Runtime 管理的插件；真正在发的事件只有 4 处、4 种，直接发到 Kafka，不经 Outbox，不用统一信封；声明的 11 个订阅没有一个有处理器。它们要逐个接入，旧的直连要拆掉，全系统才只剩一条事件总线。
- **三个阶段**：
  1. **Kafka 接线板**：L2C 的 Kafka 消费端接到 L2B 的投递核心；Kafka 不可用时 Relay 暂停而不是停放；主题由适配器按清单创建；消费端的重试、停放与重放；积压与停放的指标和告警；所有传输共用的一致性测试；共享环境切到 Kafka。
  2. **企业插件接入**：与主线的"企业插件迁移"合并，每个插件一次迁完（`PluginContext`、`PersistenceCapability`、自己的 Outbox/Inbox、新格式清单、事件 Schema 文件）。
  3. **拆掉直连**：主机总线只接受 BEST_EFFORT；`RuntimeContext.getEventBus()` 退役；内存、Webhook 总线不进生产 Profile；旧主题与遗留配置删除。
- **只有两种信息走 Outbox**：跨插件的 CRITICAL/STANDARD 事件，和跨插件命令（目前没有模块使用，将来按根 MESSAGE-010 走同一个传输）。其余信息各有固定通道，不走这条链路，见 §3.1。
- **业务代码只面向接口**：插件发事件用 `EventBusCapability`，收事件实现 `EventHandler`；Kafka 只出现在 L2C 适配器里。以后换中间件只换适配器，并重跑一致性测试。

## 1. 现状（2026-10-29 调查）

### 1.1 事件路径

| 路径 | 现状 |
|---|---|
| 平台模块 | platform-identity 发布 `IdentityAuditFactRecorded`、`FirstOwnerInviteeSetupCompleted`，platform-tenant 发布 `TenantFirstOwnerAccepted`；订阅方是 platform-audit、platform-tenant。都走 Owner Outbox → Relay → 进程内传输 → 投递核心（发布方判定、Schema 范围、解码、范围绑定）→ 订阅方 Inbox 去重与 Handler，同一事务（P4a～P4d）。写入一侧，platform-tenant 用的是它自己的 `PlatformTenantReliableEventBusCapability`，写进 Outbox 的也是统一信封；改用通用的 Owner Outbox 总线是 P4 §13.4 的遗留项，与传输无关 |
| 企业插件 | 主机打包 9 个。真正在发的 4 处经 `RuntimeContext.getEventBus()` 取到主机全局总线 `KafkaEventBusCapability`，`publishIntegration` 直接 `kafkaTemplate.send`：不看可靠性、不进 Outbox、不是统一信封。旧格式清单只写类名，没有版本、可靠性、Schema；声明的 11 个订阅没有处理器。逐插件情况见 §5.1 |
| 其他总线实现 | 内存总线（`infra-adapter-simple`）、Webhook 总线（`infra-adapter-webhook`）只在开启各自开关时创建；企业主机只打包了 Kafka 适配器 |
| 模块内部事件 | 框架事件：身份模块 1 处（Bootstrap 完成）、网关 2 处，只在模块内部 |
| 命令 | 没有任何清单声明命令 |

### 1.2 Kafka 适配器（`infra-adapter-kafka`）

| 部分 | 现状 |
|---|---|
| 发送端 | `CanonicalKafkaOutboxTransport`：在 `brix.outbox.relay.transport=kafka` 时作为 Relay 的传输；记录值是完整的统一信封 JSON，键是 `partitionKey`，信封字段同时写进记录头；同步等待确认（超时 30 秒）。生产者 `acks=all`、幂等开启 |
| 主题命名 | `{前缀}integration.{事件名的 kebab 形式}`。直连总线用同一套命名，所以统一信封的 `CaseCreated` 与旧格式的 `CaseCreatedEvent` 会落到同一个主题 |
| 消费端 | 没有。适配器里只有一个按旧 `IntegrationEvent` 计数的 `KafkaConsumerMetrics` 和一组旧的消费、Outbox 配置项（`.DLQ` 后缀、重试间隔等），都没有使用方 |
| 就绪 | 发送端没有实现 `ready()`，Kafka 不可用时每次发送都失败：Relay 按退避重试，6 次后把消息停放 |

- 共享环境：单节点 KRaft（`confluentinc/cp-kafka:7.7.0`），副本 1；没有设置 `auto.create.topics.enable`，即 broker 默认自动建主题，新主题 1 个分区，保留期 7 天。目前没有业务主题、没有消费组。
- 一次性环境（`/home/deploy/workspace/e2e/identity-slice3`）同样起一个单节点 Kafka（只绑 127.0.0.1:29092）。
- 事件 Schema：清单里写了 `schemaRef`，但事件的 Schema 文件都不存在；平台模块里唯一的 Schema 文件是 platform-audit 的策略审计记录。

## 2. 约束

- **根 3.3.0**：
  - P-1、P-3、§4.7：插件只用能力契约；不得持有中间件 SDK；EventBus 不得暴露 Producer/Consumer、Topic、Broker SDK，不得绕过 Outbox。MESSAGE-029、MANIFEST-029：插件代码里不得有 `@KafkaListener`、Topic 字符串；消息订阅只能由 Runtime 创建。A-1：插件依赖中间件 SDK 要被 CI 阻断。
  - MESSAGE-017～022：CRITICAL/STANDARD 必须事务 Outbox，没有活动事务时立即失败；BEST_EFFORT 可以直接发布。MESSAGE-021：信封字段与 eventId。
  - MESSAGE-025～028：消费方按 `(handlerId, eventId)` 去重并与副作用同事务；只按 `partitionKey` 保序；重试耗尽进入 DLQ/停放区，可观测、可审计、可人工重放，重放不改 eventId。§6.5 第 8 条：事务内发布、故障注入、重复消费测试是发布门禁。
  - MANIFEST-025、026、028：订阅的必填字段与策略引用；Invocation Context 由 Runtime 构造，Handler 不得从消息头重新解析。
  - A-5：所有入口（含 Event）只在全部必需模块 STARTED 后以入口快照原子发布，Drain 时先摘除再等在途完成。
  - OTEL-002、005、006：跨 Event 传播 W3C trace context，单一因果消息用提取出的远端父 span；每个边界适配器要有 inject/extract 和 producer/consumer span 的契约测试；指标标签基数有界，不用 tenantId、eventId。
  - Contract Schema Registry 是 Git/制品里的版本化构建资产，本基线不引入运行期网络 Schema Registry 服务。
  - §0.2：不指定具体消息中间件；LAYER-011、013：同一主机内增删插件要重启，需要独立故障域或扩缩容时拆独立主机进程。
- **multi-tenant 5.1.3**：§10 EventBus 与消息消费两行（TENANT 信封必须带 tenantId；L2B 校验信封后构造 EventInvocation，Handler 完成后清理上下文；插件不接触 Kafka）；实施验收项 I1（缓存、EventBus、对象存储、Scheduler 四个面与异步上下文）。本方案只覆盖 I1 的 EventBus 面。

## 3. 目标形态

```text
插件业务代码（只面向 EventBusCapability / EventHandler）
        │ 同一本地事务
        ▼
Owner 的 {storage}_outbox
        │ 提交后
        ▼
L2B OutboxRelay（每张 Outbox 一个，租约认领；Kafka 不可用时暂停）
        │ L2C Kafka 发送端：键 = partitionKey，值 = 统一信封
        ▼
Kafka 主题 brix.event.<eventType>（每种事件一个主题）
        │ 每个订阅一个消费组（L2C Kafka 消费端，Runtime 管理）
        ▼
L2B 投递核心：发布方判定、Schema 范围、解码、范围绑定、Trace
        │ 订阅方 Owner 的 Unit of Work
        ▼
{storage}_inbox 插入 (handlerId, eventId) + Handler 业务写，同一事务提交
        │ 提交后
        ▼
提交位移；失败按退避重试，耗尽后进入该订阅的停放主题，可列出、可重放
```

进程内传输保留：单进程的开发、测试仍可用，两种传输跑同一套一致性测试（§4.6）。

### 3.1 不走这条链路的信息

根 §6.1 的唯一通信决策表给每种需求只定了一个通道。走 Outbox 的只有需要可靠送达的跨插件异步消息：CRITICAL/STANDARD 事件（MESSAGE-017、018、022）和跨插件命令（MESSAGE-010、011）。Kafka 只是传送它们的方式，可以替换（根 §0.2）。下面这些信息不走这条链路：

| 信息 | 通道 | Outbox | Kafka | 依据 |
|---|---|---|---|---|
| BEST_EFFORT 事件（遥测、非关键提示） | 直接发布 | 不走 | 第三阶段后走 | MESSAGE-019、020：允许丢失，不得驱动关键状态 |
| 读取别的插件的数据 | typed Query，同步、只读 | 不走 | 不走 | §6.1，MESSAGE-002、008 |
| 用户请求要同步拿到结果 | 本插件自己的应用服务 | 不走 | 不走 | MESSAGE-016：不得跨插件同步写 |
| 插件内部的行为 | 方法调用、Domain Event | 不走 | 不走 | §6.1：不构成跨插件契约 |
| 插件改自己的数据 | 自己的 Unit of Work | 不走 | 不走 | DATA-002；只有别的插件需要知道时才发事件 |
| 调用 Brix 之外的服务 | ExternalHttp，限清单里的 allowlist | 不走 | 不走 | §4.7，ERROR-014 |
| 邮件、短信等通知 | NotificationCapability，由数据所属的 Owner 发送 | 不走 | 不走 | super-admin OWNER-005、NOTIFY-001 |
| 定时任务 | 由 Runtime Scheduler 触发 | 不走 | 不走 | 清单 `tasks.provides`；multi-tenant §10 |
| 日志、指标、Trace | OpenTelemetry | 不走 | 不走 | OTEL-001 |
| 平台受托表（如策略审计记录） | Runtime 在同一 Unit of Work 里直接写 | 不走 | 不走 | DATA-004 |
| 文件内容 | 对象存储；要通知别的插件时，事件里只放引用 | 不走 | 不走 | 通行做法，蓝图没有专门条款 |

两点说明：

- **通知的送达还没有收口**：邮件在事务提交之后发送，不经 Outbox。提交后发送失败怎么补救，super-admin 蓝图规定按通知专项处理，目前没有 ACTIVE 的通知专项。不在本方案范围。
- **可靠性按后果定**：丢了会造成数据不一致、或者有订阅方要据此改状态的事件，必须是 CRITICAL 或 STANDARD，走 Outbox；BEST_EFFORT 只用于丢了也不影响正确性的信息。

## 4. 第一阶段：Kafka 接线板

### 4.1 投递核心抽出来共用（L2B）

- 把 `InProcessEventTransport` 里"对一个订阅方投递一条消息"的部分抽成 L2B 的投递核心：发布方判定、Schema 范围、按 Handler 泛型解码、`EventDeliveryScopes` 决定范围（含 P-3）、在订阅方的 Unit of Work 里先写 Inbox 再调 Handler、Trace 与截止时间。
- 进程内传输与 Kafka 消费端都调用它；判定规则、错误码（`EVENT_PUBLISHER_REJECTED`、`EVENT_SCHEMA_UNSUPPORTED`、`EVENT_PAYLOAD_INVALID`、`EVENT_HANDLER_FAILED`）只有一份。

### 4.2 Kafka 消费端（L2C，Runtime 管理）

- **由 Runtime 创建**（MANIFEST-029）：按启用插件清单的 `events.subscribes`，每个订阅（handlerId）一个消费组，订阅该事件类型的主题。插件看不到消费者、主题和位移。
- **生命周期**（A-5）：插件全部 STARTED、投递核心就绪后才开始拉取；关闭时先停止拉取，等在途消息处理完（不超过截止时间），再提交位移、关闭。
- **处理一条记录**：解析统一信封 → 交给投递核心（只投给本订阅）→ 订阅方提交后才提交位移。提交位移前进程崩溃，重启后重复投递，由 Inbox 跳过（MESSAGE-025）。
- **顺序**（MESSAGE-027）：同一分区串行处理；记录键是 `partitionKey`，所以同一 key 的事件按发布顺序处理。
- **失败**：暂时性失败（Handler 抛错、订阅方未就绪）在原地按退避重试，不提交位移、不跳过；超过次数后把整条记录写进该订阅的停放主题，再提交位移、继续。永久性失败（发布方不符、Schema 不在范围、载荷解不出）直接停放。停放记录保留原信封和 eventId，附上错误码、尝试次数、时间。
- **停放与重放**（MESSAGE-028）：管理端口的端点列出各订阅的停放记录（不含载荷）；按 eventId 重放时由投递核心再投给该订阅，eventId 不变。复用 P4a 停放的指标与告警形状。
- **上下文清理**（multi-tenant §10）：范围、Trace 都在投递核心里绑定和释放；消费线程处理完不残留租户上下文。

### 4.3 发送端与 Relay

- **主题命名**：统一信封用新的命名空间 `brix.event.<eventType>`，与直连总线的 `integration.*` 分开，迁移期间不会两种格式混在一个主题里（D18）。
- **Kafka 不可用时 Relay 暂停**：发送端实现 `ready()`（定期探测集群元数据，带超时）；未就绪时 Relay 照常读积压、不认领、不消耗尝试次数，恢复后继续（与 P4a 修正后"等插件"的做法相同）。发送超时仍算一次失败（D21）。
- **配置一致性**：`transport=kafka` 而 Kafka 消费端没有启用时，主机启动即失败，避免事件发出去却没人收。

### 4.4 主题与集群

- **按清单建主题**：适配器启动时按启用插件清单的 `events.publishes` 检查并创建主题（分区数、保留期按配置），没有权限或创建失败时启动失败；broker 关闭自动建主题，拼错的主题名不会悄悄出现（D18）。
- **自动建主题何时关（施工时发现，负责人 2026-10-29 确认挪到第三阶段）**：企业插件的旧直连总线在第三阶段之前还往 `integration.*` 发，而且是同步发送；broker 关闭自动建主题后，这些主题不存在，发送会先卡住约 60 秒（生产者等元数据）再失败，案件创建会因此回滚。统一信封的主题与停放主题由适配器显式创建，不依赖自动建主题。所以共享环境第一、二阶段保持 broker 现状，关闭自动建主题移到第三阶段拆掉直连之后（§6）。
- **分区**：默认 3 个；同一 key 的顺序只在分区内保证，加分区会改变 key 的分区，所以分区数视为发布后不轻易改动的设置。
- **保留期**：7 天。重放超过保留期的事件，以发布方 Outbox 的已发布行为准（Outbox 的保留与清理按 MESSAGE-026 另行规定）。
- **共享环境**：单节点、副本 1，满足开发与验收；正式环境的副本数、认证与 ACL（只有主机的身份能读写这些主题）不在本方案范围。

### 4.5 可观测

- **指标**（标签有界：主题、订阅、事件类型、错误码）：每个订阅的消费积压（条数、最老一条的年龄）、处理成功、重试、停放计数，停放中的条数。
- **告警**：任一订阅有停放即告警（critical，与 `BrixOutboxMessageParked` 一致）；积压持续超过阈值告警（warning）；Kafka 不可用导致 Relay 暂停超过阈值告警。
- **Trace**（OTEL-002、005）：发送端注入、消费端提取 traceparent，消费处理以提取出的远端 span 为父；契约测试覆盖 inject/extract 与 producer/consumer span。
- **日志**：沿用 `event=event.delivered`、`event=event.delivery_failed`，加 `event=event.parked`、`event=event.replayed`，带订阅与 eventId，不带载荷。

### 4.6 一致性测试套件

所有传输（进程内、Kafka，以后的其他中间件）都必须通过同一套测试（§6.5 第 8 条）：

- 事务内发布：提交才有事件，回滚没有；
- 至少一次：订阅方提交后、确认前崩溃，重投被 Inbox 跳过，副作用只有一次；
- 并发重复投递只生效一次；
- 同一 `partitionKey` 保序；
- 暂时性失败重试后成功；永久性失败直接停放；耗尽后停放；重放后成功、eventId 不变；
- TENANT 事件只在信封租户的范围内处理；P-3 订阅按策略绑定并写策略审计；
- 传输不可用时暂停、恢复后继续，不丢不重复；
- 主机重启时有待投递消息，重启后按序投递。

### 4.7 共享环境切换

1. 发布第一阶段的代码时仍用进程内传输，确认新代码在旧传输下行为不变。
2. 主题与停放主题由适配器在主机启动时按清单创建，消费组由消费端首次加入时建立，部署前不用改 broker。关闭自动建主题移到第三阶段（§4.4）。
3. 把传输切到 Kafka（改环境变量，只重建后端），等 Outbox 里待投递的消息全部投递完再切，避免同一条消息先后由两种传输处理（两边都有 Inbox，重复也只生效一次，这一步只是让记录清楚）。
4. 回退：切回进程内传输即可；已经进了 Kafka、还没消费的事件，切回前要先消费完。

**第一阶段出口**：一致性测试在两种传输上全部通过；一次性环境用 Kafka 传输跑完现有全部回归，另加 Kafka 宕机、消费端崩溃、毒消息与重放、重启场景；共享环境切到 Kafka 后，平台模块的 3 种事件经 Kafka 投递，告警规则就绪。

## 5. 第二阶段：企业插件接入（与主线"企业插件迁移"合并）

### 5.1 现状（2026-10-29 逐插件调查）

主机（host-shell-standalone）打包 9 个企业插件：booking、case、contracts、identity（app-identity）、messenger、partners、products、storage、carousel。intake 在主机 pom 里被注释掉（"待集成"），compliance、tenant（app-tenant）不在任何主机里。

**8 个还不是 Runtime 管理的插件**：

- Runtime 只读 `META-INF/brix/plugin-manifest.yaml`。9 个里只有 booking 是新格式（`BrixPlugin`，不发也不订阅事件）。其余 8 个只有旧的 `module-manifest.yaml`（不进构件）和 `plugin-manifest.json`（Runtime 视为旧资源）。
- 它们由各自的 Spring 自动配置装配：仓库靠 `@EnableJpaRepositories` 扫描，事务用 Spring `@Transactional`，没有一个经 `PersistenceCapability`；没有 Outbox/Inbox 表。
- messenger、partners、products、storage、carousel 的模块类不在各自的扫描范围内，在主机里不是 Bean：它们的启动检查和定时任务都没有运行。

**真正在发的事件只有 4 处、4 种**：

| 插件 | 事件 | 发布位置 | 在事务里 |
|---|---|---|---|
| case | `CaseCreated` | `CaseService.java:128` | 是（Spring `@Transactional`，保存之后） |
| messenger | `MessageSent`、`MessageRead` | `MessageEventPublisher.java:62`、`:82`，发送失败只记日志 | 是 |
| storage | `AvatarUploaded`（清单里没声明） | `AvatarServiceImpl.java:315` | 否：这一步没有数据库写，只写 StateStore |

- 4 个事件类都没有覆写 `payload()`，按现在的样子通用 Outbox 总线会拒绝它们。
- 8 个插件的旧清单共声明 38 种发布事件，实际只发上面 4 种；partners、products 有名为 `publishEvent` 的私有方法，但只记日志（共 11 处调用）。

**声明的 11 个订阅没有一个有处理器**（没有 `EventHandler` 实现、没有监听器、没有轮询）。其中只有 contracts 订阅的 `CaseCreated`（"案件创建时关联已有合同"）指向真正在发的事件（负责人先确认保留，后改为不保留，§8 D22）；其余 10 个指向的事件没有任何地方发布（booking 的 6 个、identity 的 `UserCreated`、partners 的 `PartnerStatusChanged` 等）。case 里还有一个旧注解 `@EventHandler(eventType="UserCreatedEvent")` 的方法，没有任何东西分发给它。

**不在主机里的 3 个**：intake 用 `publish(DomainEvent)` 发 3 种领域事件，它的迁移只 ALTER 了从没被创建的表；compliance 有 2 处发布，迁移有同样的问题；tenant 的新格式清单声明了 `tenant_outbox`/`tenant_inbox`，但没有迁移创建它们。它们要先修好迁移、进主机，才谈得上接入，不在本阶段范围。

没有任何测试覆盖企业插件的事件发布。

### 5.2 每个插件怎么接入

与主线"企业插件迁移"是同一件事，每个插件一次迁完：

1. **入口**：实现 `BrixPlugin`，经 ServiceLoader 登记；Handler、Endpoint 由 Factory 创建（根 CAP-025）；去掉 `RuntimeContext`/`LifecycleCapability` 模块类，启动时的能力检查改为清单的 `capabilities.required`。
2. **清单**：`META-INF/brix/plugin-manifest.yaml`；`data` 段写 `storageId`、`schema`、`migrationLocation`，发布或订阅事件的插件写 `outbox`/`inbox`；`events.publishes` 只列真正在发的事件（`eventType`、`version`、`reliability`、`schemaRef`）；`events.subscribes` 只列确认需要的订阅。
3. **持久化**：仓库经 `PersistenceCapability.repository` 取得，事务用 `unitOfWork()`，不再用 Spring 扫描和 `@Transactional`（根 DATA-024～027）；迁移补上平台统一结构的 `{storage}_outbox`/`{storage}_inbox`。
4. **事件**：事件类覆写 `eventTypeId()`（稳定的名字）和 `payload()`（类型化记录）；发布方的 api 构件放 Schema 文件（D24）；在插件自己的 Unit of Work 里经 `PluginContext` 取到的 Owner Outbox 总线发布。
5. **订阅**：实现 `EventHandler<载荷>`，经 `bindEventHandlerFactory` 绑定。
6. **测试**：描述符与 Handler 绑定测试；事务测试（提交有 Outbox 行、回滚没有）；每条真实链路的端到端检查。

### 5.3 已知的取舍

- **storage 的 `AvatarUploaded` 没有数据库写**：推荐声明为 BEST_EFFORT，直接发布（根 MESSAGE-019；它没有订阅方，丢失不影响正确性）；等有订阅方需要可靠送达时，再把头像确认改成写文件元数据的 Unit of Work、改走 Outbox。
- **messenger 现在吞掉发布失败**：改走 Outbox 后，事件写不进 Outbox 就是整个发送失败、回滚（MESSAGE-022），不能再只记日志。这是行为变化，接入时一并改测试。
- **只记日志的 `publishEvent`**：partners、products 的这些"事件"现在没有发布，也没有订阅方。接入时删掉，需要时再按新格式加（D22）。

### 5.4 范围与出口

- 8 个旧插件，每个约 0.5～1.5 个工作日，合计约 6～10 个工作日；其中事件部分很小（4 种事件、最多 1 个订阅），主要工作量是入口、清单与持久化的迁移。booking 已是新格式，只需确认。
- **出口**：主机打包的插件全部是 Runtime 管理的插件、使用新格式清单；它们发布的 CRITICAL/STANDARD 事件全部经各自的 Outbox；插件代码里没有 `RuntimeContext.getEventBus()`；确认需要的订阅各有端到端检查。

## 6. 第三阶段：拆掉直连

- `KafkaEventBusCapability` 改为只接受 BEST_EFFORT（MESSAGE-019），CRITICAL/STANDARD 一律拒绝；BEST_EFFORT 事件也写统一信封、发到同一命名空间 `brix.event.<eventType>`，由同一个消费端投递，订阅可用不落库去重的策略（MANIFEST-025）。`RuntimeContext.getEventBus()` 退役，插件只经 `PluginContext` 取总线。
- 生产 Profile 拒绝内存总线、Webhook 总线等开发型适配器（根 BOOT-003）。
- broker 关闭自动建主题（共享环境要重建 Kafka 容器，数据卷保留，单独请负责人批准），之后只有清单里的事件类型才有主题（D18、§4.4）。
- 删除旧的 `integration.*` 主题、`KafkaConsumerMetrics`、旧的消费与 Outbox 配置项。
- CI 守卫补全：插件的 server 模块也禁止依赖 Kafka/AMQP 客户端（A-1）。
- Relay 按 key 保序：认领时，同一 `partitionKey` 前面还有未发布的消息，就先不认领后面的（§11.6 第 3 条）。
- **出口**：架构测试证明插件代码里没有直连路径；主机全局总线上的发布只剩 BEST_EFFORT；校验器通过。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| Kafka 成为关键路径，宕机时事件延迟 | Outbox 保证不丢；Relay 暂停而不停放；积压与暂停告警；恢复后按序投递 |
| 切换传输时同一条消息被两种传输处理 | 等 Outbox 清空再切；两边都有 Inbox 去重，重复也只生效一次 |
| 毒消息阻塞分区 | 重试次数有限，耗尽后停放并继续；停放即告警 |
| 共享环境单节点 Kafka 丢数据 | Outbox 的已发布行仍在数据库，可按 eventId 重新发布；正式环境的副本数另定 |
| 企业插件迁移面大 | 按插件分批，每批单独验证、单独部署 |
| 新旧两种格式落在同一主题 | 新命名空间与旧主题分开（D18），第三阶段删除旧主题 |
| Trace 断链 | 发送端与消费端的契约测试（OTEL-005） |

### 12.1 调查结论

- **这些插件在共享环境里实际没有用上**：8 个旧插件的 18 张实体表全部是空表；宿主前端只挂了平台超管和平台租户的页面，不调用它们的任何接口；没有测试覆盖它们的 HTTP 接口。另有 26 张早期设计的表（各插件迁移 V100 建的 `biz_*`、`cms_*` 等）从来没有实体映射。
- **其中几条链路本来就跑不通**：
  - case 的接口都要一个没有实现的 `AuthorizationCapability`，调用会先失败，`CaseCreated` 实际从没发出过；
  - case 的租户取自静态配置（`default`），contracts 取自登录态，两边对不上；
  - contracts 的子表（当事人、签署记录、模板版本）`tenant_id` 必填却从不赋值，建带当事人的合同、建模板、签署都会失败；
  - carousel、messenger 有不带租户条件的批量更新，products 的缓存键不含租户，都可能跨租户。
- **与 Runtime 规则的差距**：主键用 `@GeneratedValue`（持久化适配器会拒绝，要改用 `IdGeneratorCapability`）；`tenant_id` 都是 VARCHAR，而租户过滤按 BIGINT 绑定；装配全靠 Spring（`@ComponentScan`、`@EnableJpaRepositories`、`@Transactional`、`@RestController`）；app-identity 有指向 platform-auth 表的外键（DATA-003 禁止跨 Owner 外键）。
- **规模**：97 个 HTTP 接口（case 5、contracts 25、messenger 11、partners 11、products 13、carousel 14、storage 18、identity 0）、18 个实体、76 处 `@Transactional`。
- 所以第二阶段实际上是**在 Runtime 上按规范重建这些插件的后端**。接口路径保留，数据以实体表为准；表都是空的，改列类型、改主键生成方式都不用迁移数据。

### 12.2 一个插件"迁完"的标准（每个插件同一张清单）

- **入口**：plugin-server 经 ServiceLoader 只发布一个 `BrixPlugin`（MANIFEST-011）；`configure()` 只绑定清单声明的 Handler（MANIFEST-013）；不用 Spring 的组件扫描、`@RestController`、`ApplicationContext`（MANIFEST-016）；能力只经 `HandlerFactory.create(PluginContext)` 取得（MANIFEST-019）。原有的 Spring 自动配置、模块类、`application.yml` 删除。
- **清单**：`META-INF/brix/plugin-manifest.yaml`，pluginId 统一用 `app-<名称>`（与 app-booking、迁移目录 `db/migration/app-<名称>` 一致）。每个接口写清认证、权限与 grants、租户上下文、超时；写操作声明 `idempotency.mode`（MANIFEST-017/018）。events 只列真正发布的事件和确认需要的订阅。
- **持久化**：仓库只经 `PersistenceCapability.repository` 取得（DATA-026），不用 JDBC/EntityManager（DATA-025）；事务交给 Runtime 的 Handler Unit of Work（DATA-028/029），删掉 `@Transactional`；主键由 `IdGeneratorCapability` 分配；`tenant_id` 改 BIGINT，取自 Runtime 绑定的调用租户；批量更新都带租户条件。
- **迁移**：继续用原来的 `db/migration/app-<名称>` 和 Flyway 历史表，只追加新版本（改列类型、补索引、建 `{storageId}_outbox`/`_inbox`）；没映射的旧表先不动（不删数据）。
- **事件**：发布经自己的 Outbox（事件类覆写 `eventTypeId()`/`payload()`，Schema 文件加 `EventSchemaContract` 检查）；订阅实现 `EventHandler<载荷>`，经 Inbox 去重；只记日志的 `publishEvent` 删除。

### 12.5 CaseCreated 关联已有合同（已撤销，见 D22）

> **撤销**：负责人决定不保留这条订阅（§8 D22），本节只作为当时的分析留存，不再指导施工。合同与案件的关联等改造业务流程时再讨论。

- **推荐做法（按客户关联）**：
  - 案件增加客户 `customerId`。员工建案件时填写；C 端用户自己建案件时默认为本人。

  - 没有 `customerId` 就不处理，只记计数。经 Inbox 去重，重复投递没有副作用。
- **另一种做法（显式指定）**：建案件时带上要关联的合同 ID 列表，订阅方只关联这些合同，同样要求同租户、尚未关联。
- 按客户关联的前提是：案件的客户 ID 与合同客户方当事人的 `party_id` 是同一套 ID。

### 14.2 需要确认的决定

| 编号 | 推荐 | 备选 |
|---|---|---|
| D30 命令 | 现在按同一条链路做最小实现：命令写发送方自己的 Outbox（`message_kind=COMMAND`），主题 `brix.command.<commandType>`，每个命令一个消费组、只投给唯一 Owner；Owner 的 Inbox 以 `(handlerId, commandId)` 去重，业务幂等按 `(handlerId, idempotencyScope, idempotencyKey)` 保留结果；`submit()` 提交后才给 durable receipt；结果经 Owner 的事件发布（MESSAGE-010～016）。理由：根 §6.1 规定跨插件状态变更只能用命令，没有它插件会把事件当命令用（MESSAGE-001 禁止）；现有的半成品写错了 Outbox，做完才算收尾；Outbox、Relay、消费端、Inbox 都能复用。约 4 天 | 保持 D26：现在不做。去掉挂在 `platform_tenant_outbox` 上的 `CommandCapability`，插件声明需要命令时启动失败，Kafka 传输拒绝非事件消息；以后按推荐的形状增加。约 0.5 天 |
| D31 顺序范围 | 保持每种事件一个主题（D18），对外保证写明为"同一事件类型内、同一顺序键按发布顺序生效"；同一聚合跨事件类型的先后，由订阅方按载荷里的聚合版本号判断，作者文档给出写法；进程内传输按同一保证测试 | 按发布方分主题，允许一个订阅收多种事件，同一顺序键跨类型也保序；代价是订阅要从混合主题里过滤，慢订阅拖住同主题，主题与消费组要重做 |
| D32 新订阅起点 | 从首次登记时开始：主机启动、Relay 开始发送之前，为还没有位移的订阅先把位移定在当前末尾，之后发布的事件一条不漏；改 handlerId 等于新订阅，不回灌旧事件；两种传输一致。需要历史时用 Outbox 重发（K16）显式补 | 保持现状：从 Kafka 里最早还在的开始（最多 7 天） |
| D33 停放记录 | 可以丢弃：丢弃和重放都要填原因，操作人、时间、eventId、订阅、原因记入平台审计；可按订阅批量重放 | 只能重放 |
| D34 保留期 | Outbox 已发布行 14 天，Inbox 去重记录 30 天，Kafka 7 天不变；启动时检查 Inbox 保留期 ≥ Outbox 保留期 + Kafka 保留期；按 eventId 重发只允许在 Outbox 保留期内；停放主题保留到处理为止 | 只清 Outbox、Inbox 不清 |
| D35 生产 Kafka 基线 | 生产 Profile 要求 TLS 加客户端证书（SECURITY-006 的非对称客户端身份）、副本数 ≥ 3、`min.insync.replicas` ≥ 2，否则启动失败；共享环境不是生产 Profile，保持单节点 | 用户名口令（SCRAM）：属于共享密钥，按 SECURITY-006 只能用于受限兼容 Profile |
