## 0. 结论摘要

- **根蓝图的查询设计总体符合商用级做法，照做即可。** 每种需求一个通道；Schema 先行的 typed 契约；清单声明依赖、启动期解析；截止时间加平台硬上限；并发隔离与熔断；只对幂等读有界重试；未找到与故障分开；调用方事务挂起、Provider 开独立只读事务；调用上下文由 Runtime 构造。这些与 gRPC 的截止时间和状态码、Google SRE 与 AWS 的重试与退避建议、模块化单体（Spring Modulith 的模块 API、ABP 的集成服务）的做法一致。逐项对照见 §9.1。
- **要处理的三处**：
  1. **专项与根冲突（§9.2 R1）**：multi-tenant 5.1.3 要 `platform-admin` 经 typed Query 读取租户数据；根规定运维模块只经内部契约访问数据。根的做法更好：运维特权面与插件数据面分开，`OperationalContext` 不必扩大。本方案按根执行，建议给 multi-tenant 出一个 Patch 版本修正。
  2. **根的一条字面规定不利于优雅停机（§9.2 R2）**：Drain 时 Query 入口与其他入口一起摘除，已准入的请求在停机窗口里再发起的查询会失败。建议根澄清"已准入调用内发起的查询属于该调用"；批准前按字面执行，以后切换只改 Gateway 的准入判断。
  3. **根没有规定、商用必须补的（§9.3）**：结果大小上限与分页、嵌套调用占用连接池、调用深度、契约类型的二进制兼容。本方案在实现层补上，不改蓝图。
- **现状**：调用方没有任何入口（L2A 没有 `QueryCapability`）；`QueryHandler` 的签名不是冻结的 ABI；Runtime 创建 Query Handler 后随即丢弃，没有 Gateway；全平台没有一个查询的提供方或调用方。
- **目标**：与事件、命令一样，**插件只写清单和代码就能接入**。Provider 写 `queries.provides`、Schema 和 `QueryHandler`；Consumer 写 `queries.consumes`，依赖 Provider 的 api 构件，在 Factory 里取 typed client。准入、上下文、鉴权、截止时间、隔离、熔断、重试、事务、Trace 与指标都在 L2B。
- **同进程直接调用**：不经 Outbox、不经 Kafka、不做序列化，在调用方线程上执行。传输留一个 L2B 内部接口，以后某个 Provider 拆到独立主机进程时再加远程传输，插件代码与清单不变。
- **首批使用**：示例插件对加一个查询（sample-orders 读 sample-shipping 的发货单）；platform-tenant 发布 `TenantReferenceQuery`（multi-tenant §7.1、T-7）。
- **估算**：约 18～19 个工作日（§7）。

### 1.4 相邻的实施偏差（不在本方案范围，登记备查）

- `EndpointHandler` 是 `O handle(I)`、`ManagedTask` 是 `void run()`，不是 MANIFEST-027 的 `CompletionStage` 方法；`CommandInvocation` 没有根要求的 `access`、`idempotency`。
- `CommandRequest` 在 L2A 用字符串 `commandType` 定位命令，A-22 要求客户端由 Schema 生成。查询不照搬这种写法（MESSAGE-009 明确禁止字符串 target/queryName 进入 L2A 与生成客户端）。
- L2A 有 `ResilienceCapability`（L2C 由 `Resilience4jResilienceCapability` 实现），它不在根 §4.1 的 Catalog 里（CAP-006）。
- platform-tenant 只有一个 `plugin-server` 构件，MANIFEST-005 要求 api、core、server 三个。施工只拆出 `platform-tenant-api` 放查询契约（Q10），core 与 server 的拆分不在范围。
- 端点的 Error Boundary（`RuntimeShellEndpointController`）只映射 `EndpointHandlingException`；Handler 抛出的其他 `BrixException` 与未预期异常落到 Spring 的缺省 500，没有稳定错误码，也没有映射为 `platform.unknown`（根 ERROR-010、§5 Error Boundary 条）。施工只补了 `BrixQueryException` 的映射（§12.3）。

## 3. 目标形态

```text
Consumer 插件的 Handler（在 Factory 里取得 QueryClient<Q,R>）
        │ client.execute(request)：同一线程，阻塞，受截止时间约束
        ▼
L2B Query Gateway（runtime-native，插件看不到）
  1 准入：调用发生在已准入的调用里；查询在调用方 queries.consumes 里；Provider 已解析、入口在当前代次
  2 上下文：从调用方当前调用派生 caller、scope（只取调用方当前租户）、access、trace、deadline、cancellation、深度
  3 访问策略：Provider 的 accessPolicyRef
  4 截止时间：min(调用方剩余, consumes 的 timeout, provides 的 timeout, Profile 硬上限)；已耗尽直接失败
  5 熔断（调用方 × 查询）→ 并发隔离（每个查询一个信号量，不排队）
  6 挂起调用方 Unit of Work → Provider 的 Owner 上下文开只读 Unit of Work（事务超时 = 剩余截止时间），租户范围 = 调用方租户
        ▼
Provider 插件的 QueryHandler.handle(QueryInvocation)（只读、只读自己的数据）
        │ 等到截止时间
        ▼
  7 结果检查（必须是声明的生成类型）→ 结束只读 Unit of Work → 恢复调用方 Unit of Work
  8 错误映射：未找到 = empty；其余为稳定错误码；只对暂时性故障按 retryPolicyRef 重试（截止时间内）
  9 CLIENT/SERVER span、指标、日志
```

- **Gateway 只有一份，传输可替换**：准入、上下文、策略、截止时间、熔断、错误映射、遥测与传输无关；事务挂起与执行在进程内传输里（§5.10）。

### 3.1 不走这条链路的信息

根 §6.1 给每种需求只定了一个通道。typed Query 只用于"读取另一个插件拥有的数据"，下面这些不走它：

| 信息 | 通道 | 依据 |
|---|---|---|
| 要别的插件改状态 | typed Command（异步） | §6.1、MESSAGE-010 |
| 通知已经发生的事实 | Integration Event | §6.1 |
| 用户请求要同步拿到写结果 | 本插件自己的应用服务 | MESSAGE-016：不得跨插件同步写 |
| 运维模块（`platform-admin`）读写平台数据 | descriptor 声明且 allowlist 批准的内部契约 | LAYER-016、HOST-024；super-admin §2.1 |
| 浏览器与 App 访问后端 | HTTP Endpoint（前端的 Query client 也经它） | 根 §2 Endpoint 的定义；frontend 1.2.1 §2.1 |
| 插件读自己的数据 | 自己的 Repository | DATA-002 |
| 当前租户、当前用户 | `TenantContextCapability`、`AuthCapability` | ERROR-016、CONTRACT-001 |
| 调用 Brix 之外的服务 | ExternalHttp | ERROR-014 |
| 大批量导出、报表、跨插件聚合 | 使用方订阅事件建自己的只读投影，声明延迟与重建 | MESSAGE-004；multi-tenant §10.1 第 6 条 |
| 登录期跨租户发现 | Auth Owner 的专用登录发现契约 | multi-tenant §6.3、§6.4 |

两点说明：

- **typed Query 只用于小而有界的交互式读取**：一次调用读一个对象、一页或一批按 ID 列出的对象（§5.6）。
- **同一份数据既要给插件读、又要给运维面读时**，Data Owner 各提供一个薄入口（typed Query 与内部契约），共用同一个读服务。

## 4. 插件怎么接入

### 4.1 发布查询（Provider）

1. **契约**：在 api 构件放查询契约文件（`META-INF/brix/queries/<queryType>/<版本>.json`：queryType、版本、请求与响应的 schemaRef、`optional`）和请求、响应 Schema（`META-INF/brix/schemas/<plugin>/<名字>/<版本>.json`，与事件相同的位置约定）。生成器产生契约类型与 `QueryType` 常量，生成的源码检入仓库，由 api 构件里的 `ContractSourcesTest` 保持与 Schema 一致（D38，施工时的做法见 §12.3）。需要表达"未找到"的查询，契约文件写 `"optional": true`，生成类型为 `Optional<…>`（MANIFEST-027）。
2. **清单**：

```yaml
capabilities:
  required:
    - id: io.runtime.sdk.capability.PersistenceCapability
      version: ">=3.3.0 <4.0.0"
queries:
  provides:
    - queryType: sample-shipping.find-shipment
      # 版本由两个 schemaRef 给出，二者必须相同；结果"可能为空"写在契约文件的 optional 里
      request:
        schemaRef: brix://schemas/sample-shipping/find-shipment-request/1.0.0
      response:
        schemaRef: brix://schemas/sample-shipping/shipment/1.0.0
      handlerId: sample-shipping.find-shipment.query.v1
      # 在调用方的当前租户内读取
      scopePolicyRef: query-caller-tenant
      # 调用方的用户必须持有本插件声明的这个权限
      accessPolicyRef: on-behalf-of:sample-shipping:shipment:read
      timeoutPolicyRef: query-interactive
      concurrencyPolicyRef: query-standard
```

3. **代码**：

```java
// SampleShippingPlugin.configure：与已有的 HTTP 端点共用 ShipmentDesk
bootstrap.bindQueryHandlerFactory(FIND_SHIPMENT_QUERY, context -> new FindShipmentQuery(desk(context)));

final class FindShipmentQuery implements QueryHandler<FindShipmentRequest, Optional<Shipment>> {
    @Override
    public CompletionStage<Optional<Shipment>> handle(QueryInvocation<FindShipmentRequest> query) {
        // 租户取 Runtime 绑定的调用方范围，不取请求里的值；没有发货单就是 empty，不抛错
        long tenantId = Long.parseLong(query.scope().tenantId().orElseThrow());
        return CompletableFuture.completedFuture(shipments.find(tenantId, query.request().orderId()));
    }
}
```

`FindShipmentRequest`、`Shipment` 由生成器从 Schema 产生，取代 api 构件里原先手写的 `ShipmentView`（D38）。

Provider 不做的：不读别人的数据；不写、不发事件、不提交命令（Runtime 在查询里拒绝，§5.9）；不自己解析租户或用户；不把故障当作 empty 返回。

### 4.2 调用查询（Consumer）

1. **依赖**：pom 依赖 Provider 的 api 构件，只能是 `plugin-api`（LAYER-004、LIFE-010）。
2. **清单**：

```yaml
capabilities:
  required:
    - id: io.runtime.sdk.capability.QueryCapability
      version: ">=3.3.0 <4.0.0"
queries:
  consumes:
    - queryType: sample-shipping.find-shipment
      versionRange: ">=1.0.0 <2.0.0"
      # 可选：没有发货插件时订单详情照常返回，并注明发货信息暂不可用
      required: false
      timeoutPolicyRef: query-interactive
      retryPolicyRef: query-no-retry
```

3. **代码**：

```java
// SampleOrdersPlugin.configure
bootstrap.bindEndpointHandlerFactory(SHOW_ORDER, context -> new ShowOrder(
    orders(context), context.require(QueryCapability.class).client(SampleShippingQueries.FIND_SHIPMENT)));

// ShowOrder.handle
Optional<Shipment> shipment = shipments.execute(FindShipmentRequest.builder().orderId(orderId).build());
```

- `client(...)` 在 Factory 里调用（P4）：查询不在本插件的 `queries.consumes` 里、或类型与 Provider 声明的不一致，启动即失败。
- `execute` 阻塞到结果或截止时间；失败抛 `BrixQueryException`（§5.4）。required 依赖的错误直接抛出，由 Error Boundary 映射；optional 依赖只对 `query.provider_missing` 显式降级，降级要可见（"发货信息暂不可用"，不是"没有发货单"，RESILIENCE-005）。
- 不要在循环里逐条调用（N+1）：批量场景由 Provider 发布按 ID 列表查询的契约（§5.6）。

### 4.3 启动时 Runtime 检查什么

- schemaRef 都能解析；请求与响应两个 schemaRef 的版本一致；Handler 的请求、结果类型带的 `@ContractSchema` 与清单声明的 schemaRef 一致（D38）。
- 每个 `(queryType, 主版本)` 只有一个 Provider；每条 consumes 恰好解析到一个 Provider，版本在范围内（CAP-015、BOOT-004）。
- required 依赖无环（A-9、LIFE-011）。
- 策略引用都在平台策略目录里（§5.3）；`on-behalf-of` 引用的权限是 Provider 自己声明的权限。
- 有 consumes 就必须声明 `QueryCapability`；清单与 Factory 一一对应（MANIFEST-026）。
- Host Profile 配了查询截止时间的硬上限，各超时策略不超过它（MESSAGE-005）。

任何一项失败：该插件 Resolve Failed；它是 required 插件时主机启动失败（BOOT-005）。

## 5. Runtime 设计

### 5.1 L2A 契约（新增与修正）

```java
public interface QueryCapability {
    <Q, R> QueryClient<Q, R> client(QueryType<Q, R> type);
}

public interface QueryClient<Q, R> {
    /** 阻塞到结果或截止时间；失败抛 BrixQueryException。 */
    R execute(Q request);
}

/** Provider 的 api 构件里由生成器产生的常量。 */
public final class QueryType<Q, R> {
    public String queryType() { … }
    public String version() { … }
    public Class<Q> requestType() { … }
    /** 生成的结果类；响应可空时 R 为 Optional<该类>。 */
    public Class<?> resultType() { … }
    public boolean optionalResult() { … }
}

public interface QueryHandler<Q, R> {                 // 改为冻结 ABI（MANIFEST-027）
    CompletionStage<R> handle(QueryInvocation<Q> invocation);
}

public record QueryInvocation<Q>(
        Q request,
        CallerIdentity caller,
        InvocationScope scope,
        AccessDecision access,
        TraceContext trace,
        Instant deadline,
        CancellationSignal cancellation) {}
```

- `CallerIdentity`：调用方插件 ID，加上调用方当前调用的终端主体（Actor 或 Subject）；事件 Handler 与任务里的调用没有终端主体。由 Runtime 填写，插件不能自报（ERROR-006）。
- `InvocationScope`：`TENANT(tenantId)` 或 `PLATFORM`，只取调用方当前调用的范围。
- `QueryType` 里的名字是生成的数据，不是字符串 API：Gateway 只接受调用方 `queries.consumes` 声明过、请求与响应类型与 Provider 一致的 `QueryType`（MESSAGE-009）。
- `QueryHandler` 原地改为冻结签名：两仓没有实现类，旧签名从未接到任何路由。旧的 `bindQueryHandler(实例)` 保留为已弃用，下一个 Major 删除（施工时更正：CAP-019、CAP-023 不允许在 Minor 里删除 L2A 方法，§12.3）。
- `BrixQueryException` 继承 `BrixException`，只带错误码与批准的 `safeParameters`（ERROR-008、013）。

### 5.2 Gateway 的处理顺序

1. **准入**：查询只能在一个已准入调用的执行中发起（HTTP、Query、Command、Event、Task 的 Handler 里）；没有当前调用（例如 `onStart`）拒绝。Provider 的查询入口在当前入口代次里已发布（A-25）。
2. **当前调用载体**：各 Dispatcher 进入 Handler 时把调用方插件、终端主体、范围、访问判定、Trace、截止时间、取消信号、嵌套深度绑定到 L2B 私有的载体上，Handler 结束时清理（multi-tenant §11.1 允许 L2B 私有载体，不是插件契约）。Gateway 从它派生 `QueryInvocation`，进入 Provider 前再为 Provider 绑定一层（深度加 1）。插件不传、也不能伪造上下文。
3. **访问策略**：按 §5.3。授权在 Provider 一侧执行（S-2），用与端点相同的、当前入口代次的授予表计算。
4. **截止时间**：取 `min(调用方剩余, consumes 的 timeout, provides 的 timeout, Profile 硬上限)`；已耗尽直接 `query.deadline_exceeded`，不调 Provider。
5. **深度**：嵌套超过上限（默认 4）拒绝，防止 optional 依赖在运行时意外成环。
6. **熔断与并发隔离**：熔断按"调用方 × 查询"；隔离按查询，用 Provider 的 `concurrencyPolicyRef` 定的并发上限，拿不到名额立即拒绝，不排队（尽早卸载负载）。
7. **事务与范围**：挂起调用方的 Unit of Work（连同连接与持久化上下文），在 Provider 的 Owner 上下文开只读 Unit of Work，事务超时取剩余截止时间，数据库语句到时即停；租户范围为调用方租户。复用 `OwnerBoundaryProxies` 与 `OwnerUnitOfWork` 的挂起，改用 `readOnly`。
8. **执行**：调用 `QueryHandler.handle`，等到截止时间（与投递核心同一做法）；超时取消，结束只读事务。
9. **结果**：必须是声明的生成类型（拒绝实体、代理、可变集合）；`null` 视为 Provider 错误，未找到只能用 `Optional.empty()`。
10. **恢复与重试**：恢复调用方 Unit of Work；只按 consumes 的 retry 策略、只对暂时性故障、在剩余截止时间内重试，熔断打开时不重试。
11. **遥测**：§5.7。

### 5.3 平台策略目录（查询部分）

写法与事件的策略目录（K20）相同：清单只能引用，不能定义；不认识的名字启动即失败。

| 字段 | 策略 | 含义 |
|---|---|---|
| `scopePolicyRef` | `query-caller-tenant` | 调用方必须在租户调用里；Provider 在该租户内执行，仓库的租户过滤生效。没有跨租户查询（multi-tenant §6.4） |
| | `query-platform` | Provider 只读平台全局数据（multi-tenant §6.1 白名单表）；租户与平台调用方都可以调用 |
| `accessPolicyRef` | `declared-consumers` | 在 `queries.consumes` 里声明它的插件都可以调用；用于不含个人信息的引用校验类查询 |
| | `on-behalf-of:<权限>` | 调用方当前调用的终端主体必须持有 Provider 声明的这个权限，防止调用方替没有权限的用户读数据；没有终端主体的调用（事件、任务）拒绝 |
| | `on-behalf-of-or-service:<权限>` | 同上，但允许没有终端主体的调用 |
| `timeoutPolicyRef` | `query-interactive`、`query-background` | 值由 Host Profile 配置（缺省 2 秒、10 秒），不得超过硬上限 `brix.query.max-deadline`；硬上限必须配置（MESSAGE-005） |
| `concurrencyPolicyRef` | `query-standard` | 每个查询的最大并发，由 Host 配置（缺省 32） |
| `retryPolicyRef` | `query-no-retry` | 不重试（推荐的缺省） |
| | `query-transient-retry` | 只对暂时性故障再试 1 次：指数退避加 full jitter，在剩余截止时间内，熔断打开时不试 |

熔断参数不进清单（根的清单字段里没有它，MANIFEST-026 不许伪造占位），由 Host 配置：最近 20 次调用里失败率达到 50%（至少 10 次）打开，10 秒后半开放行 3 次试探。

### 5.4 错误码

| 错误码 | 什么时候 | 计入熔断 | 重试 | 建议的外部映射 |
|---|---|---|---|---|
| `query.provider_missing`（`PROVIDER_MISSING`） | 没有解析到 Provider；Provider 已 FAILED 或 STOPPED | 否 | 否 | 503 |
| `query.access_denied` | 访问策略拒绝：没有终端主体、缺权限、范围不符 | 否 | 否 | 403 |
| `query.invalid_request` | 请求为空或不符合契约（Provider 抛 `QueryRequestInvalidException`） | 否 | 否 | 500（调用方的缺陷） |
| `query.deadline_exceeded` | 截止时间已到，调用前或执行中 | 是 | 否 | 504 |
| `query.rejected` | 被拒绝准入，`reason` 为 `capacity`（隔离已满）、`draining`、`no-invocation`、`depth` | 否 | 否 | 503 |
| `query.circuit_open` | 熔断打开 | — | 否 | 503 |
| `query.serialization_failed` | 结果不是声明的生成类型；严格模式下不符合 Schema（D39） | 是 | 否 | 500 |
| `query.provider_failed` | Provider 抛出未预期异常，或其数据库暂时不可用 | 是 | 暂时性故障可重试 | 500，映射为 `platform.unknown` |

- 未找到不是错误：`Optional.empty()`（ERROR-009）。
- Provider 的预期失败只有"未找到"与"请求无效"两种，领域错误码不进查询契约（D41）。
- 原因只记在日志与 Trace 里（例如 `provider_failed` 的 cause），不带出到调用方（ERROR-010）。

### 5.5 生命周期、就绪与停机

- **解析**：在 H3 与命令同一处做（§4.3）。optional 插件被移除后，回到 H3 重算 Provider（BOOT-012）。
- **发布**：Provider 的查询入口进 Host 入口快照，与其他入口同一代次原子发布（A-25）。B3 之前没有任何调用能执行，也就没有查询。
- **就绪**：Consumer 的 pluginReady 加一项——每个 required 查询的 Provider 处于 STARTED、入口已发布、健康为 UP 或 DEGRADED（LIFE-002）。熔断状态不参与就绪，避免一次依赖抖动带动整台主机 not ready。
- **运行期 Provider 失效**：required 依赖方变为 not ready，恢复后可重新 ready；optional 依赖方的调用抛 `PROVIDER_MISSING`，就绪不变（LIFE-003）。
- **Drain**：按 LIFE-005 字面，查询入口与其他入口一起摘除，之后发起的查询返回 `query.rejected(reason=draining)`。R2 批准后改为：已准入调用内发起的查询照常执行，直到该调用结束；Provider 按依赖逆序在依赖方之后停止（D45）。

### 5.6 契约形状与兼容

- **生成的类型不可变**：请求、响应都是生成的不可变类型，集合做防御性拷贝；用 builder 构造。同一主机只有一份 Provider 的 api 构件（LAYER-010），已编译的 Consumer 运行时用的是新版的类：Minor 新增可选字段时，builder 让旧的调用代码照常运行。施工时生成的是 record，并为之前每个 Minor 保留一个构造器，所以旧代码直接调用构造器也照常运行（§12.3）。
- **兼容检查**：方案原定 CI 把 api 构件与上一个发布版本做二进制比对。施工时改为生成器自带的检查：api 构件保留已发布的各版本 Schema，生成器逐个比对 Minor；`src/main/brix/contracts.api` 列出公开 API，只许增加，`ContractSourcesTest` 在每次构建里检查（A-20，§12.3）。
- **结果有上限**：响应 Schema 里的数组必须声明 `maxItems`；列表类查询必须分页（页大小有上限）；按 ID 列表批量查询的请求数组同样有上限。生成器拒绝没有上限的数组。
- **未找到**：单对象查询的响应声明为可空，生成 `Optional<…>`；不得用 `null`、空对象或错误码表达（MANIFEST-027、ERROR-009）。
- **枚举是开放的**（CAP-021）：Provider 的新版本可能加枚举值，调用方对生成的枚举必须写 `default` 分支。
- **主版本并存**：弃用窗口内 Provider 同时发布两个主版本（两条 provides、两个 handlerId），api 构件里两套生成类型都保留（CAP-023）。
- **不缓存别人的数据**：Consumer 不缓存查询结果；Provider 需要缓存时放在自己的缓存命名空间（DATA-001），按租户隔离（multi-tenant §10）。
- **读到的是 Provider 已提交的数据**：刚提交给 Provider 的命令在 Provider 处理之前查不到，属于最终一致；作者文档写明。

### 5.7 可观测

- **Trace**：调用方建 CLIENT span，Provider 一侧建 SERVER span（父为 CLIENT）；属性按已锁定的 semconv 1.23.1：`rpc.system=brix`、`rpc.service=<Provider 插件>`、`rpc.method=<queryType>`；失败标为错误并带错误码；不放请求与结果（OTEL-002、005）。K8 的 span 接口增加 CLIENT/SERVER 两种。
- **指标**（标签只有调用方插件、queryType、结果或错误码）：调用次数、耗时直方图、在途数、隔离拒绝数、熔断状态；不用 tenantId、userId（OTEL-006）。
- **告警**（企业主机 `queries.rules.yml`，promtool 测试）：熔断打开超过 5 分钟（warning）；`provider_failed` 与 `deadline_exceeded` 的比例超过阈值（warning）。required 依赖导致的 not ready 由已有的就绪告警覆盖。
- **日志**：`event=query.failed`，带调用方、queryType、错误码、traceId，不带请求与结果。

### 5.8 连接池与嵌套调用

挂起的调用方事务仍占着它的数据库连接，Provider 的只读事务另取一个；嵌套 N 层时一个线程最多占 N+1 个连接。并发高时连接池可能被占满，所有线程都在等连接（与 requires-new 嵌套同类的问题）。对策：

1. 调用深度上限（默认 4，§5.2 第 5 步）；
2. 取连接的等待不超过剩余截止时间，取不到即 `query.provider_failed`（暂时性），不无限等；
3. Unit of Work 在第一次访问数据库时才取连接；持久化适配器还没有做到的，用 `LazyConnectionDataSourceProxy` 补上，这样"先查询、后写入"的 Handler 在查询期间不占连接；
4. 启动时比较连接池大小与请求、投递线程数，明显不足时告警；
5. 作者文档：先查询、后写入。

### 5.9 查询里的副作用

Runtime 在查询调用里拒绝副作用（MESSAGE-002）：持久化是只读事务，数据库层拒绝写；`EventBusCapability`、`CommandCapability`、`NotificationCapability` 的代理看到当前调用是查询就抛错，查询以 `query.provider_failed` 失败，原因记进日志。一致性套件逐项覆盖。

### 5.10 传输接口

`QueryTransport`（L2B 内部，插件看不到）：`ready()`、`execute(provider, invocation)`。本期只有进程内实现。以后某个 Provider 拆到独立主机进程（LAYER-013）时加远程传输：请求与结果按 Schema 序列化并校验、工作负载身份与 TLS（SECURITY-006）、截止时间随请求传递、远端 SERVER span。一致性套件对所有传输通用（§6）。

## 6. 一致性测试套件

所有传输都通过同一套测试（进 runtime 的测试 jar，在一次性 PostgreSQL 上跑）：

- **解析**：唯一 Provider；版本范围；主版本并存；required 缺失 Resolve Failed；optional 缺失可降级；required 成环启动失败；未知策略；Schema 与生成类型不一致；清单与 Factory 不一致；没有配硬上限。
- **正常路径**：结果正确；未找到为 empty；请求与结果不可变。
- **上下文与租户**：Provider 收到的租户、主体、Trace、截止时间都来自调用方；租户 A 的调用读不到租户 B 的数据；平台调用方调 `query-caller-tenant` 被拒（T-9）。
- **访问**：未声明的查询在 P4 失败；`on-behalf-of` 缺权限被拒；事件 Handler 里调 `on-behalf-of` 被拒、调 `on-behalf-of-or-service` 通过。
- **事务**：调用方有写事务时被挂起；Provider 在只读事务里执行、写入被拒；结束后调用方事务恢复并可提交；锁、连接与持久化上下文不传播（GOVERNANCE-021）。
- **副作用**：查询里发事件、提交命令、发通知被拒。
- **韧性**：截止时间（调用前已耗尽、执行中超时、数据库语句超时）；隔离已满；熔断打开与半开恢复；只对暂时性故障重试且在截止时间内；对访问拒绝、请求无效不重试。
- **生命周期**：B3 之前没有查询执行；Provider 运行期失效时 required 依赖方 not ready、恢复后 ready；Drain 之后的查询（按 D45 的结论）。
- **可观测**：调用方上下文 → CLIENT → SERVER → Handler 的 span 链，失败标记；指标标签不含 tenantId。
- **连接池**：嵌套到深度上限；连接池耗尽时在截止时间内失败，不挂起。

### 9.2 需要改蓝图的两处（RFC 建议，负责人决定）

**R1 multi-tenant：运维模块的只读路径改为内部契约（对应 D36）**

| 条款 | 现文 | 建议改为 |
|---|---|---|
| §6.3 第 4 点 | 只读数据由租户 Data Owner 发布 typed Query；平台运维动作经内部契约 | `platform-admin` 的只读与运维动作都经 descriptor 已声明且 allowlist 批准的内部契约 |
| §11.2 `TenantUsageQuery` 行 | 当前 tenant，或经批准的 platform-operational 调用方的类型化用量 | 当前 tenant 的类型化用量；`platform-admin` 经 `brix.internal.tenant.administration` 读取 |
| CONTRACT-005 | 平台只读租户数据使用 descriptor 声明的 typed Query | `platform-admin` 读写租户数据都使用 `brix.internal.tenant.administration` |
| §11.5 第 2 条 | `platform-admin` 只能按 descriptor 的 `queries.consumes` 调用 typed Query | 跨租户只读查询与聚合由 Data Owner 经版本化内部契约提供给 `platform-admin`，每次调用记 Platform Audit；插件的 typed Query 只在调用方当前租户内 |
| T-3 | 跨租户读取必须是 Owner typed Query；platform-operational 写入必须是 allowlist internal contract | platform-operational 的跨租户读写必须是 allowlist internal contract，并记录平台审计；插件不得跨租户读取 |

- 理由：根 LAYER-016 已规定运维模块"其平台数据访问 MUST 仅经对应 Data Owner 的内部契约"，HOST-014 的 descriptor 没有 `queries.consumes`，HOST-024 冻结了 `OperationalContext` 的方法；multi-tenant 自己的 §10.1 第 3 条与 super-admin §2.1 也写的是内部契约。按根 AUTH-003 与 multi-tenant 文首的"冲突裁决"，以根为准，修订专项。
- 只改文字，不改 DDL、Token、T 红线编号与隔离语义；兼容代际不变。代码已经是这样做的。
- 冲突从 multi-tenant 4.0 起一直存在，此前没有登记。

**R2 根：Drain 时已准入调用内发起的查询（对应 D45）**

- 现文：LIFE-005、BOOT-011、HOST-010 要求 Drain 先原子摘除全部入口（含 Query），摘除后到达的新请求不得进入 Handler。
- 问题：查询总是在某个已准入调用的执行中发起。按字面，已准入的 HTTP 请求在停机窗口里再发起的查询会失败，滚动发布时会有一小批 5xx。gRPC 等的优雅停机只拒绝新的外部请求，已在处理的请求连同它的下游调用照常完成。
- 建议：明确"Drain 关闭的是新的根准入；已准入调用内发起的 Query 属于该调用的 in-flight 工作，在该调用结束前照常准入；Provider 按依赖逆序在依赖方之后停止；Fatal 时仍一律拒绝"。
- 变更类型由负责人认定：作为澄清走 Patch RFC；若按 GOVERNANCE-008 认定为生命周期语义变更，则是 Major，代价大于收益，维持字面执行即可。

## 10. 风险与对策

| 风险 | 对策 |

| 同步调用把 Provider 的故障传给调用方 | 截止时间、隔离、熔断；optional 依赖显式降级；required 依赖只影响依赖方就绪 |

### 12.2 TenantReferenceQuery 的契约

- 查询类型 `platform-tenant.tenant-reference` 1.0.0，optional：引用不属于调用方租户时为空，包括别的租户的 ID，与不存在无法区分（T-9）。
- 请求 `TenantReferenceQuery{refId, refKind}`：`refId` 为正整数（与 platform-tenant 事件 Schema 一致），`refKind` 为 `MEMBER` 或 `PRINCIPAL`（CONTRACT-003），不带租户。
- 结果 `TenantReference{active}`：成员或主体当前是否为 ACTIVE。不暴露原始状态枚举：两类状态的取值不同，暴露后 platform-tenant 改生命周期就是对所有调用方的不兼容变更。
- 策略：`query-caller-tenant`、`declared-consumers`（结果不含个人信息，§5.3）、`query-interactive`、`query-standard`。
- 字段带 `x-brix-classification`（根 SECURITY-008），生成器接受这个标记，不影响类型。

### 12.3 与方案的出入

| 方案 | 施工 | 原因 |
|---|---|---|
| provides 写 `version` | 不写；版本由两个 schemaRef 给出，二者必须相同 | 运行时与 devtools 两份清单 Schema 的 `queryProvider` 本来就没有 `version`（MANIFEST-026 不许伪造字段） |
| 响应 Schema 声明可空（`find-shipment-result`） | 响应 schemaRef 指向结果对象本身（`shipment/1.0.0`）；"可能为空"写在 `META-INF/brix/queries/<queryType>/<版本>.json` 的 `optional` | 结果对象的 Schema 可与 HTTP 端点共用；生成的 `QueryType` 仍是 `Optional<…>`，满足 MANIFEST-027 |
| 生成器是 Maven 插件，构建时生成 | 生成的源码检入仓库，api 构件的 `ContractSourcesTest` 比对；`-Dbrix.contracts.write=true` 重新生成 | 离线的共享机没有编写 Maven 插件所需的工具链；检入的源码在评审里可见 |
| 不可变类加 builder；CI 做二进制兼容比对 | record 加 builder，并为之前每个 Minor 保留一个构造器；`contracts.api` 只许增加，每次构建检查；生成器逐个比对已发布的 Minor | record 保持与 Jackson 和调用代码的直接配合；保留的构造器消除了 D38 担心的 `NoSuchMethodError`；离线环境没有二进制比对工具 |
| 删除 `bindQueryHandler(实例)` | 保留为已弃用 | CAP-019、CAP-023 不允许在 Minor 里删除 L2A 方法；§7.1 第 5 条的"按实例绑定已删除"只能在下一个 Major 达成 |
| 隔离用 Resilience4j | 熔断用 Resilience4j 2.4.0（`runtime-orchestrator` 直接依赖），隔离用 `java.util.concurrent.Semaphore`，拿不到名额立即拒绝 | 不排队的信号量就是方案要的隔离，不必再引入 Bulkhead 模块 |
| 示例类型名 `ShipmentView`、`OrderDetail` Handler、`ShippingQueries` | `Shipment`、`ShowOrder`、`SampleShippingQueries` | 生成器按 Schema 名与插件 ID 命名 |
| 外部映射是"建议" | 端点的 Error Boundary 按 §5.4 映射 `BrixQueryException`：503、504、403，`provider_failed` 为 `platform.unknown`，响应只带错误码 | 不映射时调用方拿到 Spring 的缺省 500，看不出是暂时不可用还是缺陷；其他 `BrixException` 的映射是相邻偏差（§1.4） |
| — | 生成器接受 `x-brix-classification` | 查询契约与事件 Schema 一样要标数据分类（SECURITY-008） |
| — | 启动期能力校验把 `QueryCapability` 当作按插件提供的能力：Host 配了查询截止时间硬上限即满足 | 它不登记在全局能力注册表里，与 `PersistenceCapability` 同类 |

### 12.4 未做与遗留

1. **连接池（§5.8 第 2～4 条）没有做**：取连接的等待仍是连接池自己的超时（企业主机 `spring.datasource.hikari.connection-timeout: 30000`，池大小 20），不受查询截止时间约束；没有延迟取连接；启动时不比较连接池与线程数。已有的是深度上限 4、每个查询 32 个并发、事务超时取剩余截止时间。风险：高并发下调用方占着连接再等 Provider 的连接，连接池耗尽时要等 30 秒才失败，而不是在截止时间内失败。建议作为下一项施工。
2. **§6 的一致性套件没有做成与传输无关、进测试 jar 的形式**：用例分在各模块的单元测试里（`QueryGatewayTest` 30 个、`QueryRuntimeTest` 11 个、`QueryPublicationTest` 4 个、`MicrometerQueryMetricsTest` 3 个、`OwnerQueryScopeTest` 4 个、`OTelQueryTracingTest`、`DefaultPluginContextTest`、`CapabilityAutoConfigurationTest`、`RuntimeShellEndpointControllerTest`），连接池用例缺。现在只有进程内一种传输；加第二种传输之前要先抽成套件。§7.1 第 2 条按此不能算满足。
3. **D39 的严格模式（Local Profile 按 Schema 往返校验）没有做**。方案里是"可开"，不影响关闭标准。
4. **任务里不能发起查询**：端点、事件、命令三个 Dispatcher 绑定了当前调用载体，任务（`ManagedTask`）的执行没有绑定，任务里的查询按 fail-closed 返回 `query.rejected(reason=no-invocation)`。§5.2 第 1 条列了 Task；补上要先定任务调用的租户范围与主体（任务没有 `CompletionStage` 方法与调用对象，§1.4）。作者文档按现状写明只能在端点、事件、命令的 Handler 里调用。
5. **脚手架没有预置 `ContractSourcesTest`**：生成的工程按已发布的 3.2.0 构件离线构建，`runtime-contract-generator` 还不是已发布构件。模板与 README 指向作者文档，文档写明了怎么加这个测试。
6. **Q12**：见 §12.5。共享环境部署等负责人批准。
7. **R1、R2**：RFC 草稿未写，等负责人决定（§7.1 第 6 条）。
