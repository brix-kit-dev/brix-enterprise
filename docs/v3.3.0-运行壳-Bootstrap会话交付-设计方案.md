# Bootstrap 会话的交付：设计方案（决定稿）

> **状态**：已批准（2026-11-09 负责人按推荐批准 D109～D113）。施工要等根 3.4.0 那一批发布：D109、D110 要改 super-admin §6 的入口表和身份认证专项的 BFF 端点，规则写进 RFC-013（§6）
> **日期**：2026-11-09
> **依据基线**：runtime-shell 3.3.0（ACTIVE 根蓝图）；super-admin 4.0.1、identity-auth 1.0.1、frontend 1.2.1、multi-tenant 5.1.3（ACTIVE）
> **来源**：[标准链路收尾方案](v3.3.0-运行壳-标准链路收尾-设计方案.md) §11.1 单向门队列"`bootstrap/session` 怎样交付会话"（第 6 点发现，§10.17 第 4 项）

---

## 0. 结论

1. 开 Bootstrap 会话的入口 `POST /api/platform/bootstrap/session` 把会话令牌放在回答正文里。控制台拿到后放在内存，建首位超管时作为 Bearer 发出。这违反三处：
   - 根红线 S-20：Web 客户端不得在响应体里收到 Access Token。主机按访问令牌校验这个令牌（第 10b-7a 点），豁免 EX-2026-002 不包括这个入口；
   - 根 SECURITY-012：浏览器只持有会话 Cookie，令牌只在服务端；
   - super-admin SEC-004 和 §6 末段：会话不进入响应，Bootstrap 的回答只能是非敏感状态。
2. 同一个入口还有两处与 super-admin §6 的表不符：表里写"匿名 + 限流"，实际没有限流（`/api` 下的入口都没有）；表里写 `idempotency: required`，实际是 `not-applicable`。
3. 推荐（§4）：把 Bootstrap 会话交给现有的 BFF。浏览器在身份协议面提交 setup code；BFF 在进程内请身份 Owner 开会话，把令牌存在加密的服务端会话里；浏览器只拿到 `__Host-brix-session` Cookie 和 CSRF 令牌。建首位超管时，BFF 的 relay 把令牌交给 Dispatcher，照第 10b-7a 点的做法校验。身份协议面已有的限流和 CSRF 防护一并用上。
4. 这样改，super-admin §6 的入口表要改，身份认证专项要加一个 BFF 端点，所以要出 RFC-013，并入根 3.4.0 那一批，施工在发布之后。施工完成之前，登记一个过渡期豁免（D113）。
5. 建首位超管的结果重放（第 10b-7 点）不变：调用方仍是这一次会话。

## 1. 现状

### 1.1 流程（2026-11-09 核实）

| 步 | 现在 | 出处 |
|---|---|---|
| 开会话 | 控制台发 `POST /api/platform/bootstrap/session`，正文是 setup code。入口匿名，权限策略 `bootstrap:session`，`idempotency: not-applicable`。Owner 核对 setup code，签发 BOOTSTRAP_SETUP 令牌（JWT），单例行记下它的 jti；回答 `tokenType`、`accessToken`、`expiresIn` | platform-admin 描述符、`OpenBootstrapSessionHandler`、`PlatformBootstrapAdministrationService.openSession` |
| 控制台 | 令牌只放在 hook 的内存里，离到期不到 15 秒时不再使用 | `usePlatformBootstrap` |
| 建首位超管 | 带 `Authorization: Bearer <令牌>` 和 `Idempotency-Key`。主机的令牌校验认出会话，主体是 jti（D96）；Owner 在写入事务里核对并消费；结果按会话和键重放（D95、D100） | 第 10b-7a、10b-7 点 |
| 类型 | 开会话入口还没有类型化：描述符引用的请求、回答两个 Schema 文件都不存在 | platform-admin 的 `schemas/` |
| 共享环境 | 已在 Stage B，开会话答 409（bootstrap is closed）。只有全新安装会签发这个令牌 | `openSession` |

### 1.2 与蓝图的出入

| 条款 | 要求 | 现在 |
|---|---|---|
| 根 S-20 | Web 客户端不得在响应体、URL、脚本可读的 Cookie 或浏览器存储里收到 Access/Refresh Token；CI 和发布阻断 | 回答正文里有令牌 |
| 根 SECURITY-012 | 浏览器只持有会话 Cookie，令牌只在服务端会话里；改变状态的请求要有 CSRF 防护 | 令牌在浏览器内存里，以 Bearer 发出 |
| 根 SECURITY-001 | 匿名入口要限流 | 没有限流 |
| super-admin SEC-004 | setup code/token/session 不进入响应、日志、审计、指标 | 会话在回答里 |
| super-admin §6 末段 | 创建、重置、Bootstrap 的回答只能是非敏感状态与稳定标识，禁止 raw token | 同上 |
| super-admin §6 表 | 开会话：匿名 + 限流；`idempotency: required` | 没有限流；`not-applicable` |
| EX-2026-002 | 豁免旧平台登录、TOTP、setup 的接口和页面，以及控制台 sessionStorage 里的会话，到身份认证 M1 切片 4 | 不包括 Bootstrap 的入口和页面 |

super-admin 自己有一处要一起读：UI-002 写着"Bootstrap session 只保存在完成当前流程所需的最小内存态"，像是允许浏览器拿到会话。和 SEC-004、§6 末段、根 S-20 放在一起，只能理解为浏览器不拿令牌：会话由 BFF 持有，页面只留流程状态。RFC-013 写明这个解读。

### 1.3 现有的 BFF 与身份协议面

| 能力 | 现在 | 出处 |
|---|---|---|
| 会话 Cookie | `__Host-brix-session`：不透明的会话 ID，`Secure`、`HttpOnly`、`SameSite=Strict` | `BffCookies` |
| 服务端会话 | 令牌加密保存在服务端，有闲置超时和绝对时长 | `BffSession`、`BffSessionStore` |
| CSRF | 每个会话有自己的 CSRF 令牌，改变状态的请求要在 `X-Brix-CSRF` 里带上 | `BffController`、`BffSessionRelayFilter` |
| 交给 Dispatcher | `/api/*` 的请求没有 `Authorization` 时，relay 按 Cookie 找到会话，把里面的令牌交给 Dispatcher 的认证步骤，Dispatcher 照常校验 | `BffSessionRelayFilter` |
| 限流 | 身份协议面的保留前缀按来源地址限流；`/api` 下没有 | `ProtocolRateLimitFilter` |
| 进程内请 Owner 办事 | 托管设置页核对设置令牌、完成凭证设置，都经 L2A 能力在进程内调用身份 Owner，不走 HTTP | `IdentityAccountCapability` 的 `findCredentialSetup`、`completeCredentialSetup` |

## 2. 业界做法

2026-11-09 查阅：

- [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017)（OAuth 2.0 for Browser-Based Applications，BCP 212，2026 年 8 月）§6.1 BFF：
  - §6.1.3.2："The BFF MUST enable the Secure flag for its cookies."、"The BFF MUST enable the HttpOnly flag for its cookies."；`SameSite=Strict`、Path `/`、`__Host-` 一类前缀都是 SHOULD；
  - §6.1.3.3："The BFF MUST implement a proper CSRF defense."；只靠 SameSite，在 BFF 与别的应用同站时不够；宜要求浏览器应用带一个自定义请求头；
  - §6.1 的总体目标是不把任何令牌直接交给浏览器里的应用。
- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)："Do not store authentication tokens, session IDs, JWTs, refresh tokens, or any credential in `localStorage` or `sessionStorage`."，推荐 `HttpOnly; Secure; SameSite=Strict` 的 Cookie 或 BFF。
- [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)：SameSite"does not replace a proper CSRF defense in most deployments"；同步令牌与会话里的值不符就拒绝；API 可以用自定义请求头。

放到 Brix：BFF 已经按这些做了（§1.3），根 SECURITY-012、S-20 也是照这个写的。Bootstrap 会话是唯一绕开 BFF、把令牌交给浏览器的地方。

## 3. 方案

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | 把 Bootstrap 会话交给 BFF（§4） | Cookie、加密的服务端会话、CSRF、relay、限流都是现成的；符合根 S-20、SECURITY-011、SECURITY-012；要改 super-admin §6 的入口表，加一个 BFF 端点 |
| B | Runtime 入口自己发 `HttpOnly` Cookie，建首位超管时从 Cookie 读出会话 | 根 SECURITY-011 规定 BFF 会话端点属于身份协议面、只由身份提供方 Adapter 持有，这样等于在 `/api` 下另造一套浏览器会话；CSRF、限流也要另做 |
| C | 代码不改，改 super-admin 允许回答里带会话令牌 | 专项不能放宽根，S-20 是红线 |
| D | 合成一步：建首位超管时直接交 setup code | 改了 BOOT-004 的两阶段模型；setup code 每次都要过网络；结果重放也没有了调用方（D95 靠的就是这次会话） |

## 4. 决定（推荐）

| 编号 | 推荐 | 备选（不推荐） |
|---|---|---|
| D109 交付方式 | 身份协议面新加 `POST /bff/bootstrap/session`，收 setup code。BFF 在进程内请身份 Owner 核对 setup code、签发会话，把 BOOTSTRAP_SETUP 令牌存进加密的服务端 BFF 会话，回答只给有效期和 CSRF 令牌；浏览器只拿到 `__Host-brix-session`。BFF 会话与令牌同时到期；令牌被消费后，只能取回消费它的那次调用的答案（D95）。建首位超管不带 `Authorization`，改带 `X-Brix-CSRF` 和 `Idempotency-Key`；relay 把令牌交给 Dispatcher，照 D96 校验 | 方案 B、C、D（§3） |
| D110 Owner 怎样开会话 | 去掉 `/api/platform/bootstrap/session` 这个 Runtime 入口。BFF 经 L2A 能力在进程内调用身份 Owner 开会话，做法与托管设置页经 `IdentityAccountCapability` 完成凭证设置相同。用现有的能力加方法，还是新加一个只管 Bootstrap 的窄能力，在 RFC-013 里定。L2A 只加不改，算 Minor | 保留这个入口，只收 BFF 在进程内签发的内部凭证（同首位 OWNER 接受入口的做法）：要维护两条路，多一次回环 HTTP，还要一种没有身份的内部令牌。保持匿名、只靠网络位置拦：违反根 SECURITY-001（网络位置不产生信任） |
| D111 幂等 | 开会话不做结果重放：每次开一个新会话、替换旧的，重试无害；答案里有凭证，本来就不能保存。super-admin §6 表里这一行随入口移走，`required` 一并去掉。建首位超管的重放不变 | 照 §6 做成 `required`：要么把带凭证的答案存下来，要么重放时不给凭证，两样都不对 |
| D112 限流与 CSRF | 开会话用身份协议面的按来源限流（BOOT-003、根 SECURITY-001）。开会话是匿名的 POST：只收同源请求（看 `Origin` 或 `Sec-Fetch-Site`），只收 JSON。建首位超管用 BFF 的同步 CSRF 令牌 | 只靠 SameSite：RFC 10017 和 OWASP 都只把它当纵深防御 |
| D113 过渡期 | 施工完成之前，在 `architecture-exemptions.json` 登记一个豁免：开会话回答里的令牌（S-20、SECURITY-012、SEC-004），对象是这个入口和控制台的 Bootstrap 页面，2027-02-28 到期，施工完成即关闭 | 不登记：违反了红线却没有登记，和别的豁免做法不一致 |

## 5. 对接口和回答的影响

- 控制台：Bootstrap 页面先调 `/bff/bootstrap/session`，再调建首位超管，不再接触令牌。UI-002 的"最小内存态"只剩流程状态和 CSRF 令牌。
- `POST /api/platform/bootstrap/session`：不再存在。
- 建首位超管：回答、错误码和结果重放都不变；改变状态的请求缺 `X-Brix-CSRF` 或不对时，由 BFF 答 403 `BFF_CSRF_REJECTED`。
- `GET /api/platform/bootstrap/status`：不变。
- 一次性回归的 Bootstrap 段，和企业仓的 `scripts/remote-deploy/bootstrap-e2e.sh`，都要改为走 BFF：保存 Cookie，带 CSRF 令牌。
- brix 的超管 Bootstrap 运维手册（§11.1 待办里"下一次全新安装之前"那一项）按新流程写。

## 6. 规则写在哪里

RFC-013，随根 3.4.0 那一批：

- super-admin 4.0.2：§6 表去掉开会话一行，在表下注明开会话在身份协议面（`POST /bff/bootstrap/session`）；UI-002 写明会话由 BFF 持有、页面只留流程状态；BOOT-004 和 SEC-004 不变。
- identity-auth 1.0.2：身份协议面的 BFF 端点加 `POST /bff/bootstrap/session`，写明它只开 BOOTSTRAP_SETUP 会话、经身份 Owner 的能力核对 setup code。
- 根不改：S-20、SECURITY-011、SECURITY-012 已经覆盖。

## 7. 相关发现（不在本稿内）

- `/api` 下的匿名入口都没有限流：`bootstrap/status`、`bootstrap/session`，以及豁免 EX-2026-002 里的两个旧平台登录入口。根 SECURITY-001 要求匿名入口限流。按本稿，开会话移到身份协议面后由那里的限流覆盖；`bootstrap/status` 只读、只答开关状态。补上不改接口，算双向门，进待办"承载真实业务之前必须完成"。
- 开会话入口还没有类型化（§1.1）。按 D110 这个入口会去掉，不另补。
