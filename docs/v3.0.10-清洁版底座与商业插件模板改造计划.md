## 0. 架构基线声明

已读取并校验当前仓库架构基线：

- `runtime-shell=3.0.10`
- `frontend=1.1`
- `super-admin=3.0`
- `multi-tenant=4.0`
- `runtime-shell=3.0.11` 为非指导 `CANDIDATE`

本计划只使用上述 ACTIVE 基线。`v3.0.9`、`RuntimeContext + AbstractModule`、Spring Controller 自动发布、启动期业务写入、`ownerIdentityId` 创建租户、旧 Kafka Outbox 适配器等均视为待清理遗留。

## 1. 清洁版前提

### 1.1 允许清洁初始化

由于项目尚未上线，且用户已声明无需处理历史迁移兼容，本计划采用 `Pre-release Clean Initialization`：

1. 可以直接重建开发数据库；
2. 可以将尚未对外执行的 Flyway migration 收敛为符合 3.0.10 的清洁初始序列；
3. 可以删除、重命名或重写旧 3.0.9 开发期表、DTO、Controller 和测试夹具；
4. 不需要为旧 `app_tenant_record`、`owner_identity_id`、旧 Bootstrap 数据库用户、旧 `tenant_outbox/tenant_inbox` 写兼容迁移；
5. 不伪造生产 history、部署制品、SBOM、签名或运行态验收记录。

清洁初始化边界一旦进入首个共享环境、候选发布制品、外部消费者或需保留数据，即不可逆结束；此后只能用前滚迁移和真实环境证据。

### 1.2 目标产品形态

目标不是继续修补一个混合 3.0.9/3.0.10 的系统，而是形成一个干净的 Brix 底座：

```text
Host
  -> Runtime Shell 3.0.10
     -> required platform-operational: platform-admin
     -> required OSS plugin: platform-tenant
     -> optional/required commercial plugin: app-booking template
     -> L2C adapters: db / cache / kafka transport / outbox persistence / notification adapter
```

`platform-tenant` 提供 OSS 多租户底座和默认 3 租户配额。`app-booking` 只作为商业插件模板进入 Host，不拥有平台租户目录、成员、邀请、配额、平台超管路由或 `sys_*` 写权限。`app-tenant` 不作为 Phase 5 的业务开发对象；既有资产只作为遗留风险扫描和清理对象处理。

## 2. 总目标

1. 清理旧 3.0.9 架构依赖，形成以 `BrixPlugin + PluginContext + ServiceLoader + Manifest + Dispatcher` 为主链的 3.0.10 Runtime Shell；
2. 将 Bootstrap Anchor 完全改为 3.0.10 `platform-operational` 模型：无 `ApplicationRunner`、无启动期业务写入、无数据库 Bootstrap 可登录用户；
3. 保留并收口 `platform-admin` 为 `platform-commons` 下唯一 `moduleKind=platform-operational`；
4. 保留并收口 `platform-tenant` 为 OSS 平台租户目录唯一 Data Owner；
5. 保证 `FIRST_OWNER`、配额、租户激活、审计和 CRITICAL 事件 Outbox 在 `platform-tenant` Owner 本地事务内完成；
6. 将 Outbox/Inbox 收口到根蓝图 canonical envelope、Runtime Relay、Owner Outbox、Consumer Inbox，不保留旧 Kafka Outbox SSoT；
7. 将 `app-booking` 改造成商业插件模板壳：三 artifact、唯一 manifest、唯一 ServiceLoader provider、可被 Host 组装和 Runtime 启动；
8. 建立阻断性验证，避免未来商业插件继续复制旧 Controller、`ownerIdentityId`、平台租户目录或 3.0.9 入口模型。

## 3. 不做范围

1. 不实现真实商业业务能力、License 服务、计费、SSO、白标、高级隔离或合规报告；
2. 不迁移 `case/products/partners/messenger/contracts/storage/identity/carousel/intake` 等其他商业插件；
3. 不支持动态插件安装、热卸载、多 ClassLoader、OSGi 或 PF4J；
4. 不建设通知中心、邮件 Outbox、退信同步、短信、站内信或移动推送；
5. 不把安全能力商业化；租户隔离、JWT、防泄漏、审计仍属于 OSS 底座责任；
6. 不让任何商业插件（包括 `app-booking`、`app-tenant`）访问 internal contract、`/api/platform/**` 或平台租户权威表；
7. 不用脚本直接写库作为正式 Bootstrap、首位平台超管或 FIRST_OWNER 验收路径；
8. 不把 Maven 测试通过等同于真实 Host/HTTP/Relay 验收。

## 5. 关键架构决策

### 5.1 app-booking 的模板定位

`app-booking` 在 Phase 5 不承载真实预约业务开发，只作为商业插件模板壳进入 Host。它不得表示平台租户目录，也不得提供租户创建、激活、挂起、成员管理或平台管理接口。

清洁版 `app-booking` 的最小模板定位为：

```text
Commercial Plugin Template
  -> plugin-api: public DTO / schema refs
  -> plugin-core: empty or sample domain service without platform tenant authority
  -> plugin-server: BrixPlugin provider + manifest-declared endpoint factory
  -> optional ui-web: plugin shell page
```

最小可运行能力可以是：

1. `GET /api/app-booking/v1/template/status`：返回插件 id、版本、runtime status；
2. `GET /api/app-booking/v1/template/features`：返回静态 capability 示例或空 feature list；
3. 可选 `BEST_EFFORT` 示例事件不进入首轮；若声明 CRITICAL/STANDARD，则必须同时实现 Owner Outbox/Inbox。

该模板不得出现：

- `/api/v1/tenants`
- `/api/admin/tenants`
- `ownerIdentityId`
- `app_booking_tenant_record` 或 `app_tenant_record` 作为平台租户目录
- `app_booking_tenant_member` 或 `app_tenant_member` 作为平台成员权威
- `tenant_outbox` / `tenant_inbox` 作为第二套平台租户 Outbox/Inbox
- `sys_*` 表写入
- `PlatformAdminCapability`
- `TenantProvisioningCapability`
- Spring `@RestController` 自动发布业务入口

### 5.2 platform-tenant 的 OSS 边界

`platform-tenant` 是唯一平台租户 Data Owner，负责：

1. `sys_tenant`
2. `sys_tenant_member`
3. `sys_tenant_principal`
4. `biz_user_profile`
5. `sys_tenant_invitation`
6. `sys_tenant_config`
7. `sys_installation_quota`
8. `platform_tenant_outbox`
9. `platform_tenant_inbox`
10. 租户审计受托记录

开源版默认 3 租户配额是 Open Core 产品策略和 License/配置约定，不是安全边界，也不能被 `app-booking` 或 `app-tenant` 复制实现。

### 5.3 Bootstrap Anchor 的清洁模型

Bootstrap Anchor 只允许通过 Runtime 已发布入口执行：

```text
Host B0-B3 完成
  -> platform-admin endpoint published
  -> setup code verifier
  -> BOOTSTRAP_SETUP session
  -> create first PLATFORM_SUPER_ADMIN
  -> password + TOTP first verification
  -> formal admin ACTIVE
  -> Stage B closed permanently
```

禁止：

1. `ApplicationRunner` / `CommandLineRunner` 创建身份、写业务状态或发送通知；
2. Host 启动类执行业务写库；
3. `onStart()` 执行业务 Handler；
4. 数据库中存在可登录 `BOOTSTRAP` 用户；
5. Stage B 关闭后因重启、配置回放或代码回滚重新打开。

### 5.4 Outbox/Inbox 清洁模型

Outbox/Inbox 只保留根蓝图 canonical 语义：

```text
Owner local transaction
  -> business state
  -> owner audit
  -> canonical outbox record
commit
  -> Runtime Outbox Relay
  -> broker transport
  -> consumer inbox
  -> consumer side effect
```

清理目标：

1. Host 移除 `infra-adapter-kafka-outbox`；
2. Kafka Adapter 只作为 canonical envelope transport；
3. Outbox persistence 使用 `infra-adapter-outbox` 或 Runtime 指定的 broker-neutral persistence；
4. `brix.outbox.relay.enabled=true` 和 `brix.outbox.relay.persistence.enabled=true` 在 Host Profile 中显式配置；
5. CRITICAL/STANDARD 事件必须有事务提交、Relay 重试、park、Inbox 去重和重复消费测试；
6. BEST_EFFORT 可以直发，但不得承诺最终送达。

## 6. 分阶段施工计划

### Phase 0：清洁版范围冻结与遗留扫描

目标：确认本次确实走清洁初始化，不再为旧 3.0.9 数据模型写兼容。

改造动作：

1. 记录用户授权前提：未上线、无共享环境、无保留数据；
2. 扫描并列出 `3.0.9`、`RuntimeContext`、`AbstractModule`、`ApplicationRunner`、`CommandLineRunner`、`ownerIdentityId`、`/api/v1/tenants`、`infra-adapter-kafka-outbox`；
3. 确认哪些是 legacy 注释可暂留，哪些是新主链阻断；
4. 固定目标 Host composition：Runtime + platform-admin + platform-tenant + app-booking template。

验收：

- 输出遗留清单和保留/删除判定；
- 不改冻结蓝图；
- 不进入代码施工前必须重新跑架构基线校验。

### Phase 1：Runtime/Host 3.0.10 清洁装配

目标：Host 静态组装 Runtime、Adapter、platform modules 和 app-booking template，所有入口经 Runtime Dispatcher。

改造动作：

1. `host-shell-standalone` 移除旧 `infra-adapter-kafka-outbox`；
2. Host 配置新增 canonical Outbox Relay 与 persistence；
3. Host contract tests 更新为 `platform-admin` operational module 和 `app-booking` plugin discovery；
4. 删除或隔离旧 `/api/v1/tenants` Host contract 断言；
5. 入口发布只验证 Runtime route snapshot，不验证 Spring Controller。

验收：

- Host package 不跳测通过；
- Host 启动能发现 `platform-admin`、`platform-tenant`、`app-booking`；
- `/api/platform/**` 不由 Host fallback Controller 发布；
- required module 缺失时 Host fail-fast。

### Phase 2：Bootstrap Anchor 清洁改造

目标：完全移除启动期业务副作用。

改造动作：

1. 删除 `SuperAdminBootstrapRunner` 活动主链；
2. 删除对应 `ApplicationRunner` bean 和正向测试；
3. 清洁 DDL 只初始化 Bootstrap singleton/verifier 必需结构，不创建可登录 Bootstrap 数据库用户；
4. `platform-admin` endpoint 通过 `OperationalContext` 调用 Owner internal contract；
5. setup code、session token、MFA secret、setup URL 不进入响应、日志、审计、trace、metrics 或前端持久化。

验收：

- 静态扫描无平台身份启动期写入 Runner；
- Stage A 只能在 Host B3 后通过 Runtime Endpoint 使用；
- 首位正式超管 ACTIVE 后 Stage B 永久关闭；
- 重启、配置重放、旧 setup code 均不能重开。

### Phase 3：platform-tenant 清洁初始化与 FIRST_OWNER

目标：OSS 多租户底座直接初始化为 multi-tenant 4.0 语义。

改造动作：

1. 清洁初始化 `sys_tenant`、`sys_tenant_member`、`sys_tenant_principal`、`biz_user_profile`、`sys_tenant_invitation`、`sys_installation_quota`；
2. 新建租户只产生 `PENDING_ACTIVATION`；
3. 平台超管只能发起、重发、撤销 `FIRST_OWNER` 邀请；
4. 接受邀请时锁邀请、锁租户、锁安装配额；
5. 同一事务创建 `ACTIVE OWNER`、Profile、激活租户、`used + 1`、接受邀请、写审计和 CRITICAL Outbox；
6. 重复接受和并发接受不得重复创建 Member/Profile 或重复增加配额。

验收：

- 创建租户请求不含 `ownerIdentityId`；
- 平台超管不是租户 member；
- `ACTIVE/TRIAL` 租户必须至少存在一个 `ACTIVE OWNER`；
- 配额并发测试、回滚测试、幂等测试通过；
- `TenantFirstOwnerAccepted` 使用 canonical Outbox。

### Phase 4：Outbox/Inbox 最小可靠闭环

目标：Outbox 达到 3.0.10 最小最佳实践，不保留旧双 SSoT。

改造动作：

1. `platform_tenant_outbox` 和 `platform_tenant_inbox` 作为 Owner 受托表；
2. `TenantFirstOwnerAccepted` 在 Owner 事务内写 Outbox；
3. Runtime Relay claim/lease/retry/park；
4. Consumer 使用 `(handlerId,eventId)` Inbox 去重；
5. Host Profile 显式启用 Relay 和 persistence；
6. 删除旧 `tenant_outbox/tenant_inbox`、`infra-adapter-kafka-outbox` 运行依赖和相关文档暗示。

验收：

- Outbox 事务提交测试；
- Relay 重试/park 测试；
- 重复消费 Inbox 去重测试；
- Host 启动时 Relay bean 存在且配置 owner；
- 真实 Host 运行证据与单测分别记录。

### Phase 5：app-booking 商业插件模板化

目标：`app-booking` 成为 3.0.10 商业插件模板壳，可被 Host 顺利组装和运行；`app-tenant` 不进入本 Phase 的实际业务开发任务。

改造动作：

1. 保留 `booking-api`、`booking-core`、`booking-server` 三 artifact 结构；
2. `booking-server` 保留唯一 `META-INF/brix/plugin-manifest.yaml`；
3. `booking-server` 保留唯一 `ServiceLoader<BrixPlugin>` provider；
4. `configure(PluginBootstrapContext)` 只登记 manifest 声明的 Handler Factory；
5. 删除或隔离实际预约业务 Controller、DTO、Service、Entity、Repository、migration，使本 Phase 只保留模板壳；
6. 新增最小模板 endpoint，例如 `/api/app-booking/v1/template/status`；
7. 无业务功能时不声明 CRITICAL/STANDARD Event，不创建 Outbox/Inbox；
8. 如果保留 UI，只展示插件已装配状态，不做预约业务流程或租户目录管理。

验收：

- `app-booking` 无 `ownerIdentityId`；
- `app-booking` 无 `/api/v1/tenants` 和 `/api/admin/tenants`；
- `app-booking` 无 `app_booking_tenant_record`、`app_tenant_record` 等平台目录表；
- `app-booking` 不写 `sys_*`；
- `app-booking` manifest/provider/factory 双向一致；
- Host 可 required 或 optional 组装该插件并成功启动。

### Phase 6：Guard、文档与真实运行证据

目标：把本次清洁模型变成可持续门禁。

改造动作：

1. 增加 architecture-guard 规则；
2. 增加 Host contract tests；
3. 增加 app-booking template conformance tests；
4. 更新 README/开发者模板，声明商业插件不得复制平台租户目录，且 `app-tenant` 不再作为后续商业业务开发模板；
5. 记录真实 Host 启动、HTTP、Bootstrap、FIRST_OWNER、Outbox Relay 证据。

验收：

- `validate_architecture_baseline.py --require-active --check-instructions` PASS；
- 定向 Maven 测试 PASS；
- enterprise Host 不跳测测试 PASS；
- 真实 Host/HTTP/Relay 验证 PASS；
- 扫描无阻断遗留。

## 7. 阻断清单

以下任一项存在时，不得声明清洁版完成：

1. 新主链仍存在 `SuperAdminBootstrapRunner` 或其他启动期业务写入；
2. 任一商业插件（包括 `app-booking`、`app-tenant`）仍声明 `/api/v1/tenants` 或 `/api/admin/tenants`；
3. 任意新租户创建请求仍接受 `ownerIdentityId`；
4. 任一商业插件（包括 `app-booking`、`app-tenant`）仍拥有平台租户目录、成员、邀请、配额或 `sys_*` 写权限；
5. Host 仍依赖旧 `infra-adapter-kafka-outbox`；
6. CRITICAL/STANDARD 事件绕过 Owner Outbox；
7. `/api/platform/**` 由 Host 或业务 Plugin 旁路发布；
8. `platform-admin` 直接注入 Data Owner Repository/Service；
9. `configure()` 获取 Capability、创建 Handler、启动线程或发布路由；
10. 只有单测，没有真实 Host/HTTP/Relay 证据。
