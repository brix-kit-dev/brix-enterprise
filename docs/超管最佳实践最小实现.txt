请基于当前 Brix / Shinwa Platform 架构，设计“Super Admin 平台超管功能”的最小可落地方案。

目标：实现平台级超管治理闭环，不做过度扩展，但必须符合多租户架构、权限最佳实践、安全审计和运行壳架构红线。

一、核心定位

1. Super Admin 是平台级管理员，不属于任何业务租户。
2. Super Admin 不能建模为普通租户成员角色，不能简单塞进 sys_tenant_member。
3. Super Admin 用于管理平台级资源，例如平台管理员、租户生命周期、平台审计。
4. 平台超管后台和租户后台要逻辑分离。
5. 平台级接口使用 PLATFORM scope，不默认绑定 tenant_id。

二、禁止实现方式

1. 禁止在代码中硬编码字符串判断，例如 "super admin"。
2. 禁止使用 if role == "super admin" 这种方式直接放行。
3. 禁止只在前端隐藏按钮，后端必须做权限校验。
4. 禁止业务插件自行解析 JWT。
5. 禁止业务插件自行实现密码加密、Token 解析、认证逻辑。
6. 禁止把平台超管当作某个租户的 ADMIN。
7. 禁止删除最后一个可用超管账号。
8. 禁止后台展示明文密码。

三、推荐权限模型

1. 使用内置角色：PLATFORM_SUPER_ADMIN。
2. 使用权限码进行真实授权，不要直接依赖角色判断。
3. 角色只是权限包，接口放行必须基于 Permission。
4. 权限码建议最小集合：

- platform:admin:read
- platform:admin:create
- platform:admin:disable
- platform:admin:reset-password
- platform:admin:change-own-password
- platform:audit:read
- platform:tenant:read
- platform:tenant:update-status

5. 代码中必须使用常量或枚举，例如：

- RoleCode.PLATFORM_SUPER_ADMIN
- PermissionCode.PLATFORM_ADMIN_CREATE
- PermissionCode.PLATFORM_ADMIN_RESET_PASSWORD

四、最小后端功能

1. 超管登录
   - 支持平台级登录。
   - 登录成功后 Token 体现 PLATFORM scope。
   - Token 中包含 identity_id、roles、permissions 或 permissions reference。
   - 平台超管 Token 不应该伪装成某个 tenant_id 下的租户用户。

2. 超管列表
   - 查询平台超管账号列表。
   - 字段至少包括账号、姓名/昵称、邮箱/手机号、状态、最后登录时间、创建时间、创建人。

3. 新增超管
   - 只有拥有 platform:admin:create 权限的用户可以新增。
   - 新增账号默认 force_password_change = true。
   - 密码必须安全加密存储。
   - 不允许重复创建同一 identity 的平台超管关系。

4. 禁用超管
   - 只有拥有 platform:admin:disable 权限的用户可以禁用。
   - 禁止禁用最后一个 ACTIVE 的超管。
   - 禁用后该账号不能继续访问平台后台。

5. 重置超管密码
   - 只有拥有 platform:admin:reset-password 权限的用户可以操作。
   - 不允许返回明文密码。
   - 推荐生成一次性重置链接或临时密码，并强制首次登录修改。
   - 重置后设置 force_password_change = true。

6. 修改自己的密码
   - 当前登录超管可以修改自己的密码。
   - 必须校验旧密码。
   - 新密码必须符合密码策略。
   - 修改后建议刷新登录态或让旧 token 失效。

7. 租户列表与租户状态管理
   - 平台超管可以查看租户列表。
   - 平台超管可以激活、暂停、恢复租户。
   - 不做复杂计费、套餐、配额管理，先预留字段即可。

8. 平台审计日志
   - 所有超管关键操作必须写审计。
   - 至少记录：
     - SUPER_ADMIN_LOGIN_SUCCESS
     - SUPER_ADMIN_LOGIN_FAILED
     - SUPER_ADMIN_CREATED
     - SUPER_ADMIN_DISABLED
     - SUPER_ADMIN_PASSWORD_RESET
     - SUPER_ADMIN_PASSWORD_CHANGED
     - TENANT_STATUS_CHANGED
   - 审计字段至少包括：
     - actor_identity_id
     - action
     - target_type
     - target_id
     - ip
     - user_agent
     - result
     - reason
     - created_at

五、建议数据表

请根据现有数据库结构评估是否复用已有表，但最小建议如下：

1. sys_identity
   - 平台全局身份表。
   - 存储账号、邮箱、手机号、密码哈希、状态、MFA 状态、最后登录时间等。

2. sys_platform_admin
   - 平台超管授权关系表。
   - 关联 identity_id。
   - 字段包括 status、created_by、created_at、updated_at。

3. sys_role
   - 角色定义表。
   - 至少 seed 一个 PLATFORM_SUPER_ADMIN。

4. sys_permission
   - 权限定义表。
   - seed 平台级权限码。

5. sys_role_permission
   - 角色和权限绑定表。

6. sys_identity_role_assignment
   - 身份与角色绑定表。
   - 支持 scope_type = PLATFORM / TENANT。
   - 平台超管使用 scope_type = PLATFORM。

7. sys_audit_log
   - 平台审计日志表。
   - 所有超管操作必须落库。

如果为了 MVP 简化，可以先实现：
- sys_identity
- sys_platform_admin
- sys_audit_log

但角色码、权限码必须通过常量或枚举管理，不能散落硬编码字符串。

六、最小前端页面

1. 平台超管登录页
2. 平台 Dashboard
3. 超管账号列表页
4. 新增超管弹窗或页面
5. 重置密码弹窗
6. 修改自己密码页面或弹窗
7. 平台审计日志页
8. 租户列表页
9. 租户状态修改操作

七、接口建议

1. POST /api/platform/auth/login
2. GET /api/platform/admins
3. POST /api/platform/admins
4. PATCH /api/platform/admins/{id}/disable
5. POST /api/platform/admins/{id}/reset-password
6. POST /api/platform/admins/me/change-password
7. GET /api/platform/audit-logs
8. GET /api/platform/tenants
9. PATCH /api/platform/tenants/{id}/status

八、安全要求

1. 密码必须使用安全哈希算法，不允许明文存储。
2. 所有平台接口必须后端鉴权。
3. 所有平台接口必须校验 Permission。
4. 平台超管登录失败需要记录审计。
5. 连续登录失败需要考虑锁定或限流。
6. 敏感信息不能写入日志，例如 password、token、secret。
7. Token 过期时间不能过长。
8. 后续可预留 MFA，但 MVP 可以先只保留字段。

九、架构要求

1. 认证、密码、Token、权限校验应放在 platform-auth 或平台通用能力层。
2. 业务插件不得直接实现认证逻辑。
3. Host 继续保持极薄原则，不能把超管业务逻辑写进 Host。
4. 平台超管能力应属于 platform-commons 或 enterprise-platform-admin 这类平台能力模块。
5. 前端页面遵守 View → ViewModel/hooks → Repository 分层。
6. 前端页面不能直接 fetch/axios，必须通过 Repository / HttpCapability。
7. 后端接口、DTO、权限码、审计事件建议集中定义，避免散落。

十、交付物要求

请输出一份落地方案，至少包含：

1. 模块边界设计
2. 数据表设计
3. 后端接口设计
4. 权限码设计
5. 审计事件设计
6. 前端页面设计
7. 登录 Token 设计
8. 关键业务流程
9. 安全控制点
10. 最小实现顺序
11. 不允许违反的架构红线
12. MVP 范围内做什么、不做什么

十一、MVP 暂不做

1. 不做复杂 RBAC 管理页面。
2. 不做自定义角色编辑。
3. 不做复杂组织架构。
4. 不做完整 MFA 流程，只预留字段。
5. 不做计费系统。
6. 不做复杂租户配额管理。
7. 不做跨租户业务数据查询。
8. 不做超管删除，只做禁用。
9. 不做电子邮件/短信通知对接，先预留接口。
10. 不做复杂审批流。

十二、最终验收标准

1. 超管可以登录平台后台。
2. 超管可以新增其他超管。
3. 超管可以禁用其他超管。
4. 系统禁止禁用最后一个 ACTIVE 超管。
5. 超管可以重置其他超管密码。
6. 超管可以修改自己的密码。
7. 超管可以查看审计日志。
8. 超管可以查看租户列表并修改租户状态。
9. 所有平台接口都基于 Permission 校验。
10. 代码中不存在散落的 "super admin" 字符串硬判断。
11. 所有关键操作都有审计记录。
12. 不破坏现有多租户模型和运行壳架构。
