## 0. 名称与验收终点

### 0.1 “首位超管”与“首位 OWNER”必须区分

本文中的两个身份不是同一概念：

| 名称 | 数据范围 | Token / Context | 是否租户成员 |
|---|---|---|---:|
| Bootstrap Anchor | 平台首启引导 | `BOOTSTRAP_SETUP`，短 TTL、一次性、仅 bootstrap 权限 | 否 |
| 首位正式平台超管 | 平台控制面 | Platform Token，完成密码设置与 TOTP MFA | 否 |
| 首位租户 OWNER | 单租户 Actor | `aud=brix-actor` 的 Actor Token，绑定 tenant/member context | 是 |

平台超管不得被写入 `sys_tenant_member`，Bootstrap Anchor 不得被当作正式超管或 Break Glass，首位租户 OWNER 不得使用 Platform Token 进入租户上下文。

### 0.2 本计划验证的完整纵向流程

```text
Host H0-H4 + B0-B3
  -> required platform-operational / Plugin / Capability 全部 Ready
  -> 原子发布 Bootstrap、Platform Admin、Tenant Invitation Runtime Entry
  -> Bootstrap Setup Stage A
  -> 一次性 setup code 换取 BOOTSTRAP_SETUP session
  -> 创建首位正式平台超管 PENDING_SETUP
  -> 身份 Data Owner 经已声明 NotificationCapability 发送平台超管 setup link
  -> 设置密码 + 绑定 TOTP + 首次 TOTP 验证
  -> 首位正式平台超管 ACTIVE
  -> 原子永久关闭 Bootstrap Stage A
  -> 首位超管使用 Platform Token 创建 PENDING_ACTIVATION 租户
  -> 发起 FIRST_OWNER 邀请
  -> 租户 Data Owner 经已声明 NotificationCapability 发送首位 OWNER invitation link
  -> 受邀 Identity 先完成 Actor 登录，再携 invitation token 接受邀请
  -> Data Owner 本地事务内：
       锁邀请 + 锁租户 + 锁安装配额
       创建 ACTIVE OWNER
       创建/确认 Profile
       激活租户
       used + 1
       invitation = ACCEPTED
       写审计/必要 Outbox
  -> 首位 OWNER 取得 tenant/member context
```

本计划的最终验收不是“某个 Service 单测通过”，而是上述流程在 v3.0.10 Runtime Entry、权限、Data Owner、事务、通知和真实 Host readiness 边界下完整通过。

## 1. 改造目标

1. 将 `platform-admin` 从 Spring 自动扫描模块改造为根蓝图规定的 required `platform-operational` 模块；
2. 将 `/api/platform/**` 和 Bootstrap Endpoint 收敛到唯一 L2B Dispatcher，并服从 O0-O8、B0-B3、P8/O8 和 Host entry generation；
3. 让 Platform Admin 只通过 `OperationalContext.requireInternalContract(...)` 调用显式声明、版本匹配、allowlist 批准的 Data Owner 内部契约；
4. 删除 `platform-admin` 对 `platform-tenant` Repository、Entity、Service 和 Spring Bean 的直接依赖；
5. 将启动期 Bootstrap 数据副作用从 Spring `ApplicationRunner` 主链移除，禁止 B3 前写业务状态或开放入口；
6. 保留“Bootstrap Anchor → 首位正式平台超管 → 永久失效”的两阶段安全语义；
7. 将租户创建与首位 OWNER 接管分离：创建时只产生 `PENDING_ACTIVATION`，不创建 OWNER/Profile、不占用正式配额；
8. 实现 `FIRST_OWNER` 邀请的用途、发起者、Token、重发、撤销、接受、并发、幂等和审计闭环；
9. 保持 OSS Open Core 的多租户安全边界，不把平台身份、租户隔离和首位 OWNER 正确性变成商业插件私有能力；
10. 落地 v3.2.0 通用通知契约、模板编排和 SMTP Adapter，使平台超管 setup、密码重置和 FIRST_OWNER 邀请复用同一能力；
11. 保留前端 `Page → Hook → Repository → HttpCapability` 主链；
12. 建立可审计的正向、负向、并发、故障注入、真实 SMTP 和真实 HTTP 验收矩阵。

---

## 2. 不做范围

本计划不做：

1. 不批量迁移 `booking/case/products/partners/messenger/contracts/storage/identity/carousel/intake` 等商业插件；
2. 不建设通知中心、数据库模板管理、模板管理 API/UI、租户模板覆盖；
3. 不支持 HTML 邮件、附件、短信、站内信、移动推送或批量通知；
4. 不引入邮件 Outbox、自动重试、Provider callback、退信/投诉同步或通知记录表；
5. 不把邮件 OTP 作为 MFA；
6. 不实现 Break Glass，也不把 Bootstrap Anchor 当作灾难恢复账号；
7. 不开放匿名租户自助注册；
8. 不允许平台超管代用户设置密码、查看 Token 或作为租户 Member；
9. 不引入跨 Owner 事务、XA/2PC 或同步跨插件写；
10. 不修改、重命名或复用已经在共享环境执行的 Flyway migration；
11. 不在 Host 中加入业务 Controller、Handler、Service、Repository 或通知实现；
12. 不以脚本直接写数据库作为正式 Bootstrap 或 FIRST_OWNER 验收路径。

## 5. 目标模块与边界

### 5.1 固定调用链

```text
L3 Host
  -> RuntimeShellBootstrap / Bootstrap Handle
      -> L2B HostBootstrapCoordinator
          -> platform-admin PlatformOperationalModule
              -> OperationalContext.requireInternalContract(...)
                  -> Data Owner Internal Contract Proxy
                      -> Owner-scoped local transaction
                          -> NotificationCapability
                              -> platform-notification
                                  -> EmailDeliveryAdapter
                                      -> infra-adapter-email-smtp
```

### 5.2 模块职责

| 模块 | 目标职责 | 禁止事项 |
|---|---|---|
| `runtime-sdk-api` | Notification 契约；受限 internal provider-binding SPI | Registry、Spring、SMTP、业务实现 |
| `runtime-orchestrator` | Operational discovery、O0-O8、B0-B3、internal namespace、Dispatcher、readiness/fatal | 依赖 platform-admin/platform-tenant 业务类型 |
| `platform-tenant` Data Owner | 平台身份、租户、成员、邀请、配额、setup/bootstrap 状态的本地事务与 internal contracts | 被 platform-admin 直接注入 Repository；把平台超管写成 Member |
| `platform-auth` | Platform/Bootstrap/Actor Token 验证、Password/TOTP 和授权策略 | Bootstrap 角色进入标准平台登录特判 |
| `platform-notification` | 请求校验、模板、Locale、渲染、指标、Adapter 编排 | JavaMail、业务 Repository、HTML |
| `infra-adapter-email-smtp` | SMTP 配置、安全校验和纯文本投递 | 业务 templateKey 分支、重试、数据库 |
| `platform-admin` | required operational module；平台 Handler 和流程编排 | ComponentScan、Controller 自动发布、Repository/Service 直注入、第二 Dispatcher |
| `platform-admin-web` | 平台 setup/admin/tenant/FIRST_OWNER UI | 直接 fetch/axios、保存 Token 到不受控全局存储 |
| Enterprise Host | 组装依赖、Profile/Composition、探针和部署配置 | 业务 Handler、通知实现、按插件分支 |
| `app-tenant` | 经批准的租户内 UI/业务边界 | 第二套平台租户目录、平台控制面路由、创建时自动 OWNER |

### 5.3 Internal Contract 最小拆分

具体名称和版本必须在 Phase 0 专项/ADR 中冻结，职责至少分为：

1. `PlatformBootstrapAdministrationInternalContract`
   - 查询 Bootstrap 状态；
   - 创建/校验一次性 Bootstrap session；
   - 创建或重发首位正式超管 setup link；
   - 完成 Stage A → Stage B 原子关闭。
2. `PlatformIdentityAdministrationInternalContract`
   - 平台超管创建、撤销、密码重置；
   - 平台身份与 Platform Admin 授权查询；
   - 不返回 Repository、Entity、Token 原文或 Secret。
3. `TenantAdministrationInternalContract`
   - 平台视角租户列表/详情；
   - 创建 `PENDING_ACTIVATION` 租户；
   - 发起、重发、撤销 FIRST_OWNER 邀请；
   - 修改合法租户生命周期状态。
4. `PlatformAuditInternalContract`
   - 写/查平台审计；
   - 不接受 secret、完整 URL、正文、variables 或 Token。

每个 contract 必须具有 `contractId`、`contractType`、精确 `contractVersion`、providerId、owner；consumer descriptor 必须声明 Brix Range v1、required 和 privilege allowlist 引用。

### 5.4 最小 Endpoint 契约

下表是 Phase 0 必须写回对应专项蓝图的最小工作目标；专项重基线批准后，批准后的 path、Schema 和 policy 才是代码 SSoT。

| Endpoint | 身份与 tenant context | 写入/幂等语义 |
|---|---|---|
| `GET /api/platform/bootstrap/status` | anonymous allowlist；tenant forbidden | 只返回 `inBootstrap` 和最小提示，不返回邮箱、identity、过期时间或配置状态 |
| `POST /api/platform/bootstrap/session` | anonymous allowlist + 强限流；tenant forbidden | setup code 单次消费；Runtime idempotency required；不创建正式登录态 |
| `POST /api/platform/bootstrap/create-first-admin` | `BOOTSTRAP_SETUP` only；tenant forbidden | idempotency required；同目标 pending admin 可重放安全结果 |
| `GET /api/platform/auth/setup/validate` | setup token；tenant forbidden | 只读且不消耗 token |
| `POST /api/platform/auth/setup/totp/init` | setup token；tenant forbidden | idempotency required；不得返回持久化 secret |
| `POST /api/platform/auth/setup/complete` | setup token + TOTP；tenant forbidden | idempotency required；成功时消费 setup token 并关闭 Bootstrap |
| `POST /api/platform/tenants` | Platform Token + `platform:tenant:create`；tenant forbidden | 只创建 PENDING tenant；idempotency required |
| `POST /api/platform/tenants/{tenantId}/first-owner-invitations` | Platform Token + tenant admin permission；tenant forbidden | purpose/actor 由服务端决定；idempotency required |
| `POST /api/platform/tenants/{tenantId}/first-owner-invitations/resend` | Platform Token；tenant forbidden | 作废旧 token、生成新 token；idempotency required |
| `DELETE /api/platform/tenants/{tenantId}/first-owner-invitations/{invitationId}` | Platform Token；tenant forbidden | 只允许撤销 PENDING；idempotency required |
| `POST /api/v1/tenant-invitations/first-owner/accept` | 已验证 Actor identity；请求不携 tenant authority | invitation token + 当前 identity 绑定；idempotency required |

所有写 Endpoint 必须声明 request/response Schema、稳定 `handlerId`、authentication、authorization、tenantContext、timeout 和 idempotency policy；不得用 Handler 内分支临时开放匿名访问。

## 6. 流程状态机与事务

### 6.1 Bootstrap 状态机

```text
UNOPENED
  -> STAGE_A_OPEN
      -> FIRST_ADMIN_PENDING_SETUP
          -> FIRST_ADMIN_ACTIVE_WITH_MFA
              -> STAGE_B_CLOSED (永久终态)
```

规则：

1. Stage A 仅在 `completed_at IS NULL` 且不存在正式 ACTIVE + MFA 平台超管时成立；
2. Bootstrap Setup Code 只能经 Secret/安全配置边界取得，不记录明文；
3. `BOOTSTRAP_SETUP` Token 必须短 TTL、一次性、专用 audience/scope；
4. 它只能访问 bootstrap status/session/create-first-admin；
5. 创建正式超管只产生 `Identity(PENDING_SETUP)`、`PlatformAdmin(ACTIVE)` 和 setup token；
6. 只有密码完成、TOTP 绑定并首次验证成功后才能关闭 Stage A；
7. 关闭事务必须锁定 singleton bootstrap state，写 completed identity，禁用全部 Bootstrap Anchor 并使其 Token 失效；
8. Stage B 后重启、配置重放或 setup code 重放均不得重开；
9. Bootstrap Endpoint 只能在 B3/P8/O8 后可见；
10. required platform-admin 或其 internal contract/Notification 依赖不 Ready 时 Host 不 Ready。

### 6.2 FIRST_OWNER 状态机

```text
Tenant: PENDING_ACTIVATION
Invitation: PENDING(FIRST_OWNER)
  -> ACCEPTING
      -> ACCEPTED
Tenant: ACTIVE or TRIAL
Member: ACTIVE OWNER
Profile: present
Quota: used + 1
```

失败保持：

- 邮件失败：邀请创建/重发事务 fail-closed；
- Token 无效、过期、撤销、邮箱不匹配：不产生 Member/Profile/Quota 变化；
- 并发重复接受：最多一个事务成功，其他返回稳定“已接受/冲突”语义；
- 配额不足：全部回滚，租户仍为 `PENDING_ACTIVATION`，邀请状态不得伪造为 ACCEPTED；
- 已存在 ACTIVE OWNER：FIRST_OWNER 接受失败；
- 任一 DB/审计/必要 Outbox 写失败：Owner 本地事务整体回滚。

### 6.3 FIRST_OWNER 接受事务锁顺序

固定锁顺序，所有实现和测试必须一致：

1. `sys_tenant_invitation` 按 token hash `FOR UPDATE`；
2. `sys_tenant` 按 tenantId `FOR UPDATE`；
3. `sys_installation_quota` 按 installationId `FOR UPDATE`；
4. 校验邀请 purpose/status/expiry/email 与当前已验证 identity；
5. 校验租户仍为 `PENDING_ACTIVATION` 且不存在 ACTIVE OWNER；
6. 插入 `ACTIVE OWNER`；
7. 插入或确认唯一 Profile；
8. tenant → `ACTIVE/TRIAL`；
9. quota used + 1；
10. invitation → `ACCEPTED`；
11. 写 Tenant Audit/Platform Audit，并将 `TenantFirstOwnerAccepted` 作为 CRITICAL Integration Event 写入同 Owner canonical Outbox；
12. commit。

不得使用“先 COUNT 再 INSERT”、内存锁、静态 Map 或跨 Owner 事务替代该边界。

`TenantFirstOwnerAccepted` 的 relay 重试必须保持 eventId，消费者按 `(handlerId, eventId)` 持久化 Inbox 去重；不得把该事实改名为 `CreateOwnerRequestedEvent`，也不得在事务中直接同步发送 broker。

## 10. 回滚与迁移策略

1. 代码回滚以完整制品/commit 回滚，不在同一制品保留 Spring Controller fallback；
2. platform-admin operational 化后不得通过开关恢复 ComponentScan 路径；
3. YAML descriptor 与 Java provider 不得双 SSoT；
4. 已发布 Flyway 只前滚，禁止恢复旧 checksum 或手工 `repair` 掩盖差异；
5. SMTP Adapter 可替换，但 NotificationRequest、templateKey 和业务事务语义不得随 Provider 改变；
6. FIRST_OWNER 功能回滚时可停止新邀请，但不得删除已接受 OWNER 或回退已激活租户；
7. Bootstrap 一旦 Stage B 永久关闭，版本回滚不得重开；
8. required operational module 失败时不得保持永久 live-but-not-ready；
9. `app_tenant_*` 若已有数据，必须按 Phase 0 批准的数据迁移/兼容计划前滚，禁止直接删除；
10. 回滚说明必须标明数据可恢复性、邮件残余窗口和 Token 失效范围。
