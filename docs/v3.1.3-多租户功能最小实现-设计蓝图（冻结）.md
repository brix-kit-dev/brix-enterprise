## 0. 文档定位与边界

### 0.0 v3.0.10 重基线结论

1. 本文保留 `Architecture Frozen`，实施状态独立保持 `pending`；本次对齐不表示代码已经通过实施验收。
2. `platform-admin` 的唯一归属是 `platform-commons` 下的 `moduleKind=platform-operational`，其 `/api/platform/**` 入口、O0-O8 生命周期、B0-B3 屏障和内部契约访问完全服从根蓝图，本文不另建超管 Capability、Controller 或路由机制。
3. 插件获取当前租户上下文的唯一入口是根蓝图定义的 `TenantContextCapability`；租户列表、成员、配额、生命周期等领域读写必须使用版本化 typed Query、typed Command 或 typed Event。

5. 多租户数据仍由各 Data Owner 唯一拥有；Platform Operational Module 只能调用 descriptor 声明且 privilege allowlist 批准的内部契约，不得直接注入 Repository/Service 或传播调用方事务。

### 0.1 什么是"最小实现"

"最小实现"= **生产可用的多租户底座所必需的最小能力集**，不多不少：

- **必须有**：区分租户、隔离数据（全栈）、双轨认证（B 端 Actor / C 端 Subject）、租户选择与切换、租户基础配置、开源/商业边界。
- **明确不做**（留待后续版本，见 [§16 范围边界](#16-范围边界minimum--deferred)）：Schema/DB 级隔离、计费、SSO、自定义域名、白标 App、合规报告、复杂配额计量。

| 设计点 | 对标对象 | 采纳结论 |
|--------|----------|----------|

## 1. 开源版与商业版边界（Open Core）

> **核心原则一：安全是底座，不是商品。** 多租户隔离、JWT 校验、跨租户防泄漏、审计在任何版本中都完整提供，永不进付费墙。
> **核心原则二：采用 Open Core，不依赖"不可绕过的代码限制"做商业保护。** 本仓核心代码以 Apache 2.0 开源，用户**有权修改**——因此 **3 租户上限是开源版的默认配置/许可约定，而非技术上不可绕过的商业护城河**。真正的商业价值来自 License 服务、企业能力与支持，而非锁死代码。

### 1.1 Open Core 分层

| 层 | 内容 | 许可 |
|----|------|------|
| **Open Core（开源）** | 完整多租户底座：三层身份、Actor/Subject 分表、全栈隔离、JWT 双轨、防泄漏、审计、行级隔离 | Apache 2.0，可自由修改 |
| **Commercial（商业）** | 企业 License 配额、SSO/SAML/OIDC 联合登录、Schema/DB 级高级隔离、合规报告、白标、官方支持与 SLA | 商业许可 |

> 开源版默认 `maxTenants = 3`，是**许可与产品策略约定**，并通过 License 模块在官方发行版中生效；不假装它是无法被有源码者绕过的技术屏障。商业护城河 = SSO + 高级隔离 + 合规 + 支持，而非"删不掉的 if 判断"。

### 1.2 租户数量计数与配额规则（红线 [T-16](#12-架构红线)）

**1. 配额主体（统计范围）**：3 租户上限按**整个 Brix 部署实例**统计，**不得按 `owner_identity_id` 统计**——否则每个用户都能各建 3 个租户，上限形同虚设。配额主体**统一固定为单一字段 `installation_id`**（同一部署实例全局唯一），全实例共享同一配额行；**不再并列 `deployment_id` / `license_subject_id` 等多种写法**（避免多主体歧义）。

**2. 哪些状态计入上限**：仅 **`ACTIVE` 与 `TRIAL`** 状态的租户计入配额。`PENDING_ACTIVATION` / `DISABLED` / `ARCHIVED` / `DELETED`（软删）**不计入**。

**3. 删除是否释放名额**：

- **软删（`ARCHIVED`/`DISABLED`）**：仍占数据但**不计入**配额名额（可被新建复用）；保留期内可恢复——恢复时需重新占用名额（若已满则拒绝恢复并提示）。
- **硬删（数据彻底清除）**：立即释放名额。
- 名额计算统一以"当前 `ACTIVE`+`TRIAL` 计数"为准，避免软删占名额导致用户困惑。

**4. 激活租户并占用配额必须并发安全（禁止 `COUNT → INSERT`）**：

> 简单"先 `COUNT` 再 `INSERT`"在并发下会突破上限（TOCTOU）。**冻结方案固定为「首位 OWNER 接受邀请时，配额行 + `SELECT FOR UPDATE`」**（不再提供 advisory lock 备选，见 §16 Rejected Alternatives）。创建租户本身只产生 `PENDING_ACTIVATION` 租户，不正式占用租户数量配额；首位 OWNER 接管成功、租户转为 `TRIAL` 或 `ACTIVE` 时才占用配额。

```sql
-- 冻结方案：首位 OWNER 接管时，部署实例级配额行 + SELECT FOR UPDATE（全实例唯一配额主体）
BEGIN;
SELECT used, quota FROM sys_installation_quota
    WHERE installation_id = :installationId FOR UPDATE;  -- 锁定全实例唯一配额行
-- 应用层校验 used < quota，否则回滚拒绝（fail-closed）
UPDATE sys_installation_quota SET used = used + 1
    WHERE installation_id = :installationId;             -- 首位 OWNER 接管成功后正式占用名额
INSERT INTO sys_tenant_member (... tenant_id, identity_id, member_type, status, ...)
  VALUES (:tenantId, :ownerIdentityId, 'OWNER', 'ACTIVE', ...)
  RETURNING id;                                        -- 首位管理员
INSERT INTO biz_user_profile (... tenant_id, member_id, ...)
  VALUES (:tenantId, :ownerMemberId, ...);             -- 首位管理员档案
UPDATE sys_tenant SET status = 'TRIAL' WHERE id = :tenantId; -- 或 ACTIVE，按 License/试用策略决定
COMMIT;                                                  -- 失败则整体回滚，名额自动归还
```

> `sys_installation_quota` 是**全实例单行**配额表：`installation_id`（PK）、`quota`（开源版=3 / 商业版=License 值）、`used`。`SELECT FOR UPDATE` 串行化所有并发激活/恢复租户事务，杜绝突破上限。新增租户先保持 `PENDING_ACTIVATION`；首位管理员必须通过 `FIRST_OWNER` 邀请接管后创建为 `ACTIVE OWNER`（见 §5.7），不得以普通 `ADMIN` 替代；UI 可展示为“租户管理员 / 所有者”。

**5. 租户状态变化必须与配额联动（同一事务 + 行锁，红线 [T-27](#12-架构红线)）**：

> 配额 `used` 必须与租户状态变迁**在同一事务内原子变更**，且**先 `SELECT ... FOR UPDATE` 锁定 `sys_installation_quota` 配额行**，防止并发突破上限。

| 状态变迁 | 配额动作 | 说明 |
|----------|----------|------|
| 接受 `FIRST_OWNER` 邀请，将租户从 `PENDING_ACTIVATION` 激活为 `ACTIVE` / `TRIAL` | `used = used + 1` | 与创建首位 `ACTIVE OWNER`、对应 Profile、邀请置 `ACCEPTED` 同事务（见 §5.7） |
| `ACTIVE`/`TRIAL` → `DISABLED`/`ARCHIVED`/`DELETED` | `used = used - 1` | 与状态更新同事务，释放名额 |
| 恢复（`DISABLED`/`ARCHIVED` → `ACTIVE`/`TRIAL`） | 先检查再预占 | 必须先 `FOR UPDATE` 锁行、校验 `used < quota` 再 `used+1`；已满则拒绝恢复（fail-closed） |
| 硬删（彻底清除） | `used = used - 1`（若之前未减） | 与删除同事务 |

> 并发铁律：**任何会改变 `ACTIVE`+`TRIAL` 计数的状态变迁，都必须在同一事务内先锁配额行再改 `used`**；状态变更与配额变更不得拆到两个事务（否则中间态会造成计数不一致）。

License 与配额的硬约束：

1. **安全相关能力（隔离、JWT 校验、防泄漏、审计）一律不得作为付费开关**，任何版本默认开启且不可关闭。
2. 开源版默认租户数上限 = 3（许可约定）；超限时**拒绝新增租户**（fail-closed），不影响已有租户。
3. 商业版租户数由 License 配额控制；超限时**仅拒绝新增**。
4. **License 到期只禁止新增租户，绝不删除或停用已有租户数据**。到期后：
   - 已有租户：正常读写、登录、隔离、审计照常。
   - 新增租户 / 新增成员（若 License 含席位限制）：拒绝并提示续期。
5. License 校验失败按 fail-closed 处理（拒绝新增），但**不得**导致已有数据不可访问。

## 2. 核心设计共识（不可推翻）

| # | 设计共识 | 不可推翻原因 |
|---|----------|--------------|
| 1 | **Actor / Subject 物理分离** — `sys_tenant_member`（B 端）与 `sys_tenant_principal`（C 端）独立建表 | 同一人可同时是某租户员工与客户；统一表会语义污染、生命周期纠缠、C 端百万级扩展污染 B 端查询 |
| 2 | **三层身份模型** — Identity（全局）→ Member / Principal（租户接入）→ Profile（租户内档案） | 表结构与外键定型，演进只能加字段 |
| 3 | **JWT 双轨签发** — Actor Token（`mid/mtype`，aud=actor）与 Subject Token（`pid/ptype`，aud=subject）**互斥** | 已签发 Token 不可改，结构必须前向兼容 |
| 4 | **TenantContext 统一抽象** — 契约在 Layer 2A，技术实现（ThreadLocal/Reactor/TaskDecorator）在 Layer 2C | 所有业务代码依赖统一 API，实现可演进 |
| 5 | **全栈租户隔离** — 不仅 SQL，Redis/Kafka/对象存储/异步任务/搜索/审计全部携带并清理 tenant 上下文 | 任一基础设施漏过 tenant 即构成越权面 |
| 6 | **基座层零行业语义** — `member_type` / `principal_type` 仅含通用枚举 | 平台不被任何行业锁死 |
| 7 | **BusinessObject 不入基座，插件不依赖平台表** — 插件仅存不透明 `tenant_id + member_id/principal_id` 引用，禁止跨服务外键 | 保持基座中性、服务可独立演进 |
| 8 | **安全能力不商业化** — 隔离/JWT/防泄漏/审计在任何版本完整提供 | 安全是底座责任，不是付费特性 |

## 3. 三层身份模型

```text
Layer 0: sys_identity                  全局身份（手机/邮箱/凭证），跨租户共享
   │                                    与租户无关，1 人 = 1 条记录
   │
   ├─► Layer 1A: sys_tenant_member     B 端 — 组织成员（Actor）  [tenant 隔离]
   │     • member_type ∈ { OWNER, ADMIN, MEMBER }
   │     • 准入：邀请 → 审批 → 加入（管理流程）
   │
   └─► Layer 1B: sys_tenant_principal  C 端 — 访问主体（Subject）[tenant 隔离]
         • principal_type ∈ { CUSTOMER, GUEST }
         • 准入：邀请 / 预约 / 注册绑定 → 创建（自动化）
                 │
                 ▼
Layer 2: biz_user_profile              租户内用户档案（每租户独立）[tenant 隔离]
   • member_id / principal_id 双可空字段（恰一非空，见 §5.3）
   • 同一人在不同租户可有不同昵称、偏好
```

> **重要**：`sys_tenant_member` / `sys_tenant_principal` / `biz_user_profile` 均带 `tenant_id`，**受租户隔离保护**，**不在** `TenantInterceptor` 白名单内（见 [§6](#6-平台表白名单与隔离边界)）。

**四术语精确区分（防混淆）：**

| 概念 | 表 | 回答的问题 | 举例 |
|------|------|-----------|------|
| **Member** | `sys_tenant_member` | 谁管理/运营这个租户？ | OWNER/ADMIN/MEMBER |
| **Principal** | `sys_tenant_principal` | 谁有资格被这个租户服务？（准入凭证） | CUSTOMER/GUEST |
| **Profile** | `biz_user_profile` | 你在这个租户叫什么、偏好什么？ | 昵称、locale、theme |
| **BusinessObject** | 插件自建表 | 你为什么来、做了什么业务？ | medical_case / order / enrollment |

> 关键优势：同一 `identity` 可在同一租户**同时持有** Member + Principal 记录（医生在自己诊所看病），两条独立记录互不污染；通过稳定 `contextId`（§9.3）区分登录视角。

## 4. B2B2C Actor/Subject 分离模型

### 4.1 角色全景

```text
Platform
  ├── PlatformAdmin       平台运维（sys_platform_admin，全局表）
  └── Tenant
       ├── Actor（B端）   → sys_tenant_member（tenant 隔离）
       │   ├── OWNER      租户创建者 / 所有者（每租户至少 1 个，见 §5.6）
       │   ├── ADMIN      管理员
       │   └── MEMBER     普通职员（行业语义在插件层）
       ├── Subject（C端） → sys_tenant_principal（tenant 隔离）
       │   └── CUSTOMER   终端用户（患者/学员/买家...）
       └── Guest          → sys_tenant_principal
           └── GUEST      受限访客（按需启用）
```

### 4.2 行业映射（基座层零感知）

| 行业 | Actor(MEMBER) | Subject(CUSTOMER) | BusinessObject（插件自建） |
|------|---------------|-------------------|------|
| 医疗 | 医生/药师 | 患者 | medical_case（病例） |
| 教育 | 教师/教练 | 学员 | enrollment（报名） |
| 电商 | 店铺运营 | 买家 | order（订单） |
| 法律 | 律师/助理 | 当事人 | legal_case（案件） |

### 4.3 Subject 准入硬规则

- **仅在"有效准入动作"后创建 Principal**：邀请准入 / 接受邀请 / 注册并绑定租户 / 业务行为触发（提交预约、完成报名）。
- **单纯浏览品牌页、扫码预览、访问公开链接，不创建 Principal。**
- Principal 生命周期**独立于** BusinessObject：Case/Order 结束**不删除/失效** Principal。仅在「主动退出 / 管理员停用 / 状态置 `DISABLED`|`REVOKED`」时失效。

### 5.3 biz_user_profile（修复多态引用 — V009）

> **不再使用 `ref_type + ref_id` 弱多态**（无法被外键约束、易产生悬挂引用、无法保证 tenant 一致）。
> **冻结方案：单表双可空字段 `member_id` / `principal_id`**，以 CHECK 保证"恰好一个非空"，以**复合外键**保证引用对象与本行 `tenant_id` 一致。（拆两表方案见 §16 Rejected Alternatives，不作为可选实现。）

> **迁移拆分为 4 个独立 Flyway 版本，严禁在一段 SQL 内同时加列/加外键/加 CHECK/删旧列**（脏数据会导致整体失败且难回滚）。

**V009a — 仅增加新列（可空，不加任何约束）**

```sql
ALTER TABLE biz_user_profile ADD COLUMN IF NOT EXISTS member_id    BIGINT;
ALTER TABLE biz_user_profile ADD COLUMN IF NOT EXISTS principal_id BIGINT;
```

**V009b — 分批回填并检查冲突（不加约束）**

```sql
-- 按旧 ref_type 分批回填（避免长事务）：
UPDATE biz_user_profile SET member_id    = ref_id WHERE ref_type = 'MEMBER'    AND member_id    IS NULL;
UPDATE biz_user_profile SET principal_id = ref_id WHERE ref_type = 'PRINCIPAL' AND principal_id IS NULL;
-- 冲突检查（任一非空 → 阻断迁移并产报告，禁 DO NOTHING，见 §5.8）：
--   ① 存在两列都空或都非空的行
--   ② member_id/principal_id 指向的对象不存在或 tenant_id 不一致
-- 检查不通过 → 迁移以非零退出码失败 → 人工裁决后重跑
```

**V009c — 增加外键、唯一约束与 CHECK（数据已干净）**

```sql
-- 复合外键：引用对象必须与本行 tenant_id 一致（依赖 5.1/5.2 的复合唯一键）
ALTER TABLE biz_user_profile ADD CONSTRAINT fk_profile_member
    FOREIGN KEY (tenant_id, member_id)    REFERENCES sys_tenant_member(tenant_id, id);
ALTER TABLE biz_user_profile ADD CONSTRAINT fk_profile_principal
    FOREIGN KEY (tenant_id, principal_id) REFERENCES sys_tenant_principal(tenant_id, id);
-- 每个 member/principal 在租户内恰好一个 profile（快照改为 uk，确保 1:1 不可多不可少）
ALTER TABLE biz_user_profile ADD CONSTRAINT uk_profile_member    UNIQUE (tenant_id, member_id);
ALTER TABLE biz_user_profile ADD CONSTRAINT uk_profile_principal UNIQUE (tenant_id, principal_id);
-- 恰好一个引用非空（放最后，确保回填已满足）
ALTER TABLE biz_user_profile ADD CONSTRAINT chk_profile_ref_exclusive CHECK (
    (member_id IS NOT NULL AND principal_id IS NULL)
 OR (member_id IS NULL     AND principal_id IS NOT NULL)
);
```

**V009d — 应用切换完成后删除旧列（独立版本，单独可回滚）**

```sql
-- 确认应用代码已不再读写旧弱引用列后执行：
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS ref_type;
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS ref_id;
ALTER TABLE biz_user_profile DROP COLUMN IF EXISTS member_id_legacy;
```

> **顺序铁律**：V009a 加列 → V009b 回填+冲突检查 → V009c 建 FK/唯一键/CHECK → V009d 删旧列。**严禁**在回填完成前就加 FK/CHECK，**严禁**把删旧列与建约束放进同一版本。

> **Profile 必存性约束**：V009c 的外键、CHECK 与 UNIQUE 保证 Profile 引用有效、租户一致且**最多一个**——即 `UNIQUE(tenant_id, member_id)` / `UNIQUE(tenant_id, principal_id)` 只防止重复，**不能单独保证 ACTIVE Member/Principal 一定存在 Profile**。存在性属于事务级领域不变量：创建 Member/Principal 与 Profile **必须在同一事务中完成**，Profile 失败则整体回滚；该规则通过**集成测试和一致性巡检**保证。

> **说明**：此处复合外键属于 **平台基座内部表之间** 的约束，不违反 [§7 插件不得外键平台表] 的红线（后者约束的是**插件/跨服务**表）。

### 5.6 防止删除租户最后一个 OWNER（红线 T-18）

> 每个租户**任意时刻必须至少有 1 个 `ACTIVE` 的 OWNER**。删除/降级/停用最后一个 OWNER 必须被阻断。
> **并发陷阱**：两个 OWNER 在不同事务中**同时**降级时，各自的触发器都"看到对方仍是 ACTIVE OWNER"而放行，提交后租户可能 0 OWNER。**必须先取租户级锁串行化**，再做计数校验。

```sql
CREATE OR REPLACE FUNCTION guard_last_owner() RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'DELETE' AND OLD.member_type = 'OWNER')
       OR (TG_OP = 'UPDATE' AND OLD.member_type = 'OWNER'
           AND (NEW.member_type <> 'OWNER' OR NEW.status <> 'ACTIVE')) THEN

        -- 关键：先取租户级事务锁，串行化同一租户的所有 OWNER 变更，杜绝并发双降级
        PERFORM pg_advisory_xact_lock(hashtext('tenant-owner:' || OLD.tenant_id));

        -- 锁内统计（排除本行）剩余 ACTIVE OWNER；并发事务此时被阻塞，无法绕过
        IF (SELECT COUNT(*) FROM sys_tenant_member
            WHERE tenant_id = OLD.tenant_id AND member_type = 'OWNER'
              AND status = 'ACTIVE' AND id <> OLD.id) = 0 THEN
            RAISE EXCEPTION 'TENANT_LAST_OWNER_PROTECTED: tenant % must keep >=1 active OWNER', OLD.tenant_id;
        END IF;
    END IF;
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_guard_last_owner
    BEFORE UPDATE OR DELETE ON sys_tenant_member
    FOR EACH ROW EXECUTE FUNCTION guard_last_owner();
```

**并发正确性约束：**

1. 所有修改 OWNER 的应用层流程（转移所有权 / 降级 / 移除 / 停用）**必须先取同一租户级锁**——应用层用 `pg_advisory_xact_lock(hashtext('tenant-owner:'||tenantId))` 或对 `sys_tenant` 行 `SELECT ... FOR UPDATE`，使同租户的 OWNER 变更**全序化**。
2. DB 触发器内的 `pg_advisory_xact_lock` 是**兜底**：即使应用层漏锁，触发器仍强制串行化计数校验。
3. 经此双重锁，**任意并发交错下都保证至少保留一个 `ACTIVE` OWNER**。
4. 应用层应提前校验并给出友好错误（如 `TENANT_LAST_OWNER_PROTECTED`），DB 触发器作为最终防线。

### 5.7 新增租户与首位 OWNER 接管分离（红线 T-28）

> 新增租户不是直接创建可登录管理员。**创建租户与首位 OWNER 接管必须分离**：创建租户后状态固定为 `PENDING_ACTIVATION`，不自动创建 OWNER，不创建 `biz_user_profile`，不正式占用租户数量配额。平台超管随后在“租户详情 → 租户管理员”区域发送 `FIRST_OWNER` 邀请；受邀人接受后才在同一事务中创建首位 `ACTIVE OWNER`、创建/确认 Profile、激活租户并占用配额。

**最小实现语义：**

1. **创建租户状态**：租户创建请求只创建 `sys_tenant(status='PENDING_ACTIVATION')` 及必要配置，不创建 `sys_tenant_member` / `biz_user_profile`，不把平台超管写成租户成员。
2. **首位 OWNER 邀请**：平台超管发起 `FIRST_OWNER` 邀请，`target_role` 固定为 `OWNER`，邀请表必须记录 `inviter_type='PLATFORM_ADMIN'` 与 `platform_admin_id`。平台超管不得设置、查看或发送用户密码。
3. **后续成员邀请**：首位 OWNER 接管后，租户内 `ACTIVE OWNER` 使用同一邀请基础设施发起 `TENANT_MEMBER` 邀请，可邀请 `OWNER` / `ADMIN` / `MEMBER`，不改变租户状态和租户数量配额。
4. **邀请 Token 安全**：邀请 token 必须一次性、带有效期，数据库仅保存 hash；重发后旧 token 失效；API 不返回明文 token，邀请链接只能通过 `NotificationCapability` 发送。
5. **接受策略分派**：服务端必须根据 `sys_tenant_invitation.invitation_purpose` 选择 `FIRST_OWNER` 或 `TENANT_MEMBER` 接受处理器，不得根据“租户是否已有 OWNER”动态推断，也不得相信前端传入的用途。
6. **登录边界**：租户成员统一从 `/login` / Actor 登录入口进入，使用 `aud=brix-actor` 的 Actor Token；不得使用 `/platform/login`、Platform Token 或任何平台超管授权进入租户业务上下文。

租户创建流程（伪代码）：

```sql

  VALUES (..., 'PENDING_ACTIVATION', ...)
  RETURNING id INTO :tenantId;
INSERT INTO sys_platform_audit_log (... action, affected_tenants, ...)
  VALUES (..., 'TENANT_CREATED_PENDING_ACTIVATION', jsonb_build_array(:tenantId), ...);

```

```sql
  WHERE token_hash = :tokenHash

-- 校验 purpose=FIRST_OWNER、status=PENDING、expires_at、invited_email 与当前 identity 邮箱一致

  VALUES (:tenantId, :ownerMemberId, NULL, ...);
UPDATE sys_tenant SET status = 'TRIAL' WHERE id = :tenantId; -- 或 ACTIVE，按 License/试用策略决定
UPDATE sys_tenant_invitation SET status = 'ACCEPTED', used_at = NOW()
  WHERE id = :invitationId;
INSERT INTO sys_platform_audit_log (... action, affected_tenants, ...)
  VALUES (..., 'TENANT_FIRST_OWNER_ACCEPTED', jsonb_build_array(:tenantId), ...);
COMMIT;
```

> **一致性要求**：`PENDING_ACTIVATION` 租户允许暂时没有 OWNER；任何可见为 `ACTIVE` / `TRIAL` 的租户，查询其 `sys_tenant_member` 时必须至少存在 1 个 `ACTIVE OWNER`。实现阶段必须提供一致性巡检：发现“ACTIVE/TRIAL 无 OWNER 租户”即安全告警并阻断发布。重复接受同一邀请不得重复创建 Member、Profile 或增加配额。

### 5.8 迁移冲突处理（红线 T-19）

> **禁止静默 `ON CONFLICT DO NOTHING`**。数据迁移遇到冲突（如 V008 迁移 CUSTOMER/GUEST 时主键/唯一键冲突）**必须阻断迁移并生成冲突报告**，由人工裁决后再继续。

```sql
-- V008 迁移前置检查（伪代码，实际用迁移脚本/工具实现）：
-- 1. 扫描 sys_tenant_member 中 member_type IN ('CUSTOMER','GUEST') 的记录
-- 2. 检测其迁移到 sys_tenant_principal 后是否与现有 (tenant_id, identity_id) 冲突
-- 3. 若有冲突 → 写出报告文件（冲突明细）→ 迁移以非零退出码失败 → 阻断发布
-- 4. 无冲突 → 执行迁移 → 删除源记录 → 收窄 CHECK
```

### 5.9 迁移顺序与白名单

- **迁移顺序**：V001–V006（已落地）→ V007 建 principal → V008 收窄 member（含冲突阻断）→ **V009a 加列 → V009b 回填+冲突检查 → V009c 建 FK/唯一键/CHECK → V009d 删旧列** → V010 配置字段 → V011 邀请表。
- **白名单**：见 [§6](#6-平台表白名单与隔离边界)，**仅真正的平台全局表**可绕过 `TenantInterceptor`。

## 6. 平台表白名单与隔离边界

> **禁止按 `sys_*` 前缀整体加入白名单。** 白名单是越权面，必须**逐表显式**列入，且仅限**真正的平台全局表**。

### 6.1 白名单（仅这些表绕过 TenantInterceptor）

| 表 | 是否全局 | 说明 |
|----|:------:|------|
| `sys_tenant` | ✅ | 租户注册表本身（无 `tenant_id` 概念，是 tenant 的定义源） |
| `sys_identity` | ✅ | 全局身份，跨租户共享 |
| `sys_platform_admin` | ✅ | 平台超管，不归属任何租户 |
| `sys_platform_config` | ✅ | **平台全局配置**（无 `tenant_id`），可进入白名单 |
| `sys_installation_quota` | ✅ | **部署实例级配额表**（无 `tenant_id`，全实例单行，见 §1.2） |
| `sys_platform_audit_log` | ✅ | **平台审计**（跨租户/平台操作，无单一 `tenant_id`，见 §10.1） |

> **配置表必须拆分（红线 T-15 相关）**：`sys_platform_config`（平台全局）与 `sys_tenant_config`（租户级，带 `tenant_id`，**受隔离**）是**两张独立的表**。**禁止用同一张表同时承担全局配置与租户配置**——否则白名单一旦放行就会泄漏全部租户配置。

> **白名单逐表显式（红线 T-15）**：若未来出现其他 License / Installation 类全局表（如 `sys_license`、`sys_installation`），**必须逐表显式加入上表**；**禁止用表名前缀（`sys_*`）自动放行**。

### 6.2 必须受隔离的"租户关系/配置表"（**不得**进白名单）

`sys_tenant_member`、`sys_tenant_principal`、`biz_user_profile`、`sys_tenant_invitation`、**`sys_tenant_config`** 等**均带 `tenant_id`**，**必须受 `TenantInterceptor` 隔离保护**。理由：它们承载"谁能进哪个租户 / 某租户的配置"，一旦漏过隔离即等于跨租户成员枚举/配置越权。

### 6.3 例外 — 登录期跨租户查询（普通认证流程唯一允许）

登录阶段需要"列出某 identity 在**所有**租户的接入关系"，这是**普通认证流程中唯一允许**的跨租户读取（仅限登录期 Actor 租户发现）：

- **必须**走专用接口（如 `AuthnTenantLookupService`），以 `@CrossTenantAccess(reason="login-tenant-discovery")` 显式声明。
- **必须**记录审计日志（`identity_id`、查询时间、来源 IP、命中租户数）。
- **仅**返回 `tenant_id / tenant_name / role / roleType / last_access_at` 等**选择所需的最小字段**，禁止返回业务数据。
- **PlatformAdmin 跨租户查询属独立特权链路**：只读数据由租户 Data Owner 发布 typed Query；平台运维动作由 `platform-admin` 通过 descriptor 已声明且 privilege allowlist 批准的内部契约执行。它与本登录发现**互不等同**，不得再表述"登录查询是系统唯一跨租户访问"。
- 详见 [§9.2](#92-登录期跨租户发现专用审计接口)。

## 7. 插件数据引用规则

> **取消"插件业务表对平台表的强制外键"。** 插件与平台、插件与插件、跨服务之间**禁止数据库外键**，改为**不透明引用 + 应用层一致性校验**。

### 7.1 规则

1. 插件业务表**只保存** `tenant_id` + `member_id` / `principal_id` 等**不透明 ID**（无 DB 外键到 `sys_tenant_*`）。
2. 插件**不得**直接查询或 JOIN 平台租户表（`sys_tenant_member` / `sys_tenant_principal`），必须经 `TenantDirectoryCapability`（归属/引用校验）等契约访问；`BusinessObjectCapability` 仅为可选生态能力，不承担归属校验。
3. 写入/读取时**必须校验**引用对象与当前 `TenantContext.tenantId` 一致（`TenantDirectoryCapability.requireSameTenant`，防止跨租户引用注入）。
4. **跨插件、跨服务一律禁止数据库外键**（服务可独立部署/独立库，外键会硬耦合并阻断拆分）。

### 7.2 示例（医疗插件自建表）

```sql
-- ✅ 正确：不透明引用，无外键到平台表，自带 tenant_id
CREATE TABLE medical_case (
    id                   BIGINT PRIMARY KEY,
    tenant_id            BIGINT NOT NULL,         -- 受 TenantInterceptor 隔离
    patient_principal_id BIGINT NOT NULL,         -- 不透明引用，无 FK
    doctor_member_id     BIGINT,                  -- 不透明引用，无 FK
    case_number          VARCHAR(50),
    status               VARCHAR(20) NOT NULL,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_mc_status CHECK (status IN ('OPEN','IN_PROGRESS','CLOSED'))
);
-- 应用层：写入前 TenantDirectoryCapability 校验 patient_principal_id 属于当前 tenant
```

## 8. JWT Token 契约（双轨）

> **JWT 由三段组成：`Header.Payload.Signature`。** `alg` / `typ` / `kid` 属于 **JOSE Header**；`iss` / `aud` / `sub` / `exp` / `tid` 等属于 **Claims（Payload）**。下文**分别**给出 Header 与 Claims，**不得**把两者写进同一个 JSON 对象。

**Actor Token（B 端）— 有效期短（建议 ≤15min），`aud=brix-actor`**

```jsonc
// (1) JOSE Header — 仅放签名/密钥元数据
{
  "alg": "RS256",          // 固定算法，拒绝 none / alg 混淆
  "typ": "at+jwt",         // token 类型
  "kid": "<key_id>"        // 公钥轮转标识
}
```
```jsonc
// (2) Claims (Payload) — 业务与上下文声明
{
  "iss": "https://auth.brix.com",
  "aud": "brix-actor",                         // B 端专用 audience（C 端不可用）
  "scope": "actor",
  "sub": "<identity_id>",
  "iat": 0, "nbf": 0, "exp": 0, "jti": "<token_id>",
  "tid": "<tenant_id>", "tcode": "<tenant_code>",
  "cid": "<context_id>",                        // 稳定访问上下文 ID（见 §9.3）
  "mid": "<member_id>", "mtype": "ADMIN",      // OWNER | ADMIN | MEMBER
  "uid": "<profile_id>",
  "roles": ["admin"],                          // 小集合直接放；大集合存 Redis 仅放引用
  "mver": 7                                    // = sys_tenant_member.authz_version 快照（见 §8.2/§5.2）
}
```

**Subject Token（C 端）— `aud=brix-subject`**

```jsonc
// (1) JOSE Header
{ "alg": "RS256", "typ": "at+jwt", "kid": "<key_id>" }
```
```jsonc
// (2) Claims (Payload)
{
  "iss": "https://auth.brix.com",
  "aud": "brix-subject",                        // C 端专用 audience（B 端不可用）
  "scope": "subject",
  "sub": "<identity_id>",
  "iat": 0, "nbf": 0, "exp": 0, "jti": "<token_id>",
  "tid": "<tenant_id>", "tcode": "<tenant_code>",
  "cid": "<context_id>",
  "pid": "<principal_id>", "ptype": "CUSTOMER", // CUSTOMER | GUEST
  "uid": "<profile_id>",
  "pver": 3                                     // = sys_tenant_principal.authz_version 快照（见 §8.2/§5.1）
}
```

**Identity Token（临时 ≤5min，仅用于选上下文/注册）**

```jsonc
// Header
{ "alg": "RS256", "typ": "id+jwt", "kid": "<key_id>" }
```
```jsonc
// Claims
{ "iss": "https://auth.brix.com", "aud": "brix-identity",
  "sub": "<identity_id>", "iat": 0, "nbf": 0, "exp": 0, "jti": "<id>",
  "allowed_actions": ["select_context", "register_tenant"] }
```

**Refresh Token（服务端维护撤销列表 + Family）**

```jsonc
// Header
{ "alg": "RS256", "typ": "rt+jwt", "kid": "<key_id>" }
```
```jsonc
// Claims — 保存稳定 context_id（非一次性 ticket）
{ "iss": "https://auth.brix.com", "aud": "brix-refresh",
  "sub": "<identity_id>", "iat": 0, "nbf": 0, "exp": 0, "jti": "<id>",
  "cid": "<context_id>", "device_id": "<device>", "family": "<family>" }
```

> **四类 Token 必选 Claims 统一**：Actor / Subject / Identity / Refresh Token **均必含** `iss` / `aud` / `sub` / `iat` / `nbf` / `exp` / `jti`；差异仅在业务 claim（`tid` / `cid` / `mid` / `pid` / `scope` 等）。校验见 §8.1。

### 8.1 JWT 校验硬约束（红线 T-20）

1. **固定签名算法**：仅接受 `RS256`（或团队统一的一种非对称算法）；**显式拒绝 `none` 与任何对称算法**，防 alg 混淆攻击。
2. **完整校验**：Header 的 `alg`/`typ`/`kid` 与 Claims 的 `iss`/`aud`/`exp`/`nbf`/`jti` 全部校验；`kid` 必须命中当前有效公钥集（支持轮转）。
3. **B/C 区分靠 audience/scope，不靠 URL 路径**：Actor Token `aud=brix-actor`，Subject Token `aud=brix-subject`；管理 API 强制要求 `aud=brix-actor`，C 端 API 强制 `aud=brix-subject`。**严禁仅凭 `/admin/*` 路径判断权限**。
4. **`mid` 与 `pid` 互斥**：签发二选一；校验按 audience + 存在字段分派；不存在混合态。
5. **停用即失效**：Member/Principal 被停用（`DISABLED`/`REVOKED`）后，旧 Token 必须**尽快失效**——通过 (a) Access Token 短 TTL（≤15min）+ (b) `mver`/`pver` 授权版本号校验（见 §8.2）+ (c) `jti` 黑名单。
6. **`tid` 不可篡改**：JWT 非对称签名保证；禁止把 `tid` 作为业务请求参数。

### 8.2 授权版本号校验（`authz_version` ↔ `mver`/`pver`，红线 T-20）

> Token 中的 `mver`/`pver` 是签发时刻 `sys_tenant_member.authz_version` / `sys_tenant_principal.authz_version` 的**快照**。当成员/主体的**状态、角色、权限**发生变化时，对应行的 `authz_version` 自增（见 [§5.1](#51-sys_tenant_principal新增--v007) / [§5.2](#52-sys_tenant_member收窄--完整性--v008)）。

1. 每次受保护请求，鉴权层将 Token 的 `mver`/`pver` 与 DB 当前 `authz_version` 比对（可经短 TTL 缓存）。
2. **不一致即拒绝**（HTTP 401 `STALE_AUTHZ_VERSION`），客户端须重新走 refresh / select-context 取新 Token。
3. 触发自增的事件至少包括：`status` 变更、`member_type`/`principal_type`（角色）变更、权限/角色绑定变更、所有权转移。
4. 版本号 + 短 TTL + `jti` 黑名单三者叠加，保证停用/降权在秒级~分钟级生效，且无需在线撤销每一枚 Access Token。

## 9. 租户解析与认证流程

### 9.1 租户解析链 — Header/子域名/Path 仅为"提示"，非授权依据（红线 T-12/T-13）

| 优先级 | 解析器 | 来源 | 性质 | 信任边界 |
|:------:|--------|------|------|----------|
| 100 | `JwtTenantResolver` | JWT `tid`（已验签） | **授权依据** | 唯一可作为授权来源 |
| 150 | `HeaderTenantResolver` | `X-Tenant-Id` | **仅内部可信注入** | 见下方信任规则 |
| 200 | `SubdomainTenantResolver` | Host header | **提示** | 仅用于登录前品牌/租户提示 |
| 250 | `PathTenantResolver` | `/t/{code}/...` | **提示** | 仅用于路由提示 |
| — | Controller 显式处理 | Query `?tenantCode=` | **提示** | 公开注册/邀请，单独校验 |

**`X-Tenant-Id` 信任规则（强制）：**

- **公网入口的 `X-Tenant-Id` 必须由网关删除**（strip）后再转发，防止客户端伪造。
- 仅 **受信任网关** 或经 **mTLS / 服务身份认证** 的内部服务可注入 `X-Tenant-Id`。
- Header / 子域名 / Path 解析出的 `tid` **只能作为登录前提示**（选择哪个品牌、预填哪个租户），**不能作为已认证请求的授权依据**——已认证请求的 `tid` **永远**取自已验签 JWT。
- 当提示来源的 `tid` 与 JWT `tid` **冲突**时，按 [红线 T-10](#12-架构红线) 拒绝（HTTP 400 `TENANT_CONFLICT` + 审计告警）。

### 9.2 登录期跨租户发现（专用 + 审计接口，按入口严格分流）

> 发现接口**按登录入口分流**，B 端只发现 Actor，C 端只发现当前租户的 Subject。**登录入口固定为两个独立端点** `/api/auth/login/actor` 与 `/api/auth/login/subject`；**`client_type` 不作为登录通道选择依据**（通道由端点路径决定），绝不在一个响应里混合两端或跨租户数据。

```text
─── B 端入口（管理控制台 / Actor 登录端点）───
POST /api/auth/login/actor   { phone+smsCode | email+password | oauth }
  → 验证凭证 → identity_id
  → AuthnTenantLookupService.discoverActor(identityId)    // @CrossTenantAccess + 审计
       actor_contexts = sys_tenant_member WHERE identity_id=? AND status='ACTIVE'
  → 仅返回 Actor 上下文（绝不含任何 Principal / Subject 信息）
  → 写审计日志: { identity_id, entry:'actor', ip, ts, matched_context_count }

─── C 端入口（品牌 App / 租户入口，tid 已由品牌锁定）───
POST /api/auth/login/subject  { phone+smsCode | ... }   （请求绑定当前租户 tid 提示）
  → 验证凭证 → identity_id
  → AuthnTenantLookupService.discoverSubject(identityId, currentTenantId)  // 强制单租户过滤
       subject_context = sys_tenant_principal
            WHERE identity_id=? AND tenant_id=:current AND status='ACTIVE'
  → 仅返回【当前租户】的 Subject 上下文；不做跨租户聚合
  → 写审计日志: { identity_id, entry:'subject', tenant_id, ip, ts }
```

> - 该接口是 [§6.3](#63-例外--登录期跨租户查询普通认证流程唯一允许) 允许的、**普通认证流程中唯一**的跨租户读取（PlatformAdmin 特权链路除外），且**仅 B 端 `discoverActor` 可跨租户**；C 端 `discoverSubject` **强制单租户过滤**，不允许跨租户聚合。
> - 返回**仅限选择所需字段**（tenant/role/roleType/lastAccessAt），不含任何业务数据。
> - 每个上下文对应一个一次性 `selectionTicket`（见 §9.3），不下发稳定 `contextId`。

### 9.3 选择"访问上下文"协议 — `contextId` 与 `contextSelectionTicket`（解决同租户双身份）

> 同一 Identity 在同一租户可能**同时**是 Actor 和 Subject，`select-context` **不能只传 `tenantId`**（无法区分双身份）。本协议区分两类标识，**生命周期不同**：

| 标识 | 生命周期 | 用途 | 存放位置 |
|------|----------|------|----------|
| **`contextId`** | **长期稳定** | 唯一代表一个 `{ tenant + actor/subject + refId }` 接入上下文 | **Access Token / Refresh Token 的 `cid` claim**（见 §8） |
| **`contextSelectionTicket`** | **短期、一次性** | 登录后选择上下文的临时凭据，用后即焚 | 仅在登录→选择的窗口内传递，**绝不入长期 Token** |

> 设计要点：稳定的 `contextId` 是身份上下文的"主键"（来自 §5.1/§5.2 的 `context_id` 列），可被服务端长期引用、做设备记忆、放进 Token；`contextSelectionTicket` 只是"这一次登录允许选这个上下文"的一次性票据，**防止枚举他人 contextId 与重放**。
> **登录入口已在 §9.2/§9.4 严格分流**：B 端走 `/login/actor` 只产出 Actor 上下文，C 端走 `/login/subject` 只产出当前租户 Subject 上下文。**不存在同时返回 Actor 与多个租户 Subject 的通用入口**。

```text
─── B 端选择（仅 Actor 上下文；员工可属多个租户）───
Phase 1  POST /api/auth/login/actor
  → {
      "step": "SELECT_CONTEXT",
      "identityToken": "<id-jwt, ≤5min, jti=J1>",   // 绑定本次登录
      "contexts": [    // 全部为 actor；每项给一次性 ticket，不暴露稳定 contextId
        { "selectionTicket": "tkt_a1...", "tenantId": "t_a", "tenantName": "A诊所",
          "role": "actor", "roleType": "OWNER",  "lastAccessAt": "..." },
        { "selectionTicket": "tkt_b2...", "tenantId": "t_b", "tenantName": "B医院",
          "role": "actor", "roleType": "MEMBER", "lastAccessAt": "..." }
      ]
    }

─── C 端选择（仅当前租户 Subject；绝不含他租户）───
Phase 1  POST /api/auth/login/subject   （品牌已锁定 tid=t_a）
  → {
      "step": "SELECT_CONTEXT",
      "identityToken": "<id-jwt, ≤5min, jti=J2>",
      "contexts": [    // 仅 tenant=t_a 的 subject；不做跨租户聚合
        { "selectionTicket": "tkt_c3...", "tenantId": "t_a", "tenantName": "A诊所",
          "role": "subject", "roleType": "CUSTOMER", "lastAccessAt": "..." }
      ]
    }
  → 分支（C 端固定）：0 个 → NO_TENANT；1 个 → 自动进入。
     `UNIQUE (tenant_id, identity_id)` 保证同一 Identity 在同租户至多 1 个 Principal，**C 端不展示 Context Selector**（无 ≥2 分支）。

Phase 2 选上下文 POST /api/auth/select-context  Bearer <identityToken>
  Body: { "selectionTicket": "tkt_a1...", "rememberChoice": true }
  → 服务端校验 ticket：① 未过期（≤5min）② 未使用过（一次性）
      ③ 绑定的 identityToken.jti == 当前 identityToken.jti（不止 sub，见下方硬约束）
  → 校验通过 → 取出绑定记录的稳定 context_id（§5.1/§5.2）及 { tenant, role, member/principal, uid }
  → 校验绑定仍有效 + 租户 ACTIVE|TRIAL
  → 签发 Actor/Subject Token（cid=<context_id>）+ Refresh Token（cid=<context_id>）
  → 作废该 ticket（标记已使用）；更新 last_access_at

Phase 3 业务请求 GET /api/v1/...  Bearer <accessToken>
  → 验签(JWT §8.1) + authz_version 校验(§8.2) → TenantContext.set(tid, cid)
  → 按 aud 分派 Member/Principal 校验 → 对象级授权(§9.6) → 全栈隔离(§10)

Phase 4 切换上下文 POST /api/v1/context/switch  Bearer <currentToken>    （仅 Actor Token 可用）
  Body: { "targetContextId": "<context_id>" }     // 切换用稳定 contextId（已认证态，无需 ticket）
  → 切换范围铁律（见红线 [T-26](#12-架构红线)）：
      ① 仅 Actor Token 可切换，且只能切到【同一 identity 的其他 Actor 上下文】
      ② Subject Token 禁止切换：既不可切到 Actor 上下文，也不可切到其他租户（C 端原则上不提供 Context Switch）
      ③ Actor↔Subject 身份转换必须重新进入对应登录入口（/login/actor 或 /login/subject），不走本接口
  → 校验目标 contextId 属于同一 identity、role==actor 且有效 → 重签 Token（旧 jti 入黑名单）
  → 前端 queryClient.clear() + resetState() + 重载配置/品牌/features

Phase 5 刷新   POST /api/auth/refresh  { refreshToken }
  → 校验未撤销 + cid 绑定关系仍有效 → 轮转 RT（旧 RT 立即失效）
  → Family 重放检测：已失效 RT 被重用 → 撤销整个 Family → 强制重登
```

**`contextSelectionTicket` 安全硬约束（红线 T-20 相关）：**

1. **绑定 Identity Token 的 `jti`（不止 `sub`）**：ticket 必须与签发它的 `identityToken.jti` 强绑定。仅绑 `sub` 不足——同一身份的另一枚有效 identityToken（或重放的旧 token）也能用同一 ticket。校验时要求 `ticket.bound_jti == identityToken.jti`，否则拒绝。
2. **一次性 + 短 TTL**：单次使用，使用后立即作废；TTL ≤ 5min（不超过 identityToken 寿命）。
3. **防枚举**：ticket 为高熵不可预测随机值（≥128bit），**不得**是自增/可猜的 contextId；服务端按 identity 维度限流，防止暴力探测他人上下文。
4. **防重放**：作废态持久化（Redis/DB），重复提交同一 ticket 返回 409/401 且记审计；identityToken 失效（jti 过期/撤销）后其名下所有 ticket 一并失效。
5. **稳定 `contextId` 不在选择阶段下发**：客户端在选择时只见 ticket；Token 签发后才在 `cid` 中持有稳定 contextId，用于后续切换/记忆。

### 9.4 B 端与 C 端登录逻辑分离

> B 端与 C 端登录入口与可见范围**严格分离**：**B 端只查询并返回 Actor 上下文，C 端只查询当前租户的 Subject 上下文**，C 端绝不暴露用户在其他租户的任何信息。**登录入口固定为** `/api/auth/login/actor` 与 `/api/auth/login/subject` **两个独立端点**；**`client_type` 不作为通道选择依据**。

| 维度 | B 端（Actor 入口，`/login/actor`） | C 端（品牌 App，`/login/subject`） |
|------|-------------------|---------------------------|
| 查询对象 | **仅** `sys_tenant_member`（Actor） | **仅** `sys_tenant_principal`（当前租户 Subject） |
| 跨租户可见性 | **可列出员工所属的多个租户**（走 §9.2 `discoverActor`） | **只能查询当前租户的 Principal** |
| 租户判定 | 登录后选择上下文 | 品牌/子域名已锁定单一 `tid`（仅作提示，仍以服务端绑定为准） |
| 返回信息 | 该 identity 的全部 actor contexts | **仅当前租户**的 subject context |
| 禁止项 | 不返回任何 Principal/Subject 信息 | **禁止返回该用户在其他租户接受服务的任何信息**（租户名、就诊记录、订单等一律不可见） |

> C 端实现要点：品牌 App 调用的发现接口**强制注入当前租户 `tid` 过滤**，`AuthnTenantLookupService.discoverSubject` **只查 `sys_tenant_principal WHERE tenant_id = :current AND identity_id = :id`**，不做跨租户聚合。B 端实现要点：`discoverActor` 只返回 `sys_tenant_member`，绝不附带 Principal。

### 9.5 同上下文双身份 & 设备记忆

- **同租户双身份**：以稳定 `contextId` 区分（§9.3），按 `tenant_id` 分组、角色标签区分，不显示为重复租户卡片。
- **C 端品牌 App** 直进当前租户 Subject 上下文，**永不弹选择器**（`UNIQUE (tenant_id, identity_id)` 保证同租户至多 1 个 Principal）。Context Selector / Context Switch **仅属 B 端 Actor 多租户场景**。
- **设备记忆**：记 `last_context_id`（Web localStorage / Mobile SecureStorage）+ 服务端 `last_access_at` 排序。

### 9.6 租户内对象级授权（同租户越权防护，红线 T-22）

> **`TenantInterceptor` 只解决"跨租户"，不解决"同租户内用户互相越权"。** 同一租户内，A 用户不得读写 B 用户的 Case / Order / File。租户隔离之上**必须再有对象级授权**。

**强制规则：**

1. **Subject 默认数据范围 = 自己**：Subject（C 端）默认**只能访问与自己 `principal_id` 关联的业务对象**（Case、Order、File、Appointment 等）。访问他人对象一律拒绝（403），除非有显式授权关系（如家庭共享、代理）。
2. **Actor 访问业务对象必须校验 permission + data scope**：Actor（B 端）访问业务对象时，既要校验**操作权限**（permission，如 `case:read`），又要校验**数据范围**（data scope，如"仅本部门 / 仅经手病例 / 全租户"）。角色 ≠ 无限数据范围。
3. **所有客户端传入的业务对象 ID 必须做授权校验**：任何来自请求的 `caseId` / `orderId` / `fileId` 等，**服务端必须校验该对象属于当前租户且当前主体有权访问**，禁止"传了 ID 就返回"（防 IDOR / 越权）。
4. **校验在服务端、靠不可篡改上下文**：授权主体取自已验签 JWT 的 `pid`/`mid` + `tid`，**不信任**请求体内的任何归属字段。

```text
对象级授权判定（每次访问业务对象 objId）：
  1. 加载对象 → 校验 obj.tenant_id == ctx.tid           （跨租户：T-9 拒绝）
  2. if ctx.isSubject():
        allow ⇔ obj.owner_principal_id == ctx.pid
                 OR 存在显式共享授权(objId, ctx.pid)
     else if ctx.isActor():
        allow ⇔ hasPermission(ctx, action)              （permission）
                 AND inDataScope(ctx, obj)               （data scope）
  3. 否则 403 OBJECT_ACCESS_DENIED + 审计
```

> 实现建议：提供统一 `AuthorizationCapability.requireObjectAccess(objRef, action)`，插件在每个读写入口调用；禁止插件自行裸查后直接返回。

## 10. 全栈租户隔离

> **隔离不止于 SQL。** 任一基础设施漏过 tenant 即构成越权面。以下为最小实现必须覆盖的隔离面（红线 T-14）。

| 基础设施 | 隔离要求 | 实现要点 |
|----------|----------|----------|
| **关系数据库** | 所有业务表 `WHERE tenant_id=?` 自动注入 | `TenantInterceptor` + `TenantSqlGuardInterceptor`（fail-closed） |
| **Redis / 缓存** | Key **自动带 tenant namespace** | 统一 KeyBuilder：`{tid}:{domain}:{key}`；禁止裸 Key |
| **Kafka / EventBus** | 事件 **必须携带 `tenantId`** | 消息头/信封强制 `tenantId`；消费者校验后才处理 |
| **对象存储（MinIO/S3）** | 路径 + 下载授权 **校验 tenant** | 路径前缀 `tenant/{tid}/...`；预签名 URL 校验 `tid` 归属 |
| **定时任务 / 异步线程** | 建立并**清理** TenantContext | `TaskDecorator` 复制上下文；`finally` 中 `clear()` |
| **消息消费** | 从消息头恢复 TenantContext，处理后清理 | 消费入口 set → 处理 → finally clear |
| **搜索索引** | 文档带 `tenantId`，查询强制过滤 | 索引 schema 含 `tenantId`；查询注入过滤器 |
| **导出 / 报表** | 导出范围限定当前 tenant | 导出服务复用 TenantContext，禁止跨租户聚合 |
| **审计日志** | 租户业务审计每条含 `tenantId`；平台/跨租户操作走独立 Platform Audit | 见 §10.1 |

> **上下文清理是硬约束**：线程池复用线程，若异步/消费任务结束后不 `clear()`，会把上一个租户的上下文泄漏给下一个任务，造成严重越权。所有 set 必须配对 finally clear。

### 10.1 审计分层 — 租户审计 vs 平台审计（红线 T-25）

> **一张审计表无法同时正确表达"租户内业务操作"与"跨租户/平台操作"。** 强行用单一 `tenant_id` 绑定跨租户审计会丢真相（跨租户操作没有唯一 tenant）。因此**拆两套审计**：

| 审计类型 | 表 | `tenant_id` | 记录内容 |
|----------|----|:-----------:|----------|
| **租户业务审计** | `biz_tenant_audit_log` | **NOT NULL** | 租户内成员/主体对业务对象的增删改查、登录、授权变更 |
| **平台审计** | `sys_platform_audit_log` | **可空 / 多值** | 登录期跨租户发现（§9.2）、平台超管经 typed Query/内部契约执行的跨租户操作、License 变更、红线治理 |

```sql
-- 租户业务审计：强制单租户绑定
CREATE TABLE IF NOT EXISTS biz_tenant_audit_log (
    id          BIGINT PRIMARY KEY,
    tenant_id   BIGINT NOT NULL,                 -- 强制 NOT NULL
    actor_ref   VARCHAR(64),                     -- member_id / principal_id
    action      VARCHAR(100) NOT NULL,
    object_ref  VARCHAR(128),
    detail      JSONB,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_tenant_audit_tenant ON biz_tenant_audit_log(tenant_id);  -- 红线 T-1：租户业务表 tenant_id 必建索引
CREATE TABLE IF NOT EXISTS sys_platform_audit_log (
    id            BIGINT PRIMARY KEY,
    operator_ref  VARCHAR(64) NOT NULL,          -- platform_admin_id / identity_id
    action        VARCHAR(100) NOT NULL,         -- LOGIN_TENANT_DISCOVERY | CROSS_TENANT_QUERY | LICENSE_CHANGE ...
    affected_tenants JSONB,                      -- 命中/影响的租户集合（0..N），不绑单一 tenant_id
    detail        JSONB,
    ip            VARCHAR(64),
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**约束：**

1. **租户内操作**写 `biz_tenant_audit_log`，`tenant_id NOT NULL`。
2. **登录期跨租户发现 / 平台超管跨租户查询 / License 与红线治理操作**写 `sys_platform_audit_log`，**不得**硬塞一个 `tenant_id`，用 `affected_tenants` 记录 0..N 个受影响租户。
3. `sys_platform_audit_log` 属平台全局表（白名单），由平台审计 Data Owner 唯一拥有；仅 `platform-admin` 可通过 descriptor 声明并经 privilege allowlist 批准的内部契约读取，禁止直接 Repository/Service 注入。
4. `detail` 与 `affected_tenants` 必须遵守根蓝图数据分类和脱敏规则，禁止写入 secret、credential、原始 token、密码、MFA secret 或未获批准的 PII。
5. `platform-admin` 写平台审计时，L2B 代理必须挂起调用方事务，由平台审计 Data Owner 在自身 context 的独立本地事务中提交；不得跨 Owner 传播连接、`EntityManager` 或 Session。

## 11. 能力契约（runtime-sdk-api）

> 接口签名是契约红线：演进只能 (a) 新增带 `default` 的方法，或 (b) 新增可选 Capability。破坏性变更走 [§13 红线变更治理](#13-红线变更治理)。

### 11.1 TenantContext 架构分层（红线 T-21）

| 层 | 职责 | 内容 |
|----|------|------|
| **Layer 2A**（`runtime-sdk-api`） | **仅定义** | 根蓝图目录中的 `TenantContextCapability`、租户/访问上下文不可变模型，以及租户领域 typed Query/Command/Event Schema |
| **Layer 2B**（Runtime） | **统一解析与策略代理** | 在 HTTP/Query/Command/Event/Task Dispatcher 边界验证 tenant/scope，并构造不可变 Invocation Context；向插件注入绑定 module identity 的 `TenantContextCapability` 代理 |
| **Layer 2C**（Adapter） | **基础设施映射** | 仅实现数据库、消息、缓存、对象存储等 tenant 隔离映射；不得向插件暴露 ThreadLocal、Servlet、Broker SDK 或底层客户端 |

**上下文传播矩阵（L2B Runtime 统一控制，L2C Adapter 仅消费经验证上下文）：**

| 运行模型 | 传播方式 | 清理 |
|----------|----------|------|
| HTTP（Servlet/WebFlux） | L2B Dispatcher 验证入口声明、Token 与 tenant hint 后构造 `EndpointInvocation` | 以调用完成、异常或取消为边界释放；Handler 不接触 Servlet/Reactor 原始上下文 |
| Query | L2B Query Gateway 从调用方 Invocation Context 派生 `QueryInvocation.scope` | `CompletionStage` 结束后释放，不使用插件 ThreadLocal |
| Command/Event | L2B Relay 验证 Envelope 的 scope/tenant/publisher 后构造 `CommandInvocation` / `EventInvocation` | 投递完成后释放；Handler 不自行读取消息头 |
| Scheduler Task | L2B Scheduler 根据 Manifest 的 scope/execution identity 策略构造 `TaskInvocation` | 任务完成、异常或取消后释放；禁止 `@Scheduled` 旁路 |
| 基础设施异步操作 | Runtime 管理的 Capability 代理显式传递不可变 Invocation Context | 受管资源账本负责有界停止和清理 |

> 兼容实现内部 MAY 使用 ThreadLocal 或 Reactor Context 作为 L2B 私有载体，但它不是插件契约，MUST NOT 由插件 set/clear、读取或作为正确性依据。

#### 11.3 前端契约（Layer 2B）

```typescript

/** 共同字段：两端都有 */
interface TenantContextBase {

  isFeatureEnabled: (feature: string) => boolean;

/** B 端 Actor：支持多上下文切换 */
interface ActorTenantContextState extends TenantContextBase {

  availableContexts: AccessContextOption[];   // 该 identity 在各租户的 Actor 上下文
  switchContext: (contextId: string) => Promise<void>;  // 切到同一 identity 其他 Actor 上下文（T-26）
```

#### 11.4 Capability 失败/SLO 策略

| 方法 | SLO(p99) | 失败行为 |
|------|:--------:|----------|
| `getCurrentTenantId` | < 1 ms | 抛 `TenantContextMissingException`（fail-closed） |
| `getCurrentTenant` | < 10 ms | 缓存击穿走 DB；DB 失败抛异常 |
| `isFeatureEnabled` | < 5 ms | 异常 → `false`（fail-closed） |
| `requireQuota` / `requireCanCreateTenant` | < 20 ms | 异常 → 抛异常拒绝（**fail-closed**，见 §15） |

#### 11.5 Capability 跨租户参数约束（红线 T-23）

1. **普通插件 Capability 一律不接受任意 `tenantId` 参数**——作用域永远是当前 `TenantContextCapability` 返回的已验证 tenant。`getUsageSummary(String tenantId)` 旧签名**已废弃**，改为 `getCurrentTenantUsage()`。
2. **跨租户只读查询/聚合必须由对应 Data Owner 发布版本化 typed Query**；`platform-admin` 只能按 descriptor 的 `queries.consumes`、scope/access policy 和 Runtime 构造的 Invocation Context 调用，每次调用记 Platform Audit（§10.1）。
3. **跨租户运维写动作必须通过 Data Owner 的版本化内部契约**；`platform-admin` 仅可经 `OperationalContext` 调用 descriptor `internalContracts.requires` 已声明且 privilege allowlist 批准的唯一 Provider。普通插件不得消费、枚举或查找内部契约。
4. **禁止定义 `AdminCapability` / `PlatformAdminCapability` 或通用跨租户 Capability**；构建期以 ArchUnit、artifact graph 和依赖白名单阻断。
5. 插件即使拿到他租户 ID 也无法用普通 Capability 读取其数据（接口层面就不收 tenantId）。

#### 11.6 事件分层与信封约束（红线 T-24）

> **区分两类事件**，避免把富领域对象推上 Kafka、或让跨模块消费者依赖模块内部类型：

| 类型 | 边界 | 是否进 Kafka | 信封要求 |
|------|------|:------------:|----------|
| **Domain Event** | 模块**内部** | 否 | 可携带富领域对象，无需信封 |
| **Integration Event** | **跨模块 / 进入 Kafka** | 是 | **必须**经 `EventEnvelope`，字段稳定可序列化 |

1. **跨模块或进入 Kafka 的事件一律定义为 Integration Event**，实现 `TenantIntegrationEvent` 并携带 `EventEnvelope`（`eventId` / `traceId` / `tenantId` / `schemaVersion` / `occurredAt`）。
2. `PrincipalJoinedEvent` / `PrincipalLeftEvent` 等跨模块事件**必须**是 Integration Event，禁止裸字段事件。
3. 消费侧从 `tenantId` 恢复 `TenantContext`（§10），用 `eventId` 幂等去重，按 `schemaVersion` 兼容演进。
4. **模块内部** Domain Event 不得越过模块边界直接发布到 Kafka；需要外泄时由模块出口转换为 Integration Event。

|---|------|----------|----------|

| **T-3** | 跨租户访问必须显式 `@CrossTenantAccess(reason, approval)` 且记审计 | 注解扫描 + Code Review | PR 阻断 |

| **T-25** | 审计分层：租户业务审计 `tenant_id NOT NULL`；跨租户/平台操作走独立 Platform Audit，禁止强绑单一 tenantId | Schema lint + 审计写入测试 | 阻断发布 |

## 13. 红线变更治理

任何对 §12 红线的新增/修改/删除，必须：

1. **RFC**：在 `docs/rfc/` 提交 `RFC-tenant-NNN-标题.md`（动机、影响面、迁移策略）。
2. **双人评审**：≥1 名平台架构组 + 1 名安全/SRE 成员签字。
3. **公示期**：合并前公示 ≥1 个 release cycle（默认 2 周）。
4. **机器化校验同步**：红线变更必须同步更新 ArchUnit / Flyway lint / 集成测试，否则不予合并。
5. **CHANGELOG**：记录到 `CHANGELOG-tenant.md`。

紧急安全红线走 `hotfix` 通道：先合并 + 当日补 RFC + 7 日内补公示评审。

## 14. 数据隔离策略（演进路径 + 可选 RLS 第二道防线）

### 14.1 隔离级别演进

| 级别 | 实现 | 版本 | 触发条件 |
|------|------|:----:|----------|
| **Row-Level** | `tenant_id` 字段 + 拦截器自动过滤；`TenantSqlGuardInterceptor` 防绕过 | **最小实现（默认）** | 默认 |
| Schema-Level | 动态 `search_path` / `SET SCHEMA` | v2.0+ | 中大租户 / 合规 |
| Database-Level | 动态数据源路由 | 企业版按需 | 数据主权 / 独立部署 |

> 所有隔离方案统一经 `TenantContextCapability` 与绑定 module identity 的基础设施 Capability 策略代理生效，插件代码零感知底层隔离实现。

### 14.2 可选 PostgreSQL RLS（应用层之外的第二道防线，红线相关 T-2/T-9）

> 通用版本以应用层 `TenantInterceptor` 为主隔离手段。在 **PostgreSQL** 上可额外启用 **行级安全（RLS）Adapter** 作为**数据库层兜底**——即使应用层出现遗漏，数据库仍强制隔离。

```sql
-- 启用 RLS（以 medical_case 为例）
ALTER TABLE medical_case ENABLE ROW LEVEL SECURITY;
ALTER TABLE medical_case FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON medical_case
    USING (tenant_id = current_setting('brix.tenant_id')::BIGINT);
-- 每个请求在连接上 SET LOCAL brix.tenant_id = '<tid>'（由 RLS Adapter 注入）
```

**RLS 硬约束：**

1. **医疗等高敏感部署建议启用 RLS**（合规与纵深防御）。
2. RLS Adapter 在每个事务开始时 `SET LOCAL brix.tenant_id`，与 `TenantContext` 同源。
3. **生产数据库账号禁止拥有绕过 RLS 的权限**（不得为 superuser / `BYPASSRLS`）；迁移/运维用单独受控账号。
4. RLS 是**第二道防线**，不替代应用层隔离；两者并存。

## 15. 配额与 License 失败策略（统一 fail 语义）

> 取消"放行默认值"。`checkQuota()` 旧设计（默认返回 `true`）**已删除**，改为 `requireQuota()` 显式抛异常。

| 校验类型 | 失败策略 | 说明 |
|----------|:--------:|------|
| 安全隔离校验（tenant/JWT/越权） | **fail-closed** | 任何异常 → 拒绝请求 |
| License 上限（租户数/席位） | **fail-closed** | 不满足 → 拒绝新增（不影响存量，见 §1） |
| 硬配额（maxUsers/maxPrincipals） | **fail-closed** | 超限 → `QuotaExceededException` |
| 非关键统计 / 用量计数 | **fail-open + 必须告警** | 计数失败不阻断主流程，但必须打点告警 |

> **绝不允许**安全或上限类校验"出错即放行"。仅**非关键统计**允许 fail-open，且必须触发告警，禁止静默吞错。

## 18. 运行壳架构对齐

| 运行壳层 | 多租户构件 | 职责 |
|----------|-----------|:----:|
| **Layer 2A**（Contract — `runtime-sdk-api`） | `TenantContextCapability`、`Tenant`/`AccessContext` 不可变模型、`TenantDirectoryCapability`、`TenantQuotaCapability`、`TenantConfigCapability`、`BusinessObjectCapability`（可选生态）、typed Query/Command/Event Schema | **仅契约/模型** |
| **Layer 2B Runtime** | HTTP/Query/Command/Event/Task 的 tenant/scope 验证、Invocation Context 构造、Capability 策略代理、Host 入口准入与上下文清理 | **统一运行时边界** |
| **Layer 2B platform-operational** | `platform-admin` 通过 typed Query 读取跨租户数据，通过 allowlist 内部契约执行运维写动作；不定义超管 Capability | **最小特权运维控制面** |
| **Layer 2C Adapter** | 数据库、Redis、Kafka、对象存储、搜索与可选 RLS 的 tenant 隔离映射；不得向插件暴露底层客户端或上下文载体 | **基础设施实现** |
| **前端 Shared Runtime** | `useTenant()`、`useTenantConfig()` | **唯一共享前端运行时** |

> 对插件开发者：多租户复杂度完全封装，插件仅通过 Capability 契约访问，零感知隔离细节；**禁止**直接依赖平台租户表或跨服务外键。

## 附录 A · 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| 租户 | Tenant | 独立业务实体，计费与数据隔离的最小单元 |
| 身份 | Identity | 平台级唯一身份，跨租户共享 |
| 成员 | Member / Actor | 租户 B 端组织成员（员工/管理者） |
| 访问主体 | Principal / Subject | 租户 C 端访问主体（客户/访客），准入凭证 |
| 档案 | Profile | 租户内用户档案（昵称/偏好） |
| 访问上下文 | Access Context | `{tenant, role, member/principal}` 的服务端绑定，由稳定 `contextId` 引用；选择阶段用一次性 `contextSelectionTicket` |
| 上下文 ID | context_id / contextId | `sys_tenant_member`/`sys_tenant_principal` 的稳定 UUID 列，= Token `cid`，创建后不可改 |
| 领域事件 | Domain Event | 模块内部事件，不跨进程/不进 Kafka |
| 集成事件 | Integration Event | 跨模块 / 进入 Kafka 的事件，必经 `EventEnvelope` |
| 业务对象 | BusinessObject | Case/Order/Enrollment 等，由插件自建 |
| 租户上下文 | Tenant Context | 当前请求所属租户的运行时上下文 |
| 上下文切换 | Context Switch | 同一身份在不同 Access Context 间切换登录态 |
| 行级隔离 | Row-Level Isolation | 同表通过 `tenant_id` 隔离数据 |
| RLS | Row-Level Security | PostgreSQL 数据库层行级安全，作为第二道防线 |
