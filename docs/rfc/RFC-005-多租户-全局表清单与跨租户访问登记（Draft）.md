## 0. 结论

1. §6.1 白名单补入 `sys_setup_token`、`sys_bootstrap_state`。§6.1 同时是持久化 Adapter 的全局表登记清单，二者一一对应。
2. 新增 §6.4「跨租户访问登记表」，穷举允许的跨租户访问。表外的跨租户访问一律禁止。
3. 写明本专项所称 `TenantInterceptor` 指持久化 Adapter 在 ORM 层自动施加的租户过滤（根 `BRX-RS-DATA-040`），不特指某个类。
4. DDL、T-1～T-30、Token 结构、权限码目录与默认授予都不变。

## 1. 背景

按根 `BRX-RS-DATA-040`，租户过滤要从 platform-tenant 的 `StatementInspector` 移到持久化 Adapter，由 ORM 层自动施加，见设计方案 §3、§4。新机制默认拒绝：

- 没有 `tenant_id` 的表必须登记为全局表；
- 跨租户访问只能由 Runtime 按登记授予。

盘点现有代码时发现两处蓝图缺口。

**缺口一：§6.1 少两张全局表**

`sys_setup_token`、`sys_bootstrap_state` 不在 §6.1 中：

- 它们由 super-admin 4.0 定义：§15.2 是 setup token，§15.8 是 Bootstrap 单例；
- 两张表都没有 `tenant_id`；
- 现在它们靠 `sys_*` 前缀规则被放过，而这正是 T-15 禁止的写法。

**缺口二：§6.3 只登记了部分跨租户访问**

§6.3 只登记了登录期 Actor 发现，以及平台超管链路。代码中还有两处跨租户读取，蓝图没有统一登记：

| 读取 | 现状 | 现有依据 |
|---|---|---|
| 按 FIRST_OWNER 邀请 token 解析邀请 | 托管邀请页、接受入口都在租户确定前按 `token_hash` 查邀请 | identity-auth ONBOARD-002；`BRX-TENANT-ENTRY-005`；§5.7 接受伪代码的第一步就是 `WHERE token_hash = :tokenHash FOR UPDATE` |
| 受邀人完成设置后补发邀请 | 平台超管邀请一个还没有账号的邮箱时，系统先发设置链接；设置完成后，platform-tenant 按该邮箱找出所有待接受的 FIRST_OWNER 邀请并发出 | 没有条款 |

## 2. 方案比较（补发邀请）

| 方案 | 内容 | 结论 |
|---|---|---|
| **A** 登记为跨租户访问 | 键是"刚完成设置的身份的邮箱"，由 Runtime 从身份 Owner 已提交的事实取得；只能看到、修改发给这个邮箱的待接受 FIRST_OWNER 邀请；写平台审计 | **采纳**：改动小，行为不变 |
| **B** 设置流程携带邀请引用 | 设置完成后只处理随设置流程带来的邀请，每个都在自己的租户内处理，不需要跨租户读 | 不采纳：要改身份侧 setup token 表（super-admin §15.2 的表语义）和 L2A 契约，涉及两个 Owner |
| **C** 取消补发 | 设置完成后直接进入接受 | 不在本 RFC 范围：它改变用户可见的流程。以后若采用，删除 §6.4 中这一行即可 |

## 3. 条款修订（写入 multi-tenant 5.1.2）

1. **§6 前言**：新增 v5.1.2 说明——本专项所称 `TenantInterceptor` 指持久化 Adapter 在 ORM 层自动施加的租户过滤（根 `BRX-RS-DATA-040`），不特指某个类或某种实现。
2. **§6.1**：
   - 补入两行：`sys_setup_token`（super-admin 4.0 §15.2）、`sys_bootstrap_state`（super-admin 4.0 §15.8）；
   - 新增"全局表登记"说明：本表即 Adapter 的全局表登记清单。没有 `tenant_id` 又不在本表的表，Adapter MUST 在启动期失败；业务插件的表不得登记为全局表（T-1）。
3. **§6.3**：原文不变，末尾增加一条指引，指向 §6.4。
4. **新增 §6.4 跨租户访问登记表**，共四项：
   - 登录期 Actor 发现（§6.3 原有）；
   - FIRST_OWNER 邀请解析（补登记）；
   - 受邀人设置完成后补发（新增）；
   - 平台超管定向操作（§6.3 第 4 点原有）。

   每项写明依据、访问键与来源、可访问的租户表、读写和审计；另加三条通用规则：
   - 命中的行决定之后可访问的租户集合；
   - 表外的跨租户访问一律禁止；
   - 登记项名是 Runtime 策略 ID，Manifest 只能引用。
5. **§0.4**：实施验收项 I5 增加"§6.4 登记表外的跨租户访问被拒绝"。
6. **同步**：新增 §0.0d 与附录 G；文首、§0.4、§19.1 和文末状态同步。

## 5. 兼容性、迁移与回滚

- **数据与接口**：没有数据迁移，没有对外接口变化。
- **代码对应关系**：
  - Adapter 的全局表清单与 §6.1 一致；
  - Runtime 的跨租户策略与 §6.4 一一对应。

  两者都在设计方案 P1/P2 中实现。
- **施工时序**：设计方案的 P1 合并前需要 5.1.2 生效。原因是：
  - Adapter 按 §6.1 校验全局表；
  - 补发邀请的旧实现依赖即将删除的豁免。
- **未获批准时**：5.1.1 继续有效，P1/P2 不合并，现有隔离实现保持不变。
