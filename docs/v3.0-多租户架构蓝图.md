## 1. 核心设计共识

| # | 设计共识 | 不可推翻原因 |
|---|----------|--------------|
| 1 | **Actor / Subject 物理分离** — `sys_tenant_member`（B 端组织成员）与 `sys_tenant_principal`（C 端访问主体）独立建表 | 同一人可同时是某租户员工与客户（医生在自己诊所看病）；统一表会导致语义污染、生命周期纠缠 |
| 2 | **三层身份模型** — Identity（全局）→ Member / Principal（租户接入）→ Profile（租户内档案） | 表结构与外键关系定型，演进只能加字段，不能改主键 |
| 3 | **JWT 双轨签发** — Actor Token 含 `mid/mtype`，Subject Token 含 `pid/ptype`，两者**互斥** | 已签发 Token 不可修改，结构必须前向兼容 |
| 4 | **TenantContext 统一上下文** — ThreadLocal + Reactive Context + `TenantTaskDecorator` 异步装饰器 | 所有业务代码依赖此 API，下沉到 `runtime-sdk-api` |
| 5 | **行级隔离起步、适配器演进** — `tenant_id` 字段 + 拦截器；后续 Schema / DB 隔离走 Adapter，对插件零感知 | 业务表统一字段不可移除 |
| 6 | **基座层零行业语义** — `member_type` / `principal_type` 仅含通用枚举，行业语义只能在插件层出现 | 平台不被任何行业（医疗 / 教育 / 电商）锁死 |
| 7 | **BusinessObject 不入基座** — Case / Order / Enrollment 等由插件自建表，通过 `BusinessObjectCapability` 暴露通用摘要 | 避免 base 层枚举膨胀，保持基座中性 |

## 2. 三层身份模型

```text
Layer 0: sys_identity                  全局身份（手机/邮箱/凭证），跨租户共享
   │                                    与租户无关，1 人 = 1 条记录
   │
   ├─► Layer 1A: sys_tenant_member     B 端 — 组织成员（Actor）
   │     • member_type ∈ { OWNER, ADMIN, MEMBER }
   │     • 准入：邀请 → 审批 → 加入（管理流程）
   │     • 语义：谁是这个租户的员工/管理者
   │
   └─► Layer 1B: sys_tenant_principal  C 端 — 访问主体（Subject）
         • principal_type ∈ { CUSTOMER, GUEST }
         • 准入：扫码 / 预约 / 链接 → 自动创建（自动化）
         • 语义：谁有权作为外部用户访问这个租户
                 │
                 ▼
Layer 2: biz_user_profile              租户内用户档案（每租户独立）
   • ref_type ∈ { MEMBER, PRINCIPAL } + ref_id
   • UNIQUE(tenant_id, ref_type, ref_id)
   • 同一人在不同租户可有不同昵称、偏好
```

> 表结构详见 [B2B2C多租户模型-讨论定稿.md](./archived/B2B2C多租户模型-讨论定稿.md) 第 2 章；DDL 与 Flyway 迁移见 [v0.1-多租户MVP实施清单.md](./v0.1-多租户MVP实施清单.md)。

## 3. JWT Token 契约（双轨）

```jsonc
// Actor Token（B 端签发链）
{
  "sub":  "<identity_id>",      // 全局身份
  "tid":  "<tenant_id>",        // 租户（TenantFilter 唯一依赖字段）
  "mid":  "<member_id>",        // 组织成员关系
  "mtype":"ADMIN",              // OWNER | ADMIN | MEMBER
  "uid":  "<profile_id>"        // 租户内档案
}

// Subject Token（C 端签发链）
{
  "sub":  "<identity_id>",
  "tid":  "<tenant_id>",
  "pid":  "<principal_id>",     // 访问主体关系
  "ptype":"CUSTOMER",           // CUSTOMER | GUEST
  "uid":  "<profile_id>"
}
```

**硬约束：**

- `mid` 与 `pid` **必须互斥**：签发时二选一；校验侧按存在的字段分派；不允许混合态。
- `TenantFilter` 仅依赖 `tid`，对两类 Token 无差别处理。
- 租户切换或 Actor↔Subject 视角切换必须走 [§5 视角切换契约](#5-视角切换契约)，重签 Token（旧 Token 配合短 TTL + `jti` 黑名单失效）。
- 客户端不得篡改 `tid`：JWT 必须使用非对称签名（RS256），公钥支持密钥轮转（`kid`）。

## 4. 租户解析机制

按优先级单链路解析（责任链模式）：

| 优先级 | 解析器 | 适用场景 | 落地版本 |
|--------|--------|----------|----------|
| 1 | `JwtTenantResolver` | 已认证请求（绝大多数） | v0.1 ✅ |
| 2 | `HeaderTenantResolver`（`X-Tenant-Id`） | 服务间内部调用 | v0.1 ✅ |
| 3 | `SubdomainTenantResolver` | Web 登录前识别（`acme.brix.com`） | v1.2 |
| 4 | `PathTenantResolver` | 小程序、API 网关（`/t/{code}/...`） | v1.2 |
| 5 | `QueryTenantResolver` | 公开链接（注册 / 邀请） | v1.2 |
| 兜底 | 默认租户 | 单租户模式 / 开发环境 | v0.1 ✅ |

### 4.1 冲突处理规则（红线）

> **风险背景**：当 JWT 含 `tid=A`、Header 同时带 `X-Tenant-Id=B` 时，沉默覆盖将成为越权攻击面。

- **责任链终止规则**：高优先级解析器命中即终止，不再向下调用。
- **冲突拒绝规则**：当低优先级源（Header / Subdomain / Path / Query）显式声明的 `tid` 与已命中高优先级源**不一致**时，必须：
  1. 立即拒绝请求（HTTP 400 `TENANT_CONFLICT`）；
  2. 写入 `audit_security_event`，标记 `severity=HIGH`；
  3. 触发监控告警（每分钟 > N 次自动封禁来源 IP）。
- **降级仅限"未声明"场景**：低优先级源未提供 `tid` 时，使用高优先级源的解析结果，无冲突告警。

## 5. 视角切换契约

支撑场景：同一 `identity_id` 既是某租户员工（Actor）又是客户（Subject）；或在多个租户间切换。

```http
POST /auth/switch-context
Authorization: Bearer <current-token>
Content-Type: application/json

{
  "target_tenant_id": "<tenant_id>",        // 目标租户
  "target_view": "ACTOR" | "SUBJECT",        // 切换视角
  "reason": "string (可选，用于审计)"
}

→ 200 OK
{
  "access_token": "<new-jwt>",               // 重签后的 token
  "expires_in": 3600,
  "revoked_jti": "<old-jti>"                 // 旧 token 已加入黑名单
}
```

**硬约束：**

- 旧 token 立即作废（`jti` 写入 Redis 黑名单，TTL = 旧 token 剩余 TTL）。
- 切换必须通过此接口，禁止任何"客户端就地改写 claim"路径。
- 目标视角 + 目标租户必须存在对应的 Member 或 Principal 记录，否则 403。

## 6. 数据隔离策略（演进路径）

| 级别 | 实现方式 | 适用版本 | 触发条件 |
|------|----------|----------|----------|
| **Row-Level** | `tenant_id` 字段 + JPA / MyBatis 拦截器自动过滤；`TenantSqlGuardInterceptor` 防绕过 | v0.1（开源版默认） | 默认 |
| **Schema-Level** | 动态 `search_path` / `SET SCHEMA` 切换 | v1.0+（商业版默认） | 中大租户 / 合规需求 |
| **Database-Level** | 动态数据源路由 | v2.0（企业版按需） | 数据主权 / 独立部署 |

**统一抽象**：所有隔离方案均通过同一个 `TenantCapability` 契约暴露给插件，插件代码无差别使用，零感知。

## 7. TenantCapability 契约

> 位置：`runtime-sdk-api`（运行壳蓝图 Layer 2A 能力契约层）。  
> **契约演进规则**：接口签名是契约红线，演进只能 (a) 新增方法（必须带 `default` 实现），或 (b) 新增可选 Capability 接口。任何破坏性变更必须按 [§9 红线变更治理](#9-红线变更治理) 走 RFC。

```java
/** 核心 Capability（所有 Host 必须提供） */
public interface TenantCapability extends RuntimeCapability {

    /** @since 0.1 */
    String getCurrentTenantId();

    /** @since 0.1 */
    Tenant getCurrentTenant();

    /** @since 0.1 */
    void requireActiveTenant();

    /** @since 1.0 */
    default boolean isFeatureEnabled(String featureKey) {
        return false; // 默认关闭，由实现覆盖
    }

    /** @since 1.0 */
    default boolean checkQuota(String quotaKey, long requested) {
        return true;  // 默认放行，由实现覆盖
    }
}

/** 租户管理 Capability（商业版可选） */
public interface TenantManagementCapability extends TenantCapability {
    Tenant createTenant(TenantCreateRequest request);
    void   suspendTenant(String tenantId, String reason);
    void   inviteMember(String tenantId, MemberInviteRequest request);
}

/** 租户配置 Capability（v1.2 新增，承载默认语言/主题/时区/品牌） */
public interface TenantConfigCapability extends RuntimeCapability {
    TenantConfig get(String tenantId);
    void         update(String tenantId, TenantConfigPatch patch);
}

/** 业务对象 Capability（可选；让通用 UI 展示插件业务摘要，避免基座感知行业语义） */
public interface BusinessObjectCapability extends RuntimeCapability {
    List<BusinessObjectSummary> listByPrincipal(String principalId);
    boolean hasActiveBusinessRelation(String principalId);
}
```

### 7.1 Capability SLO 与降级契约

| 方法 | SLO（p99） | 失败行为 | 降级返回 |
|------|-----------|----------|----------|
| `getCurrentTenantId` | < 1 ms（纯内存） | 抛 `TenantContextMissingException` | 不降级 |
| `getCurrentTenant` | < 10 ms（带缓存） | 缓存击穿走 DB；DB 失败抛异常 | 不降级 |
| `isFeatureEnabled` | < 5 ms | 任何异常 → 返回 `false`（fail-closed） | `false` |
| `checkQuota` | < 20 ms | 任何异常 → 返回 `true`（fail-open，避免误杀） | `true` + 告警 |

> 实现层（`platform-commons/server/platform-multitenancy`）必须为每个方法附带 Micrometer 指标 + OTel span，并在 SLO 越界时触发告警。

## 8. 多租户架构红线

> 红线编号采用全局统一前缀 `T-x`（Tenant），与运行壳红线 `A-x`（Architecture）/ `S-x`（Security）正交。

| # | 红线 | 校验方式 | 违反处置 |
|---|------|----------|----------|
| **T-1** | 业务表必须带 `tenant_id BIGINT NOT NULL` 且建索引（白名单：`sys_*`） | Flyway 校验 + ArchUnit | 阻断发布 |
| **T-2** | 所有数据访问必须经 `TenantInterceptor`，禁止裸 SQL 绕过；**dev / prod 行为一致：均 fail-closed（抛异常）** | `TenantSqlGuardInterceptor` | 阻断请求；告警仅作为兜底审计，不替代阻断 |
| **T-3** | 跨租户访问必须显式 `@CrossTenantAccess(reason, approval)` 注解 | 编译期注解扫描 + Code Review | PR 阻断 |
| **T-4** | JWT `tid` 不可被客户端篡改；租户/视角切换必须经 [§5 视角切换契约](#5-视角切换契约) 重签 | 非对称签名 + 切换接口强制重签 | 服务端校验拒绝 |
| **T-5** | Actor Token 与 Subject Token 不允许同时持有 `mid` 和 `pid` | 签发单元测试 + 校验侧硬断言 | 签发拒绝 / 校验拒绝 |
| **T-6** | 基座 `sys_*` 表的枚举字段禁止行业语义（Patient / Student / Buyer 等） | Code Review + Schema lint | PR 阻断 |
| **T-7** | 插件不得直接读写 `sys_tenant_member` / `sys_tenant_principal`，必须经 `TenantCapability` | ArchUnit 包依赖规则 | CI 阻断 |
| **T-8** | C 端业务表外键指向 `sys_tenant_principal`，B 端业务表外键指向 `sys_tenant_member`，禁止交叉 | DDL Review + Flyway 校验 | 阻断发布 |
| **T-9** | 跨租户数据泄露零容忍：单租户成员不得查询/统计他租户数据 | 集成测试 + 运行时审计；与 T-2 的 fail-closed 行为一致 | 请求阻断 + 安全工单 |
| **T-10** | 责任链解析冲突必须拒绝并审计（见 [§4.1 冲突处理规则](#41-冲突处理规则红线)） | `TenantResolverChain` 单元测试 + 集成测试 | HTTP 400 + 安全告警 |

> **T-2 与 T-9 一致性说明**：旧版 v3.0.9 中 T-2 在 prod 环境降级为"告警"，与 T-9"零容忍"语义冲突。本版统一为 **dev / prod 均 fail-closed**，告警仅作为审计兜底，不替代请求阻断。

## 9. 红线变更治理

任何对 §8 红线的新增 / 修改 / 删除，必须遵循以下流程：

1. **提案（RFC）**：在 `docs/rfc/` 提交 `RFC-tenant-NNN-标题.md`，说明动机、影响面、迁移策略；
2. **双人评审**：至少 1 名平台架构组成员 + 1 名安全 / SRE 成员签字；
3. **公示期**：合并前公示 ≥ 1 个 release cycle（默认 2 周）；
4. **机器化校验同步上线**：红线变更必须同步更新对应 ArchUnit / Flyway lint / 集成测试用例，否则不予合并；
5. **CHANGELOG**：记录到 [CHANGELOG-tenant.md](./CHANGELOG-tenant.md)（如不存在则首次创建）。

紧急安全红线（如响应已暴露的越权漏洞）可走 `hotfix` 通道：先合并 + 当日补 RFC + 7 日内补公示评审。
