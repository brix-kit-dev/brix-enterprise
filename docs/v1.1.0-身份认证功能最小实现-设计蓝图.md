## 0. 文档定位与边界

### 0.1 范围

| 用户 | 典型身份 | 客户端 | 上下文 |
|---|---|---|---|
| 平台超管 | 平台运营方 | `platform-console` | platform |
| 租户员工（B 端 Actor） | OWNER、ADMIN、MEMBER | `tenant-console` | actor |
| 终端用户（C 端 Subject） | 患者、学员、买家等 | 各品牌应用 | subject |

本文覆盖上述三类用户的登录、凭证、认证强度、会话、首次设置、恢复、防滥用和认证审计。

### 0.2 与其他蓝图的边界

| 蓝图 | 负责 | 本文引用方式 |
|---|---|---|
| runtime-shell 3.4.0（根） | 身份协议面的落位与例外（`BRX-RS-SECURITY-011`）、Web 客户端 BFF（012）、特权访问防钓鱼（013）、失败防护（014）、敏感操作再验证（015）、凭证页面限制（`BRX-RS-UI-018`）、红线 S-19、S-20 | 本文在其范围内细化，不得放宽 |
| super-admin 专项 | 平台授权（`sys_platform_admin`）、Bootstrap 两阶段模型、超管管理用例 | 平台超管的登录、MFA、setup、恢复引用本文 |
| multi-tenant 专项 | 成员、主体、上下文、登录期发现、selection ticket、Token claims 语义、邀请 | 认证完成后的上下文选择按 multi-tenant 执行，载体由本文定义 |
| frontend 专项 | 前端分层、BrixUI、路由与会话消费规则 | 托管登录页和控制台的前端规则引用 frontend |

### 0.3 非目标

- 不自研认证器 App；本期不提供"自家 App 扫码登录"；
- 短信、邮件验证码不作为特权访问的认证因素；
- 不定义权限码目录和 RBAC（由授权模型另行定义）；
- 本期不实现 SAML、SCIM 和企业 IM 登录（商业版，后续 RFC）；
- 不改变 multi-tenant 的成员、主体、上下文与隔离语义，不改变 super-admin 的平台授权与 Bootstrap 语义。

### 0.4 状态

本文是 v1.1.0 的 Freeze Candidate（2026-11-13 起草）：架构委员会、安全、SRE 批准最终字节，并在控制平面 lock 中登记哈希、commit 与批准记录后生效；此前不指导施工，v1.0.1 仍是 `ACTIVE / Architecture Frozen`。v1.0 于 2026-10-22 批准生效。实施验收（Implementation Accepted）另按 §13 的门禁独立登记。

## 1. 术语

| 术语 | 唯一含义 |
|---|---|
| 身份协议面 | OIDC/OAuth 协议端点、托管登录页及其接口、BFF 会话端点的总称（根 `BRX-RS-SECURITY-011`） |
| 托管登录 | 由身份协议面提供的登录、设置、恢复页面；凭证只在这里输入 |
| BFF | Backend for Frontend：替浏览器应用保存 Token 的服务端会话层，浏览器只持有会话 Cookie（RFC 10017 §6.1） |
| 客户端策略 | 每个客户端允许的登录方式、认证强度要求、会话时长、是否允许受信设备和上下文类型 |
| 认证强度 | 一次认证达到的等级（`acr`）与所用方式（`amr`），以及认证时间（`auth_time`） |
| passkey | 基于 FIDO2/WebAuthn 的公钥凭证，可存于本机、同步到密码管理器，或经跨设备方式由手机完成 |
| 受信设备 | 完成过第二因素的设备凭据；只免除非特权账号的第二因素 |
| 敏感操作再验证 | Endpoint 声明最低认证强度和认证有效期，不满足时要求重新认证（根 `BRX-RS-SECURITY-015`） |
| 外部身份 | 第三方登录提供方返回的身份（提供方 ID + 提供方用户 ID），与 Brix 身份关联后使用 |

## 2. 架构与分层落位

```text
浏览器（平台控制台 / 租户员工控制台 / 品牌 Web）
   │  同源会话 Cookie（__Host- 前缀，HttpOnly，Secure，SameSite）+ CSRF 自定义请求头
   ▼
BFF 会话层（身份协议面）
   │  机密客户端；授权码 + PKCE；Token 只在服务端，会话存储加密
   ├──────▶ L2B Dispatcher：authentication 步骤从会话取得 Token 并按根 SECURITY-004 校验
   ▼
认证服务（身份协议面，L2C 身份提供方 Adapter，默认 Spring Authorization Server）
   ├─ 托管登录：先识别账号 → passkey / 密码 / TOTP / 短信 / 第三方
   ├─ 认证后选择上下文：员工 = 所属租户；终端用户 = 品牌应用绑定的租户
   └─ 只经 L2A 能力契约访问身份与租户数据
   ▼
platform-identity（身份、凭证、MFA 因子、受信设备、外部身份关联）
platform-tenant（成员、主体、上下文、登录期发现）

原生 App：系统浏览器 + 授权码 + PKCE（RFC 8252），Token 存系统安全存储
```

| 位置 | 模块 | 职责 |
|---|---|---|
| L2A 契约 | `runtime-sdk-api` | `AuthCapability`、`IdentityAccountCapability` 等按需扩展：凭证校验、MFA 因子、受信设备、外部身份关联、上下文发现；第三方登录提供方 SPI；Bootstrap 会话的开启（`BootstrapSessionCapability`，由 platform-identity 实现，只给身份协议面用） |
| L2C Adapter | `infra-adapter-identity-provider` | 内嵌 Spring Authorization Server，承载身份协议面：OIDC 端点、托管登录接口、BFF 会话端点、第三方登录通用层 |
| L2C Adapter | `infra-adapter-redis` | BFF 会话与授权记录的服务端存储（加密） |
| 身份 Data Owner | platform-identity | 身份、凭证、MFA 因子、受信设备、外部身份关联；实现 L2A 身份契约 |
| 租户 Data Owner | platform-tenant | 成员、主体、上下文和登录期发现 |
| L2B | Dispatcher | 会话认证、授权、再验证 |
| L3 | Host | 在 Composition 中显式选择身份提供方 Adapter，不包含认证代码 |
| 前端 | 托管登录前端模块（platform-commons 下独立模块） | 托管登录页，由身份协议面在 `/auth/**` 下提供 |

[BRX-IA-LAYER-001] 身份提供方 Adapter MUST 只依赖 L2A 契约和基础设施 SDK（根 §3.2），MUST NOT 依赖 platform-identity、platform-tenant 或任何 Owner 的实现类型；读写身份和租户数据一律经 L2A 契约。

[BRX-IA-LAYER-002] 替换为外部 IdP 时 MUST 只替换身份提供方 Adapter；插件、控制台、Owner 与 L2A 契约不得因此改变。

[BRX-IA-LAYER-003] 身份协议面使用根蓝图登记的保留前缀 `/oauth2/**`、`/.well-known/**`、`/auth/**`、`/bff/**`，MUST NOT 与 `/api/**` 重叠。

## 3. 所有权

[BRX-IA-OWNER-001] platform-identity 是身份数据的唯一 Data Owner，包括：全局身份、密码凭证、passkey 公钥凭证、TOTP 因子、恢复码、受信设备、外部身份关联和认证事件。身份协议面 Adapter 持有协议数据：客户端注册、授权码、授权记录和会话；它只经 L2A 能力契约读写身份数据。

[BRX-IA-OWNER-002] platform-tenant 仍是成员、主体、上下文和登录期发现的唯一 Owner（multi-tenant §0.5、§9.2）。身份协议面通过它的 L2A 契约完成上下文发现与选择，MUST NOT 直接读写租户表。

[BRX-IA-OWNER-003] 平台授权（`sys_platform_admin`）仍按 super-admin 定义。身份协议面只读取"是否有有效平台授权"的结果，MUST NOT 修改它。

## 4. 客户端

[BRX-IA-CLIENT-001] 平台客户端分三类，各自独立注册，audience 和上下文类型互不相同：

| 客户端 | 类型 | 上下文 | Token audience |
|---|---|---|---|
| `platform-console` | 机密（BFF） | platform | 平台 audience |
| `tenant-console` | 机密（BFF） | actor | `brix-actor` |
| 品牌应用（每个租户或品牌一个） | Web 为机密（BFF）；原生为公共 + PKCE | subject | `brix-subject` |

[BRX-IA-CLIENT-002] 客户端策略 MUST 声明：允许的登录方式、认证强度要求、会话时长上限、是否允许受信设备、上下文类型。redirect URI MUST 精确登记（根 `BRX-RS-SECURITY-003`）。

[BRX-IA-CLIENT-003] 品牌应用客户端绑定唯一租户。终端用户所属的租户由客户端注册决定，MUST NOT 由 Header、子域名或请求参数决定（multi-tenant T-13）。

## 5. 登录流程

[BRX-IA-FLOW-001] 托管登录采用"先识别账号"：先输入邮箱或手机号，再按该身份已登记的凭证和客户端策略决定下一步（passkey、密码、第三方、企业 SSO）。账号不存在时，流程、响应内容和响应时间 MUST 与账号存在时不可区分。

[BRX-IA-FLOW-002] 认证完成后，按客户端的上下文类型选择上下文：

- actor：调用登录期发现（multi-tenant `discoverActor`）。0 个上下文时显示"尚未加入任何租户"；1 个时自动选中；2 个及以上时显示租户选择页。选择使用一次性 selection ticket，multi-tenant §9.3 的 ticket 硬约束全部适用；
- subject：只发现客户端所绑定租户的主体，不显示选择页；
- platform：校验有效的平台授权，不涉及租户。

[BRX-IA-FLOW-003] 授权码 MUST 绑定所选上下文（`cid`）、客户端、PKCE challenge 和 nonce。Token 由 token 端点签发给 BFF（或原生 App），MUST NOT 由登录页直接返回给浏览器。

[BRX-IA-FLOW-004] 员工切换租户时，由控制台经 BFF 发起重新授权（`prompt=none` + 目标上下文），只能切换到同一身份的其他 Actor 上下文（multi-tenant T-26）。切换后 BFF 替换会话中的 Token，前端清空缓存和页面状态。

[BRX-IA-FLOW-005] 平台登录与员工、终端用户登录使用同一认证服务，但客户端、托管页品牌和 Token audience 互相隔离。平台登录页 MUST NOT 链接或自动跳转到员工登录，反之亦然。

[BRX-IA-FLOW-006] 不存在"接收凭证并直接返回 Token"的接口；浏览器客户端只使用授权码 + PKCE（根 `BRX-RS-SECURITY-002`）。

## 6. 凭证

[BRX-IA-CRED-001] 密码：哈希算法和参数来自安全 Profile。密码单独作为认证因素时最短 15 位，作为多因素的一部分时最短 8 位；MUST 检查已泄露密码库；MUST NOT 强制定期更换密码或规定字符组合。

[BRX-IA-CRED-002] Passkey：使用 WebAuthn，要求用户验证（`userVerification=required`）和可发现凭证。每个身份 MAY 登记多把；服务端只保存公钥和元数据；同时支持本机认证和跨设备（扫码）认证。特权账号 SHOULD 至少登记两把。

[BRX-IA-CRED-003] TOTP：遵循 RFC 6238，密钥由 platform-identity 加密保存；对特权账号只作恢复用途。

[BRX-IA-CRED-004] 恢复码：一次性使用，只存哈希，生成时只展示一次。

[BRX-IA-CRED-005] 短信/邮件验证码：只用于终端用户登录、账号找回和非特权再验证。MUST 按号码、来源、国家限流，防止短信轰炸和计费欺诈。

[BRX-IA-CRED-006] 第三方登录（OIDC/OAuth 联合登录）通过统一的通用层接入：

1. 通用层负责提供方注册、发起授权（授权码 + PKCE，带 state 和 nonce）、回调校验（签名、issuer、audience、nonce、有效期），并把提供方返回的用户信息映射为统一的外部身份（提供方 ID、提供方用户 ID、已验证的邮箱或手机号）。标准 OIDC 提供方只需配置；非标准的 OAuth2 提供方（如微信）实现同一个提供方 SPI 接入；
2. 外部身份与 Brix 身份的关联由 platform-identity 保存，"提供方 + 提供方用户 ID"唯一。只有提供方声明邮箱或手机号已验证时，才自动找出候选身份；关联到已有身份前 MUST 先用该身份的现有凭证确认；
3. 第三方登录只算第一因素（`brix:aal1`）。客户端要求 `brix:aal2` 时 MUST 再完成 Brix 的第二因素；`platform-console` MUST NOT 启用第三方登录；
4. 每个客户端是否启用某个提供方由客户端策略决定。首批只接入 Google，默认只对终端用户客户端启用；
5. 提供方的 client secret 经 `SecretCapability` 管理，MUST NOT 进入普通配置或前端；
6. 第三方登录属于 Open Core；按租户配置的企业 SSO 属于商业版。

[BRX-IA-CRED-007] 按租户配置的企业 SSO（SAML/OIDC）属于商业版，由后续 RFC 定义。

## 7. 认证强度、MFA 与再验证

[BRX-IA-MFA-001] 认证强度分为三级，写入 `acr`：

| `acr` | 含义 | 满足方式 |
|---|---|---|
| `brix:aal1` | 单因素 | 密码、第三方登录、短信/邮件验证码 |
| `brix:aal2` | 双因素 | passkey；密码 + TOTP；密码 + 受信设备（仅非特权账号，`amr` 记为 `pwd` 与 `tdev`） |
| `brix:aal2-phr` | 防钓鱼双因素 | passkey 或硬件安全密钥 |

[BRX-IA-MFA-002] 各类用户的最低要求（具体数值来自安全 Profile，初始值见 §12）：

- 平台超管：每次认证都要达到 `brix:aal2-phr`；不允许受信设备；"密码 + TOTP"只用于恢复，MUST NOT 作为日常登录方式；
- 租户员工（OWNER、ADMIN、MEMBER）：一律强制 `brix:aal2`；允许受信设备，最长 30 天。租户的 `mfa_policy` 只能在此基础上加强（例如要求防钓鱼因子、缩短受信设备期限），MUST NOT 关闭 MFA；
- 终端用户：`brix:aal1`；访问客户端策略中标记为敏感的数据时，再验证到 `brix:aal2`。

[BRX-IA-MFA-003] 受信设备：完成第二因素后才能登记。设备凭据是随机值，只存哈希，绑定身份和客户端类别；它只免除第二因素。修改密码、变更 MFA、重置凭证或管理员撤销时，该身份的受信设备 MUST 全部失效。用户可以在"设备管理"中查看和移除。

[BRX-IA-MFA-004] 敏感操作再验证：Endpoint 按根 `BRX-RS-SECURITY-015` 声明 `acr`/`max_age`。以下操作 MUST 声明再验证：平台超管的新增/撤销超管、修改平台安全设置、跨租户操作；租户内的成员权限变更、数据导出、安全策略变更。

## 8. 会话与 Token

[BRX-IA-SESSION-001] Access Token 有效期不超过 15 分钟。Refresh Token 每次使用都轮换并检测重放；发现重放时撤销整个 Family（与 multi-tenant §9.3 Phase 5 一致）。

[BRX-IA-SESSION-002] 会话分三层：认证服务的登录会话（SSO）、BFF 会话（每个客户端一个）、Token。闲置超时和绝对时长按客户端策略设定（§12）。

[BRX-IA-SESSION-003] Token 在 multi-tenant §8 和 super-admin §7 的 claims 基础上，增加 `acr`、`amr`、`auth_time`、`sid`。Identity Token（`aud=brix-identity`）只在认证服务内部使用，MUST NOT 交给浏览器应用。

[BRX-IA-SESSION-004] 用户 MUST 能查看自己的活跃会话和受信设备，并逐个撤销。撤销 MUST 在一个 Access Token 有效期内生效（通过 `sid` 与 `mver`/`pver` 校验实现）。

[BRX-IA-SESSION-005] 注销 MUST 同时撤销 BFF 会话、Refresh Token 和认证服务的登录会话（RP-Initiated Logout）。

[BRX-IA-SESSION-006] 签名密钥、算法、Token 有效期、会话时长等参数来自可版本化的安全 Profile，本文只规定上限与语义。

## 9. 首次设置、邀请与恢复

[BRX-IA-ONBOARD-001] 平台超管首次设置（super-admin §15）：setup 链接打开托管设置页 → 登记 passkey（必须）→ 生成恢复码 → 可选设置密码和 TOTP。Bootstrap 两阶段模型不变。

[BRX-IA-ONBOARD-002] FIRST_OWNER 和后续成员邀请：邀请或设置链接打开托管设置页（不在 `/platform/**` 下）→ 新身份设置凭证（passkey，或密码 + TOTP）→ 接受邀请仍走租户 Owner 的接受接口（multi-tenant §5.7）→ 跳转到租户员工控制台。

[BRX-IA-ONBOARD-003] setup、邀请、恢复链接中的 token 只在完成流程所需的最短时间内存在于内存；页面设置 `Referrer-Policy: no-referrer`；token MUST NOT 进入日志、审计、指标或浏览器持久化存储。

[BRX-IA-ONBOARD-004] 平台 Bootstrap 的开会话在身份协议面完成（super-admin §15）：`POST /bff/bootstrap/session` 收 setup code，BFF 经身份 Owner 的 L2A 契约核对 setup code、签发 BOOTSTRAP_SETUP 会话；令牌 MUST 只保存在加密的服务端 BFF 会话里，浏览器只拿到会话 Cookie 和 CSRF 令牌，回答里只有有效期和 CSRF 令牌。这个 BFF 会话只用于 super-admin 的 `create-first-admin`，与令牌同时到期；它不是登录会话，不签发 Access/Refresh Token。开会话 MUST 按来源限流（根 SECURITY-011），MUST 只收同源的 JSON 请求，MUST NOT 保存或重放答案。

[BRX-IA-RECOVERY-001] 平台超管：使用恢复码，或由另一位超管协助重置（需要再验证，并写平台审计）。MUST NOT 提供邮件自助重置。

[BRX-IA-RECOVERY-002] 租户员工：使用恢复码；OWNER/ADMIN 可以重置成员的 MFA 因子（需要再验证，并写租户审计）；OWNER 本人的重置走平台受理流程。

[BRX-IA-RECOVERY-003] 终端用户：通过已验证的手机号或邮箱找回，加风控；更换手机号、邮箱等敏感变更 MAY 设置冷静期。

## 10. 防滥用与审计

[BRX-IA-ABUSE-001] 按根 `BRX-RS-SECURITY-014` 实施："账号 + 来源"限流、渐进延迟、多次失败后人机验证。临时锁定只作用于发生失败的客户端类别和凭证，到期自动解除（时长来自安全 Profile），并通知身份持有人。

[BRX-IA-ABUSE-002] 新设备登录、凭证变更、MFA 重置、会话撤销 MUST 通知身份持有人。

[BRX-IA-AUDIT-001] 认证事件 MUST 写审计，包括：登录成功/失败、因子登记/移除、再验证、恢复、受信设备变更、会话撤销、锁定。平台客户端的事件和跨租户事件写平台审计；员工在租户内的事件写租户审计（multi-tenant T-25）。审计 MUST NOT 记录密码、验证码、恢复码、凭证私密材料或完整 Token。

## 11. 红线

| ID | 唯一含义 | 最低证明门禁 | 失败处置 |
|---|---|---|---|
| IA-1 | 所有用户登录只经托管登录 + 授权码 + PKCE；不存在"接收凭证并返回 Token"的接口 | 端点清单扫描 + 安全集成测试 | CI 阻断 |
| IA-2 | 凭证只在托管登录页输入；控制台和业务前端不出现凭证输入 | 前端制品扫描 + 页面清单 | CI 阻断 |
| IA-3 | 特权访问只接受 `brix:aal2-phr` | 认证集成测试 + Token 负例测试 | CI/安全阻断 |
| IA-4 | 受信设备不得免除第一因素或特权访问的认证要求 | 认证负例测试 | CI 阻断 |
| IA-5 | 失败处置不得形成跨入口的全局锁定 | 锁定负例测试 | CI 阻断 |
| IA-6 | 三类客户端的 Token 不能互用（audience 校验） | 跨客户端负例测试 | CI 阻断 |
| IA-7 | 无法通过登录、找回接口的响应内容或响应时间判断账号是否存在 | 账号枚举负例测试 | 安全阻断 |

[BRX-IA-GOV-001] 专项红线 MUST NOT 复用或放宽根蓝图的 A/S 红线（根 `BRX-RS-GOVERNANCE-011`）；IA-1、IA-2 是根 S-20 与 `BRX-RS-UI-018` 在本专项的具体化。

## 12. 默认策略（安全 Profile 初始值）

下表是安全 Profile 的初始值。"上限"类数值（Access Token 有效期、受信设备期限）为规范上限，Profile 只能收紧；其余为默认值，Profile 可在本文语义内调整。

| | 平台超管 | 租户 OWNER/ADMIN | 租户 MEMBER | 终端用户 |
|---|---|---|---|---|
| 主要登录方式 | passkey（本机或跨设备扫码）、硬件安全密钥 | passkey，或密码 + TOTP | 同左 | 手机号验证码、第三方（首批 Google）、邮箱 + 密码、passkey |
| 认证强度 | 每次 `brix:aal2-phr` | `brix:aal2` | `brix:aal2`（租户可加强） | `brix:aal1`；敏感数据 `brix:aal2` |
| 受信设备 | 不允许 | 最长 30 天 | 最长 30 天 | 不适用（长会话） |
| 闲置超时 | 15–30 分钟 | 1–2 小时 | 1–2 小时 | App 不设；Web 按品牌配置 |
| 绝对时长 | 8–12 小时 | 不超过 30 天（经 Refresh） | 不超过 30 天 | 数周至数月 |
| 再验证 `max_age` | 5 分钟 | 15 分钟 | 15 分钟 | 按操作设定 |
| 失败处置 | 限流 + 人机验证；该入口临时锁定 15 分钟 | 同左 | 同左 | 限流 + 人机验证 |
| 入口 | 独立域名，可加 IP 白名单，每次登录发告警 | 员工控制台域名 | 同左 | 品牌应用 |

## 13. 实施路线与验收

| 阶段 | 内容 | 验收要点 |
|---|---|---|
| 前置 | Spring Boot 4.1；Dispatcher 执行权限码；租户最小 RBAC（另起 RFC） | 全量测试通过；未授权调用在 Handler 前被拒绝 |
| M1 认证骨架 | 身份提供方 Adapter、托管登录（先识别账号、密码 + TOTP、选租户、setup）、BFF 会话；员工登录 → 选租户 → 进入控制台；平台控制台迁入 | IA-1、IA-2、IA-6 门禁；浏览器无 Token（S-20）；端到端流程 |
| M2 passkey 与策略 | passkey、恢复码、受信设备、敏感操作再验证、限流取代锁定、会话与设备管理；受邀人页面迁入托管登录 | IA-3、IA-4、IA-5、IA-7 门禁；S-19 |
