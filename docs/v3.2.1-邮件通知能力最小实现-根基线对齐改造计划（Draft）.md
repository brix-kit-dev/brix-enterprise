## 1. Root Cause 与对齐目标

v3.2.0 将 `platform-admin` 标为 L2C 业务并让其直接消费 `NotificationCapability`，同时把 `platform-notification` 标为 L2C。该调用链违反根蓝图冻结的 `L2B platform-operational → OperationalContext → internal contract → Data Owner local transaction`，也会让平台运维模块承担 Token 与通知事务编排。

v3.2.1 固定为：

```text
L3 Host
  -> Runtime Shell 唯一装配
      -> L2B platform-admin platform-operational
          -> OperationalContext.requireInternalContract(...)
              -> Data Owner internal contract provider
                  -> Data Owner local transaction
                      -> owner-scoped NotificationCapability
                          -> L2B platform-notification policy/provider
                              -> EmailDeliveryAdapter
                                  -> L2C infra-adapter-email-smtp
```

`platform-admin` 不取得 `NotificationCapability`、模板服务、SMTP Adapter、Repository、Mapper 或其他 Owner Service。Token hash、业务状态、通知调用和失败回滚由对应 Data Owner 在本地事务内编排。

---

## 2. 模块与分层

| 模块 | 分层 | 最小职责 | 禁止事项 |
|---|---|---|---|
| `runtime-sdk-api` | L2A Capability Contract | `NotificationCapability`、`NotificationRequest`、稳定错误语义 | Spring、SMTP、模板实现、业务 Entity |
| `platform-notification` | L2B Platform Capability | 请求校验、Locale 决策、模板解析、严格渲染、投递策略和指标 | 依赖 platform-admin/platform-tenant 内部实现 |
| `infra-adapter-email-smtp` | L2C Adapter | SMTP 配置校验、单次纯文本投递、Provider 异常映射 | 业务事务、Token、模板选择 |
| 身份/租户 Data Owner | L2B Owner | 本地事务、Token hash、templateKey/变量、调用 owner-scoped capability | SMTP/JavaMail、跨 Owner Repository |
| `platform-admin` | L2B platform-operational | 经 OperationalContext 调用 allowlist internal contract | 直接注入 Capability 或业务实现 |
| Host | L3 Composition | 依赖声明、profile 和配置装配 | 通知业务、模板、Fallback |

Service 仍只是部署聚合单元，不承载上述实现。

## 3. Capability Contract

`NotificationCapability` 继续使用根目录已登记的 Capability ID；本计划不新增 Capability。请求最小字段为：

```java
public record NotificationRequest(
        Long tenantId,
        String recipientEmail,
        String templateKey,
        String locale,
        Map<String, String> variables
) {}
```

约束：

1. `tenantId=null` 只表示平台级通知；租户邀请必须使用目标 tenant ID。
2. 构造器必须防御性复制变量并校验长度、控制字符、模板 Key、Locale 和变量名。
3. `toString()`、异常、日志、审计、Trace 和指标不得输出完整邮箱、变量值、正文、raw token 或完整安全 URL。
4. `send(NotificationRequest)` 成功返回 `void`，失败抛稳定的 `BrixException` 子类；不暴露 Provider 异常。
5. 兼容期可保留既有 `sendSetupLink(...)`，但只允许在 Capability provider 内部桥接，任何新业务调用不得继续依赖该方法。
6. Locale 由 Data Owner 的已验证业务上下文显式传入；没有合法值时使用平台配置默认值。不得新增或调用未进入根 Catalog 的 `TenantConfigCapability`。

稳定错误码：

| 错误码 | 语义 |
|---|---|
| `notification.request.invalid` | 请求字段、变量或 Locale 非法 |
| `notification.template.not_found` | 目标模板缺失 |
| `notification.template.invalid` | 模板结构或变量声明非法 |
| `notification.delivery.unavailable` | 当前无可用投递 Provider |
| `notification.delivery.failed` | Provider 拒绝或投递调用失败 |

所有公开类型和方法必须提供英文 Javadoc；异常链保留内部 cause，但对外映射不得泄露 Provider、地址或正文。

## 4. 模板与安全链接

本期必须随制品提供以下六个 UTF-8 纯文本资源：

| templateKey | Locale | 必需变量 |
|---|---|---|
| `platform.admin.setup.initial` | `zh-CN`、`en-US` | `setupUrl` |
| `platform.admin.setup.password-reset` | `zh-CN`、`en-US` | `setupUrl` |
| `tenant.owner.invitation.initial` | `zh-CN`、`en-US` | `inviteUrl` |

模板只支持声明式字面量占位符。缺失、多余、重复或渲染后残留变量必须失败；不允许表达式、脚本、include、条件、循环、HTML、附件或远程模板。

完整安全 URL 只能在 Data Owner 生成 raw token 后的短生命周期内存与 Notification provider 调用栈中存在。任何 profile 的 HTTP 响应、日志、审计、Trace、指标、前端状态和持久化记录均不得暴露 raw token、完整 URL、正文或 variables。前端页面使用 `Referrer-Policy: no-referrer`，安全 Token 只保存在当前内存状态，不进入 URL 查询串、localStorage 或 sessionStorage。

## 5. 装配与 Provider

1. Runtime descriptor/profile 声明 `NotificationCapability` 的 required/optional 关系，Runtime Shell 完成唯一绑定。
2. `platform-notification` 不通过 `@ConditionalOnMissingBean(NotificationCapability.class)` 建立隐藏默认实现，不通过 ComponentScan 发现业务入口。
3. SMTP Adapter 只能实现 `EmailDeliveryAdapter`；选择 provider、超时和 TLS 参数属于 profile/config，禁止 Host 代码硬编码。
4. required Notification Capability 或 required Email Adapter 缺失时，启动必须在 B3 前失败；禁止 Logging/Fake/No-op fallback。
5. 开发环境使用 Mailpit 或真实虚拟 SMTP；同样不得在日志输出安全链接。

---

## 6. 事务、审计、事件与 Outbox

本期沿用同步、单次尝试、fail-closed：

1. Data Owner 开启本地事务，创建/轮换 token，只持久化 hash。
2. Data Owner 调用 Notification Capability。
3. SMTP 调用失败则抛异常并回滚本地事务。
4. SMTP accepted 后数据库提交失败的残余窗口被明确接受；重发必须生成新 token 并作废旧 token。
5. 本期不新增通知表、自动重试、队列、事件或 Outbox，不伪造投递成功状态。
6. 若未来要求可靠异步投递，必须单独立项并使用根蓝图统一 Event Envelope 与平台 canonical Outbox/Relay；不得定义通知私有 Envelope。
7. 审计只记录操作者、动作、结果、脱敏目标标识和 correlation 信息，不记录邮箱明文、Token、URL、模板正文或变量。

---

## 7. 前端边界

本计划不新增独立通知管理页面。setup、reset、FIRST_OWNER 既有用户操作必须继续通过：

```text
Page -> Hook/ViewModel -> Repository -> HttpCapability
```

页面必须具备 Guard、权限、加载、错误、空状态、提交防重和表单校验，并通过 BrixUI/useUI 展示稳定错误文案。前端只显示“请求已受理/发送失败”等业务状态，不展示或持久化安全链接。不得直接 `fetch`/`axios`，不得启动第二 Runtime 或要求多个插件开发服务器同时运行。

## 8. 最小施工顺序

### Phase N0：契约与架构门禁

1. 三个专项重基线完成 ACTIVE 切换且 `rebaseRequired=false`。
2. 固定 Capability ID、请求字段、错误码、模板 Key、owner/transaction 边界。
3. 增加 ArchUnit/依赖守卫，阻止 platform-admin 直连 Capability、Owner 实现或 SMTP。

### Phase N1：Contract 与 L2B Provider

1. 先修改 `runtime-sdk-api` contract/api。
2. 再实现 `platform-notification` app/domain/support。
3. 提供六个模板资源和严格渲染测试。

### Phase N2：L2C SMTP Adapter 与 Runtime 装配

1. 实现 EmailDeliveryAdapter、TLS/超时/配置校验。
2. 通过 descriptor/profile 完成 Runtime binding。
3. 验证 required provider 缺失在 B3 前 fail-stop。

### Phase N3：Data Owner 迁移与前端闭环

1. 身份/租户 Owner 在本地事务内迁移 setup/reset/FIRST_OWNER。
2. 移除 platform-admin 对 NotificationCapability、Repository 和 SMTP 的直接依赖。
3. 同步补齐 Page/Hook/Repository/Route/Guard 状态与安全测试。

当前 Phase 0 未验收，不得进入 Phase N0 或修改运行时代码。

---

## 9. 验收

1. 根基线校验、文档治理测试、ArchUnit、模块单测、集成测试和 executed-test-count guard 全部通过。
2. Host 仍极薄；Service 无业务实现；插件只依赖 Capability Contract。
3. `platform-admin → OperationalContext → internal contract → Data Owner` 是唯一业务链。
4. SMTP Adapter 可替换且业务代码不变；缺失 required provider 无 fallback。
5. 六个模板、两种 Locale 均通过严格变量测试。
6. API、异常、日志、审计、Trace、指标和前端存储 DLP 测试无敏感泄露。
7. SMTP failure 回滚、accepted/commit 残余窗口、重发 token 轮换均有真实测试。
8. 不新增 Flyway、事件、Outbox 或 Timeline；若实现范围变化，必须先重新评审本计划。
