## 0.0 v2.0 升级摘要（相对 v1.1 的强制变更）

| # | v1.1 决策 | v2.0 决策（强制） | 影响面 |
|---|----------|------------------|-----|
| Δ1 | 超管与租户共用 `/api/auth/login` + 前端 `/login` | **超管入口 `/platform/login` → `/api/platform/auth/login`；普通/租户 = `/login` → `/api/auth/login`。前后端 URL、Token、路由守卫严格隔离** | 后端拆控制器；前端两套独立守卫 |
| Δ2 | 新增超管返回明文 `tempPassword`（一次） | **禁止生成默认密码**；新增超管 = 创建 `Identity(PENDING_SETUP)` + 一次性 `setup_token` → 用户在 `/platform/setup` 设密码 + 绑定 Google Authenticator TOTP 才能 `ACTIVE` | 后端去 tempPassword；前端去展示；E2E 改断言 |
| Δ3 | MFA "完整流程" 不做 | **Google Authenticator 兼容 TOTP 进入 MVP**（首次绑定 + 每次登录强制） | 新增 `TotpCapability`、`mfa_secret_encrypted` 字段 |
| Δ4 | `sys_identity.status` 复用 `MemberStatus(PENDING/ACTIVE/...)` | **独立 `IdentityStatus`：`PENDING_SETUP / ACTIVE / LOCKED / DISABLED`**；`PENDING_SETUP` 仅允许 `/platform/setup` 路径 | Identity 实体新增独立 status + Flyway 迁移 |
| Δ5 | `sys_platform_admin.status = ACTIVE / DISABLED` | **`ACTIVE / REVOKED`**：REVOKED 后不再签发 PLATFORM Token，但保留该 identity 的租户身份 | 字段语义重命名 + 登录链断言 |
| Δ6 | `SuperAdminBootstrapRunner` 直接用 ENV 密码创建"正式"超管 | **Bootstrap Admin ≠ 正式超管**：仅在不存在任何 ACTIVE 正式超管时生效，能力仅限创建首位正式超管 + 查看 bootstrap 状态；首位正式超管 ACTIVE 后 Bootstrap 永久失效，重启不再重建 | Runner 改产引导态 + 一次性 token；禁止访问 admins/tenants/audit |
| Δ7 | `platform:bypass` 写进 Token 下发前端 | **`platform:bypass` 不下发前端**，仅供后端 `PermissionAspect` / `JwtIssuerCapability` 内部识别 | JWT permissions 数组过滤；前端 UI 控制只用 `platform:*` 具体码 |
| Δ8 | `LoginResponse.platformAdminMode` 与 `/api/auth/login` 共用 | **删除** `platformAdminMode` 字段；普通 `/login` 永远不返回 PLATFORM Token；同一 identity 即使是超管也必须走 `/platform/login` | enterprise app-identity DTO 清理；E2E 改写 |
| Δ9 | 邮件不强制 | 邮件**仅**用于 setup link / 密码重置 link / 安全通知；**禁止**邮件 OTP 作为生产 MFA | NotificationCapability 必须提供 setup link 发送实现 |

> **不兼容点**：新增超管 API 响应不再含 `tempPassword`，也不返回 `setupUrl` / `setup_token` 明文。响应固定为 `{id, identityId, setupLinkSent:true}`；setup link 唯一发送路径为 `NotificationCapability`（邮件）。所有依赖 `tempPassword` 的前端弹窗、E2E 断言、文档示例必须改为展示"setup link 已发送。"；dev-only 例外见 §16.12。

## 0. TL;DR（执行摘要）

| 维度 | 决策 |
|------|------|
| **能力定位** | Super Admin 是 `platform-commons` 下唯一的 **L2B Platform Operational Module**，`moduleKind=platform-operational`；不是 L2C Adapter、Host 业务代码或 enterprise-solutions 插件 |
| **代码位置** | 后端：`platform-commons/server/platform-admin`（新建）+ 已有 `platform-tenant`（实体） + 已有 `platform-auth`（登录与权限） |
| **声明与发现** | 固定路径 `META-INF/brix/platform-operational.yaml` 是声明性 SSoT；artifact 通过 `ServiceLoader<PlatformOperationalModule>` 发布且只发布一个 provider |
| **入口发布** | `/api/platform/**` 仅由 L2B HTTP Dispatcher 通过同一 Host 入口快照发布；禁止 Spring Controller、Servlet/Filter 或第二套路由表自动发布 |
| **跨 Owner 协作** | 只通过 `OperationalContext` 调用 descriptor 已声明且 privilege allowlist 批准的版本化内部契约；禁止 `AdminCapability` / `PlatformAdminCapability`、Spring Bean/Repository/Service 直注入 |
| **登录入口** | **严格隔离**：超管 = `/platform/login` → `/api/platform/auth/login`；普通/租户 = `/login` → `/api/auth/login`。Token 互不通用；前端两套守卫互不复用路由 |
| **首次激活** | **禁止默认密码**；新建超管 = `Identity(PENDING_SETUP)` + 一次性 `setup_token` → 用户在 `/platform/setup` 设密码 + 绑定 Google Authenticator TOTP → 自动转 `ACTIVE` |
| **MFA（MVP）** | **Google Authenticator / 任意兼容 TOTP App 强制启用**；不开发自研认证器；邮件 OTP 仅用于安全通知，禁止作为生产 MFA |
| **架构红线** | 业务插件（enterprise-solutions/* / plugins/*）**禁止**依赖 `platform-admin`；超管能力**禁止**反向依赖任何业务插件 |
| **权限模型** | `RoleCode.PLATFORM_SUPER_ADMIN` + 细粒度 `PermissionCode.PLATFORM_*` 常量；接口放行**只校验 Permission**，不校验角色名字符串；`platform:bypass` **不下发前端** |
| **身份模型** | `sys_identity.status ∈ {PENDING_SETUP, ACTIVE, LOCKED, DISABLED}`；`sys_platform_admin.status ∈ {ACTIVE, REVOKED}`；超管 Token `scope=PLATFORM`，**禁止**含 `tenant_id` |
| **Bootstrap** | Bootstrap Admin 仅作引导身份：系统无任何 ACTIVE 正式超管时生效，只能访问 `/platform/setup` 创建第一位正式超管；首位正式超管激活后 Bootstrap 永久失效，重启不再重建 |
| **MVP 范围** | 平台登录（密码+TOTP）、setup 链接初始化、超管列表/新增/禁用(REVOKE)/重置密码（生成 setup link）/改自己密码、租户列表与状态变更、审计日志 |
| **不做** | 自定义角色编辑、自研认证器、计费/配额、删除超管、短信通知、Token 刷新机制 |

### 0.1 v3.0.10 重基线结论

1. `platform-admin` 实现 `PlatformOperationalModule`，不是 `BrixPlugin`；`configure(OperationalBootstrapContext)` 只登记 descriptor 已声明的 Handler/Task Factory，`onStart` 不得登记入口或执行业务 Handler。
2. 模块严格经过 O0-O8 局部管线并受 Host B0-B3 全局屏障约束；B3/P8/O8 原子提交前所有 Endpoint/Task 保持 `UNPUBLISHED`。
3. 需要 `/api/platform/**` 的 Production Composition MUST 将 `platform-admin` 显式列为 required operational module；Resolve/Start 失败阻断 Host 启动与 Ready。
4. 平台超管无默认业务数据访问权。身份、租户、审计等 Data Owner 通过 `internalContracts.provides` 提供窄契约；`platform-admin` 通过 descriptor 的 `internalContracts.requires` 和 privilege allowlist 获得最小权限。
5. 内部契约调用不得传播 `platform-admin` Handler 的事务、连接、`EntityManager` 或 Session；L2B 代理挂起调用方事务，由 Data Owner 在自身 context 中提交独立本地事务。
6. 本次重基线只更新架构约束，未证明实现合规；实施状态保持 `not-assessed`。

| # | 问题 | 影响 | 修正方案 |
|---|------|------|---------|
| C-1 | `PlatformAdminRole`（platform-tenant）依赖 `PlatformPermissions`（platform-auth）— Layer 2C 内部模块横向依赖 | 难以单独发布；语义混淆（"角色"逻辑落在租户模块） | 把 `PlatformAdminRole` + `PlatformPermissions` + `RoleCode` **下沉到 `platform-auth-api`**（纯接口/常量包，无 Spring 依赖） |

### 1.3 与运行壳架构红线对照

#### 1.3a 平台审计内部契约归属

| 分层 | 内容 | 代码库位置 |
|------|------|----------|
| **Data Owner** | 平台审计模块拥有 `sys_platform_audit_log`、Schema、迁移、写规则与生命周期，并通过 descriptor `internalContracts.provides` 声明版本化窄契约 | `brix/packages/@brix/platform-commons/packages/server/` |
| **L2B Registry internal namespace** | 根据 provider descriptor 建立确定性索引，执行 privilege allowlist、module identity、Trace、deadline 与事务隔离 | Runtime 内部，不进入插件面 L2A |
| **调用方** | `platform-admin` 在 `platform-operational.yaml` 声明 `internalContracts.requires`，仅通过 `OperationalContext` 获取审计内部契约 | `brix/packages/@brix/platform-commons/packages/server/platform-admin` |

> **红线**：`platform-admin` 禁止直接 import/注入 `AuditServiceImpl`、`AuditLogRepository` 或任意 Spring Bean，也不得定义 `AdminCapability`、`PlatformAdminCapability`、通用对象查找器或第二套 Registry。所有审计写入只能经已声明、已授权的内部契约；L2B 代理挂起调用方事务，由审计 Data Owner 在独立本地事务中提交。

| 蓝图红线 | 本设计是否遵守 |
|---------|-------------|
| 约束 1：平台运维边界 | `platform-admin` 是 L2B `platform-operational`，不向插件暴露超管 Capability |
| 约束 2：插件只依赖 Capability Contract | ✅ enterprise-solutions/* 不感知 `platform-admin` 存在 |
| 约束 3：Host 能力等价 | Standalone / Embedded Host 使用相同 descriptor、O0-O8、Dispatcher、安全链和错误语义；fatal 处置按 Host Profile 区分 |
| 约束 4：插件间事件解耦 | ✅ `TenantStatusChangedEvent` 走 EventBusCapability，业务插件按需订阅 |
| 约束 5：运行壳复杂度对插件不可见 | ✅ 业务插件无任何超管相关代码 |
| 约束 6：Host 极薄 | Host 仅静态打包并在 Composition 选择 `platform-admin`；不得包含超管业务逻辑或 Controller |
| 约束 7：前后端完全分离 | ✅ `platform-admin-web` 走 View → Hook → Repository → HttpCapability |
| 约束 8：前端运行时唯一真相源 | ✅ `platform-admin-web` 只 peerDependency `@brix-sdk/shared-runtime-web` |
| 约束 9：BrixUI 统一治理 | ✅ 所有页面通过 `useUI()` |

## 2. 模块边界与依赖图

```text
L4 Composition
  └─ operationalModules.required: platform-admin
            │ static assembly
L3 Host ────┴── packages L2B Runtime + platform-admin + selected L2C Adapters
                         │
L2B platform-admin (moduleKind=platform-operational)
  ├─ META-INF/brix/platform-operational.yaml
  ├─ ServiceLoader<PlatformOperationalModule>
  ├─ configure(OperationalBootstrapContext): Handler/Task Factory only
  ├─ /api/platform/** via the unique L2B HTTP Dispatcher
  └─ OperationalContext.requireInternalContract(...)
                         │ descriptor requires + privilege allowlist
                         ▼
L2B Registry internal namespace
  └─ versioned internal contract providers owned by platform-auth,
     platform-tenant, platform-audit and notification Data Owners

L1 business plugins ──X── platform-admin / operational SPI / internal contracts
L2C adapters         ──X── platform-admin business types
```

`platform-admin` 的 Handler Factory 仅在 O1 依赖解析、O2 `configure()`、O3 双向一致性校验和 Host B2 屏障全部成功后于 O4 创建。所有 Endpoint、Task 与受管资源在 B3/O8 原子提交前保持不可准入；启动失败按依赖拓扑逆序清理。

```

  ├─ pages/         登录、列表、详情、审计日志、租户管理

  ├─ types/         与后端 platform-admin DTO 契约一致
  └─ peerDependencies: @brix-sdk/shared-runtime-web
```

```sql
UPDATE sys_platform_admin SET status = 'REVOKED' WHERE status = 'DISABLED';
```

### 4.1 `platform:bypass` 使用边界

`bypass` 的语义是「此 Token 已经过平台最高级别身份验证，权限框架内部可跳过细粒度逐条检查」，**不等于**「该用户有权做任意业务操作」。

| 场景 | 是否允许 |
|------|----------|
| `PermissionAspect` 内部读取，检测当前用户是否持有 bypass 从而免逐权限校验 | ✅ |
| `JwtIssuerCapability` 为 `SUPER_ADMIN` Token 签发时写入该权限码 | ✅ |
| 单元测试构造 mock JWT 携带此码以验证 bypass 逻辑 | ✅ |
| `enterprise-solutions/*` 任意插件 `hasPermission(PermissionCode.BYPASS)` | ❌ R-3a |
| 任意接口使用 `@RequirePermission(PermissionCode.BYPASS)` 做门控 | ❌ R-3b |
| 前端 `permissions.includes('platform:bypass')` 控制页面元素可见性 | ❌ R-3c |

> 前端 UI 控制**必须**依赖具体 `platform:*` 权限码（如 `PLATFORM_ADMIN_CREATE`）；持有 bypass 不代表 UI 展示全部功能入口。

- 全部 Endpoint 必须在 `platform-operational.yaml` 的 `endpoints.provides` 声明，并由唯一 L2B HTTP Dispatcher 通过不可变 Host 入口快照发布；`/api/platform/**` 是 `platform-operational` 保留命名空间
- Handler 只消费 Runtime 已验证的 actor/scope/access/Trace/deadline/idempotency context；权限策略引用必须可解析，不得依赖 Spring Controller 注解、Filter 或 Handler 内临时放行
- DTO/Schema 由版本化契约生成并与 descriptor、Handler Factory 双向一致；不得在代码注解中维护第二份路由或策略声明
- 所有响应不返回 `passwordHash`、`mfaSecret` 等敏感字段（DTO 显式 whitelist）
- 认证、tenant/scope、授权、Schema、deadline、幂等、审计与稳定错误映射均由 Dispatcher 固定拦截链 fail-closed 执行

## 7. 登录 Token 设计

```jsonc
// JWT Payload (PLATFORM scope) — v2.0
{
  "sub": "<identity_id>",
  "scope": "PLATFORM",             // ★ 与租户 Token 区分；身份判定**只**依赖此 claim
  "platform_role": "PLATFORM_SUPER_ADMIN", // 只有两个可能值："PLATFORM_SUPER_ADMIN" | "BOOTSTRAP"
  "permissions": [                 // RBAC 解析后下放，前端 UI 控制用
    // ★ v2.0：JwtIssuerCapability 签发时必须**剔除** "platform:bypass"，不写入此数组
    "platform:admin:create",
    "platform:admin:read"
  ],
  "mfa": "TOTP",                   // v2.0：标记已通过 TOTP 校验；未通过则不签发 PLATFORM Token
                                    //       BOOTSTRAP Token 为例外：无 mfa claim 或为 "NONE"
  "iat": 1700000000,
  "exp": 1700003600,               // 默认 1 小时
  "jti": "<uuid>"                  // 用于改密/REVOKE/登出主动失效
}
```

**红线**：
- ❌ 平台超管 Token 中**禁止**出现 `tenant_id` claim（R-9）
- ❌ Token `permissions` 数组**禁止**包含 `platform:bypass`（R-3c / R-13）；该权限仅服务端 `PermissionAspect` 通过 RBAC 真值读取
- ❌ **禁止**使用 `force_password_change` 之类布尔字段判定首次设置；统一由 `identity.status=PENDING_SETUP` 表达（v2.0）
- ❌ **禁止**响应或 Token 中出现 `platformAdminMode` 等 boolean 平台身份标记（R-14）
- ❌ 业务插件**禁止**自行解析 JWT；必须通过 `AuthContextCapability.currentUser()`
- ❌ Token 刷新机制 MVP 不做，过期即重登
- ✅ 改密 / REVOKE / `identity.status` 变更必须使旧 Token 失效（jti 黑名单或 `password_updated_at` 校验）

## 8. 关键业务流程

> ⚠️ **v2.0 重写说明**：登录、新增超管、重置密码三条流程已被 v2.0 强制性变更（强制 TOTP、无临时密码、setup_token 流程）取代。
> - 登录流程的权威版本 → **§16.7 平台超管登录详细流程（v2.0，含 TOTP）**
> - 新增超管流程的权威版本 → **§16.5 创建超管详细流程（v2.0）**
> - 重置密码流程的权威版本 → **§16.6 Setup 完成详细流程**（重置密码复用同一 setup_token 通路，purpose=PASSWORD_RESET）
>
> 下方 §8.1 / §8.2 / §8.4 仅保留作为 v1.x 历史档案，**不得**作为实现依据；与 §16 冲突时以 §16 为准。

### 8.1 登录流程
**已迁出**：唯一权威版本见 §16.7（v2.0，含 TOTP）。v1.x 的"密码 → 直接签发 PLATFORM Token"流程**已永久废弃**，不再列出代码块，避免被 AI 编码工具误作施工依据。

### 8.2 新增超管流程
**已迁出**：唯一权威版本见 §16.5。v1.x 的"生成 `tempPassword` + 一次响应明文返回"流程**已永久废弃**；任何包含 `tempPassword` / `force_password_change` / `temp_password_expires_at` 的字段、DTO、E2E 断言必须删除。

### 8.3 撤销超管流程（v2.0：语义改为 REVOKE）
```
Client → PATCH /api/platform/admins/{id}/revoke {reason}
  → PlatformAdminService.revoke()
    ├─ 校验：count(status=ACTIVE) > 1 否则拒绝（"禁止撤销最后一个 ACTIVE 超管"）
    ├─ 校验：不能撤销自己
    ├─ 更新：sys_platform_admin.status=REVOKED, revoked_at, revoked_by, revoke_reason
    ├─ 撤销该 identity 全部活跃 Token（基于 jti 黑名单）
    ├─ **不修改** sys_identity 状态（保留该 identity 的租户身份，可继续走 /login）
    └─ AuditAction.SUPER_ADMIN_REVOKED
```

### 8.4 重置密码流程
**已迁出**：唯一权威版本见 §6 接口 #6 + §16.6。v1.x 的"生成 `tempPassword` 写哈希 + 响应明文返回 + `temp_password_expires_at` + `force_password_change` 拦截"流程**已永久废弃**；MVP 重置密码 = 重新签发 `setup_token(PASSWORD_RESET)` + 发邮件链接，与新增超管走同一通路。

### 8.5 修改自己密码流程（v2.0：强制 TOTP 二次校验）
```
Client → POST /api/platform/admins/me/change-password {oldPassword, newPassword, totpCode}
  → 校验 newPassword 强度（PasswordPolicyService）
  → PasswordHashCapability.matches(oldPassword)
  → TotpCapability.verify(currentIdentity.mfaSecret, totpCode)   // ±1 window
  → 更新 hash + password_updated_at=now（v2.0 不再设置 force_password_change）
  → 撤销当前 jti 之外的全部 Token
  → AuditAction.SUPER_ADMIN_PASSWORD_CHANGED
```

### 8.6 租户状态变更流程
```
Client → PATCH /api/platform/tenants/{id}/status {status: SUSPENDED, reason}
  → 校验目标状态合法（ACTIVE / SUSPENDED / 恢复）
  → TenantProvisioningService.updateStatus()
  → AuditAction.TENANT_STATUS_CHANGED
  → EventBusCapability.publish(TenantStatusChangedEvent)   // 业务插件按需订阅
```

## 16. 首次激活、MFA、Bootstrap 详细设计（v2.0 新增）

### 16.1 `IdentityStatus` 枚举（独立于 `MemberStatus`）

```java
package io.brix.platform.tenant.enums;

public enum IdentityStatus {
    PENDING_SETUP, // 账号已创建，未完成首次初始化；仅 /platform/setup 可访问
    ACTIVE,        // 已完成密码 + TOTP 绑定，可登录
    LOCKED,        // 登录失败 / 风控临时锁定（locked_until 到期自动解锁）
    DISABLED       // 管理员主动停用，永久禁止登录任何系统
}
```

> **迁移要求**：现有 `Identity.status` 字段类型从 `MemberStatus` 改为 `IdentityStatus`。Flyway V014 同步既有 `ACTIVE/DISABLED/LOCKED` 值；未完成 setup 的历史数据置 `PENDING_SETUP`（如有）。`MemberStatus` 保留给 `sys_tenant_member` 使用，不能复用。

### 16.2 `PlatformAdminStatus` 枚举

```java
public enum PlatformAdminStatus {
    ACTIVE,   // 该 identity 当前拥有平台超管授权
    REVOKED   // 平台超管授权已撤销；不签发 PLATFORM Token；保留租户身份
}
```

> **迁移要求**：把现有 `DISABLED` 值改为 `REVOKED`（语义校准）；删除 `disabled_at/disabled_by/disable_reason` 字段名 → 重命名为 `revoked_at/revoked_by/revoke_reason`（Flyway V015）。

### 16.3 `sys_setup_token` 表（V016）

```sql
CREATE TABLE sys_setup_token (
    id                 BIGINT PRIMARY KEY,
    identity_id        BIGINT NOT NULL REFERENCES sys_identity(id),
    token_hash         VARCHAR(128) NOT NULL,         -- SHA-256(token) ；明文 token 永不落库
    purpose            VARCHAR(32)  NOT NULL,         -- INITIAL_SETUP | PASSWORD_RESET
    expires_at         TIMESTAMP WITH TIME ZONE NOT NULL,
    used_at            TIMESTAMP WITH TIME ZONE NULL,
    issued_by          BIGINT NULL,                   -- 操作者 identity_id（Bootstrap 时为 NULL）
    created_at         TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_setup_token_hash UNIQUE (token_hash)
);
CREATE INDEX idx_setup_token_identity ON sys_setup_token(identity_id);
```

**红线**：
- 明文 `token` **只能**通过 `NotificationCapability` 发送到邮箱；**绝不**进入 HTTP 响应体（dev-only feature flag 例外见 §16.12）
- 服务端只比对 `SHA-256(token) == token_hash`
- `used_at IS NOT NULL` 或 `now() > expires_at` 即视为失效；默认 TTL = 24h
- 同一 identity 重签 setup_token 时旧 token 立即失效（`used_at=now, reason='SUPERSEDED'`）

### 16.4 `mfa_secret_encrypted` 字段（V017）

```sql
ALTER TABLE sys_identity
    ADD COLUMN mfa_secret_encrypted VARCHAR(512) NULL,    -- AES-GCM 加密的 TOTP base32 secret
    ADD COLUMN mfa_enabled BOOLEAN NOT NULL DEFAULT FALSE,
    ADD COLUMN mfa_bound_at TIMESTAMP WITH TIME ZONE NULL;
```

- 密钥来源：`platform-auth` 提供 `SecretEncryptionCapability`（KMS / 启动密钥派生）
- 服务端**只在登录校验**时解密
- TOTP 校验允许 ±1 个 30 秒窗口偏移（防时钟漂移）

### 16.5 创建超管详细流程（v2.0）

```
当前超管 → POST /api/platform/admins {username, email, role, notes}
  → L2B Dispatcher 执行 descriptor access policy `PLATFORM_ADMIN_CREATE`
  → PlatformAdminService.create()
    ├─ 校验 identity 不存在或未关联超管
    ├─ 创建 sys_identity:
    │     status=PENDING_SETUP
    │     password_hash=NULL
    │     mfa_enabled=false
    ├─ 创建 sys_platform_admin:
    │     role=PLATFORM_SUPER_ADMIN
    │     status=ACTIVE
    │     created_by=current
    ├─ 生成一次性 setup_token:
    │     SecureRandom 32 字节 → base64url；存 SHA-256 hash；TTL=24h
    │     purpose=INITIAL_SETUP；issued_by=current
    ├─ NotificationCapability.sendSetupLink(email, setupUrl)
    │     setupUrl = `${PLATFORM_BASE_URL}/platform/setup?token=${token}`
    ├─ AuditAction.SUPER_ADMIN_CREATED  (reason 不含 token)
    ├─ AuditAction.SETUP_TOKEN_ISSUED   (reason 不含 token，只记 token_id 与 expires_at)
    └─ 发布 SuperAdminCreatedEvent (DomainEvent)
  → 响应 { id, identityId, setupLinkSent: true }   ★ 仅此三个字段；不得返回明文 password / token / setupUrl / setupUrlMasked
        // setup link 唯一发送路径为 NotificationCapability（邮件）；若邮件送达失败，超管应调用 §6 接口 #6 重发，而非读取响应中的 URL。
        // dev-only 例外（仅非 prod profile）见 §16.12。
```

### 16.6 Setup 完成详细流程

```
用户访问 /platform/setup?token=XXX
  → GET  /api/platform/auth/setup/validate?token=XXX
        → token 校验：未使用 + 未过期 → 返回 {identityId, email, displayName}
  → POST /api/platform/auth/setup/totp/init  {token}
        → 服务端生成 base32 secret，缓存在 Redis(challenge_id, secret) 5 分钟
        → 返回 { challengeId, otpauthUri, qrCodePayload }
  → 用户用 Google Authenticator 扫码 → 输入 6 位 code
  → POST /api/platform/auth/setup/complete {token, challengeId, password, totpCode}
        → 校验 token 仍有效
        → 校验 password 满足策略
        → 取出 Redis 中 challenge 的 secret → 校验 totpCode
        → 原子事务：
            sys_identity.password_hash = bcrypt(password)
            sys_identity.mfa_secret_encrypted = AES-GCM(secret)
            sys_identity.mfa_enabled = true
            sys_identity.mfa_bound_at = now
            sys_identity.status = ACTIVE
            sys_setup_token.used_at = now
        → AuditAction.IDENTITY_PASSWORD_SET / TOTP_BOUND / IDENTITY_ACTIVATED / SETUP_TOKEN_USED
  → 重定向到 /platform/login
```

### 16.7 平台超管登录详细流程（v2.0，含 TOTP）

```
1. POST /api/platform/auth/login {loginId, password}
   → 查 sys_identity by loginId
   → 校验 status:
       PENDING_SETUP → 422 + {code: 'PENDING_SETUP', hint: 'Visit /platform/setup'}
       LOCKED        → 423 + {code: 'IDENTITY_LOCKED', unlockAt}
       DISABLED      → 403 + {code: 'IDENTITY_DISABLED'}
       ACTIVE        → 继续
   → 校验 password；失败 → failed_login_count++ → 5 次后 LOCKED 15 分钟 → 写审计 SUPER_ADMIN_LOGIN_FAILED
   → 校验 sys_platform_admin.status == ACTIVE；否则 403 + {code: 'PLATFORM_ADMIN_REVOKED'}
   → 生成 mfa_challenge_token (Redis TTL 3 分钟，绑定 identityId)
   → 返回 { mfaRequired: true, mfaChallengeToken }

2. POST /api/platform/auth/login/totp {mfaChallengeToken, totpCode}
   → 校验 challenge 未使用未过期
   → 解密 mfa_secret_encrypted → 校验 totpCode (±1 window)
   → 失败 → 写审计 SUPER_ADMIN_LOGIN_FAILED(reason='TOTP_INVALID')
   → 成功 → JwtIssuerCapability.issuePlatformAdminToken()
            permissions 数组**剔除** platform:bypass
            写审计 SUPER_ADMIN_LOGIN_SUCCESS
   → 返回 { accessToken, expiresIn, platformRole, permissions, identityId, displayName }
```

### 16.8 Bootstrap Admin 两阶段模型

| 阶段 | 触发条件 | Bootstrap 能力 | 失效条件 |
|------|---------|---------------|---------|
| **Stage A — Bootstrap Setup Open** | `sys_bootstrap_state.completed_at IS NULL` 且 `count(sys_platform_admin WHERE status=ACTIVE AND role=PLATFORM_SUPER_ADMIN AND identity.status=ACTIVE) == 0` | Bootstrap identity 不允许登录 `/platform/login`，也不允许调用 `/api/platform/auth/login`。Stage A 只能通过专用 Bootstrap Setup Flow 获取一次性 `BOOTSTRAP_SETUP` token。该 token 仅允许访问 `GET /api/platform/bootstrap/status` 与 `POST /api/platform/bootstrap/create-first-admin`。**禁止**访问 `/api/platform/admins/**` / `/api/platform/tenants/**` / `/api/platform/audit-logs` | 首位正式超管同时满足下述所有条件后 → Stage B |
| **Stage B — Bootstrap 永久失效** | 存在至少 1 个 identity 同时满足：`sys_identity.status=ACTIVE` ∧ `sys_identity.mfa_enabled=true` ∧ `sys_platform_admin.status=ACTIVE` ∧ `sys_platform_admin.role=PLATFORM_SUPER_ADMIN`（非 BOOTSTRAP） | Bootstrap identity 被隔离：`identity.status=DISABLED`；所有 Bootstrap Token 加入 jti 黑名单；`sys_bootstrap_state.completed_at=now, completed_by_identity_id=<首位正式超管>`；YAML / ENV 重新启用也无效（`SuperAdminBootstrapRunner` 启动时检到 `completed_at IS NOT NULL` 则静默退出） | — |

⚠️ **关键约束**：
- `POST /api/platform/bootstrap/create-first-admin` 成功后 **不会**立即使 Bootstrap 失效；只创建首位超管的 `Identity(PENDING_SETUP)` + `platform_admin(ACTIVE)` + 签发 setup_token。
- 实际平移点是首位正式超管走完 **§16.6** 全部步骤（设密码 + 扫码绑定 TOTP + 首条 TOTP 验证成功），`identity.status` 迁为 `ACTIVE` 且 `mfa_enabled=true` 后，由 `BootstrapCompletionListener` 原子性执行 Stage A → Stage B 迁移。
- Bootstrap token 为专用 `BOOTSTRAP_SETUP` token，不属于正式 PLATFORM 登录 token。建议 claim：

```jsonc
{
  "token_type": "BOOTSTRAP_SETUP",
  "scope": "BOOTSTRAP",
  "platform_role": "BOOTSTRAP",
  "permissions": [
    "platform:bootstrap:read",
    "platform:bootstrap:create-first-admin"
  ],
  "mfa": "NONE"
}
```

该 token 不得通过 `PlatformAuthGuard`，不得访问 `/api/platform/admins/**`、`/api/platform/tenants/**`、`/api/platform/audit-logs`。

```sql
-- V018__bootstrap_state.sql
CREATE TABLE sys_bootstrap_state (
    id            INT PRIMARY KEY DEFAULT 1 CHECK (id = 1),  -- 单行
    created_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    completed_at  TIMESTAMP WITH TIME ZONE NULL,
    completed_by_identity_id BIGINT NULL
);
INSERT INTO sys_bootstrap_state(id) VALUES (1) ON CONFLICT DO NOTHING;
```

**`SuperAdminBootstrapRunner` 改造要点**：
1. 启动时若 `sys_bootstrap_state.completed_at IS NOT NULL` → **静默退出**（不读 ENV、不重建）
2. 否则按 ENV 创建 / 复用一个 `sys_identity(status=PENDING_SETUP, password_hash=NULL, mfa_enabled=false)` + `sys_platform_admin(status=ACTIVE, role=BOOTSTRAP)`。该 identity 仅作为 Bootstrap 授权锚点，不具备密码登录能力
3. Bootstrap 权限**只能**由专用 `BootstrapTokenService` 签发为短 TTL、一次性、受限的 `BOOTSTRAP_SETUP` token；seed 仅为 `BOOTSTRAP` 角色绑定 `platform:bootstrap:read` + `platform:bootstrap:create-first-admin`
4. 写审计 `BOOTSTRAP_ADMIN_CREATED`

**Bootstrap 红线**：
- `PENDING_SETUP` identity 永远不能通过标准登录链路换取 token。
- `BOOTSTRAP` role 永远不能绕过 TOTP 登录链路。
- Bootstrap 权限只能由专用 `BootstrapTokenService` 签发。
- 禁止在 Platform Auth Endpoint Handler 或身份 Data Owner 内部契约中加入未由 descriptor 策略声明的 `BOOTSTRAP` 特判。
- 禁止恢复 `BRIX_BOOTSTRAP_SUPER_ADMIN_PASSWORD`。
- 禁止返回 `setup_token` / `setupUrl` / `tempPassword` 明文，dev-only 例外仍按 §16.12。

**`BootstrapCompletionListener` 触发条件（原子执行）**：
```
仅当某 identity 事务提交后同时满足：
  sys_identity.status            == ACTIVE
  sys_identity.mfa_enabled       == TRUE
  sys_platform_admin.status      == ACTIVE
  sys_platform_admin.role        == PLATFORM_SUPER_ADMIN   (非 BOOTSTRAP)
则原子性执行：
  UPDATE sys_bootstrap_state
    SET completed_at = now(),
        completed_by_identity_id = <首位正式超管 identity_id>
    WHERE id = 1 AND completed_at IS NULL;
  UPDATE sys_identity SET status='DISABLED' WHERE id = <bootstrap_identity_id>;
  将 bootstrap_identity 所有有效 jti 写入黑名单；
  写审计 BOOTSTRAP_ADMIN_DEACTIVATED（actor=首位正式超管）。
```

> ⚠️ Break Glass 不在 MVP，**禁止**把 Bootstrap 当 Break Glass 用。
> ⚠️ Bootstrap 一旦 Stage B，任何重启 / 删表 / YAML 重启都**不能**重建；严重事故需走 v1.1 Break Glass 预留通路。

### 16.10 前端路由守卫规约（v2.0）

| 守卫 | 适用路由 | 通过条件 | 失败行为 |
|------|---------|---------|---------|
| `PlatformAuthGuard` | `/platform/**`（除 login / setup） | 持有 `scope=PLATFORM` 的 Token，且未过期 | 跳 `/platform/login` |
| `TenantAuthGuard` | 所有租户业务路由 | 持有 `scope ∈ {USER, TENANT}` 的 Token | 跳 `/login` |
| `SetupOnlyGuard` | `/platform/setup` | 有 `?token=` query 参数；不允许已登录 PLATFORM 访问 | 跳 `/platform/login` |
| `BootstrapOnlyGuard` | `/platform/bootstrap` | 后端 `GET /api/platform/bootstrap/status` 返回 `inBootstrap=true` | 跳 `/platform/login` |

**前端 R-7**：`/platform/login` 不得自动跳转到 `/login`；`/login` 不得自动跳转到 `/platform`。两个登录页**严格**互不感知。

### 16.12 dev-only feature flag：setup URL 调试返回

> 生产默认关闭；CI 必须断言生产 profile 下无法启用。

| 配置项 | 默认值 | 语义 |
|--------|--------|------|
| `platform.admin.setup.return-url-for-dev-only` | `false` | 为 `true` 且 `spring.profiles.active` 不含任何 prod 标识（如 `prod`/`production`/`prd`）时，§6 接口 #4 / #6 / #15 响应体可额外携带 `setupUrl: "https://.../platform/setup?token=..."` 字段以便本地调试；任何其他情况均禁止返回该字段。 |

**实现约束**：
- `PlatformAdminConfig.@PostConstruct` 检查：若 flag=true 且 profile 含 `prod` 标识 → 启动失败并报错
- ArchUnit 测试：`application-prod.yml` / `application-production.yml` 中不得出现该 key 或出现时必为 `false`
- CI 流水线：构建产品 profile 后 grep 响应 fixture，出现 `setupUrl` 或 `setup_token` 明文 → 构建失败
- 前端 Repository 类型：`CreateAdminResponse` 严格为 `{ id: string; identityId: string; setupLinkSent: true }`；若未来需要读取 dev 状态下的 `setupUrl`，需另走 `CreateAdminResponseDevExt` 独立类型，并被 `@DevOnly` 标记
