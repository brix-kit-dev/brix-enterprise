## 0. 文档定位

本文档用于指导 **v3.1.3 多租户功能最小实现** 的代码落地、前端体验补齐、测试验收与发布门禁。

本文不是新的架构蓝图，不改变冻结设计；所有架构判断、红线、DDL 约束、Token 契约、Capability 契约仍以 `v3.1.3-多租户功能最小实现-设计蓝图（冻结）.md` 为唯一真相来源。本文只回答：

- 当前代码距离 v3.1.3 冻结蓝图还差什么；
- 应该按什么顺序开发；
- 每个阶段需要交付哪些后端、前端、测试与治理成果；
- 什么条件下可以进入下一阶段和最终 GA。

---

## 1. 总体结论

当前代码已经具备一部分多租户底座能力，例如 `sys_tenant_principal` 基础表、`TenantSqlGuardInterceptor`、`TenantResolverChain`、`PrincipalAdmissionService`、租户 CRUD 与部分前端租户管理页面。

但整体仍未达到 v3.1.3 冻结蓝图的最小生产可用标准，主要缺口集中在：

1. **数据模型未收口**：`context_id`、`authz_version`、Profile 双可空强约束、配额行锁、邀请表、审计分层仍不完整。
2. **认证协议未冻结化**：仍是通用 `login + selectTenant(tenantId)`，缺 `/login/actor`、`/login/subject`、`contextSelectionTicket`、`cid`、`mver/pver`。
3. **Capability 契约缺口明显**：`TenantDirectoryCapability`、`TenantQuotaCapability`、特权 `PlatformAdminCapability`、对象级 `AuthorizationCapability` 尚未完整落位。
4. **全栈隔离不足**：SQL 之外的 Redis、Kafka/EventBus、对象存储、异步线程、搜索、导出、审计仍缺统一租户上下文传播与清理。
5. **前端体验未按 B/C 双轨拆分**：`useTenant()` 仍以 tenantId 为中心，缺 Actor/Subject 判别类型、Context Selector ticket 化、Actor-only Switcher、租户配置 UI、对象级授权 UI。

因此本计划按 **Phase 0 ~ Phase 6** 推进，先修数据模型与租户创建初始化，再推进认证主链、前端体验、全栈隔离和交付加固。

## 2. 现状缺口摘要

### 2.1 数据模型与迁移

| 缺口 | 当前表现 | 蓝图要求 | 优先级 |
|------|----------|----------|--------|
| `context_id` | `sys_tenant_member` / `sys_tenant_principal` 尚未完整具备稳定 `context_id` 与不可变触发器 | 每个 Actor/Subject Context 必须有稳定 `context_id`，创建后 DB 层不可改 | P0 |
| `authz_version` | 当前主要使用身份级 `token_version` / `tv` | Member 使用 `mver`，Principal 使用 `pver`，状态/角色/权限变更自增 | P0 |
| `biz_user_profile` | 仍使用 `ref_type + ref_id` 弱多态 | 改为 `member_id` / `principal_id` 双可空字段 + CHECK + 复合 FK | P0 |
| V008 迁移 | 使用 `ON CONFLICT DO NOTHING` | 冲突必须阻断并产报告，禁止静默吞冲突 | P0 |
| 配额 | 当前偏租户内 `max_users/max_principals` | 新增实例级 `sys_installation_quota`，首位 OWNER 接管激活 / 恢复 / 状态变迁同事务行锁 | P0 |
| 租户创建与首位 OWNER 接管 | 新增租户可能只创建 `sys_tenant`，但缺首位 OWNER 接管邀请、接受事务和激活闭环 | 创建租户后保持 `PENDING_ACTIVATION`；平台超管发送 `FIRST_OWNER` 邀请；接受时同事务创建 `ACTIVE OWNER`、Profile、激活租户并占用配额 | P0 |
| 审计 | 单一或散落审计模型 | 拆 `biz_tenant_audit_log` 与 `sys_platform_audit_log` | P1 |

### 2.2 认证与 Token

| 缺口 | 当前表现 | 蓝图要求 | 优先级 |
|------|----------|----------|--------|
| 登录入口 | 通用 `login()` 同时聚合 Membership 与 Principalship | `/api/auth/login/actor` 与 `/api/auth/login/subject` 独立入口 | P0 |
| 上下文选择 | `selectTenant(Long tenantId)` | `select-context(selectionTicket)`，ticket 绑定 identity token `jti` | P0 |
| 稳定上下文 | 选择阶段依赖 tenantId | Token 使用 `cid=<context_id>` 表示访问上下文 | P0 |
| Token 双轨 | 已有 `mid/pid` 雏形，但 audience、版本号、cid 不完整 | Actor: `aud=brix-actor` + `mid/mtype/mver/cid`；Subject: `aud=brix-subject` + `pid/ptype/pver/cid` | P0 |
| Refresh Token | 有持久化雏形 | 绑定 `cid`，支持 Family 轮转与重放检测 | P1 |

### 2.3 Capability 与运行壳对齐

| 缺口 | 应补契约 | 优先级 |
|------|----------|--------|
| 当前租户上下文不完整 | `TenantCapability.getCurrentRoleType()`、`getCurrentRefId()`、`getCurrentUserId()`、`getCurrentTenant()`、`requireActiveTenant()` | P0 |
| 插件引用校验缺失 | `TenantDirectoryCapability.requireSameTenant(refId, RefKind)` | P0 |
| 配额语义未契约化 | `TenantQuotaCapability.requireQuota()`、`requireCanCreateTenant()`、`getCurrentTenantUsage()` | P0 |
| 跨租户特权查询边界不清 | 独立特权契约包 `runtime-sdk-admin-api` + `PlatformAdminCapability` | P1 |
| 对象级授权缺统一入口 | `AuthorizationCapability.requireObjectAccess(objRef, action)` | P1 |

### 2.4 前端体验

| 缺口 | 当前表现 | 应补能力 | 优先级 |
|------|----------|----------|--------|
| `useTenant()` 类型不匹配 | 以 `tenant / availableTenants / switchTenant(tenantId)` 为中心 | Actor/Subject 判别联合类型，暴露 `currentContext` | P0 |
| B/C 登录未拆 | 缺独立 Actor/Subject 登录 UI 与 API client | `/login/actor`、`/login/subject` 两套入口 | P0 |
| Context Selector 未 ticket 化 | 可见模型偏 tenantId | 选择阶段只使用 `selectionTicket`，不暴露 `contextId` | P0 |
| Switcher 范围不合规 | 按 tenantId 切换 | 仅 Actor 可按 `contextId` 切换，并重签 Token | P0 |
| 租户配置 UI 缺失 | 无完整 locale/timezone/theme 编辑 | `TenantConfigEditor` + `useTenantConfig()` | P1 |
| 对象级授权 UI 缺失 | 无 data scope/权限矩阵管理 | Actor 权限矩阵、data scope 管理、Subject 自有数据视图 | P1 |

**验收门禁**：

### Phase 1：数据模型与迁移收口

**目标**：完成 v3.1.3 多租户底座的数据结构，作为后续认证、前端上下文和对象授权的基础。

**对应里程碑**：M1。

**优先级**：P0。

**后端交付**：

1. **Context ID 与授权版本**
   - 为 `sys_tenant_member`、`sys_tenant_principal` 增加 `context_id UUID NOT NULL`。
   - 增加 `authz_version INTEGER NOT NULL DEFAULT 1`。
   - 增加 `UNIQUE(context_id)` 与 `UNIQUE(tenant_id, id)`。
   - 增加 `guard_context_id_immutable()` 触发器，覆盖 member / principal。

2. **Profile 强约束迁移**
   - 新增 V009a：`biz_user_profile.member_id`、`principal_id` 可空列。
   - 新增 V009b：分批回填并产冲突报告。
   - 新增 V009c：复合 FK、唯一约束、`chk_profile_ref_exclusive`。
   - 新增 V009d：删除 `ref_type` / `ref_id` / legacy 字段。
   - 更新 `BizUserProfile` Entity、Repository、Service 与测试。

3. **迁移冲突阻断**
   - 替换 V008 静默冲突策略。
   - CUSTOMER / GUEST 迁移到 principal 前必须扫描冲突；冲突时非零退出并输出报告。

4. **邀请与 OWNER 保护**
   - 新增 `sys_tenant_invitation`，token 只存 hash。
   - DB 层强制 `target_type` 与 `target_role` 组合合法。
   - 新增 `guard_last_owner()` 触发器。
   - 应用层 OWNER 降级 / 删除 / 停用前先取租户级锁。

5. **实例级配额**
   - 新增 `sys_installation_quota`。
   - 创建、恢复、禁用、归档、删除租户时，在同一事务内先 `SELECT FOR UPDATE` 锁配额行，再更新 `used` 与租户状态。

6. **审计分层表结构**
   - 新增 `biz_tenant_audit_log(tenant_id NOT NULL)`。
   - 新增 `sys_platform_audit_log(affected_tenants JSONB)`。

**前端交付**：

- 租户创建页展示配额错误、License 到期、新建被拒绝等标准错误态。
- 成员管理页增加“最后 OWNER 不可移除 / 不可降级”的交互提示。
- 邀请管理 UI 支持待接受、已接受、已过期、已撤销、重发。

**测试验收**：

- Flyway staging 迁移通过。
- Profile 脏数据会阻断迁移并产报告。
- 并发创建租户无法突破默认 3 租户上限。
- 并发降级 OWNER 无法产生 0 OWNER。
- `context_id` 更新被 DB 触发器拒绝。

### Phase 2：租户创建与首位 OWNER 接管

**目标**：把“新增租户”与“首位 OWNER 接管”拆成两个受控用例：平台超管先创建 `PENDING_ACTIVATION` 租户，再通过统一邀请基础设施发送 `FIRST_OWNER` 接管邀请；受邀人接受后，才在同一事务中创建 `ACTIVE OWNER`、Profile、激活租户并正式占用配额。

**对应里程碑**：M2。

**优先级**：P0。

**后端交付**：

1. **TenantCreationService**
   - 新增平台级 `TenantCreationService`，作为创建租户的唯一入口。
   - Controller / PlatformAdmin 能力只调用该服务，不直接拼装多张表写入。
   - 创建租户后状态固定为 `PENDING_ACTIVATION`，不自动创建 OWNER，不创建 `biz_user_profile`，不正式占用租户数量配额。
   - Host 继续保持极薄：通过依赖与 YAML 启用能力，不在 Host 写创建逻辑。

2. **统一 TenantInvitationService**
   - 新增 `TenantInvitationService`，统一处理 `FIRST_OWNER` 与 `TENANT_MEMBER` 两类邀请。
   - 邀请记录显式保存 `invitation_purpose`、`inviter_type`、`platform_admin_id` / `tenant_member_id`（二者互斥）、`tenant_id`、`target_role`、`invited_email`、`token_hash`、`status`、`expires_at`、`used_at`。
   - 服务端必须根据记录中的 `invitation_purpose` 选择接受处理器，不根据“租户是否已有 OWNER”动态推断，也不相信前端传入用途。
   - Token 一次性、带有效期、数据库仅保存 hash；重发后旧 token 失效；API 不返回明文 token，链接只能通过 `NotificationCapability` 发送。

3. **首位 OWNER 接管事务**
   - 平台端新增 `POST /api/platform/tenants/{tenantId}/owner-invitations` 及 resend / revoke 接口，只允许平台超管发起 `FIRST_OWNER` 邀请，角色固定为 `OWNER`。
   - 接受 `FIRST_OWNER` 邀请时，同事务锁定并校验邀请、Token hash、状态、有效期和邮箱；确认租户仍为 `PENDING_ACTIVATION` 且不存在 `ACTIVE OWNER`。
   - 同事务锁定并重新校验 License / 租户配额，创建 `sys_tenant_member(OWNER, ACTIVE)`，创建或确认 `biz_user_profile`，将租户改为 `TRIAL` 或 `ACTIVE`，正式占用配额，将邀请置为 `ACCEPTED`，写入 Platform Audit。
   - 任一步失败全部回滚；重复接受不会重复创建 Member、Profile 或增加配额。

4. **后续租户成员邀请**
   - 租户端新增 `POST /api/tenant/members/invitations`，仅该租户 `ACTIVE OWNER` 可发起 `TENANT_MEMBER` 邀请。
   - 可邀请 `OWNER`、`ADMIN`、`MEMBER`；接受后加入现有租户，不改变租户状态和租户数量配额。
   - 增加 `GET /api/tenant/members`、`PATCH /api/tenant/members/{memberId}/role`、`PATCH /api/tenant/members/{memberId}/status`，并保护最后一个 `ACTIVE OWNER`。

5. **公共接受入口、幂等与审计**
   - 新增 `GET /api/invitations/preview` 与 `POST /api/invitations/accept`。
   - 已有 Identity：用户使用原账号登录，校验邀请邮箱一致后接受邀请；无 Identity：用户通过一次性邀请验证邮箱，自行设置密码并激活 Identity 后接受邀请。
   - 平台超管不得设置、查看或发送用户密码；租户成员统一从 `/login` 登录并获得 Actor Token，不使用 `/platform/login` 或 Platform Token。
   - 邀请发送、重发、撤销、接受、激活租户、成员角色/状态变更均写审计；创建租户和发送首位 OWNER 邀请支持 `requestId` / 幂等键。

6. **一致性巡检**
   - 增加无 OWNER 租户巡检：`PENDING_ACTIVATION` 可无 OWNER；`ACTIVE/TRIAL` 租户必须至少有一个 `ACTIVE OWNER`。
   - 巡检失败触发安全告警，并作为发布阻断条件。

**前端交付**：

- 租户创建表单不再要求首位管理员字段；创建成功后展示 `PENDING_ACTIVATION` 状态和“发送首位 OWNER 邀请”下一步。
- 平台端“租户详情 → 租户管理员”区域支持发送、重发、撤销 `FIRST_OWNER` 邀请；不展示或输入用户密码。
- 租户端成员管理页支持 OWNER 邀请和管理 OWNER / ADMIN / MEMBER，并提示最后 OWNER 不可删除、停用或降级。
- 邀请预览 / 接受页支持已有账号登录接受，以及无账号用户验证邮箱、设置密码、激活 Identity 后接受。

**测试验收**：

- 新增租户后状态为 `PENDING_ACTIVATION`，不存在自动创建的 OWNER / Profile，且不占用正式租户数量配额。
- `FIRST_OWNER` 接受成功后，同事务创建 1 个 `ACTIVE OWNER` 与对应 `biz_user_profile`，租户变为 `TRIAL` 或 `ACTIVE`，配额 `used + 1`，邀请置为 `ACCEPTED`。
- Profile 创建、配额校验、租户激活或邀请接受任一步失败时，Member、Profile、租户状态、配额和邀请状态全部回滚。
- 并发接受 / 重放同一邀请不会重复创建 Member、Profile 或重复增加配额。
- 平台 Token 不能接受租户邀请或访问租户成员管理 API；租户 Actor Token 不能访问平台 owner-invitations API。
- 无 OWNER 巡检只阻断 `ACTIVE/TRIAL` 无 OWNER 租户，不阻断正常 `PENDING_ACTIVATION` 租户。

### Phase 3：Capability 契约与认证双轨化

**目标**：将访问上下文从 `tenantId` 升级为稳定的 `{tenant + actor/subject + contextId}`，完成 JWT 双轨与一次性选择协议。

**对应里程碑**：M3。

**优先级**：P0。

**后端交付**：

1. **TenantCapability 扩展**
   - 增加 `getCurrentTenant()`。
   - 增加 `requireActiveTenant()`。
   - 增加 `getCurrentRoleType()`。
   - 增加 `getCurrentRefId()`。
   - 增加 `getCurrentUserId()`。
   - 保持向后兼容：新增方法使用 default 或按蓝图兼容策略演进。

2. **新增核心 Capability**
   - `TenantDirectoryCapability`：固定命名，不保留别名。
   - `TenantQuotaCapability`：所有安全 / 上限类校验 fail-closed。
   - `PlatformAdminCapability`：置于独立特权契约包，普通插件无编译依赖。

3. **认证入口拆分**
   - 新增 `/api/auth/login/actor`。
   - 新增 `/api/auth/login/subject`。
   - B 端只发现 Actor contexts，允许跨租户发现并记 Platform Audit。
   - C 端只发现当前租户 Subject context，不允许跨租户聚合。

4. **contextSelectionTicket**
   - 登录第一阶段返回 `identityToken` + `contexts[].selectionTicket`。
   - ticket 高熵、一次性、TTL <= 5min。
   - ticket 绑定 `identityToken.jti`，不是只绑定 `sub`。
   - 重放、过期、跨 jti 使用全部拒绝并审计。
   - 选择阶段不下发稳定 `contextId`。

5. **JWT 双轨**
   - Actor Token：`aud=brix-actor`、`scope=actor`、`tid`、`cid`、`mid`、`mtype`、`uid`、`mver`。
   - Subject Token：`aud=brix-subject`、`scope=subject`、`tid`、`cid`、`pid`、`ptype`、`uid`、`pver`。
   - Identity Token：`aud=brix-identity`，仅允许 `select_context` / `register_tenant`。
   - Refresh Token：`aud=brix-refresh`，保存稳定 `cid`，支持 Family 轮转与重放检测。
   - 校验 Header `alg` / `typ` / `kid` 与 Claims `iss` / `aud` / `exp` / `nbf` / `jti`。

6. **授权版本校验**
   - Member 状态 / 角色 / 权限变更自增 `authz_version`。
   - Principal 状态 / 角色 / 权限变更自增 `authz_version`。
   - 请求时校验 `mver` / `pver` 与 DB 当前版本一致，不一致返回 `STALE_AUTHZ_VERSION`。

**前端交付**：

- Auth API client 拆为 `loginActor()`、`loginSubject()`、`selectContext()`、`switchContext()`、`refresh()`。
- B 端登录页仅进入 Actor 登录流程。
- C 端品牌登录页仅进入 Subject 登录流程，并绑定当前租户提示。
- 新增 `ActorContextSelector`，使用 `selectionTicket` 选择上下文。
- C 端无 Subject context 时进入 `NO_TENANT` / 注册绑定 / 邀请接受流程。

**测试验收**：

- Actor / Subject Token 互斥，不能同时含 `mid` 与 `pid`。
- Subject Token 访问管理 API 返回 403。
- C 端登录不会返回用户在其他租户的任何信息。
- ticket 重放、过期、跨 jti 使用均被拒绝。
- 停用 Member / Principal 后旧 Token 失效。

### Phase 4：前端运行时与租户体验补全

**目标**：补齐 v3.1.3 对前端运行时、上下文切换、租户配置和用户体验的要求。

**对应里程碑**：M4。

**优先级**：P0 / P1。

**前端交付**：

1. **`useTenant()` 判别联合类型**
   - Actor 返回：`role: 'actor'`、`currentContext`、`availableContexts`、`switchContext(contextId)`。
   - Subject 返回：`role: 'subject'`、`currentContext`。
   - Subject 不暴露 `availableContexts` 和 `switchContext`。
   - `currentContext` 包含 `contextId`、`roleType`、`refId`、`userId`、`displayName`。

2. **Context Switcher**
   - `ActorContextSwitcher` 只在 Actor 场景显示。
   - 切换参数为目标 Actor `contextId`。
   - 切换成功后重签 Token，旧 `jti` 入黑名单。
   - 前端执行 `queryClient.clear()`、状态重置、配置 / 品牌 / feature reload。

3. **租户配置体验**
   - 新增 `useTenantConfig()`。
   - 支持 `locale`、`timezone`、`theme`。
   - 提供 `formatDate()`、`formatTime()`、`formatCurrency()`。
   - 新增 `TenantConfigEditor`，用于平台超管 / 租户管理员编辑默认配置。

4. **登录和邀请页面**
   - `ActorLoginPage`。
   - `SubjectLoginPage`。
   - `ActorContextSelectorPage`。
   - `InvitationAcceptPage`。
   - `SubjectNoTenantState`。

5. **企业租户管理 UI 增强**
   - 租户详情页增加配额使用、License 状态、默认 locale / timezone / theme。
   - 成员页区分 OWNER / ADMIN / MEMBER，阻止最后 OWNER 操作。
   - 邀请页区分 MEMBER / PRINCIPAL 邀请。
   - 平台审计页展示跨租户发现、平台操作、License 变更。

**后端交付**：

- 提供前端所需 Session / Context / Config API。
- 实现 `TenantConfigCapability` 三层合并：user preference → `sys_tenant_config` → `sys_platform_config`。
- 收敛 `TenantWhitelist`，确保 `sys_tenant_config` 不进入白名单。

**测试验收**：

- B 端登录 → 选择上下文 → 切换上下文 E2E 通过。
- C 端登录不出现 Context Selector。
- 切换后旧租户缓存不会残留到新租户页面。
- 租户配置变更后 UI 的语言、时区、主题生效。

### Phase 5：全栈隔离与插件对象级授权

**目标**：从“SQL 层有 tenant_id”升级为“所有基础设施与所有业务对象访问都租户安全”。

**对应里程碑**：M5。

**优先级**：P1。

**后端交付**：

1. **SQL 隔离**
   - 保留并加强 `TenantInterceptor` 与 `TenantSqlGuardInterceptor`。
   - `@CrossTenantAccess(reason, approval)` 必须有 reason 和审计。
   - 登录期跨租户发现只允许 `discoverActor`，并写 Platform Audit。

2. **Redis / 缓存隔离**
   - 新增统一 KeyBuilder：`{tid}:{domain}:{key}`。
   - 禁止裸 key。
   - 缓存异常不应绕过安全校验。

3. **Kafka / EventBus 隔离**
   - Integration Event 强制 `EventEnvelope`。
   - 发布时带 `tenantId`、`traceId`、`eventId`、`schemaVersion`。
   - 消费时从消息头 / 信封恢复 TenantContext，处理后 finally clear。

4. **对象存储隔离**
   - 路径强制 `tenant/{tid}/...`。
   - 预签名 URL 生成前校验对象归属。
   - 下载时校验当前上下文与对象 tenant 一致。

5. **异步 / 定时任务隔离**
   - 统一 `TenantTaskDecorator`。
   - 所有 `set` 必须配对 finally `clear()`。
   - 定时任务必须显式声明 tenant 来源。

6. **搜索 / 导出隔离**
   - 索引文档包含 `tenantId`。
   - 查询强制注入当前 tenant filter。
   - 导出服务禁止默认跨租户聚合。

7. **对象级授权**
   - 新增 `AuthorizationCapability.requireObjectAccess(objRef, action)`。
   - Subject 默认只能访问自身 `principal_id` 关联对象。
   - Actor 必须同时校验 permission + data scope。
   - 企业插件 case、storage、booking、contracts、messenger、compliance 等读写入口逐个接入。

**前端交付**：

- Actor 权限矩阵 UI。
- Actor data scope 管理 UI。
- Subject “我的数据”视图，避免展示全租户数据入口。
- 文件、导出、详情页统一处理 403、对象不存在、跨租户拒绝。
- 插件页面统一从 `useTenant().currentContext` 读取上下文，不把请求参数中的 tenantId 当授权依据。

**测试验收**：

- 同租户 Subject A 不能读取 Subject B 的 Case / File / Order。
- Actor 有操作权限但无 data scope 时仍被拒绝。
- Redis / Kafka / Async 上下文泄漏专项测试通过。
- 插件无 DB 外键到平台租户表。
- 插件不直接 JOIN 平台租户关系表。

### Phase 6：License、平台审计与交付加固

**目标**：完成生产交付、License 行为、可观测性、安全纵深与文档。

**对应里程碑**：M6。

**优先级**：P1 / P2。

**后端交付**：

- License 模块接入 `TenantQuotaCapability`。
- 开源默认 3 租户上限按 `installation_id` 统计。
- License 到期只禁止新增，不删除、不停用、不影响存量读写。
- `sys_platform_audit_log` 覆盖登录期跨租户发现、平台超管查询、License 变更、红线治理。
- 可选 PostgreSQL RLS Adapter 原型：先影子告警，再按生产 profile 启用 `FORCE ROW LEVEL SECURITY`。
- `runtime-sdk-admin-api` 依赖白名单检查，普通插件无法 import 特权 Capability。

**前端交付**：

- License / 配额页：展示 installation quota、used、到期状态、拒绝新增原因。
- 平台审计页：按 action、operator、affectedTenants、时间过滤。
- 移动端 / Subject 端最小适配：Subject 登录、无准入、个人数据范围、租户配置生效。

**测试与文档交付**：

- JWT 双轨单测。
- ticket 重放 / 枚举 / 过期测试。
- 配额并发测试。
- OWNER 并发降级测试。
- 对象级授权 E2E。
- 上下文泄漏测试。
- License 到期行为测试。
- 更新开发者指南、插件接入手册、前端接入手册、迁移手册。

**验收门禁**：

- T-1 ~ T-28 全部有自动化或明确人工门禁。
- 无高危越权、跨租户泄漏、上下文泄漏问题。
- 可以标记 `Implementation Accepted / GA`。

## 6. 关键风险与缓解

| 风险 | 影响阶段 | 缓解措施 |
|------|----------|----------|
| `biz_user_profile` 旧数据质量不可控 | Phase 1 | V009b 独立冲突检测，阻断并产报告，staging 先演练 |
| CUSTOMER / GUEST 迁移冲突 | Phase 1 | 禁止 `DO NOTHING`，迁移前生成冲突明细，人工裁决后重跑 |
| 首位 OWNER 邀请未接受导致租户长期待激活 | Phase 2 | 新租户显式保持 `PENDING_ACTIVATION`，不占用正式配额；平台端提供邀请状态、重发、撤销；巡检只阻断 `ACTIVE/TRIAL` 无 OWNER |
| JWT 新旧协议切换影响在线用户 | Phase 3 | 灰度发布；短期兼容旧 token；前端先支持新响应，再切后端强校验 |
| C 端跨租户关系泄漏 | Phase 3 / 4 | C 端入口强制 current tenant 过滤；E2E 覆盖跨租户 Subject 数据不可见 |
| 异步线程上下文泄漏 | Phase 5 | 上下文泄漏专项测试；所有 `set` 必须 finally `clear` |
| 对象级授权接入遗漏 | Phase 5 | 插件入口清单化；ArchUnit + E2E 双门禁；高风险插件优先接入 |
| RLS 误配造成生产查询失败 | Phase 6 | 先影子模式告警，再按 profile 启用 FORCE RLS |

## 7. 开发顺序建议

推荐实际排期按以下依赖推进：

```text
Phase 0
  ↓
Phase 1 数据模型
  ↓
Phase 2 租户创建初始化
   ↓
Phase 3 认证双轨
   ├─ Phase 4 前端上下文体验
  ↓
Phase 5 全栈隔离与对象级授权
  ↓
Phase 6 License / 审计 / RLS / GA
```

其中 Phase 1、Phase 2 与 Phase 3 是不可跳过的主路径；Phase 4 可在 Phase 3 API 契约冻结后并行启动；Phase 5 需要在 `TenantDirectoryCapability` 与 `AuthorizationCapability` 基本可用后全面铺开。

## 8. 最终完成定义

当以下条件全部满足时，v3.1.3 多租户功能最小实现可标记为 `Implementation Accepted / GA`：

1. 数据模型满足 v3.1.3 §5 全部强制 DDL 与迁移规则。
2. 登录、选上下文、切上下文、刷新 Token 满足 v3.1.3 §8 / §9。
3. Capability 契约与运行壳分层满足 v3.0.10 与 v3.1.3 §11 / §18。
4. T-1 ~ T-28 均有自动化或明确人工门禁。
5. 前端完成 Actor/Subject 登录分离、Context Selector/Switcher、租户配置、关键授权失败体验。
6. 企业插件关键读写入口完成对象级授权。
7. SQL、Redis、Kafka/EventBus、对象存储、异步、搜索、导出、审计均覆盖租户隔离。
8. 迁移、并发、越权、上下文泄漏、License 到期行为测试全部通过。
