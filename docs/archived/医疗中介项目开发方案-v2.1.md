# 医疗中介SaaS平台开发方案 v2.1（架构冻结稿）

> **版本**: 2.1  
> **日期**: 2026-01-08  
> **状态**: 架构冻结（不含工期）  
> **作者**: Shinwa Platform Team

---

## 0. v2.1 的定位（与 v2.0 的差异）

v2.1 的目标不是“把医疗中介做大而全”，而是把它升级为可长期演进的平台内核：

- **插件 = 技术资产边界**（可复用的代码模块/Maven Module），不是部署容器
- **部署单元 = Service**（运维/扩缩容/发布粒度），初期可“合并部署”以降低运维复杂度
- **医疗能力变薄**：医疗相关模块只做“资料收集/协调/交付/风控”，不做医学判断与解析
- **业务流程统一为 Case 编排**：用事件流驱动 Case Node 推进，避免流程网关与条件分支

## 1. 架构原则（必须写进方案并冻结）

### 1.1 插件与部署的原则

- 插件是**代码资产**：一个插件对应一个（或一组）Maven Module，可独立演进、可复用、可替换
- Service 是**部署与运维单元**：一个 Service 可包含多个插件模块（合并部署），后期再按压力拆分
- **核心域禁止热加载**：Case 编排与事实记录属于核心域，线上不启用热加载
- **非核心可热加载**：CMS/通知/部分配置驱动模块可按平台能力启用热加载（作为可选能力）

### 1.2 事件流 BPM 原则（替换 v2.0 的 BPM 描述）

- 不使用流程网关
- 不做条件分支
- 只响应“业务事实事件”（Fact Event）
- 所有“事件 → Node 推进规则”集中在 `case-event`

### 1.3 合规与风险原则（医疗数据）

- Intake **只收集资料，不解析、不评估、不生成医疗建议**
- 话术风控 **系统化 + 审计**：禁止词检测、模板版本留痕、使用记录可追溯
- Timeline **法律级不可变事实**：只追加，不允许修改与删除

## 2. v2.1 冻结的插件资产清单（插件=资产边界）

> 说明：以下为“资产清单”（代码模块），并不代表部署容器数。

### 2.1 平台通用插件（行业无关）

- `plugin-user`：账号/权限/组织（已有，保持）
- `plugin-cms`：内容/轮播/公告（已有，保持）
- `plugin-file-center`：文件上传与隔离（新增）
  - 目标：将“医疗资料”等高风险文件能力从医疗域剥离，形成通用文件中心
- `plugin-notification`：通知/消息（新增）
  - v2.1 冻结：仅“通知记录 + 事件订阅 + 站内通知查询接口”，不对接短信/邮件/IM
- `plugin-contract`：合同模板与管理（新增）
  - 目标：通用合同管理能力，支持模板定义、版本管理、合同实例、多方签署、状态流转
  - v2.1 冻结：基础合同管理，不对接电子签名服务商（预留接口）
  - ⚠️ 裁决①：**不做电子签名系统**（第三方服务对接 v3+ 再评估）
  - ⚠️ 裁决②：**合同签署后不可变**（修改须新建版本并重新签署）
  - ⚠️ 裁决③：**合同事件不直接驱动 Case 推进**（仅作为事实记录）
- `plugin-partner-catalog`：合作方目录（新增/改名）
  - 从 `med_hospital` 通用化为合作方：医院/体检机构/翻译机构/酒店/车辆公司均可作为 Partner
- `plugin-service-package`：产品/套餐（新增/改名）
  - 从 `med_package` 通用化为产品：体检套餐/诊疗套餐/翻译服务/接送机服务均可作为 Package

### 2.2 Case 服务编排插件（核心资产）

> 合并部署为 `case-service`（一个容器）

- `case-core`：Case 聚合根（Case / Node / Parameter）
- `case-template`：流程模板（模板定义、模板版本、节点定义）
- `case-event`：事件流 BPM（订阅事实事件、推进 Node、触发派生事件）
- `case-schedule`：行程（Day 无状态、Item 有状态）
- `case-timeline`：不可变事实（Timeline Event Append-only）

### 2.3 医疗行业插件（变薄/适配层）

- `plugin-medical-intake`：医疗资料收集（不解析）
  - 只负责：创建资料收集任务、调用 `plugin-file-center` 上传/下载、记录元数据
- `plugin-appointment`：协调/预约
  - 只负责：协调记录、预约沟通记录、与 Partner/Package 的关联
- `plugin-medical-delivery`：报告/说明会交付
  - 只负责：交付记录、文件交付（走 file-center）、交付事件发布
- `plugin-risk-compliance`：禁止话术/风控
  - 只负责：禁止词/模板/免责声明/审计

> v2.1 明确：不再存在 “巨石 `plugin-medical`”。

## 3. v2.1 推荐部署拓扑（运维视角冻结）

> 初期目标：容器数少、链路清晰、可观测性集中；后期再按压测结果拆分。

### 3.1 初期（MVP/验证期）

- `gateway`（已有）
- `auth-center`（已有）
- `case-service`（核心，合并部署：case-core/template/event/schedule/timeline）
- `platform-service`（合并部署：plugin-user/plugin-cms/plugin-partner-catalog/plugin-service-package/plugin-file-center/plugin-notification/plugin-contract）
- `medical-service`（合并部署：plugin-medical-intake/plugin-appointment/plugin-medical-delivery/plugin-risk-compliance）

基础设施共享：PostgreSQL / Redis / Kafka

### 3.2 线上运维原则（冻结）

- 数据库/Redis/Kafka 初期共享集群；按容量与隔离需求再拆分
- 核心数据链路（case-service）优先保证：
  - 灰度发布可回滚
  - 严格版本兼容（事件 schema）
  - 禁止热加载

## 4. 事件流 BPM（Fact Event → Case Node 推进）

### 4.1 核心事件定义（v2.1 冻结）

> 事件只描述事实，不包含“应该如何走流程”的决策。

- `CaseCreated`
- `PackageSelected`
- `PaymentConfirmed`
- `ScheduleConfirmed`
- `ServiceCompleted`
- `ReportDelivered`

可选（v2.1 作为实现细节，不作为跨服务强依赖）：
- `IntakeMaterialUploaded`
- `AppointmentCoordinated`

### 4.2 事件 → Node 推进规则（集中在 case-event）

| 事件 | 推进 Node | 规则说明 |
|---|---|---|
| PaymentConfirmed | PAYMENT_CONFIRM → DONE | 只认“确认到账”事实 |
| ScheduleConfirmed | SCHEDULE_CONFIRM → DONE | 只认“行程确认”事实 |
| ServiceCompleted | SERVICE_EXECUTE → DONE | 只认“服务完成”事实 |
| ReportDelivered | REPORT_DELIVER → DONE | 只认“报告交付”事实 |

### 4.3 事件流示意

```text
billing-gateway
   └─ PaymentConfirmed
        ↓
case-event
   └─ 完成 PAYMENT_CONFIRM Node
        ↓
case-timeline（追加记录事实）
```

## 5. Case 模板（体检/诊疗标准节点流程）

> 模板只定义“节点序列 + 节点语义”，不做条件分支；差异通过参数与外部事件驱动。

### 5.1 Case Node 标准状态（冻结）

- `PENDING`：等待外部事实事件
- `IN_PROGRESS`：允许人工推进的执行中（可选，尽量减少）
- `DONE`：已完成

### 5.2 模板：JP_CHECKUP（来日精密体检）

节点序列（冻结）：

1. `CASE_CREATE`（创建）
2. `PACKAGE_SELECT`（选择套餐）
3. `INTAKE_COLLECT`（资料收集）
4. `PAYMENT_CONFIRM`（付款确认）
5. `SCHEDULE_CONFIRM`（行程确认）
6. `SERVICE_EXECUTE`（服务执行）
7. `REPORT_DELIVER`（报告交付）
8. `CASE_CLOSE`（关闭/归档）

推进方式：
- `PACKAGE_SELECT` 由 `PackageSelected` 推进
- `PAYMENT_CONFIRM` 由 `PaymentConfirmed` 推进
- `SCHEDULE_CONFIRM` 由 `ScheduleConfirmed` 推进
- `SERVICE_EXECUTE` 由 `ServiceCompleted` 推进
- `REPORT_DELIVER` 由 `ReportDelivered` 推进

### 5.3 模板：JP_TREATMENT（来日诊疗：肿瘤/整形/生殖/康复统一模板）

节点序列（冻结）：

1. `CASE_CREATE`
2. `PACKAGE_SELECT`（选择产品/服务包：可为“诊疗协调包/翻译包/接送包”等）
3. `INTAKE_COLLECT`（资料收集）
4. `PAYMENT_CONFIRM`
5. `SCHEDULE_CONFIRM`
6. `SERVICE_EXECUTE`
7. `REPORT_DELIVER`（含说明会交付、术后/随访资料交付）
8. `CASE_CLOSE`

v2.1 约束：
- 不引入“诊疗评估/医疗建议”节点
- 不引入网关分支（例如“是否异常”）
- “异常/追加服务”通过新 Case 或新 Package 触发，而不是在一个 Case 内分支

### 5.4 Case Parameter（冻结字段集）

> 用于把模板变成可运行的订单：模板不携带业务细节，细节放在参数。

最小参数集合（示例）：

- `package_code`：产品编码（来自 plugin-service-package）
- `partner_id`：合作方（来自 plugin-partner-catalog，医院/机构等）
- `duration_days`：预计天数
- `preferred_language`：偏好语言（v2.1 不做多语言 UI，但参数保留）
- `price_range`：报价范围（字符串即可，v2.1 不做支付）

## 6. 数据模型冻结（仅到“原型级”）

### 6.1 核心表（v2.1 新增）

- `case`
- `case_parameter`
- `case_node`
- `case_schedule`
- `case_schedule_item`
- `case_timeline_event`

关键约束（冻结）：
- `case_timeline_event` **只允许 INSERT**（append-only），禁止 UPDATE/DELETE
- `case_schedule_item` 有状态；`case_schedule`（Day）无状态

### 6.2 通用化表名（替换 v2.0 医疗专用命名）

- `med_hospital` → `partner_catalog`
- `med_package` → `service_package`

说明：医疗只是“分类/视图”，不应固化在基础能力表名中。

## 7. 功能冻结清单（v2.1 范围内 / 范围外）

### 7.1 v2.1 范围内（必须交付）

- 多租户：共享库 + `tenant_id` + `X-Tenant-Id` 传递（沿用平台既有机制）
- 合作方目录（Partner）：新增/编辑/上下架/资质字段（JSON）
- 产品/套餐（Package）：新增/编辑/定价范围/关联 Partner
- Case：创建、绑定模板、参数维护、节点状态查询
- 事件流推进：订阅事实事件并推进 Node，写入 Timeline
- 行程：Day + Item，Item 状态推进、审计
- 文件中心：上传/下载/权限控制/审计日志（用于医疗资料隔离）
- 医疗资料收集：仅“收集任务 + 元数据 + 文件关联”，不解析内容
- 风控话术：模板管理、禁止词、使用记录（审计）
- 交付：报告/说明会交付记录（文件走 file-center）
- 通知：站内通知记录（不对接短信/邮件）

### 7.2 v2.1 范围外（明确不做）

- 任何形式的诊疗评估/医疗建议/病情分析
- 在线支付对接、自动对账、退款自动化（仅保留 `PaymentConfirmed` 事件入口，允许人工触发/录入）
- 电子签名、司法级合同链路
- 即时通讯/视频咨询
- AI 话术生成/AI 诊疗建议
- 流程网关、条件分支、流程回退编排（只做事件推进）
- 多语言 UI（保留参数，不做完整 i18n 交付）

## 8. 程序结构（代码组织/模块划分/边界）

> 目标：在现有 `plugin-host-web` 多模块工程内新增模块；插件是 Maven Module，部署按 Service 聚合。

### 8.1 Maven 模块结构（建议）

```text
plugin-host-web/
├─ platform-parent/
├─ platform-gateway/
├─ platform-auth-center/
├─ platform-plugin-api/
├─ platform-plugin-engine/
├─ plugins/
│  ├─ plugin-user/                     (已有)
│  ├─ plugin-cms/                      (已有)
│  ├─ plugin-file-center/              (新增)
│  ├─ plugin-notification/             (新增)
│  ├─ plugin-contract/                 (新增)
│  ├─ plugin-partner-catalog/          (新增)
│  ├─ plugin-service-package/          (新增)
│  ├─ plugin-medical-intake/           (新增)
│  ├─ plugin-appointment/              (新增)
│  ├─ plugin-medical-delivery/         (新增)
│  └─ plugin-risk-compliance/          (新增)
└─ services/
   ├─ case-service/                    (新增，合并部署)
   │  ├─ case-core/
   │  ├─ case-template/
   │  ├─ case-event/
   │  ├─ case-schedule/
   │  └─ case-timeline/
   ├─ platform-service/                (新增，合并部署)
   └─ medical-service/                 (新增，合并部署)
```

> 注：`plugins/` 与 `services/` 的目录是建议结构，用于表达“资产”与“部署”的分层；实际落地可按现有仓库风格调整，但**原则不变**。

### 8.2 Service 内部结构（每个 Spring Boot Service）

```text
<service>/
├─ src/main/java/
│  └─ com/shinwa/service/<name>/
│     ├─ api/            Controller（仅 DTO/Facade）
│     ├─ app/            Application Service（用例编排）
│     ├─ domain/         Entity/ValueObject/DomainService
│     ├─ infra/          Repository/Outbox/Kafka/DB
│     └─ support/        Tenant/Id/Clock/Audit
├─ src/main/resources/
│  ├─ db/migration/      Flyway
│  └─ application.yml
└─ pom.xml
```

### 8.3 服务边界（同步/异步）

- 同步（REST）：用于查询与管理类请求（Partner/Package/Case Query 等）
- 异步（Kafka）：用于事实事件驱动（PaymentConfirmed/ReportDelivered 等）
- 事件契约：
  - 必含：`tenant_id`, `case_id`, `event_type`, `occurred_at`, `payload`
  - schema 版本化：`schema_version`（v2.1 开始强制）

## 9. 风险控制清单（v2.1 必须落地的技术控制点）

- 文件隔离：医疗资料必须走 `plugin-file-center`，并具备访问审计
- 权限最小化：默认只允许“Case 相关角色”访问对应资料
- 禁止词与免责声明：
  - 禁止词命中必须记录审计
  - 模板使用必须落库，保留模板版本号（可追溯）
- Timeline 不可变：
  - 技术上禁止更新/删除（至少在应用层强制；推荐再加 DB trigger 防御）
- 事件一致性：
  - `case-event` 推进 Node 与写 Timeline 必须原子化（同事务/Outbox 模式）

```text
                              └────┬─────┘
                                   │
                     ┌─────────────┼─────────────┐
                     │             │             │
                     ▼             ▼             ▼
              ┌────────────┐ ┌──────────┐ ┌──────────┐
              │IN_PROGRESS │ │   DONE   │ │ SKIPPED  │
              └─────┬──────┘ └──────────┘ └──────────┘
                    │                          ▲
                    │                          │
                    └──────────────────────────┘
                         人工跳过（极少数场景）

    触发条件：
    ─────────
    PENDING → DONE       : 收到对应 Fact Event
    PENDING → IN_PROGRESS: 人工开始执行（仅 INTAKE_COLLECT、SERVICE_EXECUTE 允许）
    IN_PROGRESS → DONE   : 收到 Fact Event 或人工标记完成
    PENDING → SKIPPED    : 人工跳过（需审批 + 审计记录）
```

## 13. 技术细节与风险控制（必须落地）

### 13.1 事件一致性保障（Outbox 模式）

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                      Outbox 模式保障事件一致性                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  1. case-event 收到 PaymentConfirmed 事件                               │
│                                                                          │
│  2. 在同一个 DB 事务中：                                                  │
│     ├── UPDATE biz_case_node SET status='DONE' WHERE node_code='PAYMENT' │
│     ├── INSERT INTO biz_case_timeline_event (...)                        │
│     └── INSERT INTO outbox_event (topic, payload, ...)                   │
│                                                                          │
│  3. 事务提交成功                                                         │
│                                                                          │
│  4. Outbox Processor（后台线程/定时任务）：                               │
│     ├── SELECT * FROM outbox_event WHERE status='PENDING'                │
│     ├── 发送到 Kafka                                                     │
│     └── UPDATE outbox_event SET status='SENT'                            │
│                                                                          │
│  ⚠️ 关键：Node 更新 + Timeline 写入 + Outbox 写入 = 同一事务              │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 13.2 Timeline 不可变性保障

```text

│                      Timeline 不可变性保障                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  层级           措施                                                     │
│  ─────────────  ──────────────────────────────────────────────────────  │

│                                                                          │

│                                                                          │
```

```text
│                                                                          │
│  防御措施：                                                              │
│  ─────────                                                               │
│  • 所有业务表必须有 tenant_id 字段（脚手架强制生成）                      │
│  • 没有 tenant_id 的 SQL 直接报错（Interceptor 拦截）                    │
│  • 定期审计：扫描无 tenant_id 的数据行                                    │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 17.2 三种获取方式详解

#### 17.2.1 方案A：本地冗余副本 + 事件同步（推荐）

```text
场景：case-service 需要显示 Partner 名称
─────────────────────────────────────────────────────

❌ 错误做法：每次查询 Case 时同步调用 platform-service 获取 Partner 名称
   └── 问题：N+1 调用、platform-service 故障导致 case-service 不可用

✅ 正确做法：

  1. case-service 本地存储冗余字段
     ┌──────────────────────────────────────────────────────┐
     │  biz_case 表增加冗余字段：                           │
     │  • partner_id       BIGINT                          │
     │  • partner_name     VARCHAR(100)   ← 冗余副本       │
     │  • partner_code     VARCHAR(50)    ← 冗余副本       │
     └──────────────────────────────────────────────────────┘

  2. 事件同步机制
     ┌──────────────────────────────────────────────────────┐
     │  platform-service                                    │
     │     │                                                │
     │     │ 发布事件: PartnerUpdated                       │

     │     ▼                                                │

     │     ▼                                                │

     • 只冗余【展示字段】，不冗余【业务逻辑字段】
```

#### 17.2.2 方案B：同步调用（Feign/OpenFeign）

```text
场景：管理端查看 Case 详情，需要 Partner 完整信息（含资质）
─────────────────────────────────────────────────────────

适用条件：
• 低频操作（管理端查看详情，非列表）
• 需要完整/最新数据
• 可接受降级（Partner 服务不可用时返回 null）

实现规范：
─────────

1. 定义 API 模块（plugin-xxx-api）

   // plugin-partner-catalog-api 模块
   @FeignClient(
       name = "platform-service",
       path = "/api/v1/partners",
       fallbackFactory = PartnerApiFallback.class
   )
   public interface PartnerApi {
       @GetMapping("/{partnerId}")
       Result<PartnerDTO> getById(@PathVariable Long partnerId);
       
       @PostMapping("/batch")
       Result<List<PartnerDTO>> getByIds(@RequestBody List<Long> partnerIds);

2. 调用方依赖 API 模块

   <dependency>
       <groupId>com.shinwa</groupId>
       <artifactId>plugin-partner-catalog-api</artifactId>
   </dependency>

3. 必须实现 Fallback

   public class PartnerApiFallback implements FallbackFactory<PartnerApi> {
       @Override
       public PartnerApi create(Throwable cause) {
           return new PartnerApi() {
               @Override
               public Result<PartnerDTO> getById(Long partnerId) {
                   log.warn("Partner service unavailable, returning null", cause);
                   return Result.success(null);  // 降级返回 null
               }
           };
       }
   }

4. 调用方处理 null

   PartnerDTO partner = partnerApi.getById(partnerId).getData();
   if (partner == null) {
       caseDetail.setPartnerName("数据暂不可用");
   } else {
       caseDetail.setPartnerName(partner.getNameCn());
   }
```

**同步调用规范（冻结）**：

| 规则 | 说明 |
|------|------|

## 18. 分布式 ID 生成策略（必须冻结）

> **改动代价极高**：ID 策略一旦上线，后期几乎无法更改。

### 18.1 ID 生成策略选型

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| UUID | 无中心、简单 | 无序、索引差、暴露信息 | ❌ 不推荐 |
| 数据库自增 | 简单 | 分库分表困难、单点 | 单体应用 |
| **Snowflake** | 有序、高性能、分布式 | 时钟回拨问题 | ✅ 推荐 |
| 号段模式 | 减少 DB 压力 | 实现复杂 | 超高并发 |

**v2.1 决策**：采用 **Snowflake 变体**（基于 Seata/MyBatis-Plus 的实现）

### 18.2 Snowflake ID 结构（冻结）

### 18.4 业务编号生成规则（冻结）

> ID 是内部主键，业务编号是给用户看的。

| 业务对象 | 业务编号格式 | 示例 |
|---------|------------|------|
| Case | `{TEMPLATE}-{YYYYMMDD}-{SEQ}` | JP-CHECKUP-20260108-0001 |
| Partner | `P-{TYPE}-{SEQ}` | P-HOSPITAL-0001 |
| Package | `PKG-{TYPE}-{SEQ}` | PKG-CHECKUP-0001 |
| 文件 | `F-{YYYYMMDD}-{RANDOM6}` | F-20260108-A3B2C1 |

**业务编号生成器**：

```java
@Service
public class CaseNumberGenerator {
    private final RedisTemplate<String, String> redis;
    
    /**
     * 生成 Case 业务编号
     * 格式：JP-CHECKUP-20260108-0001
     */
    public String generate(String templateCode, String tenantId) {
        String date = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
        String key = "case:seq:" + tenantId + ":" + templateCode + ":" + date;
        
        Long seq = redis.opsForValue().increment(key);
        if (seq == 1) {
            redis.expire(key, 2, TimeUnit.DAYS);  // 2 天过期
        }
        
        return String.format("%s-%s-%04d", templateCode, date, seq);
    }
}
```

```java
/**
 * 分页请求（统一）
 */
public class PageRequest {
    private int page = 1;      // 页码，从 1 开始
    private int size = 20;     // 每页条数，默认 20，最大 100
    private String sort;       // 排序字段
    private String order;      // ASC / DESC
    
    public int getOffset() {
        return (page - 1) * size;
    }
}

/**
 * 分页响应（统一）
 */
public class PageResult<T> {
    private List<T> items;     // 数据列表
    private long total;        // 总条数
    private int page;          // 当前页码
    private int size;          // 每页条数
    private int totalPages;    // 总页数
    
    public static <T> PageResult<T> of(List<T> items, long total, PageRequest request) {
        PageResult<T> result = new PageResult<>();
        result.items = items;
        result.total = total;
        result.page = request.getPage();
        result.size = request.getSize();
        result.totalPages = (int) Math.ceil((double) total / request.getSize());
        return result;
    }
}
```

### 20.2 事件消费幂等（案例）

```java
/**
 * 事件消费幂等实现
 */
@Service
public class NodeProgressService {
    private final ProcessedEventRepository processedEventRepo;
    
    @Transactional
    public void handlePaymentConfirmed(PaymentConfirmedEvent event) {
        String eventId = event.getEventId();
        
        // 1. 幂等检查
        if (processedEventRepo.existsByEventId(eventId)) {
            log.info("Event already processed, skipping: {}", eventId);
            return;
        }
        
        // 2. 业务逻辑
        caseNodeRepository.updateStatus(
            event.getCaseId(), 
            "PAYMENT_CONFIRM", 
            NodeStatus.DONE
        );
        
        timelineRepository.append(
            event.getCaseId(),
            "PaymentConfirmed",
            event.getPayload()
        );
        
        // 3. 记录已处理（同一事务）
        processedEventRepo.save(new ProcessedEvent(eventId, Instant.now()));
    }
}

// 已处理事件表
CREATE TABLE processed_event (
    event_id    VARCHAR(50) PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL,
    -- 定期清理 30 天前的记录
    created_at  TIMESTAMP NOT NULL DEFAULT NOW()
);
```

```java
/**
 * 幂等 Token 机制（防止重复提交）
 */
@RestController
@RequestMapping("/api/v1/cases")
public class CaseController {
    
    // 1. 获取幂等 Token
    @GetMapping("/idempotent-token")
    public Result<String> getIdempotentToken() {
        String token = UUID.randomUUID().toString();
        redis.opsForValue().set(
            "idempotent:" + token, 
            "1", 
            5, TimeUnit.MINUTES
        );
        return Result.success(token);
    }
    
    // 2. 提交时校验 Token
    @PostMapping
    public Result<CaseDTO> createCase(
            @RequestHeader("X-Idempotent-Token") String token,
            @RequestBody CreateCaseRequest request) {
        
        // 原子删除 Token（只有第一次删除返回 true）
        Boolean deleted = redis.delete("idempotent:" + token);
        if (!Boolean.TRUE.equals(deleted)) {
            return Result.fail("999908", "请勿重复提交");
        }
        
        // 业务逻辑
        return Result.success(caseService.create(request));
    }
}
```

```java
    private static final Duration CACHE_TTL = Duration.ofMinutes(30);

     * 查询 Partner（带缓存）

    public PartnerDTO getById(String tenantId, Long partnerId) {

        // 3. 写缓存
        redis.opsForValue().set(key, dto, CACHE_TTL);
        
        return dto;
    }
```

| Schema 隔离 | ❌ 禁止 schema-per-tenant | v3+ 再评估 |
| 物理库拆分 | ❌ 禁止 db-per-tenant | v3+ 再评估 |
| Kafka Topic | 共享 Topic + `tenant_id` | 事件消息必须携带租户标识 |
| Redis Key | `{tenant}:{biz}:{id}` | 统一前缀规则，避免键冲突 |

**为什么必须现在冻结？**
- 一旦有第二个租户，所有表、缓存、事件、索引都会被迫改造
- 补救成本：全系统改造

### 22.2 数据生命周期 & 删除策略（医疗数据合规）

**冻结决策**：明确数据保留与删除原则

| 数据类型 | 保留策略 | 删除方式 |
|---------|---------|---------|
| Case Timeline | **永久保留**（法律事实） | 禁止删除 |
| 医疗文件（原始文件） | 可配置保留期（3/5/10年） | 物理删除 + 审计事件 |
| 医疗文件（metadata） | **永久保留** | 禁止删除 |
| 用户数据 | 按合规要求 | **逻辑删除 + 审计事件** |

**删除原则（冻结）**：
```text
删除 = 逻辑删除 + 审计事件
- 标记 deleted_at 时间戳
- 记录删除操作者、删除原因
- 保留可审计的删除记录
- 法律事实（Timeline）永不删除
```

**为什么必须现在冻结？**
- 医疗 & 跨境业务必然遇到：用户要求删除 vs 合规要求保留 vs 纠纷取证
- 不冻结原则，后期无法处理合规审计

### 22.3 权限模型粒度（RBAC 最小可行模型）

**冻结决策**：v2.1 冻结最小可行权限模型（未来可扩展为 ABAC）

```text
┌─────────────────────────────────────────────────────────────────┐
│                    v2.1 权限模型（冻结）                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  身份（User）                                                    │
│    └── 用户账号，唯一标识                                        │
│                                                                  │
│  角色（Role）                                                    │
│    ├── CUSTOMER_MANAGER（客户经理）                              │
│    ├── TRANSLATOR（翻译）                                        │
│    ├── PATIENT（患者）                                           │
│    └── ADMIN（管理员）                                           │
│                                                                  │
│  资源（Resource）                                                │
│    ├── Case（服务订单）                                          │
│    ├── File（文件）                                              │
│    └── Timeline（事实记录）                                      │
│                                                                  │
│  操作（Action）                                                  │
│    ├── READ（读取）                                              │
│    ├── WRITE（写入）                                             │
│    ├── COMMENT（评论/批注）                                      │
│    └── DELETE（删除，受限）                                      │
│                                                                  │
│  权限规则示例：                                                  │
│    CUSTOMER_MANAGER + Case + WRITE = 可编辑 Case                 │
│    PATIENT + Case + READ = 只读自己的 Case                       │
│    TRANSLATOR + File + READ = 可读取关联 Case 的文件             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**数据模型（冻结）**：

```sql
-- 角色表
CREATE TABLE sys_role (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    role_code       VARCHAR(50) NOT NULL,
    role_name       VARCHAR(100) NOT NULL,
    description     TEXT,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_role_code UNIQUE (tenant_id, role_code)
);

-- 用户角色关联表
CREATE TABLE sys_user_role (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    user_id         BIGINT NOT NULL,
    role_id         BIGINT NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_user_role UNIQUE (tenant_id, user_id, role_id)
);

-- 角色权限表
CREATE TABLE sys_role_permission (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    role_id         BIGINT NOT NULL,
    resource_type   VARCHAR(50) NOT NULL,    -- Case/File/Timeline
    action          VARCHAR(20) NOT NULL,    -- READ/WRITE/COMMENT/DELETE
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_role_permission UNIQUE (tenant_id, role_id, resource_type, action)
);
```

**为什么必须现在冻结？**
- 一旦角色扩展（医院、第三方）或涉及跨 Case 协作、审计
- "补权限模型"几乎必然是全系统改造

### 22.4 事件 Schema 版本演进策略

**冻结决策**：事件只允许向后兼容演进

```text
┌─────────────────────────────────────────────────────────────────┐
│                 事件 Schema 演进规则（冻结）                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ✅ 允许的变更：                                                 │
│    • 新增 optional 字段（消费者忽略未知字段）                    │
│    • 扩展枚举值（新增值，旧消费者按 UNKNOWN 处理）               │
│                                                                  │
│  ❌ 禁止的变更：                                                 │
│    • 删除字段 → 必须创建新事件类型                               │
│    • 修改字段类型 → 必须创建新事件类型                           │
│    • 重命名字段 → 必须创建新事件类型                             │
│                                                                  │
│  版本管理：                                                      │
│    • 所有事件必须包含 schema_version 字段                        │
│    • 消费者必须能处理未知的 schema_version（降级/跳过）          │
│    • 重大变更 = 新事件类型（如 PaymentConfirmedV2）              │
│                                                                  │
│  消费者容错：                                                    │
│    • 未知字段：忽略                                              │
│    • 未知 schema_version：记录日志 + 按最新已知版本处理          │
│    • 解析失败：进入死信队列（DLQ）                               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**事件结构示例（冻结）**：

```json
{
  "event_id": "evt_20260109_xxxx",
  "event_type": "PaymentConfirmed",
  "schema_version": "1.0",
  "tenant_id": 1001,
  "case_id": 123456,
  "occurred_at": "2026-01-09T10:30:00Z",
  "payload": {
    "payment_id": "pay_xxxx",
    "amount": 50000,
    "currency": "JPY"
  }
}
```

### 22.5 业务级指标（可观测性）

**冻结决策**：所有 Case Node 必须可统计进入/完成时间

| 指标类型 | 说明 | 采集方式 |
|---------|------|---------|
| Node 进入时间 | 节点状态变为 PENDING/IN_PROGRESS 的时间 | `biz_case_node.started_at` |
| Node 完成时间 | 节点状态变为 DONE 的时间 | `biz_case_node.completed_at` |
| Node 停留时长 | 完成时间 - 进入时间 | 计算字段 |
| Case SLA | 创建到关闭的总时长 | 计算字段 |
| 异常率 | 超时/跳过/失败的节点比例 | 聚合统计 |

**补充 DDL（`biz_case_node` 表增加字段）**：

```sql
-- 在 biz_case_node 表增加时间统计字段
ALTER TABLE biz_case_node ADD COLUMN started_at TIMESTAMP;
ALTER TABLE biz_case_node ADD COLUMN completed_at TIMESTAMP;

-- 索引优化（按时间范围查询）
CREATE INDEX idx_case_node_started ON biz_case_node(tenant_id, started_at);
CREATE INDEX idx_case_node_completed ON biz_case_node(tenant_id, completed_at);
```

**为什么必须现在冻结？**
- 后期补时间字段 = 全量数据无历史记录
- SLA 监控、运营分析依赖这些数据

### 22.6 国际化 / 时区策略

**冻结决策**：存储统一 UTC，展示按用户时区

```text
┌─────────────────────────────────────────────────────────────────┐
│                    时区策略（冻结）                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  存储层：                                                        │
│    • 所有 TIMESTAMP 字段存储 UTC 时间                            │
│    • 数据库时区设置为 UTC                                        │
│    • 示例：2026-01-09T01:30:00Z（UTC）                          │
│                                                                  │
│  API 层：                                                        │
│    • 请求/响应统一使用 ISO 8601 格式（带时区）                   │
│    • 示例：2026-01-09T10:30:00+09:00（JST）                     │
│                                                                  │
│  展示层：                                                        │
│    • 按用户偏好时区展示                                          │
│    • 用户偏好存储在 user_preference 表                           │
│    • 默认时区：Asia/Tokyo（业务主要在日本）                      │
│                                                                  │
│  用户偏好字段：                                                  │
│    • user_preference.timezone = 'Asia/Tokyo'                    │
│    • user_preference.locale = 'ja-JP'                           │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**用户偏好表（冻结）**：

```sql
CREATE TABLE user_preference (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    user_id         BIGINT NOT NULL,
    timezone        VARCHAR(50) NOT NULL DEFAULT 'Asia/Tokyo',
    locale          VARCHAR(20) NOT NULL DEFAULT 'ja-JP',
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_user_pref UNIQUE (tenant_id, user_id)
);
```

**为什么必须现在冻结？**
- 业务涉及日本、中国等多时区
- 不统一策略，后期展示混乱、数据对不上

### 22.7 冻结决策清单汇总

| 序号 | 决策项 | 冻结内容 | 影响范围 |
|------|-------|---------|---------|
| 1 | 多租户隔离 | 逻辑隔离 + tenant_id | 全系统 |
| 2 | 数据生命周期 | 逻辑删除 + 审计 + Timeline 永久 | 存储/合规 |
| 3 | 权限模型 | RBAC（User-Role-Resource-Action） | 安全/访问控制 |
| 4 | 事件演进 | 只允许向后兼容 | 事件驱动架构 |
| 5 | 业务指标 | Node 必须有 started_at/completed_at | 可观测性 |
| 6 | 时区策略 | 存储 UTC，展示按用户偏好 | 国际化 |
| 7 | **合同不做电子签名** | v2.1 仅基础合同管理，电子签名 v3+ 评估 | 合同插件 |
| 8 | **合同签署后不可变** | 已签合同禁止修改，变更须新建版本并重签 | 合同插件/合规 |
| 9 | **合同事件不驱动 Case** | ContractSigned 仅作为事实，不直接推进 Case 节点 | 事件解耦 |

> ⚠️ 以上决策一旦冻结，变更成本极高。v2.1 开发过程中如需调整，必须经过架构评审。
