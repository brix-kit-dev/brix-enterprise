## A. 执行结论

### 裁决：**不建议冻结**

| 指标 | 结论 |
|---|---|
| P0 冻结阻断项 | **16** |
| P1 冻结前应修改项 | **22** |
| P2 冻结后可演进项 | **8** |
| 总体成熟度 | **63 / 100** |
| 达到“国际大厂最佳实践的最小实现” | **否** |

结论不是“大方向过时”。模块化单体、Ports & Adapters、契约化插件、Outbox、可观测和前端运行时治理仍然成立。不能冻结的原因是：权威关系、Host 装配、生命周期、Command/Event、可靠消息、持久化、异常、版本兼容、第三方信任和机器化证明尚未形成唯一且可验证的答案。

v3.0.10 MUST 保留为历史，不应静默覆盖。由于修订改变分层、生命周期、通信、Capability、红线和文档权威，已另行产出 `v3.0.11-运行壳架构设计蓝图（Freeze Candidate）.md`。v3.0.11 在专项文档同步、机器基线校验和委员会批准前仍不是活动根基线。

## B. 根基线权威关系

| 层级 | 文档/载体 | 权威范围 | 是否可覆盖上级 | 冲突处理 |
|---|---|---|---|---|
| 1 | 活动 Root Architecture Baseline | 全平台共享术语、分层、契约、边界和 A/S 红线 | 不适用 | 最高权威 |
| 2 | 活动专项蓝图 | 专项独有规则与对根规则的收紧 | 否 | 根已定义则根优先；根沉默才由专项裁决 |
| 3 | 已批准且被蓝图登记的 RFC/ADR | 单一变更决策 | 否 | 必须先回写上位蓝图才成为长期规范 |
| 4 | 开发计划、任务、AI Prompt、脚手架 | 实施顺序/操作 | 否 | 冲突即失效，禁止执行 |
| 5 | 代码、配置、测试、CI | 某提交的实现与合规证据 | 否 | 记为实现偏差，不反向改架构 |
| 6 | README、示例、业务方案 | 导航/验证/说明 | 否 | 只能指向活动基线 |
| 7 | Archived/Superseded | 历史追溯 | 否 | 禁止指导开发、AI 或 CI |

可直接写入根蓝图的规范原文：

> Brix 只有一个活动 Root Architecture Baseline。专项蓝图只在根蓝图未定义的专项范围内补充规则，或增加更严格的约束；专项蓝图 MUST NOT 放宽、重定义或覆盖根蓝图。开发计划、代码、测试、README、AI Prompt 和脚手架 MUST 服从活动蓝图，且 MUST NOT 创造架构决策。发生冲突时 MUST 停止实现，登记冲突并修订较低层文档；若确需改变根级概念，MUST 先批准并发布新的根蓝图版本。历史文档没有规范效力。

状态必须分为 `Draft`、`Freeze Candidate`、`Architecture Frozen`、`Implementation Accepted`、`GA`、`Superseded/Archived`。`Blueprint` 是文档类型，不是状态；Architecture Frozen 不等待实现完成，但要求决策闭合且每个 MUST 有验证方式。

## E. 2026 架构趋势评估

核验基准日为 2026-07-22。这里区分“模式仍有效”和“Brix 是否应全局强制”；流行并不自动等于适用。

| 设计理念 | 2026 状态 | Brix 匹配度 | 是否过时 | 是否过度设计 | 保留/调整/删除 | 依据与裁决 |
|---|---|---:|---|---|---|---|
| Modular Monolith | 主流实践 | 高 | 否 | 否 | **保留** | Spring Modulith 当前稳定文档仍正式提供模块 API、无环依赖和结构验证；Brix 当前比提前拆微服务更适合模块化单体。[官方验证文档](https://docs.spring.io/spring-modulith/reference/verification.html) |
| Plugin Architecture | 场景型主流 | 高 | 否 | 若承诺热卸载则是 | **调整** | 保留 Manifest、组合和逻辑生命周期；单 ClassLoader 不是版本、安全或资源隔离单元。JLS 规定 defining ClassLoader 可回收才可能卸载类。[JLS §12.7](https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html) |
| Hexagonal / Clean | 长期稳定原则 | 高 | 否 | 强制所有插件六段物理拆分可能是 | **保留原则、简化形态** | 冻结依赖向内、Port/Adapter、基础设施隔离；只强制 api/core/server，其他模块按需。 |
| Event-Driven Architecture | 场景型主流 | 中高 | 否 | 全局事件化是 | **调整** | 事件只表达已发生事实、扇出和时间解耦；写意图使用 Command。EDA 官方指南也明确最终一致、顺序、幂等和运维成本。[Microsoft EDA](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven) |
| Event Sourcing | 专用模式 | 低到中 | 否 | 作为平台默认明显是 | **不作为默认** | 仅在审计回放、时间建模等收益足以覆盖迁移、版本和投影成本时由领域 ADR 引入；根蓝图不得暗示全平台采用。 |
| Transactional Outbox | 主流可靠消息实践 | 高 | 否 | 否 | **保留并收紧** | 正确语义是业务状态与 outbox record 同一数据库事务，relay 提交后发送且可能重复；因此 Consumer 必须幂等。[Debezium Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) |
| CQRS | 场景型模式 | 中 | 否 | 全平台物化读模型是 | **调整** | typed Query 不等于 CQRS；默认可读 Owner 自有权威存储，读写扩展或聚合复杂度有证据时才投影。[Microsoft CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) |
| 微前端 | 场景型主流 | 中高 | 否 | 单团队/单发布列车可能是 | **按独立部署证据采用** | Brix 动态 UI 插件适合；简单组合场景优先构建期集成。 |
| Module Federation | 有效实现机制 | 中 | 否 | 全 UI 强制可能是 | **下沉前端专项** | 根只冻结运行时唯一性、兼容和安全不变量；`singleton` 仅限制同一 share scope，仍需 `strictVersion`、统一 scope 和产物/运行时验证。[Webpack 官方文档](https://webpack.js.org/plugins/module-federation-plugin/) |
| OpenTelemetry | 主流标准 | 高 | 否 | 否 | **保留并可测试化** | 使用 W3C Context 传播，插件不初始化 SDK；门禁检查 inject/extract、span/metric 行为，不使用含糊“覆盖率”。[OTel Context](https://opentelemetry.io/docs/concepts/context-propagation/) |
| OAuth 2.0 / OIDC | 主流安全标准 | 高 | 否 | 否 | **补全现代基线** | 使用 OIDC 与 Authorization Code + PKCE；禁 ROPC，避免 Implicit，精确 redirect URI，校验 issuer/audience/nonce，并处理 refresh token 轮换/绑定。[OIDC Core](https://openid.net/specs/openid-connect-core-1_0-35.html)、[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) |
| SBOM / SLSA / 制品签名 | 主流供应链基线 | 高 | 否 | 否 | **新增** | 每个 Host/Plugin/Remote 生成与 digest 绑定的 SPDX 或 CycloneDX SBOM、签名和 provenance；以 SLSA v1.2 Build L2-compatible 起步。[SPDX](https://spdx.dev/use/specifications/)、[CycloneDX](https://cyclonedx.org/specification/overview/)、[SLSA v1.2](https://slsa.dev/spec/v1.2/) |
| 云原生可运维性 | 主流实践 | 高 | 否 | 将云原生等同微服务/Service Mesh才是 | **保留最小运行契约** | readiness 摘流、liveness 只处理不可恢复故障，另有 startup/drain/timeout/resource budget。[Kubernetes Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-probes/) |
| Zero Trust | 稳定安全原则 | 高 | 否 | 否 | **新增边界声明** | 不因网络位置或“官方插件”隐式信任；但同 JVM 规则只是治理，不是恶意代码沙箱。[NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final) |
| Java checked exception | 语言机制仍存在 | 中 | 否 | 在统一 SPI 全面采用成本过高 | **选择 unchecked** | Spring 默认只对 RuntimeException/Error 回滚；checked 方案需要所有 SPI/AOP/事务显式配套。[Spring 回滚规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)、[JLS 11](https://docs.oracle.com/javase/specs/jls/se25/html/jls-11.html) |

**趋势总判定**：Brix 的核心理念没有过时，也不需要为“追潮流”改成微服务、OSGi、Service Mesh 或全面 Event Sourcing。当前最需要现代化的是可信制品供应链、OAuth/OIDC 安全下限、标准上下文传播，以及对“逻辑隔离”和“硬隔离”的诚实表述。

## F. 红线可执行性矩阵

状态定义：**完整**表示主分支必跑、覆盖全部适用模块、存在故意违规负向样例且不能被局部配置绕开；**部分/名义**都不能作为冻结证据。审计结论是：当前 A-1～A-23、S-1～S-9 **没有一条形成完整证据闭环**，而 §10.4 对现有工具和覆盖范围的描述显著高于事实。

| 红线 | 规范是否明确 | 当前校验方式/证据 | 是否真正可机器化 | 漏洞或旁路 | 建议最低门禁 |

| A-1 插件不依赖基础设施 | 部分；Controller 规则混入未来 Endpoint | `PluginProfile`、企业 workflow grep、Solutions Enforcer 均只覆盖一部分 | **部分** | ArchUnit 多数只看 `*-core`；包谓词与真实包错位；server/api 不入图；Kafka 黑名单 artifact 过时 | 全 reactor 字节码+依赖图扫描；覆盖 api/core/server；真实 artifact catalog；每类违规均有负向 fixture |
| A-2 不绕过 Shell | 边界明确，但 ExternalHttp 目标范围未定义 | core 的 HTTP/middleware 规则 | **部分** | server/api 和 JDBC 未扫；`HttpCapability` 接受任意 URL，可借内部 service URL 旁路 | bytecode + dependency gate；ExternalHttp manifest allowlist；运行时拒绝 Brix 内部 service ID；负向集成测试 |

| A-8 数据所有权 | 原则明确，平台受托表例外未闭合 | 跨插件 import grep；`DataOwnershipRule` 为 always-pass | **名义** | 无 schema lint；现有 identity migration 对平台表建跨域 FK；所有插件未独立 schema | 机器 ownership registry + DDL AST lint；禁止跨 Owner FK/写；Outbox relay 权限作为显式最小例外 |

| A-12 OSS 不依赖商业层 | 明确 | 根 Enforcer 只校验 Java/Maven 版本；部分 SDK ArchUnit | **否** | 无全局 bannedDependencies；真实包前缀与谓词不符；新增 POM 依赖可绕过 | 开源 reactor 的 Maven/Gradle/npm 全依赖图 deny enterprise 坐标与包；源码/字节码双检 |

| A-14 模块边界与命名 | 与“六段推荐”冲突 | 只有脚手架惯例 | **否** | 手工模块、改 artifactId/包名即可绕过 | Manifest `moduleKind` 为权威；reactor 校验 artifact/package/owner/layer；生成器也必须通过同一 validator |
| A-15 迁移单调性 | 大体明确；“rollback 说明”流程未定义 | 租户单点测试，不是全仓 Flyway lint | **否** | 不查已发布脚本 hash、版本回溯或重复；无 registry | 记录已发布 migration checksum；Git diff + Flyway 版本/重复/Owner lint；采用 forward-fix 并定义例外审批 |

| S-6 入参与反序列化 | 明确 | 无全入口 `@Valid` 或 Jackson lint | **否** | 示例合规不代表全仓；Properties 模板也无 `@Validated` | Controller/consumer DTO inventory；危险 ObjectMapper 配置 deny；反序列化/fuzz 负向测试 |
| S-7 许可证白名单 | 明确 | PR dependency-review 仅拒 GPL-3.0/AGPL-3.0 | **部分** | 不是完整 allowlist；非 PR、前端锁文件、传递依赖和商业仓未全覆盖 | 后端/前端/SBOM 全依赖许可证策略；未知/多许可证人工审批；主分支和发布均阻断 |
| S-8 高危 CVE | 阈值基本明确，例外时限未定义 | 企业 Maven OWASP CVSS≥7；PR dependency review；OSS 有 pnpm audit | **部分** | 企业前端没有等价 pnpm 门禁；只看增量；suppression 可永久化 | 所有制品/锁文件持续扫描；VEX/例外有 Owner、理由、到期日；发布时以 SBOM 再验 |
| S-9 身份代理 | 要求清楚，但与现有公开 ViewMode 模型冲突 | 无 `ImpersonationCapability`、internal-only Guard 或 fail-closed interceptor | **否** | 公开 `ViewModeCapability` 可切 tenant view，缺理由/期限/授权来源/Trace 字段 | 特权端口仅 internal artifact；请求必须含授权来源、理由、期限、tenant、trace；运行期 fail-closed + 不可篡改审计 |

横向旁路同样构成冻结阻断：

- 根 `architecture-check.yml` 并不执行 Maven tests/verify；ArchUnit 只在另一条 PR-only workflow 间接运行。嵌套在 package 下的 `.github/workflows` 不是仓库 Actions 入口，不能计作门禁。
- `architecture-guard` 自身缺完整测试 engine 和规则负向样例，规则数量在文档/模板中漂移；“有一个 Java 类”不能证明规则有效。
- 脚手架仍生成旧 `RuntimeContext + Spring @Service`、无 apiVersion 的 `module-manifest.yaml`、无 `@Validated` Properties，且不生成 BrixPlugin/ServiceLoader；即使人工新代码合规，模板仍会持续制造偏差。
- v3.0.11 新增 S-10（SBOM/签名/provenance）与 S-11（不可信代码隔离）目前也应登记为 `missing-blocking`，实现前不得标为 Enforced。

### G.2 下游同步顺序

1. 先批准 v3.0.11 的概念裁决和机器元数据，不直接修改 v3.0.10 历史原文。
2. 发布前端专项新补丁版：统一 `Page/View → Hook(ViewModel) → Repository → Capability`；冻结 MF shared 的 `singleton + strictVersion + shareScope + requiredVersion` 及运行时身份测试。
3. 发布超管 v2.1：上位根版本改为 v3.0.11；采用平台/租户审计分表；JWT 永不携带 bypass；修正 peer dependency 与页面清单。
4. 修订租户蓝图及落地计划：T-1～T-28；Event Envelope 继承根 Schema；配额在首次 OWNER 激活时占用；`invitation_purpose` 单一命名；计划不得自行创造 `AuthorizationCapability` 或 PRINCIPAL 邀请。
5. 将 AI Prompt 明确降为非规范生成物，删除“以提示词最新裁决为准”；修正 `/login`、`authz_version` 等旧协议。
6. 重写或归档 `docs-dev/开发者指南-运行壳平台系统.md`；活动 README、评审提示、模板、CI 全部切到新注册表。活动路径出现 v3.0.9 引用即失败，Archived/CHANGELOG/迁移记录除外。
7. 最后迁移代码和模板：先做一个端到端垂直切片，再扩散到全部插件；禁止同时维持两套生命周期 SSoT。

### G.3 当前实现与蓝图的主要偏差

| 领域 | 当前证据 | 冻结后的正确处理 |
|---|---|---|
| 生命周期 | 主链仍以 `RuntimeContext`、Spring Component/AutoConfiguration、旧模块抽象为主；未检出完整 `BrixPlugin/PluginContext` 主链 | 代码记为 implementation deviation；先迁一条插件垂直切片，脚手架与示例随后切换 |
| Registry 分层 | `CapabilityRegistry` 当前位于可公开依赖的 `runtime-sdk-api` 并暴露 register/get | 拆为 L2B internal registry；插件只通过 `PluginContext` consume，不得 register |
| 异常 | 现有异常以 `RuntimeException` 为主，但没有冻结的 `BrixException/errorCode` 体系 | 沿 unchecked 方向统一，不反向选择 checked |
| Manifest | 当前 JSON Schema 与模板字段、路径和 v3.0.10 YAML 约定不一致；商业后端未形成统一 manifest 主链 | 发布唯一 YAML v1 Schema、兼容迁移器和启动/CI 双验证；禁止两套声明 SSoT |
| Query/Command | 未检出蓝图声称的 typed query codegen，也没有统一 Command 契约 | 先实现 Contract artifact、codegen 和一个 provider/consumer；旧内部 HTTP 逐条迁移 |
| Guard/CI | 已有部分 architecture guard、依赖/CVE/许可证检查，但诸多蓝图坐标和规则未检出 | 使用机器注册表区分 `required/implemented/enforced`；缺失门禁不得标绿 |
| 供应链 | 未形成逐 Host/Plugin/Remote 的 SBOM、签名、provenance 验证闭环 | 新增 S-10/S-11，先达到可验证的 L2-compatible 最小实现 |

### G.4 医疗行业场景反证

归档医疗中介方案验证了“行业中立根能力 + 行业插件 + Service 组合”的方向：文件、通知、规则、Outbox、本地读模型、ACL 和租户隔离都能承载真实医疗流程，说明主架构不是纸面抽象。

同时必须修正四类反模式：

- Feign/内部 HTTP 写调用迁移为 typed Query/Command；业务事实才发布 Integration Event。
- 插件直接 Kafka、数据库和基础设施 SDK 必须通过 Capability/Adapter 收口。
- WebView/Remote JS 不得获得原始 bearer token；Host 提供 origin allowlist 和带认证请求桥。不可信前端使用独立 origin + sandboxed iframe。
- `plugin-file-center`、`plugin-notification` 拥有业务元数据、策略、模板和历史；Storage/Notification Capability 只提供基础设施传输原语，避免能力层吞掉领域。

### G.5 再次申请冻结的准入条件

以下条件缺一不可：

1. 16 个 P0 全部关闭，并由架构委员会记录裁决。
2. v3.0.11 及所有活动专项通过 authority/version/link/redline registry 校验。
3. A/S 每条红线都有 `implemented` 或显式 `missing-blocking` 状态；不得用文档存在冒充 CI 证据。
4. 至少一个插件完成 Manifest → discovery → resolve → start → Query/Command/Event → stop 的端到端垂直切片及失败路径测试。
5. STANDARD/CRITICAL Outbox + Inbox 幂等、required consumer readiness、Profile capability range、MF shared 和 OIDC 安全下限有契约测试。
6. 活动资料不再引用 v3.0.9；v3.0.10 标为 Superseded 但保持可追溯 hash。
7. 供应链最小门禁生成并验证 SBOM、digest、签名和 provenance。
