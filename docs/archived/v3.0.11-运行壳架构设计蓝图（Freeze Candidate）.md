# Brix Platform v3.0.11：运行壳（Runtime Shell）架构设计蓝图（Freeze Candidate）

> **版本**：v3.0.11  
> **日期**：2026-07-22  
> **状态**：Freeze Candidate（未获架构委员会批准前不构成活动基线）  
> **拟替代**：v3.0.10（仅在本文转为 Architecture Frozen 后生效）  
> **作者**：Brix Platform Architecture Team  

本文使用 RFC 2119 / RFC 8174 关键词：**MUST / MUST NOT** 表示强制，**SHOULD / SHOULD NOT** 表示偏离时 MUST 说明理由，**MAY** 表示可选。示例、说明和路线图不产生规范效力。

## 0. 文档效力、目标与边界

### 0.1 根蓝图目标

本蓝图只冻结以下平台级不变量：

1. Runtime Shell 的组成、分层和依赖方向；
2. Capability、Plugin、Host、Adapter、Composition 的稳定边界；
3. 跨插件查询、命令、事件和外部 HTTP 的唯一语义；
4. 数据所有权、事务、迁移、可靠消息和兼容性规则；
5. 前端共享运行时的最小边界；
6. 安全、可观测性、故障隔离和软件供应链底线；
7. 全局红线及其必需的验证门禁；
8. 根蓝图、专项蓝图、实施计划、代码和历史材料的单向权威关系。

目标是让同一插件可在符合契约的不同 Host Profile 中被**静态组装、启动期选择和运行期单向逻辑停机**，并让架构规则能够被 CI、启动校验、契约测试或显式人工审批验证。

### 0.2 非目标

本蓝图明确不承诺：

- 运行期下载、安装、升级或卸载 Java JAR；
- 单 JVM 内的安全沙箱、内存隔离、类冲突隔离或进程级故障隔离；
- 分布式事务、全局强一致、Exactly Once 或全局消息顺序；
- 将所有模块拆成微服务、将所有读写都实施为物理 CQRS，或强制使用微前端；
- 具体数据库、消息中间件、云厂商、区域拓扑和容量参数；
- 行业模型、商业许可、价格、客户分类和售卖策略；
- 代替专项蓝图定义多租户、超管、HA/DR 等领域规则。

如需求需要不可信代码执行、强资源隔离或独立扩缩容，后端 MUST 使用独立进程/容器，前端 MUST 使用独立 origin/iframe 等浏览器隔离，而不是扩大单 ClassLoader 或同一 JS 权限域的承诺。

### 0.3 适用范围

本蓝图适用于：

- Brix 官方、商业和经准入认证的第三方后端插件；
- Brix Web / Mobile UI 插件；
- Standalone、Embedded、Local Host Profile；
- 开源仓和商业仓之间的公共契约、装配和治理。

第三方插件与官方插件 MUST 满足相同的运行时、安全和数据边界。差异 MUST 仅限于准入流程：内部插件通过组织 CI，外部插件通过签名、SBOM、兼容性测试和认证门禁。未经信任的第三方代码 MUST 进程隔离；未经信任的 Web UI MUST 使用独立 origin / iframe 等浏览器隔离。

## 1. 稳定设计原则

| ID | 原则 | 规范含义 |
|---|---|---|
| P-1 | Contract First | 插件 MUST 只通过平台 Capability Contract 和显式版本化的插件公共契约跨边界协作，MUST NOT 依赖实现 |
| P-2 | 声明与代码各司其职 | Manifest 是依赖、路由和策略的权威声明；业务处理逻辑写在代码中，二者 MUST 双向一致 |
| P-3 | 基础设施隔离 | 插件 MUST NOT 持有驱动、连接、客户端或中间件 SDK；L2C Adapter 是基础设施入口 |
| P-4 | 静态组合、极薄 Host | Host 是构建/部署期组装点；业务逻辑和 Capability 实现 MUST NOT 位于 Host |
| P-5 | 所有权与消息语义优先 | Query 是只读请求，Command 是定向意图，Integration Event 是已发生事实；三者 MUST NOT 互相伪装 |
| P-6 | 前端边界稳定 | View → ViewModel → Repository 是统一逻辑模型；UI Host 提供唯一共享运行时 |
| P-7 | 安全与可观测性内建 | 身份、授权、Trace、结构化日志、指标、数据分类和审计 MUST 在边界统一执行 |
| P-8 | 兼容演进 | 公共契约 MUST 遵循 SemVer、弃用期和兼容性门禁；破坏性变更 MUST 仅进入新 Major |
| P-9 | 开源/商业单向依赖 | OSS MUST NOT 依赖商业代码；商业代码 MAY 依赖已发布 OSS 契约和实现 |
| P-10 | 诚实的隔离承诺 | 单 ClassLoader 只提供逻辑边界；需要安全/资源硬隔离的负载 MUST 跨进程部署 |

## 2. 术语与唯一含义

| 术语 | 唯一定义 |
|---|---|
| Runtime Shell | L2A Capability Contract、L2B Runtime 和 L2C Adapter 的整体架构；不是独立进程的同义词 |
| Capability Contract | L2A 中插件可依赖的稳定接口、DTO、注解和错误码；不包含 Registry、Gateway 或实现 |
| Capability Catalog | 与 L2A/BOM 一起版本化发布的机器文件，登记 Capability ID、contractVersion、bindingKind 和 Provider range；本基线不引入运行期网络目录服务 |
| Contract Schema Registry | Git/制品库中的版本化 Query/Command/Event/Manifest Schema 构建资产；本基线不引入运行期网络 Schema Registry 服务 |
| Capability Runtime | L2B 中负责发现、解析、注入、路由、生命周期和横切策略的内部实现 |
| Adapter | L2C 中对数据库、消息、HTTP、对象存储、身份提供方等基础设施的实现 |
| Plugin | 拥有业务规则、写模型和数据的最小可组合业务单元 |
| Plugin Public Contract | 插件发布的 Query / Command / Event Schema 及生成的客户端；属于 L1 公共切面，不属于平台 L2A |
| Host | 选择并打包 Runtime、Adapter 和 Plugin 的静态组装壳 |
| Host Profile | Host 提供的 Capability 集、版本、质量和安全等级声明 |
| Composition | 一组 required / optional 插件和能力约束的部署组合；不是商业许可模型 |
| Query | 无副作用的只读请求，可成功、未找到或失败 |
| Command | 指定唯一逻辑处理方的业务意图；跨插件 Command 为异步可靠消息 |
| Integration Event | 发布方已经提交的、使用过去式命名的业务事实；不要求特定订阅方执行动作 |
| Domain Event | 单插件内部事件；不构成跨插件契约 |
| Logical Stop | 从路由/订阅中摘除并释放受管资源；不代表类卸载或内存安全隔离 |
| Readiness | 当前是否可接收新流量的可变条件，不是生命周期状态 |
| Data Owner | 对数据语义、Schema、迁移、写入规则和生命周期负最终责任的唯一插件/平台模块 |
| Data Custodian | 经 Owner 显式授权，MUST 仅对已登记的受托运行表/Schema 执行获批 DML 或 migration DDL 的平台服务；不是业务数据共同 Owner |

## 3. 分层、依赖与装配

### 3.1 分层模型

```text
L4  Composition / Product Catalog
              │ assembly selection
L3  Host Assembly
      ├──── packages ────▶ L1 Plugin artifacts
      ├──── packages ────▶ L2B Runtime
      └──── packages ────▶ L2C Adapter

L1  Plugin ───── compile-time ─────▶ L2A Capability Contract
 │       └──── generated contract ─▶ other plugin public schemas only
 │
L2B Runtime ─── compile-time ──────▶ L2A
L2C Adapter ─── compile-time ──────▶ L2A + L0 Infrastructure SDK
L0  Infrastructure
```

层级编号表示职责，并不声称所有箭头只能从高到低。实现与评审 MUST 区分**源码依赖**和**组装依赖**：Host 的 POM/包清单 MUST 依赖待打包的 Runtime、Adapter 和 Plugin，但 Host 源码 MUST NOT 实现或导入它们的业务类型。

### 3.2 依赖白名单与黑名单

| 层 | 源码 MAY 依赖 | 源码 MUST NOT 依赖 | 组装职责 |
|---|---|---|---|
| L4 Composition | Manifest Schema | 实现类、业务源码 | 选择 Host Profile、插件和能力约束 |
| L3 Host | L2B 提供的唯一 bootstrap API | L1 业务类型、L0 SDK、Adapter 实现类型 | MUST 打包 L2B、L2C、选定 L1 及运维组件 |
| L2C Adapter | L2A、对应 L0 SDK | L1、L3、L4 | 实现 Capability 并声明版本/质量 |
| L2B Runtime | L2A | 任何具体 L1 插件、L3、L4 | 发现、解析、路由、生命周期、横切策略 |
| L2A Contract | JDK/语言标准库和最小注解 API | L1、L2B、L2C、L3、L0 实现 | 发布稳定插件入口契约 |
| L1 Plugin | L2A、自身模块、生成的公共契约 | L2B、L2C、L0 SDK、其他插件 core/server | 拥有业务行为和数据 |

插件消费另一个插件的 generated contract artifact 不等于允许直接调用。生成物 MUST 只含 Schema 派生 DTO/客户端接口，不含 provider 实现。

### 3.3 Runtime Shell 三部分

- **L2A** MUST NOT 包含 Provider、Runtime 或基础设施实现；为二进制兼容提供的稳定 `default` 方法 MAY 存在。插件唯一运行期入口为 `PluginContext` 及插件面 Capability。
- **L2B** MUST 持有 `CapabilityRegistry`、Query/Command Gateway、插件容器、Outbox/Inbox 协调、策略拦截器和健康聚合。
- **L2C** MUST 持有基础设施 SDK、连接/客户端、协议映射和厂商配置。
- `platform-commons` MUST NOT 成为共享业务逻辑或边界绕行的“杂物层”；每个模块 MUST 声明 owner、layer 和提供的 Capability/平台服务。

### 3.4 开源与商业边界

OSS 仓 MUST 可独立构建、测试和发布，且 MUST NOT import、依赖、反射加载或在测试夹具中引用商业 artifact。商业仓 MUST 只通过已发布且锁定版本的 OSS artifact 消费开源能力；本地联调 MAY 使用受控的 composite build，但发布依赖 MUST NOT 使用未发布的工作区引用。

### 3.5 Java 运行模型

v3.0.11 冻结为：

1. 后端插件在构建期进入同一 Spring Boot classpath / `BOOT-INF/lib`；
2. 一个 Host 进程使用一个应用 ClassLoader，不为每插件创建隔离 ClassLoader；
3. BOM 和依赖收敛门禁 MUST 保证同一进程只解析一套平台关键库；
4. Start / Drain / Stop 只控制注册、流量、订阅、任务和受管资源；类仍留在 ClassLoader 中；
5. 插件版本更新、增加、删除和类路径变化 MUST 重启 Host；
6. MUST NOT 把逻辑停机描述为 hot unload、热升级或安全隔离；
7. 需要独立故障域、独立扩缩容、依赖隔离或不可信扩展时 MUST 部署为独立 Host/进程。

多 ClassLoader、OSGi/PF4J 式热插件不属于本基线；如未来引入，MUST 新 Major RFC，MUST NOT 作为 v3.0.11 的隐藏备选实现。

## 4. Capability Contract

### 4.1 插件面与平台内部面的硬边界

插件面 L2A Capability 目录如下。目录只表示接口由平台治理，不表示每个 Host 都 MUST 提供：

| 类别 | 插件面 Capability |
|---|---|
| 消息与协作 | `EventBusCapability`、`CommandCapability`、`QueryCapability` |
| 数据与状态 | `PersistenceCapability`、`StateStoreCapability`、`StorageCapability`、`LockCapability` |
| 外部集成 | `ExternalHttpCapability`、`NotificationCapability`、`SearchCapability`、`AnalyticsCapability` |
| 平台服务 | `AuthCapability`、`PasswordCapability`、`TenantContextCapability`、`ConfigCapability`、`SecretCapability`、`ObservabilityCapability`、`IdGeneratorCapability`、`SchedulerCapability` |

以下对象是 L2B / 平台内部服务，MUST NOT 出现在插件可依赖的 L2A artifact 中：

- `CapabilityRegistry` 及其注册/枚举/状态接口；
- `PluginQueryGateway`、`PluginCommandGateway`、路由表和代理实现；
- Outbox/Inbox Dispatcher、CDC/轮询实现；
- `AdminCapability`、原生 SQL/迁移执行器；
- `ImpersonationCapability` 和身份代理执行器；
- Host Profile Validator、Plugin Container、内部 AOP/拦截器。

`ImpersonationCapability` MUST 仅由经登记的平台内部模块使用，并受授权来源、理由、时限、目标范围、Trace 和不可变审计约束。它不是业务插件的“可选扩展能力”。

### 4.2 三个正交维度

每个 Capability MUST 同时表达：

| 维度 | 取值 | 权威来源 | 失败语义 |
|---|---|---|---|
| 绑定类型 | `runtime-native` / `adapter-backed` | Capability Catalog | 无匹配 Provider 则按必备性/依赖性失败 |
| Host 必备性 | `required` / `optional` | Host Profile | Host required 缺失则 Host 启动失败 |
| 插件依赖性 | `required` / `optional` | Plugin Manifest | 插件 required 缺失则插件 Resolve 失败；optional 缺失允许降级 |

“不同 Host 契约一致”只表示它们识别同一个 Capability ID、契约和错误语义；不表示每个 Profile 提供完全相同的 Capability 集。插件 MUST 基于声明的能力可用性运行，MUST NOT 检查 `hostType == EMBEDDED` 等宿主模式。

`runtime-native` 的 Provider 实现 MUST 仅位于 L2B；`adapter-backed` 的底层 Provider 实现 MUST 仅位于 L2C，插件仍只拿到 L2B 注入的策略代理。Query/Command Gateway 是 `runtime-native`；它们使用的消息/持久化传输属于内部依赖，不改变公开绑定类型。每项基础设施能力的 `bindingKind` MUST 在 Capability Catalog 显式登记，缺失时 MUST fail-fast。业务插件 MUST NOT 提供新的平台 Capability 或借此建立跨插件旁路；领域扩展 MUST 使用版本化 Query、Command 或 Event。新增平台 Capability MUST 先进入 Capability Catalog 并按根级 RFC 评审。

### 4.3 版本模型与解析

所有 Manifest 使用唯一的 **Brix Range v1**，MUST NOT 沿用 npm/Maven 各自的隐式语义：

- 允许精确 SemVer（`1.2.3`）或空格连接的比较器交集（`>=1.2.0 <2.0.0`）；
- Range MUST NOT 使用 `^`、`~`、wildcard、逗号并集、`latest` 或省略 patch；
- prerelease 只有在 range 显式包含同一 prerelease core 时才匹配；build metadata 不参与 precedence；
- 空 range、无法解析、下界不小于上界或跨 Major 的隐式推断 MUST fail-fast；
- JSON Schema、Java/TypeScript parser 和兼容测试 MUST 共用同一组官方 test vectors。

每个 Host 进程通过 BOM 解析一个精确的 L2A artifact 版本。除此之外：

1. 每个 Capability 契约 MUST 声明 `capabilityId`、`contractVersion` 和 `bindingKind`；
2. Plugin Manifest MUST 声明构建时精确 L2A `compiledAgainst`、可运行 L2A artifact range，并为每个 required/optional Capability 声明 Brix Range v1；
3. Capability Provider Descriptor（L2B built-in 或 L2C Adapter Manifest）MUST 声明实现的 Capability 和受支持 contract range；
4. Host Profile MUST 为每个绑定声明唯一 Provider artifact 及其质量/安全属性；
5. 解析成功条件是 Host 的精确 contract version ∈ Plugin range ∩ Provider supportedRange；
6. 同一 `capabilityId` 有多个候选 Provider 且未声明唯一选择策略时，Host MUST fail-fast；
7. 版本字符串缺失、无法解析或跨 Major 不兼容时 MUST fail-fast，MUST NOT “尽力启动”。

仅比较“Adapter Minor ≥ Contract Minor”不足以证明兼容，MUST NOT 作为唯一校验。

L2A artifact version 只标识一组打包契约，MUST NOT 替代各 Capability 的 `contractVersion`。CI MUST 证明 `compiledAgainst` 存在于声明的 L2A range，并对实际选中的精确 L2A 版本运行 ABI/契约测试。

### 4.4 兼容性与弃用

公共 Capability、Query、Command、Event 和 Manifest Schema 均遵循：

- Patch：修正文档、错误码说明或不改变可观察语义的缺陷；
- Minor：MUST 仅允许向后兼容扩展；Java 接口新增行为 MUST 仅通过有稳定默认语义的 `default` 方法、扩展子接口或新接口完成；
- Major：删除、重命名、收紧输入、增加必填项、改变字段/错误码语义或改变一致性承诺；
- DTO / Schema 新字段 MUST 可选并具有明确缺省语义；
- 已发布枚举 MUST NOT 假设 closed world；消费者 MUST 对未知值 fail-safe；
- 弃用项 MUST 标注替代项、引入版本、弃用版本和移除版本；
- 移除 MUST 仅进入下一 Major，且弃用期 MUST 至少覆盖两个 Minor release train 和六个月二者中的较长者；安全漏洞经安全 RFC 可缩短，但 MUST 提供迁移说明；
- CI MUST 对上一个活动版本和仍在支持期内的最老版本执行二进制/API/Schema 兼容性测试。

### 4.5 PluginContext：唯一能力入口

L2A 固定以下语义，实际签名 MUST 由版本化 API artifact 和契约测试共同证明，MUST NOT 写“以实现代码为准”：

```java
public interface PluginContext {
    <C> C require(Class<C> capabilityType);           // 仅 Manifest required 可见
    <C> Optional<C> find(Class<C> capabilityType);    // 仅 Manifest optional 可见
    PluginIdentity pluginIdentity();
}
```

- 未声明的 Capability 请求 MUST 抛出 `BrixCapabilityException(errorCode="capability.undeclared")`；
- required 缺失在 Resolve 阶段失败，MUST NOT 拖到首次业务调用；
- optional 缺失返回 `Optional.empty()`，插件 MUST 有显式降级行为；
- 插件 MUST NOT 注入/访问 `ApplicationContext`、`BeanFactory`、Registry、反射或静态全局对象来获取 Capability；
- Capability 代理 MUST 注入 plugin identity、tenant/actor context、Trace 和策略，MUST NOT 信任插件自报身份。

### 4.6 统一错误模型

v3.0.11 唯一错误模型为 **unchecked exception + 稳定错误码**：

```java
public abstract class BrixException extends RuntimeException {
    private final ErrorCode errorCode;
    private final String traceId;

    protected BrixException(
            ErrorCode errorCode, String traceId, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = java.util.Objects.requireNonNull(errorCode);
        if (traceId == null || traceId.isBlank()) {
            throw new IllegalArgumentException("traceId must not be blank");
        }
        this.traceId = traceId;
    }

    public final ErrorCode errorCode() { return errorCode; }
    public final String traceId() { return traceId; }
}
```

- 所有 Capability 的预期失败 MUST 使用 `BrixException` 的稳定子类；
- `BrixQueryException`、`BrixCommandException` 等 MUST 继承 `BrixException`；
- 业务语义“未找到”使用 `Optional.empty()`，超时、熔断、拒绝、Provider 缺失、序列化失败 MUST NOT 伪装为未找到；
- L2B MUST 将未预期的 `RuntimeException` 映射为 `platform.unknown`，内部保留 cause/stack，跨插件或公网边界 MUST NOT 泄露原始堆栈、内部类名和敏感消息；
- 事务 MUST 对 `BrixException` 回滚；MUST NOT 再使用“受检查异常”或“checked-style”描述该模型；
- 错误码目录是版本化契约，命名为 `{capability}.{reason}`，删除或改变语义属于 Major 变更。
- 若调用进入错误边界时没有活动 Trace，L2B MUST 先创建可关联的 Trace/Correlation ID；`traceId()` 因而始终返回非空、非空白值。

### 4.7 Capability 特殊边界

| Capability | MUST 暴露 | MUST NOT 暴露 |
|---|---|---|
| EventBus | 版本化事实事件发布；Runtime 管理订阅 | Producer/Consumer、Topic、Broker SDK、绕过 Outbox |
| Command | typed 异步命令提交与 receipt | 跨插件数据库写、伪装为 Event、无幂等键重试 |
| Query | typed 只读客户端 | 字符串 target/query、写副作用、直接读对方存储 |
| ExternalHttp | Manifest allowlist 内的外部服务调用 | Brix 插件地址、任意 URL、裸客户端、默认无限重试 |
| Persistence | 绑定 plugin identity 的 Repository/Unit of Work | `DataSource`、`Connection`、`JdbcTemplate`、原生 SQL、跨插件 schema |
| Auth | 当前已验证主体与授权判定 | JWT 私自解析、`actAs`、跨租户切换、密钥 |
| TenantContext | Runtime 已解析的 tenant/scope context 和平台策略 claim | 租户列表、成员/配额/生命周期读写或其他租户领域 CRUD |
| Password | policy-driven hash/verify/needsRehash | 固定算法、参数或明文跨边界传输 |
| Config | 已声明、非敏感、类型化配置 | 环境变量/文件直读、secret 值、全局任意 key |
| Secret | 授权后的短生命周期 secret/credential handle | Manifest 默认 secret、日志输出、长期静态缓存 |
| Observability | 有界业务 metric、结构化事件、当前 context | 初始化 SDK、任意高基数 label、敏感 baggage |

`ExternalHttpCapability` 的目标 MUST 来自与插件 Manifest 对照的外部服务目录。Runtime MUST 拒绝解析到本 Host 的插件端点，防止绕过 Query/Command。

密码算法和参数属于安全 Profile，根蓝图不固定 BCrypt、Argon2id 或 PBKDF2；实现 MUST 支持算法标识、参数升级和 `needsRehash`。

`TenantContextCapability` MUST 仅提供请求上下文和隔离策略所需的已解析信息；任何租户领域数据读取、成员/配额查询或状态变更仍 MUST 走租户插件的 typed Query/Command/Event。

### 4.8 启动解析顺序

Host MUST 严格执行：

```text
H0  baseline/profile/schema/signature validation
 -> H1 classpath convergence + exact L2A version
 -> H2 required Capability binding + adapter quality/security validation
 -> H3 composition required plugins/capabilities + dependency DAG
 -> P1 plugin manifest/contract/handler bidirectional validation
 -> P2 plugin required/optional dependency resolution
 -> P3 wire and start plugins
 -> H4 aggregate readiness
```

| 阶段 | 失败处置 |
|---|---|
| H0/H1/H2 | Host 启动失败 |
| H3 required | Host 启动失败；optional composition item 仅告警并不装载 |
| P1 | 该插件 Resolve Failed；若属 composition required 则升级为 Host 失败 |
| P2 required | 该插件 Resolve Failed；optional 缺失记录降级 |
| P3 初始启动 | 失败插件停止并清理；composition required 插件失败则 Host 启动失败、MUST NOT 宣告 Ready，并以非零状态退出；optional 插件失败仅告警且不装载 |
| 运行期已启动插件失败 | 先隔离入口并清理；required 插件失败使 Host readiness=false，但不把可恢复依赖故障误判为 liveness 失败 |
| H4 | readiness 为 false；liveness 不因可恢复依赖失败而失败 |

Production Profile MUST 拒绝开发型 Adapter、占位 secret、未知/未签名插件、未锁定依赖和不符合最低可靠性/安全属性的绑定。

## 5. Plugin Contract

### 5.1 Manifest 是声明性 SSoT

每个插件 MUST 在固定资源路径 `META-INF/brix/plugin-manifest.yaml` 提供符合当前 JSON Schema 的唯一 `plugin-manifest.yaml`。其他路径或 JSON/YAML 双份声明 MUST 使构建失败。最小顶层结构为：

| 段 | 规范语义 |
|---|---|
| `apiVersion` | Manifest Schema 版本 |
| `metadata` | 唯一 plugin id、SemVer、vendor、license、外置 attestation identity 引用 |
| `runtime` | 精确 `compiledAgainst`、支持的 Runtime/L2A Brix Range v1 |
| `modules` | 每个 artifact 的 `moduleKind` 与坐标 |
| `capabilities.required/optional` | Capability ID + version range |
| `queries.provides/consumes` | Schema、版本、required/optional availability |
| `commands.provides/consumes` | Schema、唯一 handler、幂等和授权策略 |
| `events.publishes/subscribes` | Schema、可靠性、handler、重试和幂等策略 |
| `externalServices` | ExternalHttp allowlist、认证策略引用和预算 |
| `data` | schema owner、全局唯一 `storageId`、migration location、outbox/inbox 资源 |
| `permissions` | 插件权限目录 |
| `config` | key、type、default、敏感级别；secret MUST NOT 有值默认项 |
| `ui` | Web/Mobile 入口、运行时范围和契约版本 |

Manifest 是依赖和路由的权威来源；Handler 注解/注册代码只负责绑定。CI/启动期 MUST 做双向一致性检查：Manifest 声明无 Handler、代码 Handler 无声明、Schema/版本不一致均失败。

Manifest MUST 仅引用外置 attestation identity，MUST NOT 嵌入其所在 JAR/ZIP 的最终 digest、签名、SBOM 或 provenance。制品完成后由发布系统对 raw bytes 求 digest，并在外置、签名的 attestation 中绑定 artifact identity。

### 5.2 模块角色

对含后端的官方/商业插件，`api`、`core`、`server` MUST 分别成为三个物理 Maven artifact；`shared-contract`、`ui-web`、`ui-mobile` 按插件形态 MAY 存在：

| `moduleKind` | 职责 | 约束 |
|---|---|---|
| `plugin-api` | 插件公共 Schema/生成入口 | 零实现、零框架运行期依赖 |
| `plugin-core` | 领域与应用逻辑、数据模型、Repository contract | 无传输层、无 L0/L2B/L2C |
| `plugin-server` | Endpoint、Handler、插件 entrypoint | 只暴露本插件；仍 MUST NOT 接触基础设施 |
| `shared-contract` | 由同一 Schema 生成的多语言 DTO/事件/权限 | 不承载 Java 与 TypeScript 共用运行时代码 |
| `ui-web` / `ui-mobile` | 对应端 UI | 遵循 §9 |

命名后缀 `{name}-api/-core/-server/...` 是 SHOULD，`moduleKind` 元数据才是机器判定依据。Guard MUST 基于元数据、artifact 图和包规则，MUST NOT 只靠目录名猜层级。

仅 UI、仅后端等插件 MAY 省略不适用端，但 MUST NOT 把两个必需后端角色合并为一个 artifact。第三方同进程插件执行同一规则。

### 5.3 插件 SPI 与发现

每个后端插件的 `plugin-server` MUST 通过 Java `ServiceLoader` 发布且只发布一个 `BrixPlugin` provider；L2B 使用 Thread Context ClassLoader 发现。SPI 语义为：

```java
public interface BrixPlugin {
    void onStart(PluginContext context);
    void onStop();
    BrixHealth health();
}
```

- Runtime MUST 根据 ServiceLoader provider 所在 artifact 关联唯一 Manifest；SPI MUST NOT 再手写版本、依赖、路由或 descriptor 形成第二 SSoT；
- `onStart` / `onStop` MUST 有超时且 MUST NOT 创建未受 Runtime 管理的无限线程、scheduler 或 shutdown hook；
- Runtime MUST 追踪插件注册的 endpoint、subscription、query/command provider、task 和资源，以便 Drain/Stop；
- 插件内部可使用框架，但 MUST NOT 通过容器 API获取 Capability 或其他插件对象；
- 发现机制是本版本实施决策；改成 Spring component scan、动态 JAR loader 或每插件 ClassLoader 需要 RFC。

### 5.4 生命周期与 Readiness

Plugin 生命周期与 CapabilityRegistry 生命周期是**两个独立状态机**：

```text
Plugin: DISCOVERED -> RESOLVED -> WIRED -> STARTED -> DRAINING -> STOPPED
        any nonterminal state -> FAILED -> STOPPED

CapabilityRegistry (L2B internal): INIT -> DISCOVERED -> RESOLVED -> WIRED -> READY -> DRAINING -> STOPPED
```

CapabilityRegistry 在进入 `READY` 前失败 MUST 终止 Host 启动；进入 `READY` 后出现不可恢复的 Registry 不变量破坏时 MUST 先使 Host readiness=false，再执行 `DRAINING -> STOPPED` 并以非零状态退出。普通 Provider 暂时失效按下述 readiness 规则处理，MUST NOT 伪造 Registry 状态回退。

Readiness 是独立、可反复变化的条件：

```text
pluginReady = lifecycle == STARTED
              && required capabilities healthy
              && required query/command providers available
              && plugin health in {UP, DEGRADED}

hostReady = registry == READY
            && every composition.required pluginReady
```

- required Provider 在运行期丢失时，依赖插件 readiness MUST 变为 false；恢复后可重新为 true，无需伪造生命周期回退；
- optional Provider 丢失不改变 readiness，调用时返回明确 `PROVIDER_MISSING`；
- `BrixHealth` 只有 `UP / DEGRADED / DOWN / UNKNOWN` 四值；`DEGRADED` 保持 Ready 但 MUST 告警，`DOWN` 和 `UNKNOWN` 阻断插件 Ready。每个后端插件 MUST 实现 health，不存在空值或缺省绕过；
- Drain MUST 先摘除入口/Provider/订阅并停止接收新任务，再等待 in-flight 到配置上限，最后 `onStop`；
- 超时后 Runtime MAY 强制完成逻辑停止并告警，但 MUST NOT 声称线程、类或内存已被强制隔离；
- 插件停止 MUST NOT 导致无依赖插件退出或 Host JVM 崩溃；声明依赖它的插件可变为 not-ready，这是有界级联，不违反独立性。
- `FAILED` MUST 在受管资源清理后进入 `STOPPED`；`STOPPED` 在当前 Host 进程中是终态。启动期每个插件最多调用一次 `onStart`；重新启用、失败重试或再次 `onStart` MUST 重启/滚动部署 Host，MUST NOT 把状态回拨，也不代表重新加载 class。

### 5.5 插件依赖图

- 插件 MUST NOT 依赖另一个插件的 core/server artifact；
- required 同步 Query 依赖 MUST 形成 DAG，循环在构建期/启动期失败；
- Command/Event 不创建启动顺序依赖，但 Schema 依赖 MUST 可解析；
- MUST NOT 用 `startup-order` 掩盖循环依赖；启动顺序 MUST 仅由声明图拓扑计算；
- composition required/optional 表示产品完整度，不改变契约 required/optional 的技术含义。

## 6. 跨插件通信与可靠消息

### 6.1 唯一通信决策表

| 需求 | 唯一通道 | 语义 |
|---|---|---|
| 读取另一个插件拥有的数据 | typed Query | 同步、只读、可失败 |
| 要求另一个插件尝试状态变更 | typed Command | 异步、单一逻辑 Owner、可接受/拒绝、可靠投递 |
| 公布已经提交的事实 | Integration Event | 异步、零到多订阅方，不指挥订阅方 |
| 调用 Brix 之外服务 | ExternalHttp | allowlist、认证、超时、幂等预算 |
| 插件内部行为 | 内部方法/Domain Event | 不成为平台跨插件契约 |

插件 MUST NOT 直接调用另一个插件 endpoint、repository、service 或写库。Integration Event MUST 使用过去式事实命名；`CreateXRequestedEvent` 等定向意图 MUST 改为 Command。多步骤流程由显式 Process Manager/Orchestrator 发 Command、观察 Event，不使用分布式事务。

### 6.2 Typed Query

1. Provider 发布版本化 Query Schema；Consumer Manifest 声明 required/optional 并依赖生成客户端；
2. Query MUST 无副作用，MUST NOT 发布业务事件、写状态或延长事务；
3. Provider MUST 仅读取自己拥有的数据；Consumer 不感知其存储实现；
4. “ReadModel”是公共只读 DTO/port，不强制物理 CQRS 投影或独立数据库；简单场景 MAY 读取 Provider 自有权威存储；
5. 物化投影 SHOULD NOT 成为默认实现；当读写负载、复杂聚合或独立扩展收益有证据时 MAY 建立，并 MUST 声明延迟、重建和补偿；
6. 每个 Query 合约和 Host Profile MUST 分别声明请求 deadline 与平台硬上限；缺省、零、负数、超过平台上限或无界值 MUST fail-fast；
7. Runtime MUST 执行鉴权、Trace、bulkhead、deadline、熔断和有界重试；非幂等链路 MUST NOT 自动重试；
8. “未找到”返回 empty；Provider 缺失、超时、拒绝、熔断和序列化错误抛稳定异常；
9. required Provider 的解析/运行期语义按 §5.4，optional Provider 调用失败不影响插件 Ready。
10. 在同 JVM 调用时，Runtime MUST 挂起调用方写事务和事务资源，在 Provider Owner context 中创建独立 read-only Unit of Work；MUST NOT 传播调用方写锁、EntityManager/Session 或连接。

字符串 `targetPlugin/queryName` API MUST 仅存在于 L2B 内部 Gateway，MUST NOT 位于 L2A 或生成客户端。

### 6.3 Typed Command

跨插件 Command 在 v3.0.11 固定为**异步可靠命令**：

- 每个 Command 有唯一逻辑 Owner/handler、schemaVersion、commandId、idempotencyKey、issuer、scope、correlation/causation context；
- 每个 Command MUST 先持久化到发送方 canonical outbox；有活动 Unit of Work 时加入该事务，没有活动 Unit of Work 时 Runtime 为发送方创建仅持久化 Command 的本地事务；
- `submit()` 返回 `CommandSubmission{commandId, durableReceipt: CompletionStage<CommandReceipt>}`，而不是提前声称 durable 的 Receipt；
- 有外层 Unit of Work 时，`durableReceipt` MUST 在 after-commit 才完成，rollback 时 MUST 异常完成；没有外层 Unit of Work 时，Runtime 开启短事务，commit 后返回已完成的 stage；
- `CommandReceipt{commandId, persistedAt, status=QUEUED}` 只表示 durable acceptance，不表示 Owner 已接受或业务完成；commit 前 MAY 观察到 `PENDING_COMMIT` 的 Submission 状态，但 MUST NOT 将其序列化为 durable Receipt；
- Owner 可通过结果 Event 或可查询状态表达完成/拒绝；
- Handler MUST 使用 `(handlerId, commandId)` Inbox 唯一键，并在同一 Owner 本地事务内写去重记录、变更自身数据及需要的结果 Event outbox；业务幂等另以 `(handlerId, idempotencyScope, idempotencyKey)` 保留结果，重复提交 MUST NOT 重复产生副作用；
- Runtime MAY 重试，但 MUST 保持 commandId/idempotencyKey，使用退避、jitter 和总预算；
- 需要同步响应的用户请求应调用当前插件自身应用服务；MUST NOT 引入跨插件同步写或跨插件事务。

### 6.4 Integration Event

Integration Event 是已提交事实，可靠性分为：

| 级别 | 适用 | 发布保证 |
|---|---|---|
| `CRITICAL` | 资金、权限、库存、关键状态等，丢失导致严重不一致 | MUST 使用 transactional outbox；最高恢复/告警 SLO |
| `STANDARD` | 需要最终送达的普通业务事实 | MUST 使用 transactional outbox；标准恢复/告警 SLO |
| `BEST_EFFORT` | 丢失可接受且不影响业务正确性的遥测/非关键提示 | MAY 直接发布；MUST NOT 驱动正确性关键状态 |

Runtime MUST 仅对 CRITICAL / STANDARD 声明 at-least-once；BEST_EFFORT MUST NOT 宣称 at-least-once。Brix 不承诺 Exactly Once。

事件 envelope MUST 包含：`eventId`、`eventType`、`schemaVersion`、`occurredAt`、`producerPluginId`、`scope`、条件必填的 `tenantId`、`correlationId`、`causationId`、W3C trace context、`partitionKey` 和 `payload`。`eventId` 同时是该事件投递/去重的唯一 message identity，relay 重试或同一事件重放 MUST 保持不变；语义上新发生或修正发布的事实 MUST 使用新 eventId。`scope=TENANT` 时 tenantId MUST 非空；`scope=PLATFORM` 时 MUST NOT 伪造租户归属。

### 6.5 可靠消息 Outbox、Inbox 与所有权

正确的事务边界是“业务写 + outbox record”同一**本地数据库事务**，不是“业务写 + broker send”同一事务：

1. CRITICAL / STANDARD Event publish 在没有活动本地事务时 MUST fail-fast；Command submit 的无事务路径 MUST 按 §6.3 建立专用本地 outbox 事务；
2. Plugin Manifest 的 `storageId` MUST 匹配 `[a-z][a-z0-9_]{0,30}`、全局唯一且发布后不可变；插件拥有自己 schema 中的 canonical `{storage_id}_outbox` / `{storage_id}_inbox` 表及 migration，MUST NOT 从含连字符的 pluginId 临时转义生成表名；
3. L2B relay 是受托平台服务，只获得 outbox/inbox 所需最小权限，MUST NOT 读取插件业务表；
4. Relay 在提交后发送，可能重复；Event Consumer MUST 以 `(handlerId, eventId)`、Command Handler MUST 以 `(handlerId, commandId)` 持久化去重，并将去重记录与业务副作用放在同一本地事务；
5. 表结构、唯一约束、保留期、清理和失败恢复 MUST 有版本化平台 Schema；
6. 顺序保证 MUST 仅声明到相同 `partitionKey`/aggregate 范围，MUST NOT 声称全局有序；
7. 重试耗尽进入 DLQ/parking lot，MUST 可观测、可审计、可人工重放；Event 重放 MUST NOT 改变 eventId，Command 重放 MUST NOT 改变 commandId；
8. 启动校验“Adapter 支持 Outbox”只是必要条件；事务内发布测试、故障注入和重复消费测试同样是发布门禁。

### 6.6 声明与 Handler

Manifest 声明“订阅什么、可靠性、重试/幂等策略和 Handler ID”；代码实现业务 Handler。`@EventHandler` / `@CommandHandler` MAY 作为绑定注解，但 MUST 与 Manifest 一一匹配。MUST NOT `@KafkaListener`、`@RabbitListener` 或 Topic 字符串进入插件代码。

## 7. 数据所有权、持久化与事务

### 7.1 数据所有权

- 每张业务表、对象集合、缓存 namespace 和搜索索引 MUST 有且只有一个 Owner Plugin；
- Owner 是唯一 MAY 写业务数据的主体；其他插件 MUST 仅通过 Query、Command 或 Event 协作；
- MUST NOT 跨插件外键、跨插件 ORM 关联、共享写表和直接 JOIN 对方业务 schema；
- 平台审计、Outbox/Inbox、迁移元数据等平台受托表 MUST 在 Schema 注册表显式登记，不构成任意跨表访问授权；
- 插件删除/停用 MUST NOT 擅自删除其他 Owner 的数据；数据生命周期由 Owner 和专项合规规则治理。

每张表仍 MUST 有且只有一个 Owner。L2B relay、审计写入器或 migration runner MUST 仅作为 Manifest/Contract Schema Registry 显式登记的 Custodian，按列/操作最小权限访问受托运行表；Custodian MUST NOT 获得插件业务表权限，也不会成为共同 Owner。

### 7.2 PersistenceCapability 边界

插件拥有：

- 领域实体与映射；
- Repository contract 和查询定义；
- 自身 schema 的版本化 migration；
- 本地事务边界、Outbox/Inbox 记录和数据兼容策略。

Runtime/Adapter 拥有：

- 连接池、凭证、驱动、ORM provider、事务协调实现；
- migration runner、schema allowlist、租户/插件 context 注入；
- 超时、指标、慢查询、审计和数据库方言适配。

插件 MAY 依赖平台白名单中的 Jakarta Persistence **映射注解**（如 `Entity/Table/Id/Column/Embedded`）和 Brix 发布的 Repository contract；MUST NOT 依赖 `EntityManager`、`Query`、`NamedNativeQuery`、stored procedure API、数据库驱动、Spring Boot Data starter、Hibernate 厂商 API、`DataSource`、`Connection`、`JdbcTemplate`、原生 SQL执行器或 Flyway runtime。声明式 migration SQL 是受控资源例外，不是运行期原生 SQL 权限；映射注解白名单和 API 黑名单 MUST 由 bytecode/AST 负向测试证明。

### 7.3 事务边界

- 一个业务事务 MUST 只修改一个 Owner Plugin 的业务数据，加上该插件 Outbox/Inbox/审计等受托记录；
- Runtime MUST NOT 向插件暴露跨插件事务或 XA/2PC；
- 跨插件流程通过 Command/Event 达成最终一致，并显式设计补偿；
- Query MUST NOT 加入调用方写事务，也 MUST NOT 获得写锁语义；
- Unit of Work MUST 绑定 plugin identity、tenant/actor context 和 deadline；
- 同一进程内直接方法调用 MUST NOT 被用来偷渡跨插件本地事务。

### 7.4 Migration 治理

1. 已在任何正式/共享环境执行的版本化 migration MUST NOT 修改、重命名或复用版本号；
2. 更改 MUST 仅新增单调 migration；CI MUST 对已发布文件内容哈希校验；
3. migration MUST 声明 owner/schema，跨 owner DDL 失败；
4. 数据冲突 MUST fail-fast 并产出报告，MUST NOT 静默 `DO NOTHING` 掩盖丢失；
5. 发布 MUST 验证 fresh install、从每个仍支持版本升级和失败恢复；
6. rollback 说明是必需的运维资料，但 MUST NOT 以回滚脚本为由改写历史 migration；
7. 破坏性 schema 变更 MUST 采用 expand/migrate/contract，并跨越兼容窗口。

## 8. Host、Profile 与 Composition

### 8.1 Host 是静态组装壳

Host 源码 MUST 仅包含：

- 一个使用 L2B bootstrap API 的启动类；
- 依赖/包清单；
- profile 配置、部署描述和运维端点配置。

Host MUST NOT 包含业务 Service、Controller、Handler、Repository、Capability 实现、数据转换或按插件分支逻辑。手写 `@Configuration/@Bean` MUST NOT 出现在 Host 源码中；平台 Runtime/Adapter 的受测 AutoConfiguration 不属于 Host 业务源码。

Host 构建描述 MUST 组装：

```text
runtime L2B + selected adapters L2C + selected plugins L1
+ platform operational modules + exact BOM/lock data
```

“Host POM 只依赖 Adapter/Commons”是错误实现；Plugin 和 L2B 由 Host 的组装依赖进入最终 classpath。启动类行数 ≤30 是 SHOULD/warning，不是架构正确性的替代指标。

### 8.2 Profile

| Profile | 用途 | 约束 |
|---|---|---|
| Standalone | 独立产品进程 | MUST 满足 composition 的全部 required 能力和生产安全等级 |
| Embedded | 嵌入受信任客户的同一 JVM | 协议/契约相同；能力集合由 Profile 声明，MUST NOT 隐式降级安全；独立进程一律按 Standalone 部署（即使运维上作为 sidecar 共置） |
| Local | 本地开发/测试 | MAY 使用 in-memory/mock/H2；MUST NOT 以 production 启动或发布 |

所有 Profile 使用同一 Capability/错误/Manifest 语义。不同 Profile MAY 提供不同 optional Capability；这不是“能力等价”违例。契约测试 MUST 覆盖 required 核心语义，不要求集合逐项相同。

### 8.3 Composition Manifest

Composition 只描述部署组合，不描述许可或价格：

```yaml
apiVersion: brix.io/composition/v1
metadata:
  id: example
architectureBaseline:
  id: runtime-shell
  version: "3.0.11"
  compatibilityEpoch: 1
hostProfile: standalone-production
l2aContractVersion: "1.2.3"
capabilities:
  required:
    - id: event-bus
      version: ">=1.2.0 <2.0.0"
plugins:
  required:
    - id: app-core
      version: ">=2.0.0 <3.0.0"
  optional:
    - id: app-extra
      version: ">=1.0.0 <2.0.0"
```

required 插件 Resolve/Start 失败则 Host 不 Ready并启动失败；optional 插件失败则不装载并告警。Single Plugin Embedded composition 中该插件 MUST 列为 required。

### 8.4 健康与优雅停机

- startup probe 表示启动流程是否完成；
- liveness MUST 仅表示进程是否不可恢复，MUST NOT 因普通下游故障触发重启风暴；
- readiness 按 §5.4 聚合，并可随依赖恢复而变化；
- 收到停机信号后 readiness MUST 立即为 false，再 Drain，最后退出；
- drain timeout MUST 有平台安全上限并由每个 Profile 显式配置；缺失、非正数或无界值 MUST fail-fast；
- HTTP、Query、Command、Event、scheduler 等入口均 MUST 纳入 Drain 契约测试。

### 8.5 云原生边界

Production Profile MUST 具备配置外部化、无状态扩展、受控状态服务、探针、资源限额、滚动升级、结构化遥测和不可变制品。根基线不要求采用 Kubernetes、Service Mesh、特定云或微服务拆分。

## 9. UI Runtime

### 9.1 唯一分层模型

```text
Page / View / Component
        ↓
Hook（承担 ViewModel：状态与交互编排）
        ↓
Repository（协议 DTO、错误映射、缓存边界）
        ↓
Http/Query Capability
```

“View → ViewModel → Repository”与“Page → Hook → Repository → HttpCapability”是同一模型；前三项是 UI 内部三层，Capability 是外部边界。View MUST NOT fetch/axios、拼 URL 或直接 import Repository；Hook MUST NOT 构造传输 URL；Repository MUST 通过 Runtime 注入的边界调用。

前后端“shared”只共享版本化 Schema 及其生成物，不共享跨语言运行时代码。Schema 是源，Java/TypeScript/Kotlin DTO 均由同一契约生成并做兼容性测试。

### 9.2 共享运行时

- 每个 UI Host MUST 只有一个平台定义的 React realm、Router、State、Auth、Theme、I18n 和 UI contract；
- 官方/同 JS 权限域第三方 UI 插件 MUST 从 `@brix-sdk/shared-runtime-*` 获取平台 Runtime/UI Capability，并将平台关键包声明为 peer dependency；
- 插件 MUST NOT 打包第二份 React/Router 或初始化第二套 Auth/OTel runtime；
- `useEventBus()` 只用于 UI 进程内交互，MUST NOT 替代后端 Integration Event/Command。

### 9.3 Module Federation 裁决

Module Federation 是 Web 动态组合 Profile 的实施机制，不是所有 UI 的架构前提。Federation Profile MUST 满足：

1. React/ReactDOM/Router 配置 `singleton: true`、`strictVersion: true`；
2. 使用平台固定的唯一 `shareScope="default"`；
3. `requiredVersion` 来自前端 BOM，MUST NOT 手写漂移；
4. Federated Remote MUST 配置 `import: false`，由 Host 提供 singleton；仅独立 Standalone 构建 Profile MAY 提供来自同一 BOM 的本地 fallback；
5. Federated Host/Remote MUST NOT 配置 `eager: true`；
6. Host 与 Remote MUST 使用平台生成的 shared 配置；
7. CI 不仅检查 `package.json/pnpm why`，还 MUST 检查 Federation 构建产物/manifest 并运行 React 实例身份测试。

只有要求单实例的关键运行时使用 singleton；普通库 MUST NOT 无差别 singleton。若 UI 与 Host 始终同一发布列车且无需独立部署，SHOULD 使用更简单的构建期组合。

### 9.4 UI 治理与不可信 UI

- 官方和同 JS 权限域第三方插件 MUST 通过 `useUI()` / BrixUI contract 获取受治理组件；
- 专业组件逃生舱 MUST 在 Manifest 声明、通过安全/体积/许可审查并限定适配层；不存在第三方 blanket exemption；
- Module Federation Remote 与 Host 同 JS 权限域，不是安全沙箱；不可信 UI MUST 使用独立 origin + sandboxed iframe + 版本化 message bridge；
- Host MUST NOT 将原始 bearer/refresh token 暴露给 WebView、iframe 或插件 JS；跨边界请求使用受限的 authenticated request bridge 和 origin allowlist；
- 菜单/路由无对应端实现时隐藏入口；MUST NOT 加载空壳或回退到其他端代码。

## 10. 安全、可观测性、韧性与供应链

### 10.1 身份与零信任

- 网络位置、同 JVM、同仓库或“平台插件”身份 MUST NOT 产生隐式信任；每个入口 MUST 有显式版本化 access policy。受保护入口 MUST 认证并按资源授权；匿名入口 MUST 仅来自版本化 allowlist，并且 MUST 执行限流、输入验证、最小响应和安全审计；
- 用户认证 SHOULD 通过标准 OIDC Provider Adapter；Brix 不自建非标准协议；
- Browser/Public Client MUST 使用 Authorization Code + PKCE S256；ROPC MUST NOT 使用，Implicit MUST NOT 用于新实现；
- redirect URI MUST 精确匹配已登记值，MUST NOT 通配或开放重定向；
- ID Token MUST 本地验证签名、允许算法、issuer、audience、expiry/not-before 和 flow-specific nonce；JWT Access Token MUST 另验证 token type/audience/scope；Opaque Access Token MUST 经受信任 Auth Adapter introspection，使用有界缓存并 fail-closed。插件 MUST NOT 自行解析或 introspect Token；
- Refresh Token MUST 使用 rotation 或 sender constraint，并检测重放；scope/audience MUST 最小化；
- 服务到服务调用 MUST 使用 workload identity 或可轮换的非对称客户端身份和 TLS；静态共享 API key MAY 仅用于受限兼容 Profile，且 MUST NOT 有生产默认值；
- 身份代理 MUST 显式授权、限时、限范围、可审计、fail-closed；代理身份与原始 actor MUST 同时保留。

### 10.2 数据保护

- Schema/Manifest MUST 标记 secret、credential、PII、financial/health 等数据分类；
- Observability/serialization Adapter MUST 按分类默认脱敏；插件 MUST NOT 绕过；
- secret MUST NOT 进入源码、Manifest 默认值、普通 Config、日志、Trace baggage、指标 label、URL 或前端 bundle；
- 加密、保留、删除、审计和数据驻留由专项蓝图收紧，根蓝图只规定分类和边界不可绕过。

### 10.3 OpenTelemetry

- L2B/L2C MUST 统一初始化 OpenTelemetry SDK/Exporter；插件 MUST 仅使用 `ObservabilityCapability`；
- 跨 HTTP/Query/Command/Event MUST 传播 W3C `traceparent`/`tracestate`。单一可信因果消息 MUST 使用 extracted remote parent；批处理或多来源处理 MUST 使用 span links；不可信上游 MUST 创建新 root，校验成功后 MAY 添加 link，并 MUST NOT 继承为 parent；
- OTel Adapter/Profile MUST 锁定所采用的 semantic convention 版本；升级按遥测 Schema 兼容流程执行，MUST NOT 随 SDK 升级静默漂移；
- 来自不可信边界的 trace context MUST 校验/清洗；baggage MUST NOT 包含敏感信息；
- 每个边界 Adapter MUST 通过 context inject/extract、producer/consumer/client/server span、错误状态和关键 metric 的契约测试；“OTel 覆盖率”MUST NOT 单独作为证明；
- Metric label MUST 有有界基数；tenantId、userId、eventId、commandId、URL 原值 MUST NOT 作为默认 label；
- 日志 MUST 结构化并可关联 Trace，但 MUST NOT 输出原始凭证、PII 或内部堆栈给外部调用方。

### 10.4 故障隔离与资源预算

- 所有同步边界 MUST 有 deadline、并发上限、bulkhead 和取消传播；
- 重试 MUST 仅用于幂等操作或具有幂等键的命令，并 MUST 有次数/时间预算、指数退避和 jitter；
- 插件线程池、队列、scheduler、缓存和连接使用 MUST 注册到 Runtime 并有配额；
- 单插件异常 MUST NOT 越过受管入口导致进程退出；但同 JVM 无法保证 OOM、CPU 饥饿、`System.exit` 或恶意代码不影响他人；需要这种保证时 MUST 跨进程隔离；
- 降级 MUST 保留错误可见性，MUST NOT 用 empty、200 OK 或 no-op 隐藏 required 能力故障。

### 10.5 软件供应链

每次发布的 Host、Plugin、Adapter 和前端 Remote MUST 满足：

1. 使用锁定依赖和可复现的受控构建输入；
2. 生成覆盖直接/传递依赖、license、版本和 purl 的 SPDX 或 CycloneDX SBOM；
3. 将 SBOM、provenance 与制品 digest 绑定并随制品发布；
4. 由受信任 CI 生成签名制品和不可由普通构建步骤伪造的 provenance；
5. 装配/部署前验证签名、来源、digest、版本范围和撤销状态；
6. 对 secret、license、恶意包、CVE 和依赖混淆执行门禁；
7. 以 SLSA Build L2-compatible 为当前最低目标；L3 是后续增强，不作为本次冻结前置。

制品 digest、签名、SBOM 与 provenance MUST 位于外置 attestation/透明日志并以 artifact identity 关联；MUST NOT 把最终 JAR/ZIP digest 写回其内部 Manifest 形成自引用。

### 11.2 安全红线 S-x

| ID | 唯一含义 | 最低证明门禁 | 失败处置 |

| S-2 | 授权 MUST 在资源 Owner/边界执行，权限来自版本化目录 | static endpoint map + deny-path/IDOR tests | CI 阻断 |
| S-3 | 敏感数据 MUST 分类、最小化、脱敏，MUST NOT 进入日志/Trace/错误 | Schema classification + log/trace DLP tests | CI/安全阻断 |
| S-4 | secret MUST NOT 硬编码、设生产默认值或经普通 Config/前端暴露 | secret scan + profile negative tests + artifact scan | CI/启动阻断 |
| S-5 | 同步/异步资源 MUST 有 deadline、bulkhead、配额和有界重试 | policy static check + load/chaos tests | CI 阻断 |
| S-6 | 公网/消息入口 MUST 验证、限额并使用安全反序列化 | endpoint/serializer lint + fuzz/negative tests | CI 阻断 |
| S-7 | 依赖 license MUST 满足 OSS/商业分发白名单 | SBOM license policy | CI 阻断 |
| S-8 | 已知高危漏洞、恶意包和未锁定依赖 MUST NOT 进入发布 | SCA + lock integrity + exception expiry | CI 阻断 |
| S-9 | Impersonation 仅平台内部、限权限时、保留 actor、完整审计 | artifact boundary + runtime fail-closed + audit test | CI/安全阻断 |
| S-10 | 发布制品 MUST 有 SBOM、digest、签名和可信 provenance | release attestation/signature verification | 发布阻断 |
| S-11 | 未经信任的后端/UI 插件 MUST NOT 进入同 JVM/同 JS 权限域 | admission policy + signature/trust tier + isolation test | 装配阻断 |

### 11.3 证明规则

1. ArchUnit 的证明范围仅限字节码可见结构，不能单独证明方法副作用、SQL 所有权、OTel 覆盖、事务原子性或恶意反射；
2. ESLint 的证明范围仅限被解析源文件的语法/导入，不能单独证明 deployed bundle 的 Module Federation 行为；
3. 文本 grep、`pnpm why`、人工 Code Review 和行数 MUST 仅作为辅助证据，MUST NOT 单独关闭 MUST 红线；
4. 每条红线 MUST 在机器基线登记 rule id、适用 artifact、tool、test、owner 和 enforcement status；
5. 未实现或失效的门禁状态 MUST 是 `missing-blocking` / `failing`，MUST NOT 在蓝图中假称已存在；
6. 暂时无法全自动证明的规则 MUST 有到期的人工审批门禁和 Owner；“建议检查”不是合规证据。

## 12. 版本、冻结与变更治理

### 12.1 冻结门禁

Root Blueprint 从 Freeze Candidate 转为 Architecture Frozen 前 MUST 满足：

1. 没有未裁决 P0、`TBD`、互斥方案或“成熟后再定”；
2. 术语、层次、依赖、生命周期、通信、数据、兼容和红线内部一致；
3. 每个 MUST 映射到 CI、静态检查、启动校验、契约/集成测试或有 Owner/到期日的人工审批；
4. 活动专项蓝图完成冲突扫描；
5. 机器元数据通过 Schema、链接、活动版本和历史引用检查；
6. 架构委员会和安全/SRE 至少各一名 reviewer 批准；
7. 登记 Git commit、内容 SHA-256、批准记录和生效日期；
8. Changelog 记录 supersedes/superseded-by，不修改旧版内容伪造历史。

Architecture Frozen 不要求全部代码已经实现。若实现未通过门禁，`implementationStatus` MUST 保持 `pending` 或 `non-conformant`，MUST NOT 标记 Implementation Accepted / GA。

### 12.2 变更类型

蓝图文档版本与 Capability/Event 等公共契约的 SemVer 是两个维度。v3.0.10 的登记状态只是 `Blueprint`，没有 Architecture Frozen 所需的批准记录和内容哈希；因此本次按评审要求发布不可变的 v3.0.11 Freeze Candidate，用于收敛首个可冻结根基线，不构成对已生效冻结基线的静默破坏。v3.0.11 一旦冻结，后续变更按下表治理：

| 变更 | 流程 |
|---|---|
| 纠错但不改变可观察契约/红线 | Patch RFC + 双人评审 + 新文件版本 |
| 新增向后兼容 Capability/Manifest/红线 | Minor RFC + 架构/安全/SRE评审 + 兼容测试 |
| 改变分层、生命周期、通信、数据所有权、红线语义或破坏兼容 | Major RFC + 迁移计划 + 公示期；`compatibilityEpoch` MUST 加 1，文件版本仍跟随平台发布列车 |
| 已暴露安全漏洞 | 紧急 RFC；可先阻断/修复，24 小时内补记录，7 日内完成评审 |

蓝图一旦发布即不可静默重写。任何修改都 MUST 产生新版本、Changelog 和内容哈希。

`compatibilityEpoch` 是已生效 Frozen 根基线的破坏兼容代际，初始值为 1，MUST 仅单调加 1；它不是文件版本的二选一替代。尚未生效的 Freeze Candidate MAY 递增文档 patch 而不增加 epoch；一旦生效，任何根级破坏变更 MUST 增加 epoch。

### 12.3 红线治理

- A-x 由根蓝图拥有；S-x 由根蓝图与安全委员会共同拥有；专项前缀（T-x、DR-x 等）由对应专项蓝图拥有并在机器注册表登记；
- 专项红线 MUST NOT 复用 A/S 编号或放宽 A/S；
- 红线新增/修改/删除 MUST 与 Guard/测试/人工审批门禁同一 PR 或明确标记 `missing-blocking` 并阻止 Implementation Accepted；
- 任何临时豁免 MUST 包含 rule id、artifact、Owner、理由、风险、补偿控制、到期日和批准人；到期自动失败；
- 架构 Freeze MUST NOT 因 Guard 尚未实现而声称合规；Implementation Accepted MUST 全部门禁有效。

### 12.4 Implementation Accepted

Implementation Accepted 绑定具体代码 commit 和制品 digest，至少要求：

- 全部适用 A/S/专项红线通过；
- Manifest、Schema、codegen、BOM/lock 和升级矩阵通过；
- Host/Profile/Plugin 生命周期、readiness、Outbox/Inbox、Query/Command 和安全负例测试通过；
- SBOM、签名、provenance 和依赖门禁通过；
- 未关闭偏差仅允许在有期限豁免清单中，P0/P1 MUST NOT 豁免进入 GA。

## 13. 明确否决的备选方案

下列不是可选实现，冻结后 MUST NOT 绕回：

| 议题 | 冻结方案 | 被否决方案 | 原因 |
|---|---|---|---|
| 权威关系 | Root > 专项 > 计划 > 代码 | 根/专项并列或“更具体者覆盖” | 防止循环 SSoT |
| 运行模型 | 构建期静态组合、单 ClassLoader、逻辑停机 | 将 Stop 宣称为热卸载/沙箱 | 技术能力不成立 |
| 跨插件写意图 | typed async Command | 用请求式 Event 或内部 HTTP | 明确接受/拒绝和 Owner |
| 业务事实 | Integration Event | 把 Command 命名成 Event | 保持事实语义 |
| 可靠业务消息 | CRITICAL/STANDARD 均 Outbox | STANDARD 仅推荐 Outbox | 否则不能承诺最终送达 |
| 跨插件读取 | typed Query 读 Owner 数据 | 直连 API/表；强制每处物理 CQRS | 保边界且避免过度设计 |
| 错误模型 | unchecked `BrixException` | 模糊“受检查/checked-style” | 对齐 Java/Spring代理和事务 |
| Registry | L2B internal | 放在 L2A 再靠约定 MUST NOT import | 编译边界 MUST 真实 |
| Host | POM 装配 L1+L2B+L2C，源码极薄 | Host POM 只装 Adapter/Commons | 无法形成运行产物 |
| 模块判定 | `moduleKind` 元数据 + 依赖图 | 仅按后缀/目录猜测 | 机器可靠性 |
| 第三方插件 | 同权限域同规则；不可信则隔离 | 同进程第三方放宽规则 | 避免双重安全标准 |
| 微前端 | 有独立部署需求才使用 MF | 所有 UI 默认 MF | 控制复杂度 |
| 密码算法 | 安全 Profile 管理、可升级 | 根蓝图固定 BCrypt 参数 | 保持算法敏捷性 |
| 商业模型 | 移出根蓝图 | 根蓝图定义价格/客户/许可矩阵 | 与运行壳无关 |
