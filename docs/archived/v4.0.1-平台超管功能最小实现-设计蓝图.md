## 0.0 v4.0 升级摘要（以 v3.0 为底稿，按 RFC-002 重基线）

| # | v3.0 决策 | v4.0 决策（强制） | 影响面 |
|---|---|---|---|
| Σ1 | 平台登录 `/platform/login` → `/api/platform/auth/login` → `/login/totp`，前端拿到 Platform Token | 平台控制台是身份认证专项的 `platform-console` 客户端：登录在身份协议面的托管登录页完成，授权码 + PKCE，Token 只在 BFF | 删除 `/api/platform/auth/login`、`/login/totp`；删除前端登录页与 TOTP 页 |
| Σ2 | TOTP 首次绑定 + 每次登录强制 | 每次认证达到 `brix:aal2-phr`（passkey 或硬件安全密钥）；TOTP 只作恢复 | 身份 Owner 增加 passkey 凭证与恢复码 |
| Σ3 | setup 页设置密码 + 绑定 TOTP | 托管设置页登记 passkey（必须）并生成恢复码；密码与 TOTP 可选 | `/api/platform/auth/setup/*` 迁入身份协议面 |
| Σ4 | WebAuthn/FIDO2 列为"不做" | 移出"不做"；仍不做自研认证器与短信 MFA | MVP 范围 |
| Σ5 | 登录锁定由身份 Owner 与 rate limit 负责 | 按根 SECURITY-014：限流、渐进延迟、人机验证，只在发生失败的入口临时锁定 | 平台登录不再锁住该身份在其他入口的访问 |
| Σ6 | — | 新增/撤销超管、重置他人凭证、修改平台安全设置须再验证（`BRX-SA-AUTH-007`） | Endpoint access policy 声明 `acr`/`max_age` |
| Σ7 | Platform Token claim `mfa: "TOTP"` | 改为 `acr`、`amr`、`auth_time`、`sid` | Token 契约 |
| Σ8 | 修改自己密码是 `/api/platform/admins/me/change-password` | 自身凭证（密码、passkey、TOTP、恢复码）在身份协议面的账户安全页管理 | 删除该 Runtime Entry 与 `/platform/me/password` 页面 |

> **不兼容点**：v4.0 删除平台密码/TOTP 登录、setup 与修改自身密码的 Runtime Entry，平台控制台不再持有 Platform Token；兼容代际由 2 升为 3。

## 0.0.1 v3.0 升级摘要（历史；Δ1、Δ2、Δ3 中的登录、setup 与 MFA 部分已被 §0.0 取代）

| # | 历史决策 | v3.0 决策（强制） | 影响面 |
|---|----------|------------------|-----|
| Δ1 | 超管与租户共用 `/api/auth/login` + 前端 `/login` | **超管入口 `/platform/login` → `/api/platform/auth/login`；普通/租户 = `/login` → `/api/auth/login`。前后端 URL、Token、路由守卫严格隔离** | 后端拆控制器；前端两套独立守卫 |
| Δ2 | 新增超管返回明文 `tempPassword`（一次） | **禁止生成默认密码**；新增超管 = 创建 `Identity(PENDING_SETUP)` + 一次性 `setup_token` → 用户在 `/platform/setup` 设密码 + 绑定 Google Authenticator TOTP 才能 `ACTIVE` | 后端去 tempPassword；前端去展示；E2E 改断言 |
| Δ3 | MFA "完整流程" 不做 | **标准 TOTP 进入 MVP**（首次绑定 + 每次登录强制），具体实现由已登记的身份/安全 Owner 契约提供 | `mfa_secret_encrypted` 等字段由身份 Owner 持有；专项不私自新增 Capability |
| Δ4 | `sys_identity.status` 复用 `MemberStatus(PENDING/ACTIVE/...)` | **独立 `IdentityStatus`：`PENDING_SETUP / ACTIVE / LOCKED / DISABLED`**；`PENDING_SETUP` 仅允许 `/platform/setup` 路径 | Identity 实体新增独立 status + Flyway 迁移 |
| Δ5 | `sys_platform_admin.status = ACTIVE / DISABLED` | **`ACTIVE / REVOKED`**：REVOKED 后不再签发 PLATFORM Token，但保留该 identity 的租户身份 | 字段语义重命名 + 登录链断言 |
| Δ6 | `SuperAdminBootstrapRunner` 直接用 ENV 密码创建"正式"超管 | **彻底移除启动期业务写入**：Bootstrap setup code 来自 SecretCapability/安全 Profile，只换取一次性 `BOOTSTRAP_SETUP` session；首位正式超管 ACTIVE 后 Stage B 永久关闭 | 禁止 Runner、onStart 或 Host 初始化创建身份/写状态/发送通知 |
| Δ7 | `platform:bypass` 写进 Token 下发前端 | **删除通用 bypass 权限语义**；平台端、前端和业务插件只使用版本化具体 permission ID | 不 seed、不签发、不检查 `platform:bypass` |
| Δ8 | `LoginResponse.platformAdminMode` 与 `/api/auth/login` 共用 | **删除** `platformAdminMode` 字段；普通 `/login` 永远不返回 PLATFORM Token；同一 identity 即使是超管也必须走 `/platform/login` | enterprise app-identity DTO 清理；E2E 改写 |
| Δ9 | 邮件不强制 | 邮件**仅**用于 setup link / 密码重置 link / 安全通知；**禁止**邮件 OTP 作为生产 MFA | 处理 token 的 Data Owner 经已声明 NotificationCapability 编排投递 |
| Δ10 | v2.0 未覆盖平台创建租户和 FIRST_OWNER 邀请闭环 | 平台控制面只经租户 Owner 内部契约创建 `PENDING_ACTIVATION` 租户并发起/重发/撤销 FIRST_OWNER 邀请 | 平台超管不成为 member、不读取 invitation token、不接受邀请 |

> **不兼容点**：新增超管 API 响应不再含 `tempPassword`，也不返回 raw token、完整或脱敏 `setupUrl`。响应固定为 `{id, identityId, setupLinkSent:true}`；setup link 只能由 token Data Owner 通过受管通知侧信道发送。所有 profile（包括开发、测试）均无 HTTP 调试返回例外。

## 0. TL;DR（执行摘要）

| 维度 | 决策 |
|------|------|
| **能力定位** | Super Admin 是 `platform-commons` 下唯一的 **L2B Platform Operational Module**，`moduleKind=platform-operational`；不是 L2C Adapter、Host 业务代码或 enterprise-solutions 插件 |
| **代码位置** | 后端：`platform-commons/server/platform-admin`（新建）+ 已有 `platform-tenant`（实体） + 已有 `platform-auth`（登录与权限） |
| **声明与发现** | 固定路径 `META-INF/brix/platform-operational.yaml` 是声明性 SSoT；artifact 通过 `ServiceLoader<PlatformOperationalModule>` 发布且只发布一个 provider |
| **入口发布** | `/api/platform/**` 仅由 L2B HTTP Dispatcher 通过同一 Host 入口快照发布；禁止 Spring Controller、Servlet/Filter 或第二套路由表自动发布 |
| **跨 Owner 协作** | 只通过 `OperationalContext` 调用 descriptor 已声明且 privilege allowlist 批准的版本化内部契约；禁止 `AdminCapability` / `PlatformAdminCapability`、Spring Bean/Repository/Service 直注入 |
| **登录入口** | **严格隔离**：平台控制台是身份认证专项的 `platform-console` 客户端，登录在身份协议面的托管登录页完成；租户员工与终端用户使用各自客户端。Token 的 audience 互不相同、互不通用 |
| **首次激活** | **禁止默认密码**；新建超管 = `Identity(PENDING_SETUP)` + 一次性 `setup_token` → 用户在托管设置页登记 passkey（必须）并生成恢复码，密码与 TOTP 可选 → 自动转 `ACTIVE` |
| **认证强度** | 每次认证达到 `brix:aal2-phr`（passkey 或硬件安全密钥）；TOTP 只作恢复；不开发自研认证器；短信、邮件验证码禁止作为平台认证因素 |
| **架构红线** | 业务插件（enterprise-solutions/* / plugins/*）**禁止**依赖 `platform-admin`；超管能力**禁止**反向依赖任何业务插件 |
| **权限模型** | `RoleCode.PLATFORM_SUPER_ADMIN` + 版本化细粒度 permission ID；接口放行只校验具体 Permission，不校验角色名字符串；通用 `platform:bypass` 不存在 |
| **身份模型** | `sys_identity.status ∈ {PENDING_SETUP, ACTIVE, LOCKED, DISABLED}`；`sys_platform_admin.status ∈ {ACTIVE, REVOKED}`；超管 Token `scope=PLATFORM`，**禁止**含 `tenant_id` |
| **Bootstrap** | 不创建可登录 Bootstrap 数据库身份；高熵 setup code 只换取短 TTL、一次性 `BOOTSTRAP_SETUP` session；首位正式超管激活后 Stage B 永久关闭 |
| **MVP 范围** | 平台登录（经身份协议面，passkey）、setup 链接初始化、超管列表/新增/禁用(REVOKE)/重置凭证（生成 setup link）、租户列表与状态变更、审计日志 |
| **不做** | 自定义角色编辑、自研认证器、计费/配额、删除超管、短信通知 |

### 0.1 v3.0.10 重基线结论

1. `platform-admin` 实现 `PlatformOperationalModule`，不是 `BrixPlugin`；`configure(OperationalBootstrapContext)` 只登记 descriptor 已声明的 Handler/Task Factory，`onStart` 不得登记入口、执行业务 Handler或产生业务副作用。
2. 模块严格经过 O0-O8 局部管线并受 Host B0-B3 全局屏障约束；B3/P8/O8 原子提交前所有 Endpoint/Task 保持 `UNPUBLISHED`。
3. 需要 `/api/platform/**` 的 Production Composition MUST 将 `platform-admin` 显式列为 required operational module；Resolve/Start 失败阻断 Host 启动与 Ready。
4. 平台超管无默认业务数据访问权。身份、租户、审计等 Data Owner 通过 `internalContracts.provides` 提供窄契约；`platform-admin` 通过 descriptor 的 `internalContracts.requires` 和 privilege allowlist 获得最小权限。
5. 内部契约调用不得传播 `platform-admin` Handler 的事务、连接、`EntityManager` 或 Session；L2B 代理挂起调用方事务，由 Data Owner 在自身 context 中提交独立本地事务。
6. Bootstrap、平台身份、租户、审计和通知分别由唯一 Data Owner 持有；`platform-admin` 不取得 Repository、Entity、Service、Unit of Work、SMTP Adapter 或通知模板服务。
7. 本次重基线只更新架构约束，未证明实现合规；实施状态保持 `not-assessed`。

### 1.3 与运行壳架构红线对照

#### 1.3a 平台审计内部契约归属

| 分层 | 内容 | 代码库位置 |
|------|------|----------|
| **Data Owner** | 平台审计模块拥有 `sys_platform_audit_log`、Schema、迁移、写规则与生命周期，并通过 descriptor `internalContracts.provides` 声明版本化窄契约 | `brix/packages/@brix/platform-commons/packages/server/` |

| **调用方** | `platform-admin` 在 `platform-operational.yaml` 声明 `internalContracts.requires`，仅通过 `OperationalContext` 获取审计内部契约 | `brix/packages/@brix/platform-commons/packages/server/platform-admin` |

| 蓝图红线 | 本设计是否遵守 |
|---------|-------------|
| 约束 1：平台运维边界 | `platform-admin` 是 L2B `platform-operational`，不向插件暴露超管 Capability |
| 约束 2：插件只依赖 Capability Contract | ✅ enterprise-solutions/* 不感知 `platform-admin` 存在 |
| 约束 3：Host 能力等价 | Standalone / Embedded Host 使用相同 descriptor、O0-O8、Dispatcher、安全链和错误语义；fatal 处置按 Host Profile 区分 |
| 约束 4：插件间事件解耦 | 租户 Owner 在本地事务中按根蓝图事件/Outbox 语义发布 CRITICAL 事实；`platform-admin` 不直接发布 Owner 事件 |
| 约束 5：运行壳复杂度对插件不可见 | ✅ 业务插件无任何超管相关代码 |
| 约束 6：Host 极薄 | Host 仅静态打包并在 Composition 选择 `platform-admin`；不得包含超管业务逻辑或 Controller |
| 约束 7：前后端完全分离 | `platform-admin-web` 走 Page → Hook → Repository → HttpCapability |
| 约束 8：前端运行时唯一真相源 | ✅ `platform-admin-web` 只 peerDependency `@brix-sdk/shared-runtime-web` |
| 约束 9：BrixUI 统一治理 | ✅ 所有页面通过 `useUI()` |

## 2. 模块边界与依赖图

```text
L4 Composition
  └─ operationalModules.required: platform-admin
            │ static assembly
L3 Host ────┴── packages L2B Runtime + platform-admin + selected L2C Adapters
                         │
L2B platform-admin (moduleKind=platform-operational)
  ├─ META-INF/brix/platform-operational.yaml
  ├─ ServiceLoader<PlatformOperationalModule>
  ├─ configure(OperationalBootstrapContext): Handler/Task Factory only
  ├─ /api/platform/** via the unique L2B HTTP Dispatcher
  └─ OperationalContext.requireInternalContract(...)
                         │ descriptor requires + privilege allowlist
                         ▼
L2B Registry internal namespace
  └─ versioned internal contract providers owned by platform-identity,
     platform-tenant and platform-audit

L1 business plugins ──X── platform-admin / operational SPI / internal contracts
L2C adapters         ──X── platform-admin business types
```

## 5. 审计事件与字段

审计动作 ID 属于版本化 contract/api；审计表、迁移、写规则与生命周期只归 `platform-audit` Data Owner。L2B Handler 通过 `PlatformAuditAdministration` 提交类型化审计请求，不得注入 `AuditService` 或 Repository。

最小动作覆盖平台登录成功/失败、setup token 签发/使用/拒绝、passkey 登记/移除、恢复码生成/使用、再验证、身份激活/锁定、超管创建/撤销/重置、Bootstrap session/首位超管/Stage B、租户创建/状态变更和 FIRST_OWNER 邀请发起/重发/撤销。认证类事件的完整清单以身份认证专项 `BRX-IA-AUDIT-001` 为准。

| 字段 | 必填 | 说明 |
|---|---|---|
| `actorIdentityId` | 条件必填 | 已认证平台 actor；匿名 Bootstrap 请求为空 |
| `executionIdentity` | 条件必填 | 使用内部执行器或身份代理时记录，不能覆盖原 actor |
| `action` | 是 | 版本化审计动作 ID |
| `targetType/targetId` | 是/条件必填 | `PLATFORM_ADMIN`、`TENANT`、`INVITATION`、`SELF` 等 |
| `tenantId` | 条件必填 | 仅目标本身是租户事实时作为目标标识；绝不成为 Platform Token tenant context |
| `result/reasonCode` | 是 | 稳定结果与稳定 reason code，不保存 Provider 原始消息 |
| `traceId` | 是 | 由 L2B Error/Trace Boundary 注入 |
| `occurredAt` | 是 | 服务端时间 |
| `ip/userAgent` | 条件必填 | 由批准的请求元数据策略脱敏后提供 |

[BRX-SA-AUDIT-001] 审计不得记录密码、raw token、TOTP code、MFA secret、恢复码、passkey 私密材料、setup code、完整邮箱、完整 URL、通知正文、variables 或 Provider 原始消息。审计失败语义、同步阻断范围及受托写入边界必须由根蓝图和审计 Owner 唯一定义，Handler 不得吞异常或降级为日志。

[BRX-SA-AUTH-001] Platform Token 不得含 `tenant_id`、`member_id`、Actor/Subject context、`platformAdminMode` 或通用 bypass。平台超管即使同时拥有租户身份，也必须通过独立 Actor 登录获得租户 Token。

## 8. 关键业务流程

以下流程中的“Owner internal contract”均指 §2.1 冻结契约；L2B 不共享 Owner 事务或实现对象。

### 8.1 平台登录

```text
平台控制台（未登录）
  -> BFF 发起授权（platform-console 客户端，授权码 + PKCE）
  -> 身份协议面托管登录：先识别账号 -> passkey（本机或跨设备扫码）或硬件安全密钥
  -> 身份 Owner 经 L2A 契约校验 Identity ACTIVE 与有效平台授权
  -> 授权码回到 BFF -> token 端点签发 Platform Token（只存于 BFF 会话）
  -> 控制台经 BFF 会话访问 /api/platform/**
```

任何失败都返回稳定错误并审计；认证未达到 `brix:aal2-phr` 前不签发 Platform Token。先识别账号、失败处置、会话时长等细节以身份认证专项为准。

### 8.2 新增、重置和撤销超管

```text
Platform Handler
  -> PlatformIdentityAdministration
     -> identity Owner local transaction
     -> hash-only setup/reset token
     -> owner-orchestrated managed notification
     -> typed result without secret
  -> PlatformAuditAdministration
```

重置 = 作废该超管的全部凭证与会话并签发新的 setup token，对方须在托管设置页重新登记 passkey。撤销前由身份 Owner 原子校验“不能撤销自己”和“至少保留一位 ACTIVE 正式超管”；撤销只影响平台授权，不改变该 Identity 合法的租户身份。

### 8.3 管理自己的凭证

平台超管在身份协议面的账户安全页管理自己的密码、passkey、TOTP 与恢复码，操作前须再验证；身份 Owner 更新凭证并按策略撤销其他会话。该流程不再是 `/api/platform/**` Runtime Entry；L2B 不取得 hash、MFA secret 或 Token store。规则见身份认证专项 BRX-IA-CRED、BRX-IA-SESSION。

### 8.4 租户创建、状态和 FIRST_OWNER

```text
Platform Handler
  -> TenantAdministration
     -> tenant Owner local transaction
     -> PENDING_ACTIVATION tenant / lifecycle fact / FIRST_OWNER invitation
     -> owner audit + canonical event/Outbox when required
     -> invitation token owner-orchestrated notification
```

请求不得含 `ownerIdentityId`、inviterType、purpose 或审计身份覆盖字段。平台超管不能代用户设密码、查看 invitation token、接受邀请、成为 tenant member 或使用 Platform Token 进入租户上下文。FIRST_OWNER 接受属于租户 Owner 的 Actor 入口，不属于 `/api/platform/**`。

### 8.5 事件一致性

[BRX-SA-TX-001] 一个本地事务只修改一个 Data Owner 的业务数据及其受托审计/Outbox 记录。CRITICAL 事实由该 Owner 按根蓝图 canonical event envelope、Outbox 和 Relay 语义发布；`platform-admin` 不直接构造另一种 Event Envelope，也不把同步调用伪装为领域事件。跨 Owner 调用不传播事务，不使用 XA/2PC。

11. 所有 Endpoint 的 tenantContext 为 forbidden，权限由 Dispatcher 的具体 permission ID 决定。
12. 页面具备 loading/error/empty/403/重复提交阻断/表单校验，且无 direct fetch/axios 或第三方 UI 直引。

## 15. 首次激活与 Bootstrap 详细设计（认证细节见身份认证专项）

### 15.1 身份状态

```java
package io.brix.platform.identity.domain;

/**
 * Lifecycle state of a global identity.
 */
public enum IdentityStatus {
    PENDING_SETUP,
    ACTIVE,
    LOCKED,
    DISABLED
}

/**
 * Lifecycle state of a platform administrator grant.
 */
public enum PlatformAdminStatus {
    ACTIVE,
    REVOKED
}
```

`IdentityStatus` 不得复用租户 `MemberStatus`。PlatformAdmin REVOKED 只撤销平台授权，不修改同一 Identity 的合法租户身份。

### 15.2 Setup token 表语义

下例只定义字段语义，migration 版本号由施工时的 `flyway_schema_history` 决定：

```sql
CREATE TABLE sys_setup_token (
    id          BIGINT PRIMARY KEY,
    identity_id BIGINT NOT NULL REFERENCES sys_identity(id),
    token_hash  VARCHAR(128) NOT NULL,
    purpose     VARCHAR(32) NOT NULL,
    expires_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    used_at     TIMESTAMP WITH TIME ZONE NULL,
    issued_by   BIGINT NULL,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_setup_token_hash UNIQUE (token_hash)
);
```

[BRX-SA-SETUP-001] 明文 token 只存在于创建它的 Owner 的瞬时安全边界，并立即交给受管通知调用；数据库只保存不可逆 verifier/hash。

[BRX-SA-SETUP-002] TTL、hash/verifier 算法、随机源、重签作废和重放保护来自安全 Profile。本文不固定小时数、字节数或算法。

[BRX-SA-SETUP-003] setup token 使用、Identity 激活、MFA 启用和 Stage B 条件关闭必须由身份 Owner 在一个本地事务内原子完成；通知投递不得扩大该数据库事务。

### 15.3 MFA 因子

身份 Owner（platform-identity）持有全部 MFA 因子：passkey 公钥凭证、加密的 TOTP secret、恢复码哈希，以及各自的登记时间与启用状态。加密、KMS/Secret provider、TOTP 参数和时钟窗口由已批准安全 Profile/Capability Contract 提供。L2B Handler、前端和审计永远不取得解密 secret。

### 15.4 创建普通后续超管

```text
POST /api/platform/admins
  -> Dispatcher: Platform Token + platform:admin:create + schema/idempotency
  -> Handler -> PlatformIdentityAdministration.createAdministrator(...)
  -> identity Owner local transaction:
       create Identity(PENDING_SETUP)
       create PlatformAdmin(ACTIVE, PLATFORM_SUPER_ADMIN)
       create hash-only INITIAL_SETUP token
       persist entrusted audit/outbox only where owner contract allows
  -> identity Owner invokes managed NotificationCapability
  -> Handler -> PlatformAuditAdministration
  -> response {id, identityId, setupLinkSent:true}
```

邮件提交失败和事务提交后残余窗口必须只按活动通知专项处理。不得通过返回 URL、日志打印或假通知 Adapter 补偿。

### 15.5 Setup 完成

setup 链接打开身份协议面的托管设置页（身份认证专项 BRX-IA-ONBOARD-001），不再经 `/api/platform/auth/setup/*`：

1. 身份协议面执行限流、Trace 与 CSRF，并经 L2A 契约把 setup token 交给身份 Owner；
2. 身份 Owner 校验 token verifier、purpose、有效期、未消费和未被 supersede；
3. 用户登记 passkey（必须，`userVerification=required`），并生成恢复码；可选设置密码与 TOTP；
4. Owner 本地事务登记 passkey 公钥凭证、恢复码哈希、可选的密码与加密 TOTP secret，将 Identity 置 ACTIVE 并消费 token；
5. 若这是首位正式超管，使用条件更新永久关闭 Stage A 并撤销全部 BOOTSTRAP_SETUP session；
6. 页面只展示一次恢复码，清除内存态后进入平台登录（由 BFF 发起授权）。

### 15.6 正式平台登录

正式平台登录按 §8.1 经身份协议面完成：先识别账号，再用 passkey 或硬件安全密钥认证；身份 Owner 校验 Identity 状态与有效平台授权后，授权码经 BFF 换取 Platform Token。失败处置、会话时长与 Token 有效期由安全 Profile 决定（身份认证专项 §12）。登录成功和失败都写稳定、脱敏审计；Provider 原始错误不得外泄。

### 15.7 Bootstrap 两阶段模型

```text
STAGE_A_OPEN
  -> FIRST_ADMIN_PENDING_SETUP
  -> FIRST_ADMIN_ACTIVE_WITH_MFA
  -> STAGE_B_CLOSED
```

[BRX-SA-BOOT-001] Bootstrap singleton 由版本化前滚 Flyway migration 建立。禁止 `ApplicationRunner`、`CommandLineRunner`、Spring 初始化回调、Host 启动类或 `onStart` 创建 Identity、写业务状态、发送邮件或执行 Handler。

[BRX-SA-BOOT-002] Stage A 同时满足：

1. `sys_bootstrap_state.completed_at IS NULL`；
2. 不存在 Identity ACTIVE/MFA=true 且 PlatformAdmin ACTIVE/PLATFORM_SUPER_ADMIN 的正式超管；
3. required platform-admin、Owner internal contracts、Auth/Secret/Notification 依赖已解析；
4. B3/P8/O8 完成，Bootstrap Endpoint 已在完整入口快照发布。

[BRX-SA-BOOT-003] Bootstrap setup code 来自 SecretCapability/安全 Profile，只保存或比较不可逆 verifier，不创建可登录 Bootstrap 数据库用户。它必须高熵、短期、限流、可轮换，永不进入日志、响应、审计、指标或前端持久化。

[BRX-SA-BOOT-004] 正确 setup code 只能换取短 TTL、一次性的 `BOOTSTRAP_SETUP` session。其 tenant context 为 forbidden，只允许 status/session/create-first-admin；成功消费、过期、重放或 Stage B 后全部失效。

[BRX-SA-BOOT-005] 创建首位正式超管只产生 PENDING_SETUP Identity、ACTIVE/PLATFORM_SUPER_ADMIN grant、hash-only INITIAL_SETUP token、脱敏审计和 Owner 编排通知。不得创建 member，不得返回密码、raw token、完整/脱敏/调试 URL。

[BRX-SA-BOOT-006] 完成 passkey 登记（以及可选的密码、TOTP）和首次验证后，身份 Owner 在同一本地事务中将 Identity 置 ACTIVE、启用 MFA、消费 setup token、条件关闭 Stage A、撤销 Bootstrap sessions 并写受托审计。Stage B 永久；重启、配置重放、代码回滚或重新提供 code 不得重开。

### 15.8 Bootstrap singleton 语义

```sql
CREATE TABLE sys_bootstrap_state (
    id          INTEGER PRIMARY KEY CHECK (id = 1),
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    completed_at TIMESTAMP WITH TIME ZONE NULL,
    completed_by_identity_id BIGINT NULL
);
```

migration 可插入唯一 singleton 行；启动代码不得补写、修复或重建。Stage B 使用 `WHERE id = 1 AND completed_at IS NULL` 的条件更新保证并发唯一胜者，重复请求得到稳定幂等结果或冲突错误。

## 16. 租户、FIRST_OWNER、通知和错误详细规则

### 16.1 租户/FIRST_OWNER 边界

[BRX-SA-TENANT-001] 平台超管只能请求租户 Owner 创建 `PENDING_ACTIVATION` 租户及必要配置。请求体不得含 `ownerIdentityId`、inviterType、purpose 或平台审计身份覆盖字段。

[BRX-SA-TENANT-002] 平台超管只能发起、重发或撤销 FIRST_OWNER 邀请；不能代用户设密码、查看 token、成为 member 或使用 Platform Token 进入租户上下文。

[BRX-SA-TENANT-003] FIRST_OWNER 接受属于租户 Owner 的 Actor 入口。受邀 Identity 必须先完成 Actor 身份验证，再由租户 Owner 校验 invitation token 与当前 identity 绑定。

[BRX-SA-TENANT-004] 租户状态、配额、邀请、Member、Profile、审计和 CRITICAL Event 原子性由活动多租户专项定义；platform-admin 只观察类型化结果和稳定错误。

### 16.2 通知与敏感数据

[BRX-SA-NOTIFY-001] setup、reset 和 FIRST_OWNER 安全链接只能经 NotificationCapability 的受管侧信道发送。任何 profile 的 HTTP 响应、日志、审计、Trace、指标和前端持久化均不得含 raw token、完整 URL、正文或 variables。

[BRX-SA-NOTIFY-002] 不存在 `return-url-for-dev-only`、Logging/Fake 自动装配或控制器调试返回。开发和测试使用 Mailpit、虚拟 SMTP 或受控测试 Adapter，并执行相同脱敏规则。

[BRX-SA-NOTIFY-003] 邮件不是 MFA。SMTP 接受不等于送达；同步 fail-closed 和提交后残余窗口由活动通知专项唯一声明，不得同时保留隐式 Outbox/重试方案。

### 16.3 稳定错误

[BRX-SA-ERROR-001] 预期失败使用继承 `BrixException` 的稳定错误目录，wire code 为 `{capability}.{reason}`。异常只携带 ErrorCode、批准的 safeParameters 和 cause；traceId 由 L2B Error Boundary 注入外部 Envelope、日志和审计。

至少覆盖：Bootstrap 关闭/重放/无效、setup token 无效/过期/已用、MFA challenge 无效、身份状态拒绝、平台授权撤销、最后超管保护、权限拒绝、幂等冲突、Owner contract 不可用和通知提交失败。不得把异常 message、数据库错误或 Provider 原文直接返回。

## 17. 前端路由与交互详细规则

[BRX-SA-UI-001] 所有用户可见流程固定为 `Page → Hook → Repository → HttpCapability`；组件和反馈只经 BrixUI/useUI。Repository 对响应使用显式类型白名单，未知敏感字段应被拒绝并触发安全遥测，而不是渲染。

[BRX-SA-UI-002] Bootstrap session 只保存在完成当前流程所需的最小内存态；setup 与 MFA 流程在托管登录中完成（身份认证专项 BRX-IA-ONBOARD-003）。页面设置 `Referrer-Policy: no-referrer`；不得进入持久化存储、URL 分析、错误上报或埋点。

[BRX-SA-UI-003] 每个 Page/Hook 明确 loading、error、empty、permission denied、重复提交阻断、取消与表单校验。前端 Guard 和权限只改善体验；Dispatcher 始终是最终安全边界。

Platform、Actor、Subject 和 BOOTSTRAP_SETUP Guard 分别消费对应认证上下文。平台登录不得自动跳租户登录，租户登录不得推断或跳转平台身份。
